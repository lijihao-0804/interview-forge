面试问答 B：模型网关、异步可靠性与审批（RT01–RT50）

这一组问题按 2026-11-20 的固定提交回答。“项目落点”是你可以带面试官走读的真实代码；“追问”用于检验理解。示例金额、并发人数和故障场景若未注明，均是教学构造，不能当成已跑出的实验成绩。

RT01｜为什么已经用了 LiteLLM，还要再写一层模型网关？

可以这样回答： LiteLLM 主要解决不同供应商接口的适配，项目网关还需要执行自己的工作区隔离、配置冻结、能力约束、重试与 fallback、流式可见性边界、预算预占和安全观测。这些是应用的业务合同，不能由 SDK 的默认行为代替。把它们集中在一层，也能避免每个 Agent 节点各自写一套错误处理。

项目落点： ModelGatewayService 负责编排；adapter 明确一次调用只做一次 provider attempt，并设置 num_retries=0。网关、adapter

追问： 如果 SDK 和网关各允许 3 次尝试，真实请求数怎么算？你需要先说明 max_attempts 包含首次还是仅重试，并查清每层实际配置，不能凭字段名估计。

RT02｜重试与 fallback 的区别是什么？它们分别应该在哪里实现？

可以这样回答： 重试沿用当前模型配置，fallback 切换到预先允许的备用配置。两者都由统一网关决定，adapter 只执行单次请求。这样才能统一统计次数、校验能力和计算预算。fallback 还可能改变回答质量和工具行为，不能只把它看成另一个网络重试。

项目落点： _generate_chain 和 _stream 的外层遍历 profile，内层处理当前 profile 的尝试次数；冻结计划也包含重试策略。源码

追问： 当前代码是否实现指数退避？这段网关循环没有通用指数退避。若以后补，应明确等待上限、抖动、取消响应和总请求时限，而不是在简历中预先声称完成。

RT03｜为什么不对所有异常无条件重试？

可以这样回答： 无条件重试会把配置错误、权限错误和输出契约错误变成重复费用与延迟；对外部写动作，还可能重复业务副作用。重试需要具体的错误分类、次数上限、当前可见输出状态和幂等条件。同一个 timeout 在纯查询、模型生成与外部创建订单中，允许的恢复方式并不一样。

项目落点： 网关区分 retryable，流式已可见后拒绝透明替换；ActionRuntime 对无法确认的外部结果保留 UNKNOWN_OUTCOME。网关、动作执行

追问： 不可重试的网关错误是否一定禁止 fallback？不一定。结束当前 profile 的内层重试与结束整条链是两回事，要读实际外层控制流。

RT04｜为什么流式输出已有内容之后不能无感切换备用模型？

可以这样回答： 因为用户已经观察到一部分结果，这部分内容有既定来源。再拼接另一个模型的输出可能前后矛盾；工具调用 JSON 的增量更不能混接。系统应保留中断事实，明确地结束该次流，再由产品提供有新身份的重新生成，而不是把两次生成伪装成同一次。

项目落点： visible 在 MESSAGE_DELTA 或 TOOL_CALL_DELTA 后设定；随后超时或失败产生 MODEL_STREAM_INTERRUPTED。源码

追问： 已收到的 usage 还能保留吗？能。输出不可继续使用与计量回执是否存在是两个独立问题，最新版空响应处理正是按这个原则修复。

RT05｜HTTP 200、模型可用输出、Agent 成功、业务成功之间有什么区别？

可以这样回答： HTTP 200 只是传输或接口层的成功，模型可能返回空内容或不符合契约的结果。模型给了合法工具调用，只意味着 Agent 有可处理的下一步。AgentRun 正常结束，也还需要核对具体业务后置条件，例如工单是否创建在正确客户下。每层都应有自己的状态和证据。

项目落点： 网关用文本或 tool_calls 判断可用响应；Approval 又区分决定与执行状态；本地工单 Action 最终返回真实业务对象结果。网关、审批表、工单执行

追问： 面试官问“成功率”时，先确认他要哪一层成功率以及分母，否则数字不可比较。

RT06｜模型返回空答案，为什么不能记成 0 token、0 费用？

可以这样回答： 空答案说明没有可用输出，不说明模型没有计算。供应商可能因长度截断等原因返回空文本，同时给出已使用的输入、输出 token。应保留这份实际回执，并让“回答失败”与“有费用证据”同时成立；没有回执时则保留未知。

项目落点： 最新 gateway 在失败 trace 保存 rejected_response 的 usage/cost；fallback 前写 model.empty_response。源码、回归测试

追问： usage 已知但 cost 缺失怎么办？不能自动补 0；可以在另一个清晰标注的估算层定价，同时保留原始回执的完整性状态。

RT07｜fallback 成功后，为什么不能只保存最后一个 response 的用量？

可以这样回答： 最后 response 只描述最后一次尝试，前面失败或被拒收的尝试仍可能产生费用。要分别统计逻辑调用、物理尝试与已知计量回执，不能把最终答案当成整个调用链的完整成本证据。否则可用性提高的同时，成本增长会被统计口径藏掉。

项目落点： TimingCapture 对 model.generate 计逻辑调用及 attempt_count，对 model.empty_response 只补回执数量，不重复增加尝试数。源码

追问： 一次逻辑调用、两次实际尝试，两份 usage 回执，分别该是多少？答案是 1、2、2。这个例子检验的是口径，不是算术。

RT08｜冻结 AgentVersion 后，模型配置和密钥是不是再也不能变？

可以这样回答： 冻结的是非秘密执行配置和绑定身份，使历史运行可解释；密钥是否启用、工作区归属和出站端点仍要在执行时验证。撤销一个泄露凭据不能因为旧版本冻结过就失效。模型行为版本和当前授权状态必须分开处理。

项目落点： _prepare_frozen_execution 使用冻结 profile，_enabled_frozen_credential 检查 provider、workspace、enabled 和冻结端点。源码

追问： 直接把最新 profile 的所有字段覆盖到旧版本上安全吗？不安全，会使发布时约定的模型、参数或 fallback 发生静默漂移。

RT09｜为什么模型调用时不应该长时间占着 SQLAlchemy Session？

可以这样回答： 模型延迟可能远大于一次 SQL 查询。若持有 session 或事务等待外部响应，连接池会被慢网络占满，普通读写也会排队；锁还可能延长。应先在短数据库作用域解析和验证配置，释放后调用模型，再用新的短事务记录结果。

项目落点： _PreparedModelGateway 保留解析后的身份与所需凭据，不持有跨网络调用的 AsyncSession。源码

追问： 把 HTTP 调用写在数据库事务中是否能让它一起回滚？不能。PostgreSQL 事务不控制远端服务的状态。

RT10｜如何避免 fallback 配置形成环？

可以这样回答： 解析时记录已经访问的 profile ID；再次遇到同一个 ID 就拒绝配置。还需要对链上每一项校验工作区、启用状态和能力，否则主模型正常时看不出的备用配置问题会在故障时集中出现。

项目落点： ModelProfileResolver.resolve_chain 使用 visited 集合检查循环，并验证每个 profile 的能力与状态。源码

追问： 只在 UI 中禁止用户选择当前模型作为 fallback 足够吗？不够，A→B→A 跨记录环、API 写入和并发修改都需要服务端约束与解析校验。

RT11｜模型能力检查为什么要与具体请求结合？

可以这样回答： “这个模型支持聊天”不能证明它支持这次请求需要的流式、工具调用或结构化输出。能力要求应从当前操作和载荷推导，再与 profile 的能力声明匹配；这样能在发请求前拒绝必然不兼容的执行计划。

项目落点： effective_capability_requirements 与 validate_capabilities 连接请求要求和链上配置。能力模块、网关准备

追问： 声明 supports_tools=true 就算验证完成吗？还要通过 adapter 的工具名称、参数与流式解析验证。配置声明是契约输入，不自动证明实现正确。

RT12｜一次模型调用超时 30 秒，是不是整个 Agent 最多 30 秒？

可以这样回答： 不是。单次尝试超时、每个 profile 的重试、fallback 链、Agent 多轮、工具调用和后台排队都可能叠加。必须区分每次外呼期限、逻辑调用期限和整个任务期限。只设一个 profile timeout，不能自然得到整个业务任务的 SLA。

项目落点： 网关在每个尝试内使用 profile.timeout_seconds，外面仍有重试和模型链；Run 还有自己的执行与状态合同。源码

追问： 设计总期限时该怎么传？可以使用剩余 deadline 向下传播并在每个新外呼前检查，但要明确这是设计建议，不应声称当前所有入口已统一采用。

RT13｜为什么金额要用 Decimal？还有哪些细节比类型更重要？

可以这样回答： Decimal 避免二进制浮点在大量微小费用累加中的误差；还要校验有限、非负、币种和数据库精度。更关键的是不能混淆估算、预占和实际结算，即使用了 Decimal，把未知写成 0 或把 USD 与 CNY 直接相加依然是错的。

项目落点： Run 账本使用 Numeric/Decimal 与币种校验；安全 trace 对合法 estimated_cost Decimal 用字符串保留精度。账本、安全 trace

追问： 如果真实账单高于预算上限，应截断吗？不能。保留真实超额证据并阻止新增不被预算允许的请求，才不会让账本说谎。

RT14｜“预算上限”与“预计花费”为什么必须分开？

可以这样回答： 预计花费是一个估算，预算准入需要可信的保守上界。并发发送前应预占足够额度；没有结算证据不能乐观释放未决占用。否则多个任务同时依赖“可能省下的钱”，就会超支。预算合同还要说清覆盖哪些调用。

项目落点： reserve 拒绝仅用 ESTIMATE 的发送预占；预算适配器在发送前提交 reservation，结算合同要求 PROVIDER_BILL。账本、适配器

追问： 有 token 计数器就一定有可靠金额上界吗？还需要完整输入、输出上限、冻结价格、计费规则与实际调用覆盖。计数只是其中一个前提。

RT15｜数据库里的预算预占幂等，为什么网关再次看到相同 identity 时反而拒绝发送？

可以这样回答： 账本幂等允许安全地确认“这笔占用已经存在”，不证明上一次网络请求没有发送。若看到已有预占就再次请求，可能让两个远端调用共用一份额度。适配器必须区分“第一次创建成功，可以发出”与“身份已经使用，不能猜测重发”。

项目落点： RunBudgetAttemptAdapter.reserve_attempt 发现 reservation.created 不为 True 时返回 RUN_BUDGET_ATTEMPT_REPLAYED。源码

追问： 如何恢复？需要查询实际发送与结算证据，或设计明确的未发出证明；不能把远端 exactly-once 的难题藏进本地 UNIQUE 约束。

RT16｜如何排查“用户感觉没变慢，但成本突然升高”？

可以这样回答： 先比较同类任务的物理尝试数、fallback 比例、空响应、重试与辅助模型调用，再看 token/价格/计量完整性。最终响应时间可能被更快备用模型补偿，却多付了前面失败的费用。还要确认是不是统计修复让过去漏记的费用现在被看见。

项目落点： 最新空响应回执修复会改善观察完整性，不能直接被解读成模型策略新增了消耗。网关、回执统计

追问： 如何证明优化省钱？用冻结任务与相同费用口径比较，并报告未知回执比例；不要只比较最终成功回答的平均费用。

RT17｜消息进入队列就能向用户显示“任务成功”吗？

可以这样回答： 不行。队列接受只代表交付过程的一步。用户真正关心的是任务是否被领取、是否推进、产物是否就绪和业务目标是否完成。系统应该分开受理、执行中、等待、失败和完成，并为这些状态提供持久查询。

项目落点： Run API 准备 Run 后再 enqueue；入库任务还经历多个 stage 与终态。Run 路由、入库服务

追问： HTTP 202 说明什么？说明请求已被接受处理，最终结果需要后续观察；不能由 202 推导文档已可检索或动作已完成。

RT18｜为什么队列消息不能携带一份权限快照让 Worker 直接用？

可以这样回答： 消息可能延迟、重复或在成员已撤权后才执行。权限快照若被视为永久授权，会突破当前访问控制。更稳妥的消息携带任务身份，Worker 根据持久 Run 的原始 actor 和当前租户关系重新鉴权。

项目落点： AgentRunQueue 只传 workspace_id/run_id/request_id；Worker 通过 TenantService 重新获得 context。队列、Worker

追问： 任务已经排队时撤权是否应生效？项目这条入口会尊重当前撤权，不能把管理员审批或 broker 内消息当成越权许可。

RT19｜数据库行锁和执行租约分别解决什么问题？

可以这样回答： 行锁保护短事务内的并发读改写，例如两个 Worker 同时领取时谁先得到记录。租约跨越事务结束后的长时间执行，表达当前拥有者和有效期限。不能拿着一个数据库事务锁等待几十秒外部模型，也不能只靠过期时间完成原子领取。

项目落点： run_execution_lease 领取时对 Run 加锁，提交 owner 与 expiry；后续以条件更新续租。源码

追问： 还需要什么？结果写回时要验证身份，外部副作用还需要业务幂等或对方支持的 fencing，不能认为租约天然覆盖所有系统。

RT20｜lease token 为什么不能只用 job_id？

可以这样回答： job_id 标识任务，token 标识这一次拥有权。任务可能被接管多次，旧 Worker 晚到的提交仍然带同一个 job_id；只有不同 token 能区分旧拥有者与当前拥有者。条件写必须同时检查任务 ID 和当前 token。

项目落点： 入库 claim 每次生成新 lease_token；ClaimGuard 检查 token、PROCESSING 状态及有效期；Run 清理也按 execution_owner 条件更新。入库、Worker、Run 租约

追问： token 自动保证外部写安全么？只有外部服务也验证它，才是跨系统 fencing；否则它主要保护本地调度与写回。

RT21｜有心跳就说明任务在进展吗？

可以这样回答： 心跳说明当前拥有者仍能证明存活或续租，不一定说明业务阶段在推进。一个卡在供应商调用里的进程也可能持续续租。活性诊断还需要 stage、最后进度时间、处理数量、总耗时和错误记录，区分“活着”“拥有权有效”和“有效推进”。

项目落点： 入库 Worker 的租约检查与解析、编码、索引阶段是不同逻辑；协调器也需要 stale 条件，而不是只看有无进程。Worker、协调器

追问： 自动把耗时长的任务重跑安全吗？先检查任务是否可重放以及当前外部副作用，不能仅凭超时就抢占再执行。

RT22｜为什么最大尝试次数应写在 claim 的 UPDATE 条件里？

可以这样回答： 如果先 SELECT 判断、再 UPDATE 加一，多个 Worker 可能同时认为还剩一次额度。将可领取条件、attempt_count<max 与计数递增放在一条原子更新中，只有拿到返回记录的执行者可以继续，从而把次数上限变成并发不变量。

项目落点： 最新 claim_ingestion_job 已把上限检查纳入 UPDATE；这正是 RT08 对应的修复方向。源码

追问： attempt_count 等于 provider 请求数吗？不等于。一次任务领取内部可能有多批编码或多次供应商请求，两个计数控制的对象不同。

RT23｜达到最大次数后，为什么不能立即把所有同 ID 任务设为 FAILED？

可以这样回答： 可能有一个 Worker 正在完成最后一次合法尝试。旁边收到的重复消息不应终止它。耗尽处理也要满足任务当前“可领取”的条件，例如待处理或既有租约过期；活跃拥有者应保留完成机会。

项目落点： claim 失败后只锁定 claimable 且次数耗尽的任务，调用统一耗尽函数；活跃 owner 不符合这个条件。源码

追问： 这个边界如何测试？分别构造最后一次合法执行仍活跃、已经过期、重复投递三个场景，并验证状态与 provider 调用次数。

RT24｜租约续不上了，为什么仅让续租协程退出不够？

可以这样回答： 主业务协程可能毫不知情地继续编码和写索引。需要把失租信号传到真正会消耗资源或产生副作用的执行边界，并让后续派发停止；最终持久写回还需验证当前 owner，不能只在任务开始检查一次。

项目落点： 新的 _ClaimGuard 通过事件和数据库校验把失租传入解析、向量编码与索引批次。源码

追问： 这能立即停止所有计算吗？不能保证。已开始的线程函数和已交付远端的请求有自己的生命周期，系统要承认这个界限。

RT25｜取消 asyncio 协程是否能取消已经发出的外部写入？

可以这样回答： 不能据此保证。取消本地等待通常只影响本地控制流；对方可能已经接受请求并继续处理。即使 Python 侧停止了 await，底层同步线程也可能继续运行。应区分停止后续派发、取消连接、远端业务取消和补偿操作。

项目落点： 入库索引写入注释承认已提交外部写可能在接管后完成；ActionRuntime 对远端不确定结果保留 UNKNOWN_OUTCOME。入库 Worker、动作执行

追问： 用户点取消该怎么说？说明运行停止继续推进，但对已交付动作的结果仍需核对，不宣称远端已自动回滚。

RT26｜至少一次消息交付和业务恰好一次是一回事吗？

可以这样回答： 至少一次允许消息重复，保证的是某种交付机会；业务有效一次需要稳定业务身份、幂等写入、唯一约束或外部服务协议。任务只能有一个当前 owner，也无法消除“外部已成功、本地没记下”的窗口。

项目落点： Run Worker 启用 acks_late/reject_on_worker_lost，但仍依赖 Run 状态、执行租约和动作领取。create_ticket 另有业务幂等键。Worker、工单执行

追问： 简历写“Celery 保证任务恰好执行一次”准确吗？不准确。应说明交付语义与业务幂等如何组合，以及仍需对账的边界。

RT27｜数据库已提交 Run，队列投递失败了，怎么处理？

可以这样回答： 这是数据库与 broker 之间的双写窗口。后续设计可在同一事务写业务记录与待派发意图，再由 dispatcher 重复投递并确认；消费者必须幂等。当前问题不能通过“换一个更可靠的队列”自动解决，因为两套系统仍不在同一提交事务中。

项目落点： 现有 Run stream 路由先 prepare_stream，再 queue.enqueue，因此仍有初始派发窗口值得完善。源码

追问： 项目是否完全没有 outbox 思想？不是，审批已有 resume_pending 的持久恢复标记；要按入口分别描述已覆盖与未覆盖的范围。

RT28｜审批有 resume_pending 了，为什么还说恢复交付值得改进？

可以这样回答： 当前已经能把恢复意图同审批决定持久化，后台协调也能补发，这是实质能力。但人工 API 仍直接 await resume，存在即时路径与后台补偿两条入口。继续改进的是统一任务交付、失败可见性和所有入口的覆盖，不能把已有能力说成没有。

项目落点： decide 写 resume_pending；审批 API 直接恢复；周期任务派发 resume_agent_run。审批服务、API、后台任务

追问： 重复派发如何避免双执行？需要 Run owner 与 Approval claim 共同约束，不能只在 dispatcher 里维护一个本地布尔变量。

RT29｜为什么 Run 过期租约通常转 NEEDS_ATTENTION，而入库可重新领取？

可以这样回答： 两类任务的副作用合同不同。入库基于不可变 revision 和确定产物身份，较容易重放；AgentRun 可能已经调用外部写工具，租约过期时无法确定上次走到哪里。盲目重跑整个图可能重复业务操作，因此保留待核对状态。

项目落点： Run lease 遇过期 owner 不自动重跑；ingestion claim 可以在其可领取条件下接管。Run 租约、入库 claim

追问： 能不能让所有 Run 自动恢复？可以逐步扩大，但必须为每个有副作用步骤建立可靠的恢复点、外部幂等或结果查询能力。

RT30｜协调器和重试器的职责有什么不同？

可以这样回答： 重试器决定是否再执行某项工作；协调器根据多个持久证据修复状态关系。它可能把 RUNNING 改成 WAITING_APPROVAL，也可能发现 checkpoint 缺失后转 NEEDS_ATTENTION，并不一定再次调用模型或工具。将二者混同容易把坏状态“修复”成重复副作用。

项目落点： _apply_reconciliation_transition 根据活跃 owner、pending approvals、checkpoint 和 stale 条件决定下一状态。源码

追问： 为什么协调器看到活跃 owner 要谨慎退出？否则维护任务可能与正常执行者同时改变状态，制造新的并发错误。

RT31｜你怎么证明一个幂等修复真的幂等？

可以这样回答： 不只看第二次没有报错，还要验证第二次不会增加动作次数、生成第二个业务对象、改写第一次决定时间或改变已确定结果。测试应包含重复调用、并发调用、第一次部分失败后的再次调用，且用业务记录和计数判断。

项目落点： 最新审批修复的集成场景重复协调旧 CANCELLED+PENDING，验证已撤销记录的 decided_at 不被再次覆盖；动作 claim 也只允许第一次 NOT_STARTED→CLAIMED。测试、服务

追问： 仅断言返回 HTTP 200 有用吗？很有限。它不能证明底层没有重复副作用。

RT32｜为什么不同操作要统一加锁顺序？

可以这样回答： 多事务若按相反顺序锁同一组记录，会出现循环等待。例如审批决定先锁 Approval 再锁 Run，取消先锁 Run 再锁 Approval，两者就可能互等。统一顺序不能消灭所有死锁，但能减少这一类可避免的冲突，也便于代码评审。

项目落点： decide 明确按 Run→Approval 顺序，与取消和协调匹配。源码

追问： 锁是不是越多越安全？不是。应缩短事务、只锁需要维持不变量的记录，并避免在锁内等待外部模型和网络服务。

RT33｜为什么审批表要同时有 decision_status 与 execution_status？

可以这样回答： 决定状态表达是否允许做，执行状态表达是否已经领取与做成。批准之后可能尚未执行，已领取后可能结果未知。两条状态轴才能准确表达这些组合，并决定是否还能恢复或重试。单个 approved 字段无法表达执行历史。

项目落点： Approval 中决定状态为 PENDING/APPROVED/DENIED/EXPIRED/CANCELLED；执行状态为 NOT_STARTED/CLAIMED/SUCCEEDED/FAILED/UNKNOWN_OUTCOME。模型

追问： APPROVED+UNKNOWN_OUTCOME 是不是非法状态？不是，它表示动作被允许过，但实际结果没有确认；这恰是需要对账的真实场景。

RT34｜审批到底绑定什么？为什么不能只存“用户点击同意”？

可以这样回答： 必须绑定工作区、Run、已发布 AgentVersion、ToolRevision、规范化参数及逻辑提议身份。否则点击后参数或工具版本变化，就可能执行用户没有批准的内容。批准的是一项确定动作，而不是授予 Agent 无限期继续写入的权限。

项目落点： create_or_get 计算 canonical_args_hash 和 logical_action_id，保存版本与 actor 绑定；恢复还核对活跃审批和 checkpoint。服务、运行恢复

追问： 修改参数后还能沿用旧审批吗？不应该。应形成新动作身份并重新走相应决定合同。

RT35｜为什么不能用参数哈希作为全局动作去重键？

可以这样回答： 相同参数可能是用户明确发起的两个合法独立业务操作。只有业务身份相同的重复才该合并。logical_action_id 应包含运行和提议上下文，使同一动作重放复用审批，又不把不同运行的同内容请求强行去重。

项目落点： 动作身份纳入 workspace、run、tool revision、参数哈希和 proposal ordinal。源码

追问： proposal ordinal 为什么有用？它能区分同一运行内多项独立提议；但其生成与恢复必须稳定，不能每次重试随意换序号。

RT36｜管理员批准后，是否可以用管理员权限继续执行原 Run？

可以这样回答： 不应默认这样做。审批决定是允许某个既定动作，不是把审批员的权限转移给整个 Agent。恢复时应回到原运行人的当前权限，验证仍能执行该动作；否则被移除成员可借一份旧审批继续获得管理能力。

项目落点： _authoritative_run_context 按 Run.created_by 重建上下文，Worker 也回读当前租户访问。运行服务、Worker

追问： 审批者与执行者的审计要分开吗？要。requested_by、decided_by、decision_source 和实际运行 actor 承担不同解释职责。

RT37｜两个审批员同时给出相反决定，如何保证结果明确？

可以这样回答： 对审批及其所属 Run 按统一顺序加锁，只有仍是 PENDING 的记录接受第一次有效决定，后来的请求读取已确定状态。应该返回真实当前结果，不能每个请求都声称自己的决定生效。过期判断也要处于同一受控事务中。

项目落点： decide 的锁、状态检查和数据库时钟；审批决定与恢复标记一同提交。源码

追问： 前端禁用按钮能解决并发吗？只能减少重复点击，不能阻止多标签页、多人、直接 API 和网络重试。

RT38｜个人自动审批偏好如何防止“自己给自己提权”？

可以这样回答： 偏好只能在当前身份许可范围内缩小或选择路由，不能创造权限。应读取真实成员关系与账号状态，将其与当前受限 context 取交集，再按工具风险与强制人工规则判断。没有 approve_action 时设置更高委托级别应被拒绝或限制。

项目落点： locked_actor_permissions、identity_ceiling、MANUAL/LOW/MEDIUM 与 PersonalApprovalRun 共同约束委托。源码

追问： 高风险操作能因用户选了 MEDIUM 就自动执行吗？不能；HIGH 与 MCP WRITE 仍由 requires_human 强制人工。

RT39｜为什么“读取工具都不需要审批”这个说法不准确？

可以这样回答： 读取也可能敏感，而且工具自己的 approval_policy 可能明确要求审批。当前自动直接执行需要 READ、NEVER 且不属于强制人工操作，不能只看 READ。另一个细节是源码条件并未额外要求 risk=LOW，因此也不应照抄旧注释把它讲窄。

项目落点： ToolPolicy.decide 与 requires_human 两个函数的真实条件。源码

追问： 需求要求所有 MEDIUM READ 人工时，应改哪里？要修改并验证策略合同，同时考虑已发布版本、个人委托与执行入口的一致性，不能只禁用一个页面按钮。

RT40｜项目允许自己批准自己吗？

可以这样回答： 要分人工路径与委托路径。当前人工批准自己的请求有规则限制：组织 OWNER/ADMIN 是例外，普通成员不能把普通人工审批当作自己放行。个人委托是另一条有身份上限、风险限制和清楚 decision_source 的路径，不能笼统答“允许”或“不允许”。

项目落点： ApprovalService.decide 的 SELF_APPROVAL_FORBIDDEN 与 delegation.py 的授权路由。服务、委托

追问： 为什么审计要记录 HUMAN/DELEGATED？便于解释结果是一次人工判断还是基于持久个人授权自动作出的决定。

RT41｜取消 Run 与撤销待审 Approval 为什么必须放在同一个事务？

可以这样回答： 它们共同表达“这项运行不再等待这些待审动作”的业务不变量。分成两次提交，进程可能在中间退出，留下已取消 Run 和仍可操作的 PENDING 审批。同事务让它们一起成功或一起回滚，用户界面与后端状态才能一致。

项目落点： 最新 cancel 调用 cancel_pending_in_session 后统一 commit，替代了提交后另行撤销的窗口。运行服务、审批服务

追问： 如何验证？在提交前注入异常，断言两个对象均未部分改变；再正常执行，断言两者一起收敛。仓库已有对应集成测试。测试

RT42｜修复代码后，旧数据库里已经不一致的记录怎么办？

可以这样回答： 需要单独的、可重复执行的数据修复或协调路径。先定义精确坏状态 predicate，只处理可安全证明的组合，并保留重要历史时间；不能把所有异常强行改成成功。预防新错与修复旧错是两个不同验收目标。

项目落点： 协调器现纳入 CANCELLED 且仍有 PENDING 审批的运行，并撤销遗留待审项；重复协调不会改写已经完成的决定时间。协调器、回归测试

追问： 修复脚本为什么也需要幂等？部署中断、重复运行和定期维护都可能再次触发，同一问题不应因修复次数增加而制造新历史。

RT43｜为什么取消不能把 CLAIMED 或 UNKNOWN_OUTCOME 直接改成“未执行”？

可以这样回答： CLAIMED 之后可能已经把请求交给外部服务，UNKNOWN_OUTCOME 更明确表示缺少结果证据。取消只表达不再继续推进的意图，不能改变已经发生的事实。强行清零会让后续重试误以为可以重新执行，导致重复副作用。

项目落点： cancel 与 reconciliation 对已领取或未知动作保留 NEEDS_ATTENTION，并记录需要动作核对的故障码。运行服务、协调器

追问： 用户要求撤销外部业务怎么办？需要外部系统支持的撤销或补偿操作，作为另一项明确授权与可审计动作处理。

RT44｜为什么动作 claim 用条件 UPDATE，而不是先读再写？

可以这样回答： 两个恢复者可能同时读到 NOT_STARTED。原子 UPDATE 将“已批准且未开始”与“改成 CLAIMED”合成同一步，只有拿到 returning 结果的一个拥有执行资格。先读再写即使代码顺序正确，也会在并发交错中失去互斥。

项目落点： claim_execution 更新 APPROVED+NOT_STARTED，递增 execution_attempt_count 并提交。源码

追问： 这等于外部 exactly-once 吗？不等于。claim 后崩溃仍需要判断外部是否执行，本地互斥只是完整合同的一部分。

RT45｜本地 create_ticket 怎么做到重复调用不生成重复工单？

可以这样回答： 使用 workspace 范围内的稳定 idempotency_key，创建前查询已有对象，并通过数据库唯一性处理并发竞争；若发生冲突，回滚后读取已存在的同一结果。这样“同一逻辑请求”与“同一张工单”建立了可查询关系。

项目落点： CreateTicketActionExecutor.execute、_find_ticket 与异常回查。源码

追问： 只在代码里先 SELECT 再 INSERT 足够吗？没有数据库唯一约束仍可能并发创建两条；而没查到也不能总是证明某个失联 COMMIT 不会晚到。

RT46｜FAILED 与 UNKNOWN_OUTCOME 有什么本质区别？

可以这样回答： FAILED 表示已有足够证据确定执行失败；UNKNOWN_OUTCOME 表示本地无法判断外部最终结果，可能成功也可能失败。前者可按具体业务策略重试，后者通常先查询、对账或人工处理。把未知归零会牺牲数据与副作用安全。

项目落点： ActionExecutionResult 的 unknown_outcome，以及协调器将陈旧 CLAIMED 转未知。动作执行、协调器

追问： HTTP timeout 属于哪一种？要看请求是否交付、工具是否只读、外部有没有可靠状态查询，不能统一回答“失败可重试”。

RT47｜为什么恢复审批时不能随便加载“最新 checkpoint”继续？

可以这样回答： 最新 checkpoint 可能已不是当时批准的中断。恢复必须验证 approval_id、Run 的 waiting_approval_id、thread/checkpoint namespace 和 checkpoint ID 一致，并确认冻结历史绑定仍有效。否则可能把某项批准套在另一项提议上。

项目落点： _validate_checkpoint_interrupt 返回确定 resume_config；真正 invoke 前再次核对 checkpoint 身份。源码

追问： 缺 checkpoint 时能不能用日志重建一个差不多的上下文？不能默认这样做，应报告缺失并进入受控恢复。近似重建可能改变工具提议与授权语义。

RT48｜为什么远端 MCP 写工具不应该在外层粗暴套一个超时后宣称失败？

可以这样回答： 只有真正执行网络交付的客户端最清楚请求是否已发出。外层超时只知道等待结束，不知道对方是否接受；若据此宣称失败并重试，可能产生第二次写入。应由客户端报告交付阶段与结果确定性，无法确认时保留未知。

项目落点： ActionRuntime._execute_remote 把 deadline 和交付判断留给远端执行器，对逃逸异常保守返回 UNKNOWN_OUTCOME。源码

追问： 这意味着不设超时吗？不是。要在正确的层设置超时，并准确表达超时后的知识边界，而不是取消了等待就宣称取消了业务。

RT49｜如果面试让你讲最近一个真正有价值的修复，你怎么讲？

可以这样回答： 可以选“取消运行与撤销待审项原子化”。先描述用户症状：运行已取消但审批仍待处理；再给故障窗口：两个事务之间中断；说明实现：共享 session 同事务更新，并让协调器清理历史遗留；最后说验证：提交前异常回滚、正常取消、重复协调时间稳定，以及不把未知外部动作强制清零。
