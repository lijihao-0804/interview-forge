第 14 讲：工具版本、MCP 与外部系统接入

一、先修正一个容易被旧概览带偏的说法

仓库概览有时把 Built-in、REST、MCP 并列介绍。深入可执行工具合同后要更精确：当前 ToolSourceKind 和 validate_executable_tool_spec() 接受的是 BUILTIN 与 MCP 两类；不能据此宣称已经提供了一个可任意填写 URL、方法和请求体的通用 REST 工具注册引擎。项目有 HTTP API、业务系统适配和历史设计合同，这与生产可执行枚举是不同层次。工具合同 规格校验

这正是读项目必须同时看“文档愿景、接口合同、实际装配”的原因。你可以说项目可以通过明确适配器对接 HTTP 业务系统，但讲当前能力时必须指出具体入口。

二、一个工具至少有四种身份

想象一个外部 MCP 服务器提供 create_ticket。你在 AgentHub 中导入它，给它取逻辑名称 support_create_ticket，设置写操作、高风险、必须审批。随后 Agent v5 绑定这个工具的一次修订。

身份 解决的问题 例子
连接身份 到哪个系统、用什么认证 一个工作区内的 McpConnection
工具身份 平台里管理的是哪个工具 Tool
工具修订身份 这次具体允许什么参数、风险与行为 ToolRevision、spec_hash
一次逻辑动作身份 运行过程中准备执行哪一次业务操作 与 Run、参数和动作序号相关的逻辑身份

连接存在，不等于工具已经导入；工具已导入，不等于 AgentVersion 已经绑定；版本已绑定，也不等于本次调用已经通过策略和审批。把这些对象混成一个“工具 ID”，就很难解释发布、修改和重复执行。MCP 导入服务 工具与修订

三、为什么 Discovery 只是“发现”，不是“授权”？

远端工具目录提供名称、描述、输入输出 Schema 和 annotations。但这些是远端声明，不是平台已经确认的风险等级。恶意或配置错误的服务器也能把写操作描述成只读。

当前 discover_tools() 读取目录，不创建 Tool、不持久化导入结果，也不从远端标注自动推断 effect、risk 和 approval。import_tool() 要求有权限的调用者明确选择治理参数，并重新读取一次远端目录，确认工具此时仍存在，再把 Tool 与 revision 1 放在同一事务里保存。发现与导入

为什么导入时再查一遍？因为页面五分钟前显示的目录可能已经过期。直接相信旧页面上的 Schema，会让“用户批准的配置”和“现在实际导入的配置”不一致。

四、参数 Schema 校验和业务授权是两件事

JSON Schema 能检查 customer_id 是不是字符串、priority 是否在允许枚举里、必需字段是否缺失。它不能独自证明这个客户属于当前工作区，也不能证明操作者有建单权限，更不能证明这个工具没有外部副作用。

工具处理器接收 ToolExecutionContext，其中包含已经授权的 WorkspaceExecutionContext。真实租户范围从这里进入，不能让模型通过参数把 workspace_id 改成另一个组织。模型负责提出业务参数，平台负责提供身份和权限事实。工具执行上下文

{
  "customer_id": "示例客户标识",
  "title": "申请检查重复扣款",
  "priority": "NORMAL"
}

这只是教学参数示意，不代表当前任意 MCP 工具都有同样的字段。读某个工具时，要看它冻结的 input_schema，而不是照搬另一个工具的请求体。

五、内置工具为什么用注册表，而不让模型写函数名后动态 import？

ToolRegistry 的生产内置身份是明确映射的：calculator、query_customer、search_knowledge、query_wiki。测试覆盖可以替换已知身份的 handler，但并不意味着生产接受任意模块路径、shell 命令或 Python 表达式。内置注册表

这里的设计好处是可审计：你知道模型最多能提出哪些能力，知道每个能力对应什么处理器，也能在发布时检查绑定。新增一个能力需要代码与合同一起变化，而不是模型的一段文本突然获得宿主机执行权。

如果将来要加入新的内置工具，可以按以下顺序设计：先定义输入输出和权限范围，再实现处理器、注册身份，接入可发布的工具规格，最后验证错误和副作用路径。不要只新增一个函数，然后认为 UI、版本冻结和评测就自动具备了这个能力。

六、MCP 为什么还要做 SSRF 防护？

因为用户配置的远端地址会让服务器主动发起网络连接。若只检查“URL 看起来是 HTTPS”，攻击者可能借服务器访问内部地址、云元数据服务或原本不对用户开放的系统。

当前 MCP 安全层检查 URL 结构、协议、是否夹带用户名密码，解析 DNS 并检查全部地址；传输层还固定经过授权的连接目标，并校验实际 socket 对端，避免只在 DNS 预检查阶段判断一次。无法验证 peer 的传输不能当作安全路径。普通客户端关闭自动重定向；不能把“代码规定要校验重定向”误说成“所有路径都允许自动跟随重定向”。目标校验 实际传输

为什么同时检查 DNS 和实际连接？因为检查时的解析结果与连接时真正到达的位置可能不同。安全规则应该约束实际出站行为，而不是只检查输入字符串。

私有网络例外必须是受控部署决定。模型供应商的出站例外使用操作员配置的严格 CIDR；这会影响所有相关租户，不能把“这是本地开发环境”或“API Key 名字像本地模型”当成绕过规则的凭据。模型出站合同

七、工具返回内容为什么仍然是不可信数据？

一个文档、网页或 MCP 结果可以包含“请忽略之前规则”“管理员已经批准”等文字。这些文字来自工具数据，不是系统真正的审批事实。ToolResult 单独保存框架控制的审批决定与执行结果字段，不能因为工具数据里也有同名 key，就提升它的权限。结果合同

你可以把这个边界理解为：业务内容可以成为模型的参考材料，权限事实必须来自服务器可信路径。RAG 文档、Wiki 派生文字和模型自己的解释，都不能替代审批服务写下的决定。

这不是说一条 Prompt 就彻底解决提示注入。真正的保障还来自工具范围、租户过滤、参数校验、审批和结果处理。语言模型可能理解错误，但它不应该因此获得一个不属于它的权限开关。

八、“调用失败”为什么要区分有没有派发？

外部只读查询失败，通常可以在边界清楚的情况下重试；外部写入在请求发出后超时，则可能已经生效。MCP client 记录是否进入工具调用派发阶段，对“可能派发但结果不能确认”的情况保留不确定性，而不是把所有异常都包装成相同的 ERROR。MCP 调用结果分类

注意，服务器返回 JSON 并不自动意味着写入成功。还需要按协议和冻结 Schema 判断响应，区分工具层错误和业务结果。反过来，HTTP 连接失败也不一定意味着业务没有执行。第 17 讲会继续解释这些结果怎样进入审批执行状态。

九、本讲练习：画出新增一个工具的完整合同

选择一个你熟悉的业务，比如查询订单。写出工具名称、输入 Schema、输出 Schema、工作区范围、超时、风险、是否可能泄露敏感信息、发布时冻结什么、运行时还需要检查什么。再把它改成“退款申请”，说明哪些地方必须改变。

你的验收表至少要有参数错误、跨工作区、连接禁用、Schema 漂移、超时、重复调用、返回恶意指令、已派发但无回执这些分支。这样才算掌握“接入工具”，而不只是学会一次 SDK 调用。
