第 14 讲：模型网关、计费账本与 KV 友好上下文——从一次回答追到每次实际调用

第 2 讲已经解释 Agent Loop；本讲只研究它调用模型时的生产级边界。源码入口：packages/model_gateway/gateway.py、packages/model_gateway/adapters/litellm/adapter.py、packages/agent_runtime/run_budget_ledger.py、packages/agent_runtime/runtime_graph.py、packages/model_gateway/cache_capability.py。

14.1 你以为请求了一次，其实供应商可能收到三次

假设主模型 A 每次最长等待 20 秒，最多尝试两次；后备模型 B 最多尝试一次。

用户点击“发送”
  └─ 一次 AgentRun
      └─ 模型轮次 #1
          ├─ A 尝试 1：连接后超时
          ├─ A 尝试 2：无可用结果
          └─ B 尝试 1：成功返回

这里有三种不同的统计单位：

  • Run：一次业务执行。
  • Model round：Agent 在循环中一次向模型提出问题，可能包含回填后的多轮。
  • Provider attempt：真正向某个供应商发出的一次调用。

因此排查“突然变慢、变贵、失败”时，要从最后一个答案往回查看完整的 attempt 链，而不是只记录最终 B 的 usage。

网关在执行前具体检查什么？

根据已发布的模型档案与凭据路线，确定：实际模型名、Provider、模型能力、输出额度、温度、超时、重试策略、Fallback 链，以及本次工具调用/结构化输出是否需要对应能力。LiteLLM 帮助处理协议差异；AgentHub 的 Gateway 管理自己的业务策略、预算和观测。参见 6。

14.2 Retry 的关键不是次数，而是“有没有不可撤回的输出”

普通非流式调用在没有可用结果时，可按错误类型与策略进行重试。流式响应则有一个断点：

A 流式输出："订单的退款条件是……"
                     ↑ 已向前端展示
随后 A 断开

如果直接让 B 继续写，前端会拼出两次推理的半截答案。更严重的是，如果前半截是一次 ToolCall 参数，后半截由另一个模型生成，整个结构可能已失去含义。AgentHub 对 MESSAGE_DELTA / TOOL_CALL_DELTA 已对外输出的情况实施流式中断处理，而不是透明拼接。需要用户重新发起、或由业务状态机执行明确的后续步骤。9。

另一个典型问题是“模型成功返回 HTTP 200，但内容为空”。模型可能已消耗输入/输出 token，也可能触发安全拒绝。当前 ModelUsage 里保留 input_tokens、output_tokens、cached_tokens 等信息，Adapter 将 SDK 中不同字段归一化。需要按结果分类处理空回答、拒绝和结构不合规，而不是把所有 200 都当成成功输出。参见 14 与 15。

14.3 预算账本：为什么一定要“调用前预留，回执后结算”？

假设本次 Run 的费用上限为 ¥1，已经确认 ¥0.65，拟调用 A 的最坏预计费用 ¥0.45。仅在调用完成后比较账单，会出现先执行再超支的问题。预算账本将准备调用与结果结算分开，使用可识别的 Attempt ID维持本次预留身份。

业务接口和 SDK 返回时间线不总一致：

12:00:00  A 收到请求并开始生成
12:00:20  我方等待超时
12:00:21  网关准备 fallback B
12:00:25  B 成功返回

A 的费用可能存在。这个时候 B 成功 与 A 的计费证据未知 可以同时为真。针对供应商已经报告的 cached tokens，也应依据该供应商路由的价格快照计算，而不是先按全价计费再额外扣一次，造成重复折扣。预算账本的实现入口：18。

分析两个经常被混淆的费用指标

假设十条任务中六条完成，四条失败，十条总已知投入 ¥2.40；六条成功任务自身合计 ¥1.20。

  • 成功执行的条件均价：1.20 / 6 = ¥0.20。
  • 每次确认业务成功对应的平均总投入：2.40 / 6 = ¥0.40。

第一个反映成功路径自身成本，第二个把失败投入也计入业务取得的效果。在评价成本优化时，后者通常更有业务解释力。未知账单需单独记录其覆盖范围。

14.4 上下文预算与 KV Cache：两种优化目标

第 9 讲讨论如何让消息适合上下文窗口；本节研究如何让重复请求少做重复 Prefill。

推理服务如果支持跨请求前缀缓存，两次请求拥有一致的起始 Token 序列，就可能复用对应的模型计算。你现在熟悉的业务请求可以画成：

但这里有一个很重要的实现细节：工具定义通过单独的 tools 请求字段发送。上图是概念结构，不是建议把工具参数 JSON 粘进 System Prompt。

AgentHub 的实际 PREPARE 目前采用：

# 来自 runtime_graph.py 的核心消息形状
messages = [
    ModelMessage(role="system", content=runtime_policy),
    ModelMessage(role="system", content=system_prompt),
    *memory_messages,
    *history,
    ModelMessage(role="user", content=self.run.input_text),
]

这个布局的固定系统前缀是有利的；其中三处动态因素值得做专项实验：

  1. 启用线程历史搜索时，第一个 runtime_policy 可能追加包含历史丢弃数量的 history_hint。
  2. 某些数据分析回答策略通过 analysis_system_prompt(..., question)，根据当前问题追加要求。
  3. Memory 在历史之前；跨 Run 的 Memory 选择发生变化时，后面历史即使一样，也不再构成相同的连续前缀。

因此，“上下文装配稳定”与“缓存命中率最优”是不同的设计目标。这里应该先测量，不需要先引入自建的 KV 张量存储。具体参考 23。

14.5 项目现在对缓存有哪些真实支持？

  • Adapter 已按 JSON 稳定顺序序列化历史工具调用参数，减少重放前缀的无意义变化。
  • ModelUsage.cached_tokens 可以从支持该字段的供应商用量回执中获取，运行侧也能聚合。
  • prompt_cache_capabilities() 能描述某些已知模型路线的文档支持情况；对不认识的直连/中转路线返回 UNKNOWN。
  • 当前实现的这个能力检测不自动启用供应商显式 cache breakpoint。它是路由能力说明，不是缓存存储引擎。

阅读 27 与 28。

下一步的实现顺序

阶段 A：先有基线。记录 model_route、prompt_profile_hash、公共前缀身份、总 input_tokens、cached_tokens、TTFT、总耗时、实际账单；按主模型/Fallback 分层统计。

阶段 B：最小化系统区动态内容。在保持系统指令权限层级和现有预算语义的前提下，将运行时状态从稳定规则中剥离，并比较请求最终序列化的 Token 前缀；切记让模型可见内容的语义仍一致。

阶段 C：根据供应商配置显式缓存。只对明确支持且有真实配置的路由添加必要标记；控制缓存有效期、写入费用、敏感数据隔离及跨路由失效。

阶段 D：验证收益。固定一组多轮任务，A/B 同时比较结果正确性、缓存命中、TTFT 和全链路成本。优先关注两次请求最长公共前缀的位置，而不是单独统计相似文本比例。

14.6 故障练习：回答没变，费用突然翻倍

从一条 Run 开始，依次查：

  1. 本次有几个模型轮次？每轮几个 Provider Attempt？
  2. 主模型是否发生超时、空响应、fallback？
  3. 每次是否有完整 usage 和缓存 token 回执？
  4. 提示词、工具 Schema 或动态 System 是否改变，使公共前缀变短？
  5. 知识/Memory 交付是否增加了输入？
  6. 价格快照、供应商账号路线是否改变？

将原因归为调用次数增加、每次 Token 增加、缓存减少、单价变化四类，最后再考虑优化代码。

本讲掌握标准：能从一条用户回复追到每次实际模型调用；能解释“为什么准备重试”和“为什么记录 UNKNOWN_COST”；能指出上下文装配中哪一块最有可能影响缓存命中。

14.7 从源码看一次 ModelRequest 到供应商参数的转换

AgentRuntime 产生的是模型无关的 ModelRequest(messages, tools, request_mode)。LiteLLM Adapter 将每一条 ModelMessage 转成 Provider 所需的角色与内容，再加入 model、temperature、max_tokens、timeout、stream 等参数。当前代码把 SDK 内部重试设置为 num_retries=0，由 AgentHub 自己的网关负责可观察的 Retry/Fallback，以免出现两层重试都在工作的情况。

# 摘自 adapter._request_payload 的关键形状
payload = {
    "model": _provider_model(credential, profile.model),
    "messages": [_message_payload(m) for m in request.messages],
    "temperature": float(profile.temperature),
    "max_tokens": profile.max_tokens,
    "timeout": float(profile.timeout_seconds),
    "num_retries": 0,
    "api_key": credential.secret,
    "stream": stream,
}
if request.tools:
    payload["tools"] = [
        {"type": "function", "function": {
            "name": t.name,
            "description": t.description,
            "parameters": dict(t.parameters),
        }}
        for t in request.tools
    ]

为什么 SDK 不自动多重试几次？因为 Gateway 需要对每次实际 Provider Attempt 进行预算预留、事件记录和失败归类。如果 SDK 在内部悄悄发起两次，外层账本可能只看到一个调用入口，发生费用或延迟异常时更难定位。

流式请求还设置 stream_options={"include_usage": True}（适用的 OpenAI 兼容路线），让结束回包有机会携带用量。若中断前供应商没有返回完整 usage，网关保留这次尝试的未知结果，而不是生成一个猜测账单。

14.8 KV Cache 优化的一个反直觉案例

假设两个请求的消息拼装是：

请求 A:
  固定 Policy
  动态状态 "已丢弃 0 个历史回合"
  固定 System Prompt（4000 tokens）
  固定工具 Schema（1500 tokens）
  用户问题 A

请求 B:
  固定 Policy
  动态状态 "已丢弃 1 个历史回合"
  固定 System Prompt（4000 tokens）
  固定工具 Schema（1500 tokens）
  用户问题 B

虽然绝大部分内容相同，动态状态位于最前面，破坏了长的公共前缀。优化方案应先把“稳定规则”和“每次运行状态”在语义上拆分，让供应商序列化后的 Token 序列产生更长的公共起始部分。

但这不是简单把所有动态状态扔到末尾：有些状态承担系统级约束；消息的角色优先级、工具的独立请求字段、历史完整性、Context Budget 的分类位置，都需要同步考虑。项目里 _SYSTEM_PREFIX_LENGTH=2 是上下文预算的实际结构约定，改变消息位置意味着同时修改分类、回放和 checkpoint 相关测试。

怎样定义一个可用的前缀指标？

令两次经过相同供应商序列化与 tokenizer 的请求 Token 序列为 A 和 B。最长公共前缀长度为：

[ LCP(A,B)=\max{k\mid A_1\ldots A_k=B_1\ldots B_k} ]

它是一个很好的本地诊断代理指标。但最终是否收费优惠，仍要看供应商返回的 cached_tokens 和价格规则。建议同时保存 prefix_hash（仅对稳定配置身份计算，避免记录敏感正文）、已报告的缓存 tokens 和模型路线。

公共前缀很长但缓存很低，怎么排查？

可能原因包括：模型路线发生 Fallback、缓存有效期到期、前缀长度低于供应商阈值、工具 JSON 实际序列化次序不同、隐含的请求参数或系统配置变化。先对比最终 Provider 请求形状与实际返回的用量字段。不要只对比 Python 层 system_prompt 字符串。

14.9 成本与可靠性的联合验收用例

用例 受控模拟 核对输出
主模型 429、重试后成功 A1 错误、A2 成功 保存两次 Attempt；费用按各自凭据
主模型超时、B 成功 A 未拿到可靠回执、B 成功 A 费用未知、B 正常结算
流式输出 delta 后断开 已对外输出一段正文 清晰中断，不拼接备用模型文本
HTTP200 但空回答 返回 usage 但无 content/tool_calls 记录已花费的用量，并应用空响应策略
模型返回缓存 Token input=4000, cached=3000 价格计算使用正确的缓存部分口径
动态 Policy 改变 同 AgentVersion 不同问法 前缀差异定位到具体消息和 Token 区间
预算近上限 剩余额度低于保守预留 调用前得到预算结果，不先向外发请求

把模型成本相关测试和最终回答正确性测试分开。前者可以全部使用受控 Mock 回执，后者则需要固定任务上的真实模型对照。这样花更少的资源，就能明确验证哪一段代码解决了哪一种问题。
