第 2 讲：把工具调用接成完整的 Agent 循环

用户提问

继续讲下一节

讲解原文

上一节，我们已经有了一个重要能力：

给程序一份“工具名称＋参数”，程序就能找到对应的 Python 函数，并执行它。

这一节继续往前走：工具执行结束后，怎样让模型根据结果继续完成任务？

我们用一个具体任务贯穿这一节：

请计算 (2 + 3) × 4。

预期执行过程如下：

模型调用次数 模型提出什么 程序做什么
第一次 调用 add(a=2, b=3) 执行加法，得到 5，把结果交回模型
第二次 调用 multiply(a=5, b=4) 执行乘法，得到 20，把结果交回模型
第三次 返回“计算结果是 20” 结束循环，向用户返回回答

这里已经出现了一个关键区别：一次用户提问，可以触发多次模型调用。

本节先用一个按固定规则工作的 fake_model 模拟模型响应，让每一步都容易观察。我已经运行验证了下面这个例子；下一节再把它替换成真实模型 API。

一、先认识本节最重要的变量：messages

模型每次处理任务，都需要知道此前发生了什么。我们用一个列表保存这些消息：

messages = [
    {
        "role": "user",
        "content": "请计算 (2 + 3) × 4",
    }
]

这里暂时只需要认识三种角色：

role 谁产生这条消息 例子
"user" 用户 “请计算 (2 + 3) × 4”
"assistant" 模型 “我要调用加法工具”，或者最终回答
"tool" 程序根据工具执行结果生成 加法工具实际返回了 5

模型提出的工具调用，仍然是一条 assistant 消息。

等到 Python 程序真正执行了函数，程序才会生成对应的 tool 消息。

例如：

  • 模型提出：“调用 add，参数是 2 和 3。”
  • 程序执行：add(2, 3)。
  • 程序记录：“这次工具调用返回了 5。”

这三件事分别发生在不同位置，后面读代码时要能指出来。

二、保留上一节的工具函数

下面各段代码可以按顺序放在同一个 Python 文件中。

先准备两个工具和上一节的工具分发函数：

def add(a, b):
    return a + b

def multiply(a, b):
    return a * b

TOOLS = {
    "add": add,
    "multiply": multiply,
}

def execute_tool(tool_call, tools):
    name = tool_call["name"]
    handler = tools.get(name)

    if handler is None:
        raise ValueError(f"未知工具：{name}")

    return handler(**tool_call["arguments"])

这部分你已经接触过了。它的职责很明确：

找到函数，把参数传进去，返回实际执行结果。

它还没有负责“下一步做什么”。这个决定来自后面的模型响应。

三、写一个能提出下一步操作的模拟模型

我们约定，模拟模型每次返回一个字典，其中包含：

  • role：固定为 "assistant"。
  • content：给用户的回答文本；提出工具调用时暂时为 None。
  • tool_calls：这次希望执行的工具调用列表；给出最终回答时为空列表。

这是本节使用的教学数据格式。真实模型供应商的具体协议，下一节再对应。

def fake_model(messages):
    # 取当前消息列表中的最后一条消息
    last = messages[-1]

    # 第一次看到用户任务：先提出加法调用
    if last["role"] == "user":
        call = {
            "id": "call_1",
            "name": "add",
            "arguments": {"a": 2, "b": 3},
        }

    # 收到加法结果：把实际结果作为乘法的输入
    elif last["role"] == "tool" and last["name"] == "add":
        call = {
            "id": "call_2",
            "name": "multiply",
            "arguments": {
                "a": int(last["content"]),
                "b": 4,
            },
        }

    # 收到乘法结果：生成最终回答
    elif last["role"] == "tool" and last["name"] == "multiply":
        return {
            "role": "assistant",
            "content": f"计算结果是 {last['content']}。",
            "tool_calls": [],
        }

    else:
        raise ValueError("模拟模型收到了未定义的消息状态")

    return {
        "role": "assistant",
        "content": None,
        "tool_calls": [call],
    }

这段代码需要仔细看三个地方。

1．messages[-1] 是什么？

last = messages[-1]

它取出列表中的最后一个元素。

随着程序运行，最后一条消息会不断变化：

  • 开始时，是用户的任务。
  • 执行加法后，是加法工具返回的结果。
  • 执行乘法后，是乘法工具返回的结果。

我们的模拟模型根据最后一条消息，选择相应分支。

这里的 fake_model 是为这个算式编写的固定规则：它没有理解自然语言，也没有请求真实模型。真实模型接入后，会根据发送的上下文生成响应。

2．为什么乘法参数要从消息中读取？

注意这句：

"a": int(last["content"])

加法执行后，我们会把结果以字符串 "5" 放进工具消息的 content 中。

因此，这里：

int(last["content"])

会把 "5" 转成整数 5，作为乘法工具的参数。

这一步建立了前后两次工具调用之间的数据依赖。

如果加法实际算出来的是 17，后面的乘法就会使用 17。最终回答同样读取工具消息里的结果。

3．call_1、call_2 有什么作用？

它们标识某一次具体的工具调用。

稍后生成工具结果时，我们会写上对应的 tool_call_id，表示：

这条结果，属于前面哪一次调用。

同一个工具可能被调用很多次，因此工具名称和调用编号承担不同职责：

  • name="add"：说明调用哪个工具。
  • id="call_1"：说明这是哪一次调用。

这一节先理解这个对应关系即可。

四、核心部分：写出 run_agent

现在，工具和模拟模型都有了。接下来需要一个函数把它们组织起来。

def run_agent(user_input, max_rounds=5):
    messages = [
        {"role": "user", "content": user_input}
    ]

    for model_round in range(1, max_rounds + 1):
        print(f"\n第 {model_round} 次模型调用")

        # 1. 把当前全部消息交给模型
        response = fake_model(messages)

        # 2. 保存模型本次的响应
        messages.append(response)

        tool_calls = response["tool_calls"]

        # 3. 没有工具调用，说明本例中的模型给出了最终回答
        if not tool_calls:
            return response["content"]

        # 4. 执行模型提出的工具调用
        for call in tool_calls:
            print(
                f"工具提议：{call['name']}，"
                f"参数：{call['arguments']}"
            )

            result = execute_tool(call, TOOLS)

            print(f"执行结果：{result}")

            # 5. 把实际执行结果加入消息列表
            messages.append({
                "role": "tool",
                "tool_call_id": call["id"],
                "name": call["name"],
                "content": str(result),
            })

    raise RuntimeError(
        "达到最大模型调用次数，仍未得到最终回答"
    )

最后，在文件末尾调用：

answer = run_agent("请计算 (2 + 3) × 4")
print("最终回答：", answer)

运行后，你会看到：

第 1 次模型调用
工具提议：add，参数：{'a': 2, 'b': 3}
执行结果：5

第 2 次模型调用
工具提议：multiply，参数：{'a': 5, 'b': 4}
执行结果：20

第 3 次模型调用
最终回答： 计算结果是 20。

五、把循环的关键几行真正看懂

1．为什么执行工具前，要先保存模型响应？

response = fake_model(messages)
messages.append(response)

模型响应里可能包含工具调用提议。我们把它保存下来，后续消息中就同时保留了：

  • 模型提出了什么调用。
  • 程序执行后得到了什么结果。

例如，加法执行完成后，消息列表的含义是：

顺序 角色 消息内容
1 user 请计算 (2 + 3) × 4
2 assistant 提出 call_1：调用 add(a=2, b=3)
3 tool call_1 执行结果为 5

这样下一次模型调用时，程序就能提供完整的调用与结果记录。

2．工具算出结果后，模型怎样知道？

工具执行这一行：

result = execute_tool(call, TOOLS)

只会得到一个 Python 变量，例如：

result = 5

要让模型在下一次调用中获得这个结果，程序还需要做两件事。

第一件，把结果加入消息：

messages.append({
    "role": "tool",
    "tool_call_id": call["id"],
    "name": call["name"],
    "content": str(result),
})

第二件，在下一轮再次调用模型：

response = fake_model(messages)

模型能够使用工具结果，依赖的是这次结果回填和下一次模型调用。

你以后看到 AgentHub 里的 observation，可以先把它理解为“把实际执行结果整理成模型能够继续读取的消息”。

3．循环在哪里继续？

执行完工具并追加结果后，这一轮 for 循环的函数体走完，程序自然进入下一轮：

for model_round in range(1, max_rounds + 1):

进入下一轮时，仍然使用同一个 messages 列表。这个列表已经包含刚刚发生的工具提议和执行结果。

所以：

  • 第一次模型调用，收到用户任务。
  • 第二次模型调用，收到用户任务、加法提议和加法结果。
  • 第三次模型调用，又多了乘法提议和乘法结果。

4．循环在哪里结束？

关键在这里：

if not tool_calls:
    return response["content"]

Python 中，空列表 [] 在条件判断中为假，因此：

not []

为真。

在本例的响应约定中，模拟模型返回：

{
    "role": "assistant",
    "content": "计算结果是 20。",
    "tool_calls": [],
}

程序就进入结束分支。

另外，return 会退出整个 run_agent 函数，把回答交给调用者。

工具执行得到 20 时，循环仍然可以继续；直到模型返回最终回答，run_agent 才正常结束。

5．max_rounds 限制的是什么？

它限制的是模型调用次数。

这个例子中：

  • 用户提交了 1 次任务。
  • 程序调用了 3 次模拟模型。
  • 程序执行了 2 次工具。

这三个计数要分清楚。

如果把调用改成：

answer = run_agent(
    "请计算 (2 + 3) × 4",
    max_rounds=2,
)

两个工具都可能已经执行完，但程序没有第三次模型调用的机会，因此会抛出：

RuntimeError: 达到最大模型调用次数，仍未得到最终回答

这是一个很有价值的观察：拿到某个工具结果，与完成整个 Agent 任务，是两个不同的判断。

六、这段小程序怎样对应到 AgentHub？

回到我们前面核查的源码，这节的几个动作都有明确位置：

本节的小程序 AgentHub 中对应的职责
TOOLS 与工具查找 ToolRegistry 管理内置工具名称与处理函数的映射
fake_model(messages) runtime_graph.py 中的 model 节点组织模型调用并处理响应
执行工具 运行图通过 read_execute、action_execute 等节点组织工具执行
把结果追加为 "tool" 消息 observation 节点把实际执行结果加入模型消息
判断继续还是结束 图的连线以及 after_model、after_observation 等函数决定后续路径

正式项目中的控制流由状态图组织，同时加入权限、预算、审批和持久化等机制。我们现在写出的循环，可以帮助你理解这些节点为什么要连接起来。工具注册表 · 运行图与结果回填

七、本节做两个小改动

第一个：验证数据确实传到了下一步。

把 fake_model 中第一次加法的参数改成：

"arguments": {"a": 10, "b": 7}

并把演示问题改成：

"请计算 (10 + 7) × 4"

保持 run_agent 原样。

你应该观察到：

  • 加法结果为 17。
  • 乘法收到的参数为 a=17, b=4。
  • 最终回答为 68。

注意，当前模拟模型的第一步参数写在代码里，只修改提问文本不会改变它的行为。下一节接入真实模型后，工具名称与参数才会由模型根据问题生成。

第二个：观察执行上限。

把 max_rounds 分别设为 2 和 3，看两次运行在哪一步产生差异。重点看：最后一次工具执行结束以后，是否还有机会让模型生成最终回答。
