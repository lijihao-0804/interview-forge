2026-11-20 版本同步：新旧结论对照

一、本次核验到哪里

本次读取的是 GitHub 仓库 lijihao-0804/AgentHub 的主分支，并把阅读口径固定到提交 cdc9d084d3a20e71355401952ee394da4e56273b。与上一版第 11 讲核验的 ab2b5b046da86bb2b0bd0eb65f7bab3a59eff239 相比，共有 31 个新增提交、132 条变更路径。这些是 Git 比较中的提交与路径计数，不是 31 项独立功能或 132 个独立缺陷。固定提交 版本比较

本次完成了源码、相关测试定义和仓库验收材料的核对，更新教学与需求状态。没有重新运行你的项目、迁移你的业务数据库、执行浏览器矩阵或发起付费模型实验。 因此，下文“已实现”指这份源码已经包含实现；“报告记录”指仓库保留的历史验证；不把它们冒充当前部署的现场验证。

旧讲解的原文继续保留。旧章中的“当前”“暂时没有”“下一步”带有写作时点，阅读当前项目状态时，以本节和第 12—27 讲为准。这也包括仓库自己的历史文档：它们可以作为设计过程材料，不能只看标题中的“当前状态”就忽略内部日期。

二、最值得你先读的变化

1．第 11 讲的 RT10 练习，已经有真实实现可以对照了

最新知识库页面让展开修订详情参与持续观察：即使列表先显示结束，只要展开详情仍有进行中修订，或者当前修订还没有出现在详情里，仍会跟进；页面隐藏与请求进行中时避免不必要的读取，可见性恢复时重新检查。知识详情页

但当前是固定 5 秒轮询，并没有完整采用旧课示例的 5/10/20 秒退避、连续四次失败暂停。源码条件还显示：列表终态后，若详情读取失败并清空数据，自动跟进条件可能不再成立，需要错误区重试；这是源码条件推导，本次没有在浏览器复现。第 22 讲将它作为“已有核心修复与仍需定义的观察合同”来讲。

2．数据库约束与任务领取，从应用约定变得更扎实

DocumentChunk 已加入 (workspace_id, knowledge_base_id, document_id, document_revision_id) 到修订表对应列组的外键，迁移为 0061_chunk_document_revision。旧资料把它列为 RG15 待办，最新应改为已经落地的数据完整性案例。迁移先检查旧错配，发现问题会中止，不替你猜哪份文档才是正确归属。知识模型 迁移

入库领取现在同时检查 attempt_count < max_attempts，在成功领取时原子增加次数。Worker 也在解析、编码、索引等边界验证租约，失租后阻止继续派发和非法终态提交。这修复了 RT08、RT09 的关键窗口，但不等于能撤回已经发到远端的 upsert，或立即杀死已开始的同步编码线程。摄取状态机 Worker

3．并发新修订与手动重试的细节得到修复

上传同一文档的新修订时，服务在分配修订号前锁定该文档，避免两个合法请求同时得到相同的下一编号。手动重试会清空 Job 的旧错误码与安全错误消息，减少“任务已重启，页面却仍像失败”的歧义。自动退避仍可能保留上次错误作为诊断，状态和错误文本仍要分开读。知识服务

4．RAG 修复的是证据交付的具体错误，不是宣称所有答案都正确

新实现修复了 CRLF 段落分割与规范化长度问题；证据只有实际被预算接纳后，才会登记其覆盖范围，避免一个已被淘汰的大块继续把后续可用小块压掉。多快照检索在配置相应字节预算的路径中，对合并结果执行共享预算，而不再只分别约束每个快照。证据接纳 知识工具

数字引用校验与部分拒答一致性规则也更严格，但它们仍是有合同、有范围的机械规则。引用编号存在，不等于每个结论都得到语义支持；针对单个计数问题的修正，不是一个通用“模型事实验证器”。第 19 讲会用失败案例讲清这层差别。引用问答 拒答一致性

5．模型没有可见答案，也可能已经产生费用

网关对供应商完成但返回空文本、空工具调用的情况保留已有 usage 与费用证据，fallback 前记录 model.empty_response。因此最终成功的逻辑调用，仍可能有多个失败尝试和多笔计量回执。已出现可见流式增量后，仍不允许透明拼接另一个模型的回答。网关

6．取消与审批撤销现在一起提交，历史遗留也有协调路径

取消 Run 时撤销待审审批的更新已放进同一个数据库事务；协调器也会处理历史上 Run 已 CANCELLED、审批却还 PENDING 的组合。这个改动处理的是待审状态一致性，不能把已 CLAIMED 或 UNKNOWN_OUTCOME 的外部动作变成“确定没有执行”。运行服务 审批服务 审批协调

审批原本就已有 resume_pending 持久恢复意图和后台补发，不能再写成“项目完全没有后台审批恢复”。仍值得改进的是统一执行交付语义，以及初始 Run 提交与入队之间的可靠派发窗口。后台审批任务

7．前端改进涉及身份与权限，不只是视觉调整

同源标签页刷新增加了支持 Web Locks 时的串行保护；迟到刷新与 401 绑定发出时的会话身份；工作区权限区分尚未加载、加载失败、确认有权和确认无权。创建另一个组织的工作区时，要按目标组织角色判断，而不是套用当前工作区角色。检索和版本选择也使用代次隔离，避免 A→B→A 的旧响应污染新选择。认证客户端 会话 Provider 租户路由

8．评测开始更准确地区分“没有答案”和“答案错误”

Runner 只在 final_output is not None 时保存输出哈希；精确 QA 的冻结判定已经为错答时，空失败标签不会再遮住相应分类；step index 为 0 不再被当成缺失；评测器 manifest 不兼容时，相关统计接口给出明确 409，而不是笼统 500。评测 Runner 错误分类 统计服务

这些改动改善的是数据含义和诊断可信度，不应直接写成“模型准确率提高了”。没有输出、实际空答案、实际错误答案和未知观测需要分别统计。

RT13 索引灾后重建与缺失诊断仍需完整操作流程 READY 状态与索引实际存在性分开检查
RT14 已有基本健康探测，业务可推进性仍需观测 Worker 在线、队列年龄、阶段进度和模型可用性
RT15 UNKNOWN_OUTCOME 仍需要业务核对工作流 Handoff 关闭不等于外部副作用已经确认

运行域这次还新增了“取消 Run 与待审撤销同事务、协调旧遗留”的具体修复。它增强了状态一致性，但没有授权我们把以上所有恢复需求整体标为完成。运行服务 审批协调 知识页面

五、新验收报告怎么读，才能不被数字误导？

仓库 2026-11-19 的 RAG 复核记录包括长文 LF/CRLF 对照、固定历史候选池回放和录制回复解析检查。候选池回放验证既定候选之后的交付变化，不重新证明编码器召回；录制回复本地解析变好，不等于新模型生成能力提高。报告中 917 项和后续 70 项存在重叠，不能相加称 987 个独立测试。RAG 复核记录

2026-11-20 的前端报告记录了 38 种页面模板、41 个页面状态和 332 个可见控件实例。332 不是 332 个独立业务功能，也不是 332 次真实业务写入；19 个禁用控件另有复查。部分场景使用固定模型、确定性评测，非空检索补测使用隔离内嵌 Qdrant 和固定编码/重排器，因此这组材料支持页面与业务链路判断，不支持 BGE 检索质量或真实模型准确率宣称。工作区交互记录 禁用控件复查

你在面试里可以说“我核查了这些修复的源码、失败场景和验收范围”，然后展示对应代码。不要把仓库作者的历史实测全部改写成“我今天测试了”，也不要把固定应答的演示改写成真实模型成绩。

原主线 补充课程 新增的理解目标
