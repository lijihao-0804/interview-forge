第 15 讲：模型网关——可靠性、失败归因与成本账

本讲按 2026-11-20 核验的 cdc9d084d3a20e71355401952ee394da4e56273b 讲解。代码位置来自这一固定提交；示例预算金额只用来解释机制，不是供应商报价。本次没有调用付费模型或重新跑费用实验。

15.1 先换一个观察角度：调用模型不是一个函数的成败

你已经知道 Agent 循环里会反复调用模型。接下来真正值得学的是：一次“请模型回答”进入生产系统后，会分裂成几种不同的事实。

例如用户问：“请根据客户记录创建一个工单。”

系统向主模型发出请求，主模型超时；网关再次请求，得到空文本，但响应里明确写了输入 100 tokens、输出 256 tokens；于是切到备用模型，拿到了可用的工具调用。你看到的界面最终正常，不代表中间没有失败，也不代表只付了一次钱。

至少要分开记录四件事：

观察对象 它回答的问题 为什么不能用别的字段代替
逻辑模型调用 Agent 的这一轮是否取得了可继续处理的结果 一轮可能有多个物理请求
供应商尝试 向哪个 provider/model 实际发送了几次 重试、降级都会增加尝试
可用输出 是否有合法文本或工具调用 HTTP 成功不等于输出可用
用量与费用证据 哪次尝试有 usage、估算费用、最终账单 空输出和失败请求也可能产生费用

AgentHub 的 ModelGatewayService 是这些语义的集中管理者；provider adapter 负责一次实际请求。最新版对“空答案但有计量回执”的修复，正是把第三件事和第四件事重新分开了。源码：网关、计时与回执计数

这里最容易形成的错误直觉是：“只要最终请求成功，把最后一个 response 存下来就够了。”这样会把前面失败尝试的费用、故障比例、降级原因一起抹掉。下一次你想优化模型成本，就会从一个错误的分母开始。

15.2 把五类对象分清，源码一下就容易读了

在模型接入这一层，可以按“保存配置、冻结配置、执行调用”三步理解：

对象 负责什么 不负责什么
ProviderCredential provider、凭据、启用状态、连接端点等 不等于一次运行的完整模型策略
ModelProfile 模型名、temperature、最大输出、超时、能力和 fallback 绑定 不等于已发布版本永远读取的可变配置
ResolvedModelExecutionPlan 运行使用的冻结主模型、降级链与重试策略 不保存一份可随意传播的明文密钥
ModelRequest 这一轮真正要送出的消息、工具定义和请求要求 不能自己决定越过工作区权限
ModelResponse 文本、工具调用、usage、费用估算、结束原因等 不自动代表业务任务完成或最终账单结清

普通配置解析会沿 fallback 链读取 profile，校验启用状态和能力，并用 visited 集合发现循环。已发布的模型执行计划走另一条路径：使用冻结的非秘密配置，再验证当前凭据仍然可用、provider 和工作区一致；若冻结了出站端点，还要核对端点没有被悄悄替换。源码：profile 解析、冻结执行准备、请求与响应契约

为什么已经“冻结”了，还要读当前凭据？

因为冻结的是这次运行采用什么行为配置，不是授予一张永不撤销的通行证。管理员停用泄露的 API key 后，旧 AgentVersion 不能因为“我发布时有权限”就继续使用它。版本可复现与权限可撤销是两条同时存在的约束。

这一点也会反复出现在工具、知识库和审批里：内容身份可以固定，访问权仍需要在执行时检查。理解了这里，后面看恢复执行时重新鉴权就不会觉得是在重复劳动。

15.3 为什么不能拿着数据库连接等模型回答？

源码中有一个很容易被略过的设计：_PreparedModelGateway。

它先在短生命周期的 repository session 中解析配置和当前凭据，然后把执行需要的内容放到一个脱离数据库 session 的执行对象中。真正漫长的网络请求在后面发生。类注释明确说明，它的目的是避免把 AsyncSession 持有到模型网络等待结束。源码：准备后的网关

假设你的数据库连接池只有 20 条连接，20 个用户同时发起各需等待 30 秒的模型请求。如果每条请求都“开事务→调用模型→写结果→提交”，这 20 条连接可能长时间被网络等待占用。此时查看工单、列出知识库这些很短的 SQL，也会排队。

更合理的时间关系是：

  1. 短事务读取并校验当前执行身份。
  2. 得到可执行的冻结配置，结束数据库作用域。
  3. 调用外部模型。
  4. 用另一个短事务持久化结果、状态或计量记录。

这里不是要求“一次 HTTP 请求只能用一个事务”，而是让事务覆盖需要原子性的数据库变更，不覆盖不可控的外部延迟。将外部 HTTP 请求放进 SQL 事务，也不会使外部服务参与 PostgreSQL 回滚。

练习： 找到 prepare_resolved 和 _PreparedModelGateway.generate_resolved，观察从前者传给后者的到底是 session、ORM 查询器，还是已经解析好的执行数据。这个练习比记住“要用连接池”更能帮助你写出不会耗尽连接的代码。

15.4 能力检查不是“模型名字看着像能用”

同样的模型接口可能支持文本，不支持工具；支持普通返回，不支持你要求的流式协议；或对结构化输出有不同的能力限制。

AgentHub 先依据请求及操作类型得到实际需要的能力，再检查链上的 profile。这样，“我要工具调用，但 fallback 只支持文本”的配置会在实际发送前暴露，而不是主模型故障后才出现第二次难以解释的错误。源码：能力判定、fallback 解析

可以把这看成一种契约：

  • 调用方提出“我这次需要什么”。
  • 配置层声明“这个模型能做什么”。
  • 网关检查二者是否兼容。
  • provider adapter 只执行已满足前提的请求。

不要把“厂商宣传这个模型能力很强”当成接口契约。项目需要的是当前 adapter 能正确发送和解析的能力。添加新 provider 时，除了“能输出一句话”，还应该验证工具调用参数、流式事件、usage、错误映射等路径。

15.5 重试和 fallback 分别改变了什么？

重试是同一条模型配置再次尝试；fallback是进入后续备用配置。它们都可以改善可用性，但代价不同：可能增加费用、延迟，也可能改变回答风格和行为。

在当前网关里，重试次数来自 request 的 retry_policy；每个 profile 按这个上限处理重试，再进入下一 profile。provider adapter 的请求载荷明确设置 num_retries=0，避免 SDK 在网关不知道的地方再套一层重试。源码：网关重试循环、LiteLLM adapter

一个教学例子：网关允许 2 次尝试，链上有主、备两个 profile。若每个 profile 都用满自己的尝试次数，一次逻辑调用最多可能触达 4 次 provider 尝试。若 SDK 还在每次内部自动再试 3 次，你观察到的请求数就会远大于网关账面上的次数。

当前 _generate_chain 的重试循环本身没有实现通用的指数退避与随机抖动。你以后设计限流恢复时，可以增加这些机制，但不能在面试里因为项目存在重试就顺口说“已经做了指数退避”。同样，不可重试的 error 会结束当前 profile 的重试；这不自动等价于结束整条 fallback 链，要继续读外层循环。源码：重试分支

重试策略应回答四个问题：

  1. 哪些错误可以再试，哪些代表配置本身不合法？
  2. 每个逻辑调用最多产生多少物理请求？
  3. 总延迟和总费用的上限由谁控制？
  4. 哪些请求一旦已经让用户看见内容，就不能再透明替换？

最后一个问题尤其容易漏掉。

15.6 为什么流式回答露出一个字后，恢复策略就变了？

假设主模型先输出：

“你可以直接删除……”

随后连接中断，fallback 又输出：

“操作需要先审批。”

如果直接拼起来，用户得到的既不是主模型的一次完整回答，也不是备用模型的一次完整回答。工具增量更敏感：一段未完成的 JSON 参数不能与另一个模型的参数接在一起。

所以当前 stream 处理会记录是否出现 MESSAGE_DELTA 或 TOOL_CALL_DELTA。在还没有可见增量前，可以按规则重试或降级；一旦已有可见增量，再遇超时或错误，就返回 MODEL_STREAM_INTERRUPTED，而不是偷偷接上另一段输出。源码：流式 visible 分支

这不意味着产品永远不能提供“重新生成”。它意味着重新生成应当成为一个有明确身份、界面反馈和证据记录的新操作，而不是伪装成上一段回答的无缝延续。

故障排查时，可以先问：“用户是否已经收到任何可见增量？”这往往比先问“是不是网络有问题”更快地决定下一步该读哪个分支。

15.7 最新修复：空响应为什么必须保留 usage？

当前可用性检查认为，有非空文本或工具调用才是可用模型结果。若供应商完成了一次请求，但两者都没有，网关会把它归为不合格响应。源码：11

然而，不合格响应仍可能附有真实 usage：

{
  "text": "",
  "finish_reason": "length",
  "usage": {
    "input_tokens": 100,
    "output_tokens": 256,
    "total_tokens": 356
  }
}

这份 JSON 是依据测试场景整理的教学表示，不是本次发出的在线请求。它要表达的是：“我没有得到可用答案”与“供应商没有进行计费工作”不是同一个命题。

最新版新增了两种处理：

  • 若就此结束，失败 trace 中仍保留该完成响应实际提供的 usage/cost。
  • 若继续 fallback，在切换前写入 model.empty_response 记录，把前一次响应的计量挂在真正消耗它的 provider/model 上；最终逻辑 trace 描述后续结果。

计时统计中，provider_attempt_count 仍由逻辑调用的 attempt_count 统计；空响应 span 只补 usage/cost 的已知回执数量，避免同一尝试计数两次。源码：空响应记录、计时捕获、回归测试

例如主模型空响应有 28 tokens，fallback 成功有 2 tokens：

  • 逻辑调用是 1 次。
  • 物理尝试是 2 次。
  • 若两者都有 usage，已知 usage 回执是 2 份。
  • 最终返回给调用方的 response 仍然是 fallback 的结果。
  • 总消耗分析不能只读最后 response 的 2 tokens。

反过来，如果供应商根本没有返回 usage，就只能保留“未知”。不能拿本地估算 token 去冒充供应商回执，不能把缺失值写成 0。观测系统的价值之一，就是把“已知失败”和“证据不完整”分开。

15.8 成本要分成四层，才能解释“预算没超却账单上涨”

你可以先记住四个不同名词：

名词 产生时机 适合回答的问题
预计成本 请求前或请求后按 token/价目表估算 这条路径大约多贵
保守预占 发送前以可信上界占住额度 还有没有足够额度允许这次尝试
响应用量与成本估算 供应商返回或 adapter 计算后 这次返回目前有哪些计量证据
最终结算 获得可信供应商账单后 应当正式记多少费用并释放多少预占

AgentHub 有 Run 级预算账本和网关侧预算适配接口。账本预占逻辑在账户锁下验证币种、精度、稳定 attempt identity，检查“已有预占 + 已结算 + 新预占”不超过上限。重复 identity 只有内容一致时才是同一项预占；网关适配器遇到已经存在的 attempt，会拒绝再次发出，而不是把账本幂等误解成“可以再请求一次”。源码：Run 预算账本、预算适配器

一个假设例子：Run 总预算 1.00，已结算 0.20，未决预占 0.50，新的调用需保守预占 0.40。即使你猜前一笔实际只花了 0.10，也不能在没有结算证据时把那 0.50 自动释放，然后允许新调用。否则多个并发尝试会同时利用“我估计还能省的钱”，最终突破承诺。

在这个账本的结算合同中，RESPONSE_ESTIMATE 不会被当成最终供应商账单。只有可信调用方提供 PROVIDER_BILL 类型的结算证据，才允许把原预占替换为正式费用。真实账单若超过先前预占，系统应保留这个事实并阻止新增超支，不应为了让报表好看而截断金额。源码：16

但还要补一句很关键的话：存在账本原语和可接入适配器，不等于所有产品入口、所有模型、所有辅助步骤已经被统一覆盖。 接某条调用链时仍须检查它是否绑定了 budget、是否有可信上界、重试/fallback 是否逐次经过预占、最终账单由谁取得。不要只看到数据库里有 run_budget_accounts 就下整体结论。

最新空响应修复也遵循这个边界：已完成但无可用答案的响应，不会被随意标成“未知网络结果”并丢掉原回执；其已有预算占用保留，等待规定的对账方式处理。源码：空响应预算测试

15.9 金额精度、日志脱敏和可解释性为什么在同一讲？

因为你最终必须把一条用户回答追到它的调用、计量和失败原因。如果这条证据链一端不可信，另一端很难补救。

金额用 Decimal，可以避免把很多小额费用加总时引入二进制浮点误差。最新版安全 trace 对有限、非负的 estimated_cost Decimal 转为字符串保存，保留例如很小金额的精度；非法 NaN、Infinity、负金额不会以这个金额字段进入安全投影。源码：安全 trace、精度回归用例

但是“有安全 trace”也不意味着任意日志都可以直接记录完整 prompt、工具参数或凭据。观察目标应是问题定位需要的标识、模型身份、attempt、延迟、usage、故障码，而秘密信息和不必要的正文应通过明确投影控制。

本讲给你的排障顺序是：

  1. 先找 Run 和逻辑调用身份，确定是不是同一轮。
  2. 展开物理尝试，确认是否重试、是否 fallback。
  3. 查看每次尝试的 usable output 与 usage/cost 是否分别已知。
  4. 确认是否已有可见流式内容，解释为什么没有自动切换。
  5. 若涉及预算，检查预占是否已提交、attempt identity 是否重复、账单是否真的结算。
  6. 最后再判断是模型质量、网络可用性、配置契约还是费用观测的问题。

15.10 本讲练习：用三张小表解释一次“最终成功但更贵”的运行

不用先写代码。构造如下教学场景：

  • 主模型第一次超时，没有 usage。
  • 主模型第二次返回空答案，有 usage。
  • fallback 给出可用工具调用。
  • 工具执行成功，模型又进行一轮总结。

分别画出“逻辑调用表”“物理尝试表”“费用证据表”。每行标明 known/unknown，回答以下问题：

  • 最终 Agent 成功，网关内部是否存在失败？
  • 第二次空答案能不能按零成本记录？
  • 第一次超时能不能断言供应商没有收费？
  • 总结那一轮是不是新逻辑调用？
  • 你现在能计算准确总成本，还是只能计算已知部分？
  • 若想做成本优化，应该减少哪一类重复尝试，而不是只缩短最后答案？

当你能把这三张表讲清，面试中的“你们做了哪些网关治理”就不再是背“支持重试、降级和限流”几个词。
