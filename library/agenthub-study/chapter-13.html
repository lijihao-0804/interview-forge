第 10 讲：前端与异步执行

本讲目标：能从一次页面操作，追到 HTTP 请求、后端业务状态与执行者，再追到事件和页面更新；发生断线、刷新、重复提交、后台崩溃时，知道哪一层负责恢复。

源码基线：沿用前几讲的 AgentHub 固定提交 0。下面会区分项目已有实现、帮助理解的简化代码和可考虑的扩展设计。不会把常见架构模板当成本项目事实。

这一节要建立的核心认识是：

后端保存“任务实际处于什么状态”，前端维护“当前用户看到了什么”。事件让用户及时看到变化，重新读取持久状态让页面在断线、刷新之后重新对齐事实。

你已经了解 Agent 的工具调用和循环。这次我们把它放回真实产品：用户点击发送，按钮变灰，页面开始显示文字，工具执行中途等审批，用户刷新浏览器，任务仍然需要有明确身份和可查询的状态。

整个过程需要回答四个问题：

  1. 谁接收用户意图，创建了什么业务记录？
  2. 谁真正执行任务，浏览器断开是否影响它？
  3. 页面靠什么知道发生了变化？
  4. 页面丢掉了本地状态之后，靠什么恢复？

一、先把“页面”“连接”和“任务”分开

1.1 页面并不直接操作 PostgreSQL

在 AgentHub 中，浏览器主要做交互和展示：读取输入、发请求、解析响应、更新 React 状态。浏览器通过后端 API 操作业务，不会拿数据库连接去直接执行 SQL。

后端负责检查身份与工作区权限、验证输入、保存 Run、执行或派发任务。模型调用、工具执行、知识检索等发生在后端执行环境。前端拿到的是经过后端组织和权限处理的数据。前端 API 层、Run 路由、执行服务

这里有六个容易混在一起的对象：

对象 是什么 刷新浏览器后如何看待它
React 组件状态 当前页面中的输入、临时文字、加载状态 通常会丢失，需要重新建立
HTTP / SSE 连接 浏览器与服务器之间的一次通信 原连接消失，需要重新请求
Thread 持久化的会话容器 根据 Thread ID 重新读取
Turn 该会话的一次用户提交 根据持久记录重建这一轮消息
Run 一次实际执行实例 根据 Run ID 查询状态和结果
Worker / API 执行任务 当前负责推动 Run 的计算过程 要看执行模式、租约和进程是否仍然存活

Thread、Turn、Run 的关系，可以理解成“在哪个会话里”“提交了哪一次问题”“由哪一次执行处理它”。Playground 可以直接创建 Run；会话式聊天还需要 Thread 和 Turn。Thread 服务、Run 数据模型

所以：

浏览器刷新，不等于用户又提出了一次新问题；连接断开，也不等于 Run 的数据库记录消失。

不过，“记录仍在”也不等于“计算一定还在继续”。这取决于后面要讲的执行模式。

1.2 这三个“异步”不是同一件事

“异步”的位置 实际含义 没有自动获得什么能力
浏览器 await fetch(...) 等网络时，页面仍可处理其他交互 不保证后台任务持久存活
Python async def 等数据库或网络 I/O 时，事件循环能处理其他工作 不自动变成独立 Worker，不自动抗进程崩溃
Celery 后台任务 通过队列把执行交给独立进程 不自动保证只执行一次，也不自动保证任意副作用可重试

一个常见误解是：“接口写成了 async def，所以关掉浏览器也没关系。”

真正要追的是：执行任务由谁持有？它的生命周期和请求、订阅者、进程之间是什么关系？ AgentHub 对这个问题有明确的两种实现分支，不能仅靠一个 async 关键字判断。执行服务、Worker 入口

读源码时，每跨一层都追问一句：

这比只记函数名更有价值。

三、先补前端基础：页面为什么会“自己更新”？

3.1 useState：改变显示所依赖的数据

假设页面中有：

// 教学简化代码，并非项目原文件的完整实现。
const [runStatus, setRunStatus] = useState<string | null>(null);
const [assistantOutput, setAssistantOutput] = useState("");

return (
  <section>
    <p>运行状态：{runStatus ?? "尚未开始"}</p>
    <article>{assistantOutput}</article>
  </section>
);

收到事件后执行：

setRunStatus("RUNNING");

setAssistantOutput(current => current + delta);

React 会根据新的状态重新计算需要显示的界面，再把变化更新到页面上。

注意第二行用的是函数形式。流式事件连续到达时，新文本要接在“当前已有文本”后面；如果用某个旧闭包里的字符串去拼接，可能把后来已经到达的内容覆盖掉。

AgentHub 的 handleEvent 就用这一形式处理 message.delta；同时分别维护 finalOutput、活动列表、usage、审批状态和错误信息。Playground

3.2 useRef：保存控制信息，不把每次变化都当成一次界面更新

项目里有几类 Ref：

Ref 保存什么 为什么需要它
streamRef 当前 AbortController 关闭当前浏览器流连接
lastSequenceRef 已观察到的最大事件序号 重连时提供游标
generationRef 当前页面操作的世代编号 阻止旧异步响应污染新页面
recoveryRef 已处理的恢复身份 避免同一恢复流程重复启动

这里的“世代编号”很好理解。

用户原本在看版本 A，网络很慢；随后切到版本 B。A 的请求晚到，如果直接 setState，B 的页面就会突然出现 A 的结果。

简化写法：

const generationRef = useRef(0);

async function loadRun(runId: string) {
  const generation = generationRef.current;
  const run = await getRun(runId);

  if (generation !== generationRef.current) return;
  setRun(run);
}

function switchVersion() {
  generationRef.current += 1;
  streamRef.current?.abort();
  clearVisibleRun();
}

abort() 尽量停止旧连接；世代检查处理“请求已经完成、回调已经排队，或者某些请求根本没有被取消”的情况。

取消网络操作和拒绝过期结果，是两个互补措施。 项目的普通数据 Hook 主要靠身份与世代校验忽略过期响应，并不是把所有旧请求都物理取消。Playground、工作区数据 Hook

3.3 useEffect：连接外部世界，也负责收尾

页面挂载、工作区切换、Run ID 改变时，可能要建立连接或启动轮询；页面离开时，要清理计时器和订阅。

React 的 Effect 可以返回清理函数，在相关依赖变化或组件卸载时执行。它适合管理这些外部连接，但不会替你定义“停止监听是否取消业务任务”的业务语义。React 官方说明

AgentHub 还会在会话或工作区身份变化时重新挂载业务组件树，让旧工作区的页面状态失效；之后各异步回调仍需要自己的有效性校验。App Shell

四、用户点击一次“运行”，请求实际怎样发出去？

以 Playground 为例。

4.1 前端先整理本次操作的输入

startRun 会检查版本和输入，关闭旧流，增加操作世代，清空上一轮展示，设置本地 RUNNING 和 streaming=true，然后发起请求。Playground

注意：此时的本地 RUNNING 是让界面立刻响应操作，尚不能证明后端已经创建 Run。

前端本地至少有两组不同的信息：

  • streaming、busy：当前页面是否正在通信、提交动作。
  • runStatus：该 Run 的业务状态。

因此完全可能出现：

  • streaming=false，但 Run 正在等待审批。
  • 连接已经失败，后台 Run 仍在运行。
  • 后台已经成功，本地尚未收到更新。

不能只用一个 loading 布尔值表达这三种情况。

4.2 HTTP 请求是前后端约定的业务入口

流式 Run 的路径是：

POST /api/v1/workspaces/{workspace_id}/agent-versions/{version_id}/runs/stream
Authorization: Bearer <access_token>
Content-Type: application/json
Accept: text/event-stream

{"input_text":"请查询这份文档并解释结论"}

这是按项目接口构造的示例。前端用 fetch 发出 POST，带上输入、认证信息、接收流的声明，以及可取消的 signal。流式客户端

这些字段各有作用：

部分 作用
workspace_id 当前工作区的业务作用范围，后端仍必须验证访问权
version_id 本次运行使用哪个发布版本
input_text 用户这一轮输入
Authorization 提供访问身份
Accept: text/event-stream 表示客户端希望接收 SSE
signal 控制浏览器这次网络读取的取消

把 workspace ID 写在 URL 里，不等于已经授权；把按钮隐藏，也不能代替后端权限检查。

通用 API 客户端还负责把 API 错误包装成带 code 和 HTTP status 的 ApiError。HTTP 401、403、422、500 等响应不会仅因状态码就让 fetch 自动抛出网络异常，所以代码要检查 response.ok。API 客户端、Fetch 官方说明

还有一个容易忽略的项目细节：普通 JSON 请求走的通用客户端，支持认证刷新后最多重试一次；流式请求有自己的直接 fetch 路径，不能认为通用 JSON 客户端的所有重试行为会自动套到 SSE 上。API 客户端、流式客户端

4.3 后端先建立 Run，再决定如何执行

流式 POST 的关键顺序是：

  1. 解析与校验请求。
  2. 检查执行权限、工作区和 AgentVersion。
  3. prepare_stream 创建并提交 Run，冻结本次执行所需的版本与相关快照。
  4. 根据配置选择执行方式。
  5. 返回 StreamingResponse。

关键逻辑可简化为：

# 教学简化：保留实际分支，省略依赖注入、错误处理和参数细节。
run = await service.prepare_stream(context, version_id, input_text)

if settings.run_execution_in_worker:
    await queue.enqueue(workspace_id=context.workspace_id, run_id=run.id)
    stream = service.attach_stream(context, run_id=run.id)
else:
    stream = service.stream(
        context,
        prepared_run=run,
        graceful_disconnect=True,
    )

return StreamingResponse(stream, media_type="text/event-stream")

先有持久 Run，后有执行和展示，才能让“这件事”拥有脱离某次浏览器请求的稳定身份。Run 路由、执行服务

但不要过度概括：流式 POST 显式提前 await prepare_stream；GET 跟随接口中，一部分业务校验在异步生成器开始迭代时发生。不是所有 SSE 错误都必然在 HTTP 响应开始前，以普通 JSON 错误形式返回。

4.4 HTTP 状态和业务状态要分开读

接口 该版本的实际行为 应如何理解
普通 POST /agent-versions/{id}/runs await service.run(...)，再返回 201 JSON 普通入口等待执行结束或暂停，不是统一入队立即返回
流式 POST /agent-versions/{id}/runs/stream 成功建立 SSE 响应时通常是 200 后面还可能成功、失败、取消或等待审批
GET /agent-runs/{id} 返回当前持久状态 是当前 Run 事实的查询入口
GET /agent-runs/{id}/stream 观察已有 Run 不创建新 Run

因此，“Network 面板显示 200”只能证明这一层 HTTP 响应成功建立，不能证明 Agent 已经成功完成任务。Run 路由

五、后台到底是谁在跑？必须理解两种模式

该版本配置中，run_execution_in_worker 默认是 False。也就是说，不能因为仓库有 Celery、Redis 和 Worker，就认为所有 Agent Run 默认都进队列。配置

5.1 默认模式：在 API 进程里启动执行任务

API 中的 producer 推动运行；Hub 把事件分发给浏览器订阅者。它并不是每来一个浏览器连接就重新跑一遍 Agent，同一个执行和观察连接可以被分别管理。

但是，当前实现仍然设置了“没有订阅者时的宽限”。默认是 60 秒：短暂刷新或重连有机会重新接上；如果持续无人订阅，进程内生产任务会被终止。

所以，“关页以后后台一定一直执行”不适用于默认模式。任务终止后如何落到失败、取消或需要人工检查等状态，还要看当时的执行阶段与收尾逻辑。执行服务、Stream Hub、配置

5.2 Worker 模式：执行与浏览器订阅进一步分离

配置打开后，API 把 Run ID 等少量身份信息交给 Celery 队列。Worker 读取数据库中的 Run，检查状态、权限和执行所有权，再启动执行。

Worker 使用 detached=True，不因没有 SSE 订阅者而停止。浏览器关掉后，任务可以继续由 Worker 推进；但 Worker 崩溃、依赖故障、租约丢失仍会影响执行。队列适配器、Worker 入口

队列消息主要传：

{
  "workspace_id": "工作区 ID",
  "run_id": "已经保存的 Run ID",
  "request_id": "请求追踪 ID"
}

完整的任务事实由数据库承载，不需要把整个页面状态、所有提示词和所有凭据塞进队列。

5.3 Redis 在这里做什么？

组件 这一条链里的职责
PostgreSQL 保存 Run、步骤、审批、执行租约和持久事件
Redis / Celery broker 交付“请执行这个 Run”的任务消息
Worker 领取任务，执行模型与工具逻辑
API 接收用户请求、授权、提供状态查询与事件连接
浏览器 展示、提交用户动作、恢复观察状态

本项目跨进程 SSE 跟随读取的是 PostgreSQL 事件日志。这里没有把 Redis 当成一条已经实现的实时文字 Pub/Sub 通道。 Celery 还配置了 task_ignore_result=True，业务结果以 Run 等数据库记录为查询依据。Celery 配置、执行服务

5.4 两种模式的区别，直接影响用户体验

问题 API 进程内执行 Worker 执行
谁运行 Agent API 进程中的任务 Celery Worker
浏览器长期离线 有无订阅者宽限限制 不因无订阅者停止
是否可同进程拿到实时文字增量 有本地 Hub 时可以 API 与 Worker 分离，不能依赖同一个 Hub
API 如何观察跨进程结果 读取 PostgreSQL 事件与 Run 读取 PostgreSQL 事件与 Run
是否自动抵抗所有崩溃 否 否，仍需要租约、持久状态和恢复策略

下一节的“哪些事件保存”，会解释为什么开了 Worker 后，页面可能有进度事件和最终答案，却没有原来的逐段打字效果。

六、SSE 到底是什么？为什么有流式接口，页面仍可能等很久？

6.1 SSE 是一条持续返回事件的 HTTP 响应

普通 JSON 接口通常等后端组织完响应，再交给前端。SSE 则允许后端在同一个响应中不断发送事件，浏览器边读边处理。

SSE 使用 text/event-stream，按空行分隔事件。标准 EventSource 支持自己的重连机制；AgentHub 使用的是自行实现的 fetch 流读取，所以不能直接假定它具备原生 EventSource 的全部行为。HTML SSE 标准

在这个项目里，用 fetch 很自然：启动请求需要 POST、JSON 请求体和 Bearer Header。原生 EventSource 的接口不能像 fetch 一样直接表达这组请求参数。流式客户端

一个按源码协议构造的事件示例：

event: message.delta
data: {"event_id":"e-18","type":"message.delta","request_id":"q-1","run_id":"r-1","step_id":null,"timestamp":"2026-11-18T08:00:00Z","payload":{"delta":"找到两份相关资料。"},"sequence":18,"agent_version_id":"v-3"}

最后的空行是帧边界。字段含义如下：

字段 意义
type 发生了哪一类变化
run_id 属于哪一次执行
sequence 该 Run 内的事件顺序与恢复游标
event_id 单个事件的身份
request_id 请求关联与排查线索
step_id 可关联的执行步骤；允许为空
payload 该类事件允许携带的数据
agent_version_id 所属 Run 的执行版本

这里的 sequence 既不是 Token 编号，也不是 Thread 中第几轮聊天。事件协议、SSE 编码

6.2 一次网络读取，不等于一条事件

前端会执行类似：

// 教学简化：展示处理层次，不是可直接替代项目解析器的代码。
const reader = response.body!.getReader();
const decoder = new TextDecoder();

while (true) {
  const { value, done } = await reader.read();
  if (done) break;

  const text = decoder.decode(value, { stream: true });
  frameBuffer.append(text);

  for (const frame of frameBuffer.takeCompleteFrames()) {
    handleEvent(parseEvent(frame));
  }
}

为什么中间要有 TextDecoder 和 frameBuffer？

因为传输分块不遵守你的业务边界：

  • 一次读取可能只有一条事件的前半段。
  • 也可能一次包含三条完整事件。
  • UTF-8 中文字符的字节可能跨读取边界。
  • 一条模型增量可能包含多个字、半句话，甚至更长内容。

所以处理顺序是：

字节流解码 → 缓存不完整帧 → 按 SSE 边界拆帧 → 解析 JSON → 检查必要字段 → 更新业务展示。

AgentHub 把这些职责放在 consumeEventStream、SseFrameBuffer、parseAgentEventFrame 等函数中。收到协议错误时会报告 STREAM_PROTOCOL_ERROR，不会把每一块任意文本都当作模型回答。流式客户端

TypeScript 的 as AgentEvent 只能影响编译期类型理解，不能证明网络里收到的东西真的合法。因此，运行时解析检查仍然必要。不过当前解析器主要检查关键字段，不等于把所有字段都做了完整严格的 Schema 校验。

6.3 心跳只表示连接仍有数据，不代表业务有进展

项目默认每 15 秒可发送一次 SSE 心跳：

: heartbeat

这是注释帧，前端忽略它，不增加活动卡片，也不推进业务事件游标。

假设模型 Provider 卡了 2 分钟，SSE 仍然可以持续收到心跳。此时你只能知道“API 还在维持这个连接”，不能因此判断“模型正在顺利生成”。SSE 编码、配置

6.4 流式体验还会被代理缓冲影响

即便后端每隔一点时间都写入一帧，中间代理仍可能攒够一大块才发给浏览器。于是前端表现为“等很久，突然出现整段回答”。

这个仓库有一个很具体的处理：

  • 后端设置 Cache-Control: no-cache、X-Accel-Buffering: no。
  • Next 配置关闭 compress，源码明确说明是为了避免压缩缓冲 SSE。
  • 前端默认可以通过同源 /api/* rewrite 访问后端。

这些措施能解决对应链路的缓冲问题，但不能保证所有额外网关、CDN 都自动遵守同样策略。排查时要逐段看“后端是否产生事件”“代理是否及时转发”“浏览器是否及时读取”。Next 配置、Run 路由

七、事件怎样从执行过程到达页面？哪些能恢复，哪些不能？

7.1 事件有三类，不只是模型文字

类别 典型事件 页面想知道什么
执行生命周期 run.started、run.completed、run.failed、run.cancelled 运行开始、结束及结果
业务过程 retrieval.completed、tool.started、approval.required、context.budget 正在检索、调用工具、等审批或调整上下文
模型消息 message.started、message.delta、message.completed 某次模型调用正在输出什么

前几讲学过的 RAG、工具审批、上下文预算，在这一讲都变成了用户能观察到的运行过程。

例如，后端进行知识检索后发出 retrieval.completed，页面显示结果数量和耗时；上下文预算调整产生 context.budget，Playground 可以把相关信息作为活动详情展示。事件协议、Playground

7.2 对结构事件，主链路是先写数据库，再广播

执行逻辑发出事件时，AgentEventEmitter 分配事件序号，并调用 before_publish。运行服务把 RunEventRecorder.arecord 接到这里。

对需要持久化的事件，arecord 等待写入提交，之后才允许广播出去。

这样设计的意义是：浏览器即使后来断线，已经持久保存的过程还能按 Run ID 和游标读回来。结构日志写入失败时，主链路会显式报错，例如 AGENT_EVENT_LOG_UNAVAILABLE；不能假装所有历史都完整保存了。事件发射器、事件存储、执行服务

不过，这个顺序不意味着“业务表和事件表总在同一个事务里提交”。它保证的是对应事件在广播前先保存，业务状态自身仍有另外的事务边界。

7.3 最关键的取舍：message.delta 不写入持久事件表

项目明确跳过 message.delta 的 PostgreSQL 事件持久化。它保留结构过程与最终结果，没有把每个打字片段都存下来。事件存储

例如，这一次实时流可能是：

sequence 事件 是否保存到事件表
20 message.started 是
21 message.delta 否
22 message.delta 否
23 message.delta 否
24 usage 是
25 message.completed 是
26 run.completed 是

刷新后重放看到 20 → 24 → 25 → 26，是符合这个设计的。

序号不连续，不能单独作为“结构事件丢失”的证据。 反过来，也不能看到缺号就一律说没有问题；还要检查事件类型、日志完整性、错误码和 Run 状态。

最终答案主要从两处取得：

  • run.completed.payload.output。
  • 持久 Run 的 final_output。

不要误以为 message.completed 自带完整最终答案；在该协议中，它主要携带模型轮次和状态。事件协议、执行服务

7.4 为什么 Worker 模式可能没有打字动画？

API 进程和 Worker 进程不能直接共享同一个 Python 内存对象。

在默认同进程路径中，Hub 可以把正在产生的 message.delta 直接广播给本进程订阅者。Worker 模式中，API 跟随的是 PostgreSQL 事件日志，而文字增量刚好不在这个日志里。

所以会出现：

Worker 仍然流式调用模型，但 API 只能读到持久结构事件，直到最后读到完整回答。

这不是仅凭“前端实现了 SSE”就能消除的差别。运行图的模型流处理、事件存储、执行服务

如果未来要跨进程展示实时增量，可以增加专门的临时广播通道，或者选择持久化增量。这属于扩展设计，需要同时考虑慢消费者、断线补放、数据量和最终状态收敛；不能说当前仓库已经完成了它。

7.5 Run、Step、Event、Checkpoint 各管什么？

对象 更适合回答的问题
Run 这次任务现在什么状态？最终输出、失败原因是什么？
RunStep 执行经历了哪些模型、工具、策略或审批步骤？
AgentRunEvent 页面应该看到哪些变化？从某个游标之后发生了什么？
Checkpoint 图执行保留了什么状态？在哪个位置可以继续？

这几类数据可以互相关联，但不能相互替代。

事件重放可以让页面补看到 approval.required，却不能仅靠这条事件恢复图执行。审批之后如何继续，需要 Checkpoint 和审批动作状态。反过来，Checkpoint 能用于继续运行，也不适合直接当作前端展示协议。Run/Step/Event 模型、Checkpoint 适配器、审批对账

事件表的唯一约束包含 (workspace_id, agent_run_id, sequence)。这既限制同一 Run 的序号冲突，也配合按工作区、Run 和游标范围读取。Step 的序号属于另一套顺序，不能拿它代替 Event 的游标。

八、断线重连到底恢复了什么？

8.1 已经知道 Run ID 时，重连应该观察原任务

假设你已看到 Run R1 的事件 sequence=17，然后网络断开。正确的观察请求是：

GET /api/v1/workspaces/{workspace_id}/agent-runs/R1/stream?after_sequence=17
Accept: text/event-stream
Authorization: Bearer <access_token>

它表达的是：

请把这次运行在我已见游标之后的持久事件补给我，并在可能的情况下继续观察新的变化。

它没有重新提交用户问题，没有创建新 Run，也没有要求工具重跑。跟随客户端、Run 路由

项目的游标是 JSON 中的 sequence 加 URL 中的 after_sequence。它没有发送标准 SSE id: 行，也没有采用 Last-Event-ID 请求头。不要把其他 SSE 库的默认行为套到这里。

8.2 后端如何把“旧事件”和“新事件”接起来？

attach_stream 大致做这些事：

  1. 按 sequence > cursor 读取数据库中已保存的事件，并按序返回。
  2. 如果当前 API 进程拥有这个 Run 的 Hub，订阅实时广播，必要时再补读持久间隙。
  3. 如果没有本地 Hub，就周期性读取数据库新事件；默认间隔约 0.25 秒。
  4. Run 到达当前发布段的停止状态后，最后补读一次，再结束。

这说明“浏览器侧是 SSE”并不代表“服务器内部完全没有轮询”。跨进程跟随正是由 API 持续读数据库，再转成一条浏览器 SSE 响应。执行服务、事件读取器

这幅图展示跨进程读库路径；同进程路径还可以使用本地 Hub。

8.3 Playground 的重连是有条件、有上限的

该版本新启动 Run 的路径中，如果：

  • 已经观察到了 Run ID；
  • 没有被主动 abort，也没有变成过期页面操作；
  • 错误不是 HTTP 状态大于等于 400 的明确拒绝；

前端最多尝试 3 次 GET follow，等待时间分别为 500、1000、1500 毫秒，并携带已观察到的最大序号。

它不会无限重连，也不会用同一段逻辑自动处理所有 4xx/5xx，更不是再次 POST 新建 Run。Playground

这里还有一个很重要的边界：

如果 POST 已被服务器接受，但浏览器在收到第一个事件之前断线，Playground 可能还不知道 Run ID。

这个入口没有 Thread 提交中的 client_token，不能承诺一定能自动定位刚刚创建的 Run。前端清除了本地 RUNNING，也不代表服务器一定没做过任何事情。遇到这种不确定提交，盲目再创建一次可能产生新的 Run。

8.4 “重连”与“恢复执行”要分别判断

操作 要解决的问题 是否应再次执行模型或工具
GET follow / 事件重放 页面没看到已发生的变化 不应该
重新读 Run / Turn 页面当前状态不可信或已经丢失 不应该
从审批 Checkpoint 恢复 图已持久暂停，需要在决定后继续 按恢复逻辑继续
重新运行 / Replay 用户明确要再做一次 会创建新的执行

这四者都可能在产品中用到“恢复”“重试”等字眼，写代码时必须落实到明确的业务身份和接口。

8.5 两个源码边界，解释为什么不能只相信事件

第一，最终 Run 和最后一条事件并非原子提交。

从源码顺序可推导：_complete_run 先提交最终状态，之后才发出并保存结束事件；跨进程跟随可能在两者之间看到终态并结束补读。因此，存在“数据库里已经成功，但这次连接没读到最后一帧”的小窗口。这是源码推论，不是本节做过的线上故障实验。执行服务

第二，跨 API 副本读事件，不等于续上原进程的订阅者数量。

Hub Registry 是进程内对象。如果 Run 在 API 进程 A 中执行，重连落到进程 B，B 可以通过 PostgreSQL 跟随事件，却不会自动成为 A 的本地 Hub 订阅者。因此，A 的无人订阅宽限仍可能到期。这也是从当前实现组合得出的边界；Worker 的 detached 模式才明确去掉了这条订阅生命周期限制。Stream Hub、执行服务

这两个例子说明：能恢复数据观察，不代表已经解决执行耐久性和所有分布式竞争。

九、事件到页面：为什么最后还要 GET 一次 Run？

9.1 handleEvent 把后端协议翻译成页面状态

Playground 对几类事件的处理如下：

收到的事件 页面变化
run.started 记录 Run ID，更新 URL，显示运行中
message.delta 追加到临时输出
retrieval.completed 加入检索活动，展示数量和耗时
tool.started / completed / failed 加入工具活动与相应状态
approval.required 显示等待审批
usage 更新 Token 统计
run.completed 显示成功，并接收最终输出
run.failed 显示失败与 failure_code
run.cancelled 显示已取消

当前页面并非把每一种合法事件都渲染成一个组件，而是只展示与该页面用途相关的部分。Playground

活动行使用 sequence + type 去重；lastSequenceRef 记录已观察到的最大序号。但源码没有在所有事件处理之前统一做完整的重复过滤，message.delta 仍是直接拼接。因此不能把它描述成“前端已经实现任意事件恰好应用一次”。

9.2 临时输出和最终输出分开保存

项目中的展示选择非常有代表性：

const displayedOutput = finalOutput ?? assistantOutput;

这里：

  • assistantOutput 是当前连接收到的临时文字。
  • finalOutput 是完成事件或重新查询 Run 后取得的最终回答。

有了最终答案，就优先使用最终答案。这样即使中间漏掉某些不持久化的 delta，最终结果仍然可以完整展示。

如果只把所有 delta 拼起来，当作唯一答案来源，断线后就可能永久缺字；如果只等待最终答案，用户又无法及时感知进度。把两类数据分别处理，是在体验和可靠性之间建立清晰的分工。

9.3 reconcile 是“重新核对”，不是“重新执行”

Playground 正常结束一段流后调用 reconcile(runId)：

  1. GET 持久 Run。
  2. 确认响应仍属于当前页面操作世代。
  3. 用后端状态覆盖本地 status、failure_code、final_output 和 usage。
  4. 如果是 WAITING_APPROVAL，读取当前待处理审批。

它做的是把页面重新对齐已提交业务事实。Playground

因此 SSE 到达 EOF，前端不能直接：

// 这是错误示意。
setRunStatus("SUCCEEDED");

EOF 只说明这次响应体结束。后端可能成功、失败、取消，也可能只是进入等待审批。

同时要尊重源码边界：上述核对发生在正常收尾路径；重连耗尽或明确 HTTP 拒绝等提前返回分支，不会神奇地自动变成持续轮询。Playground 会显示错误并提供手动 Refresh。即使 EOF 后读到 Run 仍为 RUNNING，当前代码也不是一套无限自恢复状态机。

9.4 等待审批会结束当前这一段流

WAITING_APPROVAL 属于当前 SSE 发布段的停止状态。用户可能几分钟后、甚至更久才回来批准，旧流不需要一直为此挂着。

Playground 提交批准或拒绝后，通过普通 HTTP 请求等待后端恢复逻辑返回，再重新查询 Run。这个入口不是一个专门的“审批恢复 SSE”；审批 API 也不能统一讲成“返回 202，交给队列慢慢做”。审批路由、Playground

业务暂停、连接结束、执行最终完成，是三个需要分开的事实。

十、刷新页面以后，三种页面分别怎样恢复？

浏览器整页刷新会重新创建组件，原来的 Ref、临时 delta、AbortController 都没了。可靠恢复需要一个仍然存在的入口身份，例如 URL 里的 Run ID 或 Thread ID。

10.1 Playground：URL 保存指针，后端保存事实

Playground 将 version 和 run 写进 URL。刷新后大致执行：

  1. 从 URL 读取 Run ID。
  2. GET Run。
  3. 查询其版本，确认它属于当前页面的 Agent。
  4. 恢复输入、业务状态、最终输出、usage 和待审批信息。
  5. 从 after_sequence=0 跟随已有 Run，重建持久活动记录。
  6. 这一段流结束后，再读取 Run 校准。

URL 保存的是“去哪里找这次运行”，没有保存完整执行内存。Playground

为什么刷新后从 0 开始？

因为旧页面的活动列表已经没了，要重放结构事件才能重建。这里的 0 不是让模型从头算，而是让观察者从头读持久事件。

刷新恢复路径没有新启动路径外面的三次自动重连循环；它也不能重建未持久化的历史打字片段。恢复结构与最终结果，是当前实现能明确提供的能力。

10.2 Thread 聊天：重新读取会话，并轮询活动 Turn

会话聊天的 URL 中有 Thread ID。刷新后，页面读取这个会话的 Turn 列表，显示已有消息和它们关联的 Run 状态。

对已经读到的活动 Turn，如果页面可见，组件每 2.5 秒重新读取列表。活动状态包括 RUNNING、WAITING_APPROVAL 和 CANCEL_REQUESTED。聊天组件

这里没有和 Playground 相同的自动 GET follow 流程。首次发送可以通过 SSE 显示临时文字，刷新后的观察主要依赖持久 Turn 和轮询。

注意条件是“列表中已有活动 Turn”。如果第一次请求失败，客户端还没重新读到新 Turn，不能说轮询必然已经为这次未知提交启动。

10.3 Run 详情页：读取工程视图，按条件轮询

运行详情页围绕 runId 读取详情与时间线。在该页认为尚未结束、且标签页可见时，每 4 秒刷新一次；其停止轮询集合是 SUCCEEDED / FAILED / CANCELLED，因此等待审批或需要关注的记录仍可继续被查询。

这里用的是 /runs/{id} 等工程观测接口，不能把它的 DTO 与运行时 /agent-runs/{id} 响应混为一谈。运行详情页、观测 API 客户端

10.4 对照表：不要写出一个万能的“自动恢复”

入口 初始体验 刷新或后续跟踪 主要边界
Playground 新运行 POST SSE 条件满足时最多 3 次 GET follow 首事件前可能尚无 Run ID
Playground 刷新 先 GET Run 从 0 补放并跟随 不带同样的外层自动重试循环
Thread 聊天 POST SSE 临时显示 读取 Turn；已有活动轮次时 2.5 秒轮询 不自动套用 Playground follow
Run 详情 JSON 详情与时间线 可见且未落入停止集合时 4 秒轮询 主要用于观察，不负责续写聊天

SSE 和轮询并非只能二选一。页面可以用流提供即时反馈，用持久查询恢复页面，并根据产品用途安排轮询。

十一、会话发送为什么需要 client_token？这部分要连着数据库设计理解

11.1 网络失败，不代表后端没有执行

假设用户点击发送：

请根据这份文档生成一份分析报告。

服务器创建了 Turn 和 Run，但返回响应时网络断了。

用户看到错误，再点一次“重试”。如果前端发出一个没有稳定身份的新请求，后端很可能认为用户要生成第二份报告。

输入文字相同，不能用来证明是同一次意图。用户也可能真的想在同一会话里第二次问完全相同的问题。

所以需要一个专门的“本次提交身份”：client_token。

11.2 Token 标识逻辑提交，不是认证 Token

Thread 前端为一次逻辑发送创建 client_token。结果未知时，恢复使用原来的输入和原来的 Token；改成新的输入，则建立新的提交身份。提交身份逻辑、聊天组件

后端契约是：

请求情况 后端应如何处理
同一 Thread、同一 token、相同规范化输入 返回或继续处理原 Turn
同一 Thread、同一 token、输入不同 拒绝冲突，不能悄悄替换内容
新 token、相同文字 可以是一次新的用户提交
已有 Turn 对应的 Run 已被执行者领取 跟随已有执行，不再从头启动

这个 token 与 Bearer access token 完全不是一回事。前者证明“哪一次提交”，后者用于证明“谁在访问”。

前端提交 token 保存在组件 Ref 中，未实现跨整页刷新持久保存。整页刷新会丢掉尚未持久化的客户端恢复槽；已经在服务端建立的 Turn/Run 则仍可通过会话列表找回。不能把当前恢复能力说成任意断电后都能无条件恢复未确认提交。聊天组件

11.3 为什么不能只写一个 if exists？

两个请求可能同时到达：

  • 请求 A 查数据库，发现 token 不存在。
  • 请求 B 也查到不存在。
  • 两个请求都尝试插入。

只靠应用层先查后写，挡不住并发。

AgentHub 把几层保护组合起来：

  1. 对 Thread 行加锁，串行化该会话的 Turn 编号分配。
  2. thread_turns 用 (thread_id, client_token) 唯一约束保护提交身份。
  3. 按输入身份校验重复请求是否真的一致。
  4. agent_runs 用 (workspace_id, thread_turn_id) 唯一约束保护“一轮至多对应一个 Run”。
  5. 真正执行时，再用 Run 的执行租约保护执行所有权。

这些不是重复设计：它们分别保护提交身份、业务记录关联和实际执行。Thread 模型、Thread 服务、Run 模型、执行租约

11.4 一次发送跨越多次短事务

实际流程大致是：

这里的“安全待启动”要结合状态判断：新准备的 Run，或既有 Run 满足 RUNNING 且 execution_owner 为空。不能把“没有 owner”直接理解成可以重跑，成功、失败或等待审批的 Run 也可能没有 owner。

Turn 创建、Run 建立、模型执行、最终结果保存，并不是包在一个从开始到结束的大数据库事务里。

如果跨模型调用一直持有数据库事务和行锁，外部调用的几十秒延迟就会拖住数据库资源。项目通过稳定身份、约束、状态转换与后续重试，把分阶段操作连接起来。Thread 服务、执行服务

11.5 数据库提交了，队列投递却报错怎么办？

Thread 流式路径中，若向队列投递失败，会返回 503 RUN_DISPATCH_UNAVAILABLE，并保留尚未被执行者认领的 Run。

为什么不直接把 Run 标成失败？

因为 API 可能只是没拿到投递成功的确认，Broker 实际上已经收到消息。不能从“发送方报错”推出“接收方一定没收到”。

前端随后用同一个 token 恢复原提交，后端重新找到原 Turn/Run。如果仍未开始，可以再次派发；即使队列出现重复消息，执行租约继续限制实际执行者。Thread 路由、Thread 服务

同时应承认当前边界：这里没有核实到普通 Run 首次派发的通用事务 Outbox 自动补投。专门处理了某条恢复路径，不等于所有“数据库已提交、消息未确认”的情况都能全自动修复。

11.6 聊天结束不只是把答案贴到屏幕上

Thread 流式响应会提前在成功响应头提供：

  • X-AgentHub-Run-Id。
  • X-AgentHub-Turn-Id。

因此前端在第一段正文前就可能知道该取消哪个 Run、该关联哪一轮。Playground 的独立 Run 流式入口没有同样的这两个身份头，不能把这一保证泛化给它。Thread 路由、流式客户端

聊天正常结束后，前端重新加载 Turn，使用持久 final_output。工作台还会刷新产物列表、当前会话信息和会话列表。

这就是“应用与业务闭环”：

用户提交 → 业务执行 → 保存回答和产物 → 重新读取关联资源 → 页面各区域一起反映结果。

如果答案更新了，但报告侧栏还是旧的，问题可能出在 onTurnCompleted 没刷新相应资源，而不是模型生成失败。聊天组件、工作台

十二、取消、等待审批和失败：按钮到底改变了什么？

12.1 AbortController.abort() 停止的是浏览器连接

浏览器关闭连接，会让这次 fetch 的读取停止。它没有直接向外部工具发送撤销，也没有自动在数据库里完成 Run 取消。Fetch 官方说明

项目有独立的取消接口：

POST /api/v1/workspaces/{workspace_id}/agent-runs/{run_id}/cancel

Playground 点击取消后，会继续读流来接收后续取消事件；Thread 聊天则先请求后端取消，再中止对应浏览器流并重新读取 Turn。两种交互都必须先表达后端取消意图。Playground、聊天组件

12.2 为什么存在 CANCEL_REQUESTED？

因为“用户提出取消”和“执行者安全停下来”不是同一个时刻。

Run 正在运行时，后端通常先保存 CANCEL_REQUESTED，让执行者在可处理的位置发现它。没有活跃 owner 的某些审批等待状态，可以直接转为 CANCELLED；若涉及已领取或结果未知的外部动作，还必须保留相应不确定事实。执行服务

假设工具已经向外部系统发送“创建工单”请求：

  • 用户现在取消，可以阻止后续某些工作。
  • 已经创建的工单不会因此自动消失。
  • 如果外部请求结果未知，不能为了让按钮体验简单，就显示“全部已撤销”。

取消是一种协作状态转换。外部业务补偿需要单独的领域逻辑。

12.3 前端应该怎样读这几个状态？

Run 状态 正确解释
RUNNING 当前存在执行意图；可能尚未领取，不一定正在生成 Token
WAITING_APPROVAL 已持久暂停，等待审批决定
CANCEL_REQUESTED 已提出取消，还需要执行端收敛
SUCCEEDED 已保存成功结果
FAILED 已知失败，可以读 failure_code
CANCELLED 已完成取消状态转换
NEEDS_ATTENTION 存在需要核对的情况，不能默认等同“什么也没做，可直接重跑”

这些业务状态由后端模型约束和执行服务共同维护。前端按钮可以先显示“取消中”，但最终状态应由服务端确认。Run 模型、执行服务

12.4 审批成功也不等于工具已经成功

批准动作只是允许后续执行尝试。之后仍可能出现：

  • 原执行主体权限已改变。
  • 执行租约无法获得。
  • 工具调用失败。
  • 外部操作已经发出，但成功回执没有落库。

因此，“审批已批准”“工具执行成功”“Run 最终成功”需要分别展示和追踪。前几讲的审批状态与执行状态，在前端也不能压成同一个绿色对勾。审批路由、审批对账

十三、Worker 崩溃之后怎么办？租约不是“无脑重试许可证”

13.1 队列交付和实际执行是两层事

Celery 配置启用了延迟确认和 Worker 丢失时拒绝消息等机制，任务可能被再次投递。因此实际业务必须能处理重复交付，不能假设队列永不重复。Celery 配置

Worker 收到一个 Run ID 后，先读数据库检查：

  • 这个 Run 是否仍需要执行？
  • 是否已经终止或收到取消？
  • 原创建者当前是否仍有权限？
  • 是否存在另一个有效执行者？

队列消息不是一张永久有效的权限凭证。排队期间权限发生变化，Worker 也需要重新检查原执行主体。Worker 入口

13.2 用一张数据库记录表达临时执行权

执行租约可以理解成：

某个执行者在一个有限时间窗口内，获得推进这个 Run 的权利；执行者活着就续租，续租与释放必须匹配自己的 owner Token。对账则通过锁定记录、检查租约和状态来决定是否需要修正。

该版本的关键默认值是：

  • 租约有效期 180 秒。
  • 每 30 秒续租。
  • owner 使用身份 Token，续租和释放要匹配该 Token。

领取在事务和行锁保护下进行。有有效 owner 时，其他执行者不再启动同一个 Run。执行租约

注意，执行租约解决的是同一个 Run 的执行竞争。用户如果创建了两个不同 Run，不能指望这层租约判断“这两次外部业务其实重复了”。

13.3 为什么过期以后没有直接抢过来从头跑？

因为 Worker 可能死在这种位置：

  1. 已向外部系统发出请求。
  2. 外部系统已经成功执行。
  3. 还没来得及把成功结果写回本地数据库。
  4. Worker 崩溃。

此时本地没有成功记录，不代表外部没有成功。

AgentHub 对过期执行 owner 采取保守处理：进入 NEEDS_ATTENTION，例如记录 RUN_EXECUTION_LEASE_EXPIRED，而不是无条件接管并从头重跑。租约丢失时也会尝试停止当前执行，防止旧执行者继续把不确定状态当正常结果写回。执行租约

对已领取、但结果不明的审批动作，对账还可能把动作标为 UNKNOWN_OUTCOME，将 Run 状态置为 NEEDS_ATTENTION，并记录 failure_code=ACTION_RECONCILIATION_REQUIRED。接下来要依据外部系统查询、业务幂等键或补偿规则处理。审批对账

13.4 审批恢复有专门的持久化恢复意图

项目用 resume_pending 记录某些审批恢复尚待完成。恢复命令丢失后，对账任务可以再次派发，直到恢复被相应执行者处理。

这是针对审批恢复的明确设计，不能据此声称所有后台任务都有通用 Outbox。

另一个容易混淆的细节是时间：

参数 当前默认值或常量 含义
执行租约 180 秒 owner 的有效窗口
续租周期 30 秒 执行者证明仍然活跃
审批对账调度周期 30 秒 定时发起一次扫描任务
对账候选最小年龄 300 秒 哪些旧记录进入候选
无 Checkpoint 的僵尸 Run 判断 900 秒 更具体的一类异常判定门槛

“每 30 秒调度”不意味着所有故障在 30 秒内完成恢复；还受候选条件、队列延迟、Worker 和数据库状态影响。Celery 配置、审批 Worker、审批对账

13.5 知识处理、Wiki 编译和 Agent 工具，不能使用同一套重试想象

知识入库与 Wiki 编译各自有 Job/Compilation 状态、租约和受次数限制的重派发规则。派生数据任务可以借助稳定 Chunk 身份、upsert、编译版本和发布事务，让某些步骤适合重复执行。

但这些条件不自动适用于创建工单、发消息等外部写工具。

所以后台任务设计要先问：

再做一次会发生什么？能否证明是同一次业务？能否查询第一次结果？哪些步骤可以重复，哪些必须核对？

不能仅因为用了同一个 Celery，就给所有任务套同样的“失败就重试”策略。知识 Worker、Wiki Worker、审批对账

十四、实战走查：页面一直转圈，应该按什么顺序查？

先不要把“转圈”翻译成“模型慢”。它可能是请求没发出、认证失败、队列未消费、执行卡住、事件没到，或者页面收到数据却没有正确更新。

14.1 第一步：在浏览器中确认请求身份和结果

打开开发者工具的 Network，关注：

  1. 发的是普通 JSON POST，还是 /stream？
  2. workspace、version、thread 是否是当前页面对应的对象？
  3. HTTP 是 401、403、409、422、503，还是已经建立 200 SSE？
  4. 是否已经知道 Run ID？
  5. 重试时发的是 GET follow、同 token 的 Turn 提交，还是一个新的 POST Run？

Thread 可以从成功响应头取得 Run/Turn ID；Playground 通常从事件取得 Run ID。没有拿到 ID 时，先保留“不确定提交”的判断，不要直接宣布后端没有接受请求。流式客户端、Run 路由、Thread 路由

14.2 第二步：读取持久 Run，而不是盯着旧页面

先请求：

GET /api/v1/workspaces/{workspace_id}/agent-runs/{run_id}

重点看 status、failure_code、final_output、统计，以及是否需要审批。

若你在自己的开发环境排查，可以进一步执行参数化只读查询。以下 SQL 的冒号参数需由数据库客户端或 SQLAlchemy 绑定，不是直接填进生产环境的固定值：

-- 1. 本次执行的业务状态与执行所有权
SELECT id, status, failure_code,
       execution_owner, execution_lease_expires_at,
       event_log_complete, event_log_failed,
       started_at, completed_at
FROM agent_runs
WHERE workspace_id = :workspace_id
  AND id = :run_id;

-- 2. 持久事件：按事件游标看已经记录的结构变化
SELECT sequence, event_type, event_id, occurred_at
FROM agent_run_events
WHERE workspace_id = :workspace_id
  AND agent_run_id = :run_id
ORDER BY sequence;

-- 3. 粗粒度执行时间线：定位卡在哪类步骤
SELECT sequence_number, kind, status, created_at
FROM run_steps
WHERE workspace_id = :workspace_id
  AND agent_run_id = :run_id
ORDER BY sequence_number;

这些字段和表来自该版本模型。查询都保留工作区条件，也把 Event 序号和 Step 序号分开了。Run/Step/Event 模型

几种典型读法：

  • RUNNING + owner 为空：可能已保存但还未开始领取，先检查派发；不能只说模型慢。
  • owner 租约过期：检查进程、执行租约和对账。
  • WAITING_APPROVAL：应该展示审批入口。
  • SUCCEEDED 且有最终结果：先查前端更新或状态读取路径。
  • NEEDS_ATTENTION：读具体 failure_code，再决定核对什么。

event_log_complete 描述某个发布段的日志完整性。等待审批也可以完成一段日志；它不表示保存了所有 Token，更不表示 Run 的所有未来阶段都已经结束。

另外，读取 API 可能按权限把 input_text / final_output 投影为 null。这个 null 不一定表示数据库丢失内容；有工作区读取权但无运行内容权限时，后端会主动限制返回值。Run 路由

14.3 第三步：确认实际执行模式

若为 API 进程内模式，查：

  • 哪个 API 进程持有执行任务。
  • 是否因为断开订阅触发宽限。
  • 模型、工具或数据库调用是否失败。

若为 Worker 模式，查：

  • 任务是否成功派发，Broker 是否可达。
  • Worker 是否在消费该类任务。
  • Worker 是否取得 Run 租约。
  • 原执行主体是否仍有权限。
  • 模型凭据及依赖配置是否正确。
  • 如果依赖定时对账，beat 是否也在运行。

Worker 和 beat 是不同职责：Worker 执行任务；beat 定时把对账任务送入队列。Worker 活着，不等于周期修复正在触发。部署清单、Worker 入口、Celery 配置

API 与 Worker 还需要一致的数据库、Blob 等依赖配置；凭据加密主密钥也必须一致，否则页面可以正常访问，Worker 却可能无法解密 Provider 凭据。这类问题应沿实际任务日志和依赖配置查，不要仅检查网页能否打开。部署清单

14.4 第四步：事件有了，页面为什么没更新？

按照数据所在的位置定位：

现象 优先检查
数据库有结构事件，浏览器没收到 after_sequence、API follow、连接是否结束、代理缓冲
浏览器收到事件，活动区没变 是否处理该事件类型、当前页面是否本来就不展示它
收到 delta，文字没动 回调世代/控制器身份、临时气泡是否仍显示、拼接状态
Worker 成功但没有 delta 当前跨进程路径是否仅依赖持久事件
Run 已成功，页面还 RUNNING reconcile 是否执行、读取是否失败、当前入口是否还在轮询
切工作区后出现旧答案 sessionId、resourceKey、generation 检查
答案更新，产物侧栏没更新 onTurnCompleted 的关联资源 reload

前端不是“只要后端对就自动对”。页面仍有自己的并发和展示规则。Playground、聊天组件、工作区数据 Hook、工作台

14.5 健康检查各自能证明什么？

该版本的探针路径以 /api/v1 为前缀：

路径 实际检查范围 不能据此证明
/api/v1/health API 可以返回固定状态 数据库、队列和模型正常
/api/v1/ready PostgreSQL 连接及 SELECT 1 Worker 正在消费、模型能生成
/api/v1/dependencies PostgreSQL、Redis、Qdrant 连通性 一次真实业务任务一定能成功

因此 /ready=200 与“后台任务可完成”之间，还隔着任务投递、Worker、权限、凭据、模型服务和业务逻辑。健康接口

十五、把全部知识放进一个故障案例

下面是基于上述机制组织的教学场景，不是声称项目线上曾发生过这次事故。

场景：Thread 使用 Worker 模式，用户要求查询资料后创建一条需要审批的外部工单。

阶段 A：发送之后断网

  1. 前端为本次提交保留 client_token=T1。
  2. API 创建 Turn，并绑定 Run R1。
  3. 队列可能已经收到 R1，但 API 没收到成功确认，返回 503。
  4. 用户恢复原请求，前端仍使用 T1 和原输入。
  5. 后端找到原 Turn/Run，而不是再创造 R2。

这里解决的是：同一个用户意图在网络重试中保持身份。

阶段 B：队列里出现重复消息

  1. 两条消息都指向 R1。
  2. 第一个 Worker 取得执行租约。
  3. 第二个 Worker 发现有效 owner，不再次运行图。

这里解决的是：同一个 Run 的实际执行竞争。

如果前端换了新 token，后端创建了另一个 Run，执行租约不会自动认出两个 Run 代表同一个外部工单意图。

阶段 C：执行到了审批

  1. Run 保存等待审批状态和可恢复执行信息。
  2. 页面收到或查询到 WAITING_APPROVAL。
  3. 当前这段 SSE 结束。
  4. 用户之后批准，后端恢复相应执行段。

这里解决的是：持久暂停与人工决定之后的继续执行。

它不要求原浏览器连接一直保持，也不等于把原请求从头再来一次。

阶段 D：外部工单创建后，执行进程崩溃

  1. 外部系统可能已经创建工单。
  2. 执行者没来得及把完成回执保存到本地。正常人工审批入口由 API 直接等待恢复；不能因为初始 Run 采用 Worker 模式，就断定审批后的续跑也自动搬到了 Worker。
  3. 本地审批动作仍然是已领取、结果不明。
  4. 后续租约与审批对账识别不确定状态。
  5. Run 进入 NEEDS_ATTENTION，需要查询外部系统或依据业务幂等约定处理。

这里解决的是：把“不知道外部结果”如实表达出来，避免盲目再次写入。

阶段 E：用户刷新页面

  1. 页面从 Thread ID 重新读 Turn。
  2. 根据 Run 状态显示需要关注。
  3. 必要时进入 Run 详情，读取步骤与错误码。
  4. 若跟随事件，也只是恢复观察，不再次创建工单。

把这五个阶段放在一起，你就能看见不同机制的边界：

机制 主要保护对象
client_token 同一次逻辑提交
数据库唯一约束 同一业务记录及关联不重复
执行租约 同一个 Run 的执行所有权
Checkpoint 与审批恢复意图 可以从哪里继续、是否还有恢复工作
外部幂等键 / 查询 / 补偿 外部系统的实际业务效果
SSE 游标与状态重读 用户看到的过程和结果

任何一个机制，都无法单独替代其余所有机制。

十六、如果从零实现，建议按这个顺序写

这一部分是学习实现顺序，不是在声称当前仓库每一步都只有下面这几行逻辑。

第一步：先做“创建 Run + 查询 Run”

先把最小业务对象定义清楚：

  • Run ID。
  • 执行版本和输入身份。
  • status、final_output、failure_code。
  • 工作区与创建者。

前端能提交一次请求，再按 Run ID 查到明确结果。先保证错误不会伪装成空结果，权限限制不会只靠按钮隐藏。

第二步：把前端显示状态拆开

至少区分：

  • 用户正在输入什么。
  • 浏览器是否正在提交/读取。
  • 后端业务状态是什么。
  • 当前临时输出是什么。
  • 后端最终输出是什么。
  • 当前页面属于哪个工作区、会话、Run。

这一步能消除很多“用一个 loading 控制整页”的设计问题。

第三步：加入结构化事件，再加入文字增量

先让页面能展示开始、工具执行、等待审批、完成和失败；再接文字 delta。

确定每一种事件：

  1. 谁产生。
  2. 携带哪些字段。
  3. 是否持久化。
  4. 页面如何处理。
  5. 断线后能恢复什么。

不要直到断线以后，才发现唯一答案只存在于浏览器拼接字符串里。

第四步：建立刷新和终态收敛

URL 保存稳定身份。刷新后从后端重建状态。流结束后查询最终 Run/Turn。

切换会话或版本时，用世代和资源身份过滤迟到响应；清理连接与计时器。

这一步验收的重点是：正在运行时刷新、切到其他会话、旧请求晚到，页面会不会显示错误的任务。

第五步：加入同一提交的幂等恢复

为 Turn 建立稳定提交 token，用数据库唯一约束兜底。把“恢复原请求”和“新建一次请求”在代码和按钮语义上分开。

要能解释：同 token 同输入、同 token 不同输入、新 token 同输入各发生什么。

第六步：最后把执行搬到 Worker

迁移之前先确认：

  • 执行任务不依赖当前 HTTP 请求里未保存的内存数据。
  • Worker 能从持久记录重建执行上下文。
  • 重复交付不会直接重复执行。
  • 执行者失联能被识别。
  • 前端知道跨进程后还保留哪些实时事件。
  • 数据库提交与消息投递之间的故障窗口如何处理。

Worker 是执行部署方式的变化，也会改变数据传递与生命周期。不能仅把函数套上 task 装饰器，就认为异步系统已经完整。

十七、面试时，怎样把这一整条链讲清楚？

如果面试官问：

你这个 Agent 项目前后端是怎么接的？流式输出、异步执行和断线重连怎么实现？

可以这样组织回答：

前端用 React 组件和封装的 API 客户端提交输入，后端先检查工作区权限、固定执行版本并持久化 Run。流式入口使用 fetch 读取 SSE：事件带 run_id、sequence 和类型，前端把它们转换成进度、临时文字、审批和结果展示。执行有 API 进程内与 Worker 两条路径，Worker 由配置开启。

结构事件先写 PostgreSQL 再广播，跨进程跟随按 sequence 读取持久日志；message.delta 不持久化，因此刷新恢复的是运行结构和最终结果。Playground 用 after_sequence 补放并跟随，聊天页和运行详情还分别有状态轮询。流结束后重新读取 Run 或 Turn，让页面对齐持久结果。

对提交结果未知的情况，Thread 用 client_token 复用同一逻辑提交，数据库唯一约束保护 Turn 与 Run 关联，执行租约保护实际执行所有权。租约过期或外部动作结果未知时，进入需要核对的状态，避免不确定副作用被盲目重放。浏览器断流、后端取消、审批恢复、重新创建 Run 是不同操作。

然后准备好回答几个追问：

面试追问 回答重点
为什么 SSE 结束不能直接显示成功？ 连接结束与业务状态不同，审批暂停也会结束流
为什么用了 SSE 还要 GET / 轮询？ 补齐最终结果、恢复页面、同步其他执行者造成的变化
sequence 缺号是不是丢事件？ 可能是 delta 不持久化，结合日志与 Run 判断
怎么防止重试产生两次任务？ 稳定提交身份、唯一约束、执行租约分层保护
Worker 崩溃为什么不总是重跑？ 可能已经产生无法确认的外部副作用
为什么停止浏览器请求没停任务？ 取消观察连接与提交业务取消意图不同
为什么开 Worker 后没打字效果？ API 只跟随持久事件，而 delta 不在持久日志里
页面显示 null 是数据丢了吗？ 还可能是后端权限投影
readiness 正常为何任务不动？ 该探针只证明有限依赖，不能证明 Worker 和模型完整链路

学完这一节，你应该能够选中一条真实 Run，逐项指出：

哪个页面提交了它，哪个接口创建了它，哪个执行者在推进它，哪些数据已落库，页面最后一次看到什么，以及下一步该去哪一层查证。
