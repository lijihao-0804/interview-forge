第 7 讲：异步任务与后台 Worker

用户提问

好的，继续下一阶段的学习

讲解原文

好，接着上一节的表结构设计，我们进入下一阶段：

这一节继续用 AgentHub 的文档上传与入库来讲。它能把你关心的前端、后端、数据库连接起来：

用户上传文档 → 后端保存文件和任务 → Worker 处理文档 → 更新数据库 → 前端显示处理结果。

你上一节见到的 status、stage、attempt_count、lease_token，这节都会用上。

先记住这几个角色：

组件 在这条流程里负责什么
FastAPI 接收上传请求，校验权限，保存文件和业务记录，提交后台任务
PostgreSQL 保存“要做什么、做到哪一步、谁正在做、最后是否成功”
Redis 作为 Celery 的消息代理，传递任务通知
Celery Worker 执行解析、切块、Embedding、写入向量索引
Celery Beat 定时发出巡检任务，让 Worker 查找需要补投或重试的任务
前端 调用接口提交文件，再查询服务端状态、更新页面

下面按我核对的 AgentHub 源码提交 fafe4ab 讲解。源码会给链接；教学简化代码会单独说明。

一、先分清楚：async def 和“后台任务”分别解决什么问题？

这是看懂这一部分源码的基础。

1. 写了 async def，HTTP 请求仍然可能一直等待

看一个教学示例：

@app.post("/upload")
async def upload(file: UploadFile):
    result = await parse_and_index(file)
    return result

如果 parse_and_index() 需要较长时间，当前上传请求就要等它结束，才能执行 return。

await 的作用是：在等待可异步执行的操作时，让事件循环有机会运行其他协程。当前函数的后续代码，仍然要等这一步完成才能继续。 Python 官方文档也区分了直接 await 和创建并发任务的行为。(Python 3.15.2 documentation)

所以，以下两个问题需要分别考虑：

  • 等待期间，服务器能不能处理其他请求？
  • 当前用户的请求，什么时候可以返回？

异步 I/O 主要帮助解决前一个问题；后台任务架构让耗时工作可以在 HTTP 响应返回之后继续执行。

2. 常见的几种方式，运行位置不同

写法或机制 工作在哪里执行 对当前请求意味着什么
await some_operation() 当前异步调用链 等这一步结束，再继续执行后续代码
asyncio.create_task() 当前进程的事件循环 可以并发运行，但任务仍依赖这个进程
FastAPI BackgroundTasks Web 应用进程内 可以在响应返回后执行工作
Celery 单独运行的 Worker 进程 API 提交任务，Worker 独立执行

FastAPI 官方文档也建议：对于需要独立进程、甚至多台服务器执行的较重后台工作，可以使用 Celery 这类任务系统。(FastAPI)

AgentHub 的文档入库走的就是最后一条路线。

这里先建立一个概念：

HTTP 请求有自己的生命周期，后台任务也有自己的生命周期。数据库里的任务记录把它们连接起来。

二、用户上传文档时，API 究竟完成了哪些工作？

假设用户上传了一份“产品手册.pdf”。

1. 前端发出的是文件上传请求

真实接口是：

POST /api/v1/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}/documents

前端使用 FormData，把文件放在名为 file 的字段里：

const formData = new FormData();
formData.append("file", file);

后端这个接口声明的响应状态码是：

status_code=status.HTTP_202_ACCEPTED

也就是 202 Accepted：请求已受理，后续处理尚未完成。

源码：前端上传方法、后端上传路由。

2. 返回 202 前，后端已经保存了什么？

对于上传一份新文档，KnowledgeService.upload_document() 的主要顺序是：

  1. 校验用户权限和知识库归属。
  2. 保存原始文件。
  3. 创建 Document。
  4. 创建 DocumentRevision。
  5. 创建 IngestionJob。
  6. 提交数据库事务。
  7. 尝试把 job.id 投递到队列。
  8. 返回上传结果。

下面是保留主要顺序的教学简化代码：

stored_blob = await blob_store.put(...)

document = Document(...)
session.add(document)
await session.flush()

revision = DocumentRevision(
    document_id=document.id,
    blob_key=stored_blob.blob_key,
    ...
)
session.add(revision)
await session.flush()

job = IngestionJob(document_revision_id=revision.id, ...)
session.add(job)
await session.flush()

await session.commit()

try:
    await queue.enqueue(job.id)
except Exception:
    logger.warning("knowledge_ingestion_enqueue_failed")

return document, revision, job

这三个业务对象可以对应成：

对象 表达的业务含义
Document 这是一份什么文档
DocumentRevision 这次上传的是它的哪个版本，原始文件在哪里
IngestionJob 这个版本需要进行一次入库处理，现在进展如何

源码：KnowledgeService.upload_document。

3. 为什么一定先提交数据库，再发送任务？

因为 Worker 可能非常快。

如果顺序变成：

await queue.enqueue(job.id)
await session.commit()

就可能发生：

  1. API 发送了 job_id。
  2. Worker 立即收到。
  3. Worker 去数据库查询。
  4. API 的事务还没提交，Worker 查不到任务。

先提交数据库，就能让收到消息的 Worker 查到已经保存的任务身份与输入信息。

不过，PostgreSQL 的提交和 Redis 的投递属于两个操作，中间仍然可能失败：

数据库提交成功 → API 崩溃 → 尚未发送消息

AgentHub 对这个情况准备了后面的巡检补投机制。

这也解释了一个容易忽略的细节：

在这个实现里，202 表示上传请求已被持久受理；即使这次向 Redis 投递失败，API 也可能返回 202，后续再通过巡检补投。

4. 返回的数据是什么？

上传响应的真实顶层结构是：

{
  "document": {
    "id": "D1",
    "name": "产品手册.pdf"
  },
  "revision": {
    "id": "R1",
    "ingestion_status": "PENDING"
  },
  "ingestion_job": {
    "id": "J1",
    "status": "PENDING",
    "stage": "PARSING",
    "attempt_count": 0
  }
}

这里省略了其他字段，D1/R1/J1 是教学用标识，实际使用 UUID。

注意这个组合：

status = PENDING
stage  = PARSING

它表示任务等待处理，当前待处理阶段是解析。单看 stage=PARSING，不能判断 Worker 已经开始运行。

响应结构见：上传响应 Schema。

三、任务怎样从 API 到达 Worker？

先看主要交互关系。图中省略了鉴权、错误分支和具体存储调用；投递后，API 返回响应与 Worker 开始处理可以交错发生。

1. 队列里放的是任务名称和业务 ID

AgentHub 的队列适配器核心代码如下：

INGESTION_TASK_NAME = "agenthub.process_knowledge_ingestion"

async def enqueue(self, job_id: UUID) -> None:
    await asyncio.to_thread(
        self.celery_app.send_task,
        INGESTION_TASK_NAME,
        args=[str(job_id)],
        ignore_result=True,
    )

理解成一条指令就是：

请执行名为 agenthub.process_knowledge_ingestion 的任务，参数是这个 job_id。

源码：celery_queue.py。

消息里只携带业务任务 ID，Worker 收到后再查数据库，找到：

  • 对应的文档版本；
  • 原始文件的存储位置；
  • 所属工作区与知识库；
  • 当前处理阶段；
  • 当前是否允许执行。

这样，队列消息可以保持很小，重投时也能读取数据库中的最新状态。

另外，IngestionJob.id 和 Celery 自己的 task ID 是两种身份。这里把业务 ID 放进 args，没有设置 task_id=job_id。同一个业务任务重新入队，可以对应另一条 Celery 消息。

2. asyncio.to_thread() 在这里做了什么？

这里的 send_task() 是同步调用，因此代码把它放到线程中执行，避免阻塞 API 的事件循环。Python 官方文档将 to_thread() 定义为在独立线程中执行函数，并允许异步等待其结果。(Python 3.15.2 documentation)

在这段代码里：

  • 这个线程负责发送消息；
  • 后续文档解析由独立的 Celery Worker负责。

所以：

await queue.enqueue(job.id)

等待的是一次投递操作结束。

3. Worker 怎样找到要执行的 Python 函数？

Worker 端注册了同名任务：

@celery_app.task(
    bind=True,
    name="agenthub.process_knowledge_ingestion",
    ignore_result=True,
    acks_late=True,
    reject_on_worker_lost=True,
)
def process_knowledge_ingestion(_task, job_id: str) -> None:
    # 源码还包含 UUID 校验等处理
    ...

Celery 根据消息中的任务名称，找到这个函数，再把消息里的参数传进来。

这个入口是普通的 def，内部使用：

asyncio.run(
    _process_knowledge_ingestion(...)
)

来运行异步业务逻辑。

而 _process_knowledge_ingestion() 会自行创建数据库访问资源：

engine, factory = create_database(settings.database_url)

async with factory() as session:
    claim = await claim_ingestion_job(
        session,
        job_id=job_id,
        lease_seconds=settings.knowledge_ingestion_lease_seconds,
    )

Worker 有自己的数据库 Session。 API 请求结束、请求中的 Session 关闭，后台工作仍然可以继续。

源码：Worker 任务入口与处理函数。

这也是部署时需要单独启动 Worker 的原因：启动 API，只会让上传接口可以被调用；还需要有运行中的 Worker 消费队列消息。

四、收到消息之后，Worker 为什么还要“领取任务”？

因为一条业务任务可能被通知多次。

例如：

  • 原消息因为 Worker 异常而被重新递送；
  • 巡检程序发现任务迟迟没处理，又补投了一次；
  • 消息已经投递成功，但发送方没收到成功确认。

因此，执行代码不能把“我收到消息了”直接等同于“现在轮到我执行”。

1. 数据库决定谁能获得执行资格

AgentHub 使用 claim_ingestion_job() 领取任务。

其关键做法是一次带条件的 UPDATE。

下面是为了理解首次领取而简化的 SQL；正式实现使用 SQLAlchemy，并且还支持接管租约已过期的 PROCESSING 任务：

UPDATE ingestion_jobs
SET
    status = 'PROCESSING',
    lease_token = :new_token,
    lease_expires_at = :expires_at,
    attempt_count = attempt_count + 1,
    next_attempt_at = NULL
WHERE
    id = :job_id
    AND status = 'PENDING'
    AND (
        next_attempt_at IS NULL
        OR next_attempt_at <= :now
    )
RETURNING id;

你可以这样理解：

只有任务仍处于可领取状态，我才能把它改成处理中，并登记自己的执行身份。

假设两个 Worker 同时收到 J1：

时刻 Worker A Worker B
收到通知 准备领取 J1 准备领取 J1
条件更新 成功把任务改成 PROCESSING 更新时发现已不满足领取条件
后续行为 执行任务 领取失败，结束当前消息处理

这样就避免了“先 SELECT 判断、再 UPDATE 修改”之间的竞争窗口。

源码：claim_ingestion_job。

2. 为什么需要租约？

如果只保存：

status = PROCESSING

那么 Worker 执行到一半崩溃后，这个任务可能永远停在“处理中”。

因此项目还保存：

lease_token
lease_expires_at

可以把它理解成一张有有效期的工作凭证：

当前由持有这个 token 的 Worker 处理，有效期截止到某个时间。

当前默认配置是：

  • 租约有效期：300 秒；
  • 正常工作时每 30 秒尝试续约。

配置见：settings.py。

如果 Worker 消失，续约停止。租约过期后，任务就有机会被重新领取。

这里的数据库事务只用于完成领取、续约、推进状态等短操作。耗时的解析和 Embedding 在这些事务之外执行，避免为整段耗时工作一直持有数据库行锁。

3. 旧 Worker 又恢复了，怎么办？

考虑这个过程：

  1. Worker A 领取任务，得到 token-A。
  2. A 卡住，租约过期。
  3. Worker B 接管，得到 token-B。
  4. A 又恢复运行，试图写回结果。

AgentHub 的关键数据库更新会验证：

任务仍然是 PROCESSING
lease_token 等于自己领取时拿到的值
lease_expires_at 仍未过期

因此，A 用旧 token 更新任务状态时，就不能通过校验。

这里需要准确理解保护范围：这些检查保护 PostgreSQL 中的关键写回。 当前 Qdrant 的写入不携带这个租约 token；续约失败也不会立即取消整个处理协程。因此，向量写入还需要下面的幂等设计。

五、任务真正执行时，status 和 stage 怎样配合？

这两个字段回答不同的问题。

字段 回答的问题 实际取值
IngestionJob.status 任务总体处于什么状态？ PENDING、PROCESSING、SUCCEEDED、FAILED
IngestionJob.stage 已推进到哪个处理阶段？ PARSING、CHUNKING、EMBEDDING、INDEXING
DocumentRevision.ingestion_status 文档版本是否已完成入库？ PENDING、PROCESSING、READY、FAILED

字段定义见：知识库数据模型。

1. 四个阶段分别做什么？

阶段 主要工作 重要的持久化结果
PARSING 从原始文件提取可处理的内容 推进任务阶段
CHUNKING 把解析结果切成分块 将 chunks 写入 PostgreSQL
EMBEDDING 从分块计算向量 向后续索引步骤提供向量
INDEXING 将向量写入 Qdrant 全部成功后，版本标 READY、任务标 SUCCEEDED

这些阶段可以在同一次任务执行中连续推进。当前实现并没有要求每一个阶段都单独发送一条 Celery 消息。

尤其要注意两个状态名称：

IngestionJob.status = SUCCEEDED
DocumentRevision.ingestion_status = READY

一个表达“这次处理成功了”，另一个表达“这个文档版本已经就绪”。

2. stage 怎样帮助恢复？

关键问题是：重启后的 Worker 还能读到哪些输入？

AgentHub 的实际恢复方式是：

重新领取时的阶段 Worker 怎样继续
PARSING / CHUNKING 重新读取原始文件并解析，再生成分块
EMBEDDING / INDEXING 从 PostgreSQL 读取已经保存的分块，重新计算向量并写入索引

因此，阶段恢复允许重复执行部分计算。

例如，任务记录停在 CHUNKING，也不意味着解析出来的 Python 对象还在内存里。Worker 重启后，需要重新读取和解析文件。

数据库保存的是可恢复的业务进度，不会自动保存 Python 程序执行到某一行时的全部内存。

处理逻辑见：文档入库 Worker。

3. 为什么“保存 chunks”和“推进 stage”要放在同一事务？

假设代码这样写：

先把 stage 改成 EMBEDDING
然后保存 chunks

如果中途崩溃，下一次 Worker 会以为分块已经准备好，但数据库里实际没有完整的 chunks。

AgentHub 的 persist_chunks_and_advance() 把两件事放进同一个 PostgreSQL 事务：

写入分块
+
stage 改为 EMBEDDING

这样，事务提交后，阶段标记和它依赖的持久输入才是一致的。

这正是上一节“表结构”和“事务边界”在实际业务中的结合点。源码：persist_chunks_and_advance。

4. Qdrant 已经写进去一部分，再重试会不会重复？

向量索引使用确定性的 point ID：

def deterministic_point_id(chunk_id: str) -> str:
    return str(uuid5(AGENTHUB_KNOWLEDGE_NAMESPACE, chunk_id))

同一个 chunk，每次得到相同的 point ID。

再配合 upsert：

  • 对应 point 不存在，就插入；
  • 对应 point 已存在，就更新。

因此，假设前面一批向量已经写成功，后面一批失败，重试时可以再次写入相同 point ID，让结果收敛。

这里的幂等主要保证重复写入不会不断增加重复索引点；重新计算 Embedding 仍然可能消耗时间和调用费用。

源码：确定性 point ID、向量生成与索引写入。

六、失败之后，究竟是谁负责重试？

这一部分很适合面试展开，因为它能体现你理解了多个系统之间的协作。

1. 可重试错误，会先写回数据库

对于可以重试、且尚未达到重试阈值的错误，项目会把任务改成类似这样的状态：

status           = PENDING
stage            = 保留当前阶段
lease_token      = NULL
lease_expires_at = NULL
next_attempt_at  = 下一次允许尝试的时间
last_error_code  = 本次错误代码

next_attempt_at 的作用是：先等一段时间，给临时故障恢复的机会。

当前默认重试基础间隔是 30 秒，延迟按尝试次数增加：

delay = retry_base_seconds * 2 ** (attempt_count - 1)

例如正常策略下，前两次失败后分别等待至少 30 秒、60 秒才能再次处理。实际开始时间还取决于巡检周期、队列积压和 Worker 是否空闲。

源码：release_ingestion_for_retry。

另外，当前释放重试的操作主要修改 Job；文档版本仍可能保持 PROCESSING。两个对象的状态不要求每一刻都同名。

2. Celery Beat 定时触发巡检

项目配置了一个每 60 秒调度的任务：

"reconcile-knowledge-ingestion": {
    "task": "agenthub.reconcile_knowledge_ingestion",
    "schedule": 60.0,
}

职责关系是：

  1. Beat 定时发送 reconcile_knowledge_ingestion 任务。
  2. Worker 消费这个巡检任务。
  3. 巡检函数查询 PostgreSQL。
  4. 找到需要继续处理的任务，再投递原来的业务 job_id。

Beat 是调度器，具体巡检代码仍由 Worker 执行。这也符合 Celery 官方对 Beat 的定义。(Celery 5.7.0 documentation)

巡检主要关注：

  • 等待时间已到的 PENDING 任务；
  • 租约已经过期的 PROCESSING 任务。

实现见：定时任务配置、reconcile_ingestion_jobs。

3. 把几种故障放在一起看

故障位置 留下了什么 后续如何继续
数据库提交后，消息投递失败 PostgreSQL 中存在 PENDING Job 巡检发现后补投
Worker 领取后崩溃 PROCESSING Job，以及最终会过期的租约 重新递送或巡检后再领取
向量索引写入一部分后失败 已保存的 chunks、部分向量点、当前 stage 根据持久输入重做，使用稳定 ID upsert
遇到可重试错误 PENDING Job、错误信息、next_attempt_at 到期后由巡检重新投递
遇到不可重试错误，或正常重试策略达到阈值 FAILED 状态与错误信息 展示失败，按业务规则处理后续重试

这套设计里，Redis 负责通知执行，PostgreSQL 保留了任务的业务事实。即使某次通知没能成功到达，系统仍能依据数据库发现还有工作没有完成。

4. ACK 和“文档入库成功”有什么关系？

ACK 是 Worker 对消息系统的确认。

项目配置了：

task_acks_late = True
task_reject_on_worker_lost = True

前者将消息确认延后到任务执行之后；后者允许在执行任务的 Worker 进程丢失等情形下重新递送相关消息。Celery 官方同时强调，使用这类机制需要考虑任务的幂等性。(Celery 5.7.0 documentation)

但这里有两层结果：

层次 关注什么
消息处理层 这一条消息是否已经被处理
业务层 文档入库是否成功，是否还需要重试

例如，Worker 发现临时错误，把 Job 改成 PENDING、设置下一次尝试时间，然后正常返回。

这条消息可以被确认，而业务任务仍在等待重试。

因此，AgentHub 的页面读取自己的业务状态表；Celery 配置也使用了 task_ignore_result=True。源码：Celery 配置。

5. attempt_count 到底在什么时候加一？

每次成功领取任务时加一。

它并不会因为：

  • 收到一条但领取失败的重复消息；
  • 从 PARSING 推进到 CHUNKING；
  • 处理了一批新的向量；

就加一。

当前默认业务重试策略的上限是 3 次尝试。不过，源码中的原子领取条件目前没有同时校验最大尝试次数，上限检查主要在错误收尾和巡检中。因此，描述源码时说“默认重试策略设为 3 次”更准确，不能直接承诺所有竞态下都严格只执行三次。

七、Worker 做完了，前端是怎么知道的？

回到用户看到的页面。

1. 上传成功后，先重新查询文档列表

前端 submitUpload() 的关键逻辑是：

const result = await documentMutation.run((auth) =>
  uploadDocument(auth, knowledgeBaseId, file)
);

if (result) {
  setNotice(t("knowledge.uploadAccepted"));
  documents.reload();
}

这个 await 等待上传 HTTP 请求返回。

收到 202 后，页面显示“上传已受理”，然后重新读取列表。

2. 列表中有进行中的文档，就每 5 秒刷新

源码定义：

const INGESTION_POLL_MS = 5000;
const INGESTION_ACTIVE_STATUSES = new Set(["PENDING", "PROCESSING"]);

轮询逻辑是：

useEffect(() => {
  if (!connected || !ingestionInFlight) return;

  const interval = window.setInterval(() => {
    if (!document.hidden) reloadDocuments();
  }, INGESTION_POLL_MS);

  return () => window.clearInterval(interval);
}, [connected, ingestionInFlight, reloadDocuments]);

你可以逐行理解：

  • 已连接，而且列表存在正在入库的文档，才建立定时器；
  • 每 5 秒重新查询文档列表；
  • 页面不可见时，跳过这一次请求；
  • 条件变化或组件卸载时，清理定时器。

源码：知识库详情页面。

3. 前端查询的是业务 API

列表请求是：

GET /api/v1/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}/documents

它关注返回的：

current_revision_status

这个字段来自后端对文档最新版本状态的查询和投影。

展开版本详情时，还会请求：

GET /api/v1/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}/documents/{document_id}/revisions

详情可以展示：

revision.ingestion_status
ingestion_job.stage
ingestion_job.safe_error_message

当前代码里的 5 秒轮询只刷新文档列表，版本详情并没有对应的定时刷新。因此，应把列表状态更新与详情阶段展示分开理解。

相关源码：前端知识库 API、后端版本查询。

这条完整反馈路径是：

Worker 写数据库 → API 查询数据库 → 前端刷新展示。

八、如果现在让你自己写，应该按什么顺序实现？

你可以把这一类功能分成六块来完成。

第一步：定义业务任务和状态

先确定：

  • 任务的输入在哪里；
  • 任务总体有哪些状态；
  • 哪些步骤需要保存阶段；
  • 失败后哪些输入能够重新读取；
  • 最终结果通过什么条件判断。

对应 AgentHub，就是 IngestionJob、DocumentRevision 和阶段枚举。

第二步：实现受理接口

把文件与任务记录保存下来，提交事务，然后尝试投递任务。

这一步完成后，即使 Worker 暂时没运行，也应能在数据库中看到待处理任务。

第三步：实现投递适配器

把业务 ID 发给队列。

Service 只需要调用：

await queue.enqueue(job.id)

Celery 任务名称、参数编码等细节放到适配器里。

第四步：实现 Worker 的领取与处理

按这个顺序组织：

收到 job_id
→ 尝试领取任务
→ 读取持久输入
→ 执行当前阶段
→ 保存进度
→ 保存最终结果

领取失败就结束当前消息处理，避免重复任务同时推进业务状态。

第五步：补齐异常路径

逐个回答：

  • 投递失败，数据库中的任务还能被发现吗？
  • Worker 崩溃，谁来接管？
  • 做到一半重试，重复写会怎样？
  • 旧 Worker 恢复后，能否覆盖新 Worker 的状态？
  • 临时错误多久后再试？
  • 失败原因能否展示给用户？

AgentHub 中的租约、稳定 ID、阶段记录、重试时间和巡检任务，就是这些问题的具体答案。

第六步：接上前端状态反馈

先实现：

提交 → 显示已受理 → 查询状态 → 展示成功或失败

把这个闭环跑通，再按交互需求决定是否需要更实时的推送。

面试时，你可以怎样介绍这一块？

可以用下面这段话组织自己的回答：

我们把文档入库拆成请求受理和后台处理两个阶段。API 接收文件后，先保存源文件，并在 PostgreSQL 中创建文档、版本和入库任务记录，提交事务后再向 Redis 投递任务 ID，接口返回 202。

Celery Worker 收到消息后，通过数据库的条件更新领取任务，领取成功才执行解析、切块、Embedding 和向量索引写入。任务状态和处理阶段都保存在 PostgreSQL，前端通过业务 API 查询这些状态。

为了处理重复投递和 Worker 崩溃，我们使用租约和 token 校验关键数据库写回；分块及向量点采用稳定身份，让重复写入能够收敛。对于投递失败、租约过期和可重试错误，定时巡检会根据数据库状态重新投递。

这里需要同时考虑消息处理与业务完成：一条消息被确认后，业务任务仍可能处于等待重试的状态，所以最终是否成功以业务数据库中的状态为准。

你现在再看 IngestionJob，就可以把每个字段和一段执行逻辑对应起来：

字段 对应的代码责任
id API、队列和 Worker 共同定位同一业务任务
status 判断能否领取，以及展示整体结果
stage 判断从哪些持久输入重新处理
attempt_count 记录成功领取的次数，参与重试策略
lease_token 校验当前执行者的身份
lease_expires_at 判断执行资格是否已经过期
next_attempt_at 控制下一次允许处理的时间
safe_error_message 向前端提供可展示的失败信息

这张表，就是上一节的数据库设计在后台任务系统里真正运行起来的方式。
