技术演进需求清单与版本校正

核查日期：2026-11-18。本文从《AgentHub 学习讲解原文完整归档》中提取“当前实现”“尚未支持”“能力边界”等表述，再对照源码判断哪些值得继续开发。

共整理 47 个可追踪技术条目，覆盖已完成能力、待补齐闭环、有条件需求、待实验路线和旧文勘误。相关条目会归入同一工作包，避免重复计算开发量。优先级是建议，尚未执行应用改动或部署。

一、先给结论：真正的下一步，是补齐能力闭环

你的判断有一个很有价值的方向：讲解中反复出现的“目前只能”“暂时没有”“默认采用”，确实暴露了项目的工程边界。把这些边界变成明确问题、验收条件和有限范围的改动，就能形成下一阶段的真实项目任务。

不过，这次核查也发现了两类需要先排除的情况：有的能力在讲义之后已经实现；有的表述是在解释有意保留的边界，继续保留才符合原来的业务要求。例如，历史 AgentVersion 不自动切到新版 Wiki，是为了保留执行时的版本身份；外部写操作结果未知时不盲目重跑，是为了避免重复产生业务动作。不能只看到“没有自动……”就把它安排成自动化需求。

对当前代码而言，值得推进的工作主要集中在以下六方面：

  • 本次核查的主分支快照：ab2b5b046da86bb2b0bd0eb65f7bab3a59eff239。

二者之间有 25 次提交、168 个变更文件，已经涉及私有 Memory、分块策略、向量复用、解析和委托审批。下文的“当前”统一指本次固定的源码快照；没有检查你实际运行环境的迁移版本、开关与部署状态，因此“主分支已实现”不等于“你的实例已经启用”。 版本对照见 GitHub 比较页。

原来的理解或旧文表述 核查后的准确现状 应如何转为下一步

2.2 “已实现”之后，还剩什么需要验收

三个例子很能说明为什么要区分实现与效果：

  1. 结构分块已经接上，但不能直接换默认。 仓库同一组 72 道 QASPER 问题的实验中，结构分块提高了完整依据在分块阶段的保留，但检索 top-6 相对固定切块同时有进步题和退步题。段落完整不等于最终回答一定更好。见 当前检索比较报告。
  2. 向量缓存已经接上，但收益由复用输入决定。 两篇文档的局部修改实验中，结构策略的每路编码输入由 132 减至 27；固定窗口仍是 23 到 23，该实验中耗时反而增加。这是限定样本的结果，不是所有文档、队列负载和线上模型成本的保证。见 复用报告。
  3. 证据区间合并有研究信号，但还没完成线上来源合同。 仓库已有在固定预算下组织 source span 的研究；线上引用仍以单个 chunk 身份为核心。把多块内容合成一条后，需要保留组成块与原文区间，才能正确回查，不能把合成文本挂在一个不对应的 chunk ID 下。研究尚未证明最终生成正确性或线上成本收益。见 source span 实验说明。

三、这份清单怎么用

3.1 状态与优先级

标签 意义 下一步
已实现／旧文过时 最新代码已有核心能力 做版本说明、迁移与实际部署验收，不重复建设
明确缺口 现有路径有可说明的能力或正确性边界 写最小改动和针对性的验收案例
部分完成 组件存在，但产品流程或质量闭环未完成 复用已有组件，补缺失环节
条件需求 由多节点、规模、私密助手、严格历史重现等业务要求触发 先确认是否存在该业务场景，再排期
实验候选 问题成立，但某种技术路线收益尚未证明 先限定数据、成本、指标与停止条件
表述校正 原讲义术语错误或边界表达不准确 追加勘误，保留旧讲义原文

优先级统一采用：P1 表示直接影响正确性、核心体验或近期闭环；P2 表示由产品目标、规模或运行场景触发；P3 表示有失败证据后先做有限实验。它们不是安全事故分级，也不意味着所有 P1 都要塞进同一迭代。每张卡片中的场景条件优先于单独的 P 值。

3.2 原文定位与条目编号

后文 Lxxxx 指追加前学习归档的原始行号。因为本次采用末尾追加，原来的行号和正文保持不变。原文摘录只作为需求来源，最新实现以“当前核查”及固定提交源码为准。

条目编号方便后续引用：MW 为 Memory、上下文与 Wiki；RG 为 RAG、入库与修订；RT 为运行、前端与平台。它们是技术条目编号，不代表每项都是尚未实现的功能。

以下重复边界按一个工作包处理，不重复计算开发量：

  • MW08 + RG07：上下文预算单位、模型计数和误差校准。
  • MW11 + RG11：真实效果评价与独立验收。 Memory 的 WRITE/RECALL/ADMIT/USE 与 RAG 的检索/交付/回答分阶段指标各自保留。
  • RG10：单次运行的最终可见证据审计。 它为效果评价提供事实，但不是效果评价本身。
  • MW06 + MW14 + RG13 + RG14：来源撤销、历史身份、维护和保留。 共用规则讨论，具体存储对象与操作仍应分开实现。
  • RT01 + RG12：提交幂等的共同原则。 Run 创建和文件上传有不同的输入身份、事务和版本语义，不应强行使用一张万能业务表。

四、逐项需求：Memory、上下文与 Wiki

MW01 — 私有 Memory 作用域：已实现，旧文需要增补版本说明

原文证据：第 9 讲第九节，L7314–7318：“当前的长期记忆属于 (workspace_id, agent_id)，不是个人 user_id。”“同一 Workspace 下同一个 Agent 的不同授权使用者，可能共享这些项目记忆。”

最新核查：已实现，不应重复开发。

  • 0060_private_memory.py 新增 owner_user_id，ACTIVE 内容唯一索引分共享与私有两类。
  • models.py 193 保存 owner；store.select/load 按 owner 过滤。
  • runtime_graph._memories 452–453 将 scope=USER 解析为原 Run 的 created_by，select 与冻结 load 都传 owner。
  • Memory Worker 308–309 使用相同作用域生成候选；extractor 有 PRIVATE_MEMORY_INSTRUCTIONS。
  • 管理服务只列“共享 + 本人的私有”，私有记忆本人可失效，共享记忆需要 agent_edit。
  • 读取模式是依据冻结配置选择共享分区或 USER 分区，不能说它已经把个人与共享记忆自动融合。
  • 旧版本省略字段的 defaults 保持原有兼容，不能把“代码已支持用户隔离”理解为所有历史 AgentVersion 自动迁移成 USER。

最小方向：将旧文追加为版本勘误/升级说明，验收新草稿默认、历史版本兼容、不同用户读写隔离和审批恢复 owner 身份；如果未来确实需要“个人偏好 + 团队规则同时交付”，这是另立产品需求，需要优先级/冲突策略，不能偷偷扩大作用范围。

边界：个人 Memory 隔离不等于整个会话与产物按个人私密，相关条件性产品需求单列为 MW17。

可执行验收：A 自己发起或恢复的 Run 不得选择、加载 B 的私人 Memory；A 的 Memory 管理列表不显示 B 的私人项；共享项规则维持；同文案可分别存在于两个私人分区；冻结 Run 使用原 actor 作用域。A 能否查看按工作区规则授权共享的 B 的 Run 输出，属于 MW17 的独立可见性合同，不能由 Memory owner 过滤直接推出。

优先级：已实现；更新文档并保留相应回归边界，不再排一轮“实现个人 Memory”。

源码：迁移、模型、Store、管理服务、运行主链、Worker、抽取。

MW02 — Memory 语义召回、噪声控制与有界检索

原文证据：第 9 讲第十一节，L7498–7520：“查询词在记忆内容中的包含命中数”“salience”“创建时间”；“默认策略在数量不足时仍可能选入零词面匹配的记忆”；“限制是不能保证语义召回与语义相关性。”

最新现状：仍存在。store.select 98–136 按 workspace、agent、owner、ACTIVE、expires_at 过滤，把全部符合条件的行拉回应用排序，然后截到 limit。没有 embedding 索引。lexical_overlap_v1 只是对已选候选做词面过滤，不能恢复同义表达遗漏。Store 文件头明确将小规模词面扫描列为有意方案。

类型：质量增强 + 规模条件项，不是“用了向量库才算完成”。

用户问题：“服务端技术栈”问法可能漏掉“后端统一 Python”；不相关但高 salience 的记忆可能挤占预算；大量长期记录会增大全量扫描成本。

最小方向：

  • 建立词面、向量、混合候选的可切换策略，保留固定版本基线。
  • 允许无相关记忆时返回空，不为了填满 8 条而硬塞噪声。
  • 候选召回先严格限定 workspace/agent/owner，再回源核查状态与内容身份。
  • 冻结检索策略和选中身份；索引可重建，关系型记录仍为权威。
  • 规模达到需要时再引入有界候选索引；可以比较 PostgreSQL 全文/向量能力或现有 Qdrant，不预先指定必须新增数据库。

可执行验收：同义改写、专有名词、中文短词、零相关、私人/共享隔离、失效/过期、同一 Run 审批恢复的固定题集；同输入预算比较 required recall、irrelevant recall、实际回答收益、延迟和成本。阈值依据基线与业务目标预先约定，不能看完结果再调及无止境搜索。

优先级/依赖：P1，先做 MW11 评估基线；必须沿用 MW01 的新 owner 边界，不能复制旧共享检索条件。

源码：Store select、词面策略、运行选择与冻结。

MW03 — Memory 写入资格与派生内容忠实度：真实引文不等于该写入

原文证据：L7359：“排除临时状态、猜测、个人画像和 assistant 回答”；L7396：“引文确实存在……不能自动证明……content 完全忠实于原话”。同类语义边界在摘要 L7260–7270、Wiki L7748–7769 重复出现。

最新现状：仍存在；同时旧“排除个人画像”已不适用于全部模式。shared prompt 排除个人画像，private prompt 允许有用的个人背景/偏好。parse_candidates 校验 JSON、引文子串、kind 与长度，但主要资格判断仍由提示词承担。主分支学习文档明确记录确定性强制候选探针里临时/恶意/私人条目可以进入 shared 写入/准入，不能将该历史探针数值冒充真实 extractor 或当前 USER 模式效果。

类型：实质质量缺口；与模型无法绝对证明语义这一能力边界并存。

用户问题：临时要求变永久背景，猜测变事实，原文的否定/条件在 Memory、摘要或 claim 中丢失；真实 quote 可以为错误解释“背书”。

最小方向：

7.1 三个可以直接转成开发 Issue 的示例

示例一：文档修订详情不会自动刷新

用户故事：作为上传文档的用户，我希望在展开版本详情后，看到解析、切块、向量化和索引阶段的最新状态，不必手动关闭、重新打开或刷新页面。

当前事实：已有 5 秒轮询刷新文档列表，展开的 revision/job 详情没有对应定时刷新。见 RT10 的原文与源码。

最小范围：页面存在进行中的已展开版本时，使用现有受权 API 更新详情；终态停止；组件卸载或切换工作区后旧响应不覆盖新页面。列表与详情可以共用调度信息，但不强制引入新的状态管理框架。

验收：上传一份会经历多个阶段的文档，保持详情展开，从待处理到成功或失败能够收敛；切换文档/工作区后不会显示旧任务；没有进行中详情时不持续无效请求。

示例二：Chunk 的 Document 与 Revision 配对完整性

用户故事：作为维护者，我希望错误的直接 SQL、迁移或后续服务代码，无法把文档 D2 的 Chunk 关联到文档 D1 的修订 R1。

当前事实：分别存在的 Document 外键和 Revision 外键，可以确认两者各自存在，但未完整表达四列的配对关系。见 RG15。

最小范围：先检测历史错配；为 document_chunks 的 (workspace_id, knowledge_base_id, document_id, document_revision_id) 增加指向 document_revisions(workspace_id, knowledge_base_id, document_id, id) 的复合外键。当前 Revision 已有对应的四列唯一约束；迁移仍需核对数据与删除语义，并明确错误数据处理和回退策略。

验收：同一工作区、同一知识库中，错误 D2/R1 配对由数据库直接拒绝；合法 D1/R1 通过；正常入库、快照回查与删除行为保持可解释。这个案例比只测试 ORM 正常路径更能验证约束本身。

示例三：Memory 同义召回与错误更新

用户故事：作为反复使用同一 Agent 的用户，我希望问“界面组件用哪套”时，它能找到之前保存的“我们使用 Ant Design”；当我明确说“新项目改用另一套组件库”，旧规则不能无条件继续生效。

当前事实：词面选择与精确内容哈希分别解决了一部分召回、去重问题，并不能完成同义召回与语义变更判断。见 MW02、MW04。

最小范围：准备同义、无关、过期、条件变化和明确替换的独立样本；先保证作用域、来源与变更链，再比较检索方案。新项目与旧项目的条件不同，不能直接认定矛盾并删除旧规则。

验收：同义问法召回改善，无关记忆不明显增加；新旧事实的作用范围可说明；A 用户自己的 Run 不选入 B 用户私人 Memory；历史 Run 仍能解释当时选择了哪条。验收应覆盖最终回答，不能只看“向量查询返回了结果”。

八、哪些“没有”不应该变成待开发任务

文档里的词 为什么不能机械立项 需要改变时的正确触发条件
教学示例还没有调用真实模型 这是课堂模拟代码的阶段，不代表完整项目没有模型接入 学习练习需要接模型时，在练习范围内推进
flush 后还没有提交 是数据库事务语义，不是服务漏了功能 具体事务边界确实错误，才修改提交位置
Qdrant 没存全部正文，正文从 PostgreSQL 回读 是检索索引与权威内容的职责划分 有实测延迟、规模或一致性需求，再比较不同部署方案
没有 pgvector、Neo4j 或“Wiki 专业数据库” 技术名称不等于业务能力；现有数据库也能表达很多需求 用实际查询、成本和运维约束证明当前方案不足
没有全站 Redis 缓存 没有证据说明所有业务查询都应缓存 有稳定热点、失效规则和收益测量
历史 AgentVersion 不自动绑定新 Wiki 保留发布身份与执行可解释性 新建升级候选和发布版本，不改写历史事实
旧修订没有立刻物理删除 旧 Run、快照与已发布知识可能继续引用 明确保留期和引用保护后，再做可回收预览与分步清理
Memory 日常失效后，冻结旧 Run 仍能回读 是新选择与历史重现的区别 产品需要强制撤销/彻底删除时，另定更强规则
message.delta 不持久化 是增量体验、数据量与恢复合同的选择 Worker 实时输出或离线补放确有需求时，增加对应通道与保留策略
未知外部写入不自动再执行 防止重复创建、重复扣减等外部副作用 工具提供可证明的幂等键、结果查询或领域补偿能力
取消没有撤销已经创建的工单 已产生的外部事实不能由取消本地任务自动回滚 业务存在明确的关闭/撤回/补偿动作并有相应授权
没有 PostgreSQL 主从 高可用和数据恢复是不同目标 确定恢复时间、可容忍数据损失与可用性目标后再选拓扑
近似 token 计数不等于服务商精确计数 模型和服务商计量差异是真实边界 对已知模型校准或专用计数，对未知模型保留估算与余量
有引用仍不等于语义正确 引用身份、内容支持、适用条件是不同检查层 增加逐结论支持与质量评估，不宣称一个格式检查器能证明所有事实

这些条目对应前文各需求卡引用的源码与原文。它们不是禁止改造，而是提醒：先说清要改善的用户结果，再决定是否改变已有约束。

九、后续维护规则

这份清单可以作为后续学习和项目迭代的索引。每次完成一个工作包，在文档末尾追加一次状态更新即可，保留之前为什么提出该需求、当时对应哪个版本的证据。

每次更新至少记录以下内容：

  1. 对应条目 ID，以及本次处理的具体场景。
  2. 实现提交与实际启用的部署版本，两者分开记录。
  3. 原来的失败案例、修改后的观察，以及未覆盖的情况。
  4. 质量、成本、运行或恢复行为是否有退步。
  5. 结论：完成、部分完成、保留实验，或因证据不足暂不采用。

对于策略实验，开始前就固定验收材料、比较口径、预算和停止条件；没有通过时保留现有默认。对于可靠性改动，应验证对应的故障窗口，而不是只证明一条正常请求可以成功。对于资料与隐私语义，区分历史身份、当前访问许可和撤销要求，避免改进一处时破坏另一处。
