面试问答 D：前端、业务闭环、评测与交付（FE01–FE50）

FE01—FE50：前端、业务闭环、评测与交付

FE01．同一个页面很多请求同时返回401，怎么避免刷新令牌风暴？

回答：同一页面多个接口同时返回 401 时，前端把 Refresh 过程收敛成一个共享 Promise，首个请求发起 /auth/refresh，其他请求等待其结果。新的 Access Token 写回当前 Session 后，各调用方按原请求合同最多重放一次；失败则让当前会话进入需要重新登录的状态。AgentHub 的 apps/web/lib/api/client.ts 对同页刷新使用 single-flight，并在 finally 中释放 Promise 引用，防止一次失败影响后来请求。

追问：原请求是 POST 创建工单，刷新成功后直接重放安全吗？

追问回答：认证重放与业务幂等是两个层次。前端须保留原请求的 client_token/idempotency_key 和相同 payload，服务端通过 Key/内容摘要判断是否已提交；如果第一次请求已完成但响应丢失，重放应返回原结果而不是创建第二单。

源码定位： client.ts · auth.ts

FE02．同页single-flight为什么解决不了多个浏览器标签的刷新竞争？

回答：single-flight 的 Promise 只存在当前页面 JS 上下文，两个浏览器标签页各自维护一份 Promise，但共享同一个 Refresh Cookie。它们仍可能同时用 R0 发起请求，服务端轮换后把第二次识别为 Token Reuse。AgentHub 在支持的环境使用 Web Locks 让同源标签页串行执行刷新，关键是获取锁之后再真正发送 HTTP，以免网络请求已经竞速。

追问：为什么先执行 fetch，再在锁里 await 没有效果？

追问回答：fetch 调用时网络就已经发出，拿锁只让两个 Promise 的完成处理串行，并没有阻止两份 R0 同时进入服务端。锁应该围住“读取当前会话→决定是否仍需刷新→发送请求→更新 Session”这一组关键操作。

源码定位： auth.ts

FE03．刷新响应回来了，为什么还要核对它属于哪个会话？

回答：用户切换账号或重新登录后，旧请求可能比新会话请求晚返回。旧 Refresh 的成功响应或 401 只能改变它所属的 Session，不能覆盖当前 Account 的 Access Token。AgentHub 的 SessionProvider 和 API Client 使用会话代次/身份核对处理异步返回。这个规则也适用于跨 Workspace 切换后的权限数据，不让旧页面的数据返回覆盖新范围。

追问：为什么只核对 user_id 不够？

追问回答：同一用户登出后重新登录形成新的 Session 生命周期，旧请求仍有相同 user_id。应使用 session generation 或登录实例标识；测试构造“旧 A 请求挂起→注销→重新登录 A→旧 401 返回”，确保新会话维持正确状态。

源码定位： session-provider.tsx

FE04．权限字段为什么不直接设计成一个canEdit布尔值？

回答：AgentHub 用细粒度 permissions 集合表达实际能力，例如 workspace_read、agent_edit、agent_run、approve_action 和支持记录读取等。单一 canEdit 无法区分 Agent 发布、工单更新、审批和模型密钥管理，也无法表达组织管理员与普通开发者的差异。前端按当前 WorkspaceContext 做菜单、按钮和空状态投影；业务 Service 仍按同一权限集合执行最终校验。

追问：权限请求失败时，页面应如何降级？

追问回答：尚未得到有效权限时，写操作保持不可用；已安全加载的只读内容可以按缓存新鲜度规则保留展示，并标注当前无法更新。403 应提示具体操作缺权限，401 交给会话恢复，网络错误提供重试入口，避免把所有问题都显示成“没有权限”。

源码定位： rbac.py

FE05．前端已经把按钮禁用了，后端还需要鉴权吗？

回答：禁用按钮只约束当前页面交互，用户仍可以调用 HTTP API、修改请求体或使用别的客户端。因此 Agent 发布、MCP 导入、审批和工单修改都在后端用 WorkspaceExecutionContext 再做权限与状态检查。前端禁用是体验优化，服务端鉴权是多租户隔离与业务不变量的入口。实际测试可以绕过 UI 直接 POST，验证无权限操作被拒绝且数据库没有改变。

追问：不能运行 Agent，是否也应该看不到该 Agent 的历史 Run？

追问回答：执行权限和读取权限应单独定义。VIEWER 可能有工作区和运行状态读取权限，却没有发起 agent_run 的资格；敏感 Prompt、工具参数和来源内容还需独立响应投影。按钮权限与数据可见性不能用同一个布尔值简化。

源码定位： services.py

FE06．工作区VIEWER为什么仍可能有权创建工作区？

回答：Organization 角色和 Workspace 角色作用范围不同。某用户在现有 W1 只是 VIEWER，但他在所属 Organization 里如果拥有创建工作区的有效组织级权限，仍可能创建 W2。AgentHub 前端创建入口依据服务器给出的组织权限与目标 Organization，不应该从“当前 Workspace 是 VIEWER”直接推导整个用户账号只能只读。

追问：怎样测试跨组织切换时的创建权限？

追问回答：让同一用户在 O1 拥有创建权限，在 O2 只有普通 MEMBER，切换目标组织后核对按钮和实际 POST 行为；如果表单保留旧名称/选择项，也要确保请求使用新目标的授权上下文，不跨组织写入。

源码定位： tenancy.ts

FE07．A→B→A选择竞态，为什么只比较资源ID不够？

回答：用户选择资源 A、切到 B、再切回 A；第一次 A 的 HTTP 请求可能最晚返回。只比较 resource_id==='A' 会误把旧 A 结果作为新 A 的最新数据。useWorkspaceData 等查询 Hook 需要同时识别会话、Workspace、资源键和请求 generation，响应只在仍属于当前代次时才能写入 state。这个机制适用于文档详情、Artifact 和 Run 详情的异步读取。

追问：旧 A 的失败响应最后返回时，会产生什么错误？

追问回答：它可能把第二次 A 已经成功加载的页面改成 error 状态。测试用受控 Promise 按 A1→B→A2 发起，先返回 A2 成功，最后返回 A1 失败，确保旧错误和旧数据都被丢弃。

源码定位： use-workspace-data.ts

FE08．丢弃旧响应与取消请求是一回事吗？

回答：丢弃旧响应是客户端状态层的正确性措施，避免过期结果覆盖当前页面；取消请求是网络层尝试停止尚未完成的传输。AbortController 能减少部分无用 HTTP，但服务器可能已经处理请求。AgentHub 的 Hook 通过身份/generation 过滤迟到结果，组件卸载或切页并不意味着后台 Run/Job 已取消，后台任务仍按独立业务状态运行。

追问：关闭一个正在执行退款的页面，远端动作会被取消吗？

追问回答：页面关闭只停止本地观察。用户重新打开后通过 Run ID、Approval/Action 状态和业务回执恢复显示；如果用户明确请求取消，后端另走 Run 取消协议。已派发的外部 WRITE 继续按实际结果核对。

源码定位： use-workspace-data.ts

FE09．列表已经READY，详情却还在PROCESSING，应该排查哪里？

回答：知识详情页维护两份数据：documents 列表与 revisions 展开详情。原先五秒轮询只刷新列表，Job 已成功、列表 READY 时详情仍可能停留 PROCESSING。当前修复为展开的详情增加按其活动状态持续读取的逻辑，最终状态后让列表与详情收敛。这是典型的“两个查询投影更新时间不同”，应沿 knowledge-detail-client.tsx → listDocumentRevisions → KnowledgeService.list_revisions() 排查。

追问：页面仍使用固定五秒轮询，怎样继续提高健壮性？

追问回答：对连续 503 增加有限指数退避和明确手动重试；对 403/404 采用权限/资源状态处理；切换 Workspace 或 A→B→A 时丢弃迟到结果。测试包含列表先 READY、详情晚 READY、请求耗时超过轮询间隔和最终无活动任务。

源码定位： knowledge-detail-client.tsx

FE10．轮询时为什么要区分HTTP loading和后台PROCESSING？

回答：revisions.loading 说明浏览器当前这次 GET 还没返回；revision.ingestion_status=PROCESSING 说明后台文件处理仍在运行。一次 HTTP 读取可以在几十毫秒内完成，但读到的后台状态仍需继续观察。AgentHub 用这些维度分别控制加载动画和自动轮询；最终 Revision READY/FAILED 或 Job 终态到达后停止自动刷新，并让用户能读取阶段和错误原因。

追问：“重新读取进度”和“重试文档摄取”为什么要分成两个按钮？

追问回答：刷新进度只发 GET，不改变 Job；重试摄取是需要权限与幂等检查的业务写入，可能增加 attempt_count 和计算费用。文案、请求方法和权限提示都应区分这两种动作，避免用户误触发昂贵任务。

源码定位： knowledge-detail-client.tsx

FE11．空列表、加载失败和未加载，为什么不能统一显示“暂无数据”？

回答：loaded=false 表示还没有权威读取结果；error 表示本次请求失败；loaded=true,data=[] 才表示成功读取到空集合。统一显示“暂无数据”会把网络故障、无权限、资源删除和真正空列表混淆。AgentHub 的通用查询状态包含 loading、loaded、data、error，页面应该根据它们展示加载、错误重试或空状态。旧数据是否暂存是产品选择，需要有新鲜度提示。

追问：后台正在重新加载列表时，可否继续展示旧数据？

追问回答：可以作为 stale-while-revalidate 交互，但应区分上次成功结果和本次新结果，并禁止依赖过期状态的危险写操作；读取失败时保留旧数据同时显示异常，不能把旧内容伪装成刚刚确认的最新状态。

源码定位： use-workspace-data.ts

FE12．如何设计一个“有理由的禁用按钮”？

回答：一个好的禁用控件要解释具体前置条件，例如“工作区缺少 agent_edit 权限”“Agent 尚无有效 ToolRevision”“摄取 Job 正在 PROCESSING”“当前 Run 等待审批”。AgentHub 页面逐项计算控件状态，前端根据服务端能力和业务对象生命周期生成说明，避免只有一片灰色。点击前可预检配置，真正执行时由后端重新验证当前状态。

追问：按钮变亮能否说明最终操作一定成功？

追问回答：按钮只表示页面当前判断满足操作前置条件；实际 POST 还要经历权限、事务和后台流程。测试同时覆盖控件状态、API 返回与数据库/Run 的最终结果，尤其验证预检与执行之间数据变化造成的冲突。

源码定位： app-workbench.tsx

FE13．React通用请求hook中的reload为什么不能直接await？

回答：useWorkspaceData.reload() 当前是一个触发刷新 token 的同步函数，返回 void；真正 HTTP 请求由 Hook 的 Effect 根据新 token 发起，完成结果反映到 loading、loaded、data 和 error。因此 await reload() 不会等待网络响应，紧接着 setDone(true) 会提前宣称数据已更新。需要在状态变化中观察请求完成，或重新设计返回 Promise 的命令式接口。

追问：如何写一个真正可等待的刷新方法？

追问回答：可以让 Hook 内部 reloadAsync() 直接返回本次 fetch Promise，并绑定 generation 与 AbortSignal；结果提交前仍核对资源身份。调用方 await 的是带明确成功/失败语义的网络工作，而不是一次本地状态递增。

源码定位： use-workspace-data.ts

FE14．页面刷新丢失SSE以后，怎样恢复用户可见状态？

回答：SSE 是当前 Run 的观察通道，页面断线后应先保存 Run ID、已见事件序号和当前状态，重新连接时根据 Last-Event-ID 或事件 API 补齐持久记录，再读取 Run 终态。AgentHub 的 Run/Step/Event 存在数据库事实，跨进程 SSE 能恢复结构化事件与最终状态；逐 Token delta 的持久化范围不同，页面需要在重连后用最终回答收敛展示。

追问：能恢复最终答案，是否意味着可以逐字重放每个历史 Token？

追问回答：不等于。要按实际持久化的事件类型判断：Run 状态、步骤和完成事件可恢复，进程内即时打字增量可能没有逐条入库。若产品要求任意断点逐 Token 重放，需要为 delta 增加持久序号、存储成本和压缩策略。

源码定位： sse.py

FE15．发送消息失败后，为什么不能直接生成一个新token重发？

回答：提交消息前应生成稳定的 client_token，并与 Thread ID 和请求内容绑定。第一次 POST 可能已创建 Turn/Run，却在响应返回前断线；重试必须复用原 Token，从服务端找回同一次逻辑提交。若每次点击“重试”都重新生成 Token，服务器会认为是全新用户输入并创建第二个 Turn。AgentHub 的 Thread 提交使用这一身份机制，并校验同 Token 是否对应相同输入。

追问：用户有意把同一句话发送两遍，应如何区分？

追问回答：两次有意提交使用不同 client_token，可生成两个独立 Turn；同一提交因网络失败重发则使用相同 Token 和请求摘要。判断依据是操作身份，而不是用户文本是否重复。

源码定位： service.py

FE16．为什么关闭页面不应该直接取消后台任务？

回答：页面关闭与用户主动点击取消属于两种不同事件。AgentHub 的 Worker 模式以 detached 方式执行 Run，浏览器断线不会直接结束后台工作；API 进程内的流式执行仍保留无人订阅的宽限终止策略，默认约 60 秒。两条路径都以数据库 Run/Approval 为状态事实，页面重开先按 Run ID 恢复观察，明确点击停止才走取消接口。已派发的外部 Action 按派发记录与回执独立处理。

追问：用户关闭页面后为什么仍应保存 Run ID？

追问回答：Run ID 是恢复观察与防重复提交的入口。可以在 Thread/Turn 关系中找回最近 Run，或在前端持久化受理身份；打开页面先读取 Run 的当前状态，而不是重新发送原问题造成重复工具调用。

源码定位： runtime_service.py

FE17．前端测试中怎样可靠复现乱序响应？

回答：并发测试要能控制每一个 HTTP Promise 的完成顺序，而不是依赖随机网络延迟。可以为 A1、B1、A2 请求创建三个 Deferred Promise：先发 A1，切 B 发 B1，再切回 A 发 A2，先解决 A2，再解决 A1；检查页面仍展示 A2。也要让 A1 最后 reject，验证旧错误不会覆盖新状态。这适用于 useWorkspaceData、SessionProvider 和详情面板。

追问：为什么在测试里 sleep(100) 不稳定？

追问回答：固定延迟受 CI 机器负载、浏览器调度和网络快慢影响，可能没有真正制造竞争窗口。通过 Promise barrier 或 Playwright route 拦截显式指定响应顺序，可以稳定复现和断言具体时序。

源码定位： use-workspace-data.ts

FE18．为什么列表页会出现N+1请求，项目怎么减轻？

回答：列表渲染 N 个 Artifact 或 Run，如果每张卡片单独请求完整详情，就形成 N+1 网络请求，增加延迟和数据库负载。AgentHub 的产品页会在部分场景批量加载关联 Artifact/Run 摘要并设置读取上限，详情按需读取；结合分页、缓存和可见范围选择降低请求数。需要在 Network 里检查批量请求是否仍包含超量敏感正文，优化要遵守权限投影。

追问：为什么不一次返回所有 Artifact 全文和历史记录？

追问回答：全量 payload 会增加首屏体积、序列化成本和信息暴露范围。列表应返回 ID、标题、状态、时间等必要字段；用户展开时再按权限读取正文。对于分页与缓存，按 Workspace/Thread/身份划分 Key，防止切账号后复用旧数据。

源码定位： app-workbench.tsx

FE19．Thread、Turn、Run为什么要拆成不同对象？

回答：Thread 是一个连续会话容器，Turn 是一次明确的用户提交及其输入，AgentRun 是该提交触发的一次执行，包含模型、工具和状态事实。一个 Thread 有多个 Turn，Turn 关联具体 Run；后续 Turn 可能使用更新的 AgentVersion。分层后可以按 Turn 组织消息和 Artifact，同时精确知道某个回复来自哪次模型执行与哪份有效知识。

追问：为什么不能把“Thread 最新 Run”当作某个历史 Turn 的 Run？

追问回答：最新 Run 属于最新提交，历史 Turn 要按稳定外键找到自己的 Run。若用时间排序猜关联，会在并发提交、重试和历史迁移时错配回答。数据库应保存精确关联并通过一致性查询核验。

源码定位： models.py

FE20．多个业务工作台为什么共用AppWorkbench？

回答：Research、Support、Incident、Data Analyst 等业务工作台共享会话列表、消息发送、SSE、Run 状态和 Artifact 展示骨架，因此复用 AppWorkbench 减少重复交互代码。业务差异放在模板配置、工具绑定与领域服务：Support 关注 Customer/Ticket，Incident 关注日志、回滚和人工接管，Data Analyst 关注查询与结果表格。共享组件负责展示通用状态，具体审批与业务后置条件由各领域模块提供。

追问：如何避免 AppWorkbench 演变成上千行 if (mode==='support')？

追问回答：把可复用的会话骨架、运行事件组件和业务插件接口分开；每种业务提供自己的侧栏、工具结果投影与表单组件，数据服务保持独立 API client。新增业务模式时不改核心 Run 状态机，只新增领域配置与视图。

源码定位： app-workbench.tsx

FE21．Artifact和普通聊天消息有什么区别？

回答：聊天消息是一次交互的过程记录，Artifact 是可独立引用、编辑版本化或交接的工作产物，例如研究摘要、运营分析或客服处理说明。AgentHub 的 Artifact 保存 Workspace、Thread、Run、标题和结构化内容等关联，方便列表、详情、人工接管与审计。聊天中一句“报告完成了”不能替代可读取的 Artifact 对象，后者有明确的生命周期和持久身份。

追问：Artifact 内容存在 JSONB，为什么仍需关系字段与 Schema？

追问回答：JSONB 表达不同产物的灵活结构，Thread/Run/Workspace 外键保证来源和授权范围，应用 Schema 保证标题、正文类型与修订接口可处理。否则消费者只能猜测一大段 JSON 属于谁、何时产生以及能否安全修改。

源码定位： service.py

FE22．为什么Agent生成的Artifact不能直接编辑？

回答：Agent 生成的 Artifact 是一次具体 Run 的输出证据，直接覆盖它会改变历史执行结果。AgentHub 将普通用户编辑作为独立的可编辑产物或修订管理，原始 Run Artifact 保留来源身份；用于人工接管的源产物还需保留证据引用。这样既允许用户继续加工内容，又能追溯哪些文本由模型生成、哪些由人工修改。

追问：保持原始 Artifact 不可覆盖，是否意味着所有 Artifact 都永久不能删除？

追问回答：修改和删除是不同生命周期操作。普通业务产物可按权限和保留策略删除或归档；被人工接管引用的源证据则需先处理引用关系与审计约束。删除流程应维护来源链与业务记录完整性。

源码定位： service.py

FE23．模型说“工单已创建”，如何验证真的完成？

回答：用户看到“工单已创建”必须能找到对应 Customer、Ticket ID 与持久数据库记录。AgentHub 的 ToolResult、Run Step 和 SupportService 工单列表可以互相核对：先检查模型是否只是提出工具调用、Approval 是否已批准、Action 是否真正 SUCCEEDED，再用独立 READ 接口查询新工单和客户归属。语言回复只展示业务事实，不能成为工单创建的唯一凭据。

追问：审批通过但 execution_status 仍是 NOT_STARTED，怎么显示？

追问回答：展示“已批准，等待执行”，保留 Approval ID 和后续刷新入口；若状态进入 UNKNOWN_OUTCOME，展示“处理结果待核对”并通过业务 ID 查询。只有查到实际工单符合预期，才用“工单已创建”作为最终表达。

源码定位： service.py

FE24．客户注册接口怎样保证并发下不重复？

回答：客户注册首先需要定义业务唯一键，例如工作区内的 external_customer_ref，并由数据库唯一约束维护。SupportService.register_customer() 在事务中检查身份、已有记录与请求内容；重复提交同一客户身份可复用，冲突信息则返回明确错误。只凭姓名去重容易合并同名客户，必须依据业务系统的稳定客户编号来判断。

追问：两个请求并发注册同一客户时怎样保证一致？

追问回答：在 Service 层按业务键规范化输入，数据库建立 (workspace_id,external_customer_ref) 等唯一约束；发生 INSERT 竞争时捕获冲突并回读已提交记录，核对关键字段。返回原客户对象而不是新建第二条，也不默默覆盖已有资料。

源码定位： service.py

FE25．工单状态更新为何同时用行锁和expected_version？

回答：工单状态编辑往往发生在用户打开页面较久之后，前端保存了旧状态版本。AgentHub 的 SupportService.change_status() 使用 expected_version 比较乐观版本，再在数据库事务中锁定并修改目标工单，防止两个客服把对方刚做的决定覆盖。行锁保证写入期间一致性，版本号保证用户操作基于他实际看到的状态。

追问：收到 409 Version Conflict，应自动用最新版本重试吗？

追问回答：应先读取最新工单状态、显示与用户原视图的差异，并要求他重新确认。例如原本要从 OPEN 改到 CLOSED，但其他人已转到 ESCALATED；自动重试可能违背原操作意图。

源码定位： service.py

FE26．如何处理工单更新已成功但响应丢失？

回答：如果工单状态更新已 COMMIT，但响应丢失，客户端重发时 Service 应根据目标工单和 expected_version 判断原操作是否已完成。若当前版本刚好增加、目标状态和操作者请求一致，可以走明确的结果核对或幂等复用路径；若状态已被其他人继续修改，返回冲突并展示最新事实。AgentHub 使用版本号、行锁和业务记录把提交是否成功从 HTTP 回执中分离。

追问：这种恢复方法能直接套用外部退款吗？

追问回答：退款发生在独立系统，必须用外部 operation_id、幂等键和状态查询确认，而不是只看本地 Ticket Version。工单状态更新有 PostgreSQL 事务与本地历史；外部业务写入需要跨系统对账。

源码定位： service.py

FE27．人工接管为什么需要单独建表，而不是Artifact上加status？

回答：人工接管表示某位有权限的员工承担后续处理责任，有接管来源、责任人、状态、关闭原因和生命周期；Artifact 只是运行产生的内容对象。把接管状态塞进 Artifact 会把“证据是什么”与“谁在处理事件”混在一起。AgentHub 为接管保存独立记录，并关联源 Run/Artifact 和内容身份，使人工补充、交接、关闭都能保留时间线。

追问：源 Artifact 的 hash 对人工接管有什么价值？

追问回答：它帮助确认接管时看到的是哪份具体源内容；后续人工编辑不会改写该来源身份。核查事件时，还要结合 Run、工具回执和源文档记录判断事实，Hash 主要服务于版本一致性与审计。

源码定位： service.py

FE28．人工接管权限为什么在写入前重新查成员？

回答：人工接管可能从 AgentRun 暂停持续到数小时后的人工处理，创建者或受理人期间可能被移出工作区。因此写入接管状态、分配责任人或关闭前，应重新读取当前工作区成员关系和对应操作权限。AgentHub 的 HandOff 业务入口结合组织/工作区范围和持久业务状态处理，而不直接使用页面打开时缓存的角色。

追问：怎样测试权限在操作中途被撤销？

追问回答：用户先加载接管详情，管理员随后撤销该用户 WorkspaceMembership，旧页面再尝试修改接管状态。后端必须拒绝变更且数据库记录不动；同时检查普通读取、后台 Worker 恢复和 SSE 观察是否遵循各自的访问合同。

源码定位： service.py

FE29．接管被关闭，是否说明原工具未知副作用已解决？

回答：人工接管的 CLOSED 表示交接处理流程已经结束，可以对应人工核查完成、人工转其他渠道或业务处理终止。原 Agent 的工具 Action 若仍是 UNKNOWN_OUTCOME，其结果仍需按远端回执独立核对。AgentHub 把 HandOff 生命周期和 Run/Approval 状态分开保存，避免一个产品流程关闭动作篡改已有工具执行证据。

追问：前端如何避免用户把 CLOSED 理解成“所有问题解决了”？

追问回答：接管详情同时展示关闭状态、关闭原因、关联 Run 与尚未确认的 Action；必要时使用“接管已结束，外部操作仍待核对”的文案。报表按“接管关闭率”“业务解决率”“未知结果数”分别统计。

源码定位： models.py

FE30．用户反馈为什么不能自动加入正式HOLDOUT？

回答：用户反馈直接来自已使用系统的真实场景，适合补充 DEV 回归案例；但反馈可能包含错标、敏感信息、重复问题和已被模型或开发人员看到的题目。AgentHub 的 FeedbackService 包含提交、审核和导入 DEV 的流程，审核时确定规范化任务与评价依据。HOLDOUT 应从独立来源冻结，避免开发时反复看过的反馈题被当成未见测试集。

追问：反馈导入 DEV 后，是否会自动训练模型或更新 Memory？

追问回答：不会。导入只是产生评测题目和相关身份，开发者可以用它做回归、定位和方案比较。微调或记忆写入是另外的授权工作流，必须有单独数据处理和质量门槛。

源码定位： service.py

FE31．反馈提交与审核怎样防止重复和并发覆盖？

回答：用户点击反馈提交可能因网络重试重复发送。AgentHub 给反馈保存请求内容 Hash 与稳定提交身份，重复同一 payload 时返回已有反馈，内容变更却使用旧身份时报告冲突；审核阶段使用当前审核状态防止两位审核员互相覆盖。这样反馈不会因重复点击增加多个相同样本，也能追踪谁审定了什么结果。

追问：同一个 Idempotency-Key 携带不同评价内容应怎么办？

追问回答：应按内容摘要检查，返回 409 类冲突，要求客户端生成新的逻辑提交身份。若只判断 Key 存在就无条件复用，用户可能以为新评论已提交，其实读到的是旧反馈。

源码定位： service.py

FE32．为什么通用审计日志不能代替业务记录？

回答：通用审计记录适合记录“谁在何时做了哪个管理动作”，但业务事实还需要自己的结构化表。例如 Approval 保存参数 Hash、决定来源和 Action 结果，Ticket 保存业务状态与版本，Run Step 保存模型与工具执行位置，Feedback 保存审定结论。审计日志提供横向时间线，业务表提供可验证的后置条件，两者通过 ID 和 Request/Run 关联。

追问：如何规划一项功能需要记录哪些证据？

追问回答：先列用户要查询的事实：谁批准、执行什么、是否成功、目标对象 ID、后续是否撤销；为每项选择权威记录，再定义审计事件和索引。对外部写入尤其保留 operation_id 与回执，日志只保存可安全公开的摘要和关联身份。

源码定位： service.py

FE33．页面能查看运行列表，是否应该把完整Prompt也返回？

回答：用户能读取 Run 列表，不等于能读取完整 System Prompt、工具凭据、所有 Memory 正文或供应商原始异常。AgentHub 的 API Schema 按业务读取权限投影列表摘要与详情，部分完整观察通过单独证据入口受控获取。前端必须从服务器获得已过滤的数据，而不是先收到所有字段再通过 CSS 隐藏；这也能减少不必要的 payload。

追问：某字段被响应投影为 null，可以推断模型当时没有输出吗？

追问回答：应看 Schema 合同与相应完整执行证据。null 可能表示该角色无权查看、字段尚未物化或来源不可用。模型是否输出要从 Run Step、消息事件和适当权限下的 Observation 记录判断。

源码定位： evaluation.py

FE34．ExperimentRun显示成功，为什么task_success仍为0？

回答：ExperimentRun 的 SUCCEEDED 说明评测 Runner 按协议完成了任务调度、收集和写回结果；task_success 根据该题 expected 和业务后置条件评分。若 Agent 正常生成一段错误回答，Runner 可以成功，而 task_success=0。反过来，题目要求拒绝危险操作时，明确拒绝可能构成业务成功。AgentHub 将被测 Agent 状态、业务判断和指标可用性分别记录。

追问：为什么不能用工具调用次数或绿色 Run 数量当任务成功率？

追问回答：有的任务应只回答不执行，有的任务需要实际建单。成功应按每题 expected 的允许动作、禁止动作和最终状态定义；更多 ToolCall 可能增加费用甚至引入危险副作用。评测器根据真实结果和后置条件给出独立评分。

源码定位： runner.py

FE35．模型没有输出，为什么不能给空字符串算一个hash？

回答：模型没有返回可评价答案时，None 表示缺少观察值，空字符串是确实观察到的文本内容。若把 None 统一变成 "" 再计算 Hash，评测会把“供应商失败未产生答案”与“模型生成空字符串”混成同一种输出。AgentHub 的评测观察保留答案存在性、运行状态和错误分类，Metric 再决定哪些维度可评价。

追问：无答案的任务是否仍能有明确业务失败？

追问回答：可以。AgentRun 可能因 MODEL_PROVIDER_UNAVAILABLE 明确失败，此时可靠性维度有可判定结果，但答案语义指标为 NOT_AVAILABLE。分开存储错误码与答案字段，才能同时分析系统失败和模型质量。

源码定位： taxonomy.py

FE36．为什么预先保存的空失败标签可能遮住后来的错答？

回答：评测流水线可能先依据 Run 状态给出基础失败标签，后续又取得实际输出和 expected 的比较结果。如果“空的标签列表”被当成最终已经分类，就可能遮住后来能够确认的 ANSWER_MISMATCH。AgentHub 的 taxonomy.py 区分观察是否足以推导具体标签，按优先级和可用字段生成分类；已有非空明确错误则保留，避免后续逻辑任意覆盖事实。

追问：怎样验证失败标签补全逻辑？

追问回答：构造三类 Case：模型有输出但答错、模型无输出且 Provider 失败、已具有明确 TOOL_ERROR 标签。分别断言错答正确补充、无输出保留 Provider 失败、已有明确错误不被新推断覆盖。

源码定位： taxonomy.py

FE37．第0步错误被定位到第7步，为什么是个有代表性的bug？

回答：Step 序号从 0 开始，Python 里 0 是 falsy。若代码写 step_index = observed_step or fallback_step，真正发生在 Step 0 的错误会被替换为后面一个非零步骤，造成错误定位漂移。正确写法用 is None 判断缺失，保留 0 作为有效索引。AgentHub 相关失败归因修复体现了“字段合法取值域”比简单布尔真值更重要。

追问：除了 Step 0，还有哪些值容易被错误当作缺失？

追问回答：金额 0、Token 数 0、布尔 False、空但已加载的数组，以及 Unix 时间戳 0 都可能是合法值。数据模型中应显式表示 Optional 与状态字段，用 is None、loaded 或专门枚举区分缺失、空值与失败。

源码定位： taxonomy.py

FE38．为什么评测器版本也要冻结？

回答：评测结果是“固定观察集合 + 固定评分逻辑”的产物。某次 Case 输出不变，若之后调整 answer matching、Failure Taxonomy 或缺失值处理，历史分数也可能变化。AgentHub 的 MetricSnapshot 保存 evaluator/version、输入 CaseResult 集合 Hash 和物化结果，后续重评分应建立新的可追溯结果身份。这样 A/B 比较不会因后台代码更新而静默改变旧成绩。

追问：如何使用新的评分器重新解释旧实验？

追问回答：保留旧 CaseResult 原始观察，创建评分版本 v2 并生成新 MetricSnapshot，记录旧/新差异及导致变化的题目。展示时注明 evaluator version 和 dataset identity，不覆盖旧版发表过的比较结论。

源码定位： metrics_service.py

FE39．NOT_AVAILABLE、NOT_APPLICABLE与得分0有何不同？

回答：得分 0 表示依据充分且评价结果失败；NOT_AVAILABLE 表示缺少计算该维度的必要观察，例如模型没有输出；NOT_APPLICABLE 表示该指标对本题没有意义，例如纯文本回答无需评价外部写操作次数。AgentHub 的 MetricResult 把状态与数值分开，聚合时按该指标的分母规则处理。否则把未知填 0 会低估模型能力，把未知丢弃又可能美化系统可用性。

追问：一个 Case 可以同时是 Provider 失败和 Answer NOT_AVAILABLE 吗？

追问回答：可以。运行可靠性维度明确记录模型调用错误，答案质量维度缺乏可评价文本。报告应同时展示 Provider 错误率、可答输出覆盖率和在有效输出上的正确率，避免互相掩盖。

源码定位： metrics_service.py

FE40．为什么门禁需要INCONCLUSIVE，不能只有PASS/FAIL？

回答：发布门禁既要判定规则达到阈值，也要确认所需证据是否足够。PASS 表示指定指标和退步约束满足策略；FAIL 表示已有证据与规则冲突；INCONCLUSIVE 表示样本、完整性或置信条件尚不足以作出二元决定。AgentHub 的 ReleaseGateService 支持证据层级、配对区间、补偿与 Trade-off 规则，用 MetricSnapshot 和 Comparison 形成可复核决策。

追问：门禁 PASS 后还需要报告哪些信息？

追问回答：至少附 Policy 版本、Dataset/Experiment 身份、Case 数量、主要指标、关键退步项和缺失维度。面试时可以说“通过这组冻结规则的发布门禁”，再具体解释覆盖的风险类型。

源码定位： release_gate.py

FE41．评测指标为什么显式物化，而不是每次GET都重新计算？

回答：显式物化把 CaseResult 及评测器版本转换为持久 MetricSnapshot，保证同一实验在以后打开页面时读取的是当时评分，而不是 GET 请求碰巧使用当前新版 evaluator 重新算一遍。AgentHub 的 materialize_metrics() 还检查 Run 终态、Case 结果集合和冻结规格是否匹配，并将内容身份写入快照。报表和发布门禁引用这份固定指标记录。

追问：为什么物化结果也要保存输入集合 Hash？

追问回答：它可以检测某条 CaseResult 被意外改写、漏行或重新解释，确保评分有明确来源。重新评分时使用新的 evaluator/version 创建另一份 Snapshot，并保留其与旧观察集合的关联。

源码定位： metrics_service.py

FE42．每题运行5遍，能把10道题报告成50道独立任务吗？

回答：10 道题每题重复 5 次，对应 50 个 Case Execution，但仍只有 10 个不同任务。重复运行有助于估计同题生成波动与 pass_hat_k，不等于多了 40 个独立场景。AgentHub 的 Runner 按 item、variant、repetition_index 保存结果，Metric 聚合先按题目或协议指定单位处理，防止热门题因重复次数多而在平均值里权重过大。

追问：两份题目来自同一个文档的近义改写，样本独立性怎样处理？

追问回答：按文档、政策条款或任务族进行 Group Split，报告不同独立来源数量；同源近义题可以用于稳健性回归，但不要把它们当完全独立的泛化证据。A/B 比较采用相同题目配对。

源码定位： runner.py

FE43．pass_hat_k和常见pass@k是一回事吗？

回答：pass_hat_k 用实际重复执行观察题目在 k 次尝试中的成功频率或稳定性，具体统计口径与传统代码生成 benchmark 的 pass@k 估计器不同。AgentHub 在 StatisticsService 中明确要求有完整 k 次可判结果的题才能进入对应统计，并同时报告不完整 Case 数、覆盖率和全部题目的相关派生指标。阅读时要看公式、分母和缺失处理，而不是只看名称相似。

追问：如果某题 5 次里缺了 2 次，应该怎样参与 pass_hat_5？

追问回答：按项目的完整样本口径，这题不进入有完整 5 次观察的主指标分母，同时计入 incomplete_case_count 和 coverage；另外的 all_cases 指标按独立规则展示。报告要列出缺失是 Provider 故障还是观测丢失，方便定位问题。

源码定位： statistics_service.py

FE44．为什么A/B实验要尽量比较相同题目的配对结果？

回答：同一道题在 A/B 两个 Variant 上的结果具有共同的难度和材料背景，配对比较更容易看出“原来答对、现在答错”和“原来失败、现在通过”。AgentHub 的 Metric Comparison 支持对齐 DatasetItem、重复序号和 Variant，输出配对改善/退步以及相应区间。与单看两个独立平均值相比，配对结果保留了具体退步题，特别适合 RAG 证据策略变更。

追问：配对就能消除模型随机性或时间漂移吗？

追问回答：还要冻结模型路线、知识快照、Evaluator 和任务分组，A/B 执行顺序交替安排并按预定次数重复。对不完整配对单独报告覆盖情况，避免只留下两边都成功返回的样本。

源码定位： metrics_service.py

FE45．为什么评测页面不直接显示完整observation JSON？

回答：评测的 observation 可能包含用户输入、工具参数、知识片段、原始模型回复和业务标识，直接向所有可看列表的用户返回完整 JSON 会造成字段级越权和过大传输。AgentHub 的 Case 列表采用安全摘要，具体证据通过独立 API 和权限投影提供。前端显示简要状态、错误类和可打开的详情，后端负责筛选字段，浏览器不接收无权读取的原文。

追问：这种安全投影与 Runtime 的上下文投影有何区别？

追问回答：安全投影按读取者权限与敏感程度决定是否可见；Runtime 投影在有权限的前提下按任务相关性、Token 预算和来源可信度决定发送给模型的内容。两者都进行结构化筛选，但目标和规则不同。

源码定位： run-case-evidence.tsx

FE46．固定应答模型通过全链路测试，能证明模型质量吗？

回答：DeterministicEvaluationDriver 可以根据固定 expected 构造受控观察，用于验证 Runner 的分配、Claim、结果写回、指标物化和门禁流程；它把预期结果作为测试夹具输入。真实模型质量评测则使用 AgentRuntimeEvaluationDriver，根据 item.input 触发模型和工具，待结束后用独立 evaluator 对照 expected 评分。两类执行器共享评测框架，但观察来源不同。

追问：怎么在评测报告里清楚区分这两种执行？

追问回答：保存 driver 类型、Provider Attempt、Run ID、模型用量和测试夹具身份。确定性执行用于说明工程链路验证，真实 Runtime 执行用于说明模型/工具在这批任务上的效果；展示数据时给两个独立小节和实际样本量。

源码定位： runner.py

FE47．报告里332个控件通过检查，为什么还要解释分母？

回答：某次 UI 报告检查了 332 个控件，分母是这次遍历到的控件集合，而不是整个产品所有状态和所有浏览器的覆盖率。应记录测试环境、账号权限、页面清单、控件状态类型及通过/失败/未覆盖数量。AgentHub 的禁用控件巡检和业务工作台报告可作为界面回归证据，后续还需按风险挑选真实交互与后端效果测试。

追问：大规模控件检查之外，最值得补哪类用例？

追问回答：补页面状态切换、权限撤销、异步迟到响应、多标签 Session 冲突和危险按钮真实执行后置条件。特别把“控件能点击”与“数据库动作确实发生且范围正确”串起来检查。

源码定位： app-workbench.tsx

FE48．一份新评测成功率下降，你会按什么顺序排查？

回答：新评测成功率下降时，先比较数据版本与任务分母是否相同，再查 Runner 的 UNKNOWN/失败比例和 Provider 回执；然后检查有效 KnowledgeSnapshot、ToolRevision 和 Memory 绑定；再沿检索候选→证据交付→模型输出→评分器归因定位。只有这些工程事实一致，才开始判断 Prompt 或算法本身是否退步。AgentHub 的 Trace、CaseResult、MetricSnapshot 和 Taxonomy 对应不同排查层。

追问：如果问题是快照绑定错误，为什么先改 Prompt 反而危险？

追问回答：Prompt 可能临时弥补缺失材料，却掩盖真正的来源问题，还污染后续 A/B。应先恢复正确快照和证据集合，固定同一任务重跑，确认工程链路回到基线后再分析模型策略。

源码定位： runner.py

FE49．10题只答出8题且全对，能报告正确率100%吗？

回答：10 题里 8 题返回有效答案且全部正确，可以报告“有效输出条件下正确率 8/8=100%”，同时报告“全部发起任务的确认成功率 8/10=80%”与两题的错误类别。若两题是明确 Provider 失败，属于服务可用性问题；若运行证据缺失，属于未知观察，需要单独呈现。AgentHub 的 MetricResult 与 FailureTaxonomy 保留这几类事实，避免分母被自动过滤。

追问：两题没有答案，怎样判断接下来优先修哪里？

追问回答：查看两题的 AgentRun/ModelAttempt 是否存在、是否有 Provider 错误与 usage、是否缺少 Observation 或被评分器拒绝。已知 Provider 故障优先处理路由和重试；观测丢失优先修持久化与证据收集；模型明确空答则检查输出合同与可用性策略。

源码定位： metrics_service.py

FE50．面试时如何讲一次真实修复，让别人相信你懂而不只是背结果？

回答：我会挑一个能复现并在代码里定位的修复，按用户现象、根因、修改位置和可观察结果讲。例如文档详情轮询问题：列表 READY 后详情仍 PROCESSING，根因是两份查询各自维护状态，刷新只触发列表；修复使详情在活动 Job 期间继续读取并在终态收敛。展示实际 Diff、React/Network 事件顺序、受控迟到响应测试和真实 Revision/Job 回读，重点说明自己的判断和修改选择。

追问：这个修复来自仓库其他成员，而不是本人独立提交，如何介绍？

追问回答：把它作为深入走读的工程案例，说明自己追到了哪些函数、验证过哪些状态；个人贡献另选实际完成的代码、测试或实验，用明确提交与验收记录说明。面试官追问到哪个 if、哪个 SQL、哪项数据变化，都能按真实参与范围回答。

源码定位： knowledge-detail-client.tsx
