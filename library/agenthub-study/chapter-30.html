第 26 讲：数据库进阶、连接池与性能定位

一、性能问题先找等待在哪里

一次 RAG 回答可能包含数据库读取、查询编码、Qdrant 检索、重排、证据整理、模型生成和结果保存。如果模型生成用了 8 秒，优化一个原本 3 毫秒的 SQL，用户几乎感觉不到；如果所有请求都在等数据库连接，即使模型再快也没有用。

所以先把总耗时拆成阶段，并看失败、排队和资源占用。项目有运行步骤、结构事件、计时和错误分类，但不能因为有这些字段，就宣称已经接入了完整外部 APM 平台。观测计时 API 依赖检查

这里的关键问题不是“有没有日志”，而是“我是否能用同一个 Run 或任务身份，把用户症状连接到具体等待点”。

二、为什么外部模型调用期间不宜持有数据库连接？

假设连接池允许 10 个同时占用的连接。每次业务查询本来只需 20 毫秒，但代码把 Session 的事务一直保持到 12 秒的模型调用结束。很快，少量并发就把连接全部占满，其余请求只能等待。

这是一个教学假设，不是 AgentHub 的实测容量数字。它说明连接占用时长和并发数之间的关系：把不需要数据库的网络等待放进数据库占用窗口，会显著减少系统可处理的并发。

项目的 create_database() 使用异步引擎、pool_pre_ping=True 和 3 秒的 pool timeout；expire_on_commit=False 帮助避免提交后普通属性访问触发不必要的自动过期加载，但不意味着不会有任何属性过期，也不等于连接会自动在所有业务点及时释放。数据库工厂

合理的阶段拆分通常是：短事务读取并验证输入，结束数据库占用；执行外部计算；再开短事务确认自己仍有执行资格并写结果。拆开之后会出现并发窗口，因此必须结合版本、租约和条件写回，不能只为缩短连接时间而丢掉一致性。

三、AsyncSession 不是一个可随意共享的全局对象

Session 除了执行 SQL，还管理当前事务和 ORM 对象状态。把同一个 Session 交给多个并发协程同时修改不同对象，容易让事务边界和失败处理混在一起。工程上应给一项清晰的工作单元建立可解释的 Session 生命周期。

flush() 将待处理变更发送给数据库，可能得到主键，也可能立即遇到约束错误；commit() 提交事务；rollback() 撤销当前事务；refresh() 主动重新读取对象。第 3、5 讲已经介绍它们，这里再增加一个要点：发生 SQL 错误后，不能假装事务仍然正常，继续执行后面的保存。

项目在创建和发布等路径捕获 IntegrityError 后回滚并返回稳定业务错误。它不会把数据库异常完整堆栈作为用户操作指南。发布服务 错误响应

四、唯一约束、行锁、版本号和租约分别挡什么？

机制 主要约束 AgentHub 中的例子 不能替代
唯一约束 两条记录不能拥有相同业务身份 文档修订号、Token 哈希、部分去重键 正确的状态流转
行锁 同一段竞争状态在事务内串行处理 发布 Agent、创建文档修订、修改工单 跨事务长期任务的执行权
expected_version 用户基于哪个已读版本提交变更 客服工单的状态修改 业务终态与幂等合同
租约与 generation/token 哪个执行者此时有资格继续写 摄取与评测 Worker 已经发出的外部写入撤销
多列外键 子对象归属必须成组匹配 Chunk 与 DocumentRevision 用户授权

这些例子分别可在知识模型、摄取服务、客服服务和发布服务核对。

一个典型错误是认为“已经有唯一约束，不用加锁”。约束能挡住重复修订号，但可能把正常并发上传中的一个请求变成冲突；在同一文档行上串行分配编号，可以让两个合法请求依次生成不同修订。另一个错误是认为“有锁就不用约束”。不是所有写入永远走同一段服务代码，数据库仍需要守住不能被破坏的关系规则。

五、索引要从查询的筛选与排序推导

假设常见操作是按工作区读取某个修订的所有分块。查询同时包含 workspace_id 与 document_revision_id，当前 document_chunks 有对应的复合索引。这个索引的理由来自访问模式，而不是因为某一列“看起来重要”。分块模型

-- 教学 SQL：命名参数需由数据库客户端或驱动绑定。
SELECT chunk_id
FROM document_chunks
WHERE workspace_id = :workspace_id
  AND document_revision_id = :revision_id;

如果改成“跨全部工作区找最新 100 条”，原有索引就未必足够。设计索引时要看选择性、组合条件、排序、返回列和写入负担。每多一个索引，插入和更新时就多一份维护工作，因此不能对每列都加索引后宣布性能优化完成。

查看执行计划可以帮助判断扫描范围、估计与实际行数、排序及连接代价。学习时要知道 EXPLAIN ANALYZE 会真正执行语句；不要把它随意加到有副作用的生产写入上。对于本次文档，我们只说明方法，没有连接你的运行数据库执行性能分析。

六、部分唯一索引为什么适合 Memory？

一种常见需求是“有效记忆不能重复，但历史失效记忆需要保留”。如果对内容键建立无条件唯一约束，旧记忆失效后也可能挡住以后再次建立相同事实；如果完全没有唯一约束，并发抽取又可能产生重复有效项。

项目的 Memory 通过带有效状态条件的唯一索引支持相应去重规则，最新 USER/AGENT 范围还要参与身份区分。具体列以当前 ORM 和迁移为准，不能把“同文本”简单当作全平台同一记忆。Memory 模型

还有一个迁移细节：ORM 元数据与迁移必须共同表达索引谓词。否则自动生成迁移时，工具可能把现有部分索引理解成“模型里没有的对象”，产生错误的删除建议。自动生成是候选脚本，开发者仍要审查。数据模型规范

七、JSONB 不是“以后不用改表”的万能字段

版本规格、工具参数和结构化观察适合保存 JSONB，因为形状可能随合同演进，且需要保留整体快照。但经常被过滤、关联、排序或用于完整性规则的身份字段，通常应该拥有明确列与约束。

如果把 workspace_id、status、created_at 全部塞进一团 JSON，后续权限过滤、约束、索引和迁移都会更难解释。反过来，把每个模型观察字段都拆成列，也会制造大量稀疏字段和频繁迁移。

比较好的划分是：稳定业务身份和状态使用显式列；有版本合同的复杂内容使用 JSONB；关键摘要指标按查询需求物化，但保留它们来自什么原始记录和计算版本。AgentVersion 的规格快照与 Evaluation 的指标快照正是这种分工的不同实例。发布服务 评测模型

八、缓存最难的不是存进去，而是知道什么时候不能复用

跨修订向量缓存不能只用文本哈希做键。相同文本在不同编码器、不同模态或不同工作区约束下，不一定允许复用。当前缓存把实际编码输入和编码器身份等因素纳入判断，且即使向量复用，新修订仍拥有自己的 Chunk 身份和引用位置。向量缓存

可以把缓存分成两层思考：一层是昂贵计算的复用，另一层是业务身份和来源的保留。复用计算结果，不意味着可以把新文档假装成旧文档；否则用户点开引用时会发现来源版本不对。

缓存命中率高，也不自动代表用户体验更快。若主要耗时在解析或模型回答，编码缓存节省很大比例的编码调用，总耗时变化也可能有限。改缓存必须同时观察命中率、总延迟、错误率、存储增长和引用正确性。

九、扩容前，先找第一个真实瓶颈

CPU 解析、GPU 编码、模型远端速率限制、数据库锁、连接池、索引查询和前端重复请求，可能分别成为瓶颈。增加 Worker 数量只会增加并发压力，未必让所有任务更快。Compose 当前示例 Worker 并发设置为 1，这只是该运行配置，不是项目永远不能并发的理论限制。Compose

为某个改动写一个小型容量假设：每秒任务数、平均与尾部耗时、同时占用哪类资源、失败后重试会放大多少负载。再用隔离任务验证假设。没有测量时，就把数字写成假设，不把它包装成“支持千级并发”。

本讲的独立练习可以很小：选一个页面，统计一次打开会产生几条请求；选一个后台任务，标出数据库事务开始和结束；选一个索引，写出它服务的实际查询。你会发现这比背“Redis 提高性能”更接近工程能力。
