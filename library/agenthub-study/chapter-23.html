第 19 讲：数据库性能与并发定位——从一次慢请求找到真正的瓶颈

第 5、6 讲已学 CRUD、外键和基础索引；这里不重复定义，直接用 AgentHub 的真实查询形状和 Worker 行为学习分析方法。源码：packages/core/database.py、packages/knowledge/models.py、packages/knowledge/ingestion.py、packages/control_plane/services.py、packages/knowledge/vector_cache.py。

19.1 一个页面“慢”，不要先给所有列加索引

假设用户报告：“进入知识库详情页需要 8 秒。”这 8 秒可能花在：

浏览器等待/重复请求        120 ms
API 授权与参数解析           30 ms
等待数据库连接             2500 ms
SQL 本身                    15 ms
响应序列化                  20 ms
网络或其他阶段            5315 ms

这些数字是用于讲解的假设，不是项目跑分。若 SQL 只有 15ms，再建索引大概不会解决主要问题；应该先调查连接等待和网络。先定位瓶颈，后决定该优化哪一层。

19.2 为什么长时间持有 Session 会让系统突然崩溃式变慢？

假设连接池最多 10 条有效连接，正常查询用时 20ms。代码却在查完数据后，继续持有事务和连接等待模型 12 秒。

# 教学反例：数据库事务跨越昂贵的外部 I/O
async with session_factory() as session:
    async with session.begin():
        row = await session.get(AgentRun, run_id)
        answer = await model.generate(...)  # 等待 12 秒
        row.final_output = answer

即使模型调用不使用数据库，事务仍被持有。当并发上来时，连接池首先耗尽，后续请求堵在取连接上。

更合理的方式：

# 第一段：短事务获取并确认输入
async with session_factory() as session:
    run_snapshot = await read_and_validate_run(session, run_id)

# 外部耗时阶段不持有数据库事务
answer = await model.generate(run_snapshot.prompt)

# 第二段：短事务核对执行所有权并写回
async with session_factory() as session:
    async with session.begin():
        await update_run_if_owner_matches(session, run_id, owner_token, answer)

这引入了另外一个问题：第一段读取之后，Run 的状态可能变化。第二段必须重新检查租约或版本身份。短事务解决连接占用，条件写回解决事务之间的并发窗口。

项目的数据库工厂使用异步引擎和连接池配置，实际池大小、等待时间应按部署设置观察。5。

19.3 拿一条真实查询练习 EXPLAIN

假设应用常按 Workspace 和 Revision 查询所有 Chunk：

SELECT chunk_id, ordinal, text
FROM document_chunks
WHERE workspace_id = '00000000-0000-0000-0000-000000000001'
  AND document_revision_id = '00000000-0000-0000-0000-000000000002'
ORDER BY ordinal;

这些 UUID 是演示值，请在测试数据库使用真实存在的测试记录。

看执行计划时关注什么？

EXPLAIN (ANALYZE, BUFFERS)
SELECT chunk_id, ordinal, text
FROM document_chunks
WHERE workspace_id = '00000000-0000-0000-0000-000000000001'
  AND document_revision_id = '00000000-0000-0000-0000-000000000002'
ORDER BY ordinal;
  • Seq Scan：是否需要扫描大部分表？小表时顺序扫描有时更便宜。
  • Index Scan / Bitmap Index Scan：索引筛选了哪些条件？
  • Sort：过滤后是否额外排序，内存/磁盘开销如何？
  • rows（估计与实际）：统计信息是否严重偏离？
  • Buffers：是否大量读取数据页？
  • Execution Time：是否真的把主要耗时花在数据库执行上？

一个常见优化是为高频 (workspace_id, document_revision_id, ordinal) 读路径评估合适的复合索引。但是索引顺序必须来自WHERE 条件、排序和选择性；若当前索引已经可用，就不需要凭印象重复建一个。索引还会增加写入维护、磁盘占用与 VACUUM 成本。SQL 示例与执行计划解释是教学方法，本次没有连实际数据库跑 EXPLAIN。

19.4 为什么两种并发控制经常同时出现？

第 6 讲说过唯一约束，下面把它和锁、版本、租约放进一个具体竞争场景。

两位管理员同时给 Document D1 上传新 Revision
当前 revision_number = 4

如果都执行 SELECT max(revision_number) 并算出 5，就会竞争同一个 (document_id, revision_number)。数据库唯一约束可以让其中一个失败；但如果服务希望两次合法上传都成功并各自得到 5、6，就需要协调编号分配过程（例如锁住同一 Document 行）。

其他业务还需要不同机制：

机制 解决的真实问题 对应使用场景
业务唯一键 禁止两个记录共享同一身份 用户提交 token、单据编号、修订号
行锁 FOR UPDATE 事务内保护竞争状态 同一文档版本生成、工单状态修改
expected_version 避免基于过期页面修改 两个客服同时处理同一 Ticket
租约 + token 跨事务的长任务执行权 Worker 解析、编码与写入
复合外键 限制多列归属一致 Chunk 的 Document 与 Revision 配对

用一个 SELECT ... FOR UPDATE 持续锁住几分钟的模型推理并不合适。对跨进程的长任务，租约负责执行权，数据库短事务负责每一次可验证的状态推进。

19.5 DB 死锁和应用状态竞争不是同一件事

假设 Worker A 先锁 Run，再锁 Approval；Worker B 先锁 Approval，再锁 Run：

解决办法是所有路径尽量采用同一锁顺序，减少锁的范围与持有时间，并为明确可重试的死锁错误设置有界退避。对所有数据库异常盲目重试会掩盖业务约束冲突，尤其可能引发重复外部写入。

评估竞争问题时，把时间线写到精确步骤：哪个事务持有什么锁、什么时候读到状态、哪个字段在哪次提交改变。泛泛说“并发导致 Bug”无法指导修复。

19.6 N+1：一个列表为什么会突然变成几十个请求？

假设客服工作台列出 20 个 Thread。前端为了每个 Thread 的消息数、最新 Artifact，又逐一调用两个 API：

1 次 Thread 列表
20 次查 TurnCount
20 次查最新 Artifact
合计 41 次 HTTP 请求

解决思路：让列表提供适当的汇总字段，或一次批量查询足够的信息；权限、分页和字段范围仍由后端负责。把所有业务详情一次性全返回也不是好办法，会增加响应大小和泄露面。

在浏览器 Network 中能直观看到 N+1。修复前后比较请求数、TTFB、总带宽、页面首次可操作时间，并在不同工作区与权限下测试字段投影。

19.7 缓存为什么要有 Encoder 身份和数据来源？

跨文档修订的向量缓存是一个好例子。文本相同，不代表一定可以复用向量：还需要编码器、模型版本、编码配置、Dense/Sparse 类型、工作区安全边界等身份一致。当前实现中 encoder_fingerprint 和输入文本的内容身份参与缓存匹配，新 Revision 即便复用向量也拥有自己独立的 Chunk/Point 身份。21。

一条完整的缓存优化报告建议同时列出：

指标 对比方式
编码缓存命中 复用向量的真实条数 / 需要向量的条数
编码耗时 固定文档的 wall time 与实际调用次数
入库总耗时 包含解析、Chunk、编码、Qdrant 维护
检索与回答质量 相同原文金标是否仍可查，来源是否正确
容量 缓存表和向量索引增长速度

缓存命中后，如果等待时间主要来自模型生成，整体用户体验改善仍可能有限。因此需要量化节省发生在整条链的哪一层。

19.8 独立实战：从一条慢 SQL 到一次真正有证据的改动

推荐按以下顺序做：

  1. 固定真实查询与业务输入，记录数据量、分页和并发。
  2. 在隔离数据库运行 EXPLAIN (ANALYZE, BUFFERS)，确认扫描和排序代价。
  3. 只改变一个索引或查询方式，避免同时改 ORM、缓存与前端。
  4. 对照执行计划和 p50/p95，记录 CPU、连接等待和写入成本。
  5. 验证结果顺序、工作区过滤、分页一致、越权请求不可见。
  6. 给出迁移脚本、回滚策略、固定测试与性能对比。

本讲掌握标准：能够看到“慢”先判断是池等待、锁等待、SQL 执行还是外部模型时间，再根据真实查询决定是否建索引、批量查或缩短事务。

19.9 连接池、锁与队列之间的压力会相互放大

设想一次大批量入库：API 一次提交 100 个 Job，Beat 及时补投；Worker 增加到 16 个；每个 Worker 都在解析/编码阶段同时持有数据库 Session 并等待外部接口。虽然单任务没变慢太多，系统可能出现：

  • 数据库连接池排队变长；
  • Job 心跳续租拿不到连接，租约过期；
  • 对账程序认为任务需要处理，增加可见队列压力；
  • 重试又增加外部编码/索引负载。

这是一种反馈环，出现时应该同时调查任务吞吐、连接等待、租约失效率、重试次数和队列积压。仅调大连接池也可能把压力转移给 PostgreSQL 自身；仅加 Worker 又可能扩大争锁。

用 Little 定律建立容量直觉

若系统稳定，每秒到达 (\lambda) 项任务，平均在系统中逗留 (W) 秒，则系统内平均任务数近似：

[ L=\lambda W ]

例如每秒到达 2 个任务，平均在排队和执行中停留 15 秒，则平均约 30 个任务在系统中。这个公式给你估算积压规模的直觉；实际尾延迟、请求高峰、重试和不同资源类型还需要测量。做容量设计时先核对假设，不把这个算式当成最终机器规格。

19.10 一个复合索引为什么不是“越长越好”？

假设有三个查询：

-- 查询一：按 workspace 与 revision 读取所有块
SELECT chunk_id FROM document_chunks
WHERE workspace_id = :w AND document_revision_id = :r;

-- 查询二：按 workspace 与 document_id 统计修订
SELECT COUNT(*) FROM document_revisions
WHERE workspace_id = :w AND document_id = :d;

-- 查询三：跨 workspace 按 created_at 抓最近失败 Job
SELECT id FROM ingestion_jobs
WHERE status = 'FAILED'
ORDER BY updated_at DESC LIMIT 100;

三者的筛选、排序与表都不同。对 document_chunks 设计的索引无法直接代替 document_revisions 或 ingestion_jobs 的查询计划。即使在同一表上，索引 (workspace_id, document_revision_id) 也未必适合只按 document_revision_id 过滤的查询。应根据实际索引使用率、读写比例、表大小、排序成本和基数选择。

分析时也要避免简单的“看到 Seq Scan 就建索引”：当表只有几十行，顺序扫描很可能成本更低。EXPLAIN ANALYZE 的重点是实际处理多少行、在哪里耗时，而不是追求所有节点都显示 Index Scan。

19.11 多租户查询的索引要配合安全模型

如果应用绝大多数业务查询都以 workspace_id 为首要过滤条件，索引设计也应优先考虑这一真实访问模式。但注意“索引包含 workspace_id”不是授权。只要某条查询忘记过滤，索引不会自动限制可见范围。相反，数据库中的复合外键帮助防止跨工作区错误关联，Service 中的 Context 帮助限制谁能读取。

这里有三层可以共同优化：

  • 安全层：API 和 Service 永远绑定可信 WorkspaceContext。
  • 数据层：外键/唯一键保护工作区与关联对象归属。
  • 性能层：复合索引与查询计划减少正确范围内的扫描。

一次数据库性能优化必须复测跨工作区输入、空结果与分页；只比较单一管理员账号的查询速度是不完整的测试矩阵。

19.12 性能工程的交付格式

为每个优化建立一张表：

项 内容
症状 页面 P95 从 0.8s 升至 3.1s（假设）
定位 通过 Trace，2.2s 在 DB Pool 等待（假设）
根因 外部模型等待期间持有数据库连接
改动 外部计算移到短事务间，提交时带 owner_token 检查
对照 固定并发、请求分布、数据量，比较 P50/P95 与超时率
正确性 工单版本、权限范围、租约和重复提交测试
代价 增加一次重新加载与状态核对

用这种格式讲优化，不需要声称“一次索引就提升十倍”之类缺少前提的数字。事实、假设和验证的边界清楚，面试官才知道你具备定位能力。
