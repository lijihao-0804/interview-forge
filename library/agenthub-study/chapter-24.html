第 20 讲：真正值得研究的下一步——Memory、Wiki 与 RAG 的质量工程

这是新增研究专题，不是再次介绍 RAG、Memory 和 Wiki 的定义。第 8、9、11 讲已学基础机制与评测方法，本讲直接从现有瓶颈切入：检索为什么漏、记忆为什么错、Wiki 为什么不随原文更新，以及怎样用冻结实验决定是否引入新技术。下文“当前实现”对应 0；“候选实现”是下一轮工程计划。

20.1 定义四个独立失败点，比笼统说“Agent 答错了”有用

面对一次错误回答，先找到问题发生在哪个阶段：

这四种错误需要不同改法。如果写入端把“本次演示使用 SQLite”错误提炼为“项目长期使用 SQLite”，换更强的向量检索只会让错误记忆更常出现。若召回完全漏掉同义问题，再增加 Reranker 也救不回来。若候选里证据齐全但预算删掉例外条款，再换 Embedding 也解决不到根因。

因此先建立分层因果记录：source -> candidate -> selected -> delivered -> supported_answer。每一层保留可追踪的身份与丢弃理由，研发与评测的输入才能对齐。

20.2 Memory：下一步不是“直接加向量”，而是“召回 + 写入治理 + 冲突演化”

当前 packages/memory/store.py 主要使用词面、显著性与时间等信号选取记忆；已有 USER 私有作用域、过期字段、按 Run 冻结选中 Memory 的机制。语义召回还需要新的检索层，但它只是一个环节。

案例：语义不同说法，但事实相同

用户昨天说：我的主要开发语言是 Java。
用户今天问：我最熟悉的编程语言是什么？

如果词面选择器要求有足够的同词重叠，可能错过“开发语言 ↔ 编程语言”。候选实现可以在已授权的 Memory 范围内做 Dense 召回，再与关键词匹配并集，重排后按预算选择。

权限过滤应先成为检索合同的一部分。例如 USER 私有 Memory，不能先跨用户搜全部向量，得到结果后只在前端隐藏；向量检索与数据库回查都应绑定 owner、workspace 和 agent 范围。索引中的 metadata 只承担候选过滤，最终授权与内容加载继续由可信服务确认。

写入资格比召回效果更早出现风险

考察两句话：

  • “这次调试暂时使用 SQLite。”
  • “所有正式环境已经迁移到 PostgreSQL。”

如果模型把二者合成“默认数据库是 SQLite”，这是错误抽取。建议把 Memory 写入拆成四步：

  1. 候选抽取：从用户原话抽取主张、条件、时间范围与引用位置。
  2. 忠实度审查：检查否定、限定词、数字、时态是否被保留。
  3. 写入资格：判断是否为持续有用的用户事实；临时指令和系统生成推测应拒写。
  4. 版本关系：查找与已有 Memory 的同义、补充、条件冲突或替代关系，并保存修订依据。

可以设计更细的事实结构，例如：

{
  "subject": "user",
  "predicate": "preferred_development_language",
  "value": "Java",
  "valid_from": "2026-11-01",
  "valid_to": null,
  "scope": "USER",
  "qualifiers": {"purpose": "algorithm_interviews"},
  "provenance": {"turn_id": "...", "quote": "面试手撕题我用 Java"}
}

这是候选 Schema，不是当前 Memory 表的现有字段。

为什么要 qualifiers？“算法题用 Java”和“项目后端用 Python”可以同时成立。仅按“用户喜欢哪门语言”做覆盖式更新，会把两条本来不矛盾的事实误判为冲突。

冲突演化：不要让“最新”成为唯一真理

可以把记忆关系看成：

M1：项目默认模型 A，来源 Turn 101
M2：项目当前改用模型 B，来源 Turn 233，替代 M1
M3：实验环境仍使用模型 A，来源 Turn 235，条件不同

这里 M2 可替代 M1 的“默认配置”事实，但 M3 不应被 M2 删除。现有 SUPERSEDED 状态可作为演化基础；后续需要写入显式替代关系、冲突类型和来源条件。对于高风险数字或权限偏好，优先返回澄清而非强行合并。

固定评测怎样设计？

子集 测什么 例子
M-A 同义召回 改写问法是否召回正确 Memory “开发语言”→“编程语言”
M-B 无关拒召 不应带入与问题无关的个人偏好 查询数据库错误却召回饮食偏好
M-C 事实忠实 抽取是否保留否定、条件、时间 “仅测试时使用”不能变成常态
M-D 冲突更新 新旧事实是否正确替代或并存 实验环境和生产环境不同
M-E 权限隔离 其他用户、其他 Agent 的记忆不可泄露 跨 Workspace/owner 攻击
M-F 回放稳定 同一 Run 恢复采用原始冻结记忆 后续失效不篡改历史输入

在 DEV 上比较词面基线、词面加向量、混合重排三种配置。每条题保留可答性、应命中来源和不应命中来源；除 Recall@k 外，还统计误召、额外 Token、回答收益与 P95 延迟。这样才能判断语义检索的增益是否大于它带来的无关上下文。

20.3 Wiki：从“编译一次”升级到“原文变化后的增量维护”

基础版 Wiki 的思路第 9 讲已介绍：从冻结知识来源提取 claim、页面和关系，再验证来源，生成发布物。真正困难的是原文频繁变动时，哪些 Wiki 主张受到影响？怎么更新而不重写所有内容？

先建立依赖关系，而不是先选图数据库

设一份政策文件 V3 包含三段，Wiki Page P1 从其中两段派生出 claim C1、C2：

DocumentRevision V3
  ├─ Chunk A -> Claim C1 -> Page P1
  └─ Chunk B -> Claim C2 -> Page P1

DocumentRevision V4 只修改了 Chunk B

应该优先定位：

  • C1 的来源是否仍存在，是否能复用？
  • C2 对应原文区间是否改变，是否需要重抽？
  • P1 的展示正文、关系、冲突检查是否需要重新编译？
  • 旧 Wiki Publication 已有哪些 Run 使用？新发布是否应让这些旧 Run 随之变化？

这个问题本质是来源依赖图。如果查询方式只是“从 claim 找来源、从来源找受影响 claim”，PostgreSQL 中的关系表和索引足以表达；若将来需要复杂多跳推理、路径搜索和交互式图分析，再拿具体查询负载评估图存储。

提议的增量流程

  1. 比较来源身份与区间：用 Revision、Chunk、原文区间与内容 Hash 找实际变化。
  2. 构造受影响依赖集合：从来源向派生 Claim/页面传播 dirty 标记。
  3. 定向重新抽取：只处理受影响区域，保持未改主张的来源身份可解释。
  4. 核对合成结果：逐条验证引用是否仍指向当前源修订，检查冲突关系。
  5. 创建候选 Publication：不原位覆盖已经发布的历史版本。
  6. 人工审核并按 AgentVersion 升级：保留旧执行的历史绑定。

这里最大坑是“内容没变”不等于“适用性没变”。例如段落 A 文本没变，但它前面的章节标题从“普通商品”改成“定制商品”，A 的事实适用范围可能已改变。增量机制必须有结构依赖与引用窗口，否则盲目按 Chunk Hash 复用会制造错误主张。

冲突识别必须带条件

例如：

C1：普通商品 7 天内允许退货
C2：定制商品不适用七天无理由规则

两条主张都包含“退货”，数值或价值不同，但适用条件不同，并不冲突。

候选结构可以使用 subject / predicate / value / condition / valid_time / source 的组合键，判断同范围、同时间、同谓词下 value 是否冲突。对于无法自动归一的日期或条例优先级，可以生成需要审核的冲突候选。

源码入口：10 · 11。当前查询页面主要按标题和简单关系选取；下一步语义页面召回也应复用同一套来源和权限校验。

20.4 RAG：把关注点转移到“完整证据集”，而不是继续盲目增加 Top K

第 8 讲已经掌握 Dense/Sparse、RRF、Rerank。这一节研究两个尚未完全解决的问题。

问题 A：两个证据缺一不可

问：“定制商品第三天能不能按七天无理由退款？”

必须同时考虑：

A：普通商品七天内允许无理由退货
B：定制商品是例外

传统 Top K 更重视每个 Chunk 的单独得分，但本题评价需要一组足以回答的证据。候选选择可以从“逐条贪心”扩展到对条件和例外的覆盖，考察 evidence_group 级别的完备性。

例如：

{
  "question_id": "return-exception-01",
  "required_groups": [
    ["general-seven-day-rule"],
    ["custom-product-exception"]
  ],
  "forbidden_conclusion": "all_goods_can_return_within_7_days"
}

这是一份评测金标结构，不是把答案放进生产检索器里。线上系统没有提前知道正确 group，应该通过互补选择、候选子问题、实体条件抽取、再检索等策略提高找到完整集合的机会。

问题 B：证据合并后如何保留所有来源？

为了节省 Token，可能将相邻的两个片段合成一个可读段落：

合并文本：
"普通商品七天内可退；定制商品除外。"

如果只保存一份 Chunk ID，合并后的第二句话可能没有正确来源。建议把来源投影升级为：

{
  "merged_evidence_id": "E1",
  "text": "普通商品七天内可退；定制商品除外。",
  "parts": [
    {"chunk_id": "A", "revision_id": "V3", "span": [0, 14]},
    {"chunk_id": "B", "revision_id": "V3", "span": [0, 9]}
  ]
}

这里 span 是教学结构。真实坐标还需区分 PDF 页、段落、表格 cell 和字符范围。模型可以读 E1，但后端 Registry 应能根据每个合并片段找到原始来源。只有建立这条映射，才能安全开展 source-span 合并与预算压缩实验。

两次预算应该分别评价

RAG 工具自己的 context_budget_bytes 控制检索证据载荷；Agent 最终 ModelRequest 还有完整上下文 Token 预算。一个条款可能通过工具内部选择，却在合并 Memory/历史后被最终裁掉。因此评测时应同时记录：

  • retrieved：候选中有哪些来源。
  • selected：工具选择了哪些证据。
  • delivered：最终模型请求实际看到了哪些证据。
  • supported：回答中的每项结论由哪些来源支持。

现有 Evidence Registry 的可见来源校验提供很好的基础。下一步重点是用完整证据评测和逐结论核对推动策略，而不是把“有引用编号”当作质量指标终点。

20.5 怎样组织一次不陷入无限参数搜索的改进实验？

你之前已经学会第 11 讲的固定数据、DEV/HOLDOUT 和成对比较。现在用它们真正推进三个质量模块。

第一步：冻结一份有“错误归因”的小数据集

比如总共 60 个独立案例，按任务族冻结：

题组 数量（示例） 标注重点
Memory 写入与冲突 15 原话、抽取事实、条件、是否长期有效
Memory 同义召回 15 应选/不应选的记忆身份
Wiki 原文变更 15 受影响 claim 与页面、历史发布身份
RAG 多证据问答 15 最少需要的证据组、可接受结论与拒答

这是建议的教学规模，可以先做 20 个最具代表性的 DEV 案例跑通评测合同，再扩大到完整实验。按源文档/任务族划分数据，避免换个问法的同一事实同时进入 DEV 和 HOLDOUT。

第二步：比较少量有机制区别的候选

Memory：词面基线 → 词面+向量 → 混合重排及冲突治理。

Wiki：全量重编译基线 → 只重抽 Chunk 改动 → 带结构依赖的增量编译。

RAG：现有证据预算基线 → 互补选择 → 保留来源的 span 合并（当候选有独立质量收益时再采用）。

同一轮尽量只改变一个主要机制，并在预先固定的数据上比较。不要同时换生成模型、Embedding、Prompt、预算和评分器，然后把收益全部归给新算法。

第三步：统一质量与成本量尺

层 指标 要检查的失败
写入 事实忠实率、无关写入率、冲突演化准确率 错误信息永久化
召回 Recall@k、误召率、权限泄漏零容忍 关键材料漏掉、无关材料占预算
交付 需要的 evidence group 覆盖率、来源映射完整率 找到但裁掉，合并后来源错
回答 可答正确率、不可答正确拒答率、关键条件正确率 数值/否定/例外误读
资源 Token、缓存命中、P95、API 成本、编码次数 精度微升却成本大增

做完实验不仅报告平均值，还要列出新通过的案例、旧通过变失败的案例、未知或未评价的案例。这比单个总体 F1 更能指导下一次修复。

第四步：明确停止和发布条件

建议一次方向最多保留一份基线和两份预定候选，先完成 DEV 归因，再锁定候选进入独立验收。若核心任务没有改善、严重回归增加或成本超出约束，就保留当前默认，并把失败案例纳入下一轮的问题定义。

最后根据技术收益决定是否正式纳入主线：

这条流程的重点是让实验结果决定技术路线。向量 Memory、图数据库、语义 Wiki、Source-span RAG 都可以是候选，但只有明确解决了用户问题，才值得支付额外的系统复杂度。

20.6 一份可以交给 Coding Agent 的真实需求合同

下面给出一个足够小、可以独立交付的方向，而不是泛泛要求“全面升级 Memory”：

题目：在不改变现有授权与冻结回放规则的前提下，为 USER 私有 Memory 增加可切换的语义候选召回。

输入：当前用户问题、已授权的 workspace/agent/owner、原有候选记忆表、冻结的编码器身份。
输出：有界候选 Memory ID、召回方式与分数、最终选入 ModelRequest 的完整记录。
约束：跨用户与跨 Agent 隔离；过期/失效 Memory 不进入新选择；同一 Run 的冻结快照回放保持原语义；选择失败按原词面实现回退；不得静默扩大 Context Budget。
实验：固定 DEV/HOLDOUT 同义、无关、冲突、隔离四类题；与现有词面策略配对比较；保存误召和预算成本。
交付：配置开关、迁移、检索服务、针对性测试、逐题结果、成本及回滚计划。

这就是把“现在还没做向量检索”真正变成一项工程边界明确、能验证是否有价值的研究开发任务。
