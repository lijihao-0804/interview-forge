第 20 讲：Memory 的工程边界

20.1 先纠正两个容易沿着旧讲解传播的印象

当前 Memory 不能描述为“所有 Agent 共用的一堆记忆”。运行时选择至少受工作区、Agent 和可选用户所有者约束；owner_user_id 非空时形成用户分区。也不能描述为“只要加上向量数据库，Memory 就完整了”：当前真实难点还包括该不该写、原话是否支持、条件是否丢失、怎样处理新旧矛盾、谁能看见，以及一次 Run 到底用了哪几条。Memory 模型 选择与写入

还要同步一个已经变化的默认值：当前 AgentPublishService.create_draft 在调用方未提供 memory 配置时，默认写入 long_term_memory=true；启用记忆且未显式指定 scope 时，以 USER 为默认范围。显式关闭仍会保留，已有草稿的更新与已发布版本也要遵守各自兼容和冻结语义。因此，旧讲解里的“默认关闭”应按旧基线阅读，不能继续当成今天所有新建 Agent 的默认行为。新建草稿与配置更新

这一轮 31 个新提交并没有把 Memory 改成向量检索。因此，本讲是在最新源码基础上补全设计理解，同时给出明确标为“可做”的下一步。不要把本讲后面的方案写进简历当成已经完成。

先用三个问题区分长期记忆与普通知识库：

  • “用户希望以后先给 SQL，再给解释。”这是跨轮有效的工作偏好，适合考虑 Memory。
  • “公司 2026 年住宿报销规则是什么？”这通常应查有版本的制度原文。
  • “刚刚那一条报错的 request_id 是什么？”这是当前任务或历史记录中的细节，不一定值得成为长期记忆。

Memory 的价值是减少重复交代稳定背景。它的危险是让一次误解反复影响以后的任务。

20.2 私有分区是一条查询约束，不是一个 UI 标签

当前 Store 的选择条件是 workspace_id、agent_id、owner_user_id、ACTIVE 状态，以及未过期条件。这里的 owner 是精确匹配：选择私有分区时，不会仅因为同一个 Agent 还有共享记忆，就自动把两者合并；共享分区以空 owner 表达。Store.select

这与管理页面的可见集合不是同一件事。管理服务会按权限读取当前用户可见的共享与本人记忆，并对共享记忆管理和私人记忆管理作相应检查。管理页面可以列出的条目，不等于当前一次 Run 会注入的全部条目。Memory 管理服务

再进一步，Memory 的用户分区不等于整个应用已经变成私人空间。Thread、Run、工具结果、Artifact 和审计记录有各自的授权合同。一个模块加上 owner_user_id，不能自动推出其他表也具备相同私密性。这是未来扩大隐私范围时必须先明确的产品边界。

你在设计多租户功能时，可以按以下顺序问：

  1. 这条记录属于哪个工作区？
  2. 它属于哪个 Agent 或业务对象？
  3. 它是共享还是仅属于某用户？
  4. 管理、检索、回放、导出是否使用同样的范围？
  5. 记录被投影进下游产物后，那个产物由谁读取？

只有把第五个问题也问到，才能避免“原表已隔离，生成结果却被更广泛共享”的漏点。

20.3 当前为什么不用 Embedding：先看真实选择算法

Store 当前读取合格分区里的活动记忆，按查询词项匹配、salience 和创建时间排序，再取数量上限。它没有 Memory 向量索引。可选的 lexical_overlap_v1 是后选择过滤：要求剩余记忆与查询至少有一个词项重叠；它不会改变存储、底层排名和历史快照。选择实现 选择策略

拿一个例子看它的取舍：

  • 记忆：“给我的 Python 示例优先使用类型标注。”
  • 查询：“帮我写一个 Python 参数解析器。”

词面有 Python，容易命中。

但查询变成“写一个带静态类型提示的命令行程序”，如果分词结果没有与记忆内容重合，它可能漏掉。跨语言同义表达也可能漏掉。代码把同义改写与跨语言等价遗漏作为明确限制，而不是把词面匹配称为语义检索。选择策略限制

同时，旧的无选择策略路径可能在没有词项命中时继续按显著性与时间返回条目。增加 lexical 过滤能减少某些无关注入，却也可能损失同义场景召回。这里不是“新策略一定更好”，而是精确率与召回率需要在真实记忆任务上比较。

如果我要接向量检索，第一步应该改哪里

应该先保持 MemorySelector 合同：输入授权范围、Agent、owner、查询和数量限制，输出带稳定 ID 与内容哈希的候选。新增语义召回只是候选层的一种实现，后面仍需预算、冻结与追溯。不要让向量库直接决定权限，也不要只返回没有数据库身份的自由文本。Memory 合同

一个可验证的演进方案是：

  • 先按工作区、Agent 和 owner 限定可检索范围。
  • 在该范围内做词项与语义双路候选。
  • 保留召回原因、模型版本、得分和来源 ID。
  • 用固定记忆任务判断是否该注入，而不是仅判断文本相似。
  • 最终冻结本次实际选中内容，保留旧运行可解释性。

这是建议方案，当前源码没有自动完成这整条流程。先做小规模标注和基线，通常比先接一个很大的向量集群更有收益。

20.4 写入记忆，比读出记忆更需要克制

当前抽取只把用户输入送给抽取器；兼容 DTO 中即使还有 final_output 字段，也不会把助手回答作为抽取依据。用户文本会按既定上限截取。抽取器返回 content、kind 和用户原话 evidence；解析时要求 evidence 是实际用户输入中的非空原句。抽取器

为什么不能把助手回答也一起当长期事实？假设助手误答“这个接口始终返回 200”，再把这句内容记下来。下一次模型又看到“系统记忆：接口始终返回 200”，就可能把自己的错误当成外部事实。只从用户明确表达中抽取，有助于切断这种自我强化路径。

但原句存在还不是完整的语义保证。看这个教学例子：

用户原话：这周演示时，尽量把回答控制在三句话以内。

可能被错误提炼成：

用户永远只接受三句话以内的回答。

引文确实来自原话，条件却被扩大了。“这周”“演示时”“尽量”都消失了。现有 exact-substring 检查能证明引文不是凭空造的，不能证明总结对时间、条件和强度忠实。

这就是比“接向量库”更基础的需求：写入忠实性。你可以给 Memory 增加一组人工标注任务，明确哪些句子应记、哪些不该记、必要条件是什么、哪些只是助手推测。把“原话存在”和“记忆受原话支持”分成两个指标。

还要记住：抽取器的 JSON 合同和提示约束，是一道输入门槛，不是天然的秘密识别器或完备的个人信息政策。应按业务确定哪些信息允许长期保存，再给出可执行控制。

20.5 重复消息不能让一条记忆越来越“重要”

假设同一个 Run 的抽取任务被队列重复投递三次。如果每次看到相同内容都把 salience 加一，这条记忆就会因为基础设施重试，而被错误地当成用户强调了三次。

当前写入有两种去重：

  1. 内容规范化哈希处理相同文本；实际规范化是空白折叠与大小写折叠，不是通用同义归并。
  2. MemoryContribution 记录某个 source Run 对某段内容已经贡献过，避免同一 Run 重复强化。

写入还使用 PostgreSQL advisory transaction lock 对同一 Run 的重投递做串行化，并以数据库唯一约束处理并发竞争；单个候选冲突通过嵌套事务隔离，避免一个候选失败带走同批有效候选。Store.record Memory 数据模型 哈希合同

这里的通用工程知识是：业务上的“同一事实再次被确认”，与消息系统的“同一事件再次被送达”，必须有不同身份。

同一个用户在另一个独立 Run 再次明确这条偏好，可以是新证据；同一个 Run 因 Worker 重启被重试，不应该算新证据。内容哈希解决“说了什么”，Run 贡献身份解决“是哪一次真实表达”。这两个键缺一不可。

20.6 新旧记忆冲突，不能仅靠时间新就覆盖

假设先有：

生产服务只允许使用 Python 3.11。

两周后用户说：

新实验服务可以使用 Python 3.12。

两句话可能没有冲突，因为适用对象不同。若直接用“最新记忆替换旧记忆”，会把生产约束错误升级。反过来，如果用户明确说“生产服务也已迁移到 3.12”，就应该让旧约束不再支配新任务。

当前模型已有 ACTIVE、SUPERSEDED、INVALIDATED，以及替代关系和管理动作。但不能把这些字段存在，等同于已经实现自动理解主题、条件和时间的语义冲突解决器。状态与替代字段 Store 状态方法

可以把下一步拆成三个独立能力：

  • 判断是否谈同一对象、同一属性、同一条件。
  • 判断新话是补充、否定、临时例外，还是正式替代。
  • 写入可追溯替代关系，并让未来选择器按状态处理。

每一步都要有反例。尤其不能让“相似度高”直接触发删除；相似度高有时恰好意味着两条互相矛盾、必须一起呈现的事实。

20.7 为什么失效的记忆还能出现在历史 Run 回放里

新任务选择记忆时应排除 INVALIDATED 或 SUPERSEDED 的条目；但回放旧 Run 时，如果它当时确实看到了那条记忆，审计记录就应反映这一点。否则今天把记忆失效，昨天那条错误回答的上下文也被偷偷改掉了，事故分析会失去事实基础。

当前 load 按已冻结 ID 和顺序重读，并支持内容哈希检查；它有意允许读取后来失效或被替代的条目，以重建当时输入。带哈希的新快照会拒绝缺失、重复、哈希集合不匹配，或冻结哈希与记录中保存的 content_hash 不一致；兼容旧 ID-only 快照的分支则具有不同严格程度。冻结加载

这个完整性保证有一个实现边界：当前 load 比较的是已保存哈希，不是每次对正文现场重新计算；哈希算法本身还会规范化空白与大小写。因此不能声称它能发现任意字节变化，更不能把它说成能抵抗“直接改正文却故意保留旧 content_hash”的数据库篡改。正常写入路径维护哈希一致性；若要增加更强的存储完整性审计，需要另行重算和验证。

这不意味着“审计需要历史”可以覆盖任何撤销或删除承诺。如果产品承诺用户彻底删除某些数据，那么需要另行定义：历史快照保留什么、哪些正文必须删除、哪些引用只能显示已撤销、谁能进行审计。当前回放语义与未来隐私撤销策略之间，需要明确设计，不能靠一个 invalidate 布尔动作同时满足所有目标。

20.8 TTL：字段已经存在，完整产品能力还要看什么

expires_at 已经存在，普通选择器也会过滤已到期记录。所以“Memory 完全没有过期机制”不准确。模型与选择 Store.select

但一个完整的 TTL 产品能力至少还需要回答：

问题 为什么不能只靠一个时间字段
谁决定到期时间 用户设定、业务策略与模型猜测的风险不同
什么操作会延长寿命 一次误召回不应自动证明事实仍有效
到期是停止注入还是删除内容 它们对历史回放和隐私承诺不同
历史 Run 怎么处理 新查询过滤与历史审计是两条路径
用户能否查看或撤销 后台字段不等于用户可理解的控制
到期策略怎样评测 临时约束永久化与稳定偏好过早失效都需要样本

因此，需求应写成“补齐过期策略、管理入口和历史语义”，而不是从零再造一个现有字段。这种准确描述也能避免后续开发把已有逻辑重复实现一遍。

20.9 Memory 的评测集应该长什么样

普通知识问答题经常只标“答案正确是什么”。Memory 至少需要多一层时间与用户范围。

样本类型 示例 需要检查的结果
应写入 “以后给我代码时先给完整文件，再解释。” 稳定偏好被忠实提炼
不应写入 “这一次先别解释，赶时间。” 不被扩展成长期偏好
同义召回 记忆写“类型标注”，查询说“type hints” 有用信息能否被找到
无关查询 用户只问当前天气 不注入无关代码偏好
条件变化 实验可用 3.12，生产仍用 3.11 条件不被合并掉
用户隔离 两名用户有相反输出偏好 不跨 owner 注入
重复投递 同一 Run 的抽取任务执行两次 不重复建立或强化贡献
历史重放 记忆失效后查看旧 Run 旧依据能解释，未来不再选入

先给这些样本冻结输入、初始记忆状态和预期，再比较词项、语义或混合选择，才能判断改动是否值得。只报“召回更多条”没有意义；多注入一条无关长期约束，也可能让回答变差。

本讲练习

给“生产使用 Python 3.11；实验可用 3.12；以后先给 SQL；这次临时用英文”这四句话分别标注对象、时间、条件与是否应长期保存。然后设计两轮更新：一次补充，一次正式替代。不要先写向量代码，先说明每轮结束后应有哪些 ACTIVE 记忆、每条原话证据是什么、哪个用户能选到、旧 Run 应如何回放。你能够写出这份合同，后面的表结构和选择器才有明确目标。

20.10 为什么评测 Memory 时，要固定“初始记忆状态”

假设你用同一批问题依次测旧策略和新策略。旧策略跑题时，抽取器把新偏好写回数据库；轮到新策略时，它面对的是更丰富、甚至已看过试题答案的记忆集合。新策略成绩更好，可能不是选择器改进，而是测试顺序给了它额外资料。即使没有新增记录，salience 被重复强化，也会改变后续排序。贡献与排序

因此，一个可解释的记忆实验要同时固定问题与初始状态。可以在隔离测试工作区中，为每个案例准备独立的记忆 fixture，记录内容、状态、owner、哈希和必要时间；在测读取策略时关闭或替换写入队列，避免结果回流。在专门测写入策略时，则先固定一组用户表达，再比较结束后的记忆集合和贡献记录，而不是把读取与写入变化混在一起。这里是建议的实验方法，不是声称项目当前评测系统已自动替你冻结所有业务状态。选择与写队列合同

还需要分清三种时间：原话表达时间、记忆创建时间和模拟查询时间。带 expires_at 的例子如果依赖机器当前时间，今天通过、下周失败，不能立即说明算法退化；可能只是测试数据过期了。把时钟或固定样本的时间关系显式化，才能让到期策略的验证可重复。历史回放测试则应使用旧快照身份，不能重新调用当前选择器后声称重现了当时输入。

对于“新的策略是否真的让回答遵守长期偏好”，还应保留无 Memory 对照。否则一次回答碰巧符合偏好，你无法判断是记忆起作用，还是系统提示本来就要求这样答。可以构造三组：无记忆、现有词项选择、候选新策略，使用同一任务和有限预算比较。若新策略多召回了一条，但在真正回答里被预算剔除了，它的候选指标提升并没有转化成用户收益。

这也解释了为何评测不能只报“写入三条、召回八条”。应该交付一条完整证据链：用户明确表达了什么，系统保存了什么，本次允许读取什么，选择了什么，实际交付了什么，以及回答是否在适用条件内使用它。你能给出这条链，面试官才能分辨你实现的是可解释的长期记忆，还是把聊天内容再次拼进 prompt。
