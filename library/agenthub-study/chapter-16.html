第 12 讲：工程地图、依赖方向与发布版本

本讲对应原主线第 1、2、3 阶段的深化。源码口径统一为 cdc9d084d3a20e71355401952ee394da4e56273b；示意代码只帮助理解，不表示本次已经修改项目。

一、先问一个问题：改了一个 Prompt，为什么旧 Run 还能解释？

假设你昨天发布了客服助手 v3，它使用旧退货政策、工具修订 2 和模型档案 A。今天你把 Prompt 改了，把工具升级到修订 3，又调整了模型的输出额度。客户拿着昨天的回答问：“为什么你们昨天这样说？”

如果数据库里只剩一张 Agent 表，而且每次运行都动态读取这张表的当前内容，你只能看到今天的配置。即使保留了昨天的答案，也很难证明昨天到底发了什么请求、允许了什么工具、用了哪个知识版本。

所以，AgentHub 不只是“页面上的一个 Agent 加一个循环”。它同时管理三种不同时间尺度的事实：可以持续编辑的配置、某次发布冻结下来的规格，以及某一次执行产生的结果。对应的核心对象是 Agent、AgentVersion、AgentRun。发布服务

学习大项目时，先找到这些“事实由谁拥有”，会比从头通读所有文件有效得多。

二、模块多，不等于微服务多

项目使用模块化单体加异步 Worker。packages/knowledge、packages/approvals、packages/evaluation 是业务模块，不意味着你需要分别部署一个 Knowledge 微服务、一个 Approval 微服务。HTTP 接口主要由 FastAPI 进程提供；后台任务由 Celery Worker 执行，Beat 定期发出巡检任务；Web 是 Next.js 应用。数据库、队列和索引是另外的基础设施。仓库入口 部署装配

为什么先这样组织？因为“代码边界”和“进程边界”解决的问题不同。模块边界帮助你管理依赖、测试和业务规则；进程边界帮助你独立扩容、隔离资源和部署故障。刚开始就把每个模块拆成服务，会额外引入跨服务认证、协议兼容、网络超时和分布式事务，而业务本身可能还没有稳定。

这个图表达的是职责关系。不能从一条箭头推断“存在一次远程 RPC”，也不能从某个模块叫 Runtime 就推断它只能运行在 Worker。

三、真正值得你记住的是这张源码阅读地图

你要弄清的问题 优先入口 往下追什么
请求从哪里进入 apps/api/app.py、apps/api/routes/ 注册了什么路由、依赖是什么
谁决定一次业务操作合法 对应 packages/*/service.py 或 services.py 权限、状态、事务与错误
一行数据代表什么 对应 models.py 外键、唯一键、状态与索引
外部系统怎么接 adapters/、网关或 MCP client 超时、失败、输入输出转换
怎样在另一个进程执行 apps/worker/tasks/ 参数身份、领取、租约、完成与恢复
页面为什么没更新 apps/web/lib/api/ 与页面组件 HTTP 响应、缓存身份、事件或轮询
历史结果如何复核 Run、快照与 Evaluation 服务 冻结的输入身份、证据、指标定义

apps/api/app.py:create_app() 负责注册路由、中间件、错误处理器；lifespan() 负责连接池、Redis 客户端和可选检索模型预热等进程生命周期。它没有在每次业务请求里自动跑迁移。API 装配

你以后看到一个数千行的大服务文件，也不必立刻全部读懂。先跟踪一次具体操作，比如“发布 Agent”：路由收到请求，调用发布服务，发布服务锁定草稿、解析依赖、创建版本，提交数据库，再返回版本身份。然后才看其中某一步的实现。

四、发布并不是把草稿复制一份那么简单

AgentPublishService.publish() 先按工作区加载并锁定 Agent，再解析草稿规格，计算版本号，写入 AgentVersion。解析要回答一系列问题：模型档案是否有效、能力是否足够，工具修订是否属于本工作区、规格是否完整，知识和 Wiki 绑定能否解析，运行预算和上下文策略是否合法。发布服务

你可以把它理解为“把一组可变引用变成一份可执行合同”。例如，草稿里选择了一个模型档案；发布版本保存它当时解析出的行为参数与凭据引用，而不是把 API Key 原文放进 Prompt 或版本 JSON。

需要特别区分知识的 PINNED 和 LATEST：前者明确绑定某个快照；后者在发布规格里保留选择策略，随后在 Run 或正式实验的有效输入解析阶段固定实际使用的快照。不能说“AgentVersion 一发布，所有未来 Run 就永远使用同一个最新知识快照”。正式实验又有自己的冻结时点，不能把这几个时点合并。发布时知识解析 正式实验冻结

一个具体例子：同一个已发布版本 v3 使用 LATEST 知识策略。周一 Run A 解析到快照 S10，周二新知识发布后 Run B 解析到 S11。这并不说明版本不可变失效；不变的是版本规定的策略，A、B 各自固定的是这次运行实际采用的知识输入。复核 A 时必须读 A 的有效绑定，不能重新拿今天的 LATEST。

五、为什么需要 resolved_spec_hash？

它是配置内容的指纹，不是“质量分”，也不是运行结果的签名。项目的 canonical_json() 使用排序键、紧凑分隔符、UTF-8 内容和禁止 NaN 的序列化方式，再计算 SHA-256。因此，普通字典的键插入顺序不同，不应制造无意义的版本差异。规范化 JSON

# 教学示例：解释键顺序规范化，不是项目的新补丁。
left = {"model": "example-model", "temperature": 0}
right = {"temperature": 0, "model": "example-model"}

# 使用同一份规范化合同后，left 与 right 应得到相同内容指纹。

但别过度理解这个能力。这个函数并不自动把所有“业务上等价”的对象变成同一个值。例如，数组顺序通常仍然重要，缺省字段与显式字段是否等价，需要发布层定义；字符串的语义等价也不是 JSON 排序能解决的。规范化规则需要版本管理，不能今天换一种编码方式，就声称历史哈希“坏了”。

Hash 也不是权限。攻击者如果能同时改数据库里的规格和它的哈希，单纯重算哈希并不能提供独立防篡改证明。它主要支持内容身份校验、缓存、回放和一致性比较；更强的审计防篡改是另一个工程需求。

六、默认值为什么也需要来源？

“用户没有设置输出预算”和“用户明确设置成当前默认数值”，数值可能相同，含义却不同。以后模型窗口变化时，前者可以按新能力重新推导，后者应尊重用户的明确选择。

发布服务因此区分配置的 UNSET、DEFAULT、CUSTOM 来源；自适应上下文策略、历史策略、摘要策略也有各自的 schema 或 policy version。它们帮助新发布采用新的解析规则，同时避免把旧版本在读取时重新解释一遍。运行配置解析

这也解释了一个最新状态问题：底层历史 Memory 配置可以是关闭的，但 create_draft() 在用户未显式提供时，会为新 Agent 草稿设置启用的长期 Memory，并使用 USER 作用域。两句话描述的是不同创建路径和历史对象，不能只看一个默认常量就概括所有 Agent。新草稿创建

七、框架应该帮你做什么？

LangGraph 可以帮助执行图、暂停和保存 checkpoint；模型 SDK 可以帮你完成协议请求；SQLAlchemy 可以帮你映射数据。但是“谁能批准”“写入结果未知时怎么办”“一次运行用了什么版本”都是产品规则，不能交给框架的默认行为决定。

当框架变化时，理想情况下你修改的是适配器和装配层，业务合同仍然稳定。实际代码不可能完全没有工程耦合，但评价边界设计的标准很清楚：替换一个模型供应商，是否还得修改租户权限？更换图执行实现，是否会偷偷改变审批状态含义？如果会，就需要重新检查依赖方向。工程规则

八、本讲练习：读懂一次发布，而不是背文件树

选一个已经存在的 Agent，画出“草稿字段—解析规则—发布版本—Run 有效快照”的四列对照。回答五个问题：改草稿是否影响旧 Run；工具换修订后旧版本是否跟随；LATEST 在哪里固定；凭据秘密是否进入规格；哪一类差异会改变哈希。

完成标准不是画图漂亮，而是你能针对每个结论指出一个服务方法、一个持久字段和一条反例。后面的面试区会沿着这条线继续追问。
