第 17 讲：评测系统自身怎样可靠运行——Runner、失败分类、指标快照与上线门禁

第 11 讲已经讲了 DEV/HOLDOUT、Recall、对照实验和独立修改。本讲只追评测基础设施的生产实现：怎么安排一次批量实验、Worker 如何恢复单题、观测怎样转化为判分、历史分数如何固定。源码从 packages/evaluation/experiments.py、runner.py、taxonomy.py、metrics_service.py、release_gate.py 顺序阅读。

17.1 为什么需要一套专门的 Evaluation Runner？

如果只是循环调用大模型，似乎可以写：

for question in questions:
    answer = await agent(question)
    score = judge(answer)

这段适合原型，但当任务有工具、审批、Run 断线、不同方案、多次重复和失败恢复时，它没有回答：

  • 某题已经执行到一半，Worker 崩溃，下一次是否重新建 Run？
  • 同一题不同 Variant 使用哪份知识与 AgentVersion？
  • 一个输出为空，是模型错答还是评测执行没拿到结果？
  • 今天评分程序升级后，历史报告的分数要不要跟着变？

因此评测不是模型 API 的简单批量包装，而是一个有状态的工作流：

四种身份不可混淆

身份 作用
DatasetVersion 固定题目、参考值和分组
Variant 固定该被测方案的配置与知识绑定
ExperimentRun 执行这份计划的一次批次
CaseResult 某 Variant × 某题 × 某次重复的具体观察

例如：20 道题、两个 Variant、每题每方案两次，共 80 条 case execution，并不是 80 道独立题目。这个区别应该记录在报表里，而不是在 dashboard 上都显示成“完成 80 题”。

17.2 两种 Driver：为什么测试框架能跑通，并不代表真实模型被测过？

源码里 ExperimentRunner 可以使用 DeterministicEvaluationDriver，它根据预设数据产生受控观察，主要用于验证任务计划、领取、保存和评分的程序合同。生产 Worker 会装配适合真实 Runtime 的 Driver，构造真正的 AgentRun 或纯检索执行路径。

理解下面的接口边界就够了：

# 以接口角色为中心的教学摘示
class CaseExecutionDriver(Protocol):
    async def execute(self, ...): ...

class DeterministicEvaluationDriver:
    async def execute(self, ...): ...  # 用夹具生成观察

class AgentRuntimeEvaluationDriver:
    async def execute(self, ...): ...  # 实际 Agent/工具执行

需要看 CaseResult 与实际 Run ID 的绑定、Provider Attempt 记录、用量凭据和执行器的类型。这样复盘 benchmark 时，就能快速分辨“框架合约通过”和“模型回答达到判据”。源码：8。

17.3 批量执行怎样防止重复领取和失序完成？

一个 ExperimentRun 最终会拆成很多 CaseResult。Runner 需要在数据库里落实“某题某方案某重复”的唯一执行身份，并维护 PENDING → CLAIMED/RUNNING → 终态 之间的原子转换。

假设 Worker A 执行 Case C17，已经创建 AgentRun R17，但突然超时。Worker B 重新接到同一批任务：

Worker B 收到批次消息
    -> 查询 ExperimentRun 所有权与租约
    -> 检查 C17 已经绑定哪个 AgentRun
    -> 读取 R17 持久状态与外部动作结果
    -> 依据恢复规则继续或记录需要处理

这里评测 Runner 的重要职责是保存 Run 绑定并复用已有观察。一条队列消息被再次消费，不应该默认在业务数据库创建第二个带写操作的 AgentRun。类似地，SKIP LOCKED 能帮助领取可用行，但被其他 Worker 锁住的行暂时不可见，不能简单据此判断“所有任务都做完了”。Runner 的 prepare_run、claim_run、claim_case、recover_inflight_cases 是关键阅读顺序。源码：领取与恢复。

17.4 “空答案”和“错答案”在数据库里是两种事实

考虑三条记录：

A：Agent 正常结束，输出“错误规则”，判分 FAIL
B：Agent 执行出错，没有 final_output
C：Agent 正常拒答，因为资料不足，而且题目也不可答

如果把三者都写 score=0，就失去了故障定位信息。

当前评测分类模块以原始观察和执行事实为输入，区分输出缺失、模型错误、工具路径、业务失败等类别。错误位于第 0 步也是真实位置，Python 里判断应写 if step_index is not None，而不是 if step_index。这种看似简单的条件错误，会让所有发生在初始阶段的故障被错误归类。

# 教学反例与正确写法
first_failed_step = 0
if first_failed_step:  # 错误：0 被当作 False
    label = "failed_at_step"

if first_failed_step is not None:
    label = "failed_at_step_0"

一次故障分类建议保留以下字段：

字段 用途
execution_status 执行是否拿到可评价的观察
agent_status 被测 Agent 的真实终态
final_output_presence 输出是否存在，是否只是空文本
tool_trajectory 提议、授权、执行是否符合预期
first_failure_step 第一次定位到的错误位置
failure_labels 便于跨题聚合的原因类别

相关源码 24。

17.5 评分版本为什么要锁定？

假设 10 月某任务按词面 F1 得 0.74，11 月团队修复了中文分词和引用检查逻辑。新的评分器可能得到 0.61。这里不应该让用户每次打开历史报告，自动看到被今日算法重新计算的分数。

AgentHub 的指标服务使用显式物化的 MetricSnapshot：等批次终态、完整 case 集合与计划核对完毕后，按固定评测器版本生成指标结果，并保存与观测数据的绑定身份。读取历史快照优先读被固定的结果；想用新算法评价同一份结果，应作为新的、可识别的评分版本/比较任务。

数据库可以记录结果集 hash、评分定义版本与指标快照 hash，用于发现“评分时所用的输入与现在读取的输入不一致”。这一做法与 AgentVersion 和 KnowledgeSnapshot 的版本思维一致，只是被固定的是评价规则及其输出。参见 25。

17.6 Release Gate：不只是 score >= 0.8

实际发布可能要同时约束：成功率、关键任务是否退步、费用、延迟和引用可信度；部分指标可能因没有用量回执而缺失。

因此门禁需要区分：

结果 含义
PASS 固定规则所要求的证据满足准入条件
FAIL 一个或多个必需条件明确违反
INCONCLUSIVE 必需证据缺失或目前无法作出判定

例如：业务成功率上涨，但成本未知的任务占比过高。一个要求成本完整的 Gate 应回到证据状态，而不是悄悄把缺失计为零成本。另一方面，业务明确允许缺失的可选指标，也不必自动让全部比较失败；规则应写明可选或必需。

同一份计划下，A/B 的逐题配对比单看平均值更重要。下面是教学数据：

A、B 都通过：5 题
A 失败、B 通过：2 题
A 通过、B 失败：1 题
A、B 都失败：2 题

B 仅净提升 1 题，却带来 1 题回归。若回归题涉及外部写入安全，应单独设置硬门槛。项目的 release_gate.py 已有规则校验、比较绑定与发布决策机制；实际门槛由业务实验计划制定。源码：28。

17.7 评测基础设施本身应该怎样测试？

推荐优先测试下列路径，而不是反复把同十道题跑到满意：

用例 输入 检查
并发领取 两个 Worker 领取同一 Case 只有合法 owner 能推进
提交成功但回复丢失 相同 Case 再执行 绑定旧 Run / 结果
执行中断 旧 Run 已有关联工具动作 先恢复事实，不产生重复业务写入
空输出 模型输出不存在 缺失和错答各自分类
无账单 Token 或价格凭据缺失 费用指标可见地标为缺失
评分器升级 v1/v2 对同一份观察评分 历史快照保持 v1 身份
数据集修改 已发布版本被非法改动 完整性校验触发
门禁证据缺失 必需指标无值 INCONCLUSIVE 或预定规则结果

本讲源码跟读

沿 UI 的一次“开始评测”逐步追：apps/api/routes/evaluation.py → ExperimentService.create_run() → Celery Worker → ExperimentRunner.prepare_run()/claim_case() → AgentRuntimeEvaluationDriver → EvaluationMetricsService.materialize_metrics() → EvaluationReleaseGateService。

本讲掌握标准：能解释谁负责生成观察、谁负责评价观察、谁负责决定发布；能拿出一条 CaseResult，定位它使用哪份数据、哪个版本和哪个评测器。

17.8 从一个 CaseResult 逆向追“为什么失败”

假设仪表板显示 Variant B 在“退款政策例外”题上失败，先不要改 Prompt。按以下顺序反向追踪：

MetricSnapshot 中的 task_success = false
  -> 对应 MetricResult 的评分规则版本
     -> 对应 CaseResult 的 observation/failure_labels
        -> 绑定的 AgentRun 和 RunStep
           -> 模型最终请求包含了哪些证据？
              -> 是否发生 ToolCall/Approval？
                 -> Run 的能力与权限配置

要把以下几种原因明确分开：

报告现象 真实问题层 下一步
未返回任何模型输出 供应商/Runtime 运行错误 查模型 attempts、超时与空响应分类
返回答案但漏例外 检索/上下文交付/生成 查候选→交付的逐项来源
正确解释政策，却未经批准尝试退款 工具治理错误 查 ToolRevision/审批轨迹
工具已完成，评测仍失败 业务金标或后置条件 查业务数据库的真实结果及判据
评分器换版本后分数变动 评价定义变化 比较 v1/v2 的指标快照与逐题差异

这个排查方法的重要性在于模型质量问题与评测系统故障有不同的修复入口。如果 CaseResult 根本没运行成功，改模型 Prompt 不会修复 Worker 领取的程序缺陷。

17.9 一个带实际数值的评分口径练习

假设 20 次真实任务执行：

14 次返回可评价答案，其中 11 次正确，3 次错误
4 次供应商失败，没有完整答案
2 次工具执行结果未知，需要后续核对

报告可以同时展示：

  • 全部发起任务的确认成功率：11/20 = 55%。
  • 已返回可评价答案的条件正确率：11/14 ≈ 78.6%。
  • 供应商错误率：4/20 = 20%。
  • 业务状态待核对率：2/20 = 10%。

这样一眼能看出问题：生成质量不差，但端到端可靠性与外部工具结果核对还存在较大缺口。

再假设 A 与 B 都按同一任务、同一环境重复两次，配对比较应该以“同一题组”的结果对照为主，而不是把每一次随机运行当成完全独立的样本。多次重复反映稳定性，新增独立题目才反映问题覆盖。评分的分母定义必须提前冻结。

17.10 三个值得加到工程测试中的故障注入点

领取后失去 Worker：Case 已绑定一个 AgentRun，但 Worker 心跳中断。恢复器应先检查 Run 持久事实、动作状态，再判断是否允许执行。不能创建第二个具有相同写副作用的 Run 作为“重试”。

已终态但指标未物化：ExperimentRun 与所有 Case 都完成，MetricSnapshot 还不存在。对 GET metrics 的行为应该是读取已保存指标或返回明确状态，而不是使用当前最新评测器偷偷计算一个新成绩；物化操作本身需要幂等身份。

评测金标与模型输入串线：被测模型看到 item.expected，会使分数虚高。生成执行器只能传入被测任务和允许的环境事实；expected 留在评价端。与模拟 Driver 的受控测试分开，并记录真实执行器身份。

本讲的最小验收记录

一页完整评测复盘至少应附：DatasetVersion hash、Experiment spec hash、Variant identity、被测 Run ID、CaseResults 清单、评测器版本、指标快照、明确失败原因、价格/用量范围、回归题号、门禁决定和代码 SHA。

这样在三个月后重新打开同一份报告，你仍然能解释当时的数字从哪里来。
