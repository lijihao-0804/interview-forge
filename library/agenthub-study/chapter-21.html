第 17 讲：工具审批的进阶与外部副作用

17.1 审批保护的对象是一项确定动作

“这个用户同意了”听起来足够，实际开发远远不够。

你需要知道他同意的到底是：

  • 哪一个工作区里的运行。
  • 哪一个已发布 AgentVersion。
  • 哪一个 ToolRevision。
  • 哪一组通过 schema 校验并规范化的参数。
  • 同一轮推理中第几项逻辑提议。
  • 在什么时间、由谁、以何种授权来源同意。

AgentHub 的 create_or_get 会规范化 arguments 并生成参数哈希，再把 workspace、run、tool revision、参数哈希与 proposal ordinal 纳入 logical_action_id；审批表保存 canonical_arguments、canonical_args_hash、版本身份、requested_by、decision/execution 状态，并以工作区内 logical_action_id/idempotency_key 唯一约束防重。源码：审批创建、审批模型

为什么不能只用参数哈希？因为用户可能明确要求在两个独立运行里创建两张内容相同的工单。相同参数不必然意味着同一个业务动作。反过来，同一运行从 checkpoint 恢复时重复生成同一个提议，也不应该再产生一张新审批单。

幂等身份必须表达你希望合并哪一种重复，而不能只因为两份 JSON 长得一样就合并。

17.2 为什么审批要拆成“决定状态”和“执行状态”？

当前 Approval 至少有两条独立状态轴：

决定状态 decision_status 意义
PENDING 还没有有效决定
APPROVED 已批准这项确定动作
DENIED 已拒绝
EXPIRED 等待期限已经过期
CANCELLED 待审提议随运行取消而撤销
执行状态 execution_status 意义
NOT_STARTED 尚未取得执行资格
CLAIMED 一个执行者已经原子领取
SUCCEEDED 已获得明确成功证据
FAILED 已获得明确失败结果
UNKNOWN_OUTCOME 不能安全断言动作做成或没做成

这些状态的存在直接反映了业务事实：批准之后可能还没执行；执行之后可能成功，也可能失败；网络中断后甚至不知道是哪一种。源码：状态约束

如果只用一个 approved=true 字段，你无法回答“这个批准有没有被使用”“谁正在执行”“这个动作是否可以重试”。如果批准后立即把它改成 done，又会掩盖“外部调用已经发出但回执丢了”的窗口。

下面这个图只表示批准动作的执行轴，决定轴仍然保留在审批表中：

这里最后一个箭头不是说未知结果已经被解决，而是强调自动执行路径到此停止；不要把 UNKNOWN_OUTCOME 连回 NOT_STARTED，假装可以无条件再试。

17.3 “需要审批”与“必须人工审批”是两个层次

当前代码中，ToolPolicy.decide 允许自动直接执行的条件是：

  • effect 为 READ；
  • approval_policy 为 NEVER；
  • 不满足 requires_human。

而 requires_human 的条件是：HIGH 风险，或者 MCP 来源的 WRITE。其余不满足直接执行条件的工具会进入审批体系。源码：ToolPolicy

这比一句“读工具不用审批，写工具要审批”准确得多。高风险读取也可能需要人工。一个声明需要审批的读取工具，也不能因为是 READ 就跳过流程。

然后才进入“谁作出决定”这一层。项目支持个人委托级别 MANUAL、LOW、MEDIUM，但这受适用运行标记、用户当前权限和工具风险上限共同约束：

  • 没有偏好或 MANUAL，进入人工路径。
  • LOW 级委托可处理允许范围的 LOW 风险提议。
  • MEDIUM 级委托可覆盖对应允许范围。
  • HIGH 风险、MCP WRITE 仍然人工。
  • 没有 approve_action 权限，个人偏好不能把自己升级成可审批者。
  • 当前实际权限与受限 execution context 取交集，不能被传入 context 扩大。
  • 超出授权范围的连续自动拒绝达到上限时，转交人工，避免持续自动拒绝循环。

这些由 delegation.py 实现。它只对有 PersonalApprovalRun 标记的适用运行路由，不能据此把所有历史、评测或其他入口都写成“已经默认自动审批”。源码：个人委托、适用运行标记

17.4 人工审批时如何防并发覆盖？

设审批员 A 点批准，审批员 B 同时点拒绝。你不能让两个请求各自读到 PENDING，然后都提交一份“我成功决定了”。

ApprovalService.decide 会按照 Run→Approval 的顺序加锁，检查当前决定状态。若已经不再是 PENDING，就返回当前记录。过期与正常决定使用数据库时钟判断；有效决定会记录 decided_by/decided_at/decision_source，并写审计记录。源码：7

锁顺序也值得学。取消、协调和决定都可能同时触碰 Run 和 Approval；若一个事务先锁 Run 再锁 Approval，另一个反过来，就更容易形成互相等待。规定一致的锁顺序是减少死锁风险的常用工程手段。

这里有个权限细节也不要讲错：当前人工路径对自己批准自己的动作有约束，组织 OWNER/ADMIN 例外；个人委托是另一套明确标注的授权来源，不是伪装成一个普通人工点击。源码：自审批规则与 decision_source

因此审计时不能只显示“已批准”。最好能解释是谁、何时、通过 HUMAN 还是 DELEGATED、依据哪个路由原因完成了决定。

17.5 点了批准，为什么还要检查原运行人的权限？

因为审批者与实际运行人可能不是同一个人。

例如员工甲发起了一个需要创建工单的 Run，管理员乙批准。随后甲被移出工作区。恢复时如果直接把乙的管理员 context 传给动作执行，就把“乙允许甲做这一项动作”变成“整个后续 Agent 都获得乙的管理员能力”。

当前恢复路径会从原 Run 读取 created_by，取得原运行人当前权威 context；检查当前审批与运行绑定、活跃 waiting_approval_id、checkpoint 中断身份、冻结历史/版本绑定等，再决定是否继续。审批员的授权不被当成原运行人的权限升级。源码：8 与权威 context

另一个时间窗口是 checkpoint 变了。代码不仅第一次验证审批对应的 checkpoint，还在真正恢复前再次核对 thread_id、checkpoint_ns、checkpoint_id 与已验证配置一致。它恢复的是确定的那一个中断，不是“此时碰巧最新的某个状态”。

你可以把恢复前置条件理解为一组证据必须彼此相符：

  • Run 说自己正在等待这项 approval。
  • Approval 说自己属于这个 Run、版本和提议。
  • Checkpoint 说当前停在同一 approval_id。
  • 冻结的历史和知识绑定仍能解释这个执行上下文。
  • 原运行人现在仍有继续这一步所需的权限。

缺少任何一个，不应通过重新拼接一个近似上下文来“尽量跑起来”。

17.6 领取动作与真正执行为什么要分开？

claim_execution 使用条件 UPDATE，只允许 APPROVED 且 NOT_STARTED 的记录进入 CLAIMED，并增加 execution_attempt_count。竞争者中只有拿到返回记录的一个可以继续执行。源码：动作领取

这解决的是一个很窄但很重要的问题：并发恢复时，不让两个当前执行者都认为自己第一次使用了同一份批准。

它还没有解决下列问题：

  1. Worker 在领取成功后、调用外部服务前崩溃了。
  2. Worker 已调用外部服务，对方成功了，本地没收到响应。
  3. Worker 收到成功后，在写回 SUCCEEDED 之前崩溃了。

这三种场景本地都可能只留下 CLAIMED。你不能仅凭这一个状态识别外部到底有没有发生。

当前协调器遇到陈旧领取且没有活跃 owner 时，会进入 UNKNOWN_OUTCOME/NEEDS_ATTENTION。这个保守动作是有原因的：宁可保留“需要核对”，也不凭猜测生成第二张订单、第二封邮件或第二次外部写入。源码：未知结果收敛

17.7 本地事务工具与远端 MCP 工具为何采用不同恢复方式？

项目中的 CreateTicketActionExecutor 可以在同一个本地数据库里按 workspace + idempotency_key 查找工单。创建时先查重；唯一冲突后回滚并查找已有结果；发生异常时还有本地 reconcile 能检查是否已经出现对应工单。源码：工单 Action

这使它具备业务层的有效一次语义：相同逻辑 key 应解释为同一项工单创建。

但注意一个细节：即使回查暂时没有找到，也不一定能证明某个失联的 COMMIT 永远没有抵达服务器。当前 reconcile 在不能证明成功时仍保留未知，而不是把“查无结果”自动变成“可以再次创建”。这体现的是对时间窗口的谨慎处理，不是 SQL 查询不会用。

远端 MCP 的情况更复杂。ActionRuntime._execute_remote 将网络超时和“请求是否已交付对方”的判断留给真正发出请求的 MCP 客户端，而不是在外层再套一个粗暴超时并宣称失败。若仍有异常逃逸，它把结果视为 UNKNOWN_OUTCOME。源码：远端 Action 执行

为什么外层不能说“超时了，所以失败了”？因为 timeout 只说明本地在等待期限内没有拿到所需结果。它不等于对方没有开始，更不等于对方已经撤销。

未来若要自动核对某个远端工具，需要明确对方支持什么：

  • 接受并保证幂等键吗？
  • 能按业务键查询已创建对象吗？
  • 查询存在延迟吗？
  • 能得到稳定 operation_id 吗？
  • 取消 API 是否真的取消业务操作？
  • 哪些结果可以证明“未执行”，哪些只说明“暂时查不到”？

这些都是每个工具的业务合同，不能用“我们用了 MCP 协议”一句话替代。

17.8 最新修复：取消 Run 与撤销待审动作必须同事务

这个改动很适合你在面试里讲，因为它能把事务、状态机、故障注入和产品表现串起来。

旧窗口是：先把 Run 设为 CANCELLED 并提交，再用另一个调用撤销待审 Approval。如果第二步前进程中断，用户看到运行已取消，但审批列表还残留一个可操作的待审项。

新版 AgentRunService.cancel 在同一个 session 里调用 cancel_pending_in_session。Run 状态变更与待审撤销一同提交；若提交前发生异常，两者一起回滚。create_or_get 也会拒绝在取消中的运行上继续创建新提议。源码：取消路径、同事务审批撤销

这个图刻意没有画成“所有取消都强行 CANCELLED”。如果动作已 CLAIMED 或 UNKNOWN_OUTCOME，取消不能擦掉已经产生的不确定性。准确的用户反馈应保留“停止继续执行，但已有动作还需核对”的事实。

仓库的 2026-11-19 复验记录写明：向取消提交前注入异常，Run 和 Approval 都回滚；重试后一起取消。这是仓库已有测试与复验记录，本次整理没有重新执行该集成实验。源码：取消集成测试、历史复验报告

17.9 防新错还不够，为什么还要修旧数据？

即使你把今后的取消改成同事务，历史数据库里已经存在的 CANCELLED+PENDING 组合不会自动消失。

新版协调器把“Run 已 CANCELLED，但仍有关联 PENDING 审批”纳入候选，清理这些遗留；对已取消的记录再次协调，不会反复改写第一次决定时间。源码：候选与取消收敛、历史遗留回归测试

这给你一个非常实用的修复模板：

  1. 预防：修改业务事务，关闭产生新坏数据的窗口。
  2. 修复：用明确 predicate 找出旧坏状态并安全收敛。
  3. 幂等：同一修复跑第二次不会制造新的历史或覆盖重要时间。
  4. 验证：既验证正常路径，也注入旧窗口的中断条件。
  5. 解释：区分“取消请求成功”“审批已撤销”“外部结果已核对”。

很多初级修复只完成第一步；成熟修复会顺带回答历史数据如何处理，但不会无授权地把所有异常记录强行改成成功。

17.10 当前已有后台恢复，但仍要理解两条交付路径

人工 approve/deny 会同事务写入 resume_pending=True。当前 API 路由在 decide 之后直接 await run service 的 resume；周期审批任务也会扫描标记，派发 resume_agent_run，并由 Run 租约与动作领取约束重复交付。源码：决定接口、后台审批任务、协调派发

因此最新状态应这样描述：

项目已经有持久恢复意图和后台补偿，人工 API 还保留即时恢复路径。继续演进的重点是统一入口的可靠交付与可观测性，而不是从零添加一个后台恢复函数。

这也是你看项目时很重要的一种能力：注释或历史文档说“下一步做 X”，你需要继续查现在是否已经有其中一部分。工程需求往往经历“原语已实现→某条入口接入→全链路覆盖→故障窗口验证”几个阶段，不能只按文件存在与否打勾。

17.11 本讲练习：把“允许”和“做成”分开汇报

下面是一个教学场景：

用户发起创建工单；管理员批准；Worker 取得 CLAIMED；MCP 服务返回前连接断开；用户点击取消。

请写一段你会展示给用户的结果说明，要求：

  • 不说“工单肯定没创建”。
  • 不说“已取消，所以对方会自动撤销”。
  • 不让系统未经核对再次执行。
  • 说清已知事实、未知事实、下一步需要哪项证据。

参考思路：

这项动作已获得批准并开始交付。当前没有收到能够确认结果的回执，运行已停止继续推进；外部工单是否已创建仍需按业务身份核对。核对完成前不会再次提交同一动作。

然后到源码中分别找出这段话依赖的状态、failure_code、idempotency_key 与协调分支。你会发现，好的产品文案不是在代码写完后“润色一下”，而是准确表达系统证据合同的一部分。
