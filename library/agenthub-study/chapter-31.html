第 27 讲：把全部模块连成一次独立开发

一、先更新上一讲的练习：RT10 已经不是原来的待实现问题

第 11 讲以“文档列表已经结束，但展开修订详情不更新”为例，带你做需求定位。新主分支已经让展开详情参与持续观察，并处理页面可见性、请求进行中等条件。所以今天继续学习时，不能再把旧问题原封不动作为尚未完成的开发需求。最新知识页面

但旧课没有失去价值。你现在可以做更好的学习：比较当时提出的验收条件和当前实际实现，确认哪些被覆盖、哪些仍然有不同取舍。比如旧课展示的 5/10/20 秒失败退避是教学方案，新实现不因此自动拥有同样的失败预算与暂停行为。第 22 讲给出了现在应该阅读的路径。

这也是维护项目文档最有价值的方式：保留问题为什么出现、方案如何推导，再补上最新实现及其边界，而不是只把“未完成”三个字删掉。

二、独立开发的一张需求卡应该包含什么？

假设你选择继续完善“详情请求连续失败时的观察行为”。这是一个候选练习，不表示本次已经修改代码。

项目 可以写成什么
用户问题 网络连续失败时，页面是否持续请求却没有明确恢复入口
当前事实 最新页面已持续跟进展开修订；读取失败需要与摄取失败区分
改动目标 给观察请求定义有限重试、暂停提示和手动恢复
范围 页面观察层；不把 GET 重试变成摄取任务重试
不变量 不产生新修订，不重复派发任务，不让旧选择的响应覆盖新选择
成功证据 受控响应下验证请求节奏、身份隔离和终态停止
局限 受控 UI 验收不能证明真实 Worker 或模型质量

这张卡比“加一个重试机制”具体得多。它还避免把另一个业务动作混进去：用户点“重新读取详情”和用户点“重试摄取”应有不同接口和状态含义。

三、修改前先画影响范围

一个前端观察改动可能只需要页面与测试；一个新增 Memory 检索策略则可能影响配置 schema、发布快照、数据库查询、模型上下文、历史回放、页面展示和评测。不能用同样的工作量估计它们。

“最小完整”不是只改代码最少的地方。它表示你选择的范围能够闭合一个用户问题，而且不留下一个看起来能点、实际上没有后端语义的按钮。

四、建议按难度做三个项目练习

练习 A：前端观察失败恢复

沿用前面的需求卡。重点学习会话与资源身份、请求状态、定时器生命周期、失败退避和手动重试。你应该能证明旧响应不会污染新页面，且读取失败不会把后台任务标成 FAILED。

练习 B：为一条数据库不变量补完整证据

以已实现的分块四字段外键作为研究对象。阅读迁移中的旧数据检查、ORM 约束和集成测试，自己设计一个跨文档但同工作区的错误关联，解释为什么旧的局部约束可能放过它、新约束为何能拦住。这里主要练理解和复核，不需要为了“独立开发”重复实现同一个约束。迁移与测试

练习 C：Memory 语义召回的受控候选

先明确个人作用域和引用来源，冻结一组同义表达、噪声、冲突和跨用户样本；再设计一条候选检索策略，并在配置与发布规格里显式选择。比较召回、最终准入、实际使用和错误引用，不只比较“搜到多少条”。这仍是未来改进方向，当前不能写成已经采用向量 Memory。当前 Memory 选择

三个练习分别训练页面工程、数据一致性和智能效果评测。你不必一次完成最难的那个，但每个练习都应该能形成可读的改动说明。

五、怎样报告结果，既具体又不过度？

建议每次用四段式：

  1. 修改原因：什么场景失败，用户受什么影响，证据是什么。
  2. 实现位置：哪些接口、对象或状态规则变化，为什么选这层。
  3. 验证结果：实际执行了什么，输入和环境是什么，通过与失败分别有哪些。
  4. 剩余局限：哪些入口未覆盖、哪些数字仍未知、哪些只是受控演示。

“修复多标签页登录，测试通过”信息太少；“在支持 Web Locks 的同源标签页间串行刷新，并保留同页 single-flight；受控并发刷新与迟到响应场景已验证；不支持 Web Locks 时没有跨标签互斥保证”就能让审阅者判断改动的实际价值。

如果你只是读了源码，就说“我核验了代码和测试定义”；如果你运行了受控前端测试，就说“我验证了这些页面状态”；如果你真的执行了真实模型实验，再记录模型、数据、次数、成本和原始证据。不要把三个层次合成一句“全链路可靠”。

六、面试前，把项目讲成三种长度

30 秒版本回答“项目做什么、为什么需要这些治理”；3 分钟版本讲一个贯穿页面、后端、数据库、Worker 的真实业务；10 分钟版本深入一个你真正做过或核验过的修改，解释不变量、并发窗口、方案取舍和失败案例。

下面的面试区按主题组织，既有基础题，也有追问与场景题。它给你的是答题结构和源码落点。涉及“我实现了”“我测得了”的表述，必须按你实际贡献替换；阅读一个项目、与 AI 协作学习和独立完成改动都可以如实讲清，没必要把整个仓库的工作都说成自己独立完成。
