第 13 讲：身份、会话和多租户——把“已登录”落实到每一次资源操作

本讲只深入此前没有系统讲解的认证/授权链，不重复第 3、6 讲的 FastAPI、ORM 与表关系入门。源码基线：0。阅读入口：apps/api/auth_dependencies.py、packages/core/auth/service.py、packages/control_plane/services.py、packages/control_plane/rbac.py、apps/web/lib/api/client.ts。

13.1 一次真实请求，需要通过三道关

假设 U1 已登录 AgentHub，在客服工作区 W1 中有 Developer 权限，却尝试用地址栏访问另一个工作区 W2 的 Agent。后端至少要回答三个问题：

  1. 请求携带的 Access Token 是否对应一个有效用户 U1？
  2. U1 是否属于 W2 所在组织，并具有进入 W2 的成员关系或组织管理员身份？
  3. 即使能进入 W2，他是否具有这次操作需要的 agent_edit、tool_import 或其他具体权限？

这里最容易出错的地方不是 JWT 库，而是只对用户做了认证，却忘记给资源查询附上工作区范围。例如：

# 教学反例：仅按不可猜测的 UUID 查询对象仍有越权风险
run = await session.scalar(select(AgentRun).where(AgentRun.id == run_id))

# 业务查询至少还应绑定已经授权的工作区
run = await session.scalar(
    select(AgentRun).where(
        AgentRun.id == run_id,
        AgentRun.workspace_id == UUID(context.workspace_id),
    )
)

为什么还要检查资源关系？因为同一工作区里，也可能有仅特定角色可读取的客服记录、审计内容或原始观察。workspace_read 不等于任意业务数据都可读取。参见 9 和 10。

13.2 为什么 JWT 不直接保存整个权限表？

AgentHub 的 Access Token 以 sub、jti、iat、exp 等 Claim 为主，权限在后端访问工作区时计算。这个选择背后是“身份寿命”和“权限寿命”不同。

10:00  U1 登录成功，Access Token 仍有效
10:05  管理员把 U1 从 W1 移除
10:06  U1 继续请求 W1

如果系统只相信 JWT 中的旧 role=DEVELOPER，10:06 的请求仍可能通过。AgentHub 在每次新建工作区上下文时重新读取组织、工作区成员关系，按新事实授权。工作区成员与组织管理员属于不同维度：组织 OWNER/ADMIN 可按组织规则获得更广范围；普通 MEMBER 还需要具体 WorkspaceMembership。

另一层细节：jti 为 JWT 提供身份，但它本身不是撤销列表。登出撤销 Refresh Token Family；旧 Access JWT 会按其验证与到期机制处理。用户退出某个工作区和撤销 Refresh 会话，分别作用于不同边界。

13.3 Refresh Rotation：为什么两标签页会把同一个人登出？

Refresh Token 是服务端签发的高熵随机值，数据库持有其 SHA-256 摘要。Access JWT 不长久保存，浏览器通过受约束的 HttpOnly Cookie 携带 Refresh Token。密码使用 Argon2，因为用户密码是可猜测的低熵输入；Refresh Token 使用 SHA-256 匹配，是因为服务器随机生成的值具有足够高的熵。

关键逻辑在 17：

# 缩减的执行逻辑，保留关键事务语义
current = await sessions.get_for_refresh_update(hash_refresh_token(raw_token))
if current.used_at is not None or current.rotated_at is not None:
    await sessions.revoke_family(current.family_id, now)
    await session.commit()
    raise AgentHubError("REFRESH_TOKEN_REUSE", "...", 401)

current.used_at = now
current.rotated_at = now
next_raw = new_refresh_token()
replacement = AuthSession(
    user_id=current.user_id,
    family_id=current.family_id,
    token_hash=hash_refresh_token(next_raw),
    expires_at=expires_at,
)
session.add(replacement)
await session.flush()
current.replacement_session_id = replacement.id
await session.commit()

两标签页同时发现 Access Token 过期，可能都持有 R0：

后端的行锁保证一个旧令牌只轮换一次；安全策略将复用视作可疑行为。前端则使用同页 single-flight，并在支持 Web Locks 的环境协调同源标签页刷新，从请求源头降低竞争。两种机制配合，不能用“给 API 加一个自动重试”代替。

更隐蔽的竞态是“旧会话发出的请求回来时，新会话已经登录”。如果旧请求的 401 能直接清空整个页面认证状态，就会让新用户被旧请求登出。前端需要给会话变更加上代次/身份，并在写回结果前核对“这是否仍然是当前会话”。

13.4 授权失效的时间点：API、Worker 和 SSE 分别查什么？

假设 U1 10:00 提交了一个耗时 Run，10:01 被移出 W1，10:02 Worker 才领取任务。

队列里携带 workspace_id/run_id/request_id 等业务身份，并不意味着队列拥有授权权力。Worker 读取 Run 的原始创建者和数据库成员关系，重新生成可信上下文；如果权限已经撤销，就进入受控故障状态。参见 19。

前端 SSE 订阅是另一个请求入口。能拿到 Run ID 的人，也应满足查看该运行的资源范围要求。权限检查不能仅放在“提交 Run”处，也不能因为前端隐藏按钮而免去后端验证。

再看数据库性能：如果 API 把整个 SQLAlchemy Session 和行锁保持到模型推理、等待审批、SSE 流结束，连接池会长期被占用。项目对长执行入口采用读取短生命周期身份上下文、后续业务步骤各自开短事务的方式。你应该掌握这个拆分：可信上下文可以脱离事务继续传递；长期占用数据库连接与锁并不是授权的必要条件。

13.5 “最后一个 OWNER”为什么是并发题？

组织仅有 OWNER U1、U2。两个人同时把自己降级：

事务 A：查 OWNER 数量 = 2            事务 B：查 OWNER 数量 = 2
事务 A：降级 U1                      事务 B：降级 U2
结果：组织没有 OWNER

单独一次调用时判断 count > 1 是正确的，两个调用并发时却不能维持业务不变量。TenantService 在组织成员变更入口协调锁与计数，处理最后 OWNER 的保护。这里面试官真正想听的是检查数据与修改数据如何被序列化，而非简单说“有事务”。参见 22。

13.6 一个能落地的验证矩阵

用例 入口 预期观察
无效 JWT 任意受保护 API 401、无业务读取
MEMBER 未加入 W2 W2 Agent 列表 对象不可见，无 W2 内容
VIEWER 发布 Agent POST publish 无 agent_edit，受控拒绝
W1 用户提供 W2 Run UUID GET Run 查询按授权范围过滤
R0 两次并行刷新 Auth refresh 单次轮换成功，复用按 Family 规则处理
U1 登录后立即切换 U2，旧请求返回 前端状态 保持 U2 会话，不被旧响应覆盖
两个 OWNER 并发降级 组织成员 API 至少一条请求受阻，最终保留 OWNER
提交后撤销权限，再派发 Worker Agent Run Worker 重新核对权限

本讲掌握标准：能从一个 Authorization Header 追到 JWT、Principal、Membership、WorkspaceContext、Service 查询，能解释 Refresh 并发和 Owner 并发为什么是两种不同的事务问题。

13.7 源码精读：WorkspaceExecutionContext 到底在哪里变成授权边界？

publish_agent() 的路由签名看起来有两个和工作区相关的参数：workspace_id 和 context。其中 workspace_id 来自 URL；context 由 get_workspace_context() 通过 Principal、Session 和 TenantService.get_workspace_access() 构造。路由随后把它交给 AgentPublishService.publish()。业务服务检查 agent_edit，再按 context.workspace_id 读取草稿。

这种设计解决一个问题：外部请求只负责表达访问目标，服务端负责建立可信目标范围。不同服务各自接收同一类型的 Context，不需要每个函数都重新解析 Cookie。下面是近似真实结构的伪代码：

# 认证依赖：只解决用户身份
principal = await get_current_principal(request, session=session)

# 租户服务：结合真实成员关系，生成工作区级上下文
access = await TenantService().get_workspace_access(
    session, principal=principal, workspace_id=requested_workspace_id
)
context = access.context

# 业务服务：检查本操作需要的权限，并限定数据范围
require_permission(context, "agent_edit")
agent = await session.scalar(
    select(Agent).where(
        Agent.id == agent_id,
        Agent.workspace_id == UUID(context.workspace_id),
    )
)

这三段代码应分布在各自的服务边界，不建议把它们全部复制进每一个 HTTP 路由。这样后台 Worker 或内部服务复用授权逻辑时，也能沿着同一规则获取 Context。

避免全局授权缓存过期

假设为了减少数据库读取，缓存了 permissions[U1,W1]=DEVELOPER。管理员撤销 U1 后，如果缓存仍然有效，新的运行可能继续拥有旧权限。权限缓存必须有明确失效策略：短 TTL、变更事件、成员关系版本，或每个重要执行入口重新查权。对于审批与外部写入等高风险动作，更适合使用当前可信事实而非一个长期不更新的页面状态。

这里的状态不是“用户点击时拥有权限就永远允许执行”。长 Run 在不同时间点可能需要重新建立执行上下文：提交、Worker 领取、恢复审批、读取敏感产物，均可能是独立的授权边界。

13.8 源码精读：Refresh 的异常路径比正常路径更重要

要仔细想象下面五种响应：

场景 观察 应采取的处理
Access 过期 业务 API 401 触发一次受控刷新，随后重发原只读请求
Refresh Token 无效 Refresh 401 当前会话进入需要重新认证状态
Refresh R0 已使用 REFRESH_TOKEN_REUSE 按 Token Family 保护规则处理
网络超时 未知服务端是否已轮换 优先读取当前 Cookie/会话代次，防止拿旧 R0 并行竞争
旧会话请求在新用户登录后返回 迟到 401 只影响旧请求，不清空新的会话

网络超时值得单独研究。如果服务器已完成 R0→R1 的轮换，响应却丢失，浏览器可能继续持有 R0。重新请求时，系统会把它视作复用。前端的跨标签互斥不能消除这种“提交成功但确认丢失”的窗口；要设计更细的恢复，需要在安全模型中明确如何识别原刷新请求与响应、是否允许短暂宽限以及滥用风险。当前课程重点是能识别这个问题，而不是改成所有刷新失败都无限重试。

如何做并发测试？

纯函数 resolve_permissions() 测试只能核对角色→权限集合。验证最后 OWNER 保护必须使用真实数据库的竞争事务。建议测试执行两个降级操作，让它们在“读到当前 OWNER 数量”附近交错，最后 assert：

owners = await count_owners(session, organization_id)
assert owners >= 1

更完整的断言还需要检查两条请求各自的 HTTP 状态、审计记录与成员表最终事实。测试并发时，不要只运行一条请求十遍就叫并发测试。可以使用屏障控制重叠时序，确保代码实际经历目标竞争窗口。

13.9 四种授权错误的定位方法

当用户抱怨“页面能看见按钮但提交失败”，从请求开始分四步：

  1. 查 Authorization 头和 Principal 获取过程：身份是否有效？
  2. 查组织/工作区 Membership：目标 Workspace 是否对当前用户可见？
  3. 查本次 action 的 Permission：例如 agent_edit、knowledge_edit、support_records_read。
  4. 查目标资源的工作区归属与对象级规则：Agent 是否属于 W1，当前状态是否允许发布？

这一顺序能区分 401、404、403、409/422。前端应该展示能给用户行动指引的安全错误，如“需要管理员权限”或“资源已失效”，而不是直接展示数据库底层异常。API 错误码更适合稳定地驱动界面；后台可用 request_id 对应详细的非敏感诊断日志。

13.10 三分钟口述练习

AgentHub 将身份验证与业务授权分开。Access JWT 主要证明 user_id；访问某工作区时，TenantService 根据组织和工作区成员关系计算权限并产生可信 ExecutionContext。Service 检查具体权限，SQL 查询继续绑定 workspace_id，避免越权访问对象。Refresh Token 使用轮换和数据库行锁防重用，前端通过同页合并及跨标签协调降低正常并发造成的复用误报。对长 Run，Worker 会在实际执行前重新核对授权，从而让账号和成员关系的变更进入后续执行决策。

这段话每个短语都能继续向下追一份源码，而不是背几个安全术语。
