第 13 讲：认证、会话与多租户授权

一、先把“你是谁”和“你能做什么”分开

认证确定请求对应哪个用户；授权确定这个用户在目标组织、目标工作区中能做什么。AgentHub 的 access token 包含 sub、jti、iat、exp，没有把“这个用户永远是管理员”写进令牌。请求经过 get_current_principal() 验证令牌，并确认用户仍然存在且有效；随后业务层再解析租户关系和权限。认证依赖 令牌实现

这意味着，拿着有效令牌也不能随意换 URL 中的 workspace_id 读取别人的内容。这个 ID 是请求想访问的目标，不是服务器已经相信的授权范围。

把认证、租户和权限混为一谈，是很多初学者做多租户系统时最容易犯的错误：看到 JWT 签名正确，就直接用请求参数查数据库；看到页面隐藏了按钮，就认为后端不需要再检查。这两种做法都跳过了真正的授权边界。

二、Organization 与 Workspace 为什么要分别建成员关系？

你可能属于一家组织，但只参与其中一个项目。也可能是组织管理员，需要管理多个工作区，却没有在每张 WorkspaceMembership 表里人为补一条 Developer 记录。

当前权限解析的核心规则如下。它们来自服务器的成员关系，不来自浏览器自己声称的角色。RBAC 租户访问服务

组织身份 工作区身份 当前权限语义
OWNER / ADMIN 可以没有单独工作区成员行 具有组织管理及工作区管理、操作、审批等权限；具体成员管理仍有 OWNER 保护规则
MEMBER DEVELOPER 可以操作 Agent、知识、工具、评测及业务记录等；不因此自动成为审批者或组织管理员
MEMBER VIEWER 工作区读取与评测读取；不等于可以读取所有特殊业务详情
MEMBER 无成员关系 无该工作区访问权
无组织成员关系 即使猜到工作区 ID 无该组织下工作区访问权

这里不要把 VIEWER 简化成“所有 GET 都允许”。客服记录有自己的 support_records_read 权限，评测还可能投影隐藏参考答案或敏感观察。HTTP 方法只是协议类别，实际权限来自业务合同。

get_workspace_access() 会先查工作区，再查组织成员关系；普通成员还需要查工作区成员关系，最后构造不可变的 WorkspaceExecutionContext。应用服务和工具处理器接收这个已经授权的上下文。上下文模型

三、越权防护为什么需要多层？

假设接口是 GET /api/v1/workspaces/W1/runs/R2，但 R2 实际属于 W2。

第一层验证访问者能不能进入 W1；第二层查 Run 时必须同时限制 id=R2 和 workspace_id=W1；第三层数据库中的关联约束尽量保证对象没有跨租户错误连接。第一层通过，不能替代第二层。

# 教学伪代码：说明资源查询的复合范围，不是某个接口的逐字实现。
run = await session.scalar(
    select(AgentRun).where(
        AgentRun.id == requested_run_id,
        AgentRun.workspace_id == authorized_workspace_id,
    )
)

多列外键解决的是“数据关联不能串租户”，应用权限解决的是“谁能看、谁能改”。数据库有外键，不代表已经实现数据库行级权限；应用加了过滤，也不代表后台脚本的错误关联一定会被拦住。第 18 讲的新四字段分块约束，正好展示了关系完整性这层保护。

对工作区不存在、访问者不属于该组织等情况，访问服务使用 404，避免把资源存在性不必要地暴露给无权访问的人。同一业务域内明确无操作权限时则可能返回 403。不能把所有 404 都判断成“数据库真没有这条记录”。租户访问服务

四、密码、Access Token、Refresh Token 各自存什么？

密码使用 Argon2 哈希校验；Refresh Token 使用高熵随机值，数据库保存其 SHA-256 哈希，浏览器持有原始值。Access Token 使用 JWT，默认访问有效期是 900 秒；Refresh 默认有效期是 2592000 秒，这些都是可配置值，不是所有部署永远固定的参数。认证安全实现 配置模板

对象 目的 持久化或交付方式 不应做的事
密码哈希 验证密码是否正确 用户表 保存可逆明文密码
Access Token 短期证明当前请求身份 登录/刷新响应返回 当作工作区永久权限清单
Refresh Token 换取新的访问令牌 HttpOnly Cookie；数据库存哈希 把原始令牌写入业务日志
Provider Secret 调用模型供应商 加密密文和运行时解密 塞进 AgentVersion、Prompt 或公开响应

Refresh Cookie 设置了 HttpOnly、路径、SameSite 和 Secure 等属性。HttpOnly 减少脚本直接读取 Cookie 的机会，但不意味着所有浏览器攻击面都自动消失；生产域名、HTTPS、代理和跨站策略需要一致配置。认证路由

五、刷新为什么要轮换？为什么多标签页会互相“踢下线”？

刷新不是不断复用同一个长期令牌。AuthService.refresh() 锁定当前 AuthSession，检查有效期、撤销状态以及是否已经使用；正常刷新时把旧令牌标记为已使用，创建同一 family 的替代会话。重复使用旧令牌会触发 family 撤销，这是为了识别可能的令牌重放。认证服务 会话行锁

问题在于：两个正常浏览器标签页也可能几乎同时拿着同一枚旧 Cookie 刷新。后端按规则轮换，第一个成功，第二个就可能被判定为重放。

最新前端因此加了同页面 single-flight，以及支持 Web Locks 时的同源标签页串行刷新。这个改动不是放松后端的重放防护，而是在客户端减少正常操作制造的竞争。浏览器不支持 Web Locks 时，不能宣称仍拥有同样的跨标签页互斥保证。迟到的刷新响应或 401 还必须绑定发出请求时的会话身份，不能让旧账号的响应覆盖新账号。前端认证调用 会话提供器

六、登出是不是让所有已经签发的 Access Token 立刻失效？

当前登出撤销 refresh family 并清除 Cookie；认证依赖验证 JWT、用户存在性和启用状态，没有每次按 jti 查询全局撤销表。因此不能把当前行为描述为“登出立即吊销所有存量 Access Token”。短期令牌会到期，成员权限会在后续授权时重新读取，但这与逐令牌立即撤销不是同一机制。登出与刷新 请求认证

如果产品未来需要设备级立即撤销，需要进一步设计会话版本、denylist 或其他服务器侧检查，并评估额外数据库或缓存依赖。这里是需求推导，不表示本次项目已经实现。

七、“最后一个 Owner 不能删除”为什么不是一个简单 if？

两位 Owner 同时降级自己，各自先查询到 Owner 数量为 2；如果查询和修改之间没有并发保护，两边都认为合法，最后组织可能没有 Owner。

项目在修改组织成员时锁定成员关系并在锁内重新确认操作者角色，再执行最后 Owner 保护。组织 ADMIN 也不能因为有普通成员管理权限，就随意降级 OWNER 或创建新的 OWNER。这里的重点是把“检查所依据的事实”和“修改事实”放在同一并发控制范围内。成员变更与保护

不要把这个例子直接泛化成所有系统都应锁整张成员集合。规模、访问模式、锁顺序、唯一约束和事务隔离都要一起考虑。本项目提供的是具体业务约束下的一种实现。

八、面试练习：给角色矩阵加上失败路径

不仅测试 OWNER 成功创建 Agent，还要问：VIEWER 直接调用 POST 如何返回；普通组织成员没有 WorkspaceMembership 会发生什么；已被移出工作区的人拿着旧 Access Token 再运行 Agent 会怎样；切换账号后晚到的权限响应会不会污染页面；权限请求失败时是否被错误显示为“您是只读用户”。

通过这些问题，你才能把身份、租户、权限、网络失败和页面状态分别解释清楚。第 22 讲继续讲这些后端事实怎样正确映射成可用的前端交互。
