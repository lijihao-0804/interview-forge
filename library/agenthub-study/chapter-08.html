第 6 讲：数据库表结构设计与面试

用户提问

讲一下数据库表结构的设计吧，这个面试也挺经常问的

讲解原文

数据库表结构设计，核心是把业务中的“对象、关系和规则”准确地表达出来。 面试时，最好能沿着一条完整业务说明：为什么拆成这些表、哪些错误由数据库约束阻止、常见查询需要什么索引，以及数据变化后如何保留历史。

结合 AgentHub，你最值得掌握的主线是：

Agent 草稿 → 发布版本 → 一次运行 → 运行步骤与审批动作。

这条线能把实体拆分、主外键、版本设计、JSONB、索引和并发控制串在一起。下面依据当前源码提交 0 展开；示意 SQL 会明确标注。

一、设计表之前，先说清楚“一行代表什么”

这是最重要的起点。

假设需求是：

用户创建一个 Agent，可以反复修改、发布版本、运行任务，并查看运行过程和工具审批。

这里至少存在五种不同的业务事实：

表 一行代表什么 为什么需要独立保存
agents 一个 Agent 的身份和当前可编辑草稿 草稿可以修改，Agent 身份保持稳定
agent_versions 这个 Agent 的一次发布 需要保留发布时的运行配置
agent_runs 使用某个版本执行的一次任务 每次输入、输出、状态、耗时都不同
run_steps 一次 Run 中的一个执行步骤 步数不固定，需要逐条记录和排序
approvals 一次具体动作的审批及执行记录 每个动作有独立参数、决定和结果

这些是项目中的实际表。源码：Agent 运行模型、审批模型。

先只画核心关系：

||--o{ 在这里表示：一个父记录可以对应零个或多个子记录。

例如：

  • Agent A 是“售后助手”。
  • A 发布了 V1。
  • V1 执行了 R1、R2。
  • 后来修改草稿，发布 V2。
  • V2 执行 R3。
  • R3 有若干步骤，并提出两个需要审批的动作。

这样一描述，表之间的关系就自然出现了。

你可以把“一行代表什么”当作拆表检查：如果一张表中的一行，有时代表 Agent、有时代表运行、有时又代表审批，通常需要重新梳理。

二、最关键的拆表：Agent、Version、Run

1. agents 保存当前可编辑内容

主要字段包括：

id
workspace_id
name
system_prompt
model_profile_id
retrieval_config
runtime_config
created_at
updated_at

用户修改提示词、模型配置、检索参数，修改的是当前草稿。

2. agent_versions 保存一次发布的配置

主要字段包括：

id
workspace_id
agent_id
version_number
spec_schema_version
resolved_spec
resolved_spec_hash
created_by
created_at

发布新版本时，项目会新增一条 AgentVersion，保留这次发布解析出来的配置快照。源码：AgentPublishService.publish。

3. agent_runs 引用具体的 Version

核心关联是：

agent_runs.agent_version_id
    → agent_versions.id

当前 agent_runs 表直接保存的是 agent_version_id，没有直接保存 agent_id。 需要知道属于哪个 Agent 时，可以通过 Version 找到它。源码：AgentRun。

为什么这样设计？

假设昨天 R1 使用 V1，今天你把草稿改成了另一套提示词。如果 R1 只指向不断变化的草稿，就很难准确解释昨天的运行使用了什么配置。

通过引用具体 Version，历史运行有明确的配置依据。

这里还要讲准确一点：如果版本中保留了 LATEST 这类知识绑定策略，Run 还会记录这次实际使用的知识快照。“发布配置是什么”和“本次实际选中了哪些资源”是两个层次。

面试中可以这样解释

我把可编辑草稿、发布版本和执行实例分开。草稿用于修改，发布时新增配置快照，Run 引用具体版本，因此后续修改不会改变历史运行所关联的版本。对于运行时解析的资源，Run 另外记录实际使用结果，方便追溯。

这里的“版本不可变”是应用使用这些记录的契约。主键和唯一约束本身，并不会自动禁止所有 SQL UPDATE。

三、主键、业务唯一键、外键，要分别设计

这三个概念经常一起出现，但回答的问题不同。

机制 回答什么问题
主键 PRIMARY KEY 这一条记录是谁？
唯一约束 UNIQUE 哪种业务组合不允许重复？
外键 FOREIGN KEY 这条记录引用的对象是否存在，关联是否合法？

1. 主键：标识记录身份

AgentHub 的多数业务实体使用：

id UUID PRIMARY KEY

例如 Agent、Version、Run、Approval。

UUID 可以由应用生成，便于不同进程生成标识；PostgreSQL 有原生 UUID 类型，它是 128 位的标识。选择 UUID 时仍需考虑索引大小和访问模式，不能直接认为 UUID 在所有场景都优于自增整数。(postgresql.org)

更重要的是：

主键唯一，不代表业务上不会重复。

比如：

id agent_id version_number
V101 A1 1
V102 A1 1

两个 id 不同，所以主键不会冲突。

但同一个 Agent 出现了两个 V1，业务上已经重复了。

2. 业务唯一键：表达“不允许重复什么”

因此，项目给 AgentVersion 加了：

UNIQUE (agent_id, version_number)

它允许：

Agent A 有 V1
Agent B 也有 V1

但不允许：

Agent A 同时存在两个 V1

这就是唯一性的作用域。

项目中还有几组很典型的约束：

实际约束 表达的规则
UNIQUE(agent_id, version_number) 一个 Agent 的版本号不能重复
UNIQUE(document_id, revision_number) 一份文档的版本号不能重复
UNIQUE(thread_id, client_token) 同一会话中，一次逻辑提交不能重复创建 Turn
UNIQUE(workspace_id, logical_action_id) 同一工作区中，同一个逻辑动作不能重复创建审批
UNIQUE(workspace_id, agent_run_id, sequence_number) 同一次 Run 的步骤序号不能重复

源码分别见 运行模型、知识模型、会话模型、审批模型。

注意：步骤序号唯一，只保证“不重复”，并不自动保证序号从 1 开始、连续或没有空缺。

3. 外键：不只检查 ID，还能检查归属

AgentHub 里有一个很值得在面试中展开的设计：

FOREIGN KEY (workspace_id, agent_id)
REFERENCES agents (workspace_id, id)

为什么同时引用两个字段？

假设父记录是：

Agent A1 属于工作区 W1

但新增 Version 时错误地填写：

agent_id = A1
workspace_id = W2

如果只有：

FOREIGN KEY (agent_id) REFERENCES agents(id)

数据库只会检查 A1 是否存在。A1 存在，所以这个外键可以通过。

而复合外键检查的是：

(W2, A1) 这组值是否存在于 agents 表

因此会拒绝错误的工作区归属。

这也解释了为什么父表的 id 已经是主键，还会额外声明：

UNIQUE (workspace_id, id)

它为下游的复合外键提供可引用的唯一键。源码：Agent 与 AgentVersion 约束。

UUID 用来识别对象，workspace_id 用来表达归属，这两个字段承担不同责任。

这层约束保护的是数据关联一致性。接口仍需要鉴权，查询仍需要正确限定工作区。

4. 把这些规则写成建表语句

下面是保留关键字段的教学版 DDL，假设父表已经建立，并省略了部分字段和删除策略：

CREATE TABLE agent_versions (
    id UUID PRIMARY KEY,

    workspace_id UUID NOT NULL,
    agent_id UUID NOT NULL,

    version_number INTEGER NOT NULL
        CHECK (version_number > 0),

    resolved_spec JSONB NOT NULL,
    resolved_spec_hash VARCHAR(64) NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),

    UNIQUE (workspace_id, id),
    UNIQUE (agent_id, version_number),

    FOREIGN KEY (workspace_id, agent_id)
        REFERENCES agents (workspace_id, id)
);

你要能逐项解释：

  • PRIMARY KEY：记录身份。
  • NOT NULL：这条记录缺少该信息就不完整。
  • CHECK：字段取值必须符合条件。
  • UNIQUE：限制业务重复。
  • FOREIGN KEY：限制引用关系。
  • DEFAULT：插入时没有提供值，使用哪个默认值。

DEFAULT 和 NOT NULL 是两个独立约束，默认值并不等于禁止显式写入空值。

四、多对多关系：角色为什么放在成员表

AgentHub 的用户与组织是多对多关系：

  • 一个用户可以加入多个组织。
  • 一个组织可以拥有多个用户。

因此项目使用：

users
organizations
organization_memberships

成员表的核心结构是：

organization_id
user_id
role

复合主键是：

PRIMARY KEY (organization_id, user_id)

1. 角色属于“用户在某个组织里的身份”

同一个用户可以是：

user_id organization_id role
U1 O1 OWNER
U1 O2 MEMBER

所以，一个全局的 users.role 无法准确表达这类需求。

role 应当放在成员关系上，因为它描述的是：

U1 在 O1 中是什么身份。

工作区成员表也采用类似设计：

workspace_memberships(
    workspace_id,
    user_id,
    role
)

当前组织角色为 OWNER / ADMIN / MEMBER，工作区角色为 DEVELOPER / VIEWER。源码：control_plane/models.py。

2. 中间表不一定需要单独的 id

这里用：

PRIMARY KEY (organization_id, user_id)

就能唯一标识一条成员关系，同时防止重复入会。

也可以给中间表加 UUID 主键，但仍需要：

UNIQUE (organization_id, user_id)

来维护业务唯一性。

选择哪一种，要看这条关系本身是否经常被其他表独立引用，以及接口是否需要一个单独的关系 ID。

五、范式、冗余和 JSONB，怎样取舍

1. 三大范式要能用例子解释

规范化主要用来减少重复事实和不一致依赖，降低修改数据时的维护成本。实际设计可以根据需要保留冗余，但必须说明其一致性规则。(learn.microsoft.com)

对于面试入门，可以先这样理解：

范式 重点 用 AgentHub 举例
第一范式 避免用重复字段组表达数量不固定的关系 不设计 tool1_id、tool2_id、tool3_id，用工具绑定表表达
第二范式 非主属性应依赖整个候选键，而非组合键的一部分 成员表以“组织＋用户”为键，用户邮箱只依赖用户，应放在用户表
第三范式 避免非主属性通过其他非主属性传递依赖候选键 Agent 已引用工作区，不必在每条 Agent 中再维护工作区的当前名称

例如，下面这张成员表就有明显的问题：

organization_memberships(
    organization_id,
    user_id,
    organization_name,
    user_email,
    role
)

其中：

  • organization_name 属于组织。
  • user_email 属于用户。
  • role 才属于这条成员关系。

把组织和用户信息分开保存后，用户改邮箱只需要改用户表，组织改名只需要改组织表。

2. 项目仍然保留一些有目的的冗余

最典型的是下级表反复出现：

workspace_id
knowledge_base_id

理论上，可以通过多次 JOIN 从父记录推导它们。

但显式保存这些字段，可以：

  • 直接按工作区过滤；
  • 建立符合访问范围的联合索引；
  • 用复合外键检查父子归属一致性。

这是一种有明确约束的冗余。

3. 历史快照表达的是另一个时间点的事实

agent_versions.resolved_spec 会保存发布时的配置。

草稿中也有提示词和运行参数，这看起来有重复，但两者表达的事实不同：

  • 草稿：现在准备编辑和发布什么。
  • Version：当时发布的配置是什么。

因此，发布快照需要保留自己的内容。后续修改草稿，不应该同步改掉旧版本。

判断冗余之前，先判断两个字段表达的是“同一个当前事实”，还是“不同时间点的事实”。

4. 普通列与 JSONB 的分工

AgentHub 的实际设计很清楚：

内容 采用的形式
工作区、Agent、Version、Run 等关联 ID 普通列
状态、时间、次数、序号 普通列
发布配置 resolved_spec JSONB
工具参数 canonical_arguments JSONB
步骤附加信息 safe_metadata JSONB
文档定位信息 locator JSONB

原因是：

需要频繁关联、过滤、排序、约束的字段，适合明确建列；结构不同或需要整体保留的配置，可以使用 JSONB。

例如，不同工具的参数不同，把每个工具可能有的参数都扩展成审批表的一列，会造成大量无关字段。

但 workspace_id、run_id、decision_status 这些核心业务字段，应当保持明确的类型和约束。

PostgreSQL 的 JSONB 支持查询和索引，但使用 JSONB 不会自动为内部字段建立所有需要的索引。AgentHub 这几张核心表也没有因为使用 JSONB 就统一建立 GIN 索引。(postgresql.org)

5. 字段类型也要符合业务含义

项目里的几个实际例子：

字段 类型 设计理由
id UUID 记录身份
version_number INTEGER 用于比较、排序和约束的版本序号
system_prompt TEXT 长文本
started_at、completed_at 带时区时间戳 表达运行时刻
total_cost_amount NUMERIC(20, 8) 使用十进制定点精度保存费用
resolved_spec JSONB 结构化配置快照

其中 NUMERIC(20, 8) 表示总精度 20 位、小数部分 8 位，适合需要十进制精度的数值。源码：业务字段定义。

可空性也要表达真实业务：运行尚未完成时，completed_at 可以为空；成功运行没有错误，failure_code 可以为空。

六、知识库的表设计：文档、文档版本、知识快照

这一组很适合说明“业务身份”和“历史版本”为什么需要分开。

1. 三种概念分别是什么

  • Document：逻辑上是哪份文档，例如《售后规则》。
  • DocumentRevision：这份文档的某一次内容版本。
  • KnowledgeSnapshot：某次使用时，固定采用哪些文档版本。

这是核心关系图，省略了工作区、知识库以及部分直接外键。源码：knowledge/models.py。

2. 快照保存的是版本成员清单

假设有两份文档：

  • D1：《售后规则》
  • D2：《物流说明》

快照可以是：

snapshot document revision
S1 D1 R1
S1 D2 R4
S2 D1 R2
S2 D2 R4

这表示：

  • S1 使用旧版售后规则 R1。
  • S2 使用新版售后规则 R2。
  • 两个快照都复用物流说明 R4。

项目没有为每个快照复制一遍全部分块正文。 快照成员指向具体文档版本，再通过版本找到已有分块。源码：snapshots.py。

3. 关联表能表达更强的规则

knowledge_snapshot_items 有一条重要约束：

UNIQUE (
    workspace_id,
    snapshot_id,
    document_id
)

它表达：

同一个快照中，同一份逻辑文档最多选择一个版本。

此外，它用包含以下四列的复合外键引用文档版本：

workspace_id
knowledge_base_id
document_id
document_revision_id

这样就能同时检查：

  • 版本属于这个工作区；
  • 属于这个知识库；
  • 确实属于这份文档。

这也是使用成员关联表的实际价值：这些引用关系可以由普通关系约束检查。

4. 一个进阶检查：两个外键不一定保证彼此匹配

假设：

R1 是 D1 的版本

某条记录却写成：

document_id = D2
revision_id = R1

如果分别只有“D2 必须存在”和“R1 必须存在”两个外键，这两个检查可能都通过。

但 D2 和 R1 仍然不属于同一条版本链。

AgentHub 的快照成员表已经通过四列外键表达了这个关系。document_chunks 当前则主要通过正常写入服务“先根据 revision 查询 document，再写 chunk”保证这一步一致；它现有的两个外键并没有完整表达这组文档与版本的配对规则。

如果以后加强这部分数据库约束，可以给 chunk 增加同样的四列引用关系。 这是设计改进方向，不能当成当前已经实现的约束。源码：知识模型、分块写入逻辑。

面试中能准确说明“数据库保证了什么，服务代码还保证了什么”，比笼统说“加了外键就都一致”更有说服力。

七、索引要从查询推出来

设计完字段和关系，还要回答：

页面和后台最常怎样读取这些数据？

1. 先写典型查询

例如，查询某个工作区中，某种状态的最近运行：

SELECT id, status, started_at
FROM agent_runs
WHERE workspace_id = :workspace_id
  AND status = :status
  AND started_at >= :start_time
ORDER BY started_at DESC
LIMIT 20;

这是一条参数化查询示意。

它的访问条件是：

  1. 固定工作区。
  2. 固定状态。
  3. 按时间范围筛选。
  4. 按时间排序。

因此，下面这组联合索引与它的访问模式相符：

(workspace_id, status, started_at)

AgentHub 中确实存在这组索引。源码：AgentRun 索引。

2. 为什么列顺序有意义

可以把这组 B-tree 索引理解为，先按工作区组织，再在工作区内按状态组织，最后按时间组织。

对于前导列有等值条件、后面有范围条件的查询，这种顺序可以有效缩小需要扫描的范围。

但不要把“最左前缀”背成绝对的“缺少第一列，索引一定完全不能用”。PostgreSQL 16 的多列 B-tree 索引可以用于部分列条件，只是缺少前导列限制时，可能需要扫描更大范围，优化器也可能选择其他访问方式。(postgresql.org)

SQL 中 WHERE 条件书写的先后顺序，也不等于索引列顺序。

3. 不同查询需要不同的索引形态

项目中的一些真实索引：

索引列 对应的典型访问方式
(workspace_id, agent_id, version_number) 查看某个 Agent 的版本
(workspace_id, started_at, id) 查看工作区中的运行历史
(workspace_id, agent_version_id, started_at) 查看某个版本的运行历史
(workspace_id, agent_run_id, sequence_number) 按顺序读取 Run 步骤
(workspace_id, decision_status, expires_at) 筛选某工作区的待审批、到期记录

源码见 运行模型 和 审批模型。

索引的选择要结合数据规模、分布和查询计划验证。每多一个索引，也会增加写入维护和存储成本。

4. 两个常见追问

唯一约束和普通索引有什么区别？

唯一约束表达“不允许重复”的规则；在 PostgreSQL 中会自动创建相应的唯一 B-tree 索引。普通索引主要提供访问路径，不限制重复值。

有外键就一定有子表索引吗？

PostgreSQL 不会因为声明外键，就自动为引用方的列创建索引。是否需要，要根据关联查询和父记录更新、删除等访问方式评估。(postgresql.org)

因此，审查索引时要同时查看主键、唯一约束自动产生的索引，避免只盯着显式的 CREATE INDEX。

八、表设计还必须考虑并发、状态、删除和演进

1. 有唯一约束，仍需要设计并发流程

以发布 AgentVersion 为例：

当前最大版本号为 5

请求 A 查询到下一版本为 6
请求 B 也查询到下一版本为 6

UNIQUE(agent_id, version_number) 会阻止两个 V6 同时保存。

但它只保证数据库不会留下重复版本；它不会自动帮两个请求分别分配 V6 和 V7。

项目的发布逻辑会先锁定 Agent 行，再计算下一个版本号、插入新版本，最后提交。唯一约束仍然保留，负责防止重复数据进入数据库。源码：publish()。

你可以这样表达二者的分工：

唯一约束定义不能出现的数据；事务和锁安排并发请求怎样完成业务。

2. 状态值合法，不等于状态流转合法

审批表中分别保存：

decision_status
execution_status

因为“批准了”和“执行成功了”是不同事实。一个 Run 又可能有多个动作，因此审批需要独立记录，无法只在 Run 上加一个 approved 布尔值解决。

表中的 CHECK 可以限制：

decision_status 只能取规定的几个值

但它本身并没有完整表达：

哪种旧状态可以变成哪种新状态
谁有资格做这个转换
转换时还需要同时修改哪些记录

这些仍由服务逻辑、事务和条件更新处理。源码：审批模型。

所以面试时要分别说清楚：

  • 字段值约束；
  • 状态转换规则；
  • 转换的并发条件。

3. 删除策略要逐条关系设计

AgentHub 实际同时使用了几种策略：

策略 含义 项目例子
CASCADE 删除父记录时，删除依附的子记录 Run 与其步骤
RESTRICT 有引用时阻止删除 Run 引用具体 AgentVersion
SET NULL 保留子记录，清除已经不存在的关联 Run 的部分会话关联

例如，已经有 Run 使用某个 Version 时，RESTRICT 可以保护这个运行所依赖的历史版本记录。

项目还存在一个很具体的细节：Run 的 Thread 外键包含 workspace_id 和 thread_id。删除 Thread 时，只应清空 thread_id，保留工作区归属，因此使用：

ON DELETE SET NULL (thread_id)

如果机械地对整个复合外键执行 SET NULL，就可能连不能空的 workspace_id 一起置空，导致删除失败。源码：AgentRun 外键说明。

软删除也需要完整设计：增加 deleted_at 或某个删除状态之后，还必须明确查询过滤、唯一性、关联记录、历史引用以及恢复规则。

4. 表结构升级要处理已有数据

假设你想新增：

client_token NOT NULL

但表里已经有很多历史记录。

设计时就要考虑：

  1. 旧记录填什么值。
  2. 如何保证回填后的唯一性。
  3. 新旧应用同时运行时是否兼容。
  4. 什么时候收紧非空约束。
  5. 迁移失败后数据库会处于什么版本。

这就是 Alembic migration 需要表达的内容。改 ORM 模型只是修改了代码中的定义；已有表结构和历史数据还需要明确迁移。

九、面试时怎样把这套设计讲清楚

可以先讲核心业务模型，再让面试官沿约束、索引或并发继续追问。

下面这段可以作为你的回答骨架：

AgentHub 的核心表围绕 Agent 草稿、发布版本和执行记录设计。草稿允许修改，发布时新增配置快照，Run 绑定具体的 AgentVersion，因此能够追溯每次执行使用的配置。Run 下再拆出多个执行步骤和审批记录，分别表达运行过程，以及每个动作的人工决定和执行结果。

主键主要使用 UUID，但业务唯一性另外通过组合唯一约束表达，例如同一 Agent 的版本号不能重复、同一 Run 的步骤序号不能重复。工作区归属既用于查询过滤，也进入复合外键，防止父子记录引用到不同工作区的数据。

状态、关联 ID、时间和序号使用普通列；配置快照、工具参数等结构变化较多的内容使用 JSONB。索引根据实际的过滤和排序方式设计，例如工作区、状态和开始时间的联合索引。

在并发处理上，唯一约束防止重复数据，事务和行锁保证版本号分配等业务流程正确完成。删除和迁移则根据历史引用设计，已经被运行使用的版本需要保留，新增约束也需要先处理历史数据。

准备这部分面试时，优先把以下四个例子讲熟：

  • Agent、Version、Run 为什么必须区分。
  • UUID 已经唯一，为什么还需要业务唯一约束和工作区复合外键。
  • 一条真实查询，为什么对应某个联合索引顺序。
  • 已经有唯一约束，发布版本时为什么仍然要加锁。

这四个例子都能直接落到你项目的表和代码上。
