面试问答 C：知识摄取、RAG、Memory 与 Wiki（KG01–KG60）

本区的“项目落点”对应 2026-11-20 固定提交 cdc9d084d3a20e71355401952ee394da4e56273b。回答中的设计建议与当前实现分开表述；可口述回答可以练成 60—90 秒版本，追问部分用于继续展开。

KG01：为什么要把 Document 和 DocumentRevision 分成两张表？

可口述回答： Document 表示业务文档身份，Revision 表示一次不可变内容版本。两者分开后，文件重传不会把历史来源改写，旧快照和旧回答可以继续说明自己当时使用哪个版本。新修订处理失败，也不必立即毁掉旧的可用版本。仅在一张表上覆盖正文虽然容易实现，但会丢失来源历史、并发修订身份和可重现性。

项目落点与追问： 当前还有 Chunk 和 Snapshot 共同完成来源链。若追问“为什么不直接用 Git”，应回答业务系统还需要租户、权限、摄取状态、索引和查询绑定，不是只保存文本差异；Git 可以是来源，但不能自然代替全部业务模型。模型 快照

KG02：既然已经有 revision_id，Chunk 为什么还保存 document_id？

可口述回答： 冗余父身份可以便于按文档过滤、建立租户范围约束和提供稳定引用，但冗余就意味着必须防止彼此矛盾。不能让 chunk.document_id 指向 D1，而 revision_id 实际属于 D2。本项目现在用工作区、知识库、文档、修订四字段外键，直接约束完整配对。

项目落点与追问： 重点不是“冗余字段一定更快”，而是说明读写收益与一致性代价。若删掉 document_id，可以通过修订关联查询；若保留，就应由数据库验证业务关系，不能只相信每条应用写入都填对。模型 0061 迁移

KG03：两个外键分别存在，为什么不够保证关系正确？

可口述回答： 分别存在只证明两个对象各自合法，不证明它们属于同一关系。文档 D1 和修订 R2 都存在，R2 却可能属于 D2。组合外键把一组字段作为关系约束，才能表达“这一个修订必须属于这一个文档，并且同属该工作区和知识库”。

项目落点与追问： 本次 RG15 修复就是这个例子。追问还可以扩展到订单与订单项、项目与任务、租户与资源版本。应先写出业务不变量，再看数据库唯一键、外键和服务授权分别保护哪一层；不要用 UUID 全局唯一代替归属验证。组合约束

KG04：给已有表增加外键时，遇到历史脏数据怎么办？

可口述回答： 先识别并保留能定位问题的记录，确认业务归属后再修复，不能猜测该改哪一边。当前迁移建立新约束、检查文档与修订错配、验证历史数据，再删除旧约束。若发现错误会带身份中止，而不是自动把数据改成能通过约束的样子。

项目落点与追问： NOT VALID 解决的是约束验证的时序，不等于不用验证，也不自动保证零锁等待。本项目在同一迁移事务里完成验证；超大表仍需评估锁、耗时和发布窗口。真实数据库迁移测试比只检查 ORM 声明更能证明行为。迁移 迁移测试

KG05：并发生成同一文档的修订号，你会怎么做？

可口述回答： 直接读取 max+1 会竞争，因为两个请求可能都读到相同最大值。当前项目在写完 Blob 后锁定同一 Document 父行，再读取最新号并插入修订，让同一文档的分配串行化。锁父行是因为下一条修订还不存在，不能可靠地锁一个尚未存在的子记录。

项目落点与追问： 唯一约束仍然是最后防线，但它只能拒绝冲突，不能让两个合法上传都成功分配。还应说明为什么不在上传开始就持锁：大文件流式写入会拖长临界区。不同文档不用为一个全局锁互相等待。上传服务

KG06：文件上传为什么不能放进一个普通数据库事务里一起回滚？

可口述回答： Blob 写入、PostgreSQL 事务和队列通知属于不同系统，普通数据库事务只能原子化数据库内的修改。项目先保存原件，再提交修订与任务，最后通知队列；失败时根据确定的提交状态补偿。特别是提交确认丢失，必须按预分配身份回查，不能看到异常就删除原件。

项目落点与追问： 回滚客户端连接并不能证明服务端没提交。正确答案要区分明确成功、明确失败和结果未知。结果未知时保留可对账状态，比把所有异常都当成“从未发生”更可靠。上传提交确认

KG07：数据库提交成功，但发队列失败，怎么办？

可口述回答： 不能把数据库已经确认的任务当成不存在。本项目知识摄取先持久化 IngestionJob，发队列失败会记录诊断；协调逻辑可以继续识别和派发可恢复任务。队列消息是通知，数据库任务身份与状态是恢复依据，重复通知也必须通过原子领取判断能否执行。

项目落点与追问： 这证明的是知识摄取这条链路具有持久任务恢复，不能推导全项目所有业务都用了统一 outbox。如果进一步设计 outbox，应把业务状态和待派发事件写在同一事务，再允许发布器幂等重投。上传服务 协调器

KG08：READY、ACTIVE、SUCCEEDED 有什么不同？

可口述回答： READY 属于修订摄取状态，说明内容已完成规定处理；ACTIVE 属于修订生命周期，说明它在版本体系里处于当前有效位置；SUCCEEDED 属于 IngestionJob，说明这次任务成功收敛。一个历史修订可以 READY 且 RETIRED，不能因此说它处理失败。

项目落点与追问： 页面和后台恢复应读取正确对象的状态，而不是把字符串都映射成同一个“成功”。失败、重试与历史查询也必须保留这几个维度。当前最终激活逻辑按最高修订号的 READY 版本选择，而不是按 Worker 完成的先后抢占。模型 完成逻辑

KG09：怎样保证任务重试不会无限执行？

可口述回答： 次数上限必须在实际领取时生效，而不能只靠旁路扫描。当前条件 UPDATE 同时检查可领取状态、租约和 attempt_count 未超限，成功后原子加一。耗尽且已经可重新领取的任务才会失败化；最后一次合法执行的有效租约不能被另一条重复消息终止。

项目落点与追问： attempt_count 代表任务领取次数，不是所有底层模型物理请求的总和。模型重试、任务重试、用户手动重试可能有不同预算，必须分别定义。只说“Celery 配了三次重试”不足以解释任务状态机的所有入口。领取状态机

KG10：Worker 失去租约后，你如何阻止它继续写入？

可口述回答： 一方面在解析、编码和写索引边界重新确认 Job、token 与过期时间，失租时停止后续步骤；另一方面最终数据库状态转移也必须验证持有者。本项目新增 ClaimGuard，把续租失败信号传播到后续计算与批次。不能只停止心跳，却允许旧 Worker 继续提交 READY。

项目落点与追问： 已经交给远端的 upsert 可能仍完成，线程中的同步编码也未必立即停止。因此还需要稳定 point ID、不可变修订和可重放写入。租约 fencing 与远端动作取消是两回事。Worker 摄取状态机

KG11：确定性的向量 point ID 能带来 exactly-once 吗？

可口述回答： 它能让同一不可变来源重放时命中同一索引身份，减少重复点和对账歧义；不能保证物理请求只执行一次，也不能保证一批点全部成功。数据库、编码器和向量索引之间仍可能发生部分成功，需要持久进度、重试与最终完成条件配合。

项目落点与追问： 项目在索引确认后才完成摄取状态，并验证当前租约。面试时更准确的说法是“允许重复投递，使用稳定身份实现幂等效果”，而不是“用了 UUID 就 exactly-once”。还要说明换模型或换修订时身份与索引版本如何区分。Point ID Worker

KG12：只改一行，为什么不直接覆盖旧向量？

可口述回答： 旧向量对应旧修订的证据身份，直接覆盖会破坏历史快照与回答解释。当前先产生新修订和新块来源；计算层可通过精确输入缓存复用没变的向量。来源身份和计算结果是两件事，保留新来源不等于必须重复所有昂贵计算。

项目落点与追问： 缓存按工作区、模态、编码器身份和真实输入内容隔离。同义文本不一定命中，编码配置改变也不能复用。局部编辑是否引发大量重算，还取决于切块边界如何传播。缓存 快照

KG13：Embedding 缓存命中率很高，就能证明性能提升吗？

可口述回答： 只能证明一部分编码计算被复用。端到端延迟还包含解析、切块、模型加载或指纹、数据库读写、稀疏编码、索引确认等。应同时报告命中范围、编码输入数、各阶段耗时和上传到 READY 的总耗时，并说明冷启动是否计入。

项目落点与追问： 还要保证复用没有破坏来源身份或向量维度。当前缓存检查 payload 校验和、维度和数值有效性，损坏项不能直接当命中。性能优化必须在结果等价或质量门槛下成立，不能只展示一个漂亮的缓存百分比。向量缓存

KG14：为什么换行符这种小问题会影响 RAG 正确率？

可口述回答： 切块依赖段落边界。若单个 CRLF 被误当两个换行，一条规则的金额和条件可能分到不同块，后续只召回金额时就会错误放宽条件。当前修复统一逻辑换行识别与结构长度判断，同时保留回到原始修订的定位。

项目落点与追问： 要测试的不只是块数，还应比较有序块正文与关键证据跨度是否保留。规范化文本上的偏移不能随意应用到原始字节或原始字符序列。历史索引也不会因修改切块代码而自动重建。结构切块 复核报告

KG15：如何验证一次摄取修复，而不是只证明 happy path 能跑？

可口述回答： 把故障插在真实边界：提交确认丢失、队列通知失败、领取额度耗尽、编码后失租、部分索引写入、最终状态提交前中断。检查恢复后是否保留同一修订身份、不会越权提交、不会无限重试，且数据库完成状态与索引可用条件一致。

项目落点与追问： 组合外键应使用真实 PostgreSQL 测试，远端写入边界要模拟已发送但结果未知。还应区分本次执行结果和仓库历史测试记录；我阅读了一个测试文件，并不等于我已经在当前部署跑过它。迁移测试 摄取与 Worker

KG16：RAG 错误为什么要拆成检索、证据交付和回答三个阶段？

可口述回答： 因为同一错误答案可能来自不同原因。目标原文没进候选，是检索问题；候选有完整原文，但预算或投影丢掉条件，是交付问题；模型确实收到完整证据却推错结论，是回答问题。只有分层观察，才能决定改编码器、选择器、提示还是答案校验。

项目落点与追问： 应保存候选池、最终选择、实际消息和引用结果的身份链。界面展示了命中片段不代表本次模型看见了它。当前多项修复正发生在候选到消息之间，说明提高召回率不能自动解决整条链路。检索 问答

KG17：Dense、Sparse、Reranker 各自负责什么？

可口述回答： Dense 用编码后的相似性寻找候选，Sparse 根据词项信号补充精确术语、编号等匹配，Reranker 在有限候选中更细地比较问题与文本。召回层负责尽量别漏，重排负责把有限阅读名额给更有价值的证据；它们解决的问题不同。

项目落点与追问： 当前检索支持 DENSE 与混合、重排分支，具体策略应看冻结配置。重排无法找回从未进入候选池的块，当前稀疏适配器是 tokenizer 词项加 1+log(tf)，索引配合 IDF，并非学习式 sparse head。讲项目时应按真实算法回答。检索策略 稀疏适配器 索引配置

KG18：为什么融合用排名，而不是把两路原始分数直接相加？

可口述回答： 两路分数未必处在同一量纲，也不一定有相同分布。排名融合能在不假定分数可比较的前提下汇总多个排序信号。当前 RRF 按排名贡献融合，并在逻辑块身份上合并；随后再按候选预算进入下一阶段。

项目落点与追问： 排名融合并不自动最优，它会丢掉原始分数间隔信息。参数和候选截断都要通过固定任务验证。也不能把 RRF 得分当作“这段证据有 90% 概率正确”，更不能把 reranker 阈值套到 RRF 分数上。融合与阈值处理

KG19：Top K 越大，效果一定越好吗？

可口述回答： 更大候选池可能补回遗漏，也会增加重排成本、无关证据和最终上下文竞争。需要分别区分每路召回 K、融合候选 K、重排输入 K 和最终证据 K。只扩大最终 K，可能让冲突或重复片段挤掉关键条件，甚至使模型更难判断。

项目落点与追问： 当前知识问答的默认 profile 是 30/30 路召回、20 候选、最多 6 段，但其他入口可有不同配置。它是当前默认，不是所有任务的最优常数。比较时应同时看完整证据覆盖、答案支持率、延迟和费用。问答 profile

KG20：为什么相同块重复命中也会造成质量问题？

可口述回答： 如果候选 Top K 按命中条目而不是逻辑块计数，一个块重复出现就会占掉其他证据的名额。它不仅是展示不好看，还可能让必要的第二段条件根本没有机会进入重排。当前 DENSE 路径按逻辑块保留首个有效排名与分数后再限制候选数。

项目落点与追问： 去重不能只按文档 ID，否则同一文档中互补的不同块也会被删掉。应使用正确粒度的不可变块身份，并明确保留哪个排名与来源映射。身份去重、范围覆盖和语义去重不能混成一个 set 操作。候选去重

KG21：为什么“先去重，再裁预算”会误删有效证据？

可口述回答： 一个大块可能先把其内部短块判成重复，随后自己因为太大被预算淘汰，结果两者都没交给模型。当前改为只有实际接纳的证据才能登记覆盖，大块没进预算时，后面的小块仍可被选择。数量、预算与覆盖必须共同决定准入。

项目落点与追问： 这仍是按排名贪心，不保证全局最优组合。若改成更复杂的组合优化，需要验证它是否真的保留完整支持集，而不是只提高字节利用率。最直接的回归用例就是“高排名大块放不下，低排名短尾块包含必要条件”。证据接纳

KG22：如何判断两个片段的来源范围重叠？

可口述回答： 先确认同一不可变修订，再确认同一定位类型和局部坐标域，最后比较范围。第一页的 0–100 与第二页的 0–100 不可直接比较；行号与字符偏移也不是同一量纲。当前逻辑把页、段、块、表格行等信息纳入作用域，无法比较时不武断删除。

项目落点与追问： 部分重叠不等于完整重复，滑窗尾部可能有新例外条款。本项目只让已交付范围完全包含的后续范围被抑制。若追问文本哈希，它只能证明正文相同，不能完全说明出处和版本语义相同。定位与覆盖

KG23：为什么不直接把每块截到固定 500 字？

可口述回答： 截断可能把否定、例外、生效范围或计量单位放在尾部的内容去掉，形成看似有来源的错误依据。当前选择优先接纳完整块，放不下则继续考虑较小候选。这样来源更容易核验，但可能牺牲预算利用率，需要通过切块设计改善。

项目落点与追问： 如果确实要做句级或跨度级提取，应保存被保留跨度与原文坐标，并证明必要条件没有丢掉。不能把模型生成摘要当作原文片段，再给它贴上旧块 ID。证据的粒度改变需要新的可追溯合同。完整块选择 证据计划

KG24：context_budget_bytes 和模型 token 窗口是不是一回事？

可口述回答： 不是。前者约束指定记录列表或 compact 模型视图的 UTF-8 字节，不统一约束完整工具 envelope；模型窗口按其分词规则计 token；项目还使用近似 token 估计控制正文和完整请求。中文、英文、JSON 元数据和引用编号都有不同开销，不能简单把一字节当一个 token。

项目落点与追问： 预算要覆盖最终真实表示，包括系统提示、问题、工具 schema、模型可见引用说明和输出预留；私有来源注册表不在模型视图内。当前近似估计不是所有供应商精确计量的替代，应通过实发载荷和回执校准。变量名仍含 chars 的历史兼容字段也不能据名字猜单位。问答预算 序列化预算

KG25：多个检索源各自在预算内，为什么归并后还要再裁一次？

可口述回答： 局部约束不推出整体约束。两个源的证据列表各返回 2000 字节，合起来可能超过归并记录列表的 2500 字节预算。当前多快照搜索在配置预算时对归并池执行共享选择，还保持记录与快照引用一一配对，防止文本去重后来源重复回流。

项目落点与追问： 普通和 compact 表示的真实开销不同，要按实际交付对象计量。不能只把每路 K 除以源数，因为块大小不等且相关性不同。这类问题也会出现在多数据库搜索、多个工具结果合并和多 Agent 汇总中。多快照合并

KG26：一条回答有引用，为什么仍然可能是幻觉？

可口述回答： 引用存在只证明能找到某个来源，不证明来源支持紧邻结论。原文“过夜差旅上限 400”不能支持“所有出差都能报销 400”。需要分别检查引用身份、原文精确性、条件完整性和结论是否被支持。结构正确是可审查基础，不是语义正确的终点。

项目落点与追问： 本项目程序维护编号到快照、修订、块和定位的映射，避免让模型自行决定权威来源身份。逐结论语义支持仍需标注或评测。不能用“引用率 100%”替代“正确引用支持率”。证据计划 输出校验

KG27：answer 中的引用标记与 citation_ids 数组为什么都要校验？

可口述回答： 两个通道可能不一致：数组写 [1]，正文却出现 [99]；如果只校验数组，错误来源就被漏掉。当前要求编号属于实际可见集合，正文标记与数组一致，并检查拒答状态是否允许引用。来源检查应在规范化之前，不能先删掉未知引用再放行。

项目落点与追问： 数字数组、数学区间和代码又可能长得像引用，因此需要明确输出合同和反例测试。解析规则不等于完整自然语言理解；不同合同分支的规则也不能混用成一个口号。答案解析 回归用例

KG28：为什么“没有退货数，但有生产和销售数”应该判拒答？

可口述回答： 用户要的是退货数量，其他真实数字不能替代目标度量。答案有数字、有引用，只能说明它谈到了相关表格，不证明它回答了目标问题。当前有限规则识别完整单计数拒答，并确认附带总结只涉及其他度量，再统一拒答状态。

项目落点与追问： 零值、上下界、部分答案和复合问题不能随意折叠成拒答。规则要窄到能解释触发条件，并配对不会误伤的反例。历史一题被修复不能宣称模型整体计数能力提升，因为可能只是本地解析回放结果改变。拒答规则

KG29：如何评测需要两段证据才能回答的问题？

可口述回答： 应标注最小完整支持集，而不只标“任意相关文档”。比如金额段和适用条件段缺一不可，要分别检查候选召回是否齐全、实际消息是否同时交付、回答是否保留两者的约束。只命中金额段不能算完整成功。

项目落点与追问： 多个等价支持集可以分别记录，避免把一种正确检索路径误判为错。也要留意同一文档标题相同却修订不同。当前工程修复能减少预算误删，但是否找到完整支持集仍是需要独立质量数据证明的事情。检索与交付 复核范围

KG30：回放历史模型回复，能证明新版本回答能力提高了吗？

可口述回答： 它能证明新解析器、选择器或映射逻辑对相同输入如何变化，适合定位确定性改动与回归；不能测新的模型采样、编码召回或供应商稳定性。本项目复核明确把固定候选回放、原始回复解析和真实入库链路分开记录。

项目落点与追问： 要声称端到端提高，需要固定新旧配置、同一任务分布、有限预算和独立样本，重新测完整链路。历史题已被反复观察时，还要标明它是开发或回归集，不能偷偷当作未见 holdout。复核报告

KG31：Reranker 分数能直接当作回答可信度吗？

可口述回答： 不能。它主要用于特定模型、特定输入分布下的排序，未必校准成概率；高分也不证明证据条件完整，更不证明答案推理正确。阈值要在有标签的任务上评估误收与误拒，并与召回和最终支持率一起看。

项目落点与追问： 当前代码只在存在重排分数的地方应用相应阈值，不把 RRF 排名统计当同一量纲。换模型、文本长度或语言分布后，旧阈值可能失效。若需要概率解释，必须另外做校准和验证，不能把 0.8 口述成“80% 正确”。重排阈值

KG32：文档更新后，为何旧快照仍可能检索旧内容？

可口述回答： 固定快照的意义就是记录一次明确的来源集合。新修订出现不应偷偷改变旧快照，否则评测和已发布 Agent 的行为无法解释。需要新内容的业务应明确选择新快照或相应最新绑定语义，而历史回放继续使用原来版本。

项目落点与追问： 最新性和可重现性是不同目标，应由调用合同决定。来源撤销、物理删除和普通版本退休又不同，不能笼统地认为“旧内容永远可用”。诊断时先确认查询绑定，再决定是不是索引更新失败。快照 Wiki 来源约束

KG33：Memory、对话历史和知识库有什么区别？

可口述回答： 对话历史记录发生过的交互，Memory 选择少量跨轮仍有用的偏好、约束或决定，知识库保存可版本化的外部资料。它们不是三份同样的文本缓存。临时报错可留在历史，稳定输出偏好适合 Memory，制度条款适合从原文 RAG 获取。

项目落点与追问： 三者进入模型前都要经过权限与预算，但来源、更新和失效方式不同。把整个对话总结都塞进长期记忆，会把临时状态和助手猜测带到未来任务；把制度当用户偏好也会削弱来源与生效时间管理。Memory 合同 抽取规则

KG34：当前新建 Agent 的 Memory 默认是怎样的？

可口述回答： 当前新建草稿未提供 memory 配置时默认开启长期记忆，启用且未指定 scope 时默认 USER；显式关闭会保留。旧讲解中默认关闭属于旧基线，不能继续用于解释今天所有新 Agent。已有草稿更新和已发布冻结版本也不能被默认值静默重写。

项目落点与追问： USER 表示按运行创建者选择私有分区，并不等于整个 Thread、Run 或 Artifact 自动私有。面试回答默认行为时必须带版本和适用条件，尤其区分新建默认、迁移策略与运行时读取。草稿配置 Memory 分区

KG35：为什么 Memory 检索必须把 owner_user_id 带到底层？

可口述回答： 权限范围不能只在页面或提示词上表达。选择器必须在实际数据查询里限制工作区、Agent 和 owner，否则后置过滤很容易遗漏或把不该见到的内容送入模型。当前 Store 对 owner 精确匹配，私有分区不会自动合并全部共享与他人条目。

项目落点与追问： 如果将来接向量索引，同样要在授权范围内召回并在权威数据层复核身份，不能先全局搜再期待模型自觉忽略。管理接口能显示的集合与运行时注入集合也有不同合同。Store 选择 管理服务

KG36：Memory 还没有向量检索，是技术落后吗？

可口述回答： 要看规模和错误类型。当前词项、显著性与时间排序简单可解释，对少量稳定记忆有实际价值；它会漏同义改写和跨语言表达，但向量召回也可能把语义相近、条件相反的约束注入。是否升级应由任务标注和性能数据决定。

项目落点与追问： 可以在 MemorySelector 合同下做语义候选实验，保持权限过滤、稳定 ID、内容哈希、预算和冻结不变。先比较该注入与不该注入样本，再决定默认策略。存储产品换成向量库，不会自动解决写入忠实性和冲突更新。选择器 合同

KG37：lexical_overlap_v1 过滤器提高了什么，又可能损失什么？

可口述回答： 它过滤掉候选中与查询没有词项重叠的记忆，有助于减少旧路径按显著性或时间带入的无关条目；但同义、跨语言或省略表达也可能没有词面重叠，因此召回会受影响。它只是后选择过滤，不是新建语义检索，也不改变持久化和历史回放。

项目落点与追问： 因为只过滤已经返回的候选，它无法找回候选阶段没选中的记忆。不能只看剩余条目更少，就断言整体回答更好；应看误注入、漏注入和最终约束执行率。选择策略

KG38：有用户原话 evidence，是否能保证提炼出来的 Memory 正确？

可口述回答： 只能证明引文确实出现过，不能证明提炼完整保留条件。“这周演示时尽量短一点”可能被错误扩大为“永远必须短回答”，引文合法但记忆语义不忠实。写入评测应标注时间、对象、条件和语气强度，区分出处合法与内容受支持。

项目落点与追问： 当前抽取解析要求非空精确原话，持久化再做长度、类型、去重等门槛。未来若加忠实性检查，要用独立样本测误收和误拒，不能仅让同一个模型自评就宣布正确。抽取 写入

KG39：为什么抽取 Memory 时不把助手回答一起当事实来源？

可口述回答： 助手回答可能包含错误推断。把它再写成长期记忆，会形成“模型误答—保存为事实—未来继续引用”的自我强化。当前抽取请求只发送用户输入，兼容 DTO 中的 final_output 不会被加入抽取消息，原话证据也要来自用户文本。

项目落点与追问： 用户输入本身也可能临时、含糊或不适合长期保存，所以只取用户并不是全部质量保证。仍要判断是否稳定、是否明确断言以及是否存在敏感内容政策。抽取为空经常是正确结果，而不是失败。抽取请求

KG40：如何防止重复投递把 Memory 的 salience 加多次？

可口述回答： 要区分同一业务表达的重试和不同表达的新确认。项目用内容哈希识别同一文本，再以 source Run 的 MemoryContribution 记录一次贡献，配合事务锁和唯一约束避免并发重复强化。同一 Run 重投递不会被当成用户又强调一次。

项目落点与追问： 内容哈希只解决“说了什么”，事件身份解决“哪次真实表达”，两个维度都要有。若只是对 content 做 upsert 并无条件 salience+1，基础设施抖动就会污染后续排名。record 与贡献去重 贡献模型

KG41：为什么 Memory 的共享与私有唯一约束需要仔细处理？

可口述回答： 共享 owner 为空，私有 owner 非空，唯一性必须同时表达作用域和状态。当前模型为 ACTIVE 共享记忆和 ACTIVE 私有记忆分别建立条件唯一索引，避免同一范围中重复活动哈希，又允许历史状态保留。不能只凭应用先查后插，因为并发可同时看到不存在。

项目落点与追问： 数据库唯一约束是最终竞争仲裁，代码用保存点处理单个候选竞争，避免整批有效记忆一起回滚。解释时要说明数据库对 NULL 的唯一语义和索引条件，而不是泛称“加个 unique 就好”。Memory 索引 并发写入

KG42：新记忆与旧记忆矛盾，直接取最新可以吗？

可口述回答： 只有确认同一对象、同一属性、同一适用条件时，时间才可能帮助判断替代。“实验服务可用 3.12”并不推翻“生产必须 3.11”。当前有 SUPERSEDED 和替代关系等结构，但不能据此宣称已经实现自动语义冲突解决。

项目落点与追问： 可把演进分为对象条件识别、补充与替代分类、写入替代链三步，每步都有反例与来源。相似度高不能直接触发删除，因为相似文本可能刚好相互否定，需要一起呈现。状态模型 状态方法

KG43：Memory 是否支持过期？完整 TTL 还缺哪些设计？

可口述回答： 当前已有 expires_at，普通选择会排除到期条目，所以说完全不支持过期不准确。但完整 TTL 还要定义谁设定时间、何时续期、过期后只停止注入还是物理删除、用户怎么查看，以及历史 Run 如何解释。

项目落点与追问： 一次被召回不等于事实再次被用户确认，不能随意以读取延长寿命。到期策略应覆盖临时约束被永久化与稳定偏好被过早删除两类错误。字段存在只是基础能力，产品语义和验证仍需补齐。过期字段 选择过滤

KG44：记忆被失效后，为什么旧 Run 还能重读它？

可口述回答： 新任务应按当前状态选记忆；旧 Run 回放则要解释当时模型实际看到了什么。当前冻结加载会按旧 ID、顺序与哈希重建，即使条目后来失效或被替代，也不能悄悄篡改过去的上下文。否则事故复盘会丢失原因。

项目落点与追问： 这与彻底隐私删除是不同合同。若承诺删除内容，就需要说明历史快照保留身份还是正文、哪些回放会失败，以及审计权限。不能让一个 invalidate 动作同时被宣传成“未来不用”与“所有历史彻底擦除”。load 的历史语义

KG45：Memory 快照为什么同时保存 ID 和 content hash？

可口述回答： ID 确定是哪条记录，保存的内容哈希用来核对与冻结值是否一致。只存 ID，正常更新正文与哈希后，旧 Run 仍可能读到新内容。当前带哈希快照检查缺失、重复、集合及保存哈希是否匹配，兼容旧 ID-only 的路径有不同保证。

项目落点与追问： 哈希不是加密或授权，也不能证明内容真实。load 未现场重算正文，因此不保证发现直接改正文却保留旧哈希的篡改。当前哈希还折叠空白与大小写，不是任意语义等价判断。冻结加载 哈希合同

KG46：如果让你证明向量 Memory 比现有词项选择更好，你会怎么做？

可口述回答： 冻结初始记忆、用户范围、查询和预期注入集，覆盖同义、跨语言、无关问题、相反条件、新旧替代与历史回放。分别测漏注入、误注入、条件执行、延迟与费用，再看最终任务是否改善。不能只用相似度或召回条数证明价值。

项目落点与追问： 保持 MemorySelector 输出身份和冻结机制不变，先在实验配置下比较。评测过程中还要防止候选误召回写回成新记忆，污染后续样本。它是建议实验，当前源码仍以词项等信号选择。选择器合同 当前基线

KG47：已经有 RAG，为什么还要 Wiki？

可口述回答： RAG 每次从原文找证据，Wiki 预先把固定来源整理成主题、主张和关系，适合重复概览与跨文档导航。它用一次编译成本换后续复用，但也带来抽取错误、遗漏、更新滞后和发布维护。应由真实查询模式决定是否值得。

项目落点与追问： 本项目 Wiki 保留原句和来源身份，并能按查询需求补充原文。它不是替代所有 RAG，更不是知识真理层。若用户只偶尔查一个条款，增加编译管线可能得不偿失。编译 查询路由

KG48：Wiki 为什么没有使用专业图数据库？

可口述回答： 当前主要需求是按知识库和发布版本读取页面、验证来源、保存主张与关系，以及用事务安装整套产物。PostgreSQL 已经能承载这些数据和权限关系。是否引入图数据库，应由大量多跳遍历、路径约束和关系查询瓶颈证明。

项目落点与追问： 有 relations 字段不代表必须上图数据库；换存储也不会修复主张提炼错误或条件丢失。应先看访问模式、规模、约束与运维成本，再比较方案。当前页面、抽取缓存和撤销都在明确的关系模型中。Wiki 模型

KG49：Wiki 编译器怎样防止模型伪造来源？

可口述回答： 模型按单个源块提议结构化主张，程序要求 chunk_id 就是当前块，quote 必须是该块精确非空子串；保存前服务再验证，并由真实记录补齐文档、修订与定位。权威身份由程序掌握，不能让模型随意填一个看起来合法的 UUID。

项目落点与追问： 这些保证来源合法，不完全保证主张忠实。条件遗漏或过度概括仍需语义评测。编译请求把原文作为不可信数据且不开放工具，也有助于限制文档内容把加工流程引向外部动作。编译器 保存边界

KG50：Wiki 中两条主张的 value 不同，就一定冲突吗？

可口述回答： 还要比较对象、属性、时间和适用条件。国内门槛 5000、海外门槛 3000 可以同时成立；同一条件同一生效期的不同值才更像冲突。当前有基本分组、模型关系审查和编辑者声明，但不能说已解决所有实体消歧与时间逻辑。

项目落点与追问： 模型审查只能把既有合法证据组成冲突组，不能凭空增加主张。保留冲突标记与两边原文，比为了输出一个确定值而静默选一边更可审查。最终是否采纳还需业务规则。组织与冲突审查

KG51：一次 Wiki 编译要冻结哪些东西？

可口述回答： 至少冻结来源快照及哈希、编译器版本和 manifest、模型执行计划、输出方式与相关审查配置。最终页面还有内容哈希。这些分别回答“输入是什么”“怎样处理”“产物是否变化”，才能解释两次编译差异并复用相同身份。

项目落点与追问： 仅记录模型名字和时间不够，提示词、路由或输出合同变化也可能影响产物。哈希保证身份与完整性，不证明事实正确，也不保证外部供应商在不同时间完全确定性。编译身份 manifest

KG52：Wiki 的增量编译目前做到什么粒度？

可口述回答： 当前按修订与编译规格缓存抽取结果，输入哈希验证不可变来源。新快照仍含相同旧修订时可复用；只改一行产生新修订时，不能声称已经自动只重抽这一行。全局冲突审查和页面组织也可能受新主张影响。

项目落点与追问： 这是修订级抽取复用，与按文本输入复用 Embedding 不同。更细 Chunk 缓存或依赖图是可评估方向，应先测变更率、编译成本和维护复杂度。说“完全没有增量”与“已经最小重算”都不准确。缓存模型 执行流程

KG53：为什么 Wiki 页面生成还要做文本转义？

可口述回答： 模型输出和来源文本都不应直接变成可执行 HTML 或任意链接。当前页面组织将派生内容按字面文本转义，再生成摘录与来源展示，减少文档或模型内容改变页面行为的机会。内容处理的信任边界不仅在模型调用处，也延伸到前端渲染。

项目落点与追问： 转义不是来源真实性检查，也不替代 API 授权。应分别验证数据来自哪里、用户有没有权限看、渲染器如何解释它。若未来增加富文本或可点击关系，需要重新定义允许的结构，不能简单去掉全部转义。页面组织

KG54：为什么 Wiki 生成完成后先是 READY，而不是直接 PUBLISHED？

可口述回答： READY 表示一整套编译产物已一致安装，PUBLISHED 表示通过发布时的来源与检查合同。当前最终事务验证租约、写页面、算哈希并改 READY；发布再检查当前来源与 lint。加工完成和允许对外使用是不同责任。

项目落点与追问： 不能把部分生成的页面提前当成完整版本，也不能因为 Worker 成功就跳过发布检查。类似分层适用于模型配置、Agent 版本和评测定义。发布成功仍不意味着语义正确率 100%，要看门槛实际覆盖什么。完成与发布

KG55：Wiki lint 有警告，为什么仍可能发布？

可口述回答： error 与 warning 承担不同语义。来源非法、内容哈希不符等会破坏可用合同，应阻止发布；可能冲突等警告可以随产物保留，让用户看到不确定性。把所有警告都当错误可能让有价值的争议资料无法使用，全部忽略又会隐藏风险。

项目落点与追问： 当前发布检查会阻断 error；因此不能说 PUBLISHED 证明不存在冲突。面试时应具体举一个阻断项和一个允许保留的警告，再说明最终回答如何处理带冲突的证据。lint 与 publish

KG56：Wiki 过期与来源撤销有什么区别？

可口述回答： 过期通常指原文集合已更新，旧产物不再代表当前来源；历史固定版本仍可能有审计价值。来源撤销表示某修订不应继续用于 Wiki，当前有独立持久撤销表。旧编译若仍包含后来撤销且未排除的来源，会被拒绝，不能靠关闭 current 检查绕过。

项目落点与追问： 物理删除又是第三件事，涉及 Blob、快照、历史回答和保留承诺。撤销一条来源不能通过静默删句且保留旧哈希实现，否则产物身份失真。全系统删除要另列传播关系。撤销模型 来源验证

KG57：当前 Wiki 页面是怎么匹配问题的，有什么限制？

可口述回答： 当前主要依据标题做规范化和词项匹配，包含中文双字片段等规则，并补充部分冲突邻居。它容易解释，但可能漏同义标题、正文才有的细节和跨语言表达。标题相近也不保证主张条件适合用户问题。

项目落点与追问： 如果增加正文或语义候选，应冻结来源与编译版本，分别测漏召回、误召回和最终答案支持。不能用“命中页面更多”证明效果变好；错误页面可能反而把原文检索挤出预算。Wiki 匹配

KG58：AUTO 模式为什么有时还要回到原文 RAG？

可口述回答： 概览页面不一定覆盖事实细节或复杂综合问题。当前 AUTO 在事实或综合意图、没有合格 Wiki 证据、或存在冲突时需要原文补充；HYBRID 和 RAG 也有明确原文需求。缺少有效补充时应报告不足，不能仅因存在一个页面就强行回答。

项目落点与追问： 路由需要可解释：为什么选 Wiki、为什么补原文、哪项条件触发。路由标签不是质量证明，最终仍要检查证据真正交付和答案支持。当前这些分支也不等于一个自学习的最优路由器。路由实现

KG59：为什么 query_wiki 的 insufficient_evidence 不能当作事实判定器？

可口述回答： 查询层主要知道有没有合法来源、是否缺少必需补充、有没有已知冲突；它不能仅凭这些结构条件证明原文语义回答了问题。即使字段为 false，仍可能主题匹配错误或必要条件缺失。它反映结构性证据可用性，而非逻辑蕴含证明。

项目落点与追问： 要评价实际答案，需要逐结论支持、条件完整性和正确拒答样本。把一个结构标志直接当回答正确率，会把检索、交付和生成错误混在一起。项目函数说明明确保留这一边界。query_wiki 合同

KG60：如果只能独立完成一个知识域改进，你会选什么，怎样证明价值？

可口述回答： 我会先选一个边界清晰、能用固定样本验证的缺陷或可观测性改进，例如为 Wiki 标题匹配增加可解释候选记录，或为 Memory 建立条件保真与误注入评测。先写输入、授权范围、预期与不变量，再确定代码位置，保持其他环节不变做配对比较。

项目落点与追问： 我会交付修改原因、实现路径、实际执行的结果和未覆盖范围，不把旧报告数字当自己的测试结果。RG15、RT08、RT09 等已修项目可作为学习案例，不能再当当前待实现任务。选择新需求前应再次核验 main，并确认它解决的是用户问题。工程取舍记录
