面试问答 C：文档摄取、检索证据、Memory 与 Wiki（KG01–KG60）

KG01—KG60：文档摄取、检索证据、Memory 与 Wiki

KG01：为什么要把 Document 和 DocumentRevision 分成两张表？

回答：Document 表示一份业务文件的稳定身份，包含工作区、知识库和名称等管理属性；DocumentRevision 表示一次上传的具体内容版本，拥有自己的 Blob、内容哈希、摄取状态和版本号。修改退款政策时创建 V2，V1 仍可被历史 KnowledgeSnapshot 引用，旧回答也能追到当时的原文。新版本必须完成解析和索引后才成为 ACTIVE，失败时原 READY 版本继续服务。

追问：直接覆盖原文件内容最容易损坏哪些功能？

追问回答：历史引用会指向被改写的文本，Run 的有效知识身份失真；摄取中途失败还可能把唯一可用索引破坏。Revision 分层使内容不可变、摄取状态独立、跨版本比较和故障恢复都有明确对象。

源码定位： models.py · snapshots.py

KG02：既然已经有 revision_id，Chunk 为什么还保存 document_id？

回答：document_revision_id 表示 Chunk 来自哪次上传，document_id 便于直接按业务文档分组、查询、去重和历史追踪；workspace_id 与 knowledge_base_id 进一步确定多租户范围。保留这些列时，AgentHub 用复合外键保证它们属于同一条 DocumentRevision，而不是放任应用层传任意组合。这样检索出的 Chunk 可以直接关联文档名称、生命周期和来源修订。

追问：这是不是违背数据库规范化？

追问回答：这是受约束的冗余。查询路径常按文档聚合 Chunk，同时需要快速限定知识库；冗余字段用于性能和操作便利，复合外键负责维持一致性。只要关系受到数据库强约束，就能兼顾读取效率和数据完整性。

源码定位： models.py

KG03：两个外键分别存在，为什么不够保证关系正确？

回答：两个单独外键只能确认 Document D2 存在、Revision V1 存在，不能确认 V1 属于 D2。AgentHub 的 0061_chunk_document_revision 迁移增加 (workspace_id,knowledge_base_id,document_id,document_revision_id) 的复合引用，父表上对应列组必须具备唯一性。这样 Chunk 所声明的 Workspace、KB、Document 和 Revision 必须是数据库认可的一组归属。

追问：怎样用最小数据复现旧约束的漏洞？

追问回答：创建同一知识库下 D1/V1 和 D2/V2，插入 document_id=D2, revision_id=V1 的 Chunk。分别存在的普通外键可以接受它，复合外键应拒绝；再验证正常 D1/V1 的 Chunk 能插入。迁移测试覆盖这一正反样本。

源码定位： models.py

KG04：给已有表增加外键时，遇到历史脏数据怎么办？

回答：加外键前先查询不符合新归属关系的历史 Chunk，按 workspace、document 和 revision 分组输出数量与样例。对能依据不可变原始上传记录确定归属的行可做受控修正；无法判定来源的行应单独隔离或阻断迁移，避免凭猜测改写证据。0061 先检查错配再建立约束，保证升级失败能准确指出数据问题，而不是留下一套半可信的引用链。

追问：迁移扫描结果有 100 条错配，能直接把 document_id 改成父 Revision 的值吗？

追问回答：先确认 Chunk 文本、Locator、Blob 与该 Revision 真实匹配；有些错误可能是 revision_id 写错，而不是 document_id。修复脚本应保留审计前镜像、受影响主键和校验 Hash，重新检验后再加约束。

源码定位： models.py

KG05：并发生成同一文档的修订号，你会怎么做？

回答：同一 Document 的新 Revision 通常使用递增 version_number。两个上传同时读取最大版本号时可能都计算 V3，因此必须在短事务中对 Document 或对应版本分配对象加锁，并用 (document_id,version_number) 唯一约束做最终仲裁。Blob 保存可先形成独立上传身份，数据库再将内容绑定具体 Revision；失败的冲突请求返回可重试或明确错误，不产生两个同号版本。

追问：为什么只用数据库唯一索引可能导致糟糕的用户体验？

追问回答：唯一索引确保最终不会重号，但两个上传中有一个可能在解析和存储之后才遇到冲突。短事务内先锁定文档并分配版本号，可以更早协调并发；仍要对唯一冲突做 rollback 和稳定业务提示。

源码定位： services.py

KG06：文件上传为什么不能放进一个普通数据库事务里一起回滚？

回答：上传文件会写文件系统或 Blob Storage，元数据写 PostgreSQL，Celery 又负责异步处理；数据库事务只能控制自身的表写入。若 Blob 写完但 Revision 插入失败，需要删除孤儿文件；若事务提交后队列投递失败，Job 可以由对账恢复。AgentHub 用内容 Hash、Blob 路径、Revision/Job 状态及补偿流程建立跨组件一致性，而不是让一个 SQL COMMIT 覆盖文件系统与消息队列。

追问：文件已保存但数据库事务失败，如何清理？

追问回答：在上传服务中记录本次 Blob 身份，事务失败后执行幂等清理；对进程崩溃遗留的孤儿文件，定期按持久引用表与保留时间扫描。清理前要确认没有其他修订引用同一 Blob，避免共享内容被误删。

源码定位： services.py · ingestion.py

KG07：数据库提交成功，但发队列失败，怎么办？

回答：Revision 和 IngestionJob 在 PostgreSQL 提交后，Celery 投递可能失败或 API 崩溃。Job 状态是长期事实，队列消息只是调度信号；周期 Reconciler 查找应开始而未有效领取的 Job，按 next_attempt_at、attempt_count 和租约条件重新入队。重复消息进入 Worker 后由原子 Claim 控制实际执行权，避免两次编码同一 Revision。

追问：如果队列其实已经收到消息，只是 API 没收到确认呢？

追问回答：补投仍使用相同 Job ID；两个 Worker 竞争时，只有一个能满足 PENDING、重试时间与租约条件并更新 Token。这个设计允许重复交付，用数据库状态协调唯一有效处理者。

源码定位： ingestion.py

KG08：READY、ACTIVE、SUCCEEDED 有什么不同？

回答：IngestionJob.status=SUCCEEDED 表示某次后台摄取任务完成；DocumentRevision.ingestion_status=READY 表示该版本已经完成解析与索引；lifecycle_status=ACTIVE 表示它是当前业务文档被选用的有效修订。一个历史 Revision 可以是 READY 但 RETIRED，旧快照仍能引用；Job 可以进入 INDEXING 阶段而未成功。把三层状态分开才能处理新旧版本和异步过程。

追问：新 V3 摄取失败，V2 会怎样？

追问回答：V3 的 Job/Revision 记录失败原因，V2 继续保持可用的 READY/ACTIVE，当前 Snapshot 仍选择 V2。等 V3 成功并通过最终租约校验，才由服务选择最高 READY 版本作为 ACTIVE。

源码定位： models.py · snapshots.py

KG09：怎样保证任务重试不会无限执行？

回答：AgentHub 把 knowledge_ingestion_max_attempts 写进 Job 原子领取的 UPDATE 条件，且只在成功 Claim 时增加 attempt_count。失败后按 RetryPolicy 计算下次可领取时间；重复 Celery 消息不能额外消耗次数。达到上限时，要结合最后一次租约是否仍活跃判断是否进入终态，避免正在进行的合法最后一次执行被维护任务误判为失败。

追问：上限为 3，两个 Worker 同时抢第三次会发生什么？

追问回答：数据库对符合条件的 UPDATE 做原子仲裁，只有一个 Worker 成功把 attempt_count 从 2 变成 3 并取得新的 lease_token；另一个读到条件已变化，不再开始耗时处理。测试应验证最终次数为 3 且 Provider 只启动一次第三轮。

源码定位： ingestion.py

KG10：Worker 失去租约后，你如何阻止它继续写入？

回答：Worker 每次 Claim 获取新的 lease_token 和到期时间，并在解析、分块、编码、索引等阶段边界检查租约；最终 finalize_ingestion_ready() 要再次确认 Token、阶段和状态。若旧 Worker A 失租后 B 已领取，A 无权提交 READY，也不应继续启动下一批计算。Qdrant 中已发起的写入采用确定性 Point ID，最终是否对外可见由数据库的 READY/ACTIVE 与快照成员控制。

追问：失租时已经发出的 Embedding 请求会怎样？

追问回答：底层网络调用可能自行完成，因此处理逻辑在返回后再次检查所有权，丢弃失租结果、不推进后续批次。真正状态确认由新的合法 owner 执行；重试可利用缓存与固定 Point ID 减少重复成本。

源码定位： ingestion.py

KG11：确定性的向量 point ID 能带来 exactly-once 吗？

回答：Point ID 由 Chunk 身份确定性派生，同一 Revision 的重试 upsert 会更新同一 Point，而不是无限增加重复向量。它解决索引写入的地址稳定性和部分幂等性，但数据库状态、Qdrant 网络回执和多 Worker 的顺序仍由租约与最终确认处理。若更换 Revision，Chunk ID 不同，新旧版本向量可以共存供历史 Snapshot 选择。

追问：两个 Worker 向同一 Point 写不同向量时如何治理？

追问回答：向量身份必须包含 Revision 与编码器兼容合同，避免混用不同模型编码；Worker 在写前后检查租约，并在完成阶段核验索引。需要更强隔离时可引入索引代次、独立 Collection 或双索引切换，再由 READY 绑定确定有效版本。

源码定位： chunking.py

KG12：只改一行，为什么不直接覆盖旧向量？

回答：新 Revision 是新来源身份，即使只修改一行，也要保持旧 Revision 的 Chunk/Point 用于历史快照和追溯。直接覆盖旧向量会让过去引用的 Chunk 文本与当前向量不匹配。AgentHub 在分块时用 Revision、序号和规范化文本 Hash 构造 Chunk ID；跨修订相同文本则通过 Embedding 缓存复用计算结果。这样来源隔离与计算复用分开实现。

追问：为什么修改一行也可能导致很多块重新编码？

追问回答：固定窗口分块依赖字符位置，插入一行可能改变后续窗口边界；结构分块可在段落等稳定边界减少影响。应该按具体 Chunking Strategy 计算新旧块的内容哈希集合，再统计真正变化的编码输入，而不是按修改字符数估算。

源码定位： chunking.py · vector_cache.py

KG13：Embedding 缓存命中率很高，就能证明性能提升吗？

回答：缓存命中率只反映编码计算的复用情况，整体摄取还包含上传、解析、分块、数据库读写、Qdrant upsert 和 Worker 启动。AgentHub 的向量缓存按 Workspace、编码模态、encoder fingerprint 和输入 Hash 定位，命中后仍需要为新 Revision 创建新 Chunk 和 Point。评测应同时看编码输入数、总时间 P50/P95、DB/Qdrant 时间和额外缓存开销；固定窗口少量修改时缓存查找也可能得不偿失。

追问：怎样比较缓存开关的真实收益？

追问回答：在同一硬件与文档版本上分别跑缓存关/开，记录 warm/cold 条件、实际编码条目数、Cache hit、总用时和错误率；按 fixed/structural/adaptive 分组，避免把块数量不同导致的收益都算给缓存。

源码定位： vector_cache.py

KG14：为什么换行符这种小问题会影响 RAG 正确率？

回答：Windows 文本常用 CRLF，部分解析器还会遇到单独 CR。若分块或段落识别只按 \n 判断， 可能进入正文，破坏段落边界、文本哈希和相邻 Chunk 结构，使检索到的片段包含错误换行或丢失上下文。AgentHub 的段落解析和证据抽取要以一致的换行规范化处理输入，同时保持 Locator 能回溯到原始文档位置。

追问：修复换行符后怎样验证 RAG 效果？

追问回答：准备内容相同但采用 LF、CRLF 和 CR 的三份夹具，对比 ParsedBlock、Chunk 边界、字符范围和检索证据；再用包含跨段否定条件的问题检查答案和引用。既测解析纯函数，也测实际摄取→索引→检索路径。

源码定位： chunking.py

KG15：如何验证一次摄取修复，而不是只证明 happy path 能跑？

回答：我会把摄取拆成解析、分块、编码、Qdrant 索引、READY 确认五个可观测节点，针对每个阶段注入一次失败。验收包括：同文件重复上传的身份规则、版本号并发、最大尝试次数、旧 Worker 失租、新 Revision 失败不影响旧 ACTIVE，以及索引部分写入后的恢复。最终检查 PostgreSQL 的 Revision/Job 与 Qdrant Point、知识快照成员是否匹配，而不是只断言接口返回成功。

追问：最有价值的负例是什么？

追问回答：让 Worker A 在 Qdrant 写入后失租，Worker B 领取新代次；A 尝试提交 READY 应失败，B 按稳定 Point ID 补写并最终完成。此时历史 Snapshot 仍指向旧 Revision，新 Snapshot 只在 B 确认完成后可用。

源码定位： ingestion.py

KG16：RAG 错误为什么要拆成检索、证据交付和回答三个阶段？

回答：检索阶段负责找到可能相关的 Chunk；证据交付阶段负责把正确来源、必要条件和完整片段放进最终模型请求；回答阶段负责按这些材料生成结论与引用。AgentHub 分别保留 Retrieval Trace、Evidence Plan/Registry 和 Citation QA 记录。若 B 条款已进入召回却被字节预算移除，问题在交付；若 B 已进入最终请求而模型误读否定，问题在回答。

追问：一次错误回答怎样快速定位最早失败阶段？

追问回答：按固定 Query 和 Snapshot 追 dense/sparse 候选、RRF、Rerank、证据预算后的 ID、最终 visible_evidence_registry() 和模型输出。找到第一个丢失金标依据的阶段，再针对那个函数调整；避免先改 Prompt 掩盖上游证据问题。

源码定位： retrieval.py · evidence_registry.py

KG17：Dense、Sparse、Reranker 各自负责什么？

回答：Dense 使用语义向量找表达不同但意思相近的材料；Sparse 使用词项权重补充精确术语、编号和专有名词；Reranker 在较小候选池内直接比较 Query 与候选文本，重新排序。AgentHub 的 HybridKnowledgeRetriever 对两路结果使用 RRF 融合，再经可选句级检查和 Rerank，最后按数量、重叠与预算输出证据。三层的目标分别是召回覆盖、词面补充和精排质量。

追问：为什么不只用最强 Reranker 对全库所有段落打分？

追问回答：Cross-Encoder 等重排成本通常远高于向量索引查找，全库逐段比较会让延迟随 Chunk 总量增长。先用 Qdrant 返回几十个候选，再重排几十项，能把计算集中在高价值候选；候选池配置需要通过 Recall 与最终答案正确性共同选择。

源码定位： retrieval.py

KG18：为什么融合用排名，而不是把两路原始分数直接相加？

回答：Dense 相似度可能是余弦分数，Sparse 在当前实现中使用词频、Qdrant IDF 等信号，两者分值量纲和分布不同。直接相加会让数值范围大的一路主导排序。RRF 使用每条结果的排名 1/(k+rank) 累加，避开跨路分数尺度校准。AgentHub 配置 knowledge_rrf_k，融合后还保留源 Chunk ID 和分路 Trace，便于分析某个候选来自哪一路。

追问：什么时候可以考虑用分数融合而非 RRF？

追问回答：在有足够固定标注数据时，可以对两路分数做归一化或学习权重，检查跨领域、语言和查询类型的稳定性。需要单独做校准，不能把某次实验里两路分数碰巧接近当作普适前提。

源码定位： retrieval.py

KG19：Top K 越大，效果一定越好吗？

回答：Top K 增大提高找到关键条款的机会，也会引入更多噪声、重复邻块、上下文费用和错误来源。Rerank 的候选上限、final_top_k、单文档上限与证据预算共同决定最终给模型什么。AgentHub 还通过对重叠来源去重、候选回填和紧凑投影减少浪费。调 K 应检查完整证据覆盖、最终回答支持、P95 延迟和成本，而不是只看候选命中。

追问：为什么“候选来源多了 8 个”可能让最终答案更差？

追问回答：新增来源挤掉原本排名靠后但包含必要例外条款的 Chunk，候选 Recall 上升而完整依据下降。可以用需要多条证据的问题做成对比较，记录哪些具体 Chunk 从最终交付中被替换以及带来的回答变化。

源码定位： retrieval.py

KG20：为什么相同块重复命中也会造成质量问题？

回答：固定窗口分块会产生相邻重叠文本，Dense 和 Sparse 又可能同时找到同一个 Chunk。若把重复片段都计入 final_top_k 与证据预算，模型看到多次相同规则，却可能看不到另一条补充条件。AgentHub 先以 Chunk/Revision 等稳定身份合并，再依据来源 Locator 判定文本重叠，并从候选池向后回填有效片段，提高有限证据槽位的利用率。

追问：相同文字出现在两个不同修订中，应该视为同一证据吗？

追问回答：文本可以相同，来源身份却不同。旧政策和新政策要保留独立 Revision、有效时间与生命周期；检索时可按问题语义选优先版本，但不能直接把不同来源身份永久合并，因为历史问答可能需要引用旧修订。

源码定位： evidence_records.py

KG21：为什么“先去重，再裁预算”会误删有效证据？

回答：若先把靠后的大 Chunk 标记为已覆盖别的片段，再按预算删除它，覆盖判断就基于“其实没有交付给模型”的文本，后续小 Chunk 可能被错误去掉。AgentHub 的 EvidenceAdmission 只用已经真正接纳的片段更新覆盖范围；未通过字节预算的候选不具备遮蔽后续证据的资格。这个细节能保证“去重”与“预算交付”遵循同一可见性定义。

追问：怎样构造最小回归测试？

追问回答：准备三个候选：A 已接纳，B 与 C 有重叠但 B 太大装不进预算，C 是可以容纳的关键片段。验证 B 被预算拒绝后，C 仍然入选；同时检查输出 truncated 与来源 Registry 只包含真实交付项。

源码定位： evidence_records.py

KG22：如何判断两个片段的来源范围重叠？

回答：不能只用字符串相似度判断覆盖。AgentHub 的证据记录携带 DocumentRevision 和 Locator，可比较同一修订同一页/段落/表格行内的 char_start/char_end 或单元格范围。只有来源范围确实重叠且已经交付的文本，才可用于遮蔽重复片段；跨修订即使文字一样，也需保留版本语义。

追问：两个片段来自同一页，但页面坐标缺失时怎样去重？

追问回答：回退到更保守的 Chunk ID 或可验证正文范围去重，避免把相似但不同条件的段落删掉。必要时保留两个片段并通过最终预算处理；Locator 缺失可作为摄取质量信号记录，推动解析器补齐来源位置。

源码定位： evidence_records.py

KG23：为什么不直接把每块截到固定 500 字？

回答：固定截断会在否定词、数值单位或例外条件之间切断证据。例如“七天内可退，定制商品除外”被截成前半句，模型更容易得到错误结论。AgentHub 的 Evidence Plan 计算完整记录及序列化开销，无法容纳时跳过候选并尝试后续较小记录；来源摘录与 Locator 有明确投影规则。对于确实需要缩短的内容，应该采用保留语义边界的句级/段落级抽取，并重新验证支持关系。

追问：如果最高排名 Chunk 过长，但非常重要，怎么优化？

追问回答：在保留原始 Chunk 身份与 Locator 的前提下，增加句级证据窗或结构分块候选，保证必要条件完整，再重新进入预算竞争。比直接切前 500 字更适合可引用知识问答。

源码定位： evidence_plan.py

KG24：context_budget_bytes 和模型 token 窗口是不是一回事？

回答：context_budget_bytes 控制单次检索工具输出或紧凑证据视图的 UTF-8 序列化大小；模型窗口由 Token 上限、输出预留以及 System/Tools/Memory/History/当前问题等共同决定。AgentHub 先在 retrieval.py 选择可交付证据，Runtime 的 ContextBudgetPolicy 再对整个 ModelRequest 做 Token 估算与准入。因此证据在工具阶段通过预算，进入最终模型请求前仍可能受到总窗口约束。

追问：怎么判定某段依据最终真的进入模型请求？

追问回答：核对证据计划里分配的短 ID 与 visible_evidence_registry() 在最终 Context Admission 后保存的可见集合，并查看实际 ModelRequest 的消息投影。工具曾返回某项结果，只是中间阶段的事实；最终可见身份由发送前的校验结果决定。

源码定位： evidence_plan.py · context_budget.py

KG25：多个检索源各自在预算内，为什么归并后还要再裁一次？

回答：多个 KnowledgeSnapshot 各自的 Top K 和字节预算独立成立，合并后可能重复来源、超过总数量与消息大小上限。search_knowledge 将多快照结果按重排分数融合、去重，再统一执行证据集合选择；最终 Runtime 还有模型全局上下文预算。这样不会让多个检索源分别交付“各自合法”却共同超过模型限制，也能避免相同 Chunk 在两个快照中重复消耗槽位。

追问：多快照场景怎样保障来源引用正确？

追问回答：每条 Evidence Reference 保存 Snapshot、KB、Revision 与 Chunk 的完整身份，合并时只合并确实同源的不可变片段；紧凑引用 ID 在最终交付集合中重新生成，Registry 指向唯一来源。测试覆盖同名文档在不同 KB 中和相同 Chunk 同时属于多个快照的情况。

源码定位： search_knowledge.py

KG26：一条回答有引用，为什么仍然可能是幻觉？

回答：引用 [2] 合法只说明编号对应一条当前可见来源，仍可能发生错误解读。例如原文是“定制商品不得无理由退货”，模型回答“可以退货[2]”，结构完全合法但语义颠倒。AgentHub 的 Citation QA 检查 JSON 结构、引用编号、正文标记与 citation_ids 一致；完整可信回答还需要对结论逐项检查来源是否支持，包括否定、条件、数值和时效。

追问：如何设计逐结论引用评价？

追问回答：先把回答拆成原子 Claim，记录每个 Claim 对应的引用集合；用规则或独立语义审查判定 SUPPORTED / CONTRADICTED / INSUFFICIENT，重点验证条件是否完整。评价集加入“只改一个否定词”和“单位不同”这样的困难对，报告支持率与误接受率。

源码定位： citation_qa.py

KG27：answer 中的引用标记与 citation_ids 数组为什么都要校验？

回答：正文里的 [2] 是给读者的引用标记，citation_ids=[2] 是结构化结果字段。两套渠道必须一致，否则可能正文引用了 [4]、机器字段却列 [2]，导致展示与后续审计错位。CitationQaService 验证编号属于可见 Evidence、标记集合和数组集合相同、拒答时数组为空，并识别不规范数字组。引用输出作为版本化合同，有助于防止模型编造不可追溯引用。

追问：遇到代码片段 [0] 或数学区间时，会不会误判成引用？

追问回答：解析器需要使用明确的引用格式合同和上下文豁免规则；项目对一些字面数字组做了限定处理。测试既包含合法单编号引用，也包含代码、数组、数学区间、多编号连写与超范围编号，保证不会把普通数字误当来源，也不会放过非法引用。

源码定位： citation_qa.py

KG28：为什么“没有退货数，但有生产和销售数”应该判拒答？

回答：问题要求“退货数量”，知识库只提供生产量和销售量。即使二者都是数字，也缺少退货统计的业务口径，模型不应该自行将生产减销售定义为退货。AgentHub 的引用问答包含数量问答拒答一致性处理，结合用户请求、证据字段和回答文本判断是否缺少被问指标。正确回复是指出“资料未提供退货数量”，必要时说明可获得的两个相关数值。

追问：如果能通过公式计算，什么时候可以直接回答？

追问回答：必须有明确业务公式、同一统计期、相同口径和完整输入数据。例如库存变化还涉及期初库存、报损和调拨，不能自行设为零。可回答时把公式、数据来源与计算结果一并列出；缺少条件则保留未知项。

源码定位： refusal_consistency.py

KG29：如何评测需要两段证据才能回答的问题？

回答：为每道题标注足以支持正确回答的 Evidence Set，而不只是一个正确 Chunk。例如定制退货问题可能需要普通七天规则和定制例外两段。评价时检查候选召回、重排结果和最终模型输入分别是否覆盖一套完整支持集，再评价最终回答的条件与引用。多个等价支持集应允许择一满足，避免把不同但同样有效的来源误判为失败。

追问：怎样定义完整证据的 Recall？

追问回答：可以同时报告证据单元 Recall 与 full_support_set_coverage：前者按金标单元计数，后者判断是否包含至少一套完整证据集合。所有集合都应绑定 DocumentRevision 和原文区间，防止不同版本的同名条款混淆。

源码定位： evidence_plan.py

KG30：回放历史模型回复，能证明新版本回答能力提高了吗？

回答：历史模型输出回放适合验证评分器、证据投影、Citation Parser 或状态归因修改是否改变了对已知输出的处理。它保持输入响应固定，因此可以定位工程回归。但模型能力比较需要新旧方案在相同固定任务、知识快照、模型路由和预算下分别真实执行，再进行逐题配对；新方案也可能改变检索和 Prompt，使历史输出不再代表实际生成。

追问：怎样安排一次合理的线上前离线对照？

追问回答：先用已曝光 DEV 修复机制，再冻结两个 Variant 和评分版本，按预定重复次数在 HOLDOUT 上执行；记录模型 Attempt、证据完整度、回答、成本和退步题。分区按文档或任务族隔离，减少相似题泄漏。

源码定位： citation_qa.py

KG31：Reranker 分数能直接当作回答可信度吗？

回答：Reranker 的 Score 表示在当前模型和文本分布下的相关性排序信号，主要用于选择候选与阈值过滤。它没有直接校准为“回答正确概率”；即使高分 Chunk 相关，也可能缺少必要的例外条款。AgentHub 仅在有实际重排分数的路径应用对应 min_rerank_score，不把 RRF 的排名统计与重排 Score 混用。回答可信度需要考察完整证据集合及生成结论支持。

追问：如果希望把 Reranker 分数解释为概率，需要做什么？

追问回答：准备独立标注的 query–chunk 相关性样本，针对模型、语言和领域拟合校准函数，再在独立测试集上检查可靠性曲线与误差。即便可以校准片段相关概率，回答的事实正确率仍需要单独评价。

源码定位： retrieval.py

KG32：文档更新后，为何旧快照仍可能检索旧内容？

回答：KnowledgeSnapshot 保存的是一组确定的 (document_id,revision_id) 成员。Document 当前更新到 V3，只会改变新建 CURRENT/LATEST 快照的选择；旧 Snapshot S1 仍可指向 V1，供历史 Run、论文引用或旧政策查询使用。排查“搜到旧内容”时，先查 Run 的有效快照及 V1 生命周期，再看 Qdrant Scope 和返回的 Revision ID，确认是否为有意固定历史数据。

追问：什么时候应撤销旧来源，而不是让历史快照继续可读？

追问回答：当原文因权限、法律或隐私要求被撤销时，需要独立的来源撤销/物理删除流程，检查历史索引、Wiki 派生物、Artifact 和审计保留规则；普通 Revision 退休只表示它不再是当前首选，两者应拥有不同状态合同。

源码定位： snapshots.py

KG33：Memory、对话历史和知识库有什么区别？

回答：知识库保存文档和制度等外部来源，依靠 DocumentRevision、Snapshot 与 Locator 提供证据；对话历史保存某个 Thread 的用户与助手交互、ToolResult 和时间顺序，用于保持连续性；Memory 保存从用户信息中提炼的相对稳定偏好、约束或事实，可跨 Run 选择使用。AgentHub 分别通过 RAG、ThreadContextProvider 和 MemorySelector 注入，三类内容的权限、更新和过期规则各自独立。

追问：用户说“今天临时不吃辣”，应该存在哪里？

追问回答：这首先属于当前会话或任务上下文，是否进入长期 Memory 要看稳定性和用户表达。长期偏好如“平时不吃辣”才更适合持久化；退款政策等正式规则应属于知识库，而不是保存成用户个人偏好。

源码定位： store.py · runtime_graph.py

KG34：当前新建 Agent 的 Memory 默认是怎样的？

回答：最新创建 Agent 草稿时，若用户没有显式提供 Memory 配置，项目默认启用长期 Memory 并采用 USER 作用域；发布版本冻结具体选择策略，旧 AgentVersion 继续按它保存的规格执行。Runtime 使用 Run 创建者身份选择对应 owner_user_id 的记忆，并在 Run 首次 PREPARE 时冻结实际 Memory IDs，便于审批恢复和重放读取同一组内容。

追问：USER Memory 会自动让同一工作区内的所有会话私有吗？

追问回答：USER 限定 Memory 条目选择范围，Thread、Run、Artifact、反馈和工单有独立访问规则。要实现个人助手全链路私有，还需对这些对象的每个读取、列表、导出和后台入口加入所有者语义。

源码定位： publish.py

KG35：为什么 Memory 检索必须把 owner_user_id 带到底层？

回答：多个用户可能在同一个 Workspace 使用同一个 Agent。若 Memory 候选查询只按 workspace_id/agent_id 过滤，就可能把 U1 的个人偏好注入 U2 的回答。AgentHub 在 USER 模式下把 Run 的 created_by 作为 owner_user_id，贯穿 Memory Selector 和 Store 的查询条件；共享 AGENT 范围则走另一套分区语义。权限应在数据库候选阶段约束，而不是检索后靠 Prompt 删除。

追问：未来接入向量 Memory 时，怎样保证私有过滤？

追问回答：向量查询 Scope 中带 Workspace 和 owner_user_id，再对返回的 Memory ID 用 PostgreSQL 权威记录复核 owner、状态和过期时间。更新/撤销也按相同分区限制，避免全局索引候选被错误投影到其他用户。

源码定位： store.py

KG36：Memory 还没有向量检索，是技术落后吗？

回答：当前 Memory 选择偏词项重叠与其他明确规则，优势是可解释、成本低、结果相对稳定；代价是“喜欢清淡”和“少油少盐”这类同义表达可能互相漏召回。是否增加向量检索取决于真实任务里的漏召回与误注入比例。AgentHub 已有 MemorySelector 合同与 Run 冻结机制，可以在保持权限、预算、稳定 ID 和历史重放不变的前提下替换候选策略做对照。

追问：怎么避免语义向量把无关记忆也召回来？

追问回答：先按 owner 和状态过滤，再做向量候选、可解释的相关性门槛以及冲突/时效检查；对固定问题标注“应注入”和“不应注入”两种金标。优化目标同时包含 Recall 与误注入率，而不是只追求召回更多条目。

源码定位： store.py

KG37：lexical_overlap_v1 过滤器提高了什么，又可能损失什么？

回答：lexical_overlap_v1 在已有候选集合上进一步根据问题和记忆文本的词项交集筛选，能减少无关长期记忆占用 Token，也能降低记忆内容干扰当前任务的机会。它的成本是漏掉改写表达、同义词或隐含约束；而且它只过滤候选，无法找回上游 Selector 从未召回的条目。应通过逐题注入清单和最终答复判断过滤值，而不是以 Memory 数量变少代表效果提高。

追问：如何定位是候选召回还是 lexical filter 导致漏记忆？

追问回答：分别记录 Selector 原始候选 IDs、filter 后 IDs、预算投影后 IDs 和最终模型请求可见 IDs。若金标记忆从未进候选，改候选策略；若在过滤阶段被删除，调整 overlap 规则或增加语义补充；若因预算删除，调整记忆优先级与 Token 分配。

源码定位： selection_policy.py

KG38：有用户原话 evidence，是否能保证提炼出来的 Memory 正确？

回答：Memory Extractor 保存用户原话 Evidence，可以追踪“这条记忆根据哪句话得来”，但抽取出的规范化事实仍可能丢失时间与条件。例如“这周暂时不吃辣”提炼成“用户从不吃辣”就发生语义扩大。AgentHub 校验引用文本确实来自用户、抽取结构和长度；更深层质量需要逐项校验主语、谓词、否定、时间、范围和稳定性，避免把临时约束长期化。

追问：怎样设计一个 Memory 忠实性测试集？

追问回答：给出用户原话、预期可保存事实和禁止保存事实，覆盖“可能”“暂时”“以前”“不是”“代朋友询问”等模式。评价抽取是否保持条件和主体，也统计不该写时正确为空的比例。测试结果再进入写入阈值和人工管理策略。

源码定位： store.py

KG39：为什么抽取 Memory 时不把助手回答一起当事实来源？

回答：助手回答可能包含推断、示例或模型错误，把它们直接当长期记忆来源会让系统将自己的猜测不断写回并在未来强化。AgentHub 的 Memory 抽取以用户表达作为候选证据，要求引用可定位到真实用户文本；同一来源可以配合稳定 Turn 身份去重。用户表达也需判断是否明确、稳定和属于本人，否则不应把临时问法变成长期事实。

追问：用户说“帮朋友查某种疾病”，Memory 应怎么处理？

追问回答：记录当前任务需要的临时上下文即可；长期 Memory 只有在用户明确将事实归属自己、且符合产品保存规则时才创建。抽取器需要区分第一人称、第三人称和假设情景，避免把别人的资料写进当前用户档案。

源码定位： store.py

KG40：如何防止重复投递把 Memory 的 salience 加多次？

回答：同一用户表达可能因为队列重复投递被抽取多次。仅按内容 Hash 去重可阻止重复行，却可能每次都增加 salience，使“系统重试”被误认为“用户再次强调”。AgentHub 还记录来源事件贡献身份，把真实表达与基础设施重放区分开；同一事件重复写入只计一次贡献，不同 Turn 中再次明确表达可独立计入权重。

追问：文本 Hash 与事件 ID 分别解决什么？

追问回答：文本 Hash 识别语义对象的规范化内容，事件 ID 识别某次用户表达。两次不同 Turn 说同一句话是一个内容、两次行为；同一 Turn 重复投递是一个内容、一次行为。排序和频次应使用经过事件去重后的贡献记录。

源码定位： store.py

KG41：为什么 Memory 的共享与私有唯一约束需要仔细处理？

回答：共享 AGENT Memory 与 USER 私有 Memory 的唯一范围不同：共享条目以 workspace、agent 和规范化内容识别，私有条目还需要 owner_user_id。PostgreSQL 普通 UNIQUE 对 NULL 的行为使混用一条复合约束容易遗漏共享场景。AgentHub 在模型里为不同 scope 定义部分唯一索引，Store 并发写入利用数据库约束与保存点处理冲突，既避免重复，又防止一个候选冲突导致整批有效 Memory 回滚。

追问：两个用户保存相同偏好，应该共用一条 Memory 吗？

追问回答：USER 作用域下应存为两个所有者独立记录，互不影响失效、过期与 salience。共享 AGENT 作用域下相同规范化事实才按共享键去重。测试应同时覆盖 NULL owner 的共享索引、两个不同 owner 的同内容与同 owner 的并发重复写入。

源码定位： models.py

KG42：新记忆与旧记忆矛盾，直接取最新可以吗？

回答：新旧记忆相似不一定互相替代，例如“喜欢喝茶”和“最近不喝茶”可能是临时状态冲突，也可能是长期偏好改变。处理时先识别事实主体、属性、值、时间和条件，再判定补充、替代或并存。AgentHub 已有 Memory 状态、内容哈希和失效机制，后续可以增加显式 supersession 链与冲突审查；历史 Run 仍保留当时选中的记忆身份，新的 Run 才使用更新后的有效集合。

追问：为什么直接按最新时间取一条会出错？

追问回答：新表达可能限定“本周”“出差期间”或只针对另一个对象；时间更新不意味着条件覆盖。应保留原文证据和时效范围，在同条件下才形成明确替代；不同条件可并存并在当前问题下选择适用项。

源码定位： store.py

KG43：Memory 是否支持过期？完整 TTL 还缺哪些设计？

回答：Memory 记录已包含过期相关字段，Selector/Store 在新选择时会过滤过期和无效条目。完整 TTL 治理还需区分稳定偏好与临时任务约束、创建时的有效期、提醒或确认机制、容量上限和到期清理策略。过去被选择的记忆仍通过 Run 快照保留历史执行语义；新 Run 采用最新有效集合。数据生命周期应同时处理用户主动撤销和系统自动过期。

追问：每次 Memory 被召回，是否就把过期时间往后延长？

追问回答：读取只说明当前任务用过这条记录，不能说明用户重新确认其内容。可更新访问统计用于排序，但 TTL 延长应来自明确的用户重复表达、确认或业务定义的续期事件，避免临时事实因高频使用永久化。

源码定位： models.py

KG44：记忆被失效后，为什么旧 Run 还能重读它？

回答：Memory 的 invalidate 表示后续新选择不再使用它，历史 Run 的 effective_memory_snapshot 则回答“当时模型接收了哪些记忆”。AgentHub 在 Run 首次 PREPARE 冻结 ID 与相关内容身份，审批恢复和历史复盘按冻结集合加载，避免今天的管理修改改写昨天的执行过程。这与隐私删除是两个生命周期动作：运行可重现性和用户删除请求需要独立规则协调。

追问：用户要求彻底删除敏感记忆时，应怎样处理历史 Run？

追问回答：定义保留与删除合同，枚举 Memory Store、Run 快照、Checkpoint、工具事件、日志和备份中的正文或派生信息。可以保留不可识别的审计身份并让某些历史回放失去正文，但执行路径必须明确处理缺失来源；同时按法规及产品保留期限清理副本。

源码定位： store.py

KG45：Memory 快照为什么同时保存 ID 和 content hash？

回答：Memory ID 指向具体持久记录，content hash 用于确认冻结选择对应的规范化内容身份。Run 保存两者，可以在恢复时发现选择列表意外改变或加载对象不匹配，保证同一执行从审批暂停回来仍沿用原记忆集合。Hash 同时支持去重与审计，但不承担用户授权；真正的 owner 和 Workspace 校验仍需通过 Store 的受限查询。

追问：如果有人直接修改 Memory 正文但没有同步更新哈希，能否发现？

追问回答：需要在加载边界对当前正文重新计算规范化 Hash，并与冻结值比较，才能主动发现该类篡改；仅比较数据库保存的两个旧字段并不足够。增加这一校验时还应明确原 Hash 是否做大小写/空白规范化，区分同一规则下的内容身份与字节级差异。

源码定位： store.py

KG46：如果让你证明向量 Memory 比现有词项选择更好，你会怎么做？

回答：我会在现有 MemorySelector 接口后增加实验性的语义候选实现，沿用 Workspace/owner 过滤、有效状态、输出 Memory ID 和 Run 冻结机制。用固定多轮任务标注该注入/不该注入的记忆，比较当前词项策略与向量候选在召回、误注入、最终约束遵循、Token 开销和延迟上的逐题差异。评测前冻结原始 Memory 状态，避免测试期间写入污染后续样本。

追问：如果向量 Recall 提升但最终回答更差，下一步怎样定位？

追问回答：查看多召回的条目是否含冲突、过期或第三人称事实，再检查预算投影是否挤掉更重要的 History/RAG。可以引入候选 Rerank、事实时效评分或显式冲突过滤，保留带来源的失败样本进行二次对照。

源码定位： selection_policy.py

KG47：已经有 RAG，为什么还要 Wiki？

回答：RAG 从原始 Revision 的 Chunk 中检索相关文本，适合临时查询与保留完整原文；Wiki 把来源编译成页面、Claim 和关系，适合跨文档主题汇总、长期组织和追踪来源更新。AgentHub 的 Wiki 产物仍指向原始 KnowledgeSnapshot，并在查询时验证 Claim 来源，可以按 WIKI、RAG、HYBRID、AUTO 组合读取。两者在“直接依据原文”与“预先组织知识”之间互补。

追问：哪些场景优先用纯 RAG，哪些更适合 Wiki？

追问回答：一次性的具体条款核对优先原文 RAG，减少编译维护成本；跨多个文档反复查询同一主题、需要实体关系和冲突组织时，可以先用 Wiki 建结构化入口，再根据查询触发原文补充。选择依据是查询重复率、变更频率和最终答案质量。

源码定位： query.py · service.py

KG48：Wiki 为什么没有使用专业图数据库？

回答：当前 Wiki 页面、Claim、编译缓存、来源和关联关系都保存在 PostgreSQL，关系规模和查询模式仍可通过 SQL 组织。图数据库的价值在复杂多跳路径和图算法，不是因为有 relation 字段就必须迁移。若 Wiki 的主要瓶颈是标题匹配召回和 Claim 忠实性，换存储并不能直接改善。先测主题页匹配、跨 Claim 路径长度与数据库查询成本，随后再判断是否需要图数据库。

追问：要支持三跳实体关系查询，如何决定实现路线？

追问回答：先用当前关系表和递归 CTE 实现一个有边界的原型，记录节点/边数量、路径长度与 P95 时间；再与图存储比较查询表达、索引、同步和运维成本。来源修订与撤销约束仍需保留，不论数据存在哪里。

源码定位： service.py

KG49：Wiki 编译器怎样防止模型伪造来源？

回答：Wiki 编译输出的 Claim 必须能对应已冻结知识快照中的真实 Chunk 与原文区间。compiler.py 将文档内容作为不可信参考数据，不开放任意外部工具；WikiService 验证返回的 document/revision/chunk 身份、原文引用和所在快照关系，并在持久化前检查输出结构。这样模型生成的虚假 Chunk ID 或不属于快照的来源不能成为合法 Wiki Claim。

追问：来源身份合法，是否就意味着提炼的结论忠实？

追问回答：还需要对 Claim 的主语、谓词、条件、否定和数值做语义支持检查。例如原文“可能提高”不能提炼成“必然提高”。可以把抽取结果与对应原文配对，建立独立 Claim 支持评测并保留问题样本。

源码定位： service.py

KG50：Wiki 中两条主张的 value 不同，就一定冲突吗？

回答：Claim 的 value 不同，需要先比较主体、谓词、时间、范围、前提条件和单位。比如“2025 年收入 10 亿”和“2026 年收入 12 亿”并不冲突；同一年同口径的两个不同值才可能构成冲突。AgentHub 的 Wiki 冲突审查会围绕规范化谓词、条件和已有 Claim 组成候选冲突组，保留相关原文和标记，供后续查询选择或说明差异。

追问：对确实矛盾的两条来源，Wiki 是否应自动删除较旧一条？

追问回答：按来源版本和有效时间保留两边 Claim，标注冲突与可能的替代关系；查询最新政策时可优先有效版本，查询历史时保留旧结论。若业务明确规定权威优先级，可在查询路由中体现，并显示选择依据。

源码定位： query.py

KG51：一次 Wiki 编译要冻结哪些东西？

回答：一次 Wiki 编译需要绑定来源 KnowledgeSnapshot 及其内容身份、编译策略与提示词版本、模型路由与输出 Schema、编译器代码版本、页面/Claim 组织规则及产物 Hash。AgentHub 使用编译 Manifest、来源引用和发布记录保存这些身份，便于判断修改来源后哪些编译产物需要更新。生成完成和正式发布是两个不同生命周期步骤，发布会对来源有效性与结构完整性进一步检查。

追问：为什么只保存模型名称和编译时间不足以复现？

追问回答：同一模型在不同 Prompt、工具可见性、温度或 Schema 下可能生成不同 Claim。完整编译身份需要输入快照、具体路由配置、生成参数、规范化输出与版本化规则；检查差异时才知道是输入更新还是编译逻辑变化。

源码定位： service.py

KG52：Wiki 的增量编译目前做到什么粒度？

回答：AgentHub 已有基于来源 DocumentRevision 的抽取复用：未变化的修订可以重用已验证的 Extracted Claims，减少重新调用模型。该粒度以不可变 Revision 作为缓存键，维护简单且来源身份清楚；小改动导致新 Revision 时仍可能触发该修订的大范围重编译。更细的 Chunk 级缓存或依赖图可以作为下一步实验，测量新增缓存维护与失效成本。

追问：如何评价是否值得把缓存粒度下探到 Chunk？

追问回答：用多轮真实文档修改记录计算新旧 Chunk 的交集比例、重算 Token 与耗时；再检查 Chunk 粒度重用是否会丢失跨段上下文、页结构和 Claim 条件。只有在节省显著且语义一致性可控时，才升级缓存层级。

源码定位： service.py

KG53：为什么 Wiki 页面生成还要做文本转义？

回答：Wiki 页面正文可能来自上传文件或模型生成，其中包含 HTML、Markdown、脚本字样。渲染时需要区分纯文本与允许的结构化标记，使用安全转义避免把文档中的 <script> 当作页面代码执行。AgentHub 在组织 Wiki 页面时采用受控文本投影，前端继续按页面组件规则渲染。来源合法性、读取权限和输出转义分别解决数据真实性、访问范围与浏览器执行安全。

追问：以后要支持富文本链接和关系图，能直接关闭转义吗？

追问回答：应引入明确的节点/属性白名单，例如允许安全链接、强调、列表和关系目标 ID；对 URL Scheme、文本内容和 HTML 进行结构化消毒，保持来源对象和权限检查。禁止任意原始脚本或事件处理属性进入 DOM。

源码定位： service.py

KG54：为什么 Wiki 生成完成后先是 READY，而不是直接 PUBLISHED？

回答：Wiki 编译完成时 READY 表示候选页面与 Claim 已形成，PUBLISHED 表示管理员或发布流程已检查来源绑定、Lint 和最终 Manifest，允许它成为 AgentVersion 可引用的 Wiki Publication。这个区分使后台 Worker 可以完成昂贵的编译，但不自动把未经发布检查的内容投入正式使用。Agent Version 发布时解析 Wiki LATEST 到确定 Publication，保证历史绑定稳定。

追问：如果编译后立刻自动发布，会失去什么控制点？

追问回答：会把结构化抽取结果和最终知识发布混成一个事件。当前发布边界可以检查来源已撤销、Claim 引用无效、编译冲突和 Lint 阻断项，允许管理员在 READY 阶段先核查质量与适用范围。

源码定位： service.py

KG55：Wiki lint 有警告，为什么仍可能发布？

回答：Lint 可以产出阻断的 error，也可以产出提醒人工注意的 warning。例如来源 ID 不存在、引用跳出快照属于结构性错误，应阻止发布；两条有来源的 Claim 存在未解决的语义冲突，可能作为 warning 保留，供查询时显式处理。AgentHub 的发布检查按严重性决定是否允许 PUBLISHED，并不要求所有警告都被删除。

追问：用户问到一个带冲突的 Wiki Claim，回答应怎样组织？

追问回答：展示两条来源及各自条件、时间与数值，说明冲突点；如果查询策略要求最新有效规则，依据明确的生效日期选择并标注。缺少权威判据时返回冲突状态或请求补充条件，避免悄悄只选其中一个。

源码定位： service.py

KG56：Wiki 过期与来源撤销有什么区别？

回答：Wiki 过期表示生成内容的来源或编译版本已有更新，需要安排再编译；来源撤销表示某个基础 Revision/Claim 不再允许用于新查询或发布；物理删除涉及 Blob、数据库行、索引和备份清理。AgentHub 分别保存来源身份、发布物和撤销状态，查询时验证绑定，防止删除一个基础来源后继续把派生 Claim 当作当前可信内容。

追问：撤销某个来源后，历史 Wiki Publication 如何处理？

追问回答：保留历史 Publication 的身份和审计记录，但读取与可用性要遵循新的来源撤销策略。需要依赖图定位所有受影响的 Claim、页面和 Publication，标记不可再交付的来源；隐私彻底删除则进一步执行物理清理与历史回放规则。

源码定位： service.py

KG57：当前 Wiki 页面是怎么匹配问题的，有什么限制？

回答：当前 query_wiki() 对页面使用标题与 Query 之间的词项重叠和覆盖比例排序，再从匹配页取 Claim、关系邻居及可核查来源。标题“退款政策”能命中“退款规则”，但正文里隐藏的特定产品例外可能因标题词项不足而漏召回。下一步可增加 Claim 正文搜索、倒排索引或语义候选，再保持原有 Publication/Revision 校验与证据预算。

追问：怎样验证新的 Wiki 候选策略确实改进？

追问回答：固定编译 Publication 与问题集，分别标注应命中的 Page/Claim 和应拒绝的无关页面。比较候选 Recall、误召回、原文补检索率与最终答案支持，特别关注多命中页面是否挤掉真正必要的原文证据。

源码定位： query.py

KG58：AUTO 模式为什么有时还要回到原文 RAG？

回答：Wiki 适合在已有结构化 Claim 中读取事实，但用户问题可能涉及未编译的细节、条件或原文数值。query_wiki 的 AUTO 根据查询意图、已匹配页面、证据充分性和冲突等状态决定是否补充原始 RAG；RAG/HYBRID 则按照显式路由要求检索相应来源。这样在有结构化知识时先利用 Wiki，缺少足够依据时回到 Revision Chunk 取得原文。

追问：怎样解释 AUTO 本次为什么选择了 RAG 补充？

追问回答：在 Trace 里记录 intent、matched pages、Wiki Claim 数、冲突标志、insufficient_evidence 和最终 route，关联新增 Raw Evidence IDs。用户或评测可以看到是“标题未命中”还是“Claim 不完整”触发回退，并检查最后给模型的证据集合。

源码定位： query.py

KG59：为什么 query_wiki 的 insufficient_evidence 不能当作事实判定器？

回答：query_wiki 的 insufficient_evidence 描述当前路由在检索和证据组装层面的可用性，表示这次有没有足够的可交付材料；它没有阅读最终模型答案并逐句判断语义正确。AgentHub 的结构化 Evidence View 还包含 route、conflict、degraded 等状态，这些用于解释检索条件。真正的任务成功仍要把 Query、实际交付的来源和生成 Claim 对齐评价。

追问：如何把 Wiki 路由状态纳入评测而不误读？

追问回答：单独统计路由正确率、证据可用率、冲突识别和原文补检索覆盖；最终答案的语义支持率另做评分。对一条 insufficient=true 的请求，核查原文库是否本来有答案，再判断是合理拒答还是路由漏检索。

源码定位： query.py

KG60：如果只能独立完成一个知识域改进，你会选什么，怎样证明价值？

回答：我会优先实现“最终模型请求的完整证据集合评价”：给多条件问题标注必要来源和等价支持组，利用 Retrieval Trace、Evidence Plan、visible_evidence_registry() 检查每层保留比例。这个改动主要集中在 packages/knowledge/evidence_plan.py、packages/agent_runtime/evidence_registry.py 和评测输出，不需要先更换 Embedding 或重写全套 RAG。它能把“找到了但丢在预算里”和“模型读错了”分开定位。

追问：怎样给这项改动设置验收门槛？

追问回答：固定多证据和否定条件题集，在相同候选、预算与模型条件下比较修改前后完整证据交付率、回答支持率、Token 和 P95 延迟；回归涵盖来源错配、被预算跳过的大块和跨快照重叠。输出逐题失败列表，直接定位改动收益。

源码定位： evidence_plan.py · evidence_registry.py
