第 25 讲：启动、迁移、密钥与灾难恢复

一、部署其实要对齐四种版本

代码版本、数据库结构版本、发布业务规格版本和运行配置不是同一个东西。你拉了最新 Git 提交，并不表示数据库已经执行最新 Alembic 迁移；迁移完成，也不表示旧 AgentVersion 自动使用新 Prompt；API 能连接数据库，也不表示 Worker 拿到了正确的模型凭据解密密钥。

当前源码新增了 0061_chunk_document_revision.py，为分块归属补上更强约束。但“仓库存在 0061”只证明代码包含这次迁移，不能证明你的实际数据库已经升级。你要读部署回执或查询实际 migration revision，才能回答后一个问题。0061 迁移

可以用下面这份表组织环境事实：

维度 应记录什么 缺失时会有什么问题
源码 Git SHA、分支、是否有未提交修改 无法确认代码行为
数据库 Alembic 当前 revision、checkpoint schema 新代码遇到旧表或无法恢复图状态
运行配置 API/Worker 的执行模式、连接目标、功能开关 两个进程使用不同规则
密钥与凭据 密钥版本、恢复来源、凭据引用有效性 数据库有密文但无法解密
模型与索引 编码器身份、维度、集合、缓存与数据卷 旧向量与新编码器不兼容
业务发布物 AgentVersion、知识快照、Wiki publication 误把旧发布配置当成新行为

环境问题之所以难查，通常不是配置项特别多，而是大家在讨论不同层次的“版本”。

二、为什么迁移要在服务启动前显式执行？

如果每个 API 进程启动时都自动修改 schema，多个副本可能同时迁移；一个看似无害的重启也会变成数据库变更；失败后很难分清是启动失败还是结构变更失败。

项目把初始化放在 scripts.local_setup.prepare_database()：先执行 Alembic，再显式 bootstrap LangGraph checkpoint。Compose 的 prepare 服务成功退出后，API、Worker、Beat 才启动。业务表属于 Alembic，框架 checkpoint 表在单独的 langgraph_checkpoint schema 中由明确部署步骤建立。初始化脚本 Checkpoint 初始化 Compose

这个顺序能减少歧义，但不自动解决所有发布兼容问题。将来多副本滚动发布时，仍要考虑新旧代码同时访问新结构的窗口，必要时采用先增加、后迁移数据、最后移除旧字段的分阶段变更。这里是部署设计原则，不是宣称当前已经实现零停机发布系统。

三、为什么不能看到数据库报错就“重新生成密钥”？

项目至少有两类用途不同的密钥：JWT 签名密钥和 Provider/MCP 凭据加密主密钥。更换签名密钥会影响已有访问令牌验证；丢失加密主密钥则会让已有数据库密文无法解密。

local_setup.init 在新安装时生成独立的随机密钥，已有 .env 则验证并保留，不应悄悄覆盖。它还会发现文件与当前 shell 中的主密钥覆盖冲突。Provider Secret 使用版本化密文；加密存储和 API 响应脱敏分别负责不同边界。安装配置 凭据加密

一个常见现象是：API 能配置模型，Worker 却全部模型调用失败。原因可能是 API 使用密钥 K1 加密，Worker 使用 K2 解密，而非模型本身不可用。排障应先检查两边使用的密钥来源和环境，不能为了“让它起来”直接覆盖旧密钥。

演示账号和公开模板里的默认连接配置只属于受控环境。讲部署时，重点是理解配置怎么传递、秘密怎么恢复，而不是把演示配置直接当正式部署方案。

四、健康检查分别证明了什么？

当前 /api/v1/health 证明 API 可以处理这个简单请求；/api/v1/ready 探测 PostgreSQL；/api/v1/dependencies 分别检查 PostgreSQL、Redis 和 Qdrant 的基本可达性。它们没有运行一次完整的文档摄取，也没有证明模型凭据有效、工具能审批恢复或队列没有积压。健康探测源码

所以，如果页面能打开，但上传文档一直 PENDING，应继续检查 Worker 是否在线、任务是否被派发、业务记录是否被领取、租约和阶段是否变化。不能拿一个 green health 页面结束排障。

还要区分冷启动。检索模型可以按设置预热，也可能首次使用时才加载；共享缓存减少重复下载，但预热是否完成、设备内存是否够、超时是否覆盖加载成本，仍会影响第一次请求。API 的进程可用性和“所有模型已热身”是两件事。API lifespan 缓存挂载

五、CI 为什么不是“跑一个 pytest”那么简单？

仓库 CI 既有依赖锁定、静态检查和单元测试，也有真实 PostgreSQL/Redis/Qdrant 环境、迁移与 ORM 一致性检查、checkpoint 初始化、Worker 集成和前端生产构建。新增分块迁移也配置了专用数据库测试入口。CI 工作流

不同检查回答不同问题：

检查 主要问题 不能单独证明
静态检查 / TypeScript 构建 代码或类型是否存在可发现错误 实际业务完成
单元测试 一条规则在受控输入下是否成立 真实数据库锁语义
数据库集成 事务、约束、并发与持久读回 模型回答质量
故障注入 指定崩溃窗口如何恢复 所有未知故障都覆盖
浏览器交互 用户能否完成具体操作 所有设备、权限、网络组合
冻结质量评测 对指定数据和配置的效果 未验证人群和任务的普遍收益

本次文档更新没有重新运行项目 CI、付费模型实验或浏览器矩阵。文档中的“仓库包含测试”“历史报告记录通过”和“本次验证通过”使用不同措辞，避免把证据混在一起。

六、有持久卷为什么还需要备份？

持久卷可以让容器替换后继续使用原数据，但磁盘损坏、误删或错误迁移仍可能破坏它。备份的目标是保留一个可恢复的历史状态，恢复演练则验证这个状态真的可用。

在 AgentHub 中，恢复计划要覆盖 PostgreSQL 的业务表和 checkpoint、原始 Blob、凭据主密钥、部署配置，以及检索索引的备份或可重建路径。不能只备份 agents、agent_runs 两张表，也不能只保留 Qdrant 向量就认为所有知识和来源都还在。存储挂载 数据归属

如果 Qdrant 丢了而 PostgreSQL 还在，文档修订可能仍显示 READY；数据库这个状态并不能让索引凭空出现。需要诊断实际索引缺失并执行经过设计的重建，再验证快照范围和引用映射。当前不能把“可以从源文档重新编码”泛化成“已有一键灾后重建全部历史知识的完整控制面”。

同样，恢复数据库后看见 PENDING 或 PROCESSING 任务，不意味着全部应该重新派发。只读、可重复的摄取和外部副作用动作要按各自恢复合同处理。恢复一个待批准动作，也不应该把它变成“默认批准”。

七、怎样设计一次有意义的恢复演练？

先明确目标：允许丢失多少时间的数据，叫恢复点目标；允许多长时间恢复服务，叫恢复时间目标。不要先写一个笼统的“高可用”。

下面是演练设计，不是本次已执行的操作：在隔离环境恢复一份确定时间的备份，核对数据库结构与应用版本，检查一个历史 Run、一个等待审批的 Run、一份知识快照、一条 Memory 来源和一个业务工单；确认凭据可解密但不输出秘密；最后运行一个受控无外部副作用的任务，核对结果和事件。

演练完成的证据应包含恢复对象、版本、耗时、遗漏以及不能恢复的内容。只有“备份文件生成成功”仍不足以证明灾备可用。

八、本讲练习：做一张不包含秘密的环境指纹表

记录代码 SHA、数据库 revision、API/Worker 执行模式、连接的是哪套隔离环境、模型档案 ID、知识快照 ID、加密密钥的安全管理位置和健康检查结果。不要记录 API Key、数据库密码、Refresh Token 或完整业务正文。

当你能用这张表解释“为什么同样代码在两台机器行为不同”，你就开始掌握工程交付，而不仅是运行一个启动命令。
