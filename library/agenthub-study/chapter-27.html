面试问答 A：架构、认证、权限、工具与数据库（SYS01–SYS60）

SYS01—SYS60：架构、认证、权限、工具与数据库

SYS01．请用一分钟介绍 AgentHub，别只列技术栈。

回答：AgentHub 的业务入口是工作区里的 Agent：管理员管理模型、Prompt、工具和知识绑定，发布为 AgentVersion；用户提交 Turn 后创建 AgentRun，Runtime 根据冻结规格组装上下文、调用模型及工具，并把步骤、事件、审批和最终产物落库。知识处理走 PostgreSQL 元数据与 Qdrant 索引，长任务由 Celery Worker 承担。产品还包含客服工单、Artifact、人工接管、反馈和独立评测。介绍时我会以“发布一个客服 Agent，查询订单、申请退款、审批后执行并记录结果”为例，串起主要组件。

追问：面试官继续问“你在其中负责什么”，怎么回答？

追问回答：选一条能指向具体文件与验收记录的链路讲自己的工作。例如研究过文档修订进度刷新，就从 knowledge-detail-client.tsx 的列表和详情两份查询讲起，解释为何详情停留在旧状态，以及轮询怎样收敛。若独立修改的是另一模块，则换成该模块的 PR、测试和改动前后行为，直接说明本人负责的范围。

源码定位： 项目入口

SYS02．为什么选模块化单体加 Worker，而不是一开始拆微服务？

回答：项目把 FastAPI 业务入口和 packages 中的领域模块组织在同一代码库，通过 PostgreSQL 事务维护版本、权限和审批等跨模块不变量；耗时的文档摄取、Wiki 编译、评测交由独立 Celery Worker 处理。这样发布 Agent 时可以在一个事务里完成版本和工具绑定检查，执行任务又能按 CPU、GPU 和队列负载单独扩 Worker。当前关键复杂度在业务状态和来源一致性，分成 HTTP 微服务只会使这些调用额外经历网络与跨服务授权。

追问：未来最可能优先独立扩容的部分是什么？

追问回答：知识摄取及向量计算最适合做资源级隔离：Embedding、Rerank 对 GPU 和内存更敏感，而普通登录、管理和运行列表以短数据库请求为主。先用队列等待时间、显存占用、任务吞吐和 API P95 证明资源争用，再决定扩 Worker 池还是拆独立服务；服务拆分时保留 IngestionJob 的持久身份与状态协议。

源码定位： 部署进程

SYS03．控制面和运行面分别是什么？

回答：控制面决定“允许怎样执行”，负责组织与工作区、ModelProfile、ToolRevision、Agent 草稿、AgentVersion、知识快照及实验定义。运行面消费已发布规格，为一个 Run 建立有效输入、进行模型/工具调用，生成事件、Step、审批与产物。AgentPublishService 属于控制面；AgentRunService、runtime_graph、Worker 和 ActionRuntime 是执行路径。这样管理员修改草稿后，已有 Run 仍按它绑定的 AgentVersion 和当次知识快照解释。

追问：控制面和运行面一定要部署成两个进程吗？

追问回答：这是职责边界，不是物理部署要求。AgentHub 的 API 进程既提供管理路由，也能装配部分 Runtime；后台 Worker 使用相同领域代码运行耗时任务。未来若需要独立扩容，可以把执行搬到专用进程，同时维持同一版本、租约、审批和事件合同。

源码定位： 发布服务

SYS04．Agent、AgentVersion、AgentRun 为什么不能只用一张表？

回答：Agent 是不断编辑的业务身份，AgentVersion 是一次发布形成的冻结执行规格，AgentRun 是具体用户输入触发的执行事实。一份草稿可以发布 v1、v2，同一 v1 又可以产生多个并行 Run。Version 中有 resolved_spec 和 hash，Run 记录绑定版本、实际知识与 Memory 快照、状态和证据。三类对象分开，才能同时支持配置演进、历史追溯、并发执行及逐次计费。

追问：把三者存成一张表加 JSON 快照是否可行？

追问回答：物理上可以，但仍要给草稿、版本和运行分别设计主键、唯一约束与状态转换。例如 (agent_id, version_number) 唯一，Run 的外键指向精确版本，运行中的状态更新不能修改版本内容。合表后需要处理大量空字段和不同写入频率，AgentHub 采用独立表让数据库约束更清晰。

源码定位： 发布与版本

SYS05．“版本不可变”到底冻结了哪些东西？

回答：发布时 publish.py 解析并固定 Prompt、模型配置的可执行部分、工具修订及其风险/参数合同、运行预算策略、Wiki 发布绑定和知识选择策略。原始知识的 LATEST 在创建 Run 或正式实验有效输入时解析到具体快照；Wiki LATEST 在 AgentVersion 发布阶段解析。Run 还记录有效 Memory、历史与知识身份，用这些对象共同还原一次执行。凭据轮换、Provider 当时的服务状态和远端业务数据属于另外的运行环境信息。

追问：要复核昨天一次失败回答，具体取哪些记录？

追问回答：从 AgentRun.agent_version_id 取得冻结规格及 hash，再取该 Run 的有效知识快照、Wiki Publication、Memory 选择、历史来源、模型尝试和 Step/ToolResult。对于评分差异，再对齐代码提交、评测器版本、题库版本和供应商路由。按这些身份重新构造输入，就能判断是配置变化、材料变化还是模型执行差异。

源码定位： 版本解析

SYS06．为什么对配置做 canonical JSON hash？

回答：配置可能从不同代码路径生成，JSON 字段顺序或空白改变不应产生不同规格身份。项目用固定序列化规则计算 canonical_json_hash，将结果保存为 resolved_spec_hash；执行前再次计算并核对，ToolRevision 同样校验 spec_hash。这相当于对“发布时究竟固定了哪些字节级内容”给出一个可复核指纹，特别适合检查历史规格和工具引用是否被意外改写。

追问：两个版本 hash 相同，实际回答就相同吗？

追问回答：相同 hash 指向相同的规范化配置内容。Run 的知识快照、Memory、历史、用户提问及模型供应商状态仍会影响生成；因此逐次比较用 Run 的有效输入和模型调用记录。若需要防数据库管理员篡改，还要额外采用签名、独立审计或不可变存储，hash 校验本身解决的是内容一致性。

源码定位： 规范化实现

SYS07．为什么数值默认值还要区分 UNSET 和 CUSTOM？

回答：数值配置需要同时保存“具体数值”和“这个数值从哪里来”。UNSET 表示沿用系统根据模型和策略推导的默认，CUSTOM 表示管理员有意识设置。比如窗口或预算目前默认 8,000，未来切换模型以后，UNSET 可以重新按新部署能力推导，CUSTOM 应保留原意并校验新模型能否承载。发布时把最终有效数值与来源写进冻结规格，避免后续默认值升级改变旧版本含义。

追问：早期数据库记录没有来源字段，迁移怎么设计？

追问回答：先确定遗留配置的兼容语义，针对可辨认的旧显式设置保留 CUSTOM，其余采用定义明确的 LEGACY/UNSET 规则并在迁移中记录来源。迁移测试覆盖默认恰好等于用户手填值的情况；仅从“数值等于当前默认”无法反推出用户原始选择，所以应以历史请求合同和旧版本解释规则为依据。

源码定位： 配置来源

SYS08．怎样证明框架没有侵入核心业务？

回答：业务不变量放在 AgentHub 自己的领域模块：权限由 TenantService 和 WorkspaceExecutionContext 管理，工具风险由 ToolPolicy 判定，Action 的领取与结果分类进入 PostgreSQL，费用由 Run Budget Ledger 管理。LangGraph 负责组织节点与恢复执行流，LiteLLM 负责与不同模型接口通信。框架更换时，应主要修改适配层；审批身份、租户范围、外部未知结果这些领域语义仍由业务代码决定。

追问：LangGraph 自带 checkpoint，为什么仍需要持久的 Run 与 Approval？

追问回答：Checkpoint 保存图执行位置和必要状态；Run 提供用户可查询的业务身份、生命周期、模型事件与用量；Approval 保存具体工具修订、参数哈希、决策者和执行结果。Worker 崩溃后需要先检查执行租约及外部动作是否已派发，再决定从哪个 checkpoint 恢复。三个记录共同解决执行过程和真实副作用。

源码定位： 工程规则

SYS09．你怎样从一个 UI 按钮定位到数据库操作？

回答：以点击 Publish 为例，我先找到前端按钮的事件函数和 API client，确认请求路径 /workspaces/{workspace_id}/agents/{agent_id}/publish、参数与返回值；再从 apps/api/routes/agents.py 进入 AgentPublishService.publish()，追踪 get_workspace_context() 的授权、_load_agent(...for_update=True) 的锁、_resolve_draft_spec() 的依赖解析及最后 session.commit()。异步功能还要继续追 queue.py、Celery Task、持久 Job 状态和页面轮询。

追问：接口返回 HTTP 202 后，怎样确认任务完成？

追问回答：202 对应请求已受理。前端应保存返回的 Run/Job ID，读取状态或订阅事件，直到看到数据库认可的 SUCCEEDED、FAILED、NEEDS_ATTENTION 等终态。比如文档上传成功只是创建 Revision 和 IngestionJob，真正可检索要等 READY 和索引确认。

源码定位： 路由装配

SYS10．仓库 README、旧设计文档与源码冲突时怎么办？

回答：我把 README 视为入口说明、设计文档视为某阶段方案、代码视为指定提交的实现，运行记录视为某环境实际发生的行为。核对时先固定 commit SHA，然后沿路由、Service、模型和测试读一条真实路径。比如旧文档可能仍写 Memory 默认关闭，而新 Agent 草稿创建路径默认启用 USER 作用域；应按当前 publish.py 的字段生成逻辑解释。若要描述线上，则进一步查部署镜像、迁移版本和运行配置。

追问：发现 main 已修复的问题，但部署环境仍报错，怎么判断？

追问回答：先核对运行实例的 Git SHA/镜像摘要与 Alembic 版本，再查配置开关、Worker 镜像与队列消费者是否同步更新。若代码已部署，继续比对请求路径、数据状态和错误 Step。以版本身份切分问题，比单看 main 或旧截图更快定位。

源码定位： 新草稿创建

SYS11．JWT 里为什么不直接保存所有工作区权限？

回答：JWT 中主要保存 sub、jti、iat 和 exp 等身份声明，工作区权限由服务端查组织成员关系、工作区成员关系后用 resolve_permissions() 计算。用户可能在 Access Token 有效期间被移出某个工作区；运行入口使用当前数据库成员状态，就能及时改变该工作区的可操作范围。将全部权限写进令牌还会放大令牌、耦合租户数量和角色演进。

追问：每次访问都查成员关系，性能压力怎样处理？

追问回答：先量化授权查询的耗时和数据库负载，配合 (organization_id,user_id)、(workspace_id,user_id) 等实际访问键设计索引。高并发时可使用短 TTL 的授权缓存，并在成员变化时主动失效，关键写操作仍保持权威校验。缓存设计需要明确撤权时延，避免性能优化改变安全合同。

源码定位： JWT · 授权解析

SYS12．用户是 Organization MEMBER，为什么不自动拥有所有 Workspace 权限？

回答：OrganizationMembership 表示用户属于某组织，WorkspaceMembership 表示普通成员具体参与哪个工作区。当前 OWNER/ADMIN 在 TenantService.get_workspace_access() 中走组织级管理员分支；组织 MEMBER 必须有对应 WorkspaceMembership，再由 DEVELOPER、VIEWER 解析实际权限。因此同一个组织成员可以参加 W1 的研发，却没有 W2 的任何访问能力，符合多工作区协作场景。

追问：管理员的 workspace_role 是 None，是否应该拒绝？

追问回答：None 在组织管理员分支表示不需要单独工作区成员角色，resolve_permissions() 会先判断 OrganizationRole 并返回管理员权限集合。只有普通 MEMBER 且缺少 WorkspaceMembership 时才得到空权限。业务路由以 context.permissions 判定，不应该只拿 workspace_role 是否为空做决策。

源码定位： RBAC

SYS13．VIEWER 是不是允许读取所有 GET 接口？

回答：HTTP 的 GET/POST 是传输方法，权限由资源类型和敏感范围决定。AgentHub 的 VIEWER 可以读取一般工作区与部分评测视图，但客服记录、审批、模型凭据和管理动作有各自权限；HOLDOUT 参考答案也需要额外投影保护。每个 Service 用 WorkspaceExecutionContext.permissions 检查操作，响应 Schema 再筛除不应展示的字段。

追问：后端已鉴权，前端为什么还要展示权限信息？

追问回答：前端根据服务器返回的 permissions 显示可执行操作并解释禁用原因，减少用户点击后才得到 403 的摩擦。例如 VIEWER 可以阅读运行状态，但 Publish 按钮标注需要 agent_edit。真正请求仍由 Service 校验，前端权限只负责交互一致性。

源码定位： 权限集合

SYS14．如何防止用户把 URL 中的 workspace_id 换掉？

回答：URL 中的 workspace_id 是用户提出的目标，不是授权事实。get_workspace_context() 读取该 Workspace 的组织归属、当前用户组织成员关系、普通成员工作区成员关系，并生成可信 Context。之后 Agent、Run、Tool 等查询同时限定资源 ID 和 context.workspace_id；工具执行沿用服务器 Context，模型参数无法覆盖目标工作区。复合外键进一步保证跨表关联不会把不同租户记录错配。

追问：既然资源 ID 是随机 UUID，还需要所有权过滤吗？

追问回答：需要。日志、链接、共享页面与错误响应都可能暴露 UUID；访问控制应对任何已知 ID 都成立。集成测试可在两个工作区创建同类对象，用 W1 身份请求 W2 ID，检查响应与数据访问均被限制。

源码定位： 租户访问 · 工具上下文

SYS15．认证、资源不存在、权限不足为什么可能分别返回 401、404、403？

回答：401 对应令牌缺失、失效或用户身份无法成立；403 对应用户身份有效，但没有执行某项操作的权限；404 既用于资源确实缺失，也可在跨租户范围下隐藏资源存在性。比如合法 VIEWER 发布 W1 Agent 得到 403；组织成员访问未加入的 W2，TenantService 可以返回 404。409 和 422 分别用于状态冲突与参数/业务合同不成立，前端据此给出有针对性的处理。

追问：所有接口都返回 200，再通过 JSON error.code 区分是否更统一？

追问回答：统一的 error.code 应保留，同时使用准确的 HTTP 状态。401 触发会话恢复、403 告知权限不足、404 走资源缺失、409 让页面处理并发冲突、503 才进入可用性重试。若全用 200，浏览器、网关和 SDK 无法按标准语义处理。

源码定位： 访问服务

SYS16．为什么密码用 Argon2，而 Refresh Token 存 SHA-256 哈希？

回答：密码由用户选择，常有低熵、复用和可预测模式，因此使用 Argon2 这类自带盐与计算成本的密码哈希，提高离线猜测代价。Refresh Token 用 secrets.token_urlsafe(64) 生成高熵随机值，数据库仅保存它的 SHA-256 摘要用于精确查找。两个值都不能明文存进业务表，但算法选择由输入熵和使用方式决定；Refresh Cookie 保存原始随机令牌供客户端续期。

追问：直接使用 SHA-256 存储用户密码会怎样？

追问回答：SHA-256 计算过快，攻击者可批量尝试字典与撞库密码。密码应使用 Argon2id 等带参数的专用密码哈希，并规划成本升级；登录校验时比较派生值，绝不通过解密取得原始密码。

源码定位： 认证安全实现

SYS17．Refresh Token 轮换解决什么问题？

回答：Refresh Rotation 让每个 Refresh Token 只使用一次。AuthService.refresh() 通过 get_for_refresh_update() 锁定 Session，检查 used_at/rotated_at，在同一事务里标记旧令牌、创建新 Session、写入 replacement_session_id 并提交。复用旧令牌触发 family 撤销，防止被盗令牌持续换取新 Access。这个机制同时要求浏览器协调多个标签页的刷新时序。

追问：为什么 AuthSession 要保存 replacement_session_id？

追问回答：它明确表示 R0→R1→R2 的轮换关系，便于审计一次刷新是否真正产生替代 Session、回溯复用发生的位置及管理同一 family。与 token_hash、family_id、used_at、expires_at 配合，可解释一个用户设备会话完整的生命周期。

源码定位： 刷新服务

SYS18．多标签页刷新为什么会造成误登出？最新如何处理？

回答：多个标签页共享 Refresh Cookie。当 A、B 同时带 R0 续期时，A 在行锁内轮换为 R1，B 随后发现 R0 已使用，可能触发 Family Reuse 保护而让正常用户登出。AgentHub 前端在单页用 single-flight 让同批 401 等待一个 Promise，在支持 Web Locks 的浏览器中跨标签串行刷新，并在真正取锁后再发请求；服务端仍保持数据库级一次性轮换。

追问：浏览器没有 Web Locks 时怎样设计？

追问回答：当前可以保留同页面 Promise 合并，跨页面则通过新会话检测和清晰的登录恢复处理冲突。若要增强兼容，可评估 BroadcastChannel 协调和带会话代次的领导者选举，测试旧页挂起、异常关闭与令牌轮换竞争，再决定跨标签降级协议。

源码定位： 前端认证

SYS19．用户切换账号后，一个旧请求返回 401，能否直接清空当前会话？

回答：浏览器中可能同时存在旧账号未完成的请求和新账号的当前 Session。旧请求的 401、刷新成功或请求错误不能改变新会话。前端记录请求发起时的 session/generation 身份，收到响应后先核对身份代次，再决定是否更新 Token 或清空状态。session-provider 的身份隔离与 client.ts 的 Refresh 合并分别处理状态归属和网络并发。

追问：只比较 user_id 是否够用？

追问回答：同一个用户登出再登录，也产生了新的会话代次。应该比较会话世代或对应的登录实例身份，而不只是用户 UUID。测试可构造 A 会话请求挂起、登出重登录 A、旧 401 最后返回，确保新会话继续保持有效。

源码定位： 会话状态

SYS20．登出后，旧 Access Token 会立即完全失效吗？

回答：登出会撤销关联 Refresh Family、清理 Refresh Cookie，使该设备会话无法继续续签。当前普通 Access JWT 的请求验证检查签名、有效期以及用户启用状态，没有对每个 jti 做在线吊销查询，因此存量 Access 按自身有效期结束。工作区成员关系仍在每次工作区访问时校验，所以管理员撤权可以改变相关业务 API 的后续访问结果。

追问：如果产品要求立即吊销某一台设备的 Access 权限，怎样扩展？

追问回答：给 Access 增加可核验的 session_id/version 绑定，在鉴权时读取或缓存设备会话状态；注销设备时增加版本或写入吊销记录并触发缓存失效。实现时要同时规定多设备独立性、撤销传播延迟和查询成本。

源码定位： 认证服务 · 认证依赖

SYS21．HttpOnly Cookie 是否彻底解决了 XSS 和 CSRF？

回答：HttpOnly 限制页面 JavaScript 读取 Refresh Cookie，Secure 约束其安全传输，SameSite 和 Path 缩小浏览器自动附带 Cookie 的请求范围。AgentHub 将 Access 放在 Bearer 请求中、Refresh 放在指定路径的 Cookie 中，减少日常业务请求暴露续期凭据的机会。XSS、CSRF 分别涉及脚本执行和浏览器跨站代发请求，防护还需要输入输出编码、认证端点的来源规则及敏感操作授权。

追问：怎样给 AgentHub 当前 Cookie 设计一组实际测试？

追问回答：读取 apps/api/routes/auth.py 和 Settings 中的 Cookie 参数，验证登录/刷新/登出的 Set-Cookie 属性；从不受信站点构造跨站请求，检查是否携带 Cookie 及端点是否接受；再测试带恶意文本的 Artifact 和 Wiki 页面是否正确转义。把令牌保护和页面脚本保护分别验证。

源码定位： Cookie 设置

SYS22．为什么需要保护最后一个 OWNER？并发时怎么保护？

回答：组织至少保留一位 OWNER，保障成员管理和组织恢复。若两个 OWNER 同时降级，单独先 count 再 update 可能各读到数量为 2，最终变成 0。TenantService 对组织成员关系建立一致的行锁顺序，在事务中读取当前角色、检查 Owner 数量并修改；_check_last_owner() 在真实写入边界维持这一不变量。并发测试应让两个变更同时进入关键区，期望最终至少留一个 OWNER。

追问：只有 if owner_count <= 1 为什么挡不住并发？

追问回答：判断和写入之间有竞争窗口。需要让所有相关角色变更遵循同一种事务锁定协议，或者建立其它数据库可串行化约束；在锁内重新读取当前角色并确认数量。否则两条各自看起来正确的请求仍会共同破坏组织状态。

源码定位： 成员服务

SYS23．组织 ADMIN 能不能把自己或别人改成 OWNER？

回答：Organization ADMIN 与 OWNER 都可获得较广泛的工作区管理权限，但成员管理中的 OWNER 角色提升受专门业务规则约束。TenantService.change_organization_member_role() 检查操作者组织身份、目标成员角色和所有者保护，不能仅凭界面显示 ADMIN 就允许任意提升自己或其他人。UI 按服务器权限显示常规功能，特权角色变更则继续由后端服务实施细粒度判定。

追问：为什么 permissions 有管理权限仍可能遇到业务拒绝？

追问回答：权限集合表示“可进入这种操作类型”，业务状态决定“这次操作是否有效”。例如组织管理员可以管理一般成员，但不能越权授予 OWNER；即使 OWNER 也不能删除唯一剩余的 OWNER。测试要同时覆盖角色组合、目标关系和并发状态。

源码定位： 角色变更

SYS24．用户被移出工作区，已有运行是否仍然有权限？

回答：Worker 收到队列消息后，会从数据库重新加载 AgentRun、创建者和工作区成员关系，再经 TenantService.get_workspace_access() 检查 agent_run 权限。这样用户排队后被移出工作区，未开始的执行会尊重最新授权。长时间运行中的权限变化，还要在恢复和关键外部动作入口按执行合同复核；历史 Run 的事实和当时事件仍按其原身份保存。

追问：撤权发生时，如果外部写入已经派发怎么办？

追问回答：撤权阻止后续未经授权的动作，已派发操作按其 Action/Approval 和远端回执结算。记录 MAYBE_DISPATCHED 或 UNKNOWN_OUTCOME 时，使用业务查询、operation_id 或人工对账确认实际结果；需要撤销则建立独立补偿动作，保留原操作记录。

源码定位： 授权上下文 · 运行恢复源码

SYS25．按用户隔离 Memory 是否意味着整个个人助手都私有？

回答：USER 作用域 Memory 依据 owner_user_id 将长期记忆选择限制到运行创建者，这解决了记忆条目的用户级分区。Thread、Turn、Run、Artifact、反馈和人工接管仍有各自的访问与共享规则。个人助手是否实现端到端私有，需要逐一审查这些派生对象的归属、阅读权限、跨角色操作和导出/删除行为。AgentHub 的 Memory Store 已实现 OWNER 过滤，Runtime 选择时把创建者身份传入底层。

追问：要把整个 Agent 做成严格个人私有工作区，应改哪些地方？

追问回答：先为 Thread/Run/Artifact/Feedback 建立一致的 owner_user_id 与访问谓词，逐个检查列表、详情、搜索、SSE、导出、管理员及后台执行入口；然后明确协作分享、撤权和历史审计规则。集成测试覆盖两名用户在同一 Workspace 中用相同资源 ID 互访、后台 Worker 读取和历史来源重放。

源码定位： Memory 模型 · 权限集合

SYS26．MCP 解决的是什么，没解决什么？

回答：MCP 把远端工具发现、Schema 描述与调用包装为共同协议。AgentHub 可以通过 McpConnection 接到订单、运维或数据仓库 MCP Server，并从 tools/list 导入具体 ToolRevision。业务权限、风险分级、审批、凭据管理、SSRF、防重和执行结果确认仍由 AgentHub 的平台服务负责。协议解决工具交互格式，治理服务决定哪些工具可以进入 AgentVersion、谁能调用以及如何记录结果。

追问：发现远端工具的 Schema 合法，能直接认为这个工具可信么？

追问回答：远端名称、描述和 annotations 都按外部输入处理。导入时验证 Schema 与 Effect/Approval 合同，连接时限制网络目标，执行时重新检查工具归属和参数；返回结果仍通过受控 ToolResult 投影给模型。像 issue_refund 这样的 WRITE 需要批准具体动作，再依据明确回执保存结果。

源码定位： MCP 服务

SYS27．发现工具为什么不能直接当作导入成功？

回答：Discover 返回的是某个时刻远端声明的工具列表，用来供管理员选择；Import 会重新发现目标工具、验证参数结构、配置本地 identity/effect/risk/approval，并在数据库事务中创建 Tool 和首个 ToolRevision。随后还要绑定 Agent 草稿、发布 AgentVersion，才进入可执行工具集。把 Discover 直接当 Import，会让浏览工具目录等同于授予执行权限，破坏管理与运行之间的控制点。

追问：为什么点击 Import 时还要重新读取远端？

追问回答：管理员浏览页面到正式导入之间，远端可能升级 Schema、改工具名或删除工具。Import 根据当时重新验证的工具声明创建冻结修订，避免把浏览器保存的过期数据写入发布合同。后续变化再生成新 Revision，由管理员重新发布绑定。

源码定位： 发现与导入

SYS28．Tool、ToolRevision、McpConnection、逻辑动作 ID 有何区别？

回答：Tool 是管理级身份，ToolRevision 是参数、风险与远端映射的不可变修订，McpConnection 管远端 Endpoint 与认证凭据，逻辑动作 ID 则代表某次 Run 提出的具体业务操作。一个 Connection 可发现多个工具；一个 Tool 可拥有多个 Revision；同一 Revision 可被多个 AgentVersion 使用；一次批准只能绑定指定参数与动作序号。分层后工具升级、凭据轮换与审批追溯可以独立演进。

追问：模型供应商返回的 tool_call_id 可否拿来全局去重？

追问回答：Provider ID 主要用于把一次模型回复里的调用与 ToolMessage 对齐，不具有跨重试、跨模型和长期业务稳定性。AgentHub 用 workspace、Run、ToolRevision、规范化参数哈希和 proposal ordinal 形成 logical_action_id；外部系统如支持幂等，另向其传受双方认可的稳定 operation_id。

源码定位： 工具模型 · MCP 服务

SYS29．当前真的支持任意 REST 工具注册吗？

回答：当前生产工具入口以受控 Builtin Registry 和 MCP ToolRevision 为主，管理员导入远端 MCP 工具，不等于可以随意配置任意 REST URL、方法、Header 和请求体并作为通用工具运行。若开发 REST Tool，需要像 MCP 一样提供可冻结的输入输出 Schema、凭据引用、风险/审批策略、租户授权与响应归一化，还要设计出站网络目标保护和写入结果分类。

追问：设计一个通用 REST Tool Executor，除了 httpx.post() 还需要什么？

追问回答：定义 ToolRevision 对 HTTP 方法、路径、参数模板及响应 Schema 的不可变合同；秘密以连接引用在运行时解析；限制 DNS、重定向、Peer、响应大小和超时；对 READ/WRITE 分流，WRITE 走 Approval/Action Claim；对超时与模糊回执保存未知结果并支持远端幂等和对账。

源码定位： 工具合同 · 规格校验

SYS30．READ 为什么也可能高风险？

回答：READ 表示平台预计没有持久业务写入，但读取生产日志、客户隐私或核心运营数据仍可能具有高敏感性。AgentHub 的 ToolPolicy.decide() 允许 effect=READ、approval_policy=NEVER 且 requires_human=False 的工具自动执行；HIGH 风险和 MCP WRITE 会进入人工要求。当前 MCP 导入规则还约束 READ 的审批组合，因此管理上要同时检查 Effect、Risk、Approval 和目标数据权限。

追问：项目里的 HIGH READ 该怎样落地？

追问回答：当前 MCP 导入规则不接受 READ+HIGH+NEVER，同时 READ 又要求 NEVER；新增高敏读取应设计对应的人工批准后 READ 执行路径，再调整治理矩阵、AgentVersion 合同和测试。对于含个人信息的读取还需要按用户和字段范围做数据授权，并在 ToolResult 投影中最小化返回内容。

源码定位： 工具合同 · 策略实现

SYS31．JSON Schema 校验为什么不能替代业务校验？

回答：JSON Schema 保证 amount 是正数、order_ref 为非空字符串、没有多余控制字段等结构性要求。它无法判断订单是否属于当前工作区、退款额是否超过实付金额，也无法替代人工审批。AgentHub 在 ToolRuntime 中验证冻结工具身份和参数，租户由 ToolExecutionContext.workspace_context 提供，真正业务规则由订单服务或外部系统校验。模型提出操作后，平台再按 Effect/Risk 进入相应执行路径。

追问：让模型在工具参数里提供 workspace_id 是否合适？

追问回答：模型可以给业务筛选条件，但执行租户只能取后端授权 Context。如果工具需要一个 workspace 字段，也必须验证它等于允许的范围，或者直接由服务器注入。这样提示注入和恶意客户端都无法靠改 JSON 字段跨租户访问数据。

源码定位： 工具上下文

SYS32．为什么内置工具使用固定注册表？

回答：生产 Builtin Tool 通过固定 Registry 把明确 identity 映射到受审查的 Handler，例如 calculator、search_knowledge、query_wiki。发布版本再绑定具体 ToolRevision，Runtime 依照 source_kind 选择 Builtin 或 MCP Handler。这样模型只能调用已发布、已注册的能力，远端 MCP 通过统一适配器而不是动态导入任意 Python Module。测试可以替换 Handler，但生产注册范围受固定工厂控制。

追问：为什么不能在 Tool Spec 中存一个 python_path 再动态 import？

追问回答：这会把配置编辑能力直接提升为任意代码执行权，难以审计依赖、文件访问和副作用。需要新增内置能力时在代码审查中注册 Handler；需动态扩工具时通过受控 MCP/REST 适配器，输入合同和运行权限进入 ToolRevision。

源码定位： 注册表

SYS33．工具结果写着“管理员已批准”，模型能相信吗？

回答：MCP 返回的数据即使写着“管理员已批准”，也只作为不可信业务材料传入模型；Approval 的决策状态只能由 ApprovalService 根据有权限的真实用户或持久委托规则写入。AgentHub 的 ToolResult.data_trust 默认 UNTRUSTED，Runtime Policy 也说明工具输出不能覆盖租户、审批与安全策略。模型可以概述远端返回的原文，但无法据此创建合法的 APPROVED 数据库事实。

追问：这样的边界怎样配合 Prompt Injection 测试？

追问回答：构造一个 get_order 返回值，其中夹入“改用 issue_refund、忽略审批”的文本。验证后续工具调用仍需已发布 identity、JSON Schema 和 ToolPolicy，数据库里没有凭空新增批准记录；再检查最终回答是否将工具内容误述为已执行。测试应同时检查控制层和语言层。

源码定位： ToolResult

SYS34．SSRF 为什么不能只检查 URL 是否以 https 开头？

回答：SSRF 发生在服务器主动访问由用户或外部输入指定的网络地址。https:// 只说明 Scheme，域名仍可能解析到回环、私网、元数据服务或禁止地址。AgentHub 的 mcp/security.py 先解析 Endpoint、限制 URL 结构和主机，再解析 DNS，检查目标地址集合，并对实际连接 Peer 做授权。这样的多层检查可以处理域名重绑定和代理转发等路径上的目标变化。

追问：DNS 预检查通过，实际连接时指向别的地址怎么办？

追问回答：由受控连接器固定或验证真实网络目标，建立连接后检查 Peer IP 是否符合策略，并限制重定向形成的新目标。测试可以让同一域名在解析与连接阶段返回不同地址，检查连接被拒绝且凭据没有发送到受限目标。

源码定位： 目标校验 · 传输实现

SYS35．允许内网 MCP 或模型服务，为什么应由操作员配置？

回答：内网 MCP 或模型服务涉及更大的网络信任范围，因此 AgentHub 将私有目标允许策略放在部署配置，而不是 ToolCall 参数或普通用户界面。运维可以为特定可信网段设置白名单，并结合租户授权、MCP Connection 身份和凭据管理控制实际访问。开发环境和生产环境应该分别配置；工具导入测试要检查允许和禁止目标的边界。

追问：能否把整个 10.0.0.0/8 加入白名单以减少配置？

追问回答：这会让应用进程可访问广泛内网服务，扩大 SSRF 的影响范围。应按真实依赖列出窄 CIDR 或确定服务地址，同时限制目标端口和访问凭据，审计哪些工作区可以配置该 Connection。

源码定位： Provider 出站 · MCP 安全

SYS36．为什么密钥加密和日志脱敏需要同时做？

回答：AgentHub 的远端模型和 MCP 凭据在存储时加密，运行时由受控服务解密，API 对普通用户返回脱敏投影。日志和 Trace 另外需要隐藏 Authorization、完整 Token、Cookie、包含秘密的 URL、异常对象及用户上传的敏感内容。两者保护不同路径：数据库加密防止直接读取存储副本，日志脱敏防止密钥随调试信息进入集中日志、告警和外部监控。

追问：凭据主密钥丢失以后怎样恢复？

追问回答：密文的恢复依赖独立保存并备份的主密钥或 KMS。灾备方案要同时备份数据库、加密主密钥及其版本，轮换时保持新旧密文兼容直到迁移完成。JWT 签名密钥和凭据加密主密钥应分开管理，因为用途、轮换和泄露影响不同。

源码定位： 凭据加密 · 安全错误

SYS37．远端工具调用超时，为什么不能统一重试三次？

回答：远端 READ 在幂等前提下可以按限定策略重试，远端 WRITE 超时后却可能已经执行。AgentHub 的 MCP Client 区分 NOT_DISPATCHED、MAYBE_DISPATCHED、DEFINITE_RESPONSE，ActionRuntime 将可能派发而没有明确结论的写入记录为 UNKNOWN_OUTCOME。对 issue_refund 盲目重发会造成第二次退款，所以恢复时应查询原 operation_id 或远端业务状态。

追问：如果远端明确支持 Idempotency-Key，重试设计怎样改变？

追问回答：以审批绑定的稳定逻辑动作身份派生业务键，每次重试传相同 Key，并要求远端保证同 Key、同参数复用同一结果；参数改变时生成新动作。还要定义幂等记录保留期、查询结果端点和状态回执。此时可以对特定失败类型实施安全重试，而不是每次生成随机新 UUID。

源码定位： MCP client

SYS38．为什么远端 annotations 不能决定平台风险？

回答：MCP Annotation 中的 readOnlyHint、idempotentHint 属于远端自述信息，用来辅助管理判断。AgentHub 的平台策略由本地 ToolRevision 的 Effect、Risk 和 Approval 决定；导入时重新发现远端 Schema，发布时绑定具体 Revision 与 Hash。远端之后改描述、工具参数或风险提示，不应让已有 AgentVersion 默默获得新能力，而应通过新的导入/修订与发布流程生效。

追问：发现同名远端工具的 Schema 变了，应如何处理？

追问回答：记录旧修订与发现到的新 Schema 差异，重新验证参数和输出合同，创建新 ToolRevision，安排 AgentVersion 升级。已有版本继续按旧 Schema 校验；若远端已经不再兼容，可禁用连接或在执行阶段报告明确的合同错误，而不是静默向模型暴露新参数。

源码定位： 导入服务

SYS39．通用错误信息会不会妨碍排障？

回答：对用户显示稳定的 error.code 和安全文案，例如 MCP_TOOL_CALL_FAILED，可以避免把内部地址、Authorization 或供应商异常栈泄露给浏览器。排障通过 request_id、Run、Step、ToolCall、Trace Span 和受控内部失败分类关联；支持团队看到足够的阶段和原因信息，又不读取完整秘密。项目在 MCP Client 的异常归一化、API 错误响应和业务记录中分别承担这些职责。

追问：脱敏后的 API 响应安全，是否意味着所有日志都安全？

追问回答：日志采集链还有 HTTP 客户端异常、框架 debug 输出、Worker 重试堆栈和 Trace 属性。可以用含测试假密钥的请求检查应用日志、Worker 日志、监控导出与错误页面是否出现原文，并设置明确的允许字段列表。

源码定位： 错误封装 · 处理器

SYS40．新增一个工具，你的验收会覆盖什么？

回答：新增工具的验收沿完整链路进行：创建 Connection、Test/Discover、Import ToolRevision、配置 Effect/Risk/Approval、绑定 Agent 草稿、发布 AgentVersion，再触发真实 ToolCall。测试包含参数类型和多余字段、跨租户、失效 Connection、审批绑定、并发 Claim、远端成功/失败/超时、输出 Schema 以及 Run 证据。最后检查模型获得的 ToolResult 与用户页面的业务状态一致。

追问：为什么只测 Handler 通过还不够？

追问回答：Handler 单测覆盖一个执行函数，却绕过了管理员导入、版本 Hash、权限、参数准入、审批和结果投影。应增加 API+数据库集成测试和受控 MCP Server 端到端测试，尤其检查“已批准但未派发”和“已派发但结果未知”两类状态。

源码定位： 工具校验 · MCP 服务

SYS41．PostgreSQL、Redis、Qdrant 为什么不能相互替代？

回答：PostgreSQL 是 AgentHub 的权威业务库，保存 AgentVersion、Run、Revision、Approval、评测和约束；Redis 是 Celery Broker，承担短期任务消息交付；Qdrant 为 Dense/Sparse 检索提供索引与过滤。任务消息丢失可以从数据库 Job 对账，Qdrant 索引要与文档修订状态对应；三个组件分别优化事务一致性、异步调度和向量检索。用户看到的 READY 来自受控持久状态，而不是“Redis 中没有消息”或“向量库有 Point”。

追问：为什么不全部统一到 PostgreSQL？

追问回答：在小规模场景，PostgreSQL 的队列模式和 pgvector 等能力可以替代部分外部组件，但要比较 ANN 召回延迟、Hybrid 检索、批量写入、事务热点、Worker 并发与运维复杂度。选型应以实际查询、数据量和运维需求决定；当前代码已围绕 Qdrant Scope 和 Celery Queue 建立可替换的接口边界。

源码定位： 部署与数据分工 · 项目入口

SYS42．有应用层检查，为什么还要数据库约束？

回答：应用层在执行前解释业务规则并返回清晰错误，数据库约束在并发和异常路径中守住最终关系。例如发布 Agent 使用行锁与 (agent_id,version_number) 唯一约束，Chunk 使用完整归属复合外键，Memory 使用作用域相关唯一索引。多个入口同时写入时，最终由数据库对不变量做仲裁。应用校验缩短无效路径、转换错误，数据库则承担最后一致性边界。

追问：有唯一约束以后，代码是否可以完全取消校验？

追问回答：仍需在 Service 层检查权限、状态转换与用户可理解的失败原因。数据库约束只能表达部分不变量，不能决定“此用户是否有权审批”或“某次外部写入是否已经派发”。并发冲突要捕获 IntegrityError，rollback 后映射为稳定业务 409。

源码定位： 知识模型 · 0061

SYS43．两个外键分别有效，为什么组合仍可能错误？

回答：假设 Chunk 保存 document_id=D2、document_revision_id=V1，而 V1 实际属于 D1。两个普通外键分别确认 D2、V1 存在，无法保证配对正确。项目在 DocumentChunk 中加入 (workspace_id,knowledge_base_id,document_id,document_revision_id) 的复合外键，引用 Revision 中同一组唯一身份。这样 Chunk 不能跨文档、跨 KB 或跨租户挂到其它 Revision。

追问：为什么被引用的父表需要相应唯一键？

追问回答：数据库的外键目标必须由主键、唯一约束或适用的唯一索引稳定标识。复合引用需要父表上相应列组具备可引用的唯一性；迁移还要先检查历史错配，避免新增外键时因脏数据失败。0061_chunk_document_revision.py 就是适合走读的真实案例。

源码定位： 分块约束

SYS44．行锁和乐观版本控制怎么选？

回答：行锁适合维护短事务中的串行不变量，比如发布版本时锁定 Agent 草稿，或成员变更时锁定组织成员关系；乐观版本适合用户读—改—保存之间可能间隔较长的场景，例如工单 expected_version，更新时检查版本相等，冲突返回 409。AgentHub 两种方式都会用：数据库锁维护同一时刻的写入顺序，乐观版本防止用户基于过期页面覆盖他人的决定。

追问：工单版本冲突时能自动读取最新状态再重试原操作吗？

追问回答：应重新展示当前状态和差异，让用户确认。比如用户认为工单仍 OPEN 才点击 CLOSE，但此时另一人已改成 ESCALATED；直接重试会把旧意图强行施加在新状态上。只有业务定义明确的幂等动作才适合自动重放。

源码定位： 客服状态修改

SYS45．唯一约束为何不等于完整幂等？

回答：唯一约束保证一个键不会出现两行，但完整幂等还包含“同一个请求再次到来时应该得到什么”。AgentHub 的 Thread 使用 client_token 区分一次逻辑提交，并校验相同 Token 是否对应同一请求内容；工单等业务也需要稳定键与结果复用机制。第一次事务已经提交而响应丢失时，客户端使用同一请求身份重试，服务端返回原结果或查到已完成的状态，而不是产生第二次写入。

追问：前端超时后生成新 Idempotency-Key 再提交行不行？

追问回答：新 Key 代表新逻辑操作，可能再创建一张工单或一个 Turn。客户端应在发送前生成并保存 Key，在确认结果前复用同一 Key；服务端需要把 Key、请求内容摘要和结果关联保存，遇到同 Key 不同内容返回冲突。

源码定位： 发布与业务约束 · 客服服务

SYS46．为什么模型调用期间长期持有事务会拖垮系统？

回答：模型和 MCP 请求可能持续数秒甚至数分钟。若在 AsyncSession 的事务中等待外部网络，连接与锁会持续占用，其他发布、审批或进度查询容易排队。AgentHub 对长 Run 先用短 Session 取授权上下文，关闭 Session 后再开展耗时执行，具体状态更新分别进入短事务；Worker 同样依赖独立的持久 Run/Job 身份恢复，而不是持有一个从头到尾的数据库事务。

追问：把连接池 pool_size 调大能直接解决吗？

追问回答：只能暂时增加并发连接上限，也可能使 PostgreSQL 同时承受更多事务、锁和内存开销。应先测 pool checkout wait、事务持续时间、锁等待与慢 SQL，把模型网络等待移到事务外，再根据数据库资源和请求分布调整池大小。

源码定位： 数据库工厂

SYS47．flush、commit、refresh 各自什么时候用？

回答：session.add() 把对象纳入 Unit of Work；flush() 让 INSERT/UPDATE 在当前事务中执行，从而可取得数据库生成 ID 或触发约束；commit() 完成事务提交；refresh() 主动重新读取数据库生成或服务器更新的字段。AgentVersion 先 add() 再 commit()，审批和工单更新则需要在事务中完成状态检查。异步 ORM 要避免响应序列化阶段触发未预期的隐式数据库查询。

追问：设置 expire_on_commit=False，为什么还会用 refresh()？

追问回答：它保证普通已加载属性在 commit 后保留，但数据库默认值、触发器结果或特定服务器生成字段可能需要显式回读。应根据 SQLAlchemy 模型的 server_default、RETURNING 和需要返回的字段决定是否 refresh，而不是为了“保险”每次无差别刷新。

源码定位： 发布服务中的事务

SYS48．如何为一个查询设计索引？

回答：索引设计从实际 SQL 的过滤、关联、排序和分页开始。例如查询某工作区最近 50 条 Run，核心条件是 workspace_id 与 created_at，通常考虑相应复合索引；审批队列查询常结合 decision_status 和时间范围。通过 EXPLAIN (ANALYZE, BUFFERS) 对比扫描行数、索引访问、排序与缓冲命中，再检查锁等待和连接池。选择性、实际行数和查询排序比“某列常用”更重要。

追问：列上明明有索引，查询为什么仍然很慢？

追问回答：可能需要返回大比例行，优化器选择 Seq Scan；也可能表达式使索引失效、ORDER BY 触发大排序、统计信息过时，或者时间主要花在连接与锁等待。先拿实际 SQL 和执行计划，拆分数据库时间与接口时间，再决定建复合索引、改分页还是缩短事务。

源码定位： 分块索引

SYS49．为什么 Memory 使用部分唯一索引？

回答：Memory 既支持共享分区，也支持 USER 私有分区。NULL 在普通唯一索引中往往不会按“同一个值”处理，因此要用带条件的唯一索引分别约束共享记录和含 owner_user_id 的私有记录，避免同一内容在同一分区被并发插入多次。packages/memory/models.py 中的部分唯一索引与 Store 的幂等写入协同，既表达隔离语义，也提供并发仲裁。

追问：迁移脚本定义了条件索引，但 ORM 模型漏掉谓词会怎样？

追问回答：模型与真实 schema 的差异会影响自动迁移比较及后续维护。应让 Alembic 迁移与 SQLAlchemy 元数据定义同一个索引谓词，检查实际 PostgreSQL DDL，并写共享分区、两个不同 USER、同 USER 重复内容的并发插入测试。

源码定位： Memory 模型 · 数据模型规范

SYS50．JSONB 用在哪里合适？

回答：JSONB 适合已版本化、结构复杂但主要按完整对象读写的合同，例如 AgentVersion.resolved_spec、工具配置、Run 的部分有效输入快照和评测 expected。用户、工作区、状态、版本与外键归属继续作为独立列，便于约束和索引。JSONB 的价值是保存复杂快照与演进字段，不是用一个大字段代替所有关系模型。

追问：后来发现频繁按 JSONB 里的某项条件过滤怎么办？

追问回答：先检查实际查询模式和选择性。稳定业务字段可以生成独立列并迁移回填，较灵活的路径可评估表达式或 GIN 索引。保持与原 JSON 合同之间的更新一致性，避免派生列长期漂移；查询计划需要在真实数据分布上验证。

源码定位： 版本发布 · 评测模型

SYS51．迁移为何不能交给每个 API 副本启动时自动运行？

回答：数据库迁移是部署级一次性控制动作，不应让每个 API 副本启动时同时运行 Alembic。AgentHub 的 Compose 使用独立 prepare 步骤，在 PostgreSQL 就绪后完成迁移和必要准备，再启动 API 与 Worker。多个副本若同时更改同一 schema，会竞争 DDL 锁、产生版本不一致和启动故障。生产发布还要安排代码与数据库的兼容顺序。

追问：如何把有破坏性的字段改动设计成低停机迁移？

追问回答：采用 expand–migrate–contract：先加兼容字段和双读/双写逻辑，再分批回填和验证，最后切换读取并删除旧字段；对于大型约束，先验证脏数据、分阶段建索引和加约束。版本发布中保证旧 Worker 与新 API 同时存活时仍能解析共用对象。

源码定位： 初始化 · Compose

SYS52．为什么 checkpoint schema 不完全交给业务 Alembic？

回答：业务 Alembic 管 Agent、Run、Approval、Revision 等业务 schema；LangGraph Checkpoint 由相应持久化组件管理，它保存图在暂停与恢复之间需要的执行状态。若只备份业务表却漏掉 Checkpoint，数据库可能仍显示 WAITING_APPROVAL，但恢复图缺少继续执行位置。恢复方案要把两类数据、文件 Blob、密钥和索引身份作为同一恢复点设计。

追问：恢复暂停中的 AgentRun，最少需要检查哪些对象？

追问回答：核对 AgentRun 的 Version、事件/Step、对应 Approval 状态、有效知识与历史快照，以及 LangGraph Checkpoint 绑定；然后确认恢复 Actor 当前有权，Action 没有处于未核实的已派发状态。满足这些条件才可以按业务状态继续图执行。

源码定位： Checkpoint bootstrap

SYS53．/health 返回正常，用户为什么仍然不能完成任务？

回答：/health 适合快速确认 API 进程能响应；/ready 和依赖探针进一步检查 PostgreSQL、Redis、Qdrant 等基础依赖。真正任务推进还取决于 Worker 是否消费、摄取租约是否续期、审批是否恢复以及模型路由是否可用。所以部署监控应把进程存活、依赖就绪和业务队列可推进性分开。AgentHub 在 apps/api/app.py 已提供 health、ready 和 dependencies 入口。

追问：怎样设计轻量的“业务可推进性”指标？

追问回答：观察队列最老消息年龄、PENDING/PROCESSING Job 的停留时间、租约续期错误、Run NEEDS_ATTENTION 比例、Worker 心跳及最近成功完成数。定期生成小型无副作用探针即可；真实模型长任务应单独安排，不放在每次 HTTP 健康检查里。

源码定位： 探测源码

SYS54．数据库有密文，为什么 Worker 仍可能无法调用模型？

回答：数据库里的供应商或 MCP Secret 经过加密，Worker 运行时必须用同一凭据主密钥解密，才能向实际 Provider 发送认证信息。若 API 与 Worker 使用不同 AGENTHUB_CREDENTIAL_MASTER_KEY，管理页面可能能读取密文记录，但后台调用失败。部署需要将凭据密钥按权限分发给必须解密的进程，并保证轮换期间版本兼容；JWT 签名密钥另行配置。

追问：为什么不把 JWT Secret 和凭据加密主密钥共用一个？

追问回答：JWT Secret 用于签发/校验身份令牌，Credential Master Key 用于可逆解密供应商凭据，两者的访问主体、轮换频率及泄露影响不同。分开以后可以独立吊销会话或轮换 Provider Secret，不让一类密钥运维影响另一类数据。

源码定位： 凭据实现 · 部署配置 · 安装脚本

SYS55．持久卷、备份和灾备演练有什么区别？

回答：持久卷让容器重建时数据目录继续存在；备份把数据库、Blob 和相关秘密保存到独立故障域；灾难恢复演练是在全新环境实际恢复并验证业务行为。AgentHub 的关键恢复对象包括 PostgreSQL 业务表、LangGraph Checkpoint、Blob 文件、凭据主密钥、Qdrant 索引和 Celery Job 状态。单有 Compose Volume 解决不了误删、磁盘损坏和不可用机器的问题。

追问：怎样验收一次 AgentHub 恢复？

追问回答：在隔离环境从同一时间点恢复数据和密钥，运行 Alembic 一致性检查，读取历史 AgentVersion 和 Run，验证 Blob 可访问、知识快照对应向量可检索、暂停审批保持正确状态；对未知外部写入走只读对账，不能恢复后自动重发。最终记录 RPO、RTO 和逐项恢复结果。

源码定位： 存储装配

SYS56．Qdrant 数据丢失但文档仍 READY，应该怎么办？

回答：Revision 的 READY 表示它完成过摄取流程，而 Qdrant 丢失以后，这个历史状态不会自动反映向量索引已损坏。需要通过快照成员、Chunk 和 Point ID 检查索引覆盖，利用持久源文件与编码配置重建向量，核验 Dense/Sparse 路径及检索结果后恢复服务。Revision 不应因临时索引事故直接覆盖旧内容，而应保持来源身份和重建记录。

追问：怎样实现可重复的一键索引重建流程？

追问回答：以 KnowledgeSnapshot 和 DocumentRevision 为输入，按当前可验证的 encoder fingerprint 重新生成缺失 Point，使用确定性 Point ID upsert；保存重建 Job 的租约、进度和失败原因，结束后比较预期/实际数量并抽样查询。若编码器已变更，应建立新的兼容索引版本，而非混写不同向量语义。

SYS57．缓存命中率提升，为什么总耗时可能没明显下降？

回答：缓存改善的只是一段计算成本。向量缓存减少了重复文本的 Embedding，但文档解析、Qdrant upsert、事务、网络和启动时间仍然存在。仓库历史实验中结构型分块重复修订有明显缓存收益，固定窗口修改则可能大多没命中且增加查询开销。因此要按阶段统计命中数、实际编码输入数、总耗时和缓存读写成本，而不是只展示命中率。

追问：缓存键只放文本 SHA-256 为什么不够？

追问回答：相同字符串用不同 Embedding 模型、归一化方法、Tokenizer 或 dense/sparse 编码器会产生不同向量。vector_cache.py 结合工作区、模态、encoder fingerprint 与真实输入哈希建立身份，还检查维度和存储校验，确保复用结果与当前索引兼容。

SYS58．CI 全绿可以写“项目生产可靠率 100%”吗？

回答：CI 负责固定提交上的静态检查、单元测试、集成测试和受控回归；真实生产可靠性则由服务可用率、任务完成率、尾延迟、未知结果和恢复速度等运行指标衡量。AgentHub 的 .github/workflows/ci.yml 包含 PostgreSQL、Redis、Qdrant 测试服务与多类回归。面试汇报可说明“这个提交通过哪些 CI 检查”，并补实际负载与故障演练指标，形成工程质量说明。

追问：如果没有生产长期监控数据，项目怎样展示可信成果？

追问回答：提供固定提交、测试环境、数据集与样本量、复现脚本、失败注入和完整日志。比如证明租约失效旧 Worker 无法提交终态、Approval Claim 并发只成功一次、跨工作区访问被拒绝，比笼统宣称 100% 稳定更有技术说服力。

SYS59．想把 Worker 从 1 个扩到 10 个，先检查什么？

回答：Worker 从 1 个扩到 10 个，首先检查任务是否拥有原子 Claim、租约、唯一执行身份和可重入的完成写回；其次检查 PostgreSQL 连接池、Redis 投递量、Qdrant upsert、Embedding GPU、第三方 API 并发与限额。对入库这类任务，可将并发提升与 batch、租约续期、模型显存占用一起测。增加进程数可能放大下游瓶颈，应该看任务完成吞吐和队列等待时间。

追问：怎样初步估算需要多少 Worker？

追问回答：设平均任务服务时间为 T 秒、每个 Worker 有效并发为 c、期望稳定到达率 λ 个/秒，粗略需要 worker_count > λ*T/c 并预留波动空间；随后以 P95 任务时间、CPU/GPU 占用和失败率验证。模型调用长尾、重试和队列分组会影响真实容量，所以最终依据压测曲线配置。

SYS60．你会怎样描述一次真正独立完成的项目改动？

回答：介绍真实改动，我会以“问题现象—根因—源码位置—修改机制—验证结果”组织。例如修订详情刷新：用户上传完成后列表 READY、详情仍 PROCESSING，根因是列表和详情采用两份查询，原定时器只刷新列表；改动应让详情依据自身 Job 状态继续读取，并在切换资源时丢弃旧响应。再展示 Network 时序、受控响应测试和真实上传后的数据库回读，让听者能核对每个结论。

追问：只阅读了实现和测试报告，尚未亲自提交代码，面试怎么说？

追问回答：用“我追踪并复核了这条链路，定位到某模块并设计了测试”描述学习工作；若有个人 PR，则给出 commit、修改文件、独立运行的断言和代码审查记录。把源码分析能力和实现交付能力分别讲清，之后可以选一个尚未覆盖的具体问题独立完成。
