面试问答 A：架构、数据库、认证与交付（SYS01–SYS60）

用法：先不看答案口述 60—90 秒，再对照“项目落点”和追问。这里的答案说明系统如何设计，不代替你对个人贡献的真实陈述。凡是“可以设计”“如果要扩展”，均属于推导或候选方案。

A1．项目架构与版本设计

SYS01．请用一分钟介绍 AgentHub，别只列技术栈。

回答：AgentHub 把模型调用接进可管理的业务执行流程：用户配置和发布 Agent，运行时按冻结版本组装上下文、调用模型与工具；有风险的动作经过策略和审批；状态、来源与结果被持久保存，之后还能评测和核查。它的重点是让执行有身份、权限、恢复和证据。Web、FastAPI 与异步 Worker 共同组成产品，PostgreSQL 管业务事实，Qdrant 管检索索引，Redis 管任务传递。项目入口

追问：你的工作体现在哪里？选一条你实际改过或核验过的链路，说明前后行为和证据；不要把整个项目简介当作个人贡献。

SYS02．为什么选模块化单体加 Worker，而不是一开始拆微服务？

回答：当前业务规则之间联系紧密，模块化单体可以用清楚的代码边界和数据库事务组织一致性，同时把耗时任务交给独立 Worker。微服务会额外引入网络失败、协议演进、分布式授权和数据一致性成本。是否拆分应由独立扩缩容、团队边界、故障隔离或数据归属需求驱动。部署进程

追问：将来先拆哪个模块？不能只说“哪个代码最多”；应看资源使用和故障是否独立，例如摄取的 GPU 负载与普通 API 的访问负载。

SYS03．控制面和运行面分别是什么？

回答：控制面管理“允许以什么配置运行”，包括租户、模型、工具、AgentVersion、知识绑定和实验定义；运行面执行某一次任务，并产生 Run、步骤、事件和结果。控制面更新草稿不应悄悄改写正在执行或已经结束的运行。这一划分有助于说明发布与执行的时间边界。发布服务

追问：二者是不是必须部署成两个服务？不必，它们首先是职责边界；当前可以由同一 API 进程装配。

SYS04．Agent、AgentVersion、AgentRun 为什么不能只用一张表？

回答：Agent 是持续编辑的配置实体；Version 是一次发布的不可变执行规格；Run 是一次具体执行。混在一起会让配置更新覆盖历史，也难以表达同一版本并发运行多次。拆开后，Run 可以稳定引用版本，再保存这次有效知识、Memory 与输出。发布与版本

追问：一张表加 JSON 快照可不可以？技术上可以存，但仍然必须明确这些对象的独立身份、约束和生命周期，复杂度不会因为合表消失。

SYS05．“版本不可变”到底冻结了哪些东西？

回答：发布时冻结 Prompt、解析出的模型行为、工具修订、预算与相关绑定策略。它不等于冻结外部世界：Provider 实际服务、凭据状态和业务系统数据仍可能变化；LATEST 知识策略也会在后续 Run 或正式实验解析时形成实际绑定。版本解析

追问：怎样复现昨天结果？要读取当次有效输入，而不能只找到 AgentVersion；还要知道知识、Memory、代码和评测器等身份，并承认模型输出可能不确定。

SYS06．为什么对配置做 canonical JSON hash？

回答：同一字典内容不应因为键顺序或无意义空白不同就得到不同身份。项目先按固定规则序列化，再计算 SHA-256，方便校验发布规格和比较冻结输入。规范化实现

追问：Hash 相同是不是效果相同？不是。它证明的是按该合同计算的输入内容一致，不证明模型确定性、外部数据一致或答案正确，也不是独立防篡改签名。

SYS07．为什么数值默认值还要区分 UNSET 和 CUSTOM？

回答：用户没设置和用户明确选择了当前默认数值，未来演进时应有不同处理。换模型窗口后，未设置项可以推导新值，自定义项应保留意图。AgentHub 在草稿与发布解析中记录这些来源，避免按当前默认值重新解释旧版本。配置来源

追问：数据库里旧数据没有来源字段怎么办？需要明确兼容规则和迁移口径，不能凭“数值恰好等于默认值”就断言用户当年没设置。

SYS08．怎样证明框架没有侵入核心业务？

回答：检查权限、审批状态、逻辑动作身份、未知结果和预算是否由项目合同定义，框架只在适配器边界负责调用或 checkpoint。如果替换模型 SDK 就必须修改租户规则，说明边界耦合。AgentHub 的工程约束强调单向依赖与框架适配。工程规则

追问：用了 LangGraph 是否就自动有可靠恢复？还需要业务持久化、重入规则、执行领取和副作用分类；图状态不能替代这些事实。

SYS09．你怎样从一个 UI 按钮定位到数据库操作？

回答：先找到组件事件处理函数与 API client，再确认 HTTP 方法、路径、payload 和返回身份；从路由追到应用服务，查看权限、事务和具体模型；如果是异步任务，再跟踪队列 ID、Worker 领取及完成回写，最后确认页面如何读取新状态。路由装配

追问：接口返回 202 是成功了吗？只表示受理语义；要结合返回的业务状态判断是否已完成，不能把 HTTP 成功直接当任务成功。

SYS10．仓库 README、旧设计文档与源码冲突时怎么办？

回答：先标记各自基线和用途。旧设计描述意图或历史状态，源码说明某个提交的实现，运行回执证明某个环境实际发生的行为。当前文档核验固定到 cdc9d08；例如旧架构文档仍有早期 Memory 口径，而新草稿默认启用 USER Memory，要以当前创建路径解释。新草稿创建

追问：是不是源码永远代表生产？不是，生产可能尚未部署该提交或执行迁移。

A2．认证、授权与多租户

SYS11．JWT 里为什么不直接保存所有工作区权限？

回答：权限会随组织和工作区成员关系变化，写进长期不可变令牌会让撤权延迟、令牌膨胀，也容易把不同工作区身份混淆。当前 access token 只保存身份与时间等声明，服务器再读取用户和目标租户权限。JWT 授权解析

追问：每次查权限有成本怎么办？可以评估短期缓存和失效机制，但缓存不能没有撤权语义；当前是否缓存要继续看具体入口，不能凭理想方案推断实现。

SYS12．用户是 Organization MEMBER，为什么不自动拥有所有 Workspace 权限？

回答：组织归属与项目参与是两层关系。MEMBER 需要对应 WorkspaceMembership，DEVELOPER 与 VIEWER 才决定其工作区操作范围。OWNER/ADMIN 有组织管理范围的特殊授权，不能用普通成员规则硬套。RBAC

追问：组织管理员没有 workspace_role，是不是无权限？不是，应该看服务器解析出的有效 permissions，而不是只判断一个角色字段是否为空。

SYS13．VIEWER 是不是允许读取所有 GET 接口？

回答：不是。HTTP GET 说明操作形式，不说明数据敏感性。当前 VIEWER 有工作区与评测读取，但客服记录等有专门权限；评测响应还需要隐藏参考答案和敏感观察。应按资源合同与字段投影授权。权限集合

追问：为什么前端还要显示权限？为了解释与引导用户，减少注定失败的操作；后端检查仍然是安全边界。

SYS14．如何防止用户把 URL 中的 workspace_id 换掉？

回答：先验证用户对目标工作区的成员关系和权限，再按该工作区范围查询资源；后台工具使用服务器构造的授权上下文，不信任模型或浏览器提供的租户范围。复合外键进一步防止错误关联，但不替代授权。租户访问 工具上下文

追问：UUID 很难猜，够不够？不够，资源标识的不可预测性不是访问控制。

SYS15．认证、资源不存在、权限不足为什么可能分别返回 401、404、403？

回答：401 表示请求身份缺失或无效；403 表示已识别的请求没有操作权限；404 可表示确实不存在，也可在跨租户访问时避免泄露对象存在性。AgentHub 的工作区访问服务对不存在或不属于目标组织的访问使用 404。访问服务

追问：统一全部返回 200 再放 error 字段好不好？会模糊缓存、重试和客户端处理语义，稳定错误码应与 HTTP 语义配合。

SYS16．为什么密码用 Argon2，而 Refresh Token 存 SHA-256 哈希？

回答：用户密码通常熵较低，需要适合密码验证的成本机制；Refresh Token 由安全随机源生成，足够高熵，保存哈希是为了数据库泄露时不直接交出可使用的原始令牌。二者威胁模型不同。认证安全实现

追问：能否用 SHA-256 直接存用户密码？不能因为 Refresh Token 这样做就类推到低熵密码；还要考虑盐、成本与具体密码哈希机制。

SYS17．Refresh Token 轮换解决什么问题？

回答：每次刷新使旧令牌失去继续使用资格，再签发同一会话 family 的替代令牌。旧令牌被重用时，项目撤销该 family，以处理可能的重放。这个过程在行锁与事务中完成。刷新服务

追问：数据库里为什么记录 replacement_session_id？它帮助表达轮换链，理解会话生命周期和审计，而不是只保留一个永不改变的 token。

SYS18．多标签页刷新为什么会造成误登出？最新如何处理？

回答：多个标签页共享 Cookie，却可能并发提交同一旧 Refresh Token，第一个轮换成功后第二个触发重用检测。前端当前用同页 single-flight，并在支持 Web Locks 时串行同源刷新，减少合法并发造成的竞争。前端认证

追问：不支持 Web Locks 怎么办？当前只保留同页合并，不能宣称跨标签页互斥仍成立；更强降级方案需要单独设计和验证。

SYS19．用户切换账号后，一个旧请求返回 401，能否直接清空当前会话？

回答：不能。这个 401 可能属于旧账号的请求。响应处理必须匹配请求发出时的会话身份，否则会让新账号被旧请求登出。当前 session-provider 维护身份隔离，刷新和失效处理要核对所属会话。会话状态

追问：只有 user_id 够不够？同一用户登出再登录也是新的会话代次，需要区分旧请求与新生命周期。

SYS20．登出后，旧 Access Token 会立即完全失效吗？

回答：当前登出撤销 Refresh family 并清 Cookie，认证入口没有每次按 access token jti 查询撤销表。因此不能承诺所有存量 Access Token 即刻失效。用户启用状态与成员权限会被检查，短期令牌也会到期，但它们是不同控制。认证服务 认证依赖

追问：如果要求设备级即时撤销？需要额外会话版本或撤销机制，并明确查询成本、缓存失效和多设备语义。

SYS21．HttpOnly Cookie 是否彻底解决了 XSS 和 CSRF？

回答：没有。HttpOnly 防止普通脚本直接读取 Cookie，Secure 限制安全传输，SameSite 与路径帮助约束发送范围；但浏览器仍可能在符合条件的请求中自动携带 Cookie，脚本也可能以用户身份发起操作。必须结合应用实际认证入口、同源与跨站配置分析。Cookie 设置

追问：项目有哪些额外防护？只能依据当前代码回答，不能把安全原则自动说成已经部署的所有措施。

SYS22．为什么需要保护最后一个 OWNER？并发时怎么保护？

回答：组织需要至少一个可以继续管理的最高权限成员。仅先查数量再修改，会在并发降级中失效。项目锁定组织成员关系，在同一控制范围内重新确认角色与 Owner 数量，再允许变更。成员服务

追问：只有一个 if 判断有什么问题？它检查的事实可能在写入前改变；约束要覆盖完整竞争窗口。

SYS23．组织 ADMIN 能不能把自己或别人改成 OWNER？

回答：不能只因为有成员管理权限就这么做。当前服务对 ADMIN 操作 OWNER 或赋予 OWNER 有专门限制，并保留最后 Owner 保护。角色级别不是可以随意互换的标签。角色变更

追问：为什么 UI 要用后端 permissions？避免把“某个字段叫 ADMIN”扩展成所有动作都允许，但细粒度操作仍可能有服务端约束。

SYS24．用户被移出工作区，已有运行是否仍然有权限？

回答：新请求应重新解析租户与权限；对于后台运行和审批恢复，还要看各执行边界是否重建操作者上下文。不能仅凭创建 Run 时有权限，就概括以后所有外部操作都永久获准，也不能宣称所有已派发动作能撤回。授权上下文 运行恢复源码

追问：已发出的外部写入怎么办？授权撤销控制未来行为，已产生的业务副作用需要业务核对或补偿。

SYS25．按用户隔离 Memory 是否意味着整个个人助手都私有？

回答：不意味着。Memory 的 owner 过滤只约束这一类记录，Thread、Run、Artifact、审批和日志各自有可见性合同。如果它们仍按工作区共享，不能用 Memory 私有性推断整条任务链私有。Memory 模型 权限集合

追问：怎样设计完整私有助手？要列出所有派生对象与共享入口，逐项定义拥有者、协作、导出、撤销和管理员访问语义。

A3．工具、MCP 与安全边界

SYS26．MCP 解决的是什么，没解决什么？

回答：MCP 为工具发现和调用等交互提供协议，不替平台决定谁能使用工具、操作风险有多高、是否需要审批以及超时后是否已经写入。AgentHub 在协议之外还有连接权限、工具导入、版本绑定、策略与执行状态。MCP 服务

追问：协议兼容就能信任远端吗？不能，远端声明与结果都是需要校验的外部输入。

SYS27．发现工具为什么不能直接当作导入成功？

回答：Discovery 只读取远端目录，不创建平台 Tool，也不决定治理参数。导入时重新读取目录，验证当前工具仍存在，再由操作者选择 effect、risk 和 approval，并把 Tool 与首个修订一起提交。发现与导入

追问：为什么导入时重新读？旧页面目录可能过期；操作必须基于当前可核验的外部合同。

SYS28．Tool、ToolRevision、McpConnection、逻辑动作 ID 有何区别？

回答：Connection 定位远端与认证；Tool 是平台管理对象；Revision 冻结一个可执行规格；逻辑动作 ID 区分一次运行中的业务操作。修改连接秘密不等于创建新动作，升级工具规格也不应改写历史 Run 已绑定的修订。工具模型 MCP 服务

追问：Provider 的 tool-call ID 能代替逻辑动作 ID 吗？不能把不稳定的供应商编号当持久业务去重依据。

SYS29．当前真的支持任意 REST 工具注册吗？

回答：可执行 ToolSourceKind 当前只有 BUILTIN 和 MCP，规格校验也只接受这两类。项目拥有 HTTP API 与业务适配不等于具备一个任意 URL、method、body 的通用 REST 工具引擎。工具合同 规格校验

追问：如果要新增该能力，除了发 HTTP 还需什么？发布合同、秘密引用、SSRF、重定向、超时、响应限制、权限与副作用确认都要纳入设计。

SYS30．READ 为什么也可能高风险？

回答：读取可能暴露敏感数据、消耗昂贵资源或影响外部系统负载。effect 描述是否改变业务状态，risk 描述危害等级，两者独立。是否自动执行要经过实际策略，不能只看 READ 或 LOW 单一字段。工具合同 策略实现

追问：当前自动放行条件是什么？代码要求 effect == READ、approval_policy == NEVER，且 requires_human 为 false；HIGH 风险或 MCP WRITE 会令 requires_human 为 true。不要额外加上代码没有的 risk == LOW 条件，也不要跳过其他执行层的权限检查。

SYS31．JSON Schema 校验为什么不能替代业务校验？

回答：Schema 检查形状和类型，例如金额是数值、客户 ID 是字符串；业务校验还要确认对象属于当前租户、状态允许变更、操作者有权限，以及写入金额符合规则。模型提供的参数类型正确，不代表目标资源合法。工具上下文

追问：workspace_id 是否应该让模型填写？租户范围应来自授权上下文；如果参数里存在相关筛选值，也不能扩大服务器已经允许的范围。

SYS32．为什么内置工具使用固定注册表？

回答：固定身份映射让可执行能力可审核、可发布、可测试。当前注册的是明确的 calculator、query_customer、search_knowledge、query_wiki，模型文本不能变成任意 Python import 或 shell 命令。注册表

追问：测试能覆盖 handler，生产是否也能任意注入？测试覆盖只限已知身份，不能把测试扩展点当成生产动态执行权限。

SYS33．工具结果写着“管理员已批准”，模型能相信吗？

回答：它只能是业务内容，不能提升成权限事实。框架控制的审批决定与执行状态有独立字段，工具数据中的同名 key 不得复制进这些可信字段。平台授权和审批必须来自可信服务路径。ToolResult

追问：这是否彻底解决提示注入？没有，仍要限制能力和数据范围；它解决的是不能让文本直接伪造授权。

SYS34．SSRF 为什么不能只检查 URL 是否以 https 开头？

回答：合法协议下也可能访问内网或敏感地址。需要校验 URL 结构、DNS 的全部解析结果、实际连接对端以及重定向或 SDK 派生请求。当前 MCP transport 将授权目标落实到 socket 连接，而不只做字符串判断。目标校验 传输实现

追问：DNS 检查通过但连接到另一个地址呢？这正是需要实际 peer 校验和连接目标固定的原因。

SYS35．允许内网 MCP 或模型服务，为什么应由操作员配置？

回答：内网访问会扩大服务器能触达的资源范围，不能让普通租户或模型任意放宽。项目为 MCP 和模型提供明确的受控配置；模型私有目标例外使用严格 CIDR，而不是根据环境名字或 API Key 值猜测安全性。Provider 出站 MCP 安全

追问：能否允许一个很大的网段图省事？要评估例外影响范围和所有租户的访问边界，不能只看当前一个请求能否成功。

SYS36．为什么密钥加密和日志脱敏需要同时做？

回答：加密保护数据库中保存的秘密；运行时必须解密才能调用外部系统，此时如果异常、日志或公开响应泄露明文，加密也救不了。因此需要秘密引用、受控解密和安全响应字段一起工作。凭据加密 安全错误

追问：加密主密钥丢失能否从数据库恢复？通常不能按业务数据自行推回，需要保留正确的密钥恢复方案。

SYS37．远端工具调用超时，为什么不能统一重试三次？

回答：超时可能发生在派发前，也可能发生在外部写入成功后、回执返回前。后者重复调用可能重复建单或修改数据。MCP client 区分调用派发与不确定结果，写操作需要保留 UNKNOWN_OUTCOME 并核对。MCP client

追问：如果业务接口支持幂等键？需要稳定逻辑键和明确服务端合同，并处理幂等记录保留期与查询回执；不能只在请求头随便写一个随机 UUID。

SYS38．为什么远端 annotations 不能决定平台风险？

回答：annotations 是远端自述，可能错误、过时或恶意。平台需要有权限的操作者选择治理规则，导入后的规格也必须冻结。协议元数据可辅助理解，但不是审批权威。导入服务

追问：远端工具描述后来变化怎么办？旧版本绑定的是冻结修订；要明确如何检测漂移与发布新修订，不能静默让历史规格跟随最新目录。

SYS39．通用错误信息会不会妨碍排障？

回答：公开响应应给稳定错误码、安全消息和 request_id；内部诊断再关联细节，避免把请求参数、URL 凭据或完整异常暴露给用户。安全与可排障可以通过分层信息实现，而不是二选一。错误封装 处理器

追问：所有内部日志都一定安全了吗？不能仅凭公开响应脱敏就作此保证，日志路径和默认内容仍需要单独检查。

SYS40．新增一个工具，你的验收会覆盖什么？

回答：正向调用之外，还应覆盖参数错误、跨租户、无权限、连接禁用、Schema 不兼容、超时、返回过大、恶意内容以及写入结果不明。检查它是否能被正确导入、绑定到发布版本，并在运行证据中解释结果。工具校验 MCP 服务

追问：为什么不能只测 handler？因为真正用户路径经过配置、发布、权限、运行和投影，函数成功不足以证明产品闭环。

A4．数据库、性能与交付

SYS41．PostgreSQL、Redis、Qdrant 为什么不能相互替代？

回答：PostgreSQL 保存关系、事务、状态和历史身份；Redis 在本项目承担任务消息传递；Qdrant 提供检索索引。一个任务从 Redis 队列消失，不等于业务成功；一个向量点存在，也不能证明它属于允许访问的快照。部署与数据分工 项目入口

追问：能否全放 PostgreSQL？技术选型可以重评，但需要重新验证检索能力、负载和运维取舍，而不是只为少一种数据库。

SYS42．有应用层检查，为什么还要数据库约束？

回答：应用检查可能在并发窗口过期，也可能被脚本或另一条写入路径绕过。数据库约束保护最终关系不变量。最新 Chunk 四字段外键同时检查工作区、知识库、文档与修订配对，避免分别合法却组合错误的引用。知识模型 0061

追问：有约束后应用可以不检查吗？不宜，应用层还要给出清楚错误、减少无效工作并控制状态流转。

SYS43．两个外键分别有效，为什么组合仍可能错误？

回答：Chunk 的 document_id 可以指向文档 A，revision_id 指向文档 B 的修订，两个对象都真实存在。只有把要求同时匹配的列放进同一个复合关系，才能表达“这个修订属于这个文档”。分块约束

追问：为什么还需要父表对应唯一键？数据库需要可被该列组唯一标识的父记录，不能用一个模糊列组建立确定引用。

SYS44．行锁和乐观版本控制怎么选？

回答：行锁让事务内的竞争修改串行；expected_version 让服务发现用户基于旧页面状态发来的更新。两者可以结合：锁定最新工单后检查版本，再决定应用或拒绝，而不是互斥的两派设计。客服状态修改

追问：冲突后自动重试可以吗？要看用户意图是否仍成立，不能把旧决定无条件覆盖到新状态。

SYS45．唯一约束为何不等于完整幂等？

回答：唯一约束只限定某个键不重复。幂等还要定义同一个逻辑请求的身份、参数一致性、已完成结果回读和正在执行时的行为。不同 key 可以制造重复业务，同一个 key 配不同参数也不能默默成功。发布与业务约束 客服服务

追问：第一次请求已提交但响应丢失怎么办？客户端需要保留原提交身份，服务端需要能查询或重放结果，而不是生成一个新 key 再发。

SYS46．为什么模型调用期间长期持有事务会拖垮系统？

回答：外部等待会扩大连接和锁的占用时间，让少量慢请求耗尽有限连接池。应尽量把输入读取、外部计算和结果提交拆成短数据库阶段，同时用版本或执行权检查处理拆分后的竞争窗口。数据库工厂

追问：把 pool_size 调大就好吗？它可能把压力转移到数据库，不能消除不必要的长事务和锁等待。

SYS47．flush、commit、refresh 各自什么时候用？

回答：flush 将待写变更送到数据库，便于拿主键或尽早触发约束；commit 提交事务，使这批变更成为已提交事实；refresh 主动重新读取对象，适合需要数据库生成值的场景。flush 后仍可 rollback，不能把 flush 当持久成功。发布服务中的事务

追问：expire_on_commit=False 为什么还可能需要 refresh？部分数据库生成字段仍可能被过期处理，异步响应序列化不应意外触发隐式数据库加载。

SYS48．如何为一个查询设计索引？

回答：先列出实际筛选条件、排序、返回数量和关联，再根据选择性与访问模式设计列顺序，查看执行计划并衡量写入成本。当前 Chunk 按工作区与修订读取有对应复合索引。分块索引

追问：列上有索引为什么还慢？可能筛选不选择、排序不匹配、读取过多行、统计偏差，或者根本在等连接和锁；先定位等待而非盲目继续加索引。

SYS49．为什么 Memory 使用部分唯一索引？

回答：系统可能要求有效状态下内容不能重复，但需要保留失效历史。部分索引把唯一性限制在符合状态谓词的行，同时按作用域表达去重身份；无条件唯一可能阻止正常的历史替换。Memory 模型

追问：迁移里有谓词而 ORM 没有会怎样？自动生成迁移可能误判结构差异，应让模型与迁移共同描述同一约束。数据模型规范

SYS50．JSONB 用在哪里合适？

回答：有版本合同的复杂规格、工具参数和观察适合 JSONB；租户身份、外键、状态、常用排序字段通常需要明确列与约束。JSONB 便利保存整体快照，但不能代替所有数据建模。版本发布 评测模型

追问：以后查询 JSONB 很频繁怎么办？评估具体索引或物化字段，保留派生数据与原始合同的关系，不直接复制一份后失去来源。

SYS51．迁移为何不能交给每个 API 副本启动时自动运行？

回答：多个进程会竞争修改 schema，启动与变更失败混在一起，普通重启也可能变成结构发布。项目显式 prepare 先运行 Alembic，再初始化框架 checkpoint，成功后启动服务。初始化 Compose

追问：这是否已经实现零停机部署？没有，还需设计新旧代码兼容、回填、约束验证与发布顺序。

SYS52．为什么 checkpoint schema 不完全交给业务 Alembic？

回答：业务表由项目模型和迁移拥有，框架 checkpoint 表由对应适配器的 setup 合同拥有。分开初始化可明确升级职责，并避免 API 启动暗中修改框架结构。Checkpoint bootstrap

追问：备份只包含业务表行不行？如果要恢复暂停中的原 Run，checkpoint 也是恢复所需事实的一部分。

SYS53．/health 返回正常，用户为什么仍然不能完成任务？

回答：简单存活检查没有验证模型凭据、Worker、任务进度或完整业务链。当前 ready 主要检查 PostgreSQL，dependencies 检查基本可达性，不能证明文档能够摄取或审批能恢复。探测源码

追问：应该加什么？按重要业务设计低成本、无危险副作用的可推进性检查，并监测队列年龄、租约和错误，避免把昂贵真实任务塞进每次探针。

SYS54．数据库有密文，为什么 Worker 仍可能无法调用模型？

回答：Worker 需要与写入时匹配的加密主密钥。API 与 Worker 使用不同密钥，或者恢复时只恢复数据库而没恢复密钥，都会造成解密失败。应核对密钥来源和环境，不应盲目生成新密钥覆盖。凭据实现 部署配置

追问：JWT 密钥和凭据主密钥可否复用？当前初始化要求独立，二者生命周期与影响范围不同。安装脚本

SYS55．持久卷、备份和灾备演练有什么区别？

回答：持久卷保留容器外数据；备份保留可恢复的历史状态；演练验证能在规定条件下恢复并继续业务。磁盘损坏或误删可同时破坏正在使用的持久卷，因此不能用有 volume 证明灾备能力。存储装配

追问：AgentHub 恢复应检查哪些对象？业务表、checkpoint、Blob、密钥、索引以及被暂停或结果未知的任务，各自要按恢复语义处理。

SYS56．Qdrant 数据丢失但文档仍 READY，应该怎么办？

回答：READY 是此前业务流程写下的状态，不会自动让丢失索引重生。先确认缺失范围和保留的修订、chunks、Blob，再按设计重建对应索引并验证快照过滤与来源映射。不能直接把所有状态改回 PENDING 就认为恢复可靠。知识模型 摄取服务

追问：项目是否已有完整一键灾后重建？当前不能这样宣称，需区分可重算的基础能力与完整运维产品。

SYS57．缓存命中率提升，为什么总耗时可能没明显下降？

回答：缓存只节省某一阶段的工作，如果瓶颈在解析、重排、远端模型或排队，总延迟变化可能很小。还要考虑命中查询、序列化和存储成本。当前跨修订向量缓存复用的是编码结果，Chunk 与引用身份仍然独立。缓存实现

追问：只用文本哈希做缓存键够吗？不够，还要编码器身份、实际输入、模态和作用域等兼容条件。

SYS58．CI 全绿可以写“项目生产可靠率 100%”吗？

回答：不能。CI 证明指定检查在特定环境和输入下满足预期；真实模型质量、外部服务不确定性、容量和生产故障范围不同。AgentHub 有真实基础设施集成和确定性评测，这些证据也应分别解释。CI 定义

追问：怎么更可信？陈述检查范围、提交、样本、失败和未验证部分，生产指标还需持续观测真实任务分布。

SYS59．想把 Worker 从 1 个扩到 10 个，先检查什么？

回答：先看数据库连接、锁、GPU/CPU 内存、模型供应商速率限制、索引承载与重试放大；确认领取和过期写回有正确执行权校验。更多 Worker 不一定提高吞吐，也可能加重争用。当前 Compose 的并发 1 是具体配置，不是系统能力的全部边界。Compose 摄取执行权

追问：给一个容量数字？没有实测就给带假设的计算模型，不能捏造项目支持的 QPS。

SYS60．你会怎样描述一次真正独立完成的项目改动？

回答：先说用户问题和复现证据，再说不变量与实现位置，然后列实际执行的验证、失败场景和结果，最后说剩余边界。例如最新 RT10 已修复原详情跟进问题，继续改进应选择新的明确观察合同，而非重复声称修复旧问题。当前知识页面

追问：如果只看过源码没有运行呢？如实说完成了源码核验与方案设计；理解、实现、受控测试和真实实验是不同贡献，诚实说明更便于接受深入追问。
