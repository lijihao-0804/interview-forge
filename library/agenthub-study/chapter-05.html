第 3 讲：前端、后端分层与数据库操作

讲解原文

明白。我们把重点调整到你更需要补强的两部分：

  • 第 2 阶段：前端如何通过 HTTP 调用后端，后端如何分层处理请求。
  • 第 3 阶段：后端如何操作数据库，Agent、发布版本和运行记录如何保存。

这部分最值得掌握的是：页面里的一个字段，如何经过 HTTP、Python 对象，最终变成数据库中的一列；数据库里的记录，又如何回到页面。

我重新对照了 AgentHub 的相关源码。我们就沿着一个具体操作来讲：

在页面填写“学习助手”，点击创建，数据库新增一个 Agent，页面跳转到它的详情页。

下面代码会适当缩短，重点保留实际项目中的名称和处理逻辑。

一、先把前端、后端、数据库放在一张图里

AgentHub 的这次创建操作，大致经历下面的过程：

图中的 FastAPI 路由和业务服务，通常在同一个后端进程里通过 Python 函数调用协作。前端到后端使用 HTTP，后端到 PostgreSQL 使用数据库连接。

这条链在你的项目中对应这些文件：

位置 主要职责
apps/web/app/agents/page.tsx 表单、按钮、提交事件、页面状态
apps/web/lib/api/agents.ts 封装 Agent 相关 HTTP 请求
apps/web/lib/api/client.ts 实际发送请求、携带身份、解析响应
apps/api/routes/agents.py 接收 HTTP 请求，调用业务服务
apps/api/schemas/agents.py 定义请求和响应的数据结构
packages/agent_runtime/publish.py 创建、修改和发布 Agent 的业务逻辑
packages/agent_runtime/models.py Agent 等对象与数据库表的映射

后面看到一个函数，先判断它位于这条链的哪一段，会容易理解很多。前端页面 · 后端路由

二、前端：输入框里的内容先存在哪里？

1．先存在 React 的页面状态中

你的 Agent 列表页面里有：

const [form, setForm] = useState(EMPTY_FORM);

可以先这样理解：

  • form：当前表单中的数据。
  • setForm：更新表单数据，并让 React 根据新状态更新界面。

名称输入框的核心代码是：

<input
  value={form.name}
  onChange={(event) =>
    setForm((current) => ({
      ...current,
      name: event.target.value,
    }))
  }
/>

逐步来看：

value={form.name}

表示输入框显示的内容来自 form.name。

用户输入文字时：

event.target.value

取得输入框里的新内容。

然后：

setForm((current) => ({
  ...current,
  name: event.target.value,
}))

构造一份新表单状态。...current 保留其他字段，只更新 name。

这时改变的是浏览器中的页面状态，还没有执行创建请求。 你的项目正是通过这种方式处理名称输入。名称输入与表单状态

假设用户填完以后，页面内存中的数据类似：

{
  name: "学习助手",
  system_prompt: "帮助用户理解技术问题。",
  model_profile_id: selectedModelProfileId
}

其中 model_profile_id 是页面里选中的、已经存在的模型配置 ID。

2．点击创建后，提交函数才会发送请求

页面的表单通过 onSubmit={submit} 关联提交函数。我们把真实函数缩成主流程：

async function submit(event) {
  event.preventDefault();

  const result = await mutation.run((auth) =>
    createAgent(auth, {
      name: form.name.trim(),
      description: form.description.trim() || null,
      system_prompt: form.system_prompt,
      model_profile_id: form.model_profile_id,
    })
  );

  if (result) {
    setForm(EMPTY_FORM);
    setShowForm(false);
    agents.reload();
    router.push(`/agents/${result.id}`);
  }
}

这里有几个你需要理解的动作：

代码 作用
event.preventDefault() 把表单提交交给这段 JavaScript 处理
form.name.trim() 去掉名称首尾的空白
mutation.run(...) 管理提交中的状态、错误和当前会话身份
await createAgent(...) 等待后端请求完成
result.id 使用后端返回的新 Agent ID
router.push(...) 导航到对应详情页

真实页面还会提交知识绑定和可选运行配置，但基本过程就是这样。提交函数源码

这里也顺便理解一下 await：

当前这个异步函数要等请求完成，才能取得 result，继续执行下面的代码。

等待期间，浏览器仍然可以处理其他事件。后端 Python 里的 await 也用于等待异步操作，我们后面会看到数据库查询和提交。

三、前端到底怎样“调用”后端？

1．前后端通过 HTTP 接口约定连接

前端有一个 createAgent：

export function createAgent(input, body) {
  return apiRequest(
    `/api/v1/workspaces/${input.workspaceId}/agents`,
    input.accessToken,
    {
      method: "POST",
      body,
    }
  );
}

它规定了三件事：

  1. 请求发到哪个 URL。
  2. 使用哪种 HTTP 方法。
  3. 携带哪些数据。

你的项目中，这次请求的接口是：

POST /api/v1/workspaces/{workspace_id}/agents

前端的函数叫 createAgent，后端函数叫 create_agent。把两边连接起来的是 HTTP 方法、URL 和数据格式。 函数名本身不负责跨语言连接。Agent API 客户端

2．请求数据分布在三个地方

位置 这次请求携带什么 用途
URL 路径 workspace_id 指定操作哪个工作区
请求头 Header Authorization: Bearer ... 提供调用者的登录凭据
请求体 Body name、system_prompt、model_profile_id 等 提供要创建的业务数据

你以后读接口，应该先把这三种输入分开。

尤其注意：URL 中写了一个工作区 ID，只表示请求要访问这个工作区；是否有权限，还要由后端检查。

3．真正发送网络请求的是 fetch

client.ts 会把前面的调用整理成一次浏览器请求。核心机制可以缩成：

const response = await fetch(url, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${accessToken}`,
  },
  body: JSON.stringify(payload),
});

const data = await response.json();

两个转换特别重要：

JSON.stringify(payload)

把 JavaScript 对象转换为 JSON 文本，作为请求体发送。

await response.json()

把后端返回的 JSON 解析成 JavaScript 数据，供页面使用。

你的项目还会检查 response.ok，将失败响应转换成 ApiError，供页面显示错误。请求发送与响应处理

4．为什么前端端口和后端端口不同，仍然能访问？

AgentHub 默认让浏览器请求网页同源的 /api/...，再由 Next.js 转发到后端。

next.config.ts 中的默认目标是：

http://127.0.0.1:8000

例如，浏览器访问前端服务的：

/api/v1/workspaces/.../agents

Next.js 会根据配置，把请求转发到 FastAPI。若显式配置了其他 API 地址，则可以走另一条访问路径。代理配置

所以，读前端代码时，你可能只看见相对路径，没有看见后端端口；端口可能配置在代理层。

四、后端：FastAPI 收到请求后做什么？

1．路由把 URL 对应到 Python 函数

你的项目通过下面的前缀注册 Agent 接口：

router = APIRouter(
    prefix="/api/v1/workspaces/{workspace_id}/agents",
    tags=["agents"],
)

创建接口使用：

@router.post(
    "",
    response_model=AgentResponse,
    status_code=201,
)

前缀与这里的空路径拼接起来，就是：

POST /api/v1/workspaces/{workspace_id}/agents

因此，匹配的请求会进入 create_agent。

我们把它缩成主要逻辑：

async def create_agent(
    workspace_id: UUID,
    payload: AgentCreateRequest,
    context: WorkspaceExecutionContext = Depends(get_workspace_context),
    session: AsyncSession = Depends(get_db_session),
):
    agent = await AgentPublishService().create_draft(
        session,
        context,
        name=payload.name,
        description=payload.description,
        system_prompt=payload.system_prompt,
        model_profile_id=payload.model_profile_id,
        # 其他配置参数省略
    )

    return AgentResponse.model_validate(
        agent,
        from_attributes=True,
    )

这个函数主要负责“接住 HTTP 请求，并把它交给业务服务”。具体创建规则和数据库提交在 create_draft 中。创建接口源码

2．这四个参数分别从哪里来？

参数 来源
workspace_id URL 路径
payload 请求体 JSON，经 Pydantic 解析和校验
context 后端执行身份与工作区权限查询后构造
session 后端创建的数据库操作会话

FastAPI 根据参数声明区分路径参数、请求体等输入；声明为 Pydantic 模型的参数，可以承接并校验请求体。(FastAPI)

因此，前端并没有发送一个 Python session 对象，也没有直接提供完整可信的 context。

3．Depends 可以理解成“先准备这个参数”

看这句：

session: AsyncSession = Depends(get_db_session)

意思是：

执行路由函数时，请 FastAPI 调用 get_db_session，取得数据库会话，再把它交给 session 参数。

类似地：

context = Depends(get_workspace_context)

会通过后端依赖链：

  1. 读取请求中的 Bearer token。
  2. 确认用户身份。
  3. 查询用户对当前工作区的访问关系。
  4. 构造带有用户、工作区和权限信息的执行上下文。

之后，创建服务还会检查是否具有 agent_create 权限。身份依赖 · 工作区上下文

你阅读源码时，还会看见路由中的：

del workspace_id

这只是删除函数内部不用的局部变量名。工作区 ID 已经被权限依赖处理，服务层使用经过检查的 context.workspace_id；这里没有执行数据库删除。

4．AgentCreateRequest 怎样校验数据？

实际请求结构包含下面这些声明：

class AgentCreateRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str = Field(min_length=1, max_length=200)
    description: str | None = None
    system_prompt: str = Field(min_length=1)
    model_profile_id: UUID

    # 其他可选配置省略

你可以逐项理解：

  • name：必填，长度为 1～200。
  • description：可选，可以为空。
  • system_prompt：必填，不能为空字符串。
  • model_profile_id：必须能够解析为 UUID。
  • extra="forbid"：拒绝结构中没有声明的额外字段。

格式合法以后，业务规则还需要继续检查。 例如，一个字符串能够解析为 UUID，并不能说明数据库里存在这个模型配置，也不能说明它属于当前工作区。这些检查由服务层继续完成。

AgentHub 将这类请求结构校验失败统一返回为 HTTP 422，错误代码为 VALIDATION_ERROR。请求结构 · 错误处理

五、先区分三种“Agent 对象”

这是读后端时非常容易混淆的地方：

名称 主要作用 是否定义数据库映射
AgentCreateRequest 描述客户端允许提交什么 否
SQLAlchemy 的 Agent 描述 Python 对象如何对应 agents 表 是
AgentResponse 描述接口允许返回什么 否

例如：

payload.name

表示“从请求中解析出来的名称”。

agent.name

表示“数据库实体对象中的名称”。

它们可能都是 "学习助手"，但承担的职责不同。

请求对象可以要求客户端填写必要字段；响应对象则可以额外包含服务端生成的：

  • id
  • workspace_id
  • created_at
  • updated_at

最后通过：

AgentResponse.model_validate(agent, from_attributes=True)

从 ORM 对象的属性读取数据，构造接口响应。

前端 TypeScript 中也有一个 Agent 类型，用来帮助开发时检查字段使用。当前客户端最后的 body as T 是类型断言，并不会自动逐字段检查网络返回数据。前端类型与请求封装 · 响应结构

六、数据库：Python 对象怎样变成一条记录？

1．ORM 定义类和表之间的对应关系

你的项目使用 SQLAlchemy。Agent 模型中的部分字段如下：

class Agent(Base):
    __tablename__ = "agents"

    id: Mapped[UUID] = mapped_column(
        SQLUuid(as_uuid=True),
        primary_key=True,
        default=uuid4,
    )

    workspace_id: Mapped[UUID] = mapped_column(
        SQLUuid(as_uuid=True),
        nullable=False,
    )

    name: Mapped[str] = mapped_column(
        String(200),
        nullable=False,
    )

对应关系是：

Python 代码 数据库含义
class Agent 映射一张表
__tablename__ = "agents" 表名是 agents
agent 实例 对应某一条记录
agent.name 对应这条记录的 name 列
primary_key=True 这一列作为记录主键
nullable=False 这一列不允许为 NULL

Mapped[str] 可以先理解为“这个被映射的属性在 Python 中使用字符串类型”；mapped_column(...) 描述数据库列。

此外，model_profile_id 关联模型配置表。项目还使用包含 workspace_id 的复合外键，让关联的模型配置必须属于相同工作区。Agent 数据库模型

2．数据库会话 session 从哪里来？

项目的数据库初始化代码核心是：

engine = create_async_engine(database_url, ...)

factory = async_sessionmaker(
    engine,
    expire_on_commit=False,
)

可以分成三个概念：

对象 职责
engine 管理数据库连接资源和连接池
factory 创建 Session 的工厂
session 本次数据库工作使用的对象与事务上下文

请求需要访问数据库时，通过下面的依赖取得 Session：

async def get_db_session(request):
    factory = get_db_session_factory(request)

    async with factory() as session:
        yield session

yield session 把会话交给路由使用，使用结束后退出上下文并清理资源。这段依赖没有自动提交事务；创建 Agent 的提交发生在业务服务中。 数据库初始化 · Session 依赖

Session 会跟踪当前加载或修改的 ORM 对象，并在需要执行数据库操作时使用连接。多个并发任务应分别使用自己的 AsyncSession。(SQLAlchemy 2.0 Documentation)

3．创建服务实际做了什么？

AgentPublishService.create_draft 的顺序是：

  1. 检查创建权限。
  2. 获取当前工作区。
  3. 校验业务字段。
  4. 检查选中的模型配置是否可用。
  5. 创建 Agent(...) 对象。
  6. 加入 Session。
  7. 提交事务。

保存部分可以缩成：

agent = Agent(
    workspace_id=workspace_id,
    name=name.strip(),
    description=description,
    system_prompt=system_prompt,
    model_profile_id=model_profile_id,
    # 其他配置省略
)

session.add(agent)

try:
    await session.commit()
except IntegrityError:
    await session.rollback()
    raise

return agent

真实代码会把数据库完整性错误转成 AGENT_CREATE_FAILED 业务错误。创建草稿服务

读这段时，要区分三个时点：

构造对象：

agent = Agent(...)

此时只是构造 Python 对象。

交给会话管理：

session.add(agent)

Session 开始跟踪这个新对象，准备将其插入。

提交事务：

await session.commit()

提交之前，SQLAlchemy 会将必要变更写入数据库，然后提交事务。

4．add、flush、commit、refresh 分别是什么？

操作 作用
session.add(obj) 把对象交给 Session 管理
await session.flush() 将待处理变更发送到数据库，仍处于当前事务中
await session.commit() 提交事务；提交前会进行必要的 flush
await session.rollback() 回滚当前未提交事务
await session.refresh(obj) 从数据库重新读取对象的数据

flush 发生以后，相关 SQL 可能已经执行，但当前事务仍可以回滚。commit 是事务提交；refresh 则是重新读取。(SQLAlchemy 2.0 Documentation)

因此，在创建 Agent 这条路径中：

session.add(agent)
await session.commit()

已经完成所需的新增提交，源码没有再机械地显式调用 flush() 和 refresh()。

为什么更新路径又调用了 refresh？

项目的更新服务在提交后还有：

await session.refresh(agent)

原因与 updated_at 有关：这个字段使用数据库表达式更新，提交后需要明确读取更新后的值，以便后续序列化响应。

项目虽然配置了 expire_on_commit=False，允许提交后继续访问已加载属性，但这不意味着所有数据库生成的字段都永远无需重新读取。更新服务中的说明

5．事务可以怎样理解？

假设一个操作需要完成两项数据库修改：

  • 新增某条主记录。
  • 新增与它关联的记录。

如果它们属于同一个事务，就可以一起提交；中途失败时，可以回滚这次未提交的修改，避免只保存一半。

对你的创建接口而言，要记住一个具体边界：

服务先提交数据库，再把结果交给路由序列化，最后通过 HTTP 返回前端。

由这个顺序可以推得：提交完成以后，后续响应传输失败，并不会自动撤销已经提交的记录。 这也是排查“页面说失败，但数据库里好像有数据”时需要考虑的情况。

七、数据库写完以后，页面为什么会更新？

数据库提交之后，数据沿着返回路径走：

  1. 服务返回 ORM Agent 对象。
  2. 路由转换成 AgentResponse。
  3. FastAPI 返回 HTTP 201 和 JSON。
  4. 前端请求函数解析 JSON。
  5. 提交函数取得 result。
  6. 页面更新自己的状态。

前端取得的对象会包含后端返回的 ID、名称、时间等字段。

你的页面随后执行：

setForm(EMPTY_FORM);
setShowForm(false);
agents.reload();
router.push(`/agents/${result.id}`);

这里，agents.reload() 会触发列表重新请求，router.push 则进入新 Agent 的详情页。创建成功后的页面操作

重新查询得到数据后，查询 Hook 会执行类似：

setData(result);

React 再根据新状态渲染列表。项目中的 reload() 实际上通过更新一个状态值，使查询逻辑重新执行。页面数据查询 Hook

所以，数据库更新和页面更新是两步工作：

  • 后端负责提交数据。
  • 前端负责取得结果并更新展示状态。

八、查询和修改：同一条链再走两遍

1．查询列表：GET 对应 SELECT

前端查询 Agent 列表使用：

GET /api/v1/workspaces/{workspace_id}/agents

后端服务中的主要查询是：

query = select(Agent).where(
    Agent.workspace_id == workspace_id
)

result = await session.scalars(
    query.order_by(Agent.created_at, Agent.id)
)

return list(result)

这里分成两步：

query = select(...).where(...)

先构造查询表达式。

await session.scalars(...)

再执行查询，并取得 ORM 对象。

对应 SQL 的大意是：

SELECT *
FROM agents
WHERE workspace_id = $1
ORDER BY created_at, id;

其中 $1 表示绑定参数。

你应当特别注意工作区条件：列表查询会在数据库查询阶段按工作区筛选。列表查询实现

2．修改说明：PATCH 对应更新对象再提交

假设前端只要修改说明，可以发送：

PATCH /api/v1/workspaces/{workspace_id}/agents/{agent_id}

请求体：

{
  "description": "用于学习 Agent 开发的助手"
}

后端先根据 Agent ID 和工作区找到记录，再修改 ORM 对象。缩成一个字段就是：

agent.description = "用于学习 Agent 开发的助手"

await session.commit()
await session.refresh(agent)

SQLAlchemy 会跟踪 ORM 属性变化，在提交过程中生成相应更新操作。真实服务通过字段字典统一处理修改，并会检查权限和字段合法性。修改接口与服务

exclude_unset=True 为什么很重要？

项目的 PATCH 路由中有：

values = payload.model_dump(exclude_unset=True)

它保留客户端明确提交的字段。

下面两个请求含义不同：

{}

表示这次没有要求修改 description。

{
  "description": null
}

表示这次明确要求将 description 清空。

如果把“没有传”和“明确传了空值”混在一起，就可能出现用户改名称时，顺便把说明清空的错误。这里的 exclude_unset=True 正是在保留这种区别。

九、Agent、版本和 Run，数据库为什么要分开存？

你已经理解 Agent 执行循环，这里重点看它们的数据关系。

1．先掌握三张核心表

表 保存什么 典型变化方式
agents Agent 身份和可编辑草稿 编辑配置时更新现有行
agent_versions 发布时生成的运行配置快照 每次发布新增一行
agent_runs 某次执行的输入、状态、输出等 每次运行新增记录，执行中更新状态

其中：

  • AgentVersion.agent_id 指向某个 Agent。
  • AgentRun.agent_version_id 指向本次实际使用的版本。

因此，一个 Agent 可以有多个发布版本，一个发布版本又可以执行很多次。相关数据库模型

2．用一个具体例子理解发布

下面的 A1、V1、R1 只是示意标识。

操作 数据库发生什么
创建学习助手 A1 agents 新增一行
设置提示词“回答简洁一些” 更新 A1 的草稿字段
发布 V1 agent_versions 新增 V1，保存当时的运行配置
使用 V1 执行任务 R1 agent_runs 新增 R1，关联 V1
将草稿改为“给出详细推导” 更新 agents 中 A1 的草稿
再发布 V2 agent_versions 新增 V2
使用 V2 执行任务 R2 新增 R2，关联 V2

以后查询 R1，就能知道它执行时使用的是 V1 的配置。

项目的 publish 服务会读取草稿、解析运行配置、计算新版本号，然后新增 AgentVersion。配置保存在 resolved_spec 这个 JSONB 字段中。发布服务

这解释了两个操作的区别：

  • 保存草稿：修改现有 Agent 配置。
  • 发布版本：生成一份新的版本记录。

运行时还会单独记录实际解析到的知识等输入身份。因此，理解版本时，先抓住“运行关联具体版本”，后续再展开不同资源的冻结时点。

3．Thread 和 Turn 再补在哪里？

对象 含义
Thread 一段持续的会话或工作
Turn 用户在这段会话里提交的一轮输入
Run 为这轮输入进行的具体执行

在你的项目中，Thread 关联 Agent；每轮提交解析所用版本，该轮 Run 再关联具体的 AgentVersion。因此，一段长对话可以跨越多个发布版本，而每次执行仍然保留明确的版本身份。Playground 等独立运行可以没有 Thread 和 Turn。会话与轮次模型

十、改了 Python 模型，数据库表怎样跟着变化？

这里还需要补上 数据库迁移。

Python 代码中的：

name = mapped_column(String(200))

描述了程序期望的数据结构。数据库服务器中也有自己的实际表结构，两者需要保持一致。

AgentHub 使用 Alembic 管理这种结构变化。比如创建 Agent 相关表的迁移里，有：

op.create_table(
    "agents",
    # 各列与约束
)

项目的迁移环境会加载 ORM 元数据，迁移文件则记录如何创建、增加或调整数据库结构。Agent 表的初始迁移 · 迁移环境

以后给一个字段增加完整支持，通常需要检查：

  1. 数据库迁移：实际表里是否有这列。
  2. ORM：Python 实体如何映射它。
  3. 请求结构：是否允许客户端传入。
  4. 服务：怎样校验、保存、修改。
  5. 响应结构：是否返回这个字段。
  6. 前端：怎样输入和展示。

Alembic 的 upgrade 会按照迁移关系，将数据库升级到指定版本；head 表示目标迁移链的最新版本。(Alembic 1.20.1 documentation)
