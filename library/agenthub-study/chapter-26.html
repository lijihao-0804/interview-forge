第 22 讲：前端权限、会话并发与异步选择状态

源码基线：cdc9d084d3a20e71355401952ee394da4e56273b。这一讲接在第10讲“页面、流式事件与后台任务”之后，解释最近真实修复中的前端工程问题。源码已经存在的能力称“当前实现”，其余建议单独说明。

22.1 先从一个真实问题开始：为什么开三个标签页会把自己踢下线？

设想你已经登录，分别打开研究、知识库、运行历史。三个页面都有自己的JavaScript内存，都认为访问令牌需要续期。浏览器却让这些同源页面共享同一枚刷新Cookie。

如果三个标签几乎同时发送刷新请求，第一个成功后会轮换Cookie；另外两个可能已经带着旧Cookie发出了请求。后端看到旧刷新令牌再次使用，不能简单断言这是用户正常多开标签，也可能把它当成重放。于是，一个本来用于保护会话的服务端约束，暴露了客户端并发协调不足的问题。

当前apps/web/lib/api/auth.ts分两层处理它：同一页面模块里的refreshInFlight复用正在进行的Promise；支持Web Locks的浏览器进一步申请名为agenthub.auth.refresh的同源锁，把真正的POST /api/v1/auth/refresh放在锁回调内部。这样，后一个标签在前一个请求及响应Cookie处理结束以后，才启动自己的交换。认证客户端

注意“先获取锁，再启动请求”的顺序。如果你先写const promise = fetch(...)，然后在锁里await promise，网络请求早已发出，锁住的只是等待过程，无法避免Cookie并发轮换。这就是阅读异步代码时必须区分的两件事：创建Promise可能已经开始工作，await只是等待它。

同页合并和跨标签串行也不同。同页的多个调用可以共享一个结果；跨标签当前是分别取得自己的访问令牌，只是串行使用共享Cookie，并没有把访问令牌放入公共存储，也没有通过广播把一个标签的内存身份直接塞进另一个标签。

项目保留了一个明确的兼容边界：没有navigator.locks时直接调用交换函数，仍保留同页合并，但不能宣称已经实现所有浏览器上的跨标签互斥。仓库记录的“两轮三个页面、六次刷新均200”是其本机浏览器验收范围；本讲没有重新执行这组测试。历史交互验收

22.2 为什么有了用户ID，还要有“会话代次”？

再看一个更隐蔽的问题。标签A正在为用户甲续期；用户随后退出，又登录用户乙。甲的旧续期请求这时才回来。如果回调直接执行setAccessToken，页面可能把甲的身份重新覆盖到乙的新登录上。

仅比较“页面还挂载着没有”不够，仅比较workspace也不够。当前session-provider.tsx使用一个对象表示一次认证会话，例如{ userId }，请求捕获这个对象的引用，响应回来时检查它是否仍然等于authSessionRef.current。每次新的登录会生成新的对象；即便两次登录恰好是同一个userId，也不是同一次会话。会话Provider

这里可以建立一个非常有用的区分：

身份 回答的问题 为什么不能互相替代
userId 是哪个用户 同一用户可以退出后重新登录
workspaceId 当前在哪个工作区操作 同一工作区内也可能切换账号
session对象或sessionId 是页面认可的哪次身份代次 可以让旧异步回调失效
request generation 是当前资源的第几次请求 同一会话、同一资源也会多次加载

如果续期返回的user_id与请求所属会话不同，当前实现会让这个标签的旧身份失效，而不是继承另一标签切换后的账号。HTTP客户端还在请求发出时捕获tokenRefresher；发生401时使用当时捕获的刷新器，避免旧请求借用新会话的刷新器重试。会话Provider HTTP客户端

这一层解决的是“旧异步结果不得污染新身份”。它不等于服务端已经具备所有访问令牌的即时吊销机制；后端如何验证访问令牌、如何处理登出，仍要看第13讲的认证契约。前后端各守住自己的事实边界，才能避免把一个局部修复解释成整个身份系统的万能保证。

22.3 权限不能只有true和false，页面至少需要四种状态

你可能见过这样的体验：刚打开页面，所有者先看到“权限不足”，过半秒按钮又亮了。这通常不是角色真的变化了，而是程序把“权限还没读到”错误地当成“已经确认没有权限”。

当前Provider把权限结果绑定到workspaceId + sessionId，并给页面permissions、permissionsFailed、retryPermissions。其可观察状态至少有四种：尚未获得结果、读取失败、确认有权、确认无权。确认有权才开放对应写动作；读取失败时显示重试；确认只读时才解释角色限制。会话Provider 权限提示组件

为什么读取失败也要保留写保护？因为“没拿到权限”不能成为默认允许写入的理由。为什么又不能把所有页面都遮掉？因为已有的只读接口仍会按服务端权限判断，用户可能仍能查看有权读取的列表、状态和统计。写能力暂时不能确认，与整个账号完全不可用，是两件不同的事。

以知识库页面为例，上传新文档看knowledge_create，修改文档和上传修订看knowledge_edit，创建快照看knowledge_run。不能把“能看这个知识库”简单扩大成“能做页面里所有按钮对应的写操作”。同样，AppWorkbench的新建和删除会话依赖agent_run；页面根据权限控制交互，API仍须检查真实调用者。知识库详情页 工作台

再举一个容易答错的权限题：用户在当前工作区是VIEWER，能不能创建一个新工作区？要先问“在哪个组织里创建”。当前前端通过组织对象的org_role判断目标组织是否为OWNER或ADMIN，而不是拿当前工作区的角色回答所有操作。这是权限设计里非常通用的原则：先确定目标资源，再确定权限作用域。组织客户端

22.4 一个灰色按钮可能有四种原因，不能统一解释成“功能没做”

最近仓库专门复查了19个在截图中禁用的控件。这个案例很适合学习产品验收，因为截图只保留某一瞬间，看不到请求先后和输入前置条件。

禁用原因 例子 正确的验证方式
前置输入不足 没标题、没已发布Agent、消息只有空格 分别补齐与移除每一个条件
当前数据未就绪 版本目录还在加载、权限结果未返回 控制请求返回顺序，观察各个控件
确认无权 VIEWER不能发送或发布 页面验证之后，直接API请求仍应403
正在提交或无需操作 正在上传、已经处于默认主题 核对pending和目标状态，不误报权限

例如“新建分析”的入口按钮只需要确认可以创建并让标题框聚焦，不必等所有Agent目录加载完；“选择Agent”则依赖目录；“开始分析”还依赖标题、已发布Agent和提交状态。同一页三个按钮可以有不同依赖。如果只用一个pageLoading全部锁死，就很难解释页面行为，也容易让不相关请求拖慢操作。

仓库报告用暂停真实请求的方式区分这些状态，又通过API或数据库回读确认发布、新建、发送、运行的结果。但其生成模型为本机固定应答，非空快照补测也有内嵌Qdrant和固定编码器的边界。我们可以引用它作为产品契约与交互回归证据，不能把它写成“最新模型正确率已经提高”。19个控件复查

22.5 为什么A→B→A比A→B更容易漏测？

假设你在检索页选择快照A，发送请求1；很快切到B，随后又切回A，发送请求3。请求3先回来，结果正确。请求1最后回来。

如果只比较snapshotId === 'A'，旧请求1会被误认为仍然有效，覆盖请求3。当前资源名字相同，不能说明当前请求相同。因此项目的通用查询hook用sessionId + resourceKey + generation共同判断结果是否还属于当前视图；检索页也在提交和选择变化时递增queryGeneration。成功响应和失败响应都必须过这一关，否则旧失败可能盖住新成功。工作区查询hook 检索页面

可以用这个教学伪代码记住约束：

const mine = ++generation;
const requestedScope = currentScope;
try {
  const value = await load();
  if (mine !== generation || requestedScope !== currentScope) return;
  apply(value);
} catch (error) {
  if (mine !== generation || requestedScope !== currentScope) return;
  showError(error);
}

这里是示意代码，不是建议脱离React生命周期直接复制。真实实现还要处理会话切换、资源key变化、loading清理、函数引用和组件卸载。

还有一层边界必须讲清：丢弃旧结果，只说明旧结果不会应用到当前页面；它不意味着旧HTTP请求或服务端工作已经停止。useWorkspaceData主要用身份和代次守住响应应用，不能据此宣称所有查询都具有AbortController取消。对于写请求尤其如此：页面切走后不展示响应，也不能撤销已经提交的数据库事务。

22.6 RT10已经修复：列表完成以后，为什么详情仍要自己刷新？

第11讲把“文档列表已经READY，但展开详情仍停在PROCESSING”作为独立修改练习。现在主线已加入真实修复，应当把旧练习升级为代码走查。

原因是列表和详情是两个请求，可能在不同时间获得不同版本的状态。列表先读到了新的READY，详情还保留上次PROCESSING。如果轮询是否继续只由列表决定，就会在详情尚未看到终态时提前停下来。

当前followDetails在“文档页签打开且选中了文档”的前提下考虑三类情况：详情存在PENDING/PROCESSING修订；列表中该文档当前状态仍活动；详情已经加载，但还没有包含列表指向的当前修订。计时器每5秒分别判断是否刷新列表、是否刷新详情，并在相应请求已loading时跳过重复触发。页面隐藏时跳过；可见性变化会触发刷新检查。知识库详情页

把这个设计翻译成业务语言：每块界面都必须有机会读到自己负责展示的终态，不能只因为另一块界面结束，就停止观察。

但当前实现并不等于第11讲的整份建议代码。它没有采用5/10/20秒错误退避，也没有“连续四次失败自动暂停”的逻辑；详情跟进条件主要围绕revision状态与当前revision覆盖，不应写成一套独立且完整的Job状态机。从现有条件还可推导一个边界：列表已终态、详情读取失败后data和loaded被清空时，详情跟进条件可能不再成立，页面需依靠错误区的重试入口，不能宣称所有失败都能自动继续观察。这是源码条件推导，本轮未做浏览器复现。旧课中的退避、暂停、手动恢复仍可以作为进一步增强候选。已落地的事实与教学提出的更完整方案，必须分别标注。

22.7 怎样设计能证明问题解决的前端测试？

“点击后没有报错”信息量很低。更好的用例是操纵响应顺序和对象身份，让曾经的错误在修复前一定出现，在修复后有清楚的断言。

建议按四组思路组织。第一组是身份：同账号续期、换账号、旧401晚到、新登录先完成。第二组是权限：权限读取中、一次503、重试恢复、确认VIEWER、切workspace时旧权限晚到。第三组是选择：A→B、A→B→A、旧失败晚于新成功、版本目录慢于Agent切换。第四组是观察：列表先READY、详情仍PROCESSING、请求超过5秒、隐藏后恢复、关闭详情后不再刷新。

源码回归里可以检查组件真实处理函数和状态更新；浏览器验收检查真实焦点、禁用态、导航、网络及可读提示；API/数据库回读确认业务真的改变。这几层各证明不同事情。固定模型使链路测试更稳定，但不会证明真实模型质量。当前仓库的前端回归入口是node scripts/test_web_regressions.cjs，具体新增用例在test_web_review.cjs；本讲仅检查源码，没有执行它们。前端回归源码

22.8 查询状态与业务状态，应该画在两张纸上

文档详情有loading，修订也有PROCESSING，它们都可以显示旋转图标，但含义完全不同。前者说“浏览器还在等待这次GET”；后者说“服务端摄取任务还没完成”。一个GET可以很快成功，返回仍然PROCESSING；也可以因为网络失败，根本不知道后台是否已经READY。

因此，页面应当允许表达“后台上次观察仍在处理，但这次刷新失败”。如果把一次GET失败直接改成任务FAILED，就伪造了业务结果；如果把服务端FAILED当成网络错误不断自动重试GET，又不能帮助用户触发真正的摄取重试。当前通用hook分别保留data、error、loading、loaded，知识页另从Document和Revision读取业务状态，正是两种状态的分工。查询hook 知识库详情

同样，“列表为空”需要先知道请求成功。没有数据可以是尚未加载、当前资源被切换、请求失败，最后才是成功返回空数组。只有在当前身份的成功结果确实缺少一个对象时，才有依据处理失效选择；不能因为加载中的临时空值就把用户选择清掉。这也解释了运行历史版本目录修复为什么必须同时看当前Agent、目录加载状态和资源身份。

在实现一个新页面时，我建议先写状态表，再写JSX。表中每一行写用户可见文案、是否显示旧数据、哪些按钮可用、可否重试、会不会触发业务写入。这样，所谓“异常处理”就成为产品设计的一部分，而不是最后加一个catch弹窗。

一个很实用的审查问题是：重新加载失败时，用户能否继续复制已有信息、查看别的只读内容、保留未发送草稿？这些动作与本次失败请求通常没有强依赖。适度隔离页面区域，让一次目录请求失败只影响其依赖控件，会比一个全页遮罩更清楚，也更容易定位问题。项目最新的权限重试、目录重试和工作台独立查询提供了具体例子；是否所有页面都做到同样程度，需要逐页检查，不能只因为有通用hook就宣称全站一致。

这一讲的练习：打开知识库详情页源码，逐项写出列表、详情、上传修订、权限四块状态的生产者和消费者。再画出“列表先到、详情后到”的时间顺序，解释为什么两个查询都要有身份保护。能回答这几个问题，才算理解了修复的原因，而不仅是记住多调用一次reload。
