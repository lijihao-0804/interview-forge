第 5 讲：数据库选型、业务分工、事务与崩溃恢复

用户提问

现在着重讲一下数据库的操作吧，首先是我们使用的是什么数据库，同类的还有什么，为什么用这个，不同数据库都负责什么业务，崩溃会有什么问题怎么恢复，怎么写作完成一项任务

讲解原文

AgentHub 当前的主业务数据库是 PostgreSQL，另外配合 Redis、Qdrant 和本地文件存储。 它们分别承担业务记录、任务消息、检索索引和原始文件的保存工作。

你这一问，正好可以把前面学的接口、Agent 运行和审批串起来。数据库这部分要理解四件事：

  1. 数据存在哪里，为什么放在那里。
  2. Python 代码怎样真正读写数据库。
  3. 多个存储怎样配合完成一项任务。
  4. 执行中断后，怎样判断数据和任务该如何恢复。

下面以我刚核对的 AgentHub 当前 main——提交 1 的默认配置为准。

一、我们到底使用了哪些数据库

1. 当前实际配置

组件 仓库默认版本或实现 类型 在 AgentHub 中的主要职责
PostgreSQL postgres:16-alpine 关系型数据库 用户、工作区、Agent、版本、Run、审批、工单、文档信息、分块正文、任务状态等
Redis redis:7-alpine 内存键值存储 当前主要作为 Celery 的消息队列，向 worker 投递任务
Qdrant qdrant:v1.13.6 向量数据库 保存稠密、稀疏检索向量及关联信息，召回相关文档分块
本地文件存储 LocalBlobStore 文件系统 保存上传的原始 PDF、DOCX 等文件

这些配置可以直接在 docker-compose.yml 和 settings.py 中看到。

需要先明确一个实际情况：这一版的向量存储是 Qdrant。pgvector 可以作为另一种设计方案，但当前代码没有采用它。原始文件目前也通过本地目录保存。

项目自己的架构决策已经规定了各自的责任：

PostgreSQL 保存业务状态；Redis 承担队列、缓存这一类基础设施职责；Qdrant 提供向量检索，业务归属和有效状态以 PostgreSQL 为准。

这里“队列、缓存”是架构职责划分。当前已经实现的 Redis 主要用途是 Celery broker，并没有一个覆盖全站业务的通用 Redis 缓存层。 源码依据：存储职责 ADR、Celery 配置。

2. 同一份 PDF，会以不同形式出现在三个地方

假设你上传了一份《售后服务规则.pdf》。

位置 保存的内容
本地文件存储 完整 PDF 的二进制字节
PostgreSQL 文件名、文档版本、所属工作区、处理状态，以及解析后的分块正文
Qdrant 分块对应的向量，以及 chunk_id、文档版本 ID、工作区 ID 等关联信息

例如，PostgreSQL 中某个分块的内容可能是：

chunk_id = C3
text = 商品签收后七日内，在符合条件时可以申请退货……
document_revision_id = R1

Qdrant 中对应的记录则类似于：

point_id = 根据 C3 生成的稳定 ID
dense = [0.12, -0.08, ...]
sparse = 稀疏向量

payload:
    chunk_id = C3
    document_revision_id = R1
    workspace_id = W1

当前项目的 Qdrant payload 不保存分块正文；正文保存在 PostgreSQL 的 document_chunks.text。 检索时先找相关分块 ID，再回 PostgreSQL 读取正文和验证归属。源码：知识数据模型、向量记录构造。

这样设计后，一个检索索引即使需要重建，也仍有持久保存的文本作为来源。

二、同类的还有什么，为什么使用当前这套

先按“要解决的问题”分类，再比较产品，会比直接背数据库名称容易理解。

1. PostgreSQL：处理有关系、有规则的业务数据

与 PostgreSQL 同类的常见产品有：

  • MySQL：常见的服务端关系型数据库。
  • SQL Server、Oracle Database：同样属于关系型数据库。
  • SQLite：嵌入式关系型数据库，常用于单机应用、本地数据和轻量部署，运行方式与独立的数据库服务器不同。(sqlite.org)

AgentHub 的数据存在大量明确关系：

  • 一个工作区有多个 Agent。
  • 一个 Agent 有多个发布版本。
  • 一次 Run 使用一个具体版本。
  • 一张审批单属于一次 Run。
  • 一个文档版本有多个分块。

此外，还存在必须由数据库维护的规则：

  • 同一个 Agent 不能出现两个相同版本号。
  • Agent 不能引用其他工作区的模型配置。
  • 创建组织时，组织、创建者的成员关系、审计记录应当一起保存。
  • 多个执行者竞争一个动作时，只能有一个取得执行权。

根据这些源码需求，PostgreSQL 适合这里的理由是：关系建模、事务、约束、并发控制都能直接支持这些业务。 项目还使用了 PostgreSQL 的 JSONB 保存结构化配置，并采用 PostgreSQL 保存 LangGraph checkpoint。源码：业务模型、checkpoint 决策。

这属于根据代码需求作出的选型分析。MySQL 的 InnoDB 同样支持事务和 ACID，因此不能把原因理解成“只有 PostgreSQL 才能保证业务正确”。(dev.mysql.com)

对于这个现有项目，选择已经体现在模型、迁移、驱动和 checkpoint 适配中。换数据库需要调整这些实现，通常不能只改一个连接地址。

2. Qdrant：处理“哪些内容与这个问题相关”

PostgreSQL 很适合回答：

找到工作区 W1 中，状态为 READY 的文档。

这是一种条件查询。

Qdrant 在这里主要回答：

在允许使用的文档范围内，哪些分块与用户的问题最相关？

常见的同类选择包括 Milvus、Weaviate；另一条路线是给 PostgreSQL 安装 pgvector 扩展，把向量与业务数据放在同一个数据库里。pgvector 官方就支持向量存储和相似性查询。(GitHub)

两种设计各有取舍：

设计 主要好处 需要承担的工作
PostgreSQL + Qdrant 业务存储和检索服务分开管理；可独立调整检索配置与资源 需要维护两套服务，并处理索引与业务状态之间的一致性
PostgreSQL + pgvector 存储组件更集中，业务数据与向量可以使用同一套数据库能力 业务读写和向量检索共享数据库资源，需要一起规划负载与索引

AgentHub 当前采用前一种，Qdrant 适配器负责稠密、稀疏检索和范围过滤。源码：Qdrant 适配器。

3. Redis：让 API 把耗时工作交给 worker

对你当前学习这个项目来说，先把 Redis 的用途理解为：

API 保存好任务后，通过 Redis 告诉 worker：“请处理这个任务 ID。”

比如 PDF 解析、切块和 embedding 需要一定时间，API 可以先接收上传并保存任务，再由 worker 执行后续处理。

如果替换的是“任务消息队列”这个职能，RabbitMQ 是常见候选。Redis 和 RabbitMQ 都可以作为 Celery 的 broker。这里 RabbitMQ 属于消息中间件，比较的是它们承担的队列职责。(Celery 5.7.0 documentation)

AgentHub 当前的配置是：

Celery(
    "agenthub",
    broker=settings.redis_url,
    ...
)

同时设置了：

task_ignore_result = True

因此要区分：

  • Redis 中的消息：提醒 worker 处理哪个任务。
  • PostgreSQL 中的任务记录：这个任务是什么、进行到哪一步、最后成功还是失败。

业务结果并没有统一交给 Redis 保存。源码：celery_app.py。

4. 原始文件：当前用共享目录，也可以换对象存储

原文件保存的是完整 PDF、图片、DOCX 等字节内容。当前项目通过 LocalBlobStore 写入目录，Docker 中 API 和 worker 挂载同一个 agenthub_blobs 卷，因此双方都能读到这些文件。

如果以后把 API 和 worker 部署到不同服务器，可以实现 S3、MinIO、OSS 等对象存储适配器，或者提供真正的共享文件系统。

两台机器上配置相同的路径字符串，并不会自动共享文件。 当前的共享来自实际挂载的同一个存储卷。源码：BlobStore、部署配置。

三、Python 代码操作数据库，中间有哪些层

这里很容易把几个名称混在一起。

名称 它是什么
PostgreSQL 真正执行查询、保存数据的数据库服务
SQL 向数据库表达查询和修改操作的语言
SQLAlchemy Python 中构造 SQL、映射对象、管理事务的工具
asyncpg Python 与 PostgreSQL 通信使用的驱动
Session 一段数据库工作使用的对象和事务上下文
Alembic 管理表、列、索引、约束等结构变化的迁移工具

因此，我们在 Python 中写：

select(Agent).where(Agent.workspace_id == workspace_id)

SQLAlchemy 会根据这个表达式生成 SQL，再通过驱动发送给 PostgreSQL。

1. 模型类对应数据库表

比如：

class Agent(Base):
    __tablename__ = "agents"

表示这个 ORM 类对应 agents 表。

一个 Agent 对象，通常对应表中的一行：

agent.name

对应这一行的 name 字段。

不同模块中的 models.py 可以定义不同表，但这些表通常位于同一个 PostgreSQL 业务数据库中。代码分目录，并不意味着每个目录对应一个独立数据库。

AgentHub 的数据库名默认是 agenthub；LangGraph 的框架表放在同一 PostgreSQL 中的 langgraph_checkpoint schema 下，业务表和框架表分别管理。源码：数据库配置、checkpoint ADR。

2. 连接池和 Session

项目的数据库初始化代码很短：

engine = create_async_engine(
    database_url,
    pool_pre_ping=True,
    pool_timeout=3,
)

session_factory = async_sessionmaker(
    engine,
    expire_on_commit=False,
)

可以这样理解：

  • engine 管理数据库连接入口和连接池。
  • 连接池复用已有连接，避免每个操作都重新建立连接。
  • session_factory 用来创建 Session。
  • 业务代码用 Session 查询对象、保存修改、提交事务。

pool_pre_ping=True 会检查从池中取出的连接是否还能使用；pool_timeout=3 是等待可用连接的时间，不是 SQL 查询只能运行三秒。源码：database.py。

普通 API 请求通过依赖取得 Session：

async with session_factory() as session:
    yield session

这个依赖负责提供和关闭 Session，提交事务由业务代码决定。源码：dependencies.py。

四、实际怎样写增、删、改、查

先看基本操作，再看如何把多个操作组合成一个完整业务。

以下片段按真实代码简化，省略权限检查、参数校验和部分配置字段。

1. 新增：创建一个 Agent

agent = Agent(
    workspace_id=workspace_id,
    name="售后助手",
    system_prompt="你负责回答售后问题。",
    model_profile_id=model_profile_id,
)

session.add(agent)
await session.commit()

这里发生了三件事：

  1. Agent(...) 创建一个 Python 对象。
  2. session.add(agent) 把对象交给 Session，准备插入。
  3. commit() 提交事务，将新增记录正式保存下来。

构造 Python 对象不会自动写数据库，add() 也不代表事务已经提交。

项目的真实创建方法是 AgentPublishService.create_draft()，发生数据库完整性错误时还会调用 rollback()。源码：publish.py。

2. 查询：获取工作区内的 Agent

query = (
    select(Agent)
    .where(Agent.workspace_id == workspace_id)
    .order_by(Agent.created_at, Agent.id)
)

result = await session.scalars(query)
agents = list(result)

大致对应下面的 SQL：

SELECT *
FROM agents
WHERE workspace_id = :workspace_id
ORDER BY created_at, id;

注意两步的区别：

query = select(...)

是在构造查询。

await session.scalars(query)

才是在执行查询，并取得对应的 ORM 对象。

其中 workspace_id 应来自后端已经校验的执行上下文，用来限定这次查询的数据范围。上面这条路径对应源码中的 list_drafts()。源码：publish.py。

3. 修改：先查出对象，再修改字段

agent.name = "售后工单助手"

await session.commit()
await session.refresh(agent)

SQLAlchemy 会追踪对象字段的变化，在提交时生成相应的 UPDATE。

项目的真实更新方法还会先锁定目标记录，并检查允许修改的字段。这里调用 refresh()，是为了重新读取包括数据库更新的 updated_at 在内的字段，方便后续生成响应。源码：update_draft。

4. 删除：以移除工作区成员为例

项目中有这样的操作：

await session.delete(membership)
await session.commit()

它会删除对应的成员关系记录。实际方法还会检查权限、组织规则，并写入审计记录。源码：remove_workspace_member。

5. 五个最容易混淆的方法

方法 做了什么 是否意味着事务已提交
add(obj) 将新对象交给 Session，准备插入 否
flush() 把待处理修改发送给数据库，在当前事务中执行 否
commit() 提交当前事务；提交前会执行必要的 flush 是
refresh(obj) 从数据库重新读取对象字段 否，它是读取
rollback() 撤销当前尚未提交的事务，清理失败状态 否

flush() 已经可能执行了 INSERT，但数据仍属于未提交事务；refresh() 也不是每次写入都必须执行。SQLAlchemy 官方对这些行为有明确说明。(SQLAlchemy 2.0 Documentation)

五、用一个真实业务理解“事务”

1. 创建组织，需要写多张表

AgentHub 创建一个组织时，需要同时完成：

  1. 创建组织。
  2. 将创建者加入组织，并赋予 OWNER 身份。
  3. 写入审计记录。

假设第一步成功，第二步失败，最后留下一个没有正常创建者成员关系的组织，业务状态就不完整。

因此，这几步应放在同一个事务里。

源码中的核心结构可以简化成：

organization = Organization(
    name=name.strip(),
    created_by=user_id,
)

session.add(organization)
await session.flush()

membership = OrganizationMembership(
    organization_id=organization.id,
    user_id=user_id,
    role=OrganizationRole.OWNER,
)

session.add(membership)

# 项目还会向同一个 Session 追加审计记录。

try:
    await session.commit()
except IntegrityError:
    await session.rollback()
    raise

源码见 TenantService.create_organization。

2. 为什么中间先 flush()

因为下一条成员关系记录需要：

organization.id

在这里，先 flush，让插入阶段生成的 ID 回填到对象，再拿这个 ID 创建关联记录。

但此时整个事务还没有提交，所以后续出现错误，尚未提交的几项修改可以一起回滚。

你可以这样理解这段代码：

先让数据库执行必要的中间步骤，等整个业务都准备好，再统一提交。

3. 事务之外，还需要数据库约束

事务保证多个修改可以作为一个整体提交，但业务规则还要通过约束表达。

机制 作用 AgentHub 中的例子
主键 唯一标识一条记录 Agent.id、AgentRun.id
外键 保证引用关系成立 AgentVersion 必须关联到对应 Agent
唯一约束 防止不允许的重复 同一 Agent 的版本号不能重复
CHECK 约束 限制字段取值 版本号必须大于零
行锁、条件更新 协调多个并发操作 发布版本、审批执行权认领

这些约束由数据库执行，可以覆盖不同 API 入口、后台任务和并发请求。源码：AgentHub 业务模型。

还有一项需要区分：普通索引主要帮助加快查找，唯一约束还表达了“不允许重复”的业务规则。

4. 表结构变化由 Alembic 管理

如果你给 Python 模型加了一个字段，已有 PostgreSQL 表不会仅因为代码改了就自动增加对应列。

项目通过 Alembic migration 升级数据库结构，例如：

创建 agents 表
增加 agent_runs 的执行租约字段
创建 document_chunks 表
调整 run_steps 的状态约束

部署准备阶段会先运行业务迁移，再初始化 LangGraph 的 checkpoint 表。源码：prepare_database。

这里有两个不同的“版本”：

  • AgentVersion：某个 Agent 发布时的业务配置快照。
  • Alembic revision：数据库表结构的迁移版本。

六、这些存储怎样协作完成一项任务

我们用一个完整任务来串起来：

上传一份文档，完成解析和索引，然后根据文档回答问题。

第一阶段：把文档变成可检索的数据

第一步：API 保存原文件

API 把文件写入 LocalBlobStore，得到一个 blob_key。

文件本体放在共享存储里，blob_key 相当于后续查找它的标识。

第二步：PostgreSQL 保存文档和待办任务

API 创建：

  • documents：逻辑文档。
  • document_revisions：这次上传的具体版本、文件信息和 blob_key。
  • ingestion_jobs：需要处理这个版本的任务。

这些记录提交之后，系统才拥有一条可靠的待办记录。

第三步：通过 Redis 发出任务通知

发送的消息主要包含：

请处理 ingestion_job_id = J1

worker 收到 J1 后，会回 PostgreSQL 读取任务详情。原始 PDF 不需要通过 Redis 搬运。源码：上传服务、队列适配器。

第四步：worker 认领任务并处理原文件

worker 认领任务，记录执行租约，然后读取文件、解析文本、切分块。

租约可以理解为：

这个 worker 在有效期内负责这个任务，并需要持续表明自己还在工作。

分块正文和定位信息保存到 PostgreSQL。

第五步：写入 Qdrant

worker 从 PostgreSQL 读取分块，计算向量，然后用稳定的 point ID 向 Qdrant 执行 upsert。

upsert 的含义是：

对应 ID 不存在就新增；已经存在就更新。

第六步：确认索引完成，更新业务状态

Qdrant 确认写入完成后，worker 再把 PostgreSQL 中的：

文档版本 ingestion_status = READY
摄取任务 status            = SUCCEEDED

保存下来。源码：摄取 worker、摄取阶段与完成状态。

第二阶段：用户提问时，PostgreSQL 和 Qdrant 配合检索

提问时的主要存储交互是：

  1. PostgreSQL 确定范围。 当前工作区和知识快照允许使用哪些文档版本。
  2. Qdrant 召回候选。 在这个范围内找到相关分块 ID。
  3. PostgreSQL 加载正文。 通过这些 ID 取出正文，并再次验证工作区、知识库和快照归属。
  4. 应用组织证据。 用正文进行后续重排、证据选择，交给模型生成回答。

因此：

Qdrant 负责找可能相关的分块；PostgreSQL 负责确认这些分块的归属、版本和正文。

正常提问通常直接使用已经处理好的分块，无需重新解析原 PDF。源码：retrieval.py。

最关键的事务边界

PostgreSQL、Redis、Qdrant、文件系统之间，并没有一个覆盖所有步骤的共同事务。

也就是说：

await session.rollback()

只能回滚当前 PostgreSQL 事务，无法顺带撤销已经发送的 Redis 消息、已经完成的 Qdrant 写入或文件写入。

因此，项目依靠的是：

  • 先保存业务任务，再发送通知；
  • 记录每个处理阶段；
  • 使用执行租约；
  • 用稳定 ID 保证重复写入可控；
  • 定时扫描未完成任务并补偿处理。

这正是多组件后端与简单 CRUD 的一个主要区别。

七、崩溃后会发生什么，怎样恢复

这里需要分清楚三个问题：

  1. 保存的数据还在不在？
  2. 业务任务进行到哪一步？
  3. 刚才那个写操作究竟有没有成功？

数据库能恢复，不代表业务任务一定会自动继续；业务任务可以重试，也不代表丢失的数据库文件能凭空找回。

1. API 在事务提交前退出

例如：

创建组织
插入成员关系
尚未 COMMIT
API 进程退出

连接终止后，未提交事务不会作为已提交业务结果保留下来。重启 API 后，应该重新读取数据库确认状态。

这也是把多表操作放在同一事务中的价值：避免只保存半套业务关系。

2. 数据库提交成功，但 API 没来得及返回响应

例如：

工单 INSERT
COMMIT 成功
API 进程退出
浏览器显示请求失败

此时数据库里可能已经有工单。

浏览器没有收到成功响应，只能说明通信没有正常完成，不能据此判断业务没有写入。

如果连接恰好在 COMMIT 发送后断开，客户端甚至可能不知道服务器最终是否提交。此时应通过业务 ID、幂等键回查。

AgentHub 的 create_ticket 就会按工作区和幂等键查询已有工单；无法确认时保留未知结果。已经提交的写入也不会因为后来调用 rollback() 而被撤销。源码：工单动作执行与回查。

3. PostgreSQL 进程崩溃，但数据卷完好

PostgreSQL 使用 WAL，预写式日志。

可以把它理解为：数据库修改数据文件之前，先把需要恢复的信息写入日志。在正常持久化设置和可靠存储的前提下，数据库重启后可以依据 WAL 恢复数据文件中尚未完成的更新。(postgresql.org)

所以，数据库进程退出并不等于业务数据全部丢失。

但应用仍要处理：

  • 原有连接失效；
  • 正在执行的请求失败；
  • 部分操作的提交结果不明；
  • 后台任务需要重新判断进度。

连接池的健康检查可以帮助排除坏连接，业务是否重试还需要根据任务状态决定。

4. PostgreSQL 已保存任务，但 Redis 消息丢失

例如：

ingestion_jobs 已经提交
↓
向 Redis 投递消息失败

此时任务记录仍然存在于 PostgreSQL。

AgentHub 的定时 reconciliation 会扫描符合条件的待处理任务、租约过期任务，重新投递。达到尝试次数上限则标记失败。源码：reconcile_ingestion_jobs。

这解释了为什么业务状态必须落在数据库里：

即使一条队列通知丢了，系统仍然知道有这件待办工作。

Redis 本身可以配置 RDB 快照、AOF 日志等持久化方式，但持久化策略会影响异常退出后可能丢失的数据范围。当前 Compose 挂载了 Redis 数据卷，没有显式启用 AOF 配置，因此不能据此承诺每条队列消息都已经可靠落盘。(Docs)

5. Qdrant 写入成功，但 worker 在更新完成状态前退出

此时可能是：

Qdrant 中已经有向量
PostgreSQL 中任务仍显示处理中

项目会依据任务阶段和租约重新处理。重试使用相同的 point ID 执行 upsert，然后在确认成功后写入 READY。

因此，即使中断发生在两个数据库操作之间，也可以通过重复执行可控的步骤收敛到完成状态。源码：_index_claim。

6. Agent 执行过程中崩溃，恢复策略更保守

文档索引可以通过稳定 ID 重试。一个可能已经产生业务副作用的 Agent Run，需要更谨慎判断。

AgentHub 发现原执行者租约过期时，会把相关 Run 转为 NEEDS_ATTENTION。如果一个写动作已经被认领，但结果不明，还可能进入 UNKNOWN_OUTCOME，等待核对。

当前项目并不保证所有崩溃中的 Agent Run 都自动从头重跑或自动续跑。 源码：execution_lease.py。

此外，默认配置保留了 API 进程内执行 Run 的方式。启用 worker 执行模式后，API 和执行任务的进程才进一步分离。分析“API 崩溃是否打断任务”时，要考虑当前运行模式。源码：Settings。

7. 数据卷或磁盘丢失

这属于另一层问题：

丢失的内容 恢复路径
Qdrant 索引 恢复索引备份，或利用保留的分块文本和对应模型配置重新建立索引
PostgreSQL 业务数据 从数据库备份恢复
原始文件 从文件备份恢复
凭据加密主密钥 需要原来的密钥，才能解密已有的加密凭据

Qdrant 有自己的存储恢复机制，但整卷丢失后的全量恢复或重建仍需要明确的运维流程。当前源码不能证明它会自动扫描所有 READY 文档并重建一个空索引。(qdrant.tech)

原文件也不能仅凭 blob_key 找回。数据库中的路径标识保存得再完整，如果 PDF 的实际字节丢失，仍需要文件备份。

八、项目现在具备什么恢复能力，备份又该怎样做

1. 持久卷与备份解决不同问题

当前 Compose 为 PostgreSQL、Redis、Qdrant 和原始文件配置了命名卷。

这意味着，在保留并复用这些卷的情况下，更换容器可以继续使用原数据。

备份则需要另外保存一份能够用于恢复的数据。 当前主 Compose 中没有配置完整的自动备份、PostgreSQL 主从或 WAL 归档恢复链。源码：docker-compose.yml。

所以，现在可以说项目有：

  • 数据持久化；
  • 数据库事务；
  • 任务阶段记录；
  • 幂等写入；
  • 部分任务的补偿恢复；
  • 审批 checkpoint 恢复。

而完整灾备仍需要部署数据库备份、文件备份，以及恢复验证。

2. 一个具体的 PostgreSQL 备份例子

如果使用仓库默认 Docker Compose 配置，可以在项目目录中按下面方式备份。

先在 PostgreSQL 容器内生成归档：

docker compose exec postgres pg_dump -U agenthub -d agenthub -Fc -f /tmp/agenthub.dump

再复制到宿主机：

docker compose cp postgres:/tmp/agenthub.dump ./agenthub.dump

其中：

  • -U agenthub：数据库用户。
  • -d agenthub：要备份的数据库。
  • -Fc：使用 PostgreSQL 自定义归档格式。
  • -f：输出文件位置。

pg_dump 可以生成一致的数据库备份；这种归档格式使用 pg_restore 恢复。(postgresql.org)

这些是命令示例，并没有在你的部署上执行。

3. 恢复时，先恢复到新建的验证库

例如，新建一个空的验证数据库：

docker compose exec postgres createdb -U agenthub agenthub_restore_check

把备份复制进去：

docker compose cp ./agenthub.dump postgres:/tmp/agenthub.dump

恢复：

docker compose exec postgres pg_restore -U agenthub -d agenthub_restore_check --exit-on-error /tmp/agenthub.dump

这样可以先验证数据和结构是否能够恢复。pg_restore 负责根据归档重建相应数据库对象和数据。(postgresql.org)

但这个 .dump 只覆盖 PostgreSQL 数据库。完整恢复还要配套：

  • 原始文件目录；
  • Qdrant 索引备份或重建流程；
  • 原有的凭据加密主密钥；
  • 与恢复数据匹配的应用版本和配置。

项目的 .env.example 特别提醒要随数据库备份保留原来的 AGENTHUB_CREDENTIAL_MASTER_KEY，因为已有 Provider 凭据依赖它解密。源码：环境配置说明。

如果希望恢复到某个具体时间点，就需要进一步配置基础备份和持续 WAL 归档。普通定时备份只能恢复到备份所覆盖的状态。(postgresql.org)

4. 迁移不能代替恢复

运行：

alembic upgrade head

可以创建或升级数据库结构。

但它无法找回已经丢失的用户、Agent、审批和工单记录。

迁移解决“表应该长什么样”，备份恢复解决“过去保存的数据如何找回来”。

九、你接下来读代码时，可以按这条顺序走

为了从“看懂解释”走到“自己能写”，先读下面几处就够了：

顺序 源码 重点
1 database.py Engine、连接池、Session 工厂
2 publish.py 创建、查询、修改 Agent
3 control_plane/services.py 创建组织时，怎样把多表写入放进一个事务
4 knowledge/services.py 保存文件、写任务、提交后入队
5 knowledge/ingestion.py 阶段、租约、重试和完成状态

读每一个业务方法时，固定追踪四件事：

读取了哪些记录；修改了哪些记录；在哪一次 commit() 后正式生效；如果下一行执行前进程退出，数据库留下什么。

你能沿着这四个问题把“创建组织”和“上传文档”两条路径讲清楚，就已经开始具备独立设计数据库业务代码的能力了。
