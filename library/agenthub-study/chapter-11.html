追加日期：2026-11-17。此前内容保持原样，本次仅在文件末尾追加讲解、代码与流程图。

用户提问

上下文投影是什么意思，总是看到这个词，总是出现在组装上下文正式发送api请求之前，但是本地也无法运算这些上下文吧，解析一下，顺带解析一下RAG里面修改文档，比如只修改部分内容，具体会如何处理呢，这个问题可以补充到md文件后面

讲解原文

第 8 讲补充：上下文投影，以及 RAG 文档局部修改怎样处理

先回答你最关心的两点：

  1. 这里的“上下文投影”，主要是后端用普通代码把已有数据整理成“这一次发给模型的内容”。它不需要先运行一次大模型，也不涉及计算远端模型的隐藏状态。
  2. AgentHub 当前修改文档正文的方式，是上传完整的新修订，再重新处理这份修订的全部内容。即使只改一段，也不会自动只重算这一段；但它也不会因此重建整个知识库。

下面仍按我们前面使用的源码提交 0 解释，并把“当前实现”和“可以进一步做的增量优化”分开。

第一部分：上下文投影到底是什么？

一、把“上下文”先还原成普通程序里的数据

你说“本地也无法运算这些上下文”，这里需要区分两类运算。

处理一段文字的数据结构，和让模型理解这段文字并生成回答，是两件事情。

在请求发出之前，所谓上下文，通常就是后端内存里的：

  • 字符串：用户问题、文档正文、系统提示词。
  • 列表：消息列表、检索结果列表。
  • 字典或对象：角色、工具名称、来源 ID、检索分数。
  • 数值：预算、排序位置、长度和时间。

例如：

messages = [
    {"role": "system", "content": "根据提供的材料回答。"},
    {"role": "user", "content": "定制商品能按七天规则退货吗？"},
]

evidence = [
    {
        "chunk_id": "C17",
        "text": "定制商品不适用上述七天规则。",
        "score": 3.8,
    }
]

这只是教学示意结构。

Python 可以读取这些字符串，Java 同样可以用 String、List、Map 保存和处理它们。选择列表中的若干项、计算长度、检查 ID、把对象序列化成 JSON，都属于普通程序计算。

这些操作不要求程序理解“定制商品到底能不能退货”。

真正根据句子含义进行理解和生成，是后面的模型推理。这里的“本地”指运行 AgentHub 后端的机器，也可能是一台服务器，并不一定是你打开网页的那台电脑。

二、“投影”可以理解为：从内部数据中，生成一个面向模型的视图

这个词在这里强调的是：

同一批内部数据，哪些内容要交给模型看，以及用什么形态给它看。

类似后端有一个很完整的业务对象，但给页面返回数据时，只组装页面需要的字段。

它也不同于神经网络里“乘一个投影矩阵，把向量映射到另一个空间”的线性投影。AgentHub 这里的相关函数主要在做字段选择、引用配对、预算选择和消息格式转换。投影相关代码 · RAG 投影

1. 一个具体例子

假设后端已经拿到下面这条信息。为了方便理解，这里把几个内部对象合成一个示意字典：

internal_record = {
    "workspace_id": "W1",
    "snapshot_id": "K3",
    "document_revision_id": "V2",
    "chunk_id": "C17",
    "document_name": "退款规则",
    "snippet": "定制商品不适用上述七天规则。",
    "locator": {"type": "page", "page": 3},
    "rerank_score": 3.8,
}

模型回答问题时，需要读到正文、来源名称和适当的定位信息。但不一定需要在每一条材料里反复阅读所有长 ID。

于是我们可以构造一个更紧凑的模型视图：

{
  "id": "E1",
  "document_name": "退款规则",
  "snippet": "定制商品不适用上述七天规则。",
  "locator": {"type": "page", "page": 3}
}

后端自己保留对应关系：

registry = {
    "E1": {
        "snapshot_id": "K3",
        "document_revision_id": "V2",
        "chunk_id": "C17",
    }
}

这里发生了什么？

  • 正文没有被模型重新理解一遍。
  • 正文没有被改写成摘要。
  • 后端挑选了一组字段。
  • 后端给它分配了一个短编号。
  • 完整来源身份保留在另一个映射中。

这就已经是一种上下文投影了。

在 AgentHub 中，显式启用的 compact_v1 路径就有这种设计：assemble_evidence_plan() 生成模型可读的证据视图，并构造内部来源注册表。普通默认 RAG 投影仍可能保留完整的身份字段，不能把“所有 ID 都隐藏到注册表里”当作全部路径的默认行为。6

2. 用几行普通 Python 就能理解这种操作

下面是教学简化代码，只演示字段选择和编号，不包含正式实现的权限、来源验证和预算：

def project_records(records):
    model_view = []
    registry = {}

    for index, record in enumerate(records, start=1):
        evidence_id = f"E{index}"

        model_view.append({
            "id": evidence_id,
            "document_name": record["document_name"],
            "snippet": record["snippet"],
            "locator": record["locator"],
        })

        registry[evidence_id] = {
            "snapshot_id": record["snapshot_id"],
            "document_revision_id": record["document_revision_id"],
            "chunk_id": record["chunk_id"],
        }

    return model_view, registry

你看这里用到的操作：循环、字典取值、构造列表、字符串格式化。

它们都可以在普通 CPU 上完成，不需要加载聊天模型的权重。

三、本地不知道句子的含义，怎么决定保留哪条？

答案是：这一阶段通常使用已经存在的顺序、分数和规则，不是重新理解所有内容。

以前一节的混合检索加重排路径为例：

  1. Embedding 和检索已经给出候选。
  2. Reranker 已经给候选打过相关性分数。
  3. 检索服务已经排出一个顺序。
  4. 投影函数按既有顺序，尝试把完整记录放进预算。

假设顺序已经是：

记录 已有顺序 假设的完整记录预算成本
A 1 600
B 2 700
C 3 200

如果可用预算是 1000，简单的顺序选择可以是：

  • A 放进去，已使用 600。
  • B 放不下，跳过。
  • C 能放进去，已使用 800。

这个过程只需要比较数字。它不需要再次判断 A、B、C 在语义上分别讲什么。

当然，这样的选择可能漏掉重要证据。因此“投影结构合法”和“交付内容足以回答问题”仍需要分别评估。

AgentHub 的 project_rag_evidence_payload() 实际会：

  1. 检查证据记录和引用是否能够正确配对。
  2. 按输入顺序尝试加入一条完整记录及其引用。
  3. 对候选结果序列化并计量。
  4. 能放下就保留，放不下就跳过。
  5. 继续尝试后面的记录。

它不会在这里把一段文字“读懂后压缩成另一句话”。8

这里所谓的“无损”也有范围：被保留的单条记录不被截成半条；被跳过的整条记录仍然没有交付给模型。

四、token 数量为什么也能在本地计算？

你可能还会疑惑：

“token 不是模型内部的东西吗？没有运行模型，怎么知道占了多少 token？”

需要区分三个量。

1. 字符数：最简单的文本计数

len(text)

这是字符串长度。它不是精确的模型 token 数。

2. 使用 tokenizer 分词：不需要运行生成模型

Tokenizer 负责按特定算法和词表，把字符串转换成 token ID。

如果本地已经有匹配的 tokenizer 文件，可以在本地做类似操作：

token_ids = tokenizer.encode(text, add_special_tokens=False)
text_token_count = len(token_ids)

这一步需要 tokenizer 的算法、词表和配置，不需要先加载整套回答模型并做生成推理。Hugging Face 的官方文档也把 tokenizer 明确区分为准备模型输入的组件，并支持从本地文件或目录加载。Tokenizer 官方文档

但这里还有一个限定：数出一段正文的 token，不等于已经精确数出整个聊天请求的 token。

完整请求还可能包含：

  • 消息角色与聊天模板。
  • 特殊 token。
  • 工具定义。
  • 服务商额外加入的结构。

因此，想精确匹配服务商计数，需要匹配相应 tokenizer 和输入格式，不能只数 content 字符串。

3. AgentHub 当前默认用的是更轻量的估算

当前 ApproxTokenEstimator 的思路大致就是：

import math
import unicodedata

def estimate_tokens(text):
    wide = sum(
        unicodedata.east_asian_width(ch) in ("W", "F")
        for ch in text
    )
    other = len(text) - wide

    return math.ceil(wide / 1.6 + other / 4)

这是对源码核心算法的简化展示。“宽字符”包括具有相应东亚宽度属性的字符，不是一个严格的“汉字检测器”。

它做的事情只是：

  • 遍历字符串。
  • 查询字符属性。
  • 加减除法。
  • 向上取整。

没有网络请求，没有回答模型权重，也没有执行 Attention。11

这是近似估算，不能保证一定大于或等于服务商的真实计数。因此，本地预算检查通过后，远端仍可能因为实际 token 数超限而拒绝请求。

前一节说的字段命名问题也在这里：有些配置名仍带 bytes 或 chars，但具体路径实际使用了这个估算器。读代码时要追到计量函数，不能只看名字。

五、为什么总在正式发送 API 请求之前投影？

因为这个阶段决定的正是：

这一次请求最终要发送什么。

后端内部保存的运行状态，可能包含历史、工具结果、诊断数据、引用映射、计费信息和各种执行标记。模型调用只需要其中一部分。

AgentHub 在构造请求时，有这样的核心关系：

admission = self._admit_context(state)

request = ModelRequest(
    messages=admission.messages,
    tools=admission.tool_definitions,
)

# 后面才交给模型网关，执行实际模型调用。

这是源码关键关系的摘示，省略了日志、事件和状态更新。14

你可以把几个相邻术语分开：

术语 主要回答什么问题
组装 把哪些来源的数据收集到一起？
投影 把这些内部数据变成什么模型可见形态？
预算准入 这一组消息能不能放进本次允许的窗口？
序列化 怎样变成可以发送的 JSON 等请求格式？
模型推理 模型收到这些输入后怎样生成输出？

实际函数可能同时承担其中几项，所以你会在请求发送前反复看到“投影”这个词。

1. 为什么有时不止投影一次？

因为局部预算和总预算不同。

第一层处理：

“这一次检索工具返回的材料，最多能交付多少？”

第二层处理：

“把这些材料和系统提示词、当前问题、历史消息、工具定义放在一起，总量还能不能接受？”

一份材料单独能放下，加上其他内容之后可能放不下。

当前上下文策略还会按照消息角色、位置、工具名称和调用 ID 分类。例如，把一次 assistant 工具调用与对应的 tool 结果分成同一组，避免预算处理后留下一个没有对应调用的孤立工具结果。消息分类 · 预算准入

这仍然是结构化数据处理。程序通过 tool_call_id 配对，不需要理解工具结果的自然语言含义。

2. 可以用下面这张图理解两类工作

图中的投影和预算检查，主要是普通程序操作。生成回答的计算发生在模型推理阶段。

六、那摘要、Embedding 和重排算不算投影？

这些概念最好分开，否则容易误以为所有“压缩上下文”都不需要模型。

操作 当前讨论的计算性质
选择字段、改变数据形态 普通程序处理
给证据编号、检查来源配对 普通程序处理
按既有顺序和预算选完整记录 普通程序处理
用启发式估算 token 普通程序处理
计算 Embedding Embedding 模型推理
用 BGE Reranker 判断问题与段落的相关性 Reranker 模型推理
使用 LLM 把长历史概括成短摘要 另一次模型推理
根据证据生成回答 回答模型推理

所以，“这些投影函数不运行模型”，并不等于“后端不能运行模型”。

后端也可以部署适合的 Embedding、Reranker 或语言模型；是否本地部署，是组件的部署选择。是否需要模型推理，则取决于这个操作本身。

AgentHub 的摘要能力也有独立路径：在显式启用、满足条件时，可能复用已有摘要，或者通过 SummaryWorker 创建摘要。后者确实会调用 generate_resolved()。

但这不是每次上下文投影都会发生的隐式步骤。摘要节点 · 摘要 Worker

七、投影后丢掉的内容，数据库里也没了吗？

投影不会因为本次没有选中某条材料，就删除 PostgreSQL 中的文档正文或原文件。

但还要区分两份数据：

数据 投影或准入后可能怎样变化
文档库中的原文与 Chunk 不会被这些投影函数删除
本次运行的工作消息列表 可能变成筛选后的列表

当前运行时有明确的状态更新：

state["messages"] = list(admission.messages)

所以不能说“运行内存里的原始消息永远保持完整”。后续轮次可能沿用已经通过准入的工作上下文。18

这也解释了一个常见现象：

页面还能查到完整原文，但模型这一次并没有读到它。

原始资料是否存在，与这一次请求有没有包含它，是两个问题。

第二部分：RAG 里只修改文档的一部分，会发生什么？

八、先区分三件事：编辑文件、上传修订、编辑元数据

假设你把《退款规则》里的“七天”改成“五天”。

这涉及三个不同层次：

  1. 编辑原文件。 你在本地修改 Markdown、TXT 或 PDF。
  2. 向知识库提交新的正文版本。 让系统接收这次改动。
  3. 修改文档的业务元数据。 比如生效日期、被哪份文档替代。

当前 AgentHub 的正文更新入口是：

POST /api/v1/workspaces/{workspace_id}/knowledge-bases/{knowledge_base_id}/documents/{document_id}/revisions

它接收 multipart 的 file，也就是完整的新文件内容，返回 HTTP 202 以及文档、修订和入库任务信息。

这里没有“只发送第 15 段改动”的正文 patch 协议。仅在电脑上保存了文件，也不会通过这个上传流程自动更新服务器里的既有版本。修订上传接口

还有一个实用区别：

  • 调用 .../documents/{document_id}/revisions：给原 Document 增加修订。
  • 调用 .../documents：创建另一份 Document。

相同文件名不会自动把两次上传合并成同一份文档。身份取决于你使用的 Document ID 和入口。上传服务

九、当前实现：新建 Revision，再完整处理这份修订

假设已经有 Document D1，它的 Revision V1 保存了《退款规则》第一版，并生成了 C1、C2、C3 三个 Chunk。

上传修改后的正文后，同一份 Document 下会有两份修订：

修订 文件与 Chunks 本次更新的处理
V1 保留原来的内容和 Chunks 保留历史版本
V2 保存完整的新文件，生成属于 V2 的 Chunks 创建新的入库任务

KnowledgeService.upload_document() 的关键行为是：

  1. 保存一个新的 blob。
  2. 沿用已有 Document。
  3. 创建新的 DocumentRevision，版本号递增。
  4. 创建新的 IngestionJob。
  5. 提交数据库事务后尝试入队。

Worker 再对 V2 进行解析、分块、编码和写索引。上传服务 · 入库 Worker

1. 只改一段，也会重新处理其他段吗？

在当前这条默认链路里，会。

准确地说，是：

重新解析这份新修订、重新生成它的所有 Chunks，并为这些 Chunks 重新计算 dense 和 sparse 表示。

不是重新处理整个知识库的所有文档。

例如知识库有 100 份文档，只更新第 8 份，当前任务的处理范围是第 8 份文档的新修订，其余 99 份不会因为这个上传任务全部重建。

2. 未修改的文字为什么也会得到新的 Chunk ID？

因为当前 Chunk ID 包含修订身份：

chunk_id = Hash(
    document_revision_id,
    ordinal,
    normalized_content_hash
)

为了方便说明，假设本次改动没有跨越分块边界，其余片段的正文完全相同：

片段 V1 中的文字 V2 中的文字 内容哈希 Chunk ID
A 文档介绍 文档介绍 可以相同 因 Revision 不同而改变
B 七天内申请 五天内申请 改变 改变
C 原路退款 原路退款 可以相同 因 Revision 不同而改变

这里要分清：

内容一样，不代表版本身份一样。

Qdrant 的 point ID 又由 chunk_id 派生，所以新修订会得到自己的索引点身份。分块身份 · 索引点身份

3. 既然内容哈希相同，为什么不复用向量？

技术上可以设计复用，但当前 Worker 没有按内容哈希查询旧 Embedding 结果的分支。

它会加载新修订的 Chunks，逐批调用：

dense.embed_documents(texts)
sparse.encode_documents(texts)

再写入新索引点。编码与索引过程

因此，以下两件事情不能混淆：

能力 当前含义
同一修订任务重试时，稳定 ID 支持幂等 upsert 重试可以落到相同索引身份上
不同修订之间复用未改片段的向量 需要另外实现内容级结果缓存或复用逻辑

模型实例被缓存、没有每次重新加载权重，也不等于每段文本的向量结果已被缓存。

当前上传服务同样没有“整份文件内容相同就直接跳过”的判断分支，因此重复上传相同全文，也会建立新修订。上传服务

十、新修订还没处理完，旧版能不能继续用？

在正常的这条更新流程里，旧的可用修订会保留，新修订准备完成后再决定当前可用版本。

这里需要同时看两个状态：

  • ingestion_status：解析和索引是否已经完成。
  • lifecycle_status：修订在版本生命周期中的状态。

当前快照选取可用修订时要求：

lifecycle_status = ACTIVE
AND ingestion_status = READY

一个容易看错的细节是：新修订创建时，生命周期默认可以已经是 ACTIVE，但入库状态仍是 PENDING。仅看到 ACTIVE，并不说明它已经可以进入当前可用知识集合。模型默认值 · 快照筛选

1. 正常更新过程

实际的 finalize_ingestion_ready() 在索引写入得到确认后，才把修订标记为 READY；然后选择版本号最高的 READY 修订为 ACTIVE，其余 READY 修订设为 RETIRED。入库最终确认

因此，旧任务即使晚完成，也不会仅仅因为“完成时间更晚”就把旧版本抢回当前版本。

2. 如果新修订处理到一半失败呢？

可能出现：

  • PostgreSQL 已经保存了新修订的部分处理状态或 Chunks。
  • Qdrant 已经写入了新修订的一部分索引点。
  • 新修订尚未 READY。

这时，正常的当前快照生成不会把这个未完成修订当成可用版本。

所以这套设计的关键不是假设“多个存储一定同时成功”，而是：

即使准备过程中留下中间状态，也通过修订状态与快照范围控制哪些内容能够被正式使用。

这里并没有把 PostgreSQL 和 Qdrant 变成一个跨系统的原子事务。Worker · 最终确认 · 快照服务

3. 旧版会被马上删除吗？

这条更新流程不会立刻删除旧 Revision、旧 Chunks、旧文件或旧 Qdrant 点。RETIRED 表示不再作为当前的活动修订，不等于物理删除。

旧快照仍然可以指向旧修订，用于历史运行的来源追踪。

因此，如果新版删除了一句话：

  • 新版正文可以不再包含它。
  • 固定在旧快照上的查询，仍可能读到旧版本中的这句话。

后续如何清理不再需要的历史数据，是另一项保留与清理策略，不能理解为“上传新版会自动清空旧版”。

十一、新资料什么时候会进入 Agent？要看 LATEST 和 PINNED

这是对上一讲需要进一步展开的一点：

文档更新后，并不是所有 Agent 都必须重新发布，也不是所有正在运行的 Agent 都会立即看到新版。

对于原始 RAG 知识绑定，当前行为是：

使用方式 新修订 READY 后会怎样？
Agent 固定绑定旧快照 PINNED K1 继续使用 K1；需要明确改变绑定或相应发布配置
Agent 采用 LATEST，之后创建新 Run 创建 Run 时解析当前可用修订，可以纳入新版
已经创建的 Run 继续使用创建时冻结的快照
独立 Citation QA 接口 使用请求明确传入的 knowledge_snapshot_id

对应实现是 _resolve_effective_snapshots()：创建 Run 时，把 LATEST 解析成具体 snapshot ID 和 hash，并保存在 AgentRun.effective_knowledge_snapshots 中。运行创建与快照冻结

例如：

时间 事件 使用的知识范围
10:00 创建 Run A LATEST 解析为 K1，使用文档 V1
10:05 文档 V2 入库完成 新修订进入可用集合
10:06 创建 Run B LATEST 解析为 K2，可以使用 V2
10:07 Run A 继续执行 仍使用已经冻结的 K1

这里的时间是教学例子。

这同时满足两个需求：

  • 新的任务可以获得更新后的资料。
  • 一个已经开始的任务，不会在不同轮次里悄悄换一套知识版本。

上一讲说 search_knowledge 执行时使用固定快照，指的是工具拿到的有效执行范围。发布配置可以表达 LATEST；运行创建阶段先把它解析成具体快照，工具执行时再使用这个固定结果。两者并不矛盾。发布绑定 · 有效快照解析 · 检索工具

十二、只改生效日期等元数据，也要重新 Embedding 吗？

在当前 AgentHub 中，不需要走正文入库链路。

已有的：

PATCH /.../documents/{document_id}

主要修改 effective_date、superseded_by_document_id 等生命周期元数据。它更新 PostgreSQL 并记录审计，不创建新的正文 Revision，也不启动新一轮 Embedding。45

原因是这些字段在当前实现中不需要通过改写每个向量来生效。检索回读 PostgreSQL 时，会把相关元数据附到证据中。检索证据构造

但要补充一个准确的边界：

Snapshot 固定的是修订成员和正文身份，不是所有 Document 可变元数据的历史副本。

例如，生效日期与“被哪份文档替代”从当前 Document 行读取。旧快照再次检索时，这些元数据也可能反映后来的更新。

所以“固定快照”不能被无限扩大成“整个业务世界的所有字段都永远不变”。

十三、如果想做到“只重算改动的部分”，应该怎么设计？

下面是可以进一步实现的优化方案，当前源码尚未实现这套跨修订的向量结果复用。

核心思路是：

新版本继续保留独立的来源身份；相同的编码输入，可以复用相同配置下已经计算过的向量。

1. 先切块，再判断哪些编码输入真的没变

比较新旧分块时，大致有三类：

情况 新版本要做什么
编码输入没有变化 可以复用已有向量结果
编码输入变化或新增 重新计算
旧版有、新版没有 不纳入新版本；旧版本是否保留取决于历史策略

注意比较的应当是真正送给编码器的输入。

假设 Embedding 输入是：

文档标题 + 章节标题 + Chunk 正文

正文没变，但章节标题改了，实际编码输入就变了。此时不能仅凭正文哈希相同就直接复用。

2. 缓存键不应只有文本哈希

一个更完整的概念设计是：

embedding_cache_key = Hash(
    实际编码输入,
    Embedding 模型及精确版本,
    影响编码的预处理配置,
    前缀与截断配置
)

如果模型、预处理或输入前缀改变，旧向量未必还能复用。

Dense 和 Sparse 的表示也要分别考虑各自编码配置，不能只缓存一个“笼统的向量”。

3. 用伪代码看它和当前实现的区别

# 设计示意：不是当前 AgentHub 已有的缓存实现。
for chunk in new_revision_chunks:
    encoder_input = build_encoder_input(chunk)

    key = make_cache_key(
        encoder_input,
        model_revision,
        preprocessing_config,
    )

    vector = embedding_cache.get(key)

    if vector is None:
        vector = embedder.encode(encoder_input)
        embedding_cache.put(key, vector)

    # 即使复用了计算结果，也建立新修订自己的来源身份。
    write_new_revision_point(
        point_id=point_id_for(chunk.chunk_id),
        vector=vector,
        revision_id=new_revision.id,
        locator=chunk.locator,
    )

这里节省的是模型编码计算。

它不要求把新旧版本混成同一个会变化的索引身份。沿用现有版本模型时，即使向量数值复用，新修订仍然可以有自己的 Chunk 记录、定位和 Qdrant point。

复用计算结果，与覆盖旧版本身份，是两件事。

4. 为什么“只改一个段落”仍可能影响很多 Chunk？

因为分块边界也可能变化。

当前默认是按字符窗口切分。如果你在文档开头插入 100 个字符，后面的固定窗口会相对于原文移动：

  • 原来一个窗口包含的文本可能变了。
  • 相邻重叠窗口也可能变化。
  • 后续多个片段的内容哈希可能一起改变。

所以：

业务上只改一段，不保证算法上只影响一个 Chunk。默认窗口分块

结构分块可以让一些局部修改更容易局限在相关段落附近，但也不是保证。标题变化、段落合并、解析顺序变化，都可能扩大影响范围。

实现增量优化时，必须一起考虑“分块是否稳定”和“编码结果是否可以复用”，不能只加一个哈希字典就认为所有局部更新都能做到最小重算。

5. 增量优化后，版本切换规则仍然需要保留

即使未来只给部分新 Chunk 计算了向量，仍然应该在新修订所需的记录和索引全部准备好后，再让它进入可用集合。

否则用户可能查到：

  • 一部分新规则。
  • 一部分旧规则。
  • 缺失的例外条件。

因此可以优化准备过程中的计算量，但仍需要明确的修订身份、完整性条件和快照切换规则。

十四、把这两个问题放到同一次运行里看

假设你把政策从“七天”改成“五天”，之后用户发起一个新任务：

步骤 程序在做什么 是否属于上下文投影
上传完整新文件 保存 V2 和入库任务 否，文档管理
解析、分块 把新修订变成片段 否，入库处理
计算向量并写索引 让 V2 可被检索 否，其中编码需要模型推理
新 Run 解析 LATEST 固定本次使用的快照 否，版本范围解析
检索和重排 找到相关规则并排序 否，证据获取
选择字段、编号、按预算保留材料 形成模型可读的证据消息 是
合并系统提示、历史、问题并检查总预算 决定最终请求消息 属于上下文准入，与投影紧密相连
调用回答模型 根据可见证据生成回答 否，模型推理

你以后再看到“投影”这个词，可以先问三个具体问题：

  1. 输入是什么数据结构？
  2. 输出保留了哪些字段、哪些记录？
  3. 函数里到底有没有调用模型，还是只做容器、字符串和数值处理？

在 AgentHub 的这些上下文投影函数里，沿着这三个问题读，就能把这个词还原为你已经熟悉的普通程序操作。
