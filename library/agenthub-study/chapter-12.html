第 9 讲：上下文、Memory 与 Wiki

追加日期：2026-11-17。此前所有讲解、代码和流程图保持原样；本次只追加完整的新章节。

讲解原文

学习路线第 6 阶段：哪些信息进入模型，为什么进入，来源在哪里

上一节我们把“上下文投影”拆成了普通的程序操作。这一节再向前追一步：

模型当前看到的资料，是谁保存的、什么时候挑出来的、为什么保留这几条，以及回答出问题后能不能找回原始依据？

先给出整个模块的核心结论：

上下文负责“这次给模型看什么”；长期 Memory 负责“哪些跨对话的信息值得保存并再次取出”；Wiki 负责“把原始资料提前组织成可以复用、发布和追溯的知识”。

它们最终都可能变成模型请求的一部分，但保存方式、有效范围、更新时机和来源证明不同。

本讲继续以我们已经使用的 AgentHub 提交 0 为准。源码中的已实现能力、教学简化代码和可以改进的方向，会分别说明。下面涉及“差旅规则”“项目约定”的内容均为教学示例。

第一部分：先分清几个经常被混用的概念

一、模型“记得”，通常是应用程序再次把信息交给它

假设你第一次说：

“这个项目的后端统一使用 Python，示例也优先用 Python。”

隔了几天，你在新对话里问：

“帮我设计一下这个项目的上传接口。”

Agent 仍然给出 Python 示例。这种连续性可以通过一条非常具体的工程链路实现：

  1. 系统保存了“项目后端统一使用 Python”这条信息。
  2. 新任务开始时，后端查到了它。
  3. 后端把它放进本次模型输入。
  4. 模型根据输入生成 Python 示例。

这里不需要改变模型权重。

资料长期保存在应用的存储中；模型在这次请求里看到被重新取出的那一部分。

LangGraph 官方也按作用范围区分短期和长期记忆：短期记忆服务于一个 Thread，可以通过 Checkpoint 持久化；长期记忆跨 Thread 保存，具体隔离范围由应用定义。因此，“短期”不等于“只存在 RAM”，“长期”也不等于“必须使用向量数据库”。Memory 官方概念说明

一个非常有用的区分

保存了多久：数据生命周期的问题
允许谁读取：权限与作用范围的问题
这次发了多少：上下文预算的问题
原始依据在哪：来源追踪的问题

这四个问题不能用一个“Memory”概念全部代替。

二、AgentHub 中这几种数据到底有什么区别？

对象 主要保存或表达什么 作用范围 是否自动全部进入模型
当前上下文 本次请求的消息、工具定义和证据 一次模型调用 它本身就是最终输入
Thread 历史 同一聊天中的用户问题、回答和可验证的执行记录 当前业务对话 需要选择、规划或检索
Run Checkpoint 当前执行到哪个节点、工作状态是什么 一次 Agent Run 只有其中需要的内容会进入
历史摘要 对某段历史的派生概括及来源关系 指定历史范围 通过验证和预算后使用
长期 Memory 值得跨对话保留的项目约束、共享偏好、决策等短句 Workspace + Agent 需要选择、冻结和准入
原始 RAG 文档版本、原始分块和检索结果 固定知识范围 检索到且交付成功的部分进入
Wiki 对原始资料的主题组织、引文、关系和冲突标记 固定编译与发布版本 查询后交付相关证据

这里最容易混淆的是 Thread 和 Checkpoint。

页面上的一个聊天 Thread 可以有很多轮，每轮关联一次 Run。AgentHub 的 LangGraph Checkpoint 使用的是按 Workspace 和 Run 生成的执行身份：

agenthub:{workspace_id}:{run_id}

所以：

  • Thread 组织“我们聊过哪些轮”。
  • Run 组织“这一次任务怎样执行”。
  • Checkpoint 记录“这一次执行中断后从哪里恢复”。

它们可以有关联，但不是同一张表，也不是同一个 ID。不能因为 LangGraph 的配置项叫 thread_id，就直接认为它等于网页上的聊天 Thread ID。Thread 模型 · Checkpoint 适配器

三、一次模型调用的上下文是怎样组装出来的？

在当前实现中，首次准备阶段的核心消息顺序是：

  1. Runtime 系统规则。
  2. Agent 已发布版本的系统提示词。
  3. 本次选中的长期 Memory。
  4. 本 Thread 中符合条件的历史。
  5. 当前用户问题。

工具定义单独放在 ModelRequest.tools，不是简单拼进某条用户消息。

后续如果 Agent 调用 RAG、Wiki 或其他工具，工具结果才会进入后面的消息序列，并再次接受投影与预算检查。3 与模型节点

下面是教学简化代码：

spec = load_published_agent_version(run.agent_version_id)

memories = load_or_freeze_memory(run, spec)
history = load_or_freeze_history(run, spec)

messages = [
    runtime_policy_message(),
    agent_system_message(spec),
    *render_memories(memories),
    *plan_or_summarize_history(history, spec),
    user_message(run.input_text),
]

admission = admit_context(
    messages=messages,
    tools=published_tool_definitions,
    policy=spec.context_policy,
)

request = ModelRequest(
    messages=admission.messages,
    tools=admission.tool_definitions,
)

这里的 plan_or_summarize_history() 只是为了教学合并几个步骤，并不表示每次必然调用摘要模型。

你要特别注意：

数据库里的 Memory、全部历史、整个知识库，不会因为“系统连接了数据库”，就自动被模型读取。

真正决定输入的是最终的 admission.messages 和工具定义。

第二部分：上下文预算，为什么远不止“超长了截一下”

四、首先要算清楚：到底有多少空间能放输入？

很多初学实现只看一个数字：

“模型支持 128K，所以我最多塞 128K。”

但实际还要考虑：

  • 模型的独立输入上限。
  • 输入与输出合计的总窗口。
  • 给回答保留的输出空间。
  • 部署方设定的输入限制。
  • 工作区或 Agent 配置的预算。
  • 后备模型是否具有更小的窗口。
  • 计数不精确时需要保留的余量。

AgentHub 的新上下文策略会对冻结的模型链逐个计算可用输入，再取共同允许的范围。6

可以用下面这个简化关系理解：

[ B_{\text{输入}} = \min\left( B_{\text{工作区}}, B_{\text{主模型可用}}, B_{\text{后备模型1可用}}, \ldots \right) ]

其中，某模型的可用输入，要综合它已知的输入限制、总窗口减输出预留、部署限制，并减去安全余量。

一个具体例子

假设：

  • 主模型支持较大的输入。
  • 后备模型的总窗口为 32,000。
  • 预留输出 4,000。
  • 净输入上限为 28,000。
  • 教学例子中安全余量取 1,400。

那么后备模型实际允许的工作输入就是：

[ 32{,}000-4{,}000-1{,}400=26{,}600 ]

如果希望同一份请求可以切换到这个后备模型，就不能仍按主模型的大窗口组装。

这些数字是演示值，不是宣称你的 Agent 当前使用这组配置。

此外，上一节讲过：当前默认 token 计量是近似估算。安全余量能够降低风险，但不能把近似计数变成精确的服务商计数。预算实现

输入缓存也不会让文本从上下文中消失。即使服务商对某段前缀命中缓存，那段文本仍属于请求上下文；不能拿“缓存了多少 token”去抵消窗口占用。

五、哪些内容必须保留，哪些内容可以筛选？

AgentHub 把不同内容显式分类，核心区别如下：

类别 例子 预算处理原则
Runtime policy 平台运行规则 必需
System prompt 已发布的 Agent 指令 必需
Current user task 用户这次的问题 必需
Tool definitions 工具名称、参数 schema 必需
Conversation 历史问答、完整工具交换 按组处理
Memory 跨对话共享短句 可以筛选或丢弃
RAG evidence RAG、Wiki 返回的证据 接受证据预算与来源校验
Tool result 其他工具结果 接受工具结果预算

必需内容自己就放不下时，系统应该明确报错。不能悄悄删掉用户问题的一半，然后发送一个看似成功但含义已经改变的请求。分类与准入

1. 为什么按“完整交换”处理历史？

假设历史中存在：

[
  {"role": "assistant", "tool_calls": [{"id": "call_7"}]},
  {"role": "tool", "tool_call_id": "call_7", "content": "检索结果"}
]

这是省略参数的结构示意。

如果只留下第二条，工具结果就失去了对应调用；只留下第一条，也可能形成不完整的交换。

因此，预算处理需要识别一组消息之间的结构关系：

  • 一次用户输入与对应回答。
  • 一次 assistant 工具调用与相应 tool 结果。
  • 带有来源注册表的证据及其引用关系。

“删一条消息”不一定是一个合法的操作单位。

当前分类器通过角色、位置和调用 ID 做这件事，不需要先让模型理解文本。7

2. 不要背一个过度简单的优先级口诀

例如：

“永远先保留 RAG，再保留 Memory，最后保留历史。”

这并不符合当前所有代码路径。

基础 ContextBudgetPolicy 会先保障必需项；会话历史按完整组保留最近后缀；独立 Memory、证据等使用剩余空间。RAG 和工具结果各自还有池内限额，较新的观察优先获得相应池内预算。

此外，显式启用的 deterministic_history_v1 有更严格的历史规划和完整性要求。

所以准确的理解是：

先看内容类别，再看它属于哪个完整组，再看已发布版本启用了哪套策略。基础准入 · 严格历史规划

六、摘要解决什么问题？为什么不把所有旧消息随便压一下？

摘要的用途是：

用一个更短的派生产物，代替一段符合条件的旧历史，让后面的任务仍能理解必要背景。

但摘要有两个成本：

  1. 需要额外模型推理。
  2. 可能改变原文含义、遗漏条件或丢失证据关系。

因此，AgentHub 的摘要能力不是一个无条件执行的 summarize(all_messages)。

在显式启用的上下文策略中，默认有三条压力线：

阈值 含义
工作输入预算的 70% 软压力线
85% 硬压力线
55% 期望压缩到的目标线

这些比例可以通过符合约束的发布配置调整。判断压力时要看裁剪前的需求及预计增长，避免“先删掉一部分，再宣称上下文没有压力”。上下文策略 · 历史规划

当前摘要范围比你想的严格

当前 plain_text_prefix_v1 主要允许处理：

  • 从最旧历史开始的一段连续前缀。
  • 具有持久化资格证明的纯文本问答。
  • 保留最近的完整轮次；当前应用路径保留最后两轮历史。

包含工具调用、证据注册表、知识快照、Wiki publication 或 Artifact 的历史，不能直接当作普通文本丢给这条摘要路径。

原因是这些历史还包含执行与来源关系。把它压成“此前查询过差旅政策”，不等于保留了：

  • 查的是哪个文档版本。
  • 工具究竟成功还是失败。
  • 当时引用了哪个片段。
  • 那条来源现在是否仍被允许读取。

当必须保留的材料放不下，又没有合格摘要覆盖时，严格路径会阻止请求。历史范围与资格 · 摘要应用

七、一个可追溯的摘要，不只是一个字符串

最简单的实现可能是：

summary = llm("请总结以上历史")

但在这个项目里，摘要需要带结构和来源。

概念上类似：

{
  "goal": {
    "text": "此前讨论上传接口的设计",
    "source_ids": ["turn_1"]
  },
  "decisions": [
    {
      "text": "项目后端采用 Python",
      "source_ids": ["turn_2"]
    }
  ],
  "open_questions": [
    {
      "text": "是否需要支持批量上传",
      "source_ids": ["turn_3"]
    }
  ]
}

这是简化示意；实际 schema 还包括支持事实、冲突、已完成动作引用、下一步和遗漏来源等字段。摘要结构

整个过程包括：

  1. 固定摘要覆盖哪些历史来源。
  2. 检查执行权、权限和预算。
  3. 记录任务及模型请求的派发状态。
  4. 调用摘要模型。
  5. 保存原始响应。
  6. 校验结构、来源 ID、覆盖范围和必要事实。
  7. 保存不可变的摘要产物与版本身份。
  8. 在后续模型调用前再次验证来源绑定。

相关表将任务、来源、派发、响应和产物分开保存，避免只留下“一段看不出从哪里来的总结”。摘要 Worker · 摘要数据模型

两个边界尤其重要

第一，有 source_ids 不等于摘要语义一定正确。

机械校验能检查来源是否存在、是否在允许范围内，却不能仅凭一个 ID 证明：

“不得报销”

没有被错误概括成：

“允许报销”。

项目的摘要校验代码也明确承认这类语义边界。摘要校验

第二，历史计划不是当前指令。

例如摘要里写着“下一步准备删除旧索引”，那只是以前讨论过的计划，不能自动成为当前必须执行的操作。

当前摘要视图明确标记为 UNTRUSTED_DERIVED_SUMMARY 和历史背景；当前用户问题仍作为独立消息存在。服务端保护的原话事实和权威动作记录也会单独交付。摘要渲染

摘要失败时同样要分情况：如果原上下文仍能合法发送，可以回退；如果原计划已经被预算阻塞，就不能假装摘要成功后继续。模型调用结果未知、权限变化和执行权丢失还有专门处理。

八、历史没放进窗口，能不能再找回来？

可以有补读路径，但它与长期 Memory 是不同能力。

AgentHub 的 thread_history_search 需要相应开关、当前 Run 所属的 Thread 和搜索实现。它只查询：

  • 当前 Workspace。
  • 当前 Thread。
  • 当前轮次之前。
  • 已成功且归属关系可验证的 Run。

当前实现主要对用户输入和最终回答做 SQL ILIKE 词面搜索，不是向量检索全部历史，也不是跨所有用户搜索聊天记录。历史搜索实现 · 工具装配

这三种操作可以这样区分：

操作 想解决的问题
保留最近历史 让对话自然连续
压缩合格的旧历史 在预算内保存必要背景
主动检索更早历史 当前问题需要回查某件旧事

而长期 Memory 解决的是下一部分的问题：

> 换一个 Thread 后，哪些稳定的项目背景仍值得被取出？

第三部分：长期 Memory，怎样保存、怎样读取、怎样治理

九、当前项目怎样把一句用户原话变成长期记忆？

先明确范围：

AgentHub 当前的长期记忆属于 (workspace_id, agent_id)，不是个人 user_id。

这意味着，同一 Workspace 下同一个 Agent 的不同授权使用者，可能共享这些项目记忆。它适合记录“项目统一使用 Python”这类团队约定；不能直接把它当成按个人隔离的用户画像系统。

长期 Memory 默认关闭，需要在发布配置中启用。它也不是“每一句聊天都必须记住”。Memory 数据模型 · 运行配置

1. 写入发生在主任务成功之后

当前主要路径是：

这里调用抽取模型的是后台任务。即使抽取失败，也不应把已经成功的业务 Run 改成失败。运行完成处理 · Memory Worker

无 Thread 的单次 Playground Run 不走这条自动抽取路径。

2. 抽取模型看什么？

一个非常关键的设计是：

当前 extractor 只接收这一轮的用户原话，不接收 assistant 的答案。

为什么？

假设模型第一次回答错了：

“这个项目使用 Java。”

如果再把这段 assistant 回答当成可靠记忆保存，下一次它又从 Memory 中读到“项目使用 Java”，错误就被自己的输出反复强化。

因此，当前抽取提示主要允许保存用户明确陈述的团队、项目、工作流信息，并排除临时状态、猜测、个人画像和 assistant 回答。抽取请求

源码还有输入长度上限：抽取请求取用户消息前 2,000 字符左右的片段。因此它不是对任意长对话的完整理解与永久保存。

3. 模型返回的是候选，还不能直接当事实入库

假设用户说：

“我们这个项目的后端统一使用 Python，示例请优先给 Python。”

教学示例中的候选可以是：

{
  "memories": [
    {
      "content": "项目后端统一使用 Python。",
      "kind": "CONSTRAINT",
      "evidence": "我们这个项目的后端统一使用 Python"
    }
  ]
}

后端要检查：

  • 结构是否符合要求。
  • 内容长度是否在允许范围。
  • 是否有非空的原话引文。
  • 引文是否确实出现在用户输入中。
  • 是否与已有记忆重复。
  • 当前任务是否仍有合法写入权限。

当前正式写入每轮最多接收 3 条，每条 8–400 字符，原话证据最多 300 字符。没有值得记忆的信息时，空数组是正常结果。抽取校验 · 写入门禁

这里也必须保留一个边界：

“引文确实存在”能够证明用户说过这段话，不能自动证明模型生成的 content 完全忠实于原话。

十、Memory 的数据库为什么要分成三张表？

你前面已经学过数据库表设计，这里正好把它用起来。

1. workspace_memories：记忆内容本身

字段 作用
id 这条记忆的稳定身份
workspace_id、agent_id 归属与共享边界
content 可独立阅读的短句
content_hash 归一化内容身份，用于去重与快照校验
kind FACT、PREFERENCE、DECISION、CONSTRAINT
status ACTIVE、INVALIDATED、SUPERSEDED
thread_id、source_run_id 最初从哪个对话、哪次运行产生
provenance 原话证据等来源信息
salience 有多少不同来源运行强化了这一陈述
expires_at 新选择时是否已过期
last_used_at 最近被纳入准入请求的时间

注意：字段名称叫 FACT，不等于系统已经证明内容在现实中为真；salience 也不是模型置信度。Memory 模型

2. memory_extraction_jobs：后台任务的进度

这张表回答：

  • 哪个 Run 需要抽取？
  • 是否有人正在处理？
  • 是否可能已经调用过模型？
  • 模型候选有没有保存？
  • 失败发生在什么位置？

如果只用 Celery 队列而不保存任务意图，可能出现：

主任务已经结束，但任务消息没投递出去，之后没人知道还欠着一次 Memory 抽取。

把意图先持久化，恢复程序才有依据寻找未完成任务。

3. memory_contributions：同一句话由哪些运行贡献？

假设用户在三个不同对话中重复强调：

“项目后端统一使用 Python。”

这可以强化同一条记忆。

但如果只是同一个 Celery 消息被投递了三次，就不应该把重要性加三次。

因此，这张表用来源 Run 和内容身份约束一次贡献：

同一个 Run + 同一个 content_hash → 只算一次贡献
不同 Run 再次表达同一句话 → 可以强化已有记忆

同时，数据库对同一 Workspace、Agent 下 ACTIVE 记忆的内容哈希设了部分唯一索引。并发去重最终由数据库约束兜底，不能只靠“先查一下，没有再插入”。模型约束 · 记录与强化逻辑

为什么不用一张表全部解决？

因为三个对象的生命周期不同：

  • 记忆内容可能存在很久。
  • 抽取任务可能成功、失败或跳过。
  • 同一记忆可以被多个 Run 贡献。

拆开后，才能分别解释“记住了什么”“这次抽取怎么了”“为什么它越来越容易被选中”。

十一、读取 Memory：当前并不是向量检索

在首次 PREPARE 中，当前实现主要做：

  1. 读取本 Workspace、Agent 的 ACTIVE 且未过期记忆。
  2. 根据当前问题生成搜索词。
  3. 对记忆排序。
  4. 最多选择 8 条。
  5. 把选择结果冻结到当前 Run。
  6. 将选中的内容组装成 Memory 消息。
  7. 再接受上下文预算检查。读取逻辑 · 运行快照

1. 数据库先负责范围过滤

简化 SQL 可以理解为：

SELECT id, content, content_hash, kind, salience, created_at
FROM workspace_memories
WHERE workspace_id = :workspace_id
  AND agent_id = :agent_id
  AND status = 'ACTIVE'
  AND (expires_at IS NULL OR expires_at > :now);

这段 SQL 是教学表达。实际实现还会在应用层进行排序与选择。

2. 排序依次看什么？

当前主要顺序是：

  1. 查询词在记忆内容中的包含命中数。
  2. salience。
  3. 创建时间。

这是依次比较的排序键，不能理解为已经训练好的语义相关性模型。

例如：

记忆 与“后端接口”词面关系 可能的作用
项目后端统一使用 Python 有直接词面关联 很可能有帮助
本项目输出先结论后依据 可能没有直接词面重叠 有时仍是有用背景
每周三下午进行项目例会 通常关系弱 可能是干扰

默认策略在数量不足时仍可能选入零词面匹配的记忆。显式启用的 lexical_overlap_v1 才会进一步过滤没有词面重叠的候选。

但词面过滤也可能遗漏同义表达。例如“服务端实现”与“后端接口”语义接近，却不保证形成足够的匹配。

因此：

当前策略的优点是简单、可解释、无需额外向量索引；限制是不能保证语义召回与语义相关性。排序实现 · 可选选择策略

3. 为什么选完还要冻结？

假设一次任务要经过工具审批：

  • 10:00 创建 Run，选中 M1、M2。
  • 10:02 等待审批。
  • 10:05 后台产生新的 M3。
  • 10:10 审批通过，任务恢复。

如果恢复时重新选择，任务进行到一半，背景就可能变了。

当前 Run 会保存类似下面的快照：

{
  "selected_at": "示意时间",
  "memory_ids": ["M1", "M2"],
  "memory_content_hashes": {
    "M1": "hash_of_M1",
    "M2": "hash_of_M2"
  }
}

同一个 Run 再次准备时，按照冻结 ID 加载并验证内容身份，不重新挑选。即使当初选中的是空列表，也是一份有效的“已经选择过”的结果。35 · 快照读取

它的意义是固定这次运行的背景选择，方便恢复与解释；不是保证模型在相同输入下每次生成完全相同的回答。

十二、选中了 Memory，为什么模型还可能没用到？

这里有四个不同阶段：

阶段 能说明什么 不能说明什么
已保存 数据库里有记录 这次任务会选中
已选择 Run 的候选快照包含它 最终预算一定保留
已准入 准备发送的请求包含它 服务商必然收到
模型已正确采用 回答确实符合该背景 仅靠数据库使用时间就能证明

Memory 的预算投影以完整单条为单位。例如：

“生产环境禁止直接删除用户文件。”

预算不够时，应该整条跳过；不能只交付成：

“直接删除用户文件。”

当前 memory_atomic_v1 会按冻结顺序尝试放入完整的 id、kind、content 记录，放不下则跳过，必要时丢弃整个 Memory 消息。Memory 原子投影

一个源码细节：role 和预算类别不是同一个概念

Memory 初始消息使用 role=system 包装，但分类器明确把它识别为 MEMORY，不会因此把它列入必须保留的 SYSTEM_PROMPT。

内容还会明确标记 UNTRUSTED，提示它可能过时或有误，应服从当前用户要求。这里表达的是应用对材料的用途和信任定位，不是对模型绝不会误用的证明。消息构造与分类

last_used_at 也在模型请求发送前更新，所以它准确表达的是“被纳入准入请求”，而不是“模型已正确理解”。

排查“它怎么忘了”时，先确定在哪个阶段掉了，才能决定应该改抽取、选择、预算还是回答策略。

十三、旧记忆错误、冲突或者过期，怎么处理？

1. 当前不会自动解决所有语义冲突

假设先保存：

“项目后端统一使用 Java。”

后来用户说：

“项目后端以后改用 Python。”

这两句话内容哈希不同，不能靠哈希去重发现它们描述的是同一事项的变更。

当前自动抽取流程没有完整的语义替换能力。虽然表里有 SUPERSEDED 和 superseded_by_id，自动抽取并不会据此自动识别矛盾并替换旧项。

字段存在，不等于整套业务策略已经实现。Memory 状态与写入 · Store

当前管理能力主要包括：

  • 查看与搜索记忆。
  • invalidate：让记录失效。
  • reactivate：恢复可恢复的失效记录。

这些操作经过相应权限检查。Memory 管理服务

2. 新 Run 和旧 Run 的行为不同

情况 当前行为
某条 Memory 被人工失效 后续新 Run 的候选选择排除它
旧 Run 已经冻结该 Memory 恢复时仍可按旧快照加载
冻结记录的内容被改写，hash 不再匹配 新格式快照完整性检查报错
删除来源 Thread Memory 可以继续存在，来源外键可置空

这是一种明确的取舍：日常失效影响新的选择，历史 Run 仍能解释当时使用过的背景。

不过，删除来源 Thread 后，即使记忆中还保留原话片段，也不等于完整原对话永远可访问。来源可追踪到什么程度，取决于相关原始记录是否仍然保留。

3. 后台崩溃时，不是所有情况都应该重调模型

崩溃位置 合理的恢复依据
任务意图已提交，但队列消息没投递 对账后补投任务
确认尚未发送模型请求 可以恢复执行
模型候选已经保存，Memory 写入未完成 重做确定性的数据库写入
可能已调用模型，但没有可恢复候选 标记结果未知，避免盲目重发

当前代码已经区分“候选已落盘”和“模型调用结果未知”。后者会记录 MEMORY_EXTRACTION_OUTCOME_UNKNOWN，不能假装费用和结果都不存在。恢复逻辑

另外，虽然 expires_at 可以参与过滤，当前自动抽取并没有普遍设置自动 TTL，也没有自动按时间衰减 salience。重复出现次数高，也不能证明内容更真实。

第四部分：Wiki，怎样把原文编译成可追溯的派生知识

十四、已有 RAG，为什么还需要 Wiki？

我们用一个具体问题理解。

知识库里可能有：

  • 《差旅管理制度》。
  • 《会议费用补充说明》。
  • 《特殊审批流程》。
  • 《常见报销问题》。

用户反复问到“住宿”“会议”“审批”这些主题。

原始 RAG 每次围绕当前问题检索相关片段。Wiki 则尝试提前完成一些可以复用的工作：

  • 哪些片段属于“住宿报销”。
  • 哪些片段讲“事前审批”。
  • 哪些主题之间有关系。
  • 哪些说法可能存在冲突。
  • 每条摘录分别来自哪里。

所以，两条路径的区别可以概括为：

维度 原始 RAG Wiki
主要组织时间 用户提问时 编译时提前组织
直接读取对象 原始分块 主题页、claims 与来源引文
主要成本 查询编码、检索、重排等 编译提取，加后续查询
容易出的问题 漏召回、排序不合适 归组错误、条件遗漏、版本过期
依据最终来自哪里 原始文档 仍然来自原始文档

Wiki 的价值在于复用组织工作，不在于让生成内容自动获得原文的权威性。

当前 AgentHub 还没有引入 Neo4j 或 Wiki 专属向量数据库。Wiki 主要保存在 PostgreSQL；Qdrant 仍属于原始 RAG 检索侧。Wiki 数据模型 · 查询实现

十五、这里的“知识编译”具体编译什么？

可以借用编译器的思路理解，但它不是传统语言编译器那种严格等价转换。

传统程序编译器把源代码转换成目标程序；这里是：

把固定版本的原始资料，转换成结构化 claims、主题页面、关系和来源映射。

转换过程中有模型参与，所以语义可能出错。版本、来源和校验就格外重要。

1. 模型从原始 Chunk 提出候选

当前 GatewayWikiCompiler.extract() 按原始 Chunk 逐个调用模型，要求返回结构化结果。

例如原文 C17：

“普通差旅住宿超过每天 500 元，须在出差前取得审批。”

教学示例中的候选可以是：

{
  "topic": "住宿费用审批",
  "kind": "topic",
  "predicate": "超标准住宿要求",
  "value": "出差前审批",
  "condition": "普通差旅且每天超过500元",
  "chunk_id": "C17",
  "quote": "普通差旅住宿超过每天 500 元，须在出差前取得审批。",
  "related_topics": ["差旅报销"]
}

模型在这里做的是语义提取：判断主题、关系、条件和候选命题。这个步骤确实需要模型推理。Wiki 编译器

2. 后端验证原文身份和引句

后端会检查：

  • 输出结构是否合法。
  • chunk_id 是否就是允许处理的原始片段。
  • quote 是否非空。
  • quote 是否确实是该片段的精确子串。
  • 来源是否属于允许的 Workspace、知识库和快照。

随后，document_id、document_revision_id 和 locator 等身份信息由服务端根据原始 Chunk 补齐，不能让模型任意指定。

在落库边界还会再次执行验证。57

这里的关键思想是：

模型负责提出“这段话可能表达什么”；程序负责验证“这段话究竟从哪里来、能不能使用”。

3. 普通代码组织页面

organize() 会按主题归组，去重，构建关系，并生成页面。

当前 Markdown 主体主要由经过验证的原文引文组成，类似：

# 住宿费用审批

> 普通差旅住宿超过每天 500 元，须在出差前取得审批。

Source: C17

这是教学示意。

当前不是再调用一个模型自由写出整篇百科文章，然后把这篇生成文章当成第一手事实继续编译。59

4. 精确引用仍然不能证明理解正确

设原文仍是：

“普通差旅住宿超过每天 500 元，须在出差前取得审批。”

某个错误候选却把条件写成：

“所有住宿都需要审批。”

即使 quote 逐字正确，条件解释仍然错了。

因此，这几个保证必须分开：

检查 能证明什么
ID 和快照检查 来源身份及范围匹配
精确引文检查 这段话确实存在于原文
语义评估 引文是否支持候选命题或最终回答
现实业务核实 原文件本身是否真实、适用、仍有效

前两项可以大量依赖确定性代码，后两项不能只靠“子串存在”就完成。

十六、Wiki 在数据库里怎样组织？为什么有多层版本？

当前四张核心表是：

表 保存什么
wiki_compilations 一次编译、来源快照、编译规格、任务状态、发布信息
wiki_extractions 某原文 Revision 在某提取规格下的结构化提取缓存
wiki_pages 某次编译产生的页面、Markdown、claims、relations
wiki_source_revocations 在 Wiki 使用范围内被撤销的原文 Revision

这里有两个非常容易凭名称猜错的地方：

  1. 当前没有单独的 wiki_publications 表。发布主要是 WikiCompilation 进入 PUBLISHED 状态。
  2. 当前没有另造一张 WikiPageRevision 表。页面属于某个 compilation_id，新的编译产生新的页面集。

claims 和 relations 作为 JSONB 保存；Markdown 是便于阅读的投影，不能只靠解析 Markdown 来恢复全部业务身份。Wiki 表结构

为什么不能只有“原文快照版本”？

因为同一批原文也可能用不同的：

  • 提取提示词。
  • 模型版本或执行计划。
  • 输出 schema。
  • 组织规则。
  • 冲突复核配置。

编译出不同的页面。

因此至少要分三层：

身份 回答的问题
source_snapshot_id + hash 编译用了哪些原文版本？
identity_hash 使用这些原文和哪一套冻结编译规格？
content_hash 最终这一套页面和结构化内容具体是什么？

只记录“来源是 K1”，还不足以知道“当时给 Agent 使用的是哪一版 Wiki”。编译请求与内容身份

从请求到发布

READY 表示编译产物准备好了，PUBLISHED 表示它已经经过发布动作成为可绑定版本。

当前发布由具备权限的调用方显式执行，不由提取模型自行决定。编译执行与发布

十七、与上一节衔接：只改一份文档，Wiki 能复用什么？

上一节讲过：原始 RAG 的新 Revision 会完整重新处理，没有自动按相同文本复用旧 Embedding 的跨修订缓存。

Wiki 这里存在另一种缓存：

同一个原文 Revision，在同一套提取配置下，其已经验证的结构化提取结果可以复用。

当前缓存按以下身份查找：

workspace_id
+ document_revision_id
+ compiler_hash

还会核对输入内容身份 input_hash。76

假设知识库中有：

文档 上一次编译 下一次编译
A：基础制度 A-V1 A-V1，未变
B：补充说明 B-V1 B-V2，修改过
C：审批流程 C-V1 C-V1，未变

在提取配置不变时：

  • A-V1 可以复用原提取结果。
  • C-V1 可以复用原提取结果。
  • B-V2 是新 Revision，当前会重新提取它的全部 Chunks。
  • 最后汇总这些结果，重新组织新的完整页面集。

所以，准确说法是：

Wiki 可以跨编译复用未变化的 Revision 提取结果；还不能由此推导出“同一文档只改一段，就只调用一次模型处理那一段”。

此外，如果模型已经完成 A 的提取且缓存已提交，随后编译进程崩溃，恢复时可以复用 A 的结果。整套页面与 READY 在最后一个事务中安装，避免把只生成一半的页面集宣布为完整可用。

但如果模型调用已经发生、结果尚未持久化就崩溃，仍可能产生无法完全避免的重复成本。持久任务和缓存不等于所有外部模型调用都拥有严格的“恰好一次”保证。

十八、查询 Wiki 时，怎样决定读 Wiki、读原文，还是都读？

当前不是部署一个额外的智能路由模型来决定所有策略。调用方通过 mode 和 intent 表达请求，查询代码执行明确规则。

请求 当前主要行为
WIKI 只取 Wiki 页面与经过验证的引文
RAG 调用原始检索器，仍受指定来源范围约束
HYBRID 同时获取 Wiki 与原始 RAG 证据
AUTO + overview 优先 Wiki；缺少 Wiki 证据或存在冲突时补原文
AUTO + fact 请求原始 RAG 证据
AUTO + synthesis 请求原始 RAG，可同时利用 Wiki

这里有两种不同的“混合”：

  • 原始 RAG 的混合检索：例如 Dense 与 Sparse 的候选融合。
  • Wiki 的 HYBRID：派生 Wiki 证据与原始 RAG 证据结合。

它们不处于同一个层次。Wiki 查询路由

1. 当前 Wiki 页面是怎么匹配的？

主要是对固定编译版本的页面进行标题包含、词项重合等匹配；中文也使用二元组等词面处理。关系可以帮助补充相关冲突页。

因此不要把当前实现说成：

“我们已经做了图数据库上的复杂多跳知识推理。”

当前有结构化关系和导航，但没有因此自动获得完整 GraphRAG 的能力。

2. query_wiki 会不会再调用一个模型回答？

原生 Agent 工具的典型链路是：

  1. Agent 模型选择调用 query_wiki。
  2. 工具查询并返回证据。
  3. 后端登记来源并投影。
  4. 下一轮 Agent 主模型根据证据回答。

工具本身返回证据，不是每次都额外运行一个完整问答模型。原生 Wiki 工具

独立 REST 查询接口则允许显式提供回答模型配置，再额外调用独立回答器。这个路径与原生 Agent 下一轮生成不能混为一谈。Wiki API

此外，字段 insufficient_evidence=false 最多说明没有触发当前代码检查到的不足条件，不能解释为“材料已经被语义证明足够回答问题”。

十九、派生知识怎样保留原文来源？这是本节最核心的一条链

假设回答中出现：

“这种住宿费用需要事前审批。[E1]”

后端需要同时回答两个问题：

  1. E1 来自哪一版 Wiki？
  2. 这一版 Wiki 的这条引文，又来自哪一个原始片段？

1. 为什么来源不能只记录一个文档名？

因为同名文件可能有多个版本；同一份文档也可能被多次上传、修改、替代。

“来源：《差旅制度》”不足以回答：

  • 哪次修订？
  • 哪个片段？
  • 原话是什么？
  • 当时属于哪个快照？
  • 哪一版 Wiki 对它进行了组织？

所以当前派生证据需要同时保留：

  • origin = WIKI_DERIVED。
  • publication ID 和 hash。
  • Wiki 页面身份。
  • 原始 Revision、Chunk 与引文。
  • 原文定位信息。
  • 来源快照范围。

Wiki 查询返回的原始 RAG 记录则明确标记为 RAW。证据 envelope

2. 模型是不是必须看到所有这些长 ID？

不需要。

当前 query_wiki 会通过紧凑的证据视图，把适合阅读的内容交给模型。例如：

{
  "id": "E1",
  "origin": "WIKI_DERIVED",
  "wiki_page_id": "住宿费用审批的页面键",
  "snippet": "普通差旅住宿超过每天 500 元，须在出差前取得审批。",
  "locator": {"page": 3},
  "conflict": false
}

这是简化的阅读视图示意。完整 publication hash、来源身份与映射保存在私有注册表中。

这里就用到了上一节的“投影”：

模型看到适合阅读和引用的视图；后端保留适合核查和恢复的完整来源关系。

当前模型侧的 wiki_page_id 使用页面 page_key，不必等同于 wiki_pages 表的主键 UUID。派生证据结构 · 证据视图

3. 两条路径命中同一个原文，不代表两份独立证据

如果：

  • 原始 RAG 返回 C17。
  • Wiki 页面也引用 C17。

这说明同一份原始材料通过两条路径被找到，不能据此说：

“有两份独立资料证明这条规则。”

来源身份不仅用于生成漂亮的引用，也用于避免把重复出现误当成独立支持。

同样，source_revisions 表示一个页面受理 claims 涉及的来源修订集合，不代表每一条引句都得到集合中每个文档的共同支持。

二十、原文更新后，Wiki 和 Agent 会怎样变化？

这一部分与上一讲的文档修改直接衔接。

1. Wiki 不会因为原文改了，就原地修改旧页面

典型维护过程是：

  1. 上传原文新 Revision。
  2. 完成原始入库。
  3. 以新的来源范围请求 Wiki 编译。
  4. 复用未变 Revision 的提取缓存。
  5. 生成新的页面集。
  6. lint 后显式发布。
  7. 让需要使用新版 Wiki 的 Agent 版本绑定新版。

旧页面、旧编译身份与历史来源仍然分开保留。Wiki 编译与发布服务

2. 特别注意：两种 LATEST 的解析时间不同

能力 LATEST 在何时解析 新资料发布后，旧 AgentVersion 的新 Run 会怎样？
原始 RAG 知识绑定 新 Run 创建时 可纳入新的可用原文修订
Wiki 绑定 Agent 发布时 继续使用该 AgentVersion 已冻结的 Wiki

这不是对上一讲的推翻，而是两种绑定的实际实现不同。

Wiki 的 AgentVersion 已保存具体 publication ID 和 hash。新 Run 主要验证该绑定仍存在、身份匹配且未被撤销，不再重新解析“最新 Wiki”。发布绑定 · Run 有效绑定

因此：

发布了新版 Wiki，并不会自动让所有旧 AgentVersion 切过去。

想使用新版，需要更新相应绑定并重新发布 Agent 版本。这里也没有“原文更新后自动编译、自动审核、自动发布”的完整订阅流程。

3. 过期、历史可读和撤销，要分开

状态或场景 含义
WIKI_STALE 对要求 current 的入口而言，来源不再匹配当前可用集合
读取固定历史版本 明确使用旧的冻结来源，可能仍允许
来源被撤销 不允许继续通过相应 Wiki 路径交付该来源

独立 Wiki 查询默认要求 current，原文更新后旧 Wiki 可能报 stale。

原生 Agent 工具使用冻结历史语义，允许使用已绑定的旧版本，但仍执行来源撤销检查。

所以：

  • “旧版”不必然等于“无法读取”。
  • “已经固定版本”也不意味着可以忽视撤销。

Wiki 专用撤销的范围是 Wiki 及其原文回退路径，不等于全局删除原始文档。来源检查 · 原生工具

还有一个更深入的细节：以前的 Wiki 结果再次作为历史进入上下文时，也要重新检查发布身份、原文及撤销状态。“以前看过”本身不能代替现在的来源验证。Wiki 历史证据验证

4. 冲突不会自动由模型选出“赢家”

当前普通归组会把某些相同主题、谓词、条件却取值不同的陈述标为可能冲突。还支持显式的模型复核或人工声明路径，但这不代表冲突识别已经完美。

发现冲突后要保留双方依据，不能仅因为某条排在前面，就直接覆盖另一条。

对于带有例外条件的规则，“500 元标准”与“会议统一安排时按通知标准”也可能只是适用范围不同。是否冲突，需要理解条件；简单标签和字符串比较不一定能正确判断。归组与冲突处理

第五部分：把上下文、Memory、Wiki 放进同一项任务

二十一、一次实际问答中，三者怎样协作？

假设项目已经保存共享约定：

“本项目的答复先给结论，再列原文依据。”

知识库中有两份教学材料：

  • A：普通差旅住宿超过 500 元需要事前审批。
  • B：会议统一安排的住宿按会议通知标准处理。

用户现在问：

“沿用我们的答复格式，解释一下会议统一安排的住宿超过 500 元怎么处理。”

一次合理的执行过程可以是：

阶段 系统取得的信息 为什么要进入或影响本次请求
当前问题 会议统一安排、超过 500 元 确定这次要解决的具体问题
Memory 选择 先结论，后原文依据 延续共享的答复格式
历史选择 同一 Thread 中尚相关的背景 理解省略的业务语境
Wiki 查询 住宿、会议、审批的组织结果 快速定位相关主题和例外关系
原始 RAG A、B 的完整相关原句与条件 检查具体适用范围
证据投影与准入 能完整交付的证据及短引用 控制长度，并保留必要来源关系
模型生成 根据已交付的两类条款回答 解释会议规则与普通规则的适用区别

其中：

  • Memory 决定的是已有的项目背景，不应该凭空成为报销规则的法律或业务依据。
  • Wiki 帮助组织资料，但最终仍要核对原文条件。
  • 上下文预算决定模型最后究竟看到了 A、B 两条，还是只看到了其中一条。

如果只交付 A，漏掉 B，模型就可能误把普通规则直接套在会议场景。

这时错误可能发生在：

  1. B 根本没被检索到。
  2. B 被查到了，但在投影或总预算中被丢掉。
  3. B 已经进入请求，但模型没有正确理解例外条件。

这三种错误需要不同的修复。不能一看到回答不对，就统称为“大模型幻觉”。

二十二、以后怎样回答“哪些信息进了模型，为什么，来源在哪”？

可以给每类材料建立一张解释表：

材料 进入的原因 去哪里追来源
当前用户问题 当前任务，属于必需输入 当前 Turn / Run 输入
Agent 系统指令 当前发布版本的行为规则 AgentVersion 的冻结配置
最近历史 对话连续性或严格历史规划要求 Thread Turn、历史 transcript、来源清单
历史摘要 合格旧前缀在预算压力下被摘要替代 Summary artifact、source_ids、绑定与版本
长期 Memory 本次选择命中，并通过 Memory 预算 Memory ID、内容 hash、来源 Run、原话 evidence
原始 RAG 检索与选择后交付 Snapshot、Revision、Chunk、locator
Wiki 证据 路由命中派生页，并通过来源校验 Publication、页面 claim，以及对应原始 Chunk

对一条有争议的回答，不妨按四个问题排查：

  1. 存储层：原始信息和对应版本是否存在？
  2. 选择层：这次运行有没有选中它，为什么？
  3. 交付层：最终 ModelRequest 是否真的包含它？
  4. 回答层：模型对已交付内容的解释是否正确？

真正有用的运行日志，要能连接这四层。

“查到了 10 条”“本次用了 8,000 token”“Memory 最近使用过”这些单独数字，都不能完整解释回答为什么正确或错误。

二十三、如果由你从零实现，应该按什么顺序写？

这里给一条便于动手的实现顺序。它是学习建议，不表示需要重写当前 AgentHub。

第一步：只实现可解释的上下文组装

先能打印或检查：

  • 系统规则来自哪个发布版本。
  • 当前问题是什么。
  • 哪几轮历史被保留。
  • 工具定义占用多少预算。
  • 哪些证据被丢掉以及原因。

先把“实际发了什么”弄清楚，再增加更复杂的长期能力。

对应阅读入口：98、99、100。

第二步：实现最小的长期记忆闭环

完成：

  • 成功对话后的抽取任务。
  • 结构与原话证据验证。
  • 关系型数据库保存。
  • 同一作用范围内读取。
  • 冻结本次选择。
  • 完整条目预算准入。
  • 人工失效与来源查看。

重点理解为什么要有 jobs、memories、contributions 三种对象。

对应入口：Memory 模型、Store、抽取逻辑、Worker。

第三步：实现一份能回查原文的 Wiki

先只做：

  • 固定一个原文快照。
  • 从少量 Chunk 提取候选。
  • 校验精确 quote。
  • 按主题组织页面。
  • 保存编译身份。
  • 显式发布。
  • 查询时返回原文引用。

能从一条最终引用回到原文后，再考虑更强的语义匹配、冲突识别和增量优化。

对应入口：Wiki 模型、编译器、Service、Query、Agent 工具。

面试时可以怎样描述这套设计？

可以这样组织，而不是只说“我接了 Memory 和 RAG”：

我们把短期执行状态、跨会话记忆和派生知识分开管理。上下文侧按消息类别和完整交换做预算准入，并在明确配置下对可验证的旧历史前缀做摘要。长期记忆从成功对话的用户原话中异步提取，存入 PostgreSQL，运行开始时冻结所选 ID 与内容身份，再按完整条目交付。Wiki 则从固定原文快照提取结构化候选，用精确引文校验保留来源，生成版本化页面；Agent 绑定固定发布版，查询后通过短引用与私有注册表追溯到原始 Revision 和 Chunk。排错时分别检查信息有没有保存、有没有选中、有没有交付，以及模型有没有正确采用。

这段描述的技术重点，是每份信息都有明确的作用范围、进入请求的理由和可检查的来源。同时还要主动说明当前边界：词面 Memory 检索不等于语义召回，精确引用不等于语义正确，固定版本也不等于绕过来源撤销。
