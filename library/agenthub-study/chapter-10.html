第 8 讲：完整 RAG——从文档分块到带引用的回答

讲解原文

这一讲对应我们学习路线里的 第 5 阶段“完整 RAG”。归档按实际讲解顺序编号，所以它是第 8 讲。

前面你已经理解了数据库、后台 Worker 和 Agent 工具循环。现在把这些能力接起来，回答一个完整问题：

一份文档上传之后，程序怎样找出能回答问题的内容，把它完整地交给模型，再让用户知道答案依据了哪里？

这一节最重要的学习目标是：面对一个错误回答，你能够区分“没找到正确材料”“找到了但没有交付给模型”“模型读到了却答错了”。

源码继续沿用前面课程的固定提交 0。下文会明确区分项目已有实现、教学简化代码和可以进一步增强的设计；源码行为不等于已经核实了线上部署配置。

一、先建立全局认识：RAG 有两条链路

RAG 是 Retrieval-Augmented Generation，通常译为“检索增强生成”。

你可以把它理解成：回答之前，先从允许访问的资料中找证据，再把这些证据放进模型这一次的输入。

在这条链路里，上传文档通常不会修改回答模型的参数。模型之所以能够回答你的内部资料，是因为程序把相关内容提供给了它。

1. 写入链：把文档变成可检索的数据

这是上一节后台 Worker 继续往下做的事情：

这里的“离线入库”是指它不必在每次用户提问时重新执行，并不表示任务一定与网络无关。快照由后续发布、解析 LATEST 等调用触发；Worker 标记 READY 后不会自动创建快照。

2. 读取链：把问题变成有证据的回答

图里两条召回分支表示两种检索方法。这个提交的源码按顺序 await 两路搜索，不能从分叉图推断它们已经并行执行。

写入链的核心在 Worker，读取链的核心在 3；回答的校验行为还要看使用的是独立 Citation QA，还是通用 Agent。

二、先把数据库里的几个对象重新连起来

RAG 并不是“把 PDF 放进向量数据库，然后就能问答”。在 AgentHub 里，几个对象各自解决不同的问题。

对象 你可以怎样理解 主要保存或表达什么
Document 一份文档的长期身份 属于哪个知识库、名称、业务属性
DocumentRevision 这份文档的某一次内容版本 原文件位置、版本号、入库状态
DocumentChunk 某个版本中的一小段内容 正文、分块顺序、内容哈希、定位信息
KnowledgeSnapshot 本次可以使用的资料清单 固定的知识版本集合及其哈希
KnowledgeSnapshotItem 清单中的一项 某份文档对应的某个 Revision
RetrievedEvidence 一次查询取得的证据对象 Chunk 正文、身份、定位、分数、元数据

前五项是持久化的数据模型；RetrievedEvidence 是检索服务构造的返回对象，不应因为它有名字，就认为它一定对应一张独立的数据库表。数据模型 · 检索合同

1. 为什么文档、修订和分块不能混成一个对象？

假设你上传《退款规则》，后来把“七天”改成“五天”。

合理的数据变化是：

  • Document 仍是同一份《退款规则》。
  • 新增一个 DocumentRevision。
  • 新修订产生自己的 Chunks。
  • 新快照可以纳入新修订。
  • 已固定旧快照的历史运行，仍能解释它当时为什么依据“七天”回答。

如果直接覆盖旧 Chunk 的正文，却继续使用旧的身份和快照，历史引用就会失去解释力。

2. PostgreSQL 和 Qdrant 到底怎样分工？

在这个项目里：

PostgreSQL 保存 Chunk 的真实正文和关系；Qdrant 保存适合召回的向量、稀疏表示与身份信息。

Qdrant 中一个点的 payload 主要包括：

{
  "workspace_id": "...",
  "knowledge_base_id": "...",
  "document_id": "...",
  "document_revision_id": "...",
  "chunk_id": "...",
  "locator": {"type": "page", "page": 3}
}

这里没有完整正文。命中后，检索服务还要拿着 chunk_id 回 PostgreSQL 查询 DocumentChunk.text。索引记录构造 · 正文回读

这一步经常叫 hydrate。看到这个词，你就把它翻译成：

“索引给了我候选身份，现在把这个候选的真实内容补齐。”

这也接上了你前面学的数据库知识：向量索引负责寻找候选，关系数据库负责提供正文、归属和版本关系。

三、文档分块：为什么必须切，怎样切才不容易丢信息？

1. 为什么不把整本手册作为一个向量？

设想一本几百页的手册同时介绍退款、物流、账号和发票。

把整本书压成一个检索单元，会遇到几个工程问题：

  • 一个向量要表达许多不同主题，具体问题的信号可能被稀释。
  • 找到整本文档后，仍要定位具体段落。
  • 把整本书送入模型，会消耗大量上下文。
  • 引用只能指向“某本手册”，难以说明是哪条规则支持答案。

所以我们把文档切成更小的检索单元：Chunk。

但分块有一个核心取舍：

太大，带入很多无关内容；太小，可能把一个完整规则的前提、结论和例外拆散。

这里没有一个适用于所有文档的万能长度，参数需要结合材料和问题验证。

2. AgentHub 先怎样解析文档？

当前解析器支持文本、Markdown 和 PDF：

输入 实际解析方式 需要理解的边界
TXT / Markdown UTF-8 文本解码，形成文本 Block Markdown 并不因此自动获得完整的标题语义分块
PDF pypdf 逐页提取文字，非空页形成 Block 没有在这里实现 OCR、表格单元格恢复或复杂版面理解

如果扫描 PDF 只有图片，没有可提取的文字，这条解析链不能自动理解图片中的规则。此时应先检查解析结果和入库状态。16

源头没有得到正确文本，调大检索 top-k 无法补回它。

3. 当前生产默认：1200 字符，重叠 200 字符

Worker 默认使用 build_deterministic_chunks()，配置是：

knowledge_chunk_size_chars = 1200
knowledge_chunk_overlap_chars = 200

注意单位：Python 字符串的字符数，不是 token，也不是 UTF-8 字节数。

假设一个已经规范化的 Block 有 2500 个字符：

Chunk 字符区间 长度
0 [0, 1200) 1200
1 [1000, 2200) 1200
2 [2000, 2500) 500

起点每次前进：

step = chunk_size - overlap
     = 1200 - 200
     = 1000

下面是用于理解窗口算法的教学简化代码，省略了源码中的文本规范化、定位和 ID 生成：

def split_text(text: str, size: int, overlap: int) -> list[str]:
    if size <= 0 or not 0 <= overlap < size:
        raise ValueError("overlap 必须小于正数 size")

    chunks = []
    start = 0

    while start < len(text):
        end = min(start + size, len(text))
        chunks.append(text[start:end])

        if end == len(text):
            break

        start += size - overlap

    return chunks

实际实现逐 Block 分块，不跨 Block 拼接。因此默认 PDF 按页生成 Block 时，重叠不会自动跨页发生。分块实现 · Worker 的默认选择

4. 重叠能缓解什么，又不能保证什么？

下面是本讲自造的教学材料，不代表项目真实业务规则：

普通商品签收后七天内可以申请退货。
定制商品不适用上述七天规则。
退款审核通过后，三个工作日内原路退回。

假设第一个窗口正好在“定制商品不适用……”之前结束，模型只看到第一句，就可能误用规则。

重叠可以增加相邻片段保留上下文的机会，但它不能保证每个规则都完整，更不能保证跨页表格、长段落和多处例外自动正确组合。

因此检查分块效果时，要看：

“关键问题所需的前提、结论和例外，实际落在哪几块里？”

5. 仓库已有结构分块，但不是当前 Worker 的默认

structural_chunking.py 提供了优先按段落、标题和句子切分的实现。它默认 1000 字符，并要求 overlap 为 0。

这是可注入的另一种实现，不能因为仓库有这个文件，就说所有上传都已经使用它。结构分块实现

你将来想比较两种算法，可以用同一批问题，观察：

  • 正确证据是否更容易进入候选。
  • 条件句是否完整。
  • 交付给模型的总内容量。
  • 最终回答是否真正改善。

6. 每个 Chunk 为什么还需要稳定身份？

当前逻辑可以概括为：

内容哈希 = SHA256(规范化后的 Chunk 正文)

chunk_id = Hash(
    document_revision_id,
    ordinal,
    内容哈希
)

Qdrant point_id = UUIDv5(固定 namespace, chunk_id)

同一修订、同一切分结果可以得到相同身份，使重复写入能够对应到同一个索引点；新的修订会产生新的 Chunk 身份。22 · 23

这和上一节的重试机制联系起来了：稳定身份帮助重复执行安全写入，但不会让重复的 Embedding 计算自动免费。

四、Embedding：程序怎样理解“说法不同，意思接近”？

先区分三个经常混在一起的模型：

组件 输入 输出 在链路中的职责
Embedding 模型 一段文本 一个数值向量 找语义接近的候选
Reranker 问题与候选文本这一对输入 一个相关性分数 在少量候选中精细排序
回答模型 问题、证据和回答要求 自然语言或结构化回答 组织并生成答案

它们是不同职责，不要把“调用了模型”都理解为在生成聊天答案。

1. Dense：用稠密向量表达语义

AgentHub 默认通过 SentenceTransformer 加载 BAAI/bge-m3，配置维度为 1024，编码时进行向量归一化；Qdrant 的 dense 路径使用 cosine 距离配置。Embedding 适配器 · Qdrant 配置

教学上，你可以把它想成：

document_vector = embed("退款审核通过后，三个工作日内原路退回。")
query_vector = embed("审核通过以后，钱多久能到账？")

两句话没有逐字相同，但模型可能把它们编码到比较接近的位置。

实际向量有很多维。每一维不应被简单解释成一个人类可命名的词义，例如“退款程度”“时间程度”。

2. 文档和问题必须处于兼容的向量空间

入库时用模型 A 编码，查询时换成模型 B，即使两者维度相同，也不能据此认为向量可以直接比较。

所以更换 Embedding 模型时，要同时考虑已有索引的重建或迁移。这是向量空间一致性的工程要求。

AgentHub 的工具路径也有已发布检索模型身份与部署组件的检查，不匹配可以产生 KNOWLEDGE_MODEL_IDENTITY_DRIFT。工具中的身份检查

3. Sparse：补充对具体词项的匹配

语义接近有时还不够。

例如你问：

“AX-310 的 E104 错误怎样处理？”

AX-310、E104 这些精确词项很重要。词法检索可以补充 dense 的语义召回。

但这里一定要按实际代码讲：AgentHub 的这个 sparse adapter 使用 BGE-M3 的 tokenizer 取 token ID，再按词频构造权重：

某个 token 的权重 = 1 + log(它在文本中的出现次数)

Qdrant 的 sparse 索引再配置 IDF modifier。因此它适合被描述为：

基于 tokenizer 词频权重和 IDF 的词法稀疏检索。

不能仅凭 BgeM3SparseEncoder 这个类名，就认定它调用了 BGE-M3 的 learned sparse 权重；也不能直接把它说成完整的标准 BM25 实现。30 · 31

五、真正开始检索前，先决定“这次允许查什么”

这一层和你前面学的多租户、数据库关系、版本冻结直接相关。

假设 Qdrant 同时存在：

  • A 工作区的内部手册。
  • B 工作区的内部手册。
  • 同一份手册的旧修订和新修订。

检索不能只计算“哪个向量最接近”。

它还要保证：

候选属于当前工作区、当前知识库，以及本次固定快照包含的修订。

1. Snapshot 是一份固定清单

例如：

快照 K1
  文档 A → 修订 A-v2
  文档 B → 修订 B-v5

快照 K2
  文档 A → 修订 A-v3
  文档 B → 修订 B-v5

K1、K2 表达的是不同的成员集合。它们不是把所有文本和向量各复制一遍。快照服务

所以一个很常见的排错问题是：

“我已经上传新政策，而且 READY 了，为什么这个 Agent 还回答旧政策？”

首先要看这个 Agent 本次运行固定了哪个 Snapshot。

如果它使用的 K1 本来就不包含新修订，旧回答可能与该运行的固定资料完全一致。应检查版本绑定和发布流程。

2. Qdrant 先做范围过滤

源码会把 Snapshot 解析成允许的 Revision ID 集合，再构造相当于下面的条件：

workspace_id = 当前工作区
AND knowledge_base_id = 当前知识库
AND document_revision_id IN 本快照的修订集合

Snapshot ID 并不是直接作为一条文档正文写进 Qdrant。它先在 PostgreSQL 中被解析为 Revision 白名单。范围解析 · 索引过滤

3. 回 PostgreSQL 时再核对一次

拿到候选 chunk_id 之后，_load_chunks() 会关联：

  • DocumentChunk
  • Document
  • DocumentRevision
  • KnowledgeSnapshotItem

并再次约束工作区、知识库和快照成员关系。38

这一步的作用不仅是“拿正文”，还包括：

确认这个候选真的属于本次可用的资料集合。

理解到这里，你就能解释面试里的一个好问题：

“向量数据库已经过滤过了，为什么还要查关系数据库？”

因为索引命中只是候选发现；业务归属、版本成员关系和真实正文还要从持久化业务数据中确认。

六、混合检索与 RRF：两份排名怎样合成一份？

1. 为什么不把两路原始分数直接相加？

因为两路分数的含义和尺度不同。

Dense 的相似度和 sparse 的词法分数并不天然可比。例如一个是 0.82，另一个是 15.6，不能据此说后者“更相关”。

AgentHub 用 RRF，Reciprocal Rank Fusion，即“倒数排名融合”。

它主要利用候选在各个列表中排第几，而不是直接相加原始分数。融合源码 · Qdrant 官方融合说明

2. 用三个候选手算一次

假设两路结果是：

候选 Dense 排名 Sparse 排名
A 1 3
B 2 1
C 3 未命中

当前默认 rrf_k = 60。每路命中的贡献是：

[ \frac{1}{60 + rank} ]

因此：

A = 1/61 + 1/63 ≈ 0.03227
B = 1/62 + 1/61 ≈ 0.03252
C = 1/63       ≈ 0.01587

B 会排到 A 前面，因为它在两条检索路径上都有较好的排名。

下面是忽略并列排序等细节的教学简化代码：

def rrf(dense_ids, sparse_ids, k=60):
    scores = {}

    for ranking in (dense_ids, sparse_ids):
        for rank, chunk_id in enumerate(ranking, start=1):
            scores[chunk_id] = (
                scores.get(chunk_id, 0.0) + 1.0 / (k + rank)
            )

    return sorted(scores, key=scores.get, reverse=True)

正式实现还会处理重复身份、无效分数和稳定的并列顺序。40

3. 这里的分数不是“答案正确概率”

retrieval_score 在 Hybrid 路径里是 RRF 分数，在 Dense 路径里是 dense 分数。

它衡量的是候选排序信号。即使某段排第一，也不意味着它足以回答问题。

一个知识库里完全没有“退款税费”的规定，你问税费如何承担，检索仍可能返回最接近的退款段落。存在 top-1，不等于存在正确答案。

七、重排：为什么已经找到了，还要再算一次？

1. 召回与重排各自解决一个问题

召回的任务是：

“从大量片段里，先找出可能相关的几十段。”

重排的任务是：

“把问题和每段候选放在一起看，判断哪些更能回答这一个问题。”

Bi-encoder 可以提前计算文档向量；Cross-encoder 则一起处理问题与候选内容，所以通常放在较小的候选池上。这是常见的 Retrieve & Re-Rank 设计。Sentence Transformers 官方说明

AgentHub 默认重排模型为 BAAI/bge-reranker-v2-m3，适配器把 Query / Chunk 成对输入，取模型输出分数进行排序。Reranker 适配器

2. 一定要区分几个 top-k

以下是本课基线的常见默认配置；已发布的 Agent 可以覆盖它们：

参数 默认 控制什么
dense_top_k 30 Dense 召回上限
sparse_top_k 30 Sparse 召回上限
candidate_top_k 20 RRF 融合后保留的候选池
rerank_top_k None，沿用 candidate 数量 真正交给重排模型的候选上限
final_top_k 6 最终返回证据条数上限

这里的 30 + 30 不意味着一定得到 60 条不同候选，两路可能命中同一个 Chunk；后续还可能因为范围核验、去重、分数过滤或预算而减少。检索请求合同 · 检索流程

三个问题对应不同参数：

  • 正确证据根本没进候选池：先查解析、范围、召回和融合池。
  • 正确证据进了池，但没进重排：看 rerank_top_k 和候选选择。
  • 正确证据重排后仍落选：看排序、最终条数、阈值、去重和预算。

只调 final_top_k，救不回一个从未进入候选池的片段。

3. 项目里的重排分数可以为负数

当前适配器返回原始 logits，没有把它统一转成 0～1 的概率。

因此：

rerank_score = -1.2

不能解释为“负 120% 的可信度”；rerank_score = 3.4 也不能解释为“340% 可信”。

最低相关性分数 knowledge_min_rerank_score 默认关闭。若要启用，需要用你的材料和问题标定，不能把某个通用数字直接当真理。Reranker 输出 · 配置

4. 重排不能创造不存在的证据

如果检索只找到了“一般规则”，完全没找到“定制商品例外”，重排最多重新排列已有候选。

它不能凭空把缺失的例外规则加进来。

另外，当前基础 Embedding、Sparse、Qdrant 或 Reranker 出错时，会进入 KNOWLEDGE_INDEX_UNAVAILABLE 等错误路径；基础重排失败没有默认静默跳过重排的保证。检索异常处理

“服务出错”和“正常检索但没有足够证据”，需要分别处理。

八、组织证据：这是最容易被忽略的一层

检索函数成功返回，并不表示这些内容全部进入了模型输入。

中间还要做：

  1. 去除确实重复的内容。
  2. 保留来源和正文的对应关系。
  3. 在预算内选择能完整交付的记录。
  4. 与系统提示词、历史消息、用户问题一起通过最终上下文检查。

1. 一条证据不只有一段文字

概念上，一条证据需要类似这样的信息：

{
  "document_revision_id": "修订身份",
  "chunk_id": "片段身份",
  "locator": {"type": "page", "page": 3},
  "text": "定制商品不适用上述七天规则。",
  "document_name": "退款规则",
  "effective_date": "2026-01-01",
  "superseded": false
}

这是为讲解而合并的示意结构，不是某个 API 的完整响应。实际 RetrievedEvidence、工具 results 和引用对象的字段略有不同。检索合同 · 证据记录投影

它们共同回答两组问题：

  • 模型需要读到什么内容？
  • 这段内容来自哪个确定版本、哪个位置？

有效日期、是否已被替代也有意义。用户问“当时政策”还是“现行政策”，需要的材料可能不同。

2. 去重不能把有独有内容的相邻片段删掉

看这两个窗口：

A: [0, 1200)
B: [1000, 2200)

它们重叠 200 个字符，但 B 还有 1000 个 A 没有的字符。

所以不能说：“只要有重叠，就删掉 B。”

当前去重逻辑主要判断：在同一修订、可比较的定位范围内，后来的片段是否被已经保留的片段完整包含。

部分重叠会保留，没有可比较坐标时也不会盲目删除。56

这就是实现细节怎样影响回答质量：如果把“重叠”误写成“冗余”，可能正好删掉例外条件。

3. 预算为什么会让证据消失？

假设重排得到三条记录：

证据 作用 示例预算成本
A 一般规则 1200
B 定制商品例外 1200
C 一段较短的补充说明 300

这些成本是教学假设，使用同一计量单位，并假设已经计入对应记录的序列化开销。

如果当前预算只有 1600，顺序选择可能得到 A 和 C，B 放不下。

于是：

  • 检索确实找到了 B。
  • 重排结果里也有 B。
  • 但回答模型没有读到 B。

如果它因此把一般规则套到了定制商品，这首先是一个证据交付不完整的问题。

4. 当前项目按完整记录选择，不把 JSON 截到一半

在当前 RAG 专用投影中：

  • 一条记录与它的来源引用成对保留。
  • 放不下就跳过这一整条。
  • 继续尝试后面更小的记录。
  • 身份与引用无法可靠配对时，投影失败。

因此，不能把旧式 json_text[:5000] 当成这个提交的默认 RAG 交付方式。58

这解决了“半条正文、断掉的 JSON、错位引用”的结构问题，但还有一个质量问题：

完整地交付了几条记录，也可能没有交付完整的回答依据。

例如 A、C 都完整，最关键的 B 仍然缺失。

5. 字符、字节、token 要分清

位置 实际计量
默认 Chunk 的 1200 / 200 字符数
Retriever 的 context_budget_bytes 选择 紧凑 JSON 的 UTF-8 字节数
Runtime 的 max_retrieval_tokens 近似 token 估算
Citation QA 的 max_evidence_chars 名称有历史包袱，当前选择函数实际使用近似 token 估算
回答模型的总窗口 还要容纳系统消息、历史、问题、工具结构和输出预留

Runtime 的 ContextBudgetConfig 默认检索池为 5000 个估算单位，但具体运行可以采用发布配置；它不是每个模型真实 tokenizer 的精确计数。

还有一个阅读源码时的细节：运行时仍会接收名为 context_budget_bytes 的旧配置，并结合 token 池收紧预算，但执行投影时使用的是 ApproxTokenEstimator。字段名不能代替对实际计数函数的检查。预算实现 · Observation 处理 · QA 证据选择

6. 模型真正看到的是最终请求

Agent 工具路径里至少要区分：

检索服务返回的 evidence
    → 工具返回的 results / evidence_refs
    → observation 投影后的工具消息
    → 最终 admission.messages
    → 真正发送的 ModelRequest

最后一次上下文准入可能继续移除证据或较旧的消息组。

所以排错时最重要的问题是：

“这次生成答案时，模型实际收到的消息里，是否真的包含那句关键条件？”

仅看检索界面或工具完成记录，回答不了这个问题。运行图 · 最终上下文预算

九、带引用的回答：编号从哪里来，代码检查什么？

AgentHub 有一个独立的 Citation QA 入口：

POST /api/v1/knowledge/query

它接收工作区、知识库、知识快照、模型配置和问题，调用 CitationQaService.answer()，返回回答、引用和检索过程。接口路由 · 请求响应模型

1. 先给实际选中的证据编号

假设本次确实交付了两条证据：

[1]
来源：退款规则
正文：普通商品签收后七天内可以申请退货；
      定制商品不适用上述七天规则。

[2]
来源：退款时效说明
正文：退款审核通过后，三个工作日内原路退回。

模型可以写：

定制商品不适用这项七天退货规则。[1] 如果退款申请已经审核通过，按所提供的时效说明，款项将在三个工作日内原路退回。[2]

这里尤其要留意第二句的“如果已经审核通过”。不能因为有一段到账时效，就替用户推断退款一定能获批。

2. 系统要求模型输出一个合同明确的对象

在生成之前，系统提示还明确要求：只依据提供的证据回答；证据不足时承认不足；把文档内容视为参考资料。如果资料里出现“忽略之前的要求”之类文字，它仍然属于文档内容，不能升级为系统指令。

该入口要求类似：

{
  "answer": "定制商品不适用这项七天规则。[1]",
  "citation_ids": [1],
  "insufficient_evidence": false
}

程序可以检查：

  • 能否严格解析为 JSON。
  • 字段与类型是否正确。
  • 正文中的 [n] 是否属于本次可见证据。
  • citation_ids 是否与正文中的引用编号一致。
  • 声明证据不足时，是否仍错误地附带引用。

这些检查把输出格式和引用对应关系变成了可执行的约束。输出 schema 与验证函数

3. 最终来源由服务器解析

模型输出 [1]，服务器用本次已经选择的证据表去构造引用信息：

1
→ document_id
→ document_revision_id
→ chunk_id
→ source / locator / excerpt

因此，引用的真实身份不需要由模型自由编一个 URL 或数据库 ID。

没有选中任何证据时，该服务会直接返回证据不足，不再进入答案生成调用。部分引用错误可以触发有界纠正，但不是所有格式和语义错误都会自动修复。69

4. “编号合法”和“这句话被支持”还隔着一层

假设材料写：

定制商品不适用上述七天规则。

模型却回答：

定制商品也适用七天规则。[1]

编号可以完全合法，来源也真实，但意思反了。

因此至少要分清三个检查层次：

层次 要回答的问题
来源身份 这条引用对应真实且可追溯的证据吗？
格式一致 正文引用和引用列表是否对应？
语义支持 这段证据是否支持这句话，包括前提、例外、否定与时间？

当前 Citation QA 的格式验证不能被描述成“自动证明所有事实正确”。它的系统提示明确要求依据证据回答，但提示要求与语义证明是不同层面的东西。提示词与验证代码

十、再注册成 Agent 工具：复用检索能力，让 Agent 决定何时使用

你已经了解工具循环，这里重点看模块怎样接线。

1. 先区分两个实际入口

入口 谁安排检索 谁生成最终回答 当前关键边界
独立 Citation QA 固定应用流程 CitationQaService 调用回答模型 检查结构化输出与引用编号合同
Agent 的 search_knowledge Agent 提出工具调用，服务端执行 Agent 下一轮模型调用 工具交付证据；通用 Agent 没有自动调用同一套 Citation QA 输出校验

search_knowledge 的 handler 本身不会先生成一份完整回答，再把回答当作工具结果交回去。它返回证据，让 Agent 继续自己的任务。检索工具 · 通用模型节点

2. 注册表负责“工具身份对应哪个函数”

实际注册代码的核心是：

"search_knowledge": partial(
    search_knowledge,
    retriever=retriever,
    section_selector=section_selector,
)

你可以把 partial 理解为“先把固定依赖填好”。

运行时再把本次调用的上下文和参数交给这个 handler。这样检索器可以被替换或测试，工具 handler 不必在每次调用时自行创建所有组件。74

3. 模型可以提供 query，但不能自由决定租户范围

动态参数的典型形态是：

{
  "query": "定制商品适用七天退货规则吗？",
  "limit": 6
}

而下面这些内容来自服务端：

信息 来源
当前 Workspace 和执行身份 已验证的运行上下文
允许使用哪个工具 Agent 发布版本与工具定义
工具输入 schema 已冻结的 ToolRevision
可以查哪些 Snapshot 已发布或本次运行冻结的知识绑定
检索策略与预算 版本中的检索配置

当前工具要求 PINNED 知识绑定，核对 snapshot ID/hash，并检查工作区归属。

实际 JSON Schema 来自冻结的工具定义；注册表负责函数接线，两者不是同一个东西。工具解析与执行 · 快照绑定检查

4. limit 默认 10，为什么前面又说 final_top_k 默认 6？

因为它们属于不同层次：

  • 工具动态参数 limit 默认 10，最大 10。
  • 常见发布检索配置的 final_top_k 默认 6。
  • 实际结果还受版本配置、快照组合、去重、证据预算影响。

所以 limit=10 是一个调用上限，不保证某次模型最终一定看见 10 条证据。79 · 发布配置

5. 工具返回后才进入 Agent 的下一轮回答

如果显式启用 compact_v1，系统还会给模型提供短证据 ID，并在内部注册表保留完整的来源映射；最终不可见的证据不会继续冒充可见证据。证据注册表

但这里仍要记住：

通用 Agent 在这个基线中，没有自动把最终文本送进独立 Citation QA 的编号验证函数。

如果你以后要把“所有 Agent 回答都必须符合严格引用合同”作为产品要求，需要在 Agent 的回答出口接上相应解析、验证和失败处理。这是明确的增强方向，不能说项目仅仅注册一个检索工具就已经自动完成了它。

十一、怎样判断错误发生在检索、证据交付还是回答阶段？

我们继续使用前面的虚构材料。

问题是：

“定制商品签收第五天，能按七天规则申请退货吗？”

正确回答必须读到“定制商品不适用”这条限定。

1. 按关键条件第一次丢失的位置排查

这是排查顺序，不是说每个失败案例只能有一个原因。一条链路可能同时存在多个问题；先找到最早能确认的缺口，通常更容易修。

2. 六种具体情况

看到的现象 优先定位
扫描 PDF 没有提取出文字 解析与入库
新政策 READY，但当前 Snapshot 没包含它 版本范围与绑定
快照里有例外规则，Dense / Sparse 候选没有它 召回
候选有例外规则，最终检索结果没有它 重排或证据选择
工具返回有例外规则，最终 ModelRequest 没有它 证据交付
ModelRequest 有完整例外规则，回答仍说“可以” 回答理解、推理或语义支持

这张表把错误现象对应到具体模块，帮助你确定下一次修改应当落在哪里。

3. 项目已经提供哪些观察点？

RetrievalTrace 包含各检索阶段的 Chunk ID、排名、分数和耗时，不包含完整正文。

你可以观察：

  • dense：语义召回找到了谁。
  • sparse：词法召回找到了谁。
  • fusion：融合后保留了谁。
  • selection：实际交给重排的候选。
  • rerank：排序结果。
  • 最终 evidence：经过后续过滤和选择的证据。

API 投影把内部的 fusion 命名为 fused。默认未启用字节预算时，rerank trace 不一定包含整个重排池，因此不能把它当完整输入名单；输入名单要看 selection。检索 trace · API 路由

4. 前端看见来源，不等于模型最终看见来源

工具完成事件在 Observation 投影之前产生。前端工具面板展示来源引用，可以证明工具返回过这些来源；它本身不能证明最终上下文保留了全部来源。运行事件顺序 · 前端证据面板

同样，Playground 的 snippet 只预览前 1000 字符。不能因为预览没展示后半段，就断言 Agent 也没有收到后半段。Playground 响应构造

展示预览、工具返回、实际模型输入，是三个不同对象。

5. 三种“看起来没证据”的状态也不同

状态 可能表达的事实
检索结果本来就是空的 当前范围没有返回候选或可用结果
投影后 results=[]，并且 truncated=true 检索可能有结果，但没有记录能进入预算
evidence_projection="FAILED" 工具成功，但投影未能形成合法证据消息；可能是结构或身份配对异常，也可能预算过小

最后一种不能简单翻译成“知识库没有答案”。RAG 投影 · Observation 失败标记

十二、为什么只看 Recall 或“有引用”还不够？

假设问题要同时知道：

  • A：退货时间窗口。
  • B：定制商品例外。

如果只找到 A，回答仍然可能错误。

1. 检索指标回答“找到了多少”

例如，对某个问题标注两条必要证据 A、B：

找到 A、B：必要证据召回率 = 2 / 2
只找到 A：必要证据召回率 = 1 / 2

但实际任务可能要求 A、B 同时存在才可回答。此时还需要看：

完整的必要证据集合是否被找齐。

2. 交付指标回答“模型读到了多少”

同样两条材料：

检索结果：A、B
实际模型输入：A

检索阶段的必要证据召回可以是 2/2，交付阶段仍然不完整。

所以评测要把候选、最终检索结果、实际可见证据分开记录。

3. 回答指标回答“是否正确使用了这些材料”

即使 A、B 都进入了模型输入，还要检查：

  • 有没有遗漏例外。
  • 有没有把否定说成肯定。
  • 有没有把旧政策当现行政策。
  • 有没有把“审核后到账”说成“必然获批”。
  • 引用是否支持紧邻的具体结论。
  • 没有资料时是否承认未知。

仓库的评测代码已经区分候选召回、最终召回、引用存在、引用相关和语义正确等维度。其中语义正确性来自该次评测的抽样审阅，未审阅样本保持未知，不能理解为系统已自动证明全部答案都受到证据支持。RAG 评测审计

因此，一份有说服力的 RAG 评测应能解释：

“这道题失败，是正确材料没找齐、没交付齐，还是已经交付齐但没有用对？”

十三、如果让你从零写，按什么顺序最容易完成？

先把模块的输入、输出固定下来，再增加算法和运行时治理。

下面的步骤是本课的实现练习顺序，不表示要立即修改你的现有仓库。

第一步：做出能检查的文档解析和分块

输入：一份小 Markdown。

输出：若干 Chunk，每条至少有：

{
    "chunk_id": "...",
    "document_revision_id": "...",
    "text": "...",
    "locator": {...},
}

第一轮就人工检查“规则与例外”是否分布合理。这个阶段发现的信息丢失，后面会一路传递。

第二步：先实现 Dense 检索，检查真实命中

输入：问题 + 固定范围。

输出：Chunk 身份、分数，以及回读的正文。

此时先不让模型回答。你要能看见：

“这个问题为什么取回了这几段？”

第三步：增加 Sparse、RRF 和 Reranker

保持同一批问题和同一个 Snapshot，对比：

  • 只用 Dense。
  • Dense + Sparse + RRF。
  • 再加 Reranker。

记录正确证据在哪个阶段进入、在哪个阶段落选。先解释差异，再决定是否调整参数。

第四步：做出证据交付和带引用问答

把实际选中的证据编号，明确预算，生成结构化回答，并检查引用编号。

这里有一条必须坚持的数据关系：

模型允许引用的 ID 集合
    = 本次实际提供给它的证据 ID 集合

不能把“索引里存在的所有 ID”或“工具曾经返回的所有 ID”当成本次允许引用的集合。

第五步：把检索服务接成 Agent 工具

把稳定的 retrieve() 能力注册给工具运行时。

动态参数只处理问题和必要的结果上限，知识范围和执行身份从服务端提供；工具返回证据，Agent 下一轮负责回答。

用一段伪代码串起整个设计

下面是模块关系伪代码，不是可以直接复制运行的 AgentHub 函数：

async def answer_question(context, query, snapshot_id):
    # 1. 先确定本次可使用的资料范围
    scope = await load_authorized_snapshot(context, snapshot_id)

    # 2. 大范围寻找候选
    dense_hits = await search_dense(query, scope)
    sparse_hits = await search_sparse(query, scope)
    candidate_ids = fuse_by_rank(dense_hits, sparse_hits)

    # 3. 拿真实正文，并再次校验业务归属
    chunks = await load_scoped_chunks(context, scope, candidate_ids)

    # 4. 对已有候选做精细排序
    ranked = await rerank(query, chunks)

    # 5. 组织完整记录；记录哪些证据最终被交付
    evidence = select_complete_records(ranked, evidence_budget)
    visible_evidence = admit_with_other_messages(query, evidence)

    if not visible_evidence:
        return insufficient_evidence_result()

    # 6. 生成并校验本入口要求的回答合同
    response = await generate_answer(query, visible_evidence)
    return validate_and_resolve_citations(response, visible_evidence)

实际项目把这些职责拆到多个模块，是为了让解析、存储、检索、预算、模型和工具治理各自有明确的边界。

十五、面试时，可以怎样把这条链路讲完整？

如果面试官问：“你的 RAG 是怎么实现的？”

你可以按下面这个顺序回答：

我把 RAG 分成文档入库和在线查询两条链路。入库时，后台 Worker 解析文件并切块，PostgreSQL 保存版本、片段正文和定位信息，Embedding 与词法稀疏表示写入 Qdrant，索引完成后确认修订可用。

在线查询先根据工作区和知识快照确定允许使用的文档修订，再做 Dense 与 Sparse 召回，用 RRF 融合候选。候选还要回 PostgreSQL 读取正文并再次校验范围，然后做 Cross-encoder 重排、去重与证据选择。

检索结果进入模型之前，还要经过证据预算和最终上下文准入。我们把正文和来源身份成对保留，所以排错时会分别检查检索到了什么、模型实际看到了什么、最后回答使用了什么。

独立带引用问答入口会校验结构化输出、引用编号和可见证据的对应关系；检索能力也可以注册成 Agent 工具，由 Agent 下一轮生成回答。通用 Agent 的出口如果要求同样严格的引用合同，需要明确接入校验。

我不会用“存在引用”直接证明答案正确，还会检查引用是否支持具体结论，以及有没有遗漏时间、条件或例外。

这段回答的重点是：你能解释每一步的职责、数据如何传递，以及出错后怎样定位。

本讲练习

用一份只有三条规则的小文档，完成下面三个观察：

  1. 找齐证据。 问一个必须同时利用“一般规则”和“例外规则”的问题，指出相关内容各在哪个 Chunk。
  2. 观察预算。 在练习环境收紧证据预算，比较检索结果与最终模型输入，检查关键条件是否还在。
  3. 检查引用支持。 构造一句“编号正确，但意思说反”的回答，解释为什么引用编号验证不能单独发现所有语义错误。

你真正掌握这一节的标志是：

拿到一个错误回答，能够指出“关键依据在哪一层第一次缺失或被误用”，并找到对应的源码入口。
