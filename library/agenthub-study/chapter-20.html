第 16 讲：从 AI 聊天到真实产品——Artifact、工单、人工接管和反馈的业务闭环

这是原八阶段主线真正讲得较少的一块。第 10 讲已经掌握 SSE 和 Turn 的基本恢复，本讲把一次用户输入连接到可以长期编辑、追责和验收的业务对象。源码从 apps/web/components、packages/artifacts、packages/support、packages/handoff、packages/feedback 向下阅读。

16.1 用户究竟是要“一个回答”，还是要“一件事情被办好”？

假设客服用户说：“请记录我的投诉，安排专人跟进，并保留刚才讨论的证据。”

模型只回复“我已经记录”，页面就算显示流畅，也不足以支撑后续客服工作。一个成熟应用至少要留下：

  • 对话：用户说了什么，Agent 如何回复。
  • 执行：用了哪个 AgentVersion，实际调用过哪些工具。
  • 业务：是否有 Customer / Ticket，以及当前状态。
  • 产物：对话生成了哪份可复用、可供人工查看的整理记录。
  • 接管：如果需要人工，谁接到任务，怎样处理，何时结案。
  • 反馈：用户认为回复是否准确，错误是否进入受控改进流程。

为什么要把这些拆开？因为它们有不同的生命周期。Run 成功结束、Ticket 仍在 IN_PROGRESS、HandoffCase 仍在 OPEN，可以同时成立。用一个总 status 字段把所有对象混在一起，操作员将无法表达复杂的业务事实。

16.2 同一个工作台，为什么要有不同业务面板？

研究、运维、分析、客服都需要相同的对话基础：选 Thread、输入、提交 Turn、跟随 Run、刷新恢复、显示历史。AgentHub 使用共享 AppWorkbench 承担这部分职责，各业务页注入自己的侧栏、文案和产物视图。这样可以把“用户切换工作区时旧请求覆盖新请求”的处理统一在共用组件，而不在每个页面复制一份。

但业务面板仍要向各自的服务查询：客服面板读 Customer/Ticket，运维面板读事件与操作证据，研究页读 Artifact。统一的是交互骨架，不是业务对象本身。

一次提交的身份链

Thread T1           持续的会话容器
  └─ Turn Tn         用户这一次逻辑提交
      └─ Run Rn      与某个 AgentVersion 绑定的执行
          ├─ ToolCalls / Approval
          ├─ RunSteps / 最终输出
          └─ Artifact A1 / 业务写入结果

这条链还带来实际的页面恢复方案：最初 POST 流断开后，前端保留原 client_token 和输入身份来恢复 Turn；刷新后读取持久 Turn 与 Run 事实。模型连续输出中的临时 delta 可以消失，但已提交的业务对象必须能回读。

16.3 Artifact：为什么“运行时生成的文档”和“可编辑副本”要区分？

假设模型在昨天生成了事故时间线：

09:00 报警
09:05 开始人工确认
09:12 执行回滚
09:15 恢复

今天操作员发现 09:12 实际应该是 09:13。如果直接把昨天那份与 Run 绑定的 Artifact改成新内容，那么以后打开昨天的 Run，系统展示的将不再是当时生成的结果。

AgentHub 的 ArtifactService.update() 对 Run 产物与普通可编辑副本采用不同处理：

# 教学概括：表达业务规则，不替代真实源码
if artifact.run_id is not None:
    raise ArtifactError("运行产物不可直接改写")

# 用户修改应保存没有 Run 源头绑定的可编辑副本
editable = Artifact(
    workspace_id=workspace_id,
    thread_id=thread_id,
    run_id=None,
    type="incident_summary",
    content=edited_content,
)

相应模型还保留：workspace_id、thread_id、可选 run_id、type、title、JSONB content、创建者和创建时间。这里的 JSONB 适合不同类型产物的正文，但归属、来源与唯一约束继续使用明确列。参见 15。

如果 Artifact 进一步被 HandoffCase 引用为源证据，修改和删除还会受到额外的保护。这个设计像 Git 中“提交记录”和“工作区修改”：历史记录保留当时的内容，后续修订是新对象。

16.4 工单：前端文字不是业务状态

真实客服操作可以调用同一套 Customer/Ticket 业务服务。工单变更不是把 JSON 中的 status 改一下就结束，还必须考虑并发。

例如两名操作员同时打开 Ticket T1，初始状态 OPEN、版本 version=3：

expected_version 解决用户基于过期页面状态做出的修改；数据库行锁确保状态转移和版本检查不会在事务里互相踩踏。这两个机制解决不同问题。

客户注册同样需要业务幂等：在同一 Workspace 中，某个 customer_ref 的重复提交，如果姓名、邮箱一致，可复用已有 Customer；如果同一个 ref 却提交互相矛盾的信息，应返回冲突而不是静默覆盖。关键在数据库唯一约束加冲突后事实核对。参见 21。

16.5 Handoff：人工接管不只是“在回复里写请联系人工”

接管对象 HandoffCase 记录了从哪份 Artifact 建立、由谁负责、处于哪个阶段、处理意见和未解决事项。其源 Artifact 应保留作为交接时的事实副本。你可以把接管理解为一个小型工单系统，但它的核心任务是连接 AI 输出与人工流程。

设计 HandoffCase 而不是在 Artifact 上加 handoff_status，原因是：Artifact 是来源，Handoff 是会被领取、分派、处理和结案的事务性工作。源材料不可变与处理状态可变，两者需要分离。

注意接管里的 CLOSED 是“这次人工处理已结束”的事实。原外部工具若有 UNKNOWN_OUTCOME，仍需核对远端业务事实；接管关闭不能直接冲销原动作证据。

16.6 Feedback：把生产错误送回评测，而不是直接当作 Memory

用户对某条 Run 点击“回答错误”，留下说明。之后流程应该是：

RunFeedback（用户提交）
  -> 人工审阅与纠正答案
  -> APPROVED 的审核版本
  -> 生成新的 DEV 数据集版本
  -> 下一轮对照评测
  -> 经验证的产品迭代

当前 FeedbackService 的导入要求审核通过、审核版本一致、有可用的纠正答案，以及符合 DEV-only 的目标数据。为什么 DEV？因为这条反馈已经被开发人员看过并据此改系统，它适合充当回归题。要评价新方案的独立泛化效果，仍应另行保留未曝光的验收数据。

一条反馈和一条长期 Memory 的触发条件不同：反馈主要是关于系统质量的观察，Memory 主要是用户希望在后续任务中复用的持续事实或偏好。把所有反馈都写入 Memory，会混淆目标；把所有反馈都当成训练数据，则会引入错误金标。参见 25。

16.7 一次完整故障排查：“Agent 说已创建工单，但页面找不到”

按下面顺序检查，直到定位第一个事实缺口：

层 核查对象 定位问题
提交 Turn、client_token 请求是否创建或复用了正确回合？
执行 Run、RunStep 是否执行了预期 ToolCall？
授权 Approval、ToolRevision 写操作被批准的是哪份参数？
结果 ToolResult / Action 记录 工具明确成功、失败还是未知？
业务 Ticket 查询 W1 内是否真的有目标工单？
前端 当前工作区、查询状态 页面是否读错范围、响应未刷新或权限被拒？

不要先改页面上的绿色提示。先找到真正拥有业务事实的服务，然后再决定页面应该展示“已受理”“待审批”“执行中”“已创建”还是“需要核对”。

本讲练习

选一个客服场景，自己画出 UI → Turn → Run → 工具 → Ticket/Artifact → Handoff/Feedback 全链路，标出每一层的数据库主键、权限与并发保护。然后构造“重复提交”“响应丢失”“两个操作员同时改状态”三个受控测试。

本讲掌握标准：可以把“聊天完成”变成可持久化的业务闭环，并知道一条最终产品事实到底由哪个对象负责。

16.8 业务对象之间如何设计外键与读取范围？

一个 Run 产物很可能被人工接管、客服记录引用，最怕两个工作区的对象错误地绑定到一起。设计关联时至少考虑：

Artifact.workspace_id = Thread.workspace_id = Run.workspace_id
HandoffCase.workspace_id = source Artifact.workspace_id
Ticket.workspace_id = Customer.workspace_id
Feedback.workspace_id = Run.workspace_id

若数据库只检查每个 UUID“存在”，还要思考如何保证它们属于同一个 Workspace。第 6 讲已经讲过复合外键，本处可以直接使用那套思路，不需要重复理论。让数据库守住基础归属，再由 Service 检查业务状态：哪些产物允许被引用、哪个 HandoffCase 可以关闭、哪个客服成员有权限读取记录。

业务操作与页面刷新之间的时间差

用户点击“保存人工接管意见”，可能出现：

T0  前端提交 PATCH HandoffCase
T1  后端锁定对象、验证 expected_version
T2  后端成功 COMMIT
T3  响应途中断开
T4  前端显示网络错误

不要立即再次生成一个新 HandoffCase，也不要认为提交一定失败。前端可以先按原 ID 读取当前 Case 与版本，再根据后端是否已保存相同处理意见，选择继续、重试或提示冲突。这里 expected_version、请求 Hash 和稳定业务对象身份共同处理“结果丢失”的问题。

16.9 权限对前端展示有实际影响

假设 Viewer 能看到某个 Thread 的摘要信息，但没有 agent_run 权限。后端可以返回允许展示的 Thread、Turn 身份与状态，把 user_input、final_output 等敏感正文投影为空。页面应该把它显示为“内容受限”，而不是误判成模型没有回答。

这说明三层状态要清楚：

  • 数据不存在：没有记录。
  • 数据尚未读取：网络请求还没完成。
  • 数据被权限限制：服务端按角色过滤正文。

只在前端隐藏文字并不能提供数据隔离；敏感字段要在 API 投影阶段就按授权范围收敛。同时，前端统一的请求 Hook 要跟踪会话代次，避免用户 A 切换到用户 B 后，迟到的响应重写页面。

16.10 如何做一次真的业务闭环验收？

设定四个稳定断言：

场景：U1 请求创建一张投诉工单并交接给人工

1. Turn 数量：本次 client_token 对应恰好一条有效提交
2. Run 归属：使用已经发布的客服 AgentVersion，workspace=W1
3. 工单事实：Customer C1 下恰好有目标 Ticket T1，状态合法
4. 接管事实：HandoffCase H1 引用源 Artifact A1，后续可被有权人员领取

随后分别做：原提交重试、两个操作员修改、被撤权的处理员操作、删除原 Artifact、刷新页面重查。完整的业务验收要有数据库行和 API 回读结果，不能只截一张最后的聊天截图。

本节可以直接写进简历的能力点：围绕客服工作流设计了从 Agent 执行到工单/接管/反馈的持久化业务链路，并实现事务、版本校验和可重试读回。只有你实际参与实现和测试对应功能时，才按这个句式描述自己的工作；源码阅读阶段则可将它作为练习目标。
