第 16 讲：异步可靠性的进阶——状态机、租约与幂等

16.1 一项后台任务有三个时刻，不能混成“已经成功”

先看一个最普通的上传文档场景：

  1. API 接受了请求，数据库创建了任务。
  2. Worker 领取了任务，开始执行。
  3. 所有需要的产物已经写入并达到可查询状态。

这三个时刻分别意味着“已受理”“在处理”“业务完成”。Celery 收到消息只说明某个传输步骤发生了；Worker 进程还活着也只说明基础设施活着。你真正需要知道的是：哪一项任务，由谁处理，走到了哪一步，结果是否可重现，失败后谁负责收敛。

当前 AgentHub 的入库任务、AgentRun、审批与实验执行都用持久状态承载这类信息，但它们的恢复合同不同。不能把某一种任务的重试策略直接复制到所有任务上。源码：入库状态处理、AgentRun 执行租约、审批恢复

文档切块失败后重新切块，通常可以从同一个不可变 revision 推导相同的结果；一个“转账或创建外部对象”的调用断线后，重发可能产生第二个业务对象。两者都叫 retry，允许的条件却不同。

16.2 Worker 消息为什么只携带 ID？

AgentHub 的 Run 队列消息携带 workspace_id、run_id、request_id。Worker 回读 Run、原始运行人和当前工作区访问权限，再构造执行 context。它没有把客户端或旧 API 请求里的一整份权限集合当成永久授权。源码：队列合同、Run Worker

假设消息排队时用户是工作区编辑，十分钟后被移除了。若 Worker 直接使用十分钟前序列化进去的权限，就会在账号已经撤权后继续做事。当前 Worker 会通过 TenantService 获取当前访问，无法满足 agent_run 时把运行标成需要关注并记录 RUN_ACTOR_ACCESS_REVOKED。

这里有两个容易混淆的身份：

  • 任务身份：告诉 Worker 应该读哪一个 Run。
  • 授权身份：告诉 Worker 现在能以哪个用户的权限执行。

消息携带前者；后者必须由服务端可信数据重新得到。request_id 适合关联日志，也不能自动代替一个稳定的业务幂等键。

练习： 给队列消息随意增加 permissions=["admin"]，为什么 Worker 不应该因此得到更多权限？请沿 _authorized_run_context 的调用链回答，不要只说“后端要校验”。

16.3 租约解决什么问题？为什么一把布尔锁不够？

假设任务有个字段 processing=true。Worker A 把它改成 true 后突然断电，谁来把它改回 false？如果后台每十分钟粗暴清理，A 恰好只是处理得慢，Worker B 就可能与 A 同时执行。

租约比布尔值多了“有期限的当前拥有权”：

  • owner/token：这一轮执行的身份。
  • expires_at：当前资格何时过期。
  • renewal：仍活着且有资格的拥有者定期续租。
  • guarded write：写结果时同时验证自己仍是当前拥有者。

AgentRun 的 run_execution_lease 当前以 180 秒租期、30 秒续租间隔管理执行拥有者。这些是当前源码常量，不是所有系统都该照搬的推荐值。读取并领取时锁住 Run，续租更新时要求 owner token 相同且租约还有效；清理时也按 token 条件更新，避免旧 Worker 清掉新状态。源码：执行租约

为什么必须带 token？因为任务 ID 只标识“要做哪件事”，不标识“现在是谁被授权做它”。同一个任务在不同时间可能被不同 Worker 接管。token 把“旧人回来提交结果”与“当前人正常提交结果”区分开了。

需要再细分一个概念：数据库条件写可以拒绝旧拥有者的结果；若远端服务不认识这个 token，它不能替你阻止已经发送的外部副作用。这是后面谈 fencing 边界的基础。

16.4 为什么 AgentRun 失租后不会统一自动重跑？

在 Run 租约源码里，如果发现已有 owner 但租约过期，并不会简单清空它再从头跑图，而会把 Run 转为 NEEDS_ATTENTION，记录 RUN_EXECUTION_LEASE_EXPIRED。续租失败也会尝试写入失租故障，取消当前运行协程。源码：Run 租约

原因很具体：Run 可能已经执行了一部分工具调用。图的某个 checkpoint 只告诉你本地看到哪一步，不必然证明外部系统没有做过下一步。

你可以这样解释几个状态：

状态 应该如何理解
RUNNING 运行还在执行阶段；还需查看 owner/lease 判断是否存在活跃拥有者
WAITING_APPROVAL 当前有一个持久化审批中断，等待明确决定
CANCEL_REQUESTED 系统接到了取消意图，执行者还需要安全收敛
CANCELLED 运行已按取消路径收敛，不代表历史外部动作已自动回滚
NEEDS_ATTENTION 有不能安全自动推断的中断、缺失证据或动作结果不确定
SUCCEEDED / FAILED 按运行合同得到成功或失败终态；业务效果还要看具体输出与动作证据

这里的 NEEDS_ATTENTION 不是“异常都扔给人”的偷懒状态。它的价值在于精确承认：系统知道自己缺了哪一种证据，因此不做可能重复外部操作的猜测。要减少这个状态，需要建设相应工具的查询、对账和幂等合同，而不只是写 except: retry。源码：协调器状态收敛

16.5 最新修复之一：执行次数上限必须在领取处原子消耗

旧式写法常见如下逻辑，以下仅为反例：

job = await load_job(job_id)
if job.attempt_count < max_attempts:
    job.attempt_count += 1
    await save(job)
    await execute(job)

两个 Worker 可以同时读到 attempt_count=2，而上限为 3，然后都觉得还有一次额度。即使最后数字只增加一次，外部工作已经被执行了两次。问题不在“检查有没有写”，而在检查与占用是否不可分割。

当前入库 claim 将任务可领取条件与 attempt_count < knowledge_ingestion_max_attempts 放进同一条 UPDATE，成功领取才同时把状态改为 PROCESSING、写入新 lease token、增加 attempt_count，并返回这次领取结果。没有领取到的调用者不能继续执行。源码：11

若任务已经达到上限，系统也只对仍可领取的记录做耗尽处理。一个正在进行最后一次合法尝试的活跃 owner，不应被旁边来的重投消息强制标为 FAILED。这个细节说明“最大尝试次数”不仅是一个数字，还涉及并发任务之间谁有权改变状态。

伪 SQL 可以帮助理解，实际实现以源码为准：

UPDATE ingestion_jobs
SET status = 'PROCESSING',
    attempt_count = attempt_count + 1,
    lease_token = :new_token
WHERE id = :job_id
  AND /* 当前满足待处理或过期可接管条件 */
      :claimable_condition
  AND attempt_count < :max_attempts
RETURNING *;

这个示意故意没有拼成可直接运行的完整 SQL，因为可领取条件还包括 next_attempt_at、现有租期等业务约束。学习时应该把“比较与更新同一次提交”的思想带走，再去源码读完整 predicate。

16.6 最新修复之二：心跳失败之后，必须真的停止后续工作

仅有一个后台协程定期续租，不代表业务协程知道自己已经失租。

典型故障是：

  • 续租协程发现 token 不匹配，悄悄退出。
  • 编码协程还在继续给每一批 chunk 调 embedding。
  • 最后提交数据库时才发现自己无权完成。
  • 状态没有被写错，但额外费用和外部写入已经发生。

最新入库 Worker 引入 _ClaimGuard。它在解析前后、切块持久化之前、dense/sparse 编码边界、索引 collection/upsert 前，以及结束前检查任务仍是 PROCESSING、token 一致、lease 未过期；续租无法确认时设置失租事件。向量缓存的调用路径也接收 owner check。源码：入库 Worker

你会注意到图中最后一条分支仍然存在：一个远端 upsert 一旦被对方接受，即使本地之后失租，它仍可能完成。Python 取消协程也不能保证立即杀掉 asyncio.to_thread 中已经开始的同步调用。

所以这个修复的准确收益是：更早发现失租，阻止后续批次继续派发，并防止旧拥有者非法写入最终状态。 它没有把外部系统变成 PostgreSQL 事务的一部分。

16.7 稳定 revision、确定 point ID 与幂等是如何配合的？

入库可以比通用 AgentRun 更积极地重放，是因为它操作的是同一不可变 revision 的派生产物。稳定的 chunk/revision 身份与确定的索引 point ID，让重复 upsert 更接近“把同一份结果写回同一个位置”，而不是每次制造一个新对象。源码：索引写入批次

不过要分清三个层级：

  1. 传输去重：队列是否重复交付消息。
  2. 执行去重：只有一个当前拥有者进入执行。
  3. 业务幂等：同一逻辑操作重做后，最终业务状态仍符合合同。

有第二层，不等于已经完成第三层。Worker A 在外部写入后、数据库完成前断电，新的恢复过程仍可能面对“外面已成功，本地没记录”的窗口。业务幂等是处理这个窗口的关键。

例如本地工单工具通过 workspace 和 idempotency_key 查询既有工单并依赖唯一性保障并发；这是“创建同一个逻辑工单”层面的去重。若外部 MCP 服务完全忽略你传入的 key，仅在 AgentHub 里存一串 key，不会使它自动变得幂等。源码：本地 Action 执行

16.8 为什么有 Celery 仍然可能出现“Run 已创建但没有启动”？

看当前 stream 路由的顺序：

  1. prepare_stream 先准备并持久化 Run。
  2. 若配置 run_execution_in_worker，调用 queue.enqueue。
  3. API 成为该 Run 事件流的观察者。

数据库提交与向 broker 发送消息是两个动作。若进程在两者之间退出，数据库可能已有 Run，而队列没有收到对应消息。存在 Worker、Celery 或 Redis，都不会自动消除这个双写窗口。源码：Run 路由、队列适配器

一种后续可考虑的设计是 transactional outbox：

  • 业务事务同时写 Run 和一条“需要派发 Run”的数据库记录。
  • dispatcher 扫描未派发记录并向 broker 投递。
  • 投递可以重复，但消费者凭稳定身份和执行合同安全处理。
  • 派发记录被确认后更新交付状态。

这是设计方向，不是本次确认已经全面采用的初始 Run 派发架构。同时别走到另一个极端，说“项目完全没有 durable resume”：审批决定已有 resume_pending 持久标记和周期补发，详见下一讲。工程能力常常是按入口逐步覆盖，不是一个“有/没有”布尔值。

理解 outbox 时也不要承诺“消息只会发送一次”。它通常把容易丢失的提交窗口变成可恢复、可重复的派发，重复消费仍要靠消费端业务合同处理。

16.9 协调器不是重跑器，它是在证据之间恢复一致状态

AgentHub 的审批协调器会结合：

  • Run 当前状态及其 owner/lease。
  • 是否有等待中的审批。
  • 审批决定与执行状态。
  • checkpoint 是否存在。
  • 当前记录是否已经足够陈旧。

有活跃 owner 时，它会避免把正在工作的运行当僵尸处理。发现陈旧 CLAIMED 动作时，会将其标为 UNKNOWN_OUTCOME 并把 Run 转入 NEEDS_ATTENTION；有审批但缺 checkpoint，不会伪造一个恢复点。等待审批且已有决定、checkpoint 存在时，才产生相应恢复意图。源码：18

你可以把协调器想成一个认真核对账本的人：它要根据现有证据得出可证明的下一状态，而不是因为“这个任务还没完成”就再做一遍。

这对面试很有帮助。面试官问“服务崩溃后怎么恢复”，不要只回答“队列重试”。可以回答：

我先区分任务是否可重放，再检查谁是当前拥有者，以及副作用证据是否完整。可重放入库可凭不可变输入和确定产物身份恢复；已领取但结果不明的外部动作先进入待对账状态；恢复状态与重新执行是两项不同决策。

16.10 一次真实故障推演应该怎么做？

假设用户说：“上传后一直在转圈，刷新也没好。”

你可以按下面顺序建立证据，而不是先重启所有服务：

检查点 你想排除什么
DocumentRevision / IngestionJob 是否存在 API 是否真正受理，前端是否只是保持旧 loading
stage/status/attempt_count/next_attempt_at 在处理、等待重试、耗尽次数还是已终态
lease token 和过期时间 是否有合法活跃拥有者，是否遗留过期执行
Worker 是否收到相同 job ID 是派发问题还是执行问题
最后一个成功的有边界步骤 解析、切块、编码、索引哪个环节未推进
chunk / index 派生产物 外部写入是否部分完成，能否按稳定身份恢复
详情接口的最新响应 后端已完成但页面还在观察旧快照的可能性

对于“运行创建工单时卡住”，检查顺序则必须增加 Approval execution_status、idempotency_key、工单或外部业务记录，不能直接套文档入库的自动重试。

本讲的最终练习是画一张故障窗口表：提交前、提交后但派发前、领取后但外部调用前、外部成功后但本地记录前、终态写入后但页面收到前。 对每个窗口填上“重试安全条件”“谁负责恢复”“需要哪一种持久证据”。能填满这张表，你就真的进入了异步系统设计，而不是只会启动一个 Worker。
