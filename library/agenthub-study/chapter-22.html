第 18 讲：把项目真正部署并运维起来——配置、迁移、健康检查与恢复演练

第 5 讲介绍数据库与备份基础，本讲关注真实环境中四个经常混淆的“版本”，以及一套可执行的部署与故障处理流程。主要文件：docker-compose.yml、scripts/local_setup.py、apps/api/app.py、.github/workflows/ci.yml、migrations/。

18.1 为什么同一份代码在两台机器上行为完全不同？

一个部署实例至少有四类独立版本：

  1. 代码版本：Git SHA、镜像摘要、启动命令。
  2. 数据库与运行状态结构：Alembic schema revision、LangGraph checkpoint schema。
  3. 运行配置和 Secret：DB/Redis/Qdrant URL、模型路由、加密主密钥、功能开关、Worker 角色。
  4. 业务发布物：AgentVersion、KnowledgeSnapshot、Wiki Publication、模型档案与工具修订。

假设从主分支更新了代码，但数据库还停留在上一个 migration：Python ORM 可能访问不存在的列。再比如数据库有加密的 Provider Secret，API 使用 K1、Worker 使用 K2，模型调用会在解密阶段失败，表面看似“模型供应商不通”。

先做一张环境指纹表：

记录项 样例或来源 排障价值
Git SHA / 镜像摘要 git rev-parse HEAD 确定代码行为
当前迁移 Alembic revision 确定实际表结构
API/Worker 配置 进程角色、队列、数据库目标 判断是否连到同一套环境
模型身份 ModelProfile / 凭据路由 查请求究竟发到哪里
索引参数 Qdrant Collection / 向量维度 / Encoder 排查模型与索引不兼容
Blob 存储 实际目录、挂载或对象存储 原文件是否在所有 Worker 可见范围
密钥管理 Secret 的安全来源与版本 判断已有密文是否可正常读取

环境指纹不需要包含明文密码或 API Key。

18.2 Docker Compose 的依赖启动顺序怎么设计？

AgentHub 仓库当前的 Compose 文件包含 PostgreSQL、Redis、Qdrant、prepare、API、Worker、Beat 等服务。prepare 单独负责数据库准备，然后应用进程启动。

为何把迁移独立于 API 启动？因为有多个 API 副本时，如果每个副本启动都尝试修改数据库结构，会出现并发迁移、异常回滚和部署顺序问题。真正迁移还可能涉及历史数据清理、人工审核和独占维护窗口。把它当成明确可观察的部署步骤更可靠。7 · 8。

迁移与框架 Checkpoint 是两套结构

业务表由 Alembic 迁移管理。LangGraph 的持久 checkpoint 有自己的 schema/bootstrap 流程。部署时应同时核对，而不能因为 Alembic 显示“已升级”，就认为所有图检查点读写必然正常。

可在隔离环境按仓库实际脚本执行：

# 请在已按照仓库 README 配置好的隔离环境执行，先确认命令输出
python -m scripts.local_setup init
python -m scripts.local_setup prepare

# 观察当前源码和服务
 git rev-parse HEAD
 docker compose ps

使用仓库推荐的 uv run 或 Compose prepare 服务，也应保持同一个环境与依赖锁文件。上面的命令用于教学检查，不包含真实密钥或迁移执行记录。

18.3 数据库迁移的四步做法：以 Chunk 复合外键为例

最新版有 0061_chunk_document_revision.py，修复了一个业务约束：Chunk 的 document_id 和 document_revision_id 分别存在，还不意味着它们是一对正确关系。

以前可能写入：

D1 -> Revision R1
D2 -> Revision R2
Chunk C1: document_id=D2, document_revision_id=R1

新增复合外键需要两个动作：

检查历史数据 → 确认干净 → 建立约束。

为什么不是直接给错误记录自动替换一个 Revision ID？因为这意味着改写了证据来源；数据库迁移不知道原作者真实想表达的文档是哪一份。

真正的上线还应考虑：旧代码是否会继续插入新约束不接受的数据、迁移锁等待多久、数据量有多大、失败后如何恢复。复杂 schema 演进可以采用先兼容新增、再回填/检查、最后收紧约束的分阶段流程。参考 13。

18.4 为什么 API 能打开，但上传始终停在 PENDING？

当前 API 提供 /api/v1/health、/api/v1/ready、/api/v1/dependencies 等探测入口。它们各自检查范围不同：简单 HTTP 存活、PostgreSQL 可用性、PostgreSQL/Redis/Qdrant 基本连接。要排查 PENDING 任务，还需要沿 Job 事实继续追到 Worker。

观察 下一步
/health 200，页面仍不能查询 看认证、工作区权限、ready 和请求错误码
上传返回成功，但 Job 一直 PENDING 检查 Redis、Worker、Job 的 next_attempt_at、租约、对账
Job 进入 EMBEDDING 后很慢 看模型首次加载、设备、批量大小、模型缓存
Qdrant 已有 Point，Revision 没 READY 看 Worker 最终确认、租约和索引写入回执
API 可调用模型，Worker 不行 比较进程配置、密钥、网络路由和进程角色
历史 Run 恢复失败 检查 checkpoint schema、源版本/快照与权限重新校验

这是一种“沿同一任务身份逐层排查”的方法。Celery Beat 会定期发起业务对账，但应根据各任务的状态和可恢复性判断是否补投，而不是简单重发所有旧消息。19 · 20。

18.5 Secret 的安全生命周期

API Key 不应散落在 AgentVersion JSON、日志、聊天记录或前端 LocalStorage 里。项目对 Provider/MCP Secret 提供加密存储与读取通道，credential_master_key 是运行时解密的核心输入之一。

这里三种动作要区分：

  1. 轮换供应商凭据：不改变 MCP 服务器或模型档案的逻辑身份，但更换访问令牌。
  2. 轮换加密主密钥：涉及历史密文的重新加密、密钥版本与可回滚方案。
  3. 切换 Endpoint：改变远端目标身份，通常需要新连接/新发布合同。

丢失加密主密钥时，数据库密文仍存在也无法自然恢复原凭据。与数据库备份相配套的 Secret 备份/托管流程，是灾备的一部分。JWT 签名密钥又具有另一套令牌失效语义，应单独管理。

一条日志也可能泄漏 Secret

比如供应商 SDK 抛异常时，把请求 Header、URL Query、完整 HTTP body 打进日志。因此 API 层需要使用稳定 error_code 和经过脱敏的 message，对内部细节设置访问范围；工程调试日志则单独管理并进行敏感字段过滤。普通用户看到 MODEL_PROVIDER_UNAVAILABLE 可以配合 request_id 定位后台原因，但不应该拿到 Bearer Token。

18.6 备份与灾难恢复：设计最小可执行演练

至少要覆盖以下对象：

对象 为什么重要
PostgreSQL 业务表 Agent/Run/Approval/Ticket/Memory/Wiki/评价结果
Checkpoint schema 图执行暂停和恢复所需的状态
Blob 原文件 重建知识索引时的原始输入
Qdrant 数据或索引重建计划 恢复检索能力
凭据主密钥及配置来源 解密现有受保护字段
代码与迁移版本 按适配的 schema 读取历史数据

一次完整恢复演练可以在隔离环境进行：

1. 记录备份时间点与 Git SHA
2. 新建数据库、Blob 目录、Qdrant 实例
3. 从备份恢复相关数据及必需密钥
4. 升级到备份适配的应用/迁移状态
5. 读取一条历史 Run、一个 Approval、一个旧知识快照
6. 运行一个不产生外部写入的冒烟任务
7. 检查引用、权限、日志、模型路由与索引状态
8. 记录恢复点、恢复耗时、缺失项和故障处置

还应给不同数据设定 RPO/RTO：允许丢多少数据、多久恢复。备份文件“生成了”与演练“恢复可用”是两种交付记录。

案例：Qdrant 丢失，PostgreSQL 仍把 Revision 标为 READY

此时应把检索入口的索引完整性作为新的诊断对象：确认快照成员、实际 Collection/Point 状态，按保留的原文件、Chunk、编码器身份重建，核对来源映射，再恢复服务。不能简单重新设置 READY，因为 READY 原本表达的是之前一次入库完成的结果，不会使丢失的索引自动出现。

18.7 CI 与生产环境的关系

仓库 .github/workflows/ci.yml 不只包含 Python 单元测试，也有 PostgreSQL、Redis、Qdrant 服务、迁移相关检查、后端与前端构建。它们提供不同层次的证据：

  • 静态检查保证可发现的语法、类型、依赖问题被发现。
  • 单元测试验证纯业务规则。
  • 真数据库测试验证约束、锁、迁移与事务。
  • 浏览器走查验证用户入口和异步页面状态。
  • 受控模型/业务实验评估真实供应商和工具效果。

每次修改应针对其风险选择测试，不必把所有检查堆成同一个漫长命令。关键是缺什么保证，补相应的验证。参见 CI。

本讲掌握标准：可以解释 API 存活而后台任务不推进的至少三种原因；能画出 prepare/migration/Worker/依赖的启动顺序，并制定一份真正可操作的隔离恢复演练表。

18.8 运维值班：三个具体事故的处置剧本

事故 A：任务量突然上涨，Redis 队列堆积

先对照 API 受理速度、Broker 消息数、活跃 Worker 数、数据库 PENDING/RUNNING 数量。如果 Worker 根本没有消费任务，检查 Celery 进程、Broker URL、任务注册、权限和密钥。若 Worker 已经消费但 Job 进展很慢，再看 Qdrant、Embedding 模型与 CPU/GPU 利用率。不要第一步就把 worker_concurrency 翻十倍：数据库连接池、GPU 显存和外部模型并发限额也可能随之被打满。

事故 B：Worker 重启后大量任务进入 NEEDS_ATTENTION

先按业务类型分组：摄取、纯检索、Agent 工具写操作。允许重新计算的文档摄取可能在租约过期后重新领取；存在未知外部写入的 AgentRun 应保留核对结果。批量“把所有旧 RUNNING 改成 PENDING”会把不同恢复合同混在一起。逐项记录初始 owner、租约到期、最近的 RunStep、Approval 及外部操作 ID。

事故 C：模型请求全部返回凭据错误

检查 API 与 Worker 实际读取的 credential_master_key、Provider Credential 是否启用、目标 BaseURL/模型名、出站网络策略，以及网关的安全错误码。切勿把新密钥覆盖旧密钥后重新启动，让历史凭据变成不可读。若需要轮换主密钥，先在隔离环境完成旧密文→新密文的迁移与核对。

18.9 灾备演练具体怎样算“完成”？

可以用一个可复核的演练表，而不是写“备份成功”：

验收对象 输入 通过条件
数据库结构 备份 + 固定代码 SHA 表与迁移版本适配，无意外结构更改
历史 AgentRun 已完成 Run ID 读取源版本、步骤、终态、产物
待审 Run WAITING_APPROVAL ID 审批状态可回读，仍遵守操作者权限
已发布知识 Snapshot S1、Revision V1 源文件、Chunk、索引/引用相互匹配
密文 测试模型凭据 受控调用可成功、日志无明文 Secret
接管工单 Ticket/HandoffCase ID 版本、归属与处理历史完整
安全冒烟 一个只读任务 工作区隔离与错误路径正常

演练报告同时记录恢复点时间、开始和完成时间、跳过的对象、异常、恢复后的数据一致性检查。数据库备份和索引重建计划要有共同的数据版本标签，避免“数据库恢复到周一、Qdrant 却来自周五”而造成引用错配。

18.10 一次发布的回滚设计

对简单前端样式修改，回滚镜像通常足够。对数据库迁移，回滚要更审慎：如果新代码已经写入新字段或按新格式创建业务数据，直接 alembic downgrade 未必保持数据可用。

对涉及破坏性 schema 变更的发布，可采用三阶段思路：

  1. 扩展：增加新字段/表，旧代码仍可运行。
  2. 迁移：回填并验证，逐步把读写路径切换到新结构。
  3. 收缩：待兼容窗口结束再移除旧字段。

每个阶段都有单独的测试与部署回执。这样的改造更接近可维护的生产演进，而不只是一次性“迁移脚本跑通”。
