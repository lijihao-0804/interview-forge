第 18 讲：文档修订、摄取与索引一致性

版本说明：本讲以 2026-11-20 核验的 cdc9d084d3a20e71355401952ee394da4e56273b 为准。第 11 讲之后的工程改动已纳入；本讲的例子用于解释设计，不冒充本次执行过的生产操作或测试。

18.1 先从一件很普通的事说起：把报销上限从 300 改成 400

你打开一份制度文档，只改了一句话，然后重新上传。站在页面上看，这只是一次上传；站在系统里看，它至少涉及四种不同身份。

对象 它回答的问题 修改这句话之后会怎样
Document “这是哪份业务文档？” 原文档身份继续存在
DocumentRevision “这份文档的哪一次内容版本？” 产生新的修订身份
DocumentChunk “哪一个修订里的哪段原文？” 新修订有自己的块身份和定位
KnowledgeSnapshot “某次检索允许看到哪些修订？” 旧快照不自动切到新修订，需要新快照表达新集合

这四种身份不能压缩成一个“文档 ID”。如果把原来的块直接改写，旧回答里的引用虽然还指向同一个 ID，打开后却变成了新内容。你就无法回答：“模型当时为什么说上限是 300？”这个项目选择保留修订和快照，正是为了保留这个问题的答案。数据模型 快照服务

再往前想一步：新修订上传完成时，它还没有成为可用证据。它需要被解析、切块、编码、写入索引，随后才能完成摄取。旧修订可以在这段时间里继续服务。当前完成逻辑会在 READY 的修订中选择修订号最高者作为 ACTIVE，其余 READY 修订进入 RETIRED；它不是“哪个 Worker 最后完成，哪个修订就赢”。这避免了较旧修订处理得慢，反而在最后覆盖新版本的情况。摄取完成逻辑

这里有两个状态维度，面试时经常混淆。

  • 摄取状态说明“这份内容处理好了没有”：PENDING、PROCESSING、READY、FAILED。
  • 生命周期状态说明“这份已存在内容在版本体系里是什么地位”：ACTIVE、RETIRED、DELETED。

READY 不等于当前默认版本；RETIRED 也不等于内容已经物理不存在。是否允许进入一次查询，还要看快照、生命周期和相应的服务规则。把这两个维度分开，才能解释历史重现、日常最新检索和来源撤销为什么不是同一个操作。数据模型

18.2 上传接口为什么先存文件，再写数据库，再通知队列

上传服务中可以追到三类介质：Blob 保存原始文件；PostgreSQL 保存 Document、Revision、Job 和审计记录；队列通知后台 Worker。它们不会因为都写在一个 Python 函数里，就自动组成一笔跨系统事务。上传服务

可以把操作理解成下面的分支：

为什么“提交结果丢失”不能直接当成失败清理文件？假设 PostgreSQL 已经提交 Revision，但是网络在回传成功时断了。客户端调用 rollback()，只能处理自己当前连接的事务状态，不能穿越网络把刚才已经提交的数据抹掉。如果此时删除原始文件，数据库里的修订就会指向不存在的内容。

当前实现会在尝试提交前确定 Document、Revision、Job 的 UUID。遇到不确定提交结果后，按这组具体身份回查；如果仍不能证明没提交，就保留文件。这里宁可暂时留下可对账的孤立文件，也不轻易删除可能已经被正式记录引用的唯一原件。提交确认分支

这件事可以迁移到很多普通业务：上传头像、支付后写订单、生成报表、提交外部工单。真正要区分的是三个状态：

  1. 明确没有成功。
  2. 明确已经成功。
  3. 已经发出动作，但还不知道它成功与否。

第三种状态需要回查和对账，不能靠“再执行一次肯定没事”来解决。

队列通知失败也不等于修订应该回滚。项目已经有持久的 IngestionJob；通知只是让后台尽快来处理它，协调器还能检查可恢复任务。但这不表示系统所有任务类型都已具有同一套完整的持久派发机制。知识摄取的恢复能力，应当按照这条具体链路讨论。上传服务 协调逻辑

18.3 本次最值得学的数据库修改：两个合法 ID，为什么组合起来仍然可能非法

假设同一个知识库里有：

对象 所属文档
修订 R1 文档 D1
修订 R2 文档 D2

现在插入一个 Chunk：document_id=D1，document_revision_id=R2。

如果数据库只分别验证“D1 存在”和“R2 存在”，两项都可能通过。即使修订外键包含工作区和知识库，也只能证明 R2 属于正确租户与知识库，不能证明它属于 D1。

当前新增的组合外键直接表达完整关系：

-- 用于解释约束含义的简化表示，正式定义见迁移与 ORM 模型。
FOREIGN KEY (
    workspace_id,
    knowledge_base_id,
    document_id,
    document_revision_id
)
REFERENCES document_revisions (
    workspace_id,
    knowledge_base_id,
    document_id,
    id
);

它约束的是一整组值的配对，而不是四个字段各自存在。这次 RG15 从需求清单进入了实际模型和迁移，是理解“数据库约束如何承载业务关系”的好案例。模型组合外键 迁移 0061

数据库已经有正确约束，为什么服务层还要检查工作区和知识库？因为两层承担不同任务。服务层负责在业务入口给出合适权限语义与错误；数据库负责对所有写入路径兜住结构关系，包括后台脚本、未来新增服务和并发竞态。前者不能替代后者，后者也不替代授权检查。

迁移不是把 D1 悄悄改成 D2

迁移先建立新的 NOT VALID 约束，再诊断既有错配，验证历史数据，最后移除旧约束。发现错配时，它会给出 Chunk、文档、修订和真实修订所属文档的身份并中止，而不是擅自改某个字段。迁移 0061

为什么不自动修？因为数据库只知道这组值不一致，不知道最初究竟是 Document 填错了，还是 Revision 填错了。如果原文引用已经发给用户，改错一边会制造一个“结构正确、语义归属错误”的结果。应先回到来源、摄取记录和原文件确定真实归属。

还要注意，当前迁移在同一迁移事务中做诊断和验证。不能仅因为出现 NOT VALID，就宣称它已经是适合任意超大表的“完全无阻塞在线迁移”。数据量、锁等待和验证耗时仍需要针对实际部署评估。仓库增加的真实 PostgreSQL 迁移测试，有价值的地方在于它检查约束行为和失败后的状态，而不只是比较 ORM 字符串。迁移测试

18.4 为什么 max(revision_number) + 1 在并发下不可靠

两个请求同时给 D1 上传新修订：

  • 请求 A 看到最大修订号是 7，准备写 8。
  • 请求 B 也看到 7，也准备写 8。
  • 唯一约束最多让其中一个失败，无法让两个合法上传都顺利得到不同序号。

当前服务在 Blob 写完后，对同一 Document 行加分配锁，再查询最新修订号。先拿到锁的请求分配并提交；后拿到锁的请求继续读取，就能看到前一个请求的修订号。修订分配逻辑

这里的技巧是：要分配的第 8 条修订还不存在，不能锁一条不存在的子记录；但它们共同的父 Document 已经存在，可以拿父行作为同一文档内的串行化点。

为什么不是在开始上传时就拿锁？大文件流式写入可能很慢。整个上传期间占着父行锁，会让其他同文档操作白白等待。当前顺序把锁留在需要分配修订号的临界区，能缩短持锁时间。但 Blob 和数据库仍是两种介质，失败补偿问题不会因此消失。

这种设计适合“每个父对象拥有自己的连续版本序号”。如果未来需要极高吞吐、允许序号不连续或全局排序，分配策略可能不同。面试时不要只背“加锁就行”，要说明锁的粒度、存在的竞争对象、为什么锁这个对象、持锁期间做了哪些慢操作。

18.5 有限重试次数必须与领取动作在同一处生效

以前的技术演进清单指出：如果次数上限只在后台扫描时判断，一个直接领取任务的入口可能在扫描器介入前继续执行。现在领取函数把条件和计数更新合到一次数据库 UPDATE 中：

-- 教学伪 SQL：省略时间、阶段与租约等具体条件。
UPDATE ingestion_jobs
SET status = 'PROCESSING',
    attempt_count = attempt_count + 1,
    lease_token = :new_token
WHERE id = :job_id
  AND job_is_claimable
  AND attempt_count < :max_attempts
RETURNING *;

关键不是 SQL 长相，而是成功领取和消耗一次机会不可拆开。两个 Worker 同时竞争时，数据库负责判断谁实际拿到任务；拿不到的 Worker 不应该消耗一次成功领取额度。原子领取实现

次数耗尽后也有一个容易写错的边界。假设上限是 3，第 3 次合法执行正在进行，租约仍有效。另一个重复消息来了，不能因为看到 attempt_count=3 就把正在跑的任务标成 FAILED。当前失败化只针对已经可再次领取、但额度耗尽的任务；有效持有者仍受保护。

自动退避和用户手动重试也应分清。自动退避可以保留上次错误，帮助理解为什么正在等待；本次手动重试路径会重置错误字段，并把修订恢复为 PENDING。页面判断是否失败，不能只看“错误文本非空”，应结合当前 Job 与 Revision 状态。重试与领取 手动重试服务

18.6 “失去租约就停止”到底能保证到哪一步

租约解决的是“当前谁有权推进任务”。如果 Worker A 很长时间没有续租，Worker B 接管了任务，A 之后恢复运行时不能继续以旧身份提交最终状态。

本次增加 _ClaimGuard：它确认 Job 仍为 PROCESSING、token 相同、租约未到期；续租失败或数据库错误导致持有权无法确认时，设置失租信号。解析、切块、编码和索引的关键边界会检查这个信号与数据库身份。向量缓存的编码调用前后也支持持有者检查。Worker Guard 缓存持有者检查

但是要把这句话说完整：停止越过下一个处理边界，不等于把已经交给远端的动作撤销。

例如 A 已经调用 Qdrant upsert，随后失租；远端可能仍把请求执行完。再例如同步编码函数正在线程里运行，设置一个 asyncio 事件不保证底层计算立即停止。因此代码仍需要确定性的 point ID、不可变修订，以及最终状态提交时的持有者验证。它们共同把重复工作限制在可识别、可重放的范围里。索引边界 Point ID

这几层保护针对不同故障：

保护 它阻止什么 它不负责什么
有限领取次数 同一 Job 无限获得新执行机会 不统计一切模型内部物理尝试
Lease token 旧 Worker 冒充当前持有者 不自动取消已经发出的远端调用
编码与索引边界检查 失租后继续做后续批次 不保证抢占所有同步计算
稳定 point ID 重放产生另一批无关联点 不自动证明所有点已完整写入
最终事务验证 旧持有者把 Job 标成成功 不把 PostgreSQL 和 Qdrant 变成同一事务

这个表很适合面试：每个机制都说得出保证和不保证，才表明你理解了恢复设计。

18.7 只改一小段，为什么还会产生新 Chunk；向量缓存又如何省事

新修订里的块需要指向新修订，即使正文和旧修订完全一样。来源身份属于“这段文字出现在哪个版本”的问题；编码结果属于“这个编码器对这段输入算出什么向量”的问题。两者可以独立。

当前向量缓存按工作区、模态、编码器身份和实际输入内容识别可复用计算。命中缓存时可以复用向量，但新块与索引记录仍携带新修订来源。若编码器指纹无法可靠建立，代码选择重新编码；不能仅凭“模型名字看起来相同”就使用旧向量。向量缓存

所以，局部修改后的实际成本取决于两件事：

  1. 切块变化传导了多远。固定窗口可能因为前面插入内容，导致后续窗口正文变化；结构切块有机会限制影响，但仍需要看具体文档。
  2. 新块的真实编码输入有多少与旧输入完全一致。只差标题、前缀、归一化方式或其他输入配置，也可能导致缓存失效。

不要把精确缓存说成“模型理解了两段话意思相同，所以自动复用”。本项目这条路径是计算身份相同的复用；同义但不同的文本没有这种保证。

同样，不要把“Embedding 请求变少”直接等价为“端到端耗时同比例下降”。解析、冷启动、模型指纹、数据库读写、稀疏编码、索引确认都仍可能占时间。验证时要同时报告缓存命中与完整 READY 延迟。

18.8 换行为什么会影响答案：一个真实的解析细节

一行文本在 Windows 中常用 CRLF 表示换行。如果正则在匹配时把一个 CRLF 拆成 CR 和 LF 两个换行，就可能把本来只换了一行的内容当成空段。金额在上一行，适用条件在下一行，本应在同一段里，却被错误分开。结构分块

当前修复让段落识别把单个 CRLF 作为一个逻辑换行，并让自适应结构阈值按规范化文本长度判断。这样同样的可读内容，不会仅仅因为换行编码不同就变成截然不同的切块结果。自适应分块

同时必须保留“规范化后的内容”和“原始修订里的位置”的区别。检索和编码可能需要统一换行；引用定位却必须能回到真实原件。假如在规范化后算出的第 100 个字符，直接拿去切原始 CRLF 字符串，定位就可能偏移。这个问题说明：文本清洗、切块和来源坐标设计需要一起考虑。

仓库的复核报告用两篇长文对照了 LF/CRLF 结果，并记录修复后的有序块正文一致。这是具体材料上的证据；它没有修改旧快照，也不意味着所有历史索引自动变好。仓库复核报告

18.9 你应该怎样排查“上传了，但问不到”

建议沿着证据逐层缩小范围，而不是先换一个 Embedding 模型。

观察 下一步检查 可能的故障层
接口成功但页面一直等待 Revision、Job 是否实际存在，任务是否有租约或退避时间 提交、派发、领取
Job 在 PROCESSING 不推进 lease 是否有效、attempt 是否耗尽、最近阶段和错误 Worker 与恢复
Revision READY，却没有相关结果 查询实际绑定哪个 Snapshot，快照是否包含新修订 版本选择
Snapshot 正确但召回为空 索引点及 payload 身份、索引配置、过滤条件 编码或索引
能看到目标块，但模型漏条件 完整证据是否被预算选入、实际消息是否保留条件 证据交付
正文完整但回答错误 模型输出、引用映射、拒答或校验阶段 生成与答案合同

这不是要你一次打印所有原文日志。先用 ID、状态、阶段、数量和安全错误码定位，再按权限查看必要原文。尤其不要把数据库里“存在这段文字”当成“模型本次看到了它”。

本讲练习

用一份三段制度做一个有限实验：第二段写金额，第三段写适用条件；上传 R1，冻结 S1，再只改金额上传 R2，冻结 S2。分别查询 S1 与 S2，记录修订 ID、块 ID、完整条件和答案引用。随后写一张故障推演表：分别在 Blob 后、事务提交后、首次编码后、部分 upsert 后和 READY 提交前中断，说明恢复者会靠哪个持久身份继续，以及哪些动作可能重复。这里要求先解释设计；真做故障注入时应使用隔离环境和可丢弃数据。
