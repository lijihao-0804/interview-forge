第 4 讲：工具审批与恢复执行

用户提问

先再讲一下4工具审批这一块吧

讲解原文

好，这一节我们专门讲 第 4 部分：工具审批与恢复执行。

你已经理解 Agent 的工具调用，所以我们从“模型已经提出一次工具调用”往下讲，重点看：前端如何展示和提交审批，后端如何保存决定，以及数据库如何保证执行过程可恢复、可追踪。

先抓住这一点：

批准一次工具调用，表示允许执行这个具体动作；动作是否执行成功，需要另外记录。

AgentHub 围绕这两个事实，分别设计了审批状态、执行状态和 Run 状态。下面以源码提交 0 为依据，用内置的 create_ticket 贯穿讲解。

一、从“模型要创建工单”这个例子开始

假设当前工作区已经有客户 C-001，用户说：

帮这个客户创建一张工单，跟进登录失败的问题。

模型提出的工具调用，可以表示为：

{
  "name": "create_ticket",
  "arguments": {
    "customer_ref": "C-001",
    "subject": "跟进客户登录失败的问题",
    "priority": "MEDIUM"
  }
}

这里的 C-001 是教学示例。AgentHub 的这个内置工具，最终会向 PostgreSQL 的 tickets 表写入一条工单记录。

在工具目录中，create_ticket 的定义是：

字段 实际配置 含义
effect WRITE 会改变业务数据
risk_level HIGH 工具被标记为高风险
approval_policy ALWAYS 配置为需要审批
execution_kind action 通过动作执行路径运行

注意，参数里的 priority: MEDIUM 是这张工单的业务优先级，与工具的 risk_level: HIGH 是两个不同概念。源码见 内置工具目录。

是否需要审批，由后端策略判断

AgentHub 当前的 ToolPolicy.decide() 判断很直接：

if (
    definition.effect is ToolEffect.READ
    and definition.approval_policy is ToolApprovalPolicy.NEVER
):
    return ToolPolicyDecision.ALLOW_AUTO

return ToolPolicyDecision.REQUIRE_APPROVAL

也就是说，当前代码只让 READ + NEVER 的组合自动通过，其他组合返回“需要审批”。这里并没有单独用 risk_level == HIGH 作为判断条件。源码见 policy.py。

二、数据库里先保存一张“审批单”

你可以把 Approval 理解为一张业务单据：

某次 Run，准备使用某个版本的工具，携带这一组确定的参数执行一个动作，现在请求人工决定。

因此，审批记录需要保存的内容，远不止一个 approved: true。

1. 审批绑定的是一个具体动作

AgentHub 的 approvals 表包含这些重要信息：

信息 主要字段 为什么需要
属于哪次任务 workspace_id、run_id 找到所属工作区和 Run
使用哪个版本 agent_version_id、tool_revision_id 确定本次审批对应的 Agent 和工具版本
准备做什么 tool_identity、canonical_arguments 保存工具身份和经过校验、规范化的参数
这是哪一次动作 logical_action_id、idempotency_key 识别重复恢复和重复业务请求
人作出了什么决定 decision_status、decided_by、decided_at 保存审批结果及责任人
动作实际做得怎样 execution_status、safe_result、失败信息 保存执行结果

源码见 Approval 数据模型。

这里最值得你记住的是：

用户批准的工具参数会保存在数据库里，真正执行时也从这条审批记录读取。

比如用户审阅的是：

{
  "customer_ref": "C-001",
  "subject": "跟进客户登录失败的问题",
  "priority": "MEDIUM"
}

审批后就应执行这组参数。如果换成另一个客户或另一个动作，那就已经超出了这张审批单表达的许可范围。

2. 必须区分三个状态

这是整节课最重要的一张表：

状态字段 回答的问题 示例
Approval.decision_status 人是否允许执行？ PENDING、APPROVED、DENIED
Approval.execution_status 动作实际执行到哪里？ NOT_STARTED、CLAIMED、SUCCEEDED
AgentRun.status 整次 Agent 任务运行到哪里？ WAITING_APPROVAL、RUNNING、SUCCEEDED

例如，下面这组状态完全合理：

decision_status  = APPROVED
execution_status = NOT_STARTED
run.status       = WAITING_APPROVAL

它表达的是：

人的批准决定已经提交到数据库，但恢复执行还没开始。

再比如：

decision_status  = APPROVED
execution_status = SUCCEEDED
run.status       = RUNNING

它表达的是：

工单已经创建成功，但 Agent 还在处理后续步骤，例如组织给用户的回复。

所以，审批成功、工具执行成功、整次 Run 完成，是三个不同的时刻。 状态定义见 contracts.py。

三、Run 如何暂停，并在之后继续

人可能马上审批，也可能十分钟后才审批。系统需要把恢复所需的信息持久化下来。

AgentHub 在这里保存两类东西：

持久化内容 负责保存什么
审批记录 Approval 具体动作、工具参数、人工决定、执行结果
LangGraph checkpoint 图的运行状态、执行位置和等待中的中断

审批单记录业务事实，checkpoint 记录运行进度。

AgentHub 使用 PostgreSQL 的 checkpoint 实现，恢复标识按工作区和 Run 生成：

agenthub:{workspace_id}:{run_id}

这里 LangGraph 使用的 thread_id 是围绕 Run 构造的恢复标识，与项目业务层的会话 AgentThread.id 要区分开。源码：checkpoint.py

1. 创建审批单之后，触发中断

在运行图的 policy 节点中，可以把核心逻辑理解成下面这个教学简化版：

approval = await approval_service.create_or_get(
    # 当前 Run、工具版本、工具参数等
)

resume_payload = approval_interrupt({
    "approval_id": str(approval.id),
    "logical_action_id": approval.logical_action_id,
})

approval_interrupt() 是对 LangGraph interrupt() 的适配包装。触发中断后，运行状态会被保存，Run 进入 WAITING_APPROVAL。之后可以通过新的请求恢复这次运行。源码：运行图、LangGraph 适配层。

2. 恢复时，中断所在的节点会重新进入

这个细节很容易被忽略：

LangGraph 恢复中断时，会从该节点的开头重新执行。 执行到对应的 interrupt() 时，取得这次传入的恢复值，然后继续往下走。它依赖 checkpointer 保存状态。(reference.langchain.com)

这解释了为什么前面的函数叫：

create_or_get(...)

因为恢复时，创建审批单之前的代码可能再次执行。此时应该拿到原来的审批单。

AgentHub 为每次具体提议生成稳定的 logical_action_id，结合工作区、Run、工具版本、参数和提议序号识别同一动作；数据库再用唯一约束防止重复创建。

这里的“同一动作”指同一次提议的重放。用户后来再次提出相同需求，可以形成新的提议，不会把所有参数相同的调用永久合并。源码：create_or_get 与动作身份计算、contracts.py。

四、人点击“批准”之后，前后端具体做了什么

这一段可以直接接上上一节的：

React 页面 → HTTP 请求 → FastAPI 路由 → Service → 数据库。

1. 前端先读取审批列表

审批页获取待审批记录的请求形如：

GET /api/v1/workspaces/{workspace_id}/approvals?decision=PENDING&limit=50&offset=0

返回数据后，页面把审批对象保存到 React state，并展示工具参数、决策状态和执行状态。

源码中有两个独立的状态展示：

<StatusBadge status={approval.decision_status} />
<StatusBadge status={approval.execution_status} />

这正对应前面讲的“人是否批准”和“动作是否执行”。源码：审批页面。

2. 点击批准，只提交对这张审批单的决定

实际请求形如：

POST /api/v1/workspaces/{workspace_id}/approvals/{approval_id}/approve
Content-Type: application/json

{}

请求体是空对象。

工具参数已经保存在审批单中，前端通过 URL 中的 approval_id 指明批准哪一个动作。

拒绝则调用另一个入口，可以附带理由：

POST /api/v1/workspaces/{workspace_id}/approvals/{approval_id}/deny
Content-Type: application/json

{
  "reason": "已经有同类工单，无需重复创建"
}

源码见 前端 approvals API 客户端。

3. 后端路由先保存决定，再恢复 Run

批准路由的核心调用顺序是：

approval = await approvals.decide(
    context,
    approval_id,
    decision=ApprovalDecisionStatus.APPROVED,
)

result = await _agent_run_service(request).resume(
    context,
    run_id=approval.run_id,
    approval_id=approval.id,
)

这两次调用分工很清楚：

  • decide()：把人的决定可靠地保存下来。
  • resume()：恢复这张审批单所属的 Run。

当前正常请求路径会在 API 中直接 await resume()。后台任务承担另外的补偿恢复职责，后面再讲。源码：审批路由。

4. decide() 是一个数据库事务

ApprovalService.decide() 会先检查审批权限，读取并锁定相关 Run 和 Approval，再检查审批是否仍然有效、是否已经有决定。

对于一个有效的批准请求，它在同一事务里保存：

Approval.decision_status = APPROVED
Approval.decided_by      = 当前审批人
Approval.decided_at      = 当前时间

AgentRun.resume_pending  = True

审计日志：谁在什么时间批准了哪一个动作

然后 commit()。

如果这张审批单已经决定过，服务会返回已有结果，避免后来的请求随意覆盖历史决定。源码：ApprovalService.decide。

这里正好体现上一节的事务知识：

“决定已经保存”与“这个 Run 还需要恢复”要一起提交，确保数据库同时记住这两件事。

至于真实工具是否成功，要等后续执行阶段才能知道。

五、恢复 Run 后，先取得执行权，再运行工具

1. 恢复的是原来的 Run

AgentHub 的 resume() 会验证：

  • 审批单是否属于当前 Run、工作区和 Agent 版本；
  • 是否就是这个 Run 当前等待的审批；
  • 保存的 checkpoint 是否对应这次中断；
  • 原 Run 发起者现在是否仍有执行所需的权限。

然后用类似下面的恢复载荷继续图运行：

Command(resume={"approval_id": "这次审批的 ID"})

项目实际通过 resume_command() 适配函数构造这个命令，并使用已经验证的 checkpoint。

恢复时会重新读取数据库中的审批决定。审批人提供的是许可；执行仍依据原 Run 创建者当前的权限。管理员批准一个动作，并不会把管理员身份交给这个 Run。源码：runtime_service.py。

2. 数据库要防止多个执行者同时行动

现在考虑一个现实问题：

用户连续点击了两次批准，或者恢复任务被重复投递，会不会创建两张工单？

按钮禁用可以改善体验，但执行端仍需要数据库保证。

AgentHub 使用 claim_execution() 认领动作执行权。它的 SQLAlchemy 操作可以翻译成下面这条教学 SQL：

UPDATE approvals
SET
    execution_status = 'CLAIMED',
    execution_attempt_count = execution_attempt_count + 1
WHERE
    workspace_id = :workspace_id
    AND id = :approval_id
    AND decision_status = 'APPROVED'
    AND execution_status = 'NOT_STARTED'
RETURNING id;

关键就在 WHERE 中：

execution_status = 'NOT_STARTED'

假设执行者 A、B 都尝试认领：

  1. A 成功把状态从 NOT_STARTED 改成 CLAIMED。
  2. B 再检查这条更新条件时，记录已经不满足 NOT_STARTED。
  3. B 更新不到记录，因此拿不到执行权。

检查“尚未执行”和修改“已经认领”，放在同一条数据库更新语句中完成。

这比在 Python 中先查询、再根据查询结果决定执行更可靠，因为两次独立操作之间可能插入另一个执行者。源码：claim_execution。

CLAIMED 的准确含义是：

某个执行者已经获得这个动作的执行资格。

它还不代表工单创建成功。

3. 真正执行时，读取审批单里的参数

取得执行权后，运行图的调用核心是：

await action_runtime.execute(
    context,
    definition,
    dict(claimed.canonical_arguments),
    idempotency_key=claimed.idempotency_key,
)

这里有两个关键输入：

  • canonical_arguments：这张审批单绑定的工具参数。
  • idempotency_key：传给业务执行器，用来识别同一个业务动作。

因此，人工看到的参数和真正执行的参数通过数据库中的同一条记录联系起来。源码：action_execute。

六、真正创建工单，就是你上一节学的数据库操作

到了 CreateTicketActionExecutor.execute()，逻辑就回到了普通业务后端：

  1. 校验 customer_ref、subject 等业务参数。
  2. 按 workspace_id + idempotency_key 查询是否已经创建过这张工单。
  3. 查询当前工作区内的客户。
  4. 创建 Ticket ORM 对象。
  5. 执行 session.add()、commit()、refresh()。
  6. 返回工单创建回执。

成功回执的形状是：

{
  "ticket_id": "工单 UUID",
  "ticket_ref": "T-工单编号",
  "status": "OPEN"
}

这里表示“创建了一张处于 OPEN 状态的工单”。源码见 CreateTicketActionExecutor。

1. 业务表还会再做一层去重

tickets 表对下面两个字段组合设置了唯一约束：

workspace_id + idempotency_key

同一个工作区内，同一业务动作只能对应一条这样的工单记录。执行器如果查到已有工单，就返回原来的工单；遇到并发唯一约束冲突，也会回查已有结果。源码：Ticket 模型、动作执行器。

现在可以把几层保护区分开：

机制 解决的问题
create_or_get 与稳定动作 ID 恢复节点时，重复创建审批单
claim_execution 条件更新 多个执行者同时执行同一审批动作
业务表的幂等键与唯一约束 同一次业务动作重复产生工单

这三层保护各有作用。前面一层存在，并不意味着后面的业务表就可以省去约束。

2. 执行结束后，更新审批的执行结果

工单创建成功之后，运行时会通过 complete_execution() 保存：

execution_status = SUCCEEDED
safe_result      = 工单创建回执
executed_at      = 执行完成时间

然后把工具结果交回后续运行步骤，Agent 可以据此回复：

已创建工单，编号为 T-……，目前状态为 OPEN。

源码见 审批结果保存 与 运行图中的动作执行。

3. 后端把最新状态返回前端

批准接口在恢复执行后，会重新读取审批记录，返回：

approval    最新审批对象
run_id      对应的 Run
run_status  当前 Run 状态

前端用返回的审批对象替换 React state 中原来的那一项，重新渲染两个状态标签，并提供返回 Run 的入口。它还会继续通过轮询获取更新。源码：批准接口、审批页面。

因此，前端判断结果时，需要查看返回的具体状态。HTTP 200 本身不能代替 execution_status。

七、理解三个特殊情况，就能看懂这套设计为什么需要这些字段

情况一：决定保存成功，但 API 在恢复前崩溃

过程可能是：

批准决定已 commit
↓
API 进程退出
↓
resume() 还没来得及执行

这时数据库里会留下：

decision_status = APPROVED
resume_pending  = True

resume_pending 相当于一个持久化待办：

这次决定已经落库，Run 还有恢复工作需要完成。

AgentHub 的后台 reconciliation 会扫描相关记录，补充派发恢复任务。这就把“API 进程恰好活着”与“已经保存的决定最终得到处理”分离开了。源码：reconciliation.py、审批后台任务。

这也是为什么前面要把“决定”和 resume_pending 放在同一个事务里。

情况二：动作可能已经执行，但没有拿到确定回执

换成一个远程 MCP 写工具，更容易理解这个问题：

AgentHub 发出创建请求
↓
远程系统可能已经创建成功
↓
连接断开
↓
AgentHub 没收到回执

这时，AgentHub 能确定的是“没有收到结果”，还不能确定“对方没有执行”。

所以执行状态中需要：

UNKNOWN_OUTCOME

表示结果无法确认。

对于内置 create_ticket，执行器发生超时或异常时，会尝试按幂等键回查业务记录；能确认结果就返回确定结果，仍无法确认时保留未知状态。运行图遇到未知结果，会将 Run 转为 NEEDS_ATTENTION，要求进一步核对。源码：ActionRuntime、未知结果处理。

这也揭示了数据库事务的边界：

批准决定、动作认领、业务写入、执行结果保存，是多个明确的事务阶段。 中间的中断和不确定性，需要通过恢复标记、幂等键、结果回查等机制处理。

情况三：用户拒绝了审批

拒绝之后，AgentHub 也会恢复原 Run。

原因是 Agent 需要拿到这个结果：

这次工具动作没有获得批准。

运行图会产生 TOOL_APPROVAL_DENIED 对应的工具结果，让模型继续处理，例如回复：

这次创建工单的请求未获批准，因此没有创建工单。

此时可能出现：

decision_status  = DENIED
execution_status = NOT_STARTED
run.status       = SUCCEEDED

它表示：系统正确处理了拒绝，并完成了本次对话流程。

所以，“动作被拒绝”不必等于“整个 Run 运行失败”。源码：拒绝路由、审批结果转为工具观察。

八、你读源码时，先抓住这四个方法

这部分源码很长，但审批业务可以先围绕 ApprovalService 的四个方法建立理解：

方法 你读代码时要确认的事情
create_or_get() 这次准备执行什么？如何保证恢复后仍找到同一张审批单？
decide() 谁作出了什么决定？决定和待恢复标记如何一起提交？
claim_execution() 哪个执行者获得执行资格？并发时如何只让一个执行者成功？
complete_execution() 最后确认了什么结果？如何把它保存下来供后续读取？

这四个方法都在 packages/approvals/service.py。

然后围绕它们向外看：

  • 向前端看：审批页面怎样展示记录、调用批准和拒绝接口。
  • 向路由看：接口怎样串起 decide() 和 resume()。
  • 向运行图看：哪里触发中断，哪里读取审批，哪里认领执行。
  • 向业务层看：CreateTicketActionExecutor 怎样把批准的动作变成数据库记录。

这一节真正要建立的能力，是看到“批准按钮”时，能够继续追到它背后的审批记录、恢复入口、执行权认领和业务表写入。 这样你读到的就不只是一个 Agent 功能，而是一条可以独立实现的完整前后端业务流程。
