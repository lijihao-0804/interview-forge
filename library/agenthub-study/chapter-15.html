第 11 讲：评测与独立修改

  • 追加日期：2026-11-18。
  • 主题：评测与独立修改。
  • 源码基线：ab2b5b046da86bb2b0bd0eb65f7bab3a59eff239。
  • 用户要求：讲解“用固定任务检查效果，独立完成一项真实项目改动；冻结评测与指标、面试题、情景推演；能给出修改原因、实现位置、验证结果和局限”，并追加到文档。

这一阶段要完成的转变是：从“我能解释代码怎样运行”，进一步到“我能提出一个明确改动，用证据判断它是否有效，并说明还有哪些事情没有证明”。

前面我们已经学习了工具、审批、数据库、RAG、Memory、Wiki，以及前端和异步执行。这一节把它们变成一套可以自己使用的工作方法。

先记住四个问题：

  1. 为什么改？ 哪个可观察的问题说明当前实现需要调整？
  2. 改哪里？ 现象经过哪些页面、接口、服务、数据和执行状态？
  3. 怎么证明？ 用哪些固定输入、判据和对照排除“只是这次运气好”？
  4. 证明到哪里？ 哪些场景通过，哪些结果仍然未知，哪些结论不能外推？

本节仍以核查到的 AgentHub 固定提交 1 为源码依据。下面会区分仓库已经实现的机制、仓库记录的历史实验、教学示例，以及建议你自己完成的练习。本次是在讲解和追加文档，没有把示意改动说成已经合并或实测成功。

一、先分清：测试通过、任务完成、回答正确

假设 Agent 回复：

已经为你创建工单。

仅凭这一句话，你不知道数据库中是否真的有工单，也不知道是否重复创建了两张，更不知道它的解释是否符合政策。

至少需要分开看三件事：

层次 要回答的问题 一个具体例子
程序与接口行为 代码是否按照约定工作 同一提交重试是否得到同一个 Run；错误参数是否被拒绝
业务后置条件 操作以后，业务事实是否满足要求 工单恰好新增一张，客户正确，审批要求得到满足
回答质量 回答是否正确、完整、被材料支持 没漏掉“定制商品除外”，引用确实支持当前结论

运行进入 SUCCEEDED，主要说明这段运行按协议完成；业务是否成功，还要有独立判据。同样，HTTP 200 只说明接口按它的响应契约返回，不自动证明正文正确。AgentHub 的执行、业务评价和语义评价也是分层组织的。评测教材 · 运行与评价边界

“测试”和“评测”在实践中会交叉，但可以先这样理解：

  • 工程测试：验证明确契约，例如复合外键拒绝错误配对、重复领取不会获得两份执行权。
  • 效果评测：比较一批任务上的正确性、证据完整性、拒答、延迟与成本。
  • 实际验收：沿真实入口检查用户能不能完成目标，例如页面能否自动看到后台任务的最终状态。

对应的证据不能互相替代。模拟模型能帮助检查任务编排；真实模型实验才能观察模型在这些任务上的行为；浏览器中的真实状态更新，又需要检查页面与 API 的衔接。

二、一条固定任务，应该固定哪些内容？

2.1 只有一句问题，还不够

例如，测试问题是：

定制商品购买第三天，可以按七天无理由规则退货吗？

如果知识库每天在变、Memory 中保存了前一轮的答案、两个方案用了不同的用户权限，那么这两次回答就很难直接比较。

一条可解释的任务，应当至少包含：

内容 作用
input 让被测 Agent 看到什么任务
初始环境 使用哪个工作区、用户、文档修订、Memory 和业务数据
expected 独立的正确性判据，包括应做、禁止做、应回答或应澄清的内容
数据分组 这条任务可以用于开发，还是留作独立验收
身份与版本 后续能确认执行的到底是哪份任务和环境

假设教学夹具 returns-policy-v1 明确规定“一般适用七天规则，但定制商品除外”。下面是教学结构，不是直接提交给 AgentHub API 的请求体：

{
  "case_id": "returns-01",
  "split": "DEV",
  "fixture": "returns-policy-v1",
  "input": "定制商品购买第三天，可以按七天无理由规则退货吗？",
  "expected": {
    "answerability": "ANSWERABLE",
    "required_claims": ["定制商品不适用该无理由退货规则"],
    "required_evidence_groups": [
      ["general-seven-day-rule"],
      ["custom-product-exception"]
    ],
    "forbidden_actions": ["issue_refund"]
  }
}

这里的 expected 交给评价程序或审阅者，不能作为参考答案偷偷塞给被测模型。本题只询问政策，因此也不能把“自动发起退款”当成热心加分项。

required_evidence_groups 表达的是：需要一般规则与例外条件共同支持判断。若一个事实允许由多个等价来源支持，可以在同一组中列出备选来源；组内满足一种即可，组间需要同时满足。真实标注不必硬凑两段：如果一段已经包含完整规则与例外，它可以同时覆盖两组事实。

比较不同分块策略时，还要注意：Chunk ID 可能随分块方式改变。金标应尽量定位到原始修订、原文区间或事实要求，再映射到各方案的 Chunk。直接拿旧 Chunk ID 作为所有新策略的唯一答案，会把身份变化误判为召回失败。

2.2 为什么要区分 DEV 和 HOLDOUT？

DEV 可以理解为开发练习题，HOLDOUT 是提前留出的验收题。

你在 DEV 上查看错误、改提示词、调分块和预算，这是正常开发。一旦反复看某组题的答案并据此调整方案，这组题仍有回归价值，但已经不能继续充当“完全没参与开发的独立证据”。

AgentHub 已有发布数据版本、DEV/HOLDOUT 分组，以及 HOLDOUT 参考答案的后端投影与权限边界。当前运行中的曝光编号，也不能简单解释为“查看答案页面的次数”：相关持久 exposure_index 在创建 HOLDOUT 实验运行时更新。数据集服务 · 实验服务

一个适合学习的小规模方案可以是：先准备 12 条 DEV、8 条 HOLDOUT。这个数量只是练习建议，足以练流程，不足以证明项目在所有真实任务上的准确率。

分组还应注意相关性：同一份政策的多个近似问法，不宜随意散到开发集与验收集后，就宣称完全独立。可以按源文档、业务场景或任务族分组，减少“换一句话的同一道题”造成的乐观判断。

2.3 固定数据，还需要固定实验条件

需要记录的条件包括：

  • 发布的数据版本及其内容、schema 身份。
  • 每个方案各自的 AgentVersion、提示词、工具和执行配置。
  • 文档修订、知识快照、Wiki 发布身份，以及 Memory 初始状态或明确关闭策略。
  • Embedding、重排和生成模型的可识别版本，候选数量、预算等参数。
  • 重复次数、执行顺序、超时与重试规则。
  • 评价程序和人工判据的版本。
  • 费用使用的价格快照，以及运行代码的提交。

这些记录让别人知道“比较条件是什么”，并不承诺外部模型每次逐字返回相同内容。即使温度设为 0，服务端模型更新、推理实现和环境差异仍可能影响复现。

如果 A、B 的提示词不同，它们的规格身份本来就应该不同。控制变量的意思是“清楚指出两者只在哪些方面不同”，不是强行让不同方案共用一个版本号。AgentHub 已冻结数据版本、变体规格、有效知识与 Wiki 身份、评分和价格等信息；上面的清单还包含实验者应额外控制的初始环境、Memory 和执行顺序，不能仅凭 finalize 就认为全部外部状态都已复制冻结。实验冻结实现

三、评测指标：从问题出发选，不要先追求一个总分

3.1 业务成功：看实际产生的结果

如果任务是创建工单，可以检查：

  • 目标工作区和客户是否正确。
  • 是否恰好新增一张符合要求的工单。
  • 需要审批时是否按规则得到许可。
  • 没有发生禁止动作或重复副作用。

每条 case 应从隔离、可重复的初始状态开始。否则 A 先创建了一张工单，B 执行时读取到 A 的产物，就失去了公平的起点。外部动作最好使用可控的测试业务环境；不能只在最终答案里搜索“已创建”三个字。

3.2 检索命中、证据完整、回答正确，是连续但不同的检查

对于前面的退货例子：

阶段 检查什么 可能出现的错误
候选召回 有用的材料是否进入候选 同义表达没有命中
重排与选择 有用材料是否保留在前面的结果 例外条款被低排或挤掉
上下文交付 必要依据是否实际进入最终模型请求 工具返回了例外，但预算投影把它删了
回答 模型是否按照完整材料作答 已看到例外，仍错误肯定回答

可以把一个简单的检索 Recall 写为：

[ \operatorname{Recall@k} =\frac{\text{前 k 项命中的相关证据单元数}}{\text{金标相关证据单元数}} ]

关键是先定义“证据单元”指文档、段落、事实还是某种来源配对。不同单位的 Recall 不能直接混着比较。分子应按该单位去重，不能靠重复返回同一来源多次得分。没有金标相关单元时，这个 Recall 不适用，应按预定的不可答判据评价，不能计算 0/0。

假设本题确实需要 A、B 两项依据，最终只交付 A，那么 Recall 可以是 1/2，但对这道题而言，完整回答依据仍然不齐。因此，还应记录“是否至少覆盖一套足以回答的完整依据”，并在最终模型请求处再次检查。

MRR 关注第一个相关结果排得多靠前，也可能因为 A 排第一而得高分，却看不见 B 缺失。这些指标各有用途，不能自动代替最终回答评价。检索与证据计分实例

3.3 回答评价：正确、拒答、澄清都可能是成功

建议至少区分三类题：

类别 正确行为
材料可回答 给出受支持的结论，保留条件、数字和例外
材料不可回答 说明资料不足，不补造缺失事实
问题有歧义 澄清关键条件，或明确列出适用分支

引用还需要分成两个检查：身份是否合法，以及引文是否支持这句话。引用了正确文档，也可能读错数值或遗漏否定。

词面相似度只能提供辅助信号。一个教学反例是：

参考：You may not create the ticket without approval.
错答：You may create the ticket without approval.

去掉 not，业务含义反了。但按仓库英文 token F1 的标准化方式，这对文本仍有约 92.31% 的 F1。该实现还按空白切词，不能直接当作可靠的中文语义评分器。词面评分实现

因此，数值、否定、适用条件、时间、引用支持，应有明确判据；规则适合检查可确定的条件，模型评审与人工抽检可以补语义判断。模型评审本身也会错，需要保留原输出、理由与抽样复核，不能把另一个模型的分数当成不可质疑的真值。

3.4 失败怎样进入分母？

看一个教学例子：10 次已经发起的任务，8 次返回了可评价输出，其中 6 次正确；另外 2 次发生服务错误。

  • 面向全部发起任务的“确认成功率”：6/10。
  • 在返回可评价输出条件下的正确率：6/8。
  • 服务错误：2/10，单独报告。

第二个数字可以帮助分析模型，但不能隐藏那两次服务错误。语义尚未判定、外部写入结果未知、费用缺凭据，也应分别保留，不能统一填成 0 或直接删除。

若任务本来要求拒绝某个操作，那么正确拒绝可以是成功；如果评测夹具的权限配置错了导致任务根本无法开始，应记录夹具或基础设施问题。分类依据要在运行前说明，而不是看到成绩以后调整分母。

3.5 延迟与成本，也要对应用户实际经历

延迟可以分别记录：排队、检索、模型首个文字、总完成时间。SSE 收到第一条“任务已受理”事件，不等于模型已经输出首个 token。p50、p95 也应说明样本数量、超时处理、冷启动与并发条件；只统计快且成功的请求，会遗漏用户遇到的等待。

成本要涵盖生成、重试、fallback 和辅助模型等实际调用。若供应商的总输入 token 已包含缓存命中部分，计算时应先拆出非缓存输入，避免重复计费；具体仍按该供应商的 usage 定义和冻结价格解释。

一个可用于业务比较的教学指标是：

[ \text{每次确认成功的平均投入} =\frac{\text{所有任务的已记录总成本}}{\text{确认成功的任务数}}. ]

分子包含失败任务的投入。若存在未知费用，就只能报告已知部分、缺失范围或估计，不能称为完整账单；成功次数为 0 时，该比值也没有可用的有限结果。

注意实际指标名。AgentHub 中 cost_per_successful_execution_<currency> 与 effective_task_cost_<currency> 的计算口径不同：前者关注成功且费用已知的执行费用均值；后者才把已知总投入与业务成功次数联系起来，并保留成本是否完整的标记。读指标实现比凭名字理解更可靠。指标聚合实现 · 业务成本指标

四、对照实验：怎样知道改动有没有用？

4.1 先建立基线，再改变一个明确机制

例如，这次只研究“结构分块是否改善政策问答”。那么应尽量保持语料、题目、生成模型、评价标准和其他策略一致，并记录分块改变带来的块数、预算和成本变化。

如果同时换模型、改提示词、扩大候选数量、调整评审规则，即使总分提高，也很难说清哪个改动起作用。多个变化确有必要时，可以先把它们当一个方案包，再通过消融解释各机制的贡献；这与每次无限叠加新技术不同。

4.2 成对比较：同一道题看进步，也看退步

下面仍是教学数字：

同一批 10 道题 数量
A、B 都通过 5
A 失败、B 通过 2
A 通过、B 失败 1
A、B 都失败 2

A 是 6/10，B 是 7/10。B 净增加 1 题，但它同时损失了原本通过的 1 题。如果损失的是关键业务场景，平均分提高未必足以支持发布。

成对比较需要保留具体题号、原输出、判分和变化原因。为了减小时间、负载或缓存差异的影响，可以预先安排 A/B 与 B/A 交替执行，并记录冷、热状态；这属于离线受控比较，与线上用户随机分流的 A/B 实验要分开描述。

4.3 重复次数增加，不等于独立题目增加

20 道题、2 个方案、每个方案每题重复 2 次：

[ 20\times2\times2=80\text{ 次 case execution} ]

这里仍然只有 20 道不同的题；它们是否相互独立，还取决于是否共享同一政策、源文档或任务模板。重复执行帮助观察同一道题的波动，不增加独立问题的数量；每个 Agent 执行又可能多轮调用模型，因此 80 次 case execution 也不等于 80 次供应商请求。

4.4 开始前写停止条件

一个有限的练习可以规定：先在 DEV 上完成预定两种策略的比较，修复明确实现错误后锁定候选，再进行一次事先约定的 HOLDOUT 验收。没有达到门槛就保留原默认，并记录为什么没有采用。

门槛应包括目标指标、关键退步条件、成本或延迟预算。没有收益、出现退步、证据不足，都是可以交付的结论。反复调整同一批已曝光问题，直到分数变漂亮，会让成绩越来越难解释。

五、用仓库里的两组真实结果理解指标

5.1 候选召回提高，完整依据反而下降

SciFact 的同一批 553 道题中，固定候选数量的 BM25 补位得到：

指标 原双路 RRF BM25 补位
候选命中的题目–来源对 539/625 547/625

为什么会这样？因为“同一来源的靠后重复块”有时恰好包含必要依据。为了引入新来源把它移除，相关论文还在，完整证据却丢了。

这组结果说明：需要逐阶段定位损失，不能只看到候选召回提高就换默认。报告使用已多次曝光的 TRAIN 分区，终点是原文块，不直接证明最终回答效果。原始报告

5.2 HTTP 一次成功，内部可能已经调用两次模型

因此，可以说“这组题在包含纠正机制的产品入口上全部通过”，同时必须说明它使用了额外模型调用。题目已在前轮使用、每题每臂仅运行一次，又只来自两张表，不能直接写成全库准确率 100%。表格问答报告

这两组例子对应同一种能力：先问数字评价的是哪一层、分母是什么，再问它能支持什么结论。

六、回到源码：AgentHub 怎样把一份评测计划跑起来？

前面讲的是方法，现在看工程实现。可以把评测平台理解为：为一批有固定身份的任务安排执行，保存原始观察，再按固定规则评价。

6.1 数据库为什么要拆成这些对象？

项目对象 实际表名 一行代表什么
Dataset evaluation_datasets 一套逻辑题库，例如“客服退货问答”
DatasetVersion evaluation_dataset_versions 题库的某个具体草稿或发布版本
DatasetItem evaluation_dataset_items 该版本中的一道题及其 input、expected、split
Experiment evaluation_experiments 一份比较计划：数据、分组、重复次数、评分和构建身份
Variant evaluation_experiment_variants 计划中的一个被比较方案，绑定发布 AgentVersion 等身份
ExperimentRun evaluation_experiment_runs 按这份计划发起的一次批量执行
CaseResult evaluation_experiment_case_results 某题、某方案、某次重复的执行观察

这与前面学习的 Agent、AgentVersion、AgentRun 是相同的建模思路：逻辑身份、冻结定义、一次执行、执行结果，分别保存。

同一个 Dataset 可以有多个版本，因此只报 dataset_id 无法说明题目有没有变化。同一个 Experiment 也可以发起多次批量执行。CaseResult 通过题目、变体和重复序号定位一项具体执行，不能把整批任务都塞进一个状态字段。评测模型

6.2 发布数据、冻结实验、开始执行，是三个不同动作

数据集服务创建版本时验证题目结构，发布时重新核对内容身份，并将版本推进为 PUBLISHED。修改题目或参考答案，应建立新版本，而不是直接修改旧发布行再沿用旧 hash。

实验服务只接受已发布数据，增加各个 Variant；finalize_experiment() 固定实验规格，推进为 READY。READY 表示计划可以执行，不表示题目已经跑完。

随后 create_run() 建立 QUEUED 的 ExperimentRun，API 才把运行 ID 交给队列。Worker 再读取这份持久计划。公开服务合同中的“发布后不可修改”，也不要扩大成“数据库管理员绝对无法直接改行”的保证。数据集发布 · 实验冻结与运行创建

6.3 从 API 找到函数，再找到数据库记录

当前评测路由的公共前缀是：

/api/v1/workspaces/{workspace_id}/evaluation

第一次读源码，可以先追下面几个入口：

操作 前缀后的实际入口 主要实现
发布题库版本 POST /datasets/{dataset_id}/versions/{version_id}/publish EvaluationDatasetService.publish_version
冻结实验 POST /experiments/{experiment_id}/finalize ExperimentService.finalize_experiment
发起批量运行 POST /experiments/{experiment_id}/runs create_run，随后入队
查看进度 GET /experiment-runs/{run_id}/progress 读取持久执行进度

最后两个接口需要特别区分。Runner 执行完成，并不代表指标快照已经自动生成。当前物化操作要求批量运行及单题都已终态，实际 CaseResult 集合与冻结计划匹配，再按冻结的评分版本生成结果。普通 GET 不应悄悄用今天的新评分器改写历史实验。评测 API · 指标物化

6.4 Worker 为什么仍需要领取和租约？

队列可能重复投递，Worker 也可能中途退出。因此 Runner 大致要完成四件事：

  1. 准备题目执行记录。按题目 × Variant × 重复次数建立 PENDING CaseResult；唯一身份防止重复投递生成第二套执行记录。
  2. 领取运行与题目。检查 owner、租约和 generation；领取题目时使用数据库行锁与 skip_locked 跳过已被事务锁定的行。这是领取冲突的处理机制；同一批量运行仍受当前 owner/generation 控制，不能仅凭这个参数就宣称已经实现多 Worker 并行执行同一个 Run。
  3. 先绑定，再执行。真实 Runtime 路径先准备 AgentRun，并把身份保存到 CaseResult，然后进入实际执行，便于崩溃后对账。纯 RETRIEVAL 路径可以直接检索，不一定建立 AgentRun。
  4. 保存观察、失败和恢复结果。写回检查当前执行身份；恢复时查旧 AgentRun 的事实，不能在外部副作用未知时盲目重跑。

这里与第七阶段相通：队列消息提示“有工作”，数据库记录说明“谁可以做、做到了哪里、结果是否确定”。skip_locked 没有领到某一行，也不代表整批任务已经完成。Runner · 评测 Worker

6.5 一个非常重要的源码细节：默认 Runner 可以是模拟执行

ExperimentRunner 默认使用 DeterministicEvaluationDriver。这个执行器可以从 item.expected 构造受控观察，用于验证编排、持久化和评分契约。

因此，你直接跑一个使用它的 benchmark，看到“通过率 100%”，首先应问：

这份观察来自真实模型和工具，还是来自测试夹具？

生产 Worker 会显式构造 Runtime driver，并通过路由选择对应执行器；AgentRuntimeEvaluationDriver 从 item.input 形成被测任务，expected 仍可合法用于实验控制和判分，但不能泄漏成模型应该输出的答案。

实际使用了哪个 driver、是否有真实执行关联、观察与用量来自哪里，必须一起核对。单独写了 REAL_PROVIDER 标签，也不是已经调用供应商的充分证据。模拟与 Runtime 执行器 · 生产装配

6.6 这几个“成功”和“不可用”，怎样区分？

字段或结果 含义
CaseResult / ExperimentRun 的 SUCCEEDED 评测执行按其协议完成，取得了观察
observed_agent_status 被测 Agent 的运行终态
task_success、业务成功指标 按各自判据评价任务
Metric 的 AVAILABLE / NOT_AVAILABLE / NOT_APPLICABLE 这个指标是否有足够适用证据可以计算
Gate 的 PASS / FAIL / INCONCLUSIVE 是否满足发布比较规则，或证据不足无法判定

例如，某个故障用例就是要检查 Agent 遇到特定问题后会正确失败。此时观察到预期失败，评测任务可以成功。反过来，Agent 正常结束但答错了，质量指标仍然失败。

当前普通 task_success 会先汇总同题的可用重复，再汇总题目；business_task_success_rate 的 v2 则用业务成功数除以全部 case execution，并记录未知数量。普通延迟 p95 也先计算每题重复的平均延迟，再求题间分位数。把看板上的指标导出时，要把聚合单位和缺失情况一起带走。指标与聚合 · 业务观察指标

发布门禁也是按已有规则判断。必需证据缺失应保留未决；可选指标没有测到，不一定阻断整体 PASS，所以整体通过不能解释为每个可选维度都已经验证。门禁实现

6.7 实际打开页面后，怎样追一条评测证据？

从实验详情页点击启动，startRun 调用前端 startExperimentRun，后端创建批量运行并入队；前端取得 ID 后进入 /evaluations/runs/{runId}。当前评测运行页在可见、运行未终态时按 2.5 秒间隔读取运行状态，进度查询还有自己的状态条件；这条页面链采用轮询。实验页面 · 评测运行页面

七、独立修改：怎样把一个现象变成能动手的任务？

“独立”不要求你背出所有函数，也不要求从空文件写完整系统。它要求你能亲自决定改动边界，理解调用关系，验证结果，并解释为什么这么改。文档、搜索和 AI 都可以帮助定位；最终的判断需要你能复述和核查。

7.1 先写清楚问题，而不是先决定用什么框架

问题陈述可以是：

上传文档后，列表会更新，但用户展开的修订详情可能停留在旧阶段。希望用户保持详情展开时，能够自动看到 Job 与 Revision 的最新结果。

这句话已经包含用户动作、可观察现象和期望结果。接下来可以形成最小验收：

  • 详情展开且任务进行中时会继续读取状态。
  • 成功或失败后显示最终事实，停止无效自动刷新。
  • 切换文档或工作区后，不显示旧资源的迟到响应。
  • 查询暂时失败时有明确提示和有限重试，手动重试仍可用。

这里不需要先更换全站状态管理库，也不需要把所有轮询统一改成 WebSocket。先把这个现象的实际原因查清楚。

7.2 怎样复现并定位哪一层有问题？

打开浏览器开发者工具的 Network，保留详情展开，然后同时观察：

观察结果 优先检查
没有发出详情请求 页面刷新条件、计时器与 effect
请求持续发出，但响应一直是旧状态 详情 API 的查询、事务可见性、后台任务进度
响应已更新，页面仍旧 前端状态写入、渲染字段、旧响应覆盖
数据库的 Job 本身不再推进 Worker、队列、租约与实际执行失败

这一步的目的，是先证明“该改页面刷新”这个判断成立。不能看到转圈就一律改提示词，也不能看到状态旧就一律缩短轮询间隔。

7.3 本项目的真实问题，定位到哪里？

当前页面是：

apps/web/app/knowledge/[knowledgeBaseId]/knowledge-detail-client.tsx

页面已有 5 秒轮询，但调用的是 documents.reload()。展开的修订详情由另一份 useWorkspaceData 查询维护；文档列表更新，不会自动替这份查询重新发请求。

详情的实际链路如下：

位置 输入与输出
展开按钮 设置 selectedDocumentId

7.4 决定何时继续读取之前，先读懂状态

字段 活动状态 成功状态 失败状态
revision.ingestion_status PENDING / PROCESSING READY FAILED
ingestion_job.status PENDING / PROCESSING SUCCEEDED FAILED

另外还有 revision.lifecycle_status 的 ACTIVE / RETIRED / DELETED，以及 Job 的 PARSING / CHUNKING / EMBEDDING / INDEXING 阶段。生命周期、摄取状态和阶段是三个维度。成功后阶段仍可能是 INDEXING，不能自己发明一个 DONE 阶段来判断完成。知识模型与枚举

还有两类错误必须分开：

  • 详情 GET 失败：这次读取没成功，不知道后台最新情况。
  • GET 成功，Job 报告失败或重试信息：已经读到了后台事实，按它的状态处理。

后台准备自动重试时，Job 可以是 PENDING，同时保留 safe_error_message。因此，“出现错误文字”不能直接成为停止前端观察的条件。入库重试逻辑

7.5 为什么不能只加一句 revisions.reload()？

最容易想到的办法是：在原来的列表轮询里顺手刷新详情。

但原列表轮询受“列表是否仍有活动任务”控制。如果列表先读到 READY，计时器停止，而详情还停在 PROCESSING，它仍可能错过最后一次读取。

更清楚的做法是：详情根据自己的结果决定是否继续观察。已有详情请求还在加载时，不安排下一次；读取完成后，再决定等待、停止或退避。

图中“停止观察”只表示不继续自动读取，不表示后台任务一定成功。切换资源还需要取消旧计时器，并依靠查询身份防止旧响应写入新面板。

7.6 一段接近实际改动的示意

下面是待实施的教学示意，沿用现有页面的查询对象和变量；它不是已经合并、已经浏览器验收过的补丁。页面还需要接入对应提示和操作后的刷新入口。新增的 Hook 应放在组件顶层、现有条件返回之前，不能只在“当前已展开”分支内调用。

先把“是否有活动详情”写成一个可解释条件：

function isActiveDetail(entry: DocumentRevisionStatus): boolean {
  return entry.revision.lifecycle_status !== "DELETED" && (
    INGESTION_ACTIVE_STATUSES.has(entry.revision.ingestion_status) ||
    INGESTION_ACTIVE_STATUSES.has(entry.ingestion_job.status)
  );
}

页面现有的 INGESTION_ACTIVE_STATUSES 是 PENDING / PROCESSING。同时看 Revision 与 Job，可以避免只依赖列表的简化投影。

再安排一次性读取，而不是每隔五秒无条件叠一个请求：

const detailKey = `${sessionId}:${scope}:${selectedDocumentId ?? ""}`;
const reloadRevisions = revisions.reload;
const failure = useRef({ key: detailKey, error: revisions.error, count: 0 });
const [pollMode, setPollMode] = useState("idle");

function retryRevisions() {
  failure.current = { key: detailKey, error: null, count: 0 };
  reloadRevisions(); // 返回 void；请求完成由 query 状态反映
}

useEffect(() => {
  if (failure.current.key !== detailKey) {
    failure.current = { key: detailKey, error: null, count: 0 };
    setPollMode("idle");
    return; // 等待查询切换身份，避免使用上一资源的状态
  }
  if (!connected || tab !== "documents" || !selectedDocumentId || revisions.loading) return;

  const error = revisions.error;
  let delay = INGESTION_POLL_MS;
  if (error) {
    if (failure.current.error !== error) {
      failure.current.error = error;
      failure.current.count += 1;
    }
    const transient = error.status === 0 || error.status === 408 ||
      error.status === 429 || error.status >= 500;
    if (!transient || failure.current.count > 3) {
      setPollMode("paused");
      return;
    }
    delay *= 2 ** (failure.current.count - 1); // 5、10、20 秒
    setPollMode("backoff");
  } else {
    if (!revisions.loaded) return;
    failure.current = { key: detailKey, error: null, count: 0 };
    if (!(revisions.data ?? []).some(isActiveDetail)) {
      setPollMode("idle");
      reloadDocuments(); // 详情终态或空结果后核对列表
      return;
    }
    setPollMode("watching");
  }

  let timer: number | undefined;
  const clear = () => { window.clearTimeout(timer); timer = undefined; };
  const arm = () => {
    if (!document.hidden && timer === undefined) {
      timer = window.setTimeout(() => {
        timer = undefined;
        reloadRevisions();
      }, delay);
    }
  };
  const onVisibility = () => { clear(); arm(); };
  arm();
  document.addEventListener("visibilitychange", onVisibility);
  return () => {
    clear();
    document.removeEventListener("visibilitychange", onVisibility);
  };
}, [connected, tab, selectedDocumentId, detailKey, revisions.loading,
    revisions.loaded, revisions.error, revisions.data, reloadRevisions, reloadDocuments]);

不必一下背下所有行，先理解几个设计原因：

  1. 资源身份包含会话、工作区范围和文档。切换资源后，旧错误次数不能继续限制新资源。
  2. 先检查 loading。请求尚未结束时可能仍保留旧 data，不能把旧结果当作本次读取已经成功。
  3. 每个新错误只计一次。普通重新渲染不能把同一次失败反复累加。
  4. 一次性 setTimeout 等当前请求结束再安排。自动观察期间避免慢请求叠加。
  5. 错误后退避且有上限。5、10、20 秒是这份教学设计，第四次连续失败后暂停；若实际接口有重试提示，还应按契约处理。
  6. 手动重试清计数。用户恢复网络后，可以重新开始观察，而不一直受旧错误预算限制。

pollMode 适合用来显示“自动观察中”“稍后重试”“自动刷新已暂停”等状态；watching 主要包含等待下一次请求的时间，真正请求进行中应看 revisions.loading。落地时应使用项目已有的本地化方式，并保留原来的错误信息。

7.7 两个很容易写错的异步细节

第一，reload() 不是一个等待网络完成的 Promise。

当前 useWorkspaceData.reload 返回 void，只是推进刷新 token，由 hook 的 effect 发请求。因此不能写 await revisions.reload()，然后认为下面一行已经拿到新结果。完成与失败要通过 loading / loaded / data / error 判断。数据查询 hook

第二，清定时器不等于取消已发出的 HTTP。

clearTimeout 阻止尚未触发的下一次读取。当前 hook 通过 session、resource key 和 generation 检查迟到响应是否仍属于当前查询，但这条详情读取路径没有传递 AbortSignal。A→B→A 时，也需要 generation 防止第一次 A 的结果覆盖第二次 A。

这次练习应复用现有查询的身份检查，自己只控制何时触发读取。若以后要支持离开页面即中止网络请求，应再设计 signal 的完整传递与取消语义，不能在本次完成说明里提前声称已经做到。数据查询 hook · 详情请求签名

7.8 还需要补哪些用户动作？

只写定时器，还没有接完整：

动作 应更新什么
详情错误后的“重试” 清详情读取失败计数，再刷新详情
人工重试摄取成功 清详情读取失败计数，列表与详情都刷新，让详情重新观察活动状态
上传新修订成功 清详情读取失败计数，详情与列表都刷新，显示新版本及其状态
详情读到终态 停止详情轮询，并核对列表投影
收起、切页或换工作区 清旧计时器，等待新资源的查询身份

轮询本身只发 GET。它不能自动调用摄取重试的 POST，更不能重新上传文件来模拟刷新。

还有一个真实接口边界：当前 list_revisions() 直接查询关联记录，文档物理移除后可能返回 200 与空数组。空数组也可能只是当前没有可返回的修订，不能单独据此宣布“文档已删除”。只有当前范围满足 documents.loaded && !documents.loading && !documents.error，并在这份成功结果中确认所选 ID 不存在，才适合清除选择；查询失败时的 data ?? [] 不是权威空列表。知识服务

八、这项修改怎样验收，才算真的完成？

验收应对应前面定义的行为。可以在本地使用受控接口响应或浏览器请求拦截，按照实际 API 字段构造下面的序列，先验证页面逻辑；不需要为了检验一个计时器反复调用模型。

场景 操作或受控输入 应观察到的结果
正常推进与查询先后不同 详情从 PENDING 到 PROCESSING，最终 Revision=READY、Job=SUCCEEDED；列表先到 READY；其中一次读取超过 5 秒 详情仍能读到最终状态；自动请求不叠加；终态后停止
任务重试和失败 Job 为 PENDING 且带错误文字，后来 Revision 与 Job 均为 FAILED；再人工重试 错误文字不误停活动任务；FAILED 可见；人工重试后恢复观察
读取失败 连续 503 四次，再恢复；另检查 403 错误可见、退避、暂停、手动恢复；权限错误不无限循环
页面生命周期 收起详情、换标签、隐藏浏览器、离开页面 不再安排旧面板的后续读取；恢复时没有重复计时器
迟到响应 A→B→A，旧 A 最后返回；再切工作区 旧结果不覆盖新资源，错误次数不串资源
空结果与删除 分别返回 lifecycle=DELETED、空数组；列表仍存在、确认不存在或读取失败 DELETED 项不推动详情轮询；空、删除、读取失败分别呈现，不因 null 数据误判删除

以上属于前端行为验收。它能证明这些受控响应下页面如何收敛，不能直接证明真实解析、Embedding、队列和 Worker 全部正常。若要写“真实上传链路已验收”，还需要另走一次真实入口，并记录对应 Revision/Job。

完成代码后，先看改动是否仍集中在这个问题，再执行针对性的验证与仓库要求的门禁。在已安装项目依赖的仓库中，现有前端脚本包括：

npm --prefix apps/web run test:regression
npm --prefix apps/web run build

这两条是供你实施练习时使用的命令，本节没有执行。回归脚本和构建通过，可以支持相应契约或构建结论，仍然不能替代上表中的浏览器观察。也不需要因为改了一处页面，就无目的地重跑所有模型实验。前端脚本配置

九、怎样把修改结果写成别人能审核的说明？

建议固定用以下结构：

修改原因

写可复现现象，例如：

文档列表已更新到 READY，但持续展开的修订详情仍显示 PROCESSING；详情查询没有自动刷新入口。

实现位置与行为变化

说明改了哪些函数或组件，为什么在那里改。例如：

在知识详情页为现有 revisions 查询增加独立观察调度，以详情返回的 Revision/Job 活动状态判断是否继续；保留现有查询身份检查，补上传和人工重试后的刷新。

验证结果

只写真正执行过的内容：代码提交、测试或走查方法、实际状态序列、通过和未通过的场景。没做的验收应写“未执行”，不要把本节提供的验收表直接改成“全部通过”。

局限

说明结果适用范围，例如：

受控响应验证了页面状态更新；真实上传链路另行验收。轮询展示的是读取时刻的状态，可能跳过很短的中间阶段；清计时器不会中止已发出的 HTTP。

局限应与已经做出的结论相连。对于这次改动，不需要把整个项目未来的所有缺口写进同一个 PR。

十、面试和情景推演：检验你是否真的掌握

1. 面试官问：“你怎么证明效果提升？”

可以按这个顺序回答：

先固定任务、参考判据和环境，为旧方案保留基线；明确候选只改变什么。逐题比较正确性与退步，另外记录失败、延迟和全部已知成本。开发数据用于查错，独立验收数据用于验证。结论同时写清样本、重复次数、真实执行范围与未知项。

随后拿你真正执行过的一项修改或实验展开，而不是只背指标名称。

2. “为什么需要 DatasetVersion，只有 dataset_id 不行吗？”

dataset_id 表示逻辑题库。版本决定具体 input、expected、split 和内容身份；题库名相同不代表题目相同。实验必须能够指向当时使用的那一版。

3. “模拟模型全部通过，是不是 Agent 已经可靠？”

模拟执行说明相应编排和契约在受控条件下工作；真实模型选择工具、读材料和形成回答，还需要真实执行与独立评价。还要看模拟观察是否直接从 expected 构造。

4. “召回提高了，为什么没有换默认？”

因为候选来源、完整依据、最终交付和回答效果不同。可以用本节 SciFact 例子说明：候选多找回来源，但替换掉的块可能包含关键依据，需要看逐题收益、退步和额外成本。

5. “为什么页面已经显示成功，还要回读详情？”

列表和详情是不同投影，更新时间不同。详情需要根据自己的结果收敛；页面显示的文案和后台权威记录也应区分。这个答案应能指向 documents 与 revisions 两份实际查询。

6. “一个调用超时了，能不能删掉后重跑，免得影响成绩？”

不能为了成绩删除。先保存超时事实，判断结果是否可确认、是否有外部副作用、是否已有费用；是否重试按预先规则和工具能力处理。后续诊断重跑也要保留与原运行的关系，不能悄悄替换原始结果。

7. “评测门禁 PASS，可以说生产可靠率达标了吗？”

只能说明满足这份门禁针对已提供证据的规则。可选指标可能缺证据，小样本、模拟环境与真实生产负载也有差异。应指出哪些规则检查了什么，再解释剩余验证范围。

十一、你这一阶段的实际学习任务

可以按三个递进练习完成：

练习 A：追一条已有评测结果。

从一次 ExperimentRun 找到数据版本、Variant、一个 CaseResult、对应执行证据和指标快照。写清楚“这条为什么通过或失败”，以及它属于模拟执行还是真实 Runtime。若还没有运行环境，可以先用本节源码入口完成纸面追踪，不把纸面结果当运行记录。

练习 B：独立完成 RT10。

先自己写问题、状态和验收，再读示意；实施后记录每个实际观察。做到能解释为什么需要详情独立刷新、为什么不能 await reload、为什么空结果不等于删除。

练习 C：完成一项有限的质量比较。

使用一小组固定 DEV/HOLDOUT 任务，比较一个明确的 Agent 或检索策略变化。提前固定预算、次数、判据和停止条件，记录进步、退步、未知和成本。若没有改善，就交付“不采用该候选”的证据与理由。

本阶段的通过标准是，你能拿出一份由自己核实的记录，清楚回答：

我为什么改了这里，实际改了什么，哪些证据证明它解决了什么问题，以及哪些问题仍然没有被证明解决。
