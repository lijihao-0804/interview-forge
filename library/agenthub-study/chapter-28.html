面试问答 B：模型网关、异步可靠性、审批与外部执行（RT01–RT50）

RT01—RT50：模型网关、异步可靠性、审批与外部执行

RT01｜为什么已经用了 LiteLLM，还要再写一层模型网关？

回答：LiteLLM 负责不同 Provider 的消息格式、Tool Calling 和流式 API 适配；AgentHub 的 ModelGatewayService 在其外面实现工作区模型路由、Profile 能力校验、凭据与出站策略、Retry/Fallback、逐次 Trace 和 Run 费用账本。调用者只提供 ModelRequest，网关解析冻结执行计划再对接 Provider。这样切换模型供应商时，业务层的预算、错误分类与事件合同保持一致，模型 SDK 的异常被归一化为平台错误。

追问：SDK 和外层网关都允许三次尝试，可能发出多少次实际请求？

追问回答：如果两层的 max_attempts 都包含首次，且每次外层尝试都触发三次 SDK 尝试，理论最多 3×3=9 次；有多个 fallback Profile 时还会乘上链长度。AgentHub 在 LiteLLM Adapter 传 num_retries=0，统一由网关管理尝试，避免重复重试层和失控账单。

源码定位： 网关 · adapter

RT02｜重试与 fallback 的区别是什么？它们分别应该在哪里实现？

回答：Retry 是对同一个 ModelProfile 重新发送请求，Fallback 是在某个 Profile 达到失败条件后转向链上的下一个 Profile。AgentHub 的 gateway.py 先解析模型链，对每个档案执行受控尝试，再按错误码决定留在当前档案、进入后备档案或结束。每次尝试都有独立的费用预占、回执和 Trace；因此最终生成一次答案，记录中可能有多个供应商 Attempt。

追问：当前网关是否已经为每个错误实现统一指数退避？

追问回答：现有循环主要按错误种类和尝试次数控制，没有通用指数退避。新增时应为可重试错误设置带抖动的退避、上限和总 Deadline，并使取消能即时打断等待；结合 429 的 Retry-After、每次预算预留和模型链长度，控制端到端尾延迟。

源码定位： 源码

RT03｜为什么不对所有异常无条件重试？

回答：有些失败来自临时网络或供应商容量，例如超时、503；另一些来自配置或请求本身，例如身份错误、参数不支持、上下文超窗、目标被出站策略拒绝。后者反复发送同一请求只会重复失败并产生额外开销。ModelGatewayService 将异常归一化为错误码，在单档案重试与外层 Fallback 两个层次分别判断；安全拒绝和协议错误应沿明确策略处理。

追问：当前档案不可重试，是否意味着整条 Fallback 链也要停止？

追问回答：两层判定分开：有的错误意味着当前档案不再重试，但链中的另一兼容 Profile 可以承接；请求结构或策略本身不成立时，切换模型也没有意义。排查时看 _generate_chain() 对具体 ModelGatewayErrorCode 的处理，以及新 Profile 能否满足同一 CapabilityRequirements。

源码定位： 网关 · 动作执行

RT04｜为什么流式输出已有内容之后不能无感切换备用模型？

回答：流式生成可能已经向用户发送 MESSAGE_DELTA 或 TOOL_CALL_DELTA，这些增量组成一条具体模型回复。若 A 输出半句后切换 B，B 并不知道 A 的内部采样状态，直接拼接会形成无效答案或重复 ToolCall。AgentHub 在无外显输出时允许按策略 Retry/Fallback；一旦有外显增量，流中断以 MODEL_STREAM_INTERRUPTED 呈现，由 Runtime 保存已经观察到的事件和失败状态。

追问：流式中断前已经收到 usage，账单怎么处理？

追问回答：把调用是否产生可用输出与费用回执分别存储。供应商返回的 prompt_tokens、completion_tokens、cached_tokens 仍进入此次 Attempt 的用量记录；缺少回执时按预算账本的 UNKNOWN 语义处理。用户看到流中断，并不抹掉已计算过的 Token 和相应费用。

源码定位： 源码

RT05｜HTTP 200、模型可用输出、Agent 成功、业务成功之间有什么区别？

回答：HTTP 200 表示传输层成功返回；模型可用输出要求内容或工具调用满足本次请求结构和 Provider 协议；AgentRun SUCCEEDED 表示 Runtime 按执行合同到达成功终态；业务成功由后置条件核验，例如工单确实新增、订单金额正确，或 RAG 答案受到证据支持。AgentHub 评测把 observed_agent_status 与 task_success 分开，就是防止绿色执行状态掩盖业务错误。

追问：面试时说“成功率 90%”，需要先定义哪些东西？

追问回答：定义分母是 HTTP 请求、模型 Attempt、AgentRun 还是业务任务；明确超时、未知结果和拒绝执行如何计入；说明成功判据是状态机还是业务后置条件，并给样本集与时间窗。对固定评测还应交代每题重复次数、题库版本和裁判规则。

源码定位： 网关 · 审批表 · 工单执行

RT06｜模型返回空答案，为什么不能记成 0 token、0 费用？

回答：模型可能处理了完整输入、生成了内部 Token，最后返回空 content 与空 tool_calls。AgentHub 的 Gateway 会把它识别为不可用的普通响应，按照规则尝试后续处理；已经取得的 Provider usage 仍写入对应 Attempt。对 content_filter、refusal 等明确安全返回，则保持原有语义。费用来自实际供应商处理，不由最终展示的字符串长度决定。

追问：Provider 返回了 usage，却缺少明确 cost 时怎么记录？

追问回答：保存原始用量和计费凭据完整性，把货币金额标记为待估算；若使用冻结价格表形成估算，单独记录价格版本、输入/输出、缓存计费与币种。模型成本统计可以同时展示“已知账单”和“估算值”，避免把空金额作为零费用参与比较。

源码定位： 源码 · 回归测试

RT07｜fallback 成功后，为什么不能只保存最后一个 response 的用量？

回答：Fallback 链会产生多次实际 Provider Attempt，主模型即使最终超时，也可能消耗输入和输出 Token。若只记录最后 B 的 usage，Run 总账会低估成本。AgentHub 的预算账本按每个尝试预占、结算或保留未知，再汇总逻辑生成的全部 Attempt；Trace 同时记录哪一轮属于 retry、哪一轮属于 fallback，支持排查成本突然升高的原因。

追问：一次逻辑调用先请求 A、再请求 B，两者都有用量回执，记录数是多少？

追问回答：逻辑生成调用 1 次，实际模型尝试 2 次，usage 回执 2 份。Run 层按两份回执汇总总 Token 与费用；用户界面可能只显示 B 的最终回答，但账本保留 A 的输入和失败事实。

源码定位： 源码

RT08｜冻结 AgentVersion 后，模型配置和密钥是不是再也不能变？

回答：AgentVersion 发布时固定 ModelProfile 的关键执行配置，包括模型标识、温度、最大输出、能力与 Fallback 计划。运行时仍要读取当前可用的 Provider Credential，并检查身份与出站目标；密钥轮换属于凭据管理，不要求重新写一份业务发布规格。冻结配置用于保证历史 Prompt 与模型策略有明确身份，连接凭据和外部服务健康则是运行时依赖。

追问：可以在旧 Run 中直接读取最新 Profile 替换已发布字段吗？

追问回答：应该从 Version 的冻结规格解析执行计划，当前 Profile 更新只能通过新的版本选择生效。否则温度、模型、能力或 Fallback 变化会让同一 Version 的历史含义漂移；密钥状态、吊销和目标网络规则则照常按当前安全配置检查。

源码定位： 源码

RT09｜为什么模型调用时不应该长时间占着 SQLAlchemy Session？

回答：Provider 调用可能持续几十秒，期间占用 SQLAlchemy Session 容易拖住连接池，尤其在事务中还持有行锁时，会阻塞审批、发布和状态查询。AgentHub 采用短事务读取工作区授权、创建模型 Attempt/预算预占，然后在不持有数据库事务的阶段请求 Provider，拿到回执再开启短事务结算。外部 HTTP 执行与本地数据库更新属于两个系统的独立操作。

追问：把 Provider HTTP 请求放在数据库事务内，失败后 rollback 能撤销费用吗？

追问回答：数据库 rollback 只撤销本地未提交写入，供应商已经处理的请求和计费不会回滚。正确流程是先保存稳定 Attempt 和预算身份、释放数据库连接、发请求，完成后按回执写结算；超时保留未知账单，按供应商记录核对。

源码定位： 源码

RT10｜如何避免 fallback 配置形成环？

回答：Fallback Profile 构成一张有向引用图，最直接错误是 A→A，隐蔽错误是 A→B→C→A。AgentHub 在模型路由解析服务中沿链遍历、记录已访问 Profile，并检查能力与凭据有效性，避免循环导致无限递归或无穷尝试。冻结发布规格会记录解析出的执行计划，运行时按既定链执行。

追问：前端禁用“选择自己为备用”是否足以避免环？

追问回答：服务端还要在 API 写入、发布解析和实际链解析阶段检查完整路径。可以构造 A→B→A 和三个节点环，验证返回稳定错误；并发编辑时依赖服务端最终状态校验，而不是浏览器表单里当前看到的选项。

源码定位： 源码

RT11｜模型能力检查为什么要与具体请求结合？

回答：模型能力应对应当前请求的实际要求：有 Tool Calling 就需要支持 tools；使用 JSON Schema 输出就需要相应结构化输出能力；流式执行还要求适配器能正确解析文本、ToolCall 增量和 usage。AgentHub 用 CapabilityRequirements 配合 ProfileResolver 过滤可用模型链，随后由 LiteLLM Adapter 根据 ModelRequest 生成供应商参数。能力检查把模型配置与执行合同联系起来，而不只是一张宣传能力表。

追问：Profile 填 supports_tools=true，怎样验证真实 Tool Calling？

追问回答：用受控供应商或实际目标模型请求携带两个 ToolSchema，检查返回的 tool_calls 名称、JSON 参数、call_id 以及流式增量合并逻辑；在不支持能力的路由上验证准确失败。配置声明用于计划选择，适配器回归验证协议正确性。

源码定位： 能力模块 · 网关准备

RT12｜一次模型调用超时 30 秒，是不是整个 Agent 最多 30 秒？

回答：ModelProfile 的 timeout_seconds 限制一次具体 Provider Attempt 的等待，不等于 AgentRun 的总耗时。一个 Run 可能经过多轮模型、ToolCall、RAG、Fallback 和审批；每一轮都可能具有单独超时。AgentHub 还通过运行配置控制模型轮数、预算和任务执行状态。分析用户端延迟时，要拆开排队、首字、模型总时长、工具执行以及人工等待。

追问：如果产品要求整个任务 120 秒内完成，怎样传播超时？

追问回答：在 Run 创建时记录绝对 deadline_at，每个模型/工具外呼取 min(单次上限, 剩余时间)，进入新节点前检查剩余额度，并为持久审批等待定义单独生命周期。Worker 重试和 Fallback 也使用同一剩余总时限，避免几个局部 30 秒累加超预算。

源码定位： 源码

RT13｜为什么金额要用 Decimal？还有哪些细节比类型更重要？

回答：货币计算用 Decimal 避免二进制浮点在费用累计、价格换算和阈值比较时产生微小误差。AgentHub 的 Run Budget Ledger 不只需要类型正确，还要保存币种、冻结价格身份、输入/输出/缓存 Token、每次 Attempt 的预留与实际回执。多次 Retry/Fallback 统一结算，UNKNOWN 费用占用安全余量；预算决策与财务统计由不同字段表达。

追问：真实 Provider 回执显示费用超过预算预留，怎样处理？

追问回答：先按真实回执金额入账，记录超出预留的差额与原因，再阻止新增超过余量的调用。不能把实际成本截成预算上限；需要检查估算器、价格表、隐藏推理 Token、缓存定价和错误尝试，以修正后续预算预占策略。

源码定位： 账本 · 安全 trace

RT14｜“预算上限”与“预计花费”为什么必须分开？

回答：预算上限是运行管理者允许消耗的资源边界，预计费用是根据模型价格、输入长度和输出上限计算出的执行前估算。AgentHub 在每次调用前做 Budget Reservation，拿到 Provider usage 后结算；调用失败但收费状态不明时保留 UNKNOWN。一次逻辑回答可能包含多个模型 Attempt，预算必须覆盖每个实际外呼而不是只看最终文本。

追问：已知输入 Token 和 max_tokens，是否一定能算出可靠货币上界？

追问回答：还需要明确计费口径、缓存输入单价、推理 Token 是否包含在输出额度内、服务商额外计费、Fallback 链以及完整价格版本。对无法给出上界的模型路由，应采用受控估算与预算保护策略，并明确超额后的阻断和对账流程。

源码定位： 账本 · 适配器

RT15｜数据库里的预算预占幂等，为什么网关再次看到相同 identity 时反而拒绝发送？

回答：预算预占的幂等身份用于避免同一次逻辑模型尝试重复扣留额度。若网关发现相同 Attempt Identity 已有 RESERVED 或 UNKNOWN，直接再次发送可能制造第二笔供应商费用；因此需要先核对原尝试的状态，而非把 UNIQUE 冲突解释成“可以继续”。本地数据库锁和唯一约束保护预算记录，实际 Provider 请求是否发生还要靠调用边界证据。

追问：第一次请求在预占后崩溃，怎样恢复到可继续状态？

追问回答：检查该 Attempt 的发送前记录、Trace 和供应商请求标识：确认未派发时可释放预占并以受控身份继续；已可能派发则等待/查询结算回执或保留 UNKNOWN，再由策略处理是否另开新逻辑尝试。恢复设计要维持“不会无缘无故重复付费”的目标。

源码定位： 源码

RT16｜如何排查“用户感觉没变慢，但成本突然升高”？

回答：用户体感延迟没变但费用升高，首先查看每 Run 的 Provider Attempt 数、Retry/Fallback 比例、每轮 Prompt Tokens、缓存 Token、输出/推理 Tokens 和模型价格版本。常见原因包括主模型频繁空响应、隐藏重试增加、动态历史膨胀、缓存前缀失效或高价备用模型触发。AgentHub 有 Attempt Trace、Run Budget Ledger 与 Context Budget 统计，可以把费用拆到模型路线和上下文来源。

追问：怎样评价一次 KV Cache 或 Prompt 压缩优化确实省钱？

追问回答：冻结题目、AgentVersion、模型路由与价格口径，比较 A/B 两套请求的总已知费用、cache hit、总输入、TTFT 和回答质量；把失败 Attempt 的费用一起纳入分子，单独统计 usage 缺失。若优化导致漏依据或业务成功率下降，即使缓存命中率提高，也应从综合成本/正确任务角度重新取舍。

源码定位： 网关 · 回执统计

RT17｜消息进入队列就能向用户显示“任务成功”吗？

回答：API 将 AgentRun 或 IngestionJob 写入 PostgreSQL 后，把稳定 ID 投递到 Celery；Redis 收到消息说明任务进入可处理队列，但 Worker 还要领取、续租、执行和写回终态。用户界面应该显示“已提交/排队中”，随后通过状态 API 或事件更新到 PROCESSING、READY 或 SUCCEEDED。队列和数据库分别是交付层与业务事实层。

追问：HTTP 202 应在界面显示什么？

追问回答：显示“任务已受理”及可恢复的 Run/Job 标识，允许用户离开页面后回来查询。对于文档摄取，只有 Revision READY 且索引可用才显示可检索；对于外部工具，必须取得 Action 的成功回执才显示业务动作完成。

源码定位： Run 路由 · 入库服务

RT18｜为什么队列消息不能携带一份权限快照让 Worker 直接用？

回答：队列消息由 Broker 交付，可能滞留、重复或被伪造，不是永久授权凭据。AgentHub 的 Worker 只从消息取 workspace_id/run_id/request_id，随后查询权威 AgentRun 与创建者身份，通过 TenantService.get_workspace_access() 重新计算权限并检查 agent_run。因此用户提交以后被移出工作区，未开始的执行会按照新的成员关系处理，不会继续使用过期权限快照。

追问：任务排队时管理员撤销用户权限，Worker 应执行吗？

追问回答：它应在领取时重新校验创建者对目标工作区的访问和执行权限；不满足时写出明确受限状态，保留已提交的 Run 记录。对已经派发的 Action 另按实际回执结算，不能用队列中保存的一份旧权限文本替代当前授权。

源码定位： 队列 · Worker

RT19｜数据库行锁和执行租约分别解决什么问题？

回答：数据库行锁保护一次短事务里的状态检查与更新，例如同一 Run 的执行权领取；租约把这种所有权延伸到跨事务、持续几分钟的任务执行。execution_owner 和到期时间由 Worker 续期，写回时必须核对 owner，防止失租 Worker 覆盖新执行者状态。行锁解决瞬时并发，租约解决长时间工作所有权。

追问：有租约后还需要哪些手段防止重复业务动作？

追问回答：审批执行使用独立的原子 Claim；外部 WRITE 使用业务幂等键、操作查询或 UNKNOWN_OUTCOME 对账；数据库写回验证租约代次。租约不会自动让支付系统识别旧 Worker，跨系统 fencing 要求远端也校验相应令牌或操作身份。

源码定位： 源码

RT20｜lease token 为什么不能只用 job_id？

回答：Job ID 代表长期任务身份，租约 Token 代表某一次具体领取。Worker A 取得 L1，失租后 Worker B 取得 L2，两者处理的可能仍是同一个 Job ID。若写回只核对 Job ID，A 恢复后仍可能把旧结果覆盖 B。lease_token 随每次 Claim 改变，最终状态更新要求匹配当前 Token 和未到期条件，形成真正的执行代次隔离。

追问：Lease Token 能直接阻止旧 Worker 对 Qdrant 或外部支付写入吗？

追问回答：它首先保护 AgentHub 本地数据库授权与写回。跨系统要靠在外呼前检查租约、使用确定性 Point ID 或远端支持的 fencing/幂等协议；已发出的网络请求可能继续完成，所以最终可见性必须由当前租约持有者确认。

源码定位： 入库 · Worker · Run 租约

RT21｜有心跳就说明任务在进展吗？

回答：心跳说明 Worker 进程或租约续期路径仍能运行，不等于业务步骤持续前进。一个摄取任务可能心跳正常，却卡在外部 Embedding；一个 Run 可能仍续租，却长时间没有新 Step。AgentHub 需要同时观察 lease_expires_at、Job stage、最后一次进度变化、Provider 等待时间及重试记录。运行维护应区分“存活”与“有进展”，针对不同阶段设置告警。

追问：任务耗时明显超过预期时，应直接重新投递吗？

追问回答：先判断当前 owner 是否活跃、任务是否正在不可取消的网络调用，以及操作是否可安全重入。文档分块/向量 upsert 可以使用稳定 Point ID 重试；外部退款等 WRITE 必须先查 Action 是否派发与回执状态。超时告警先推动诊断，只有符合领取和副作用合同才触发恢复。

源码定位： Worker · 协调器

RT22｜为什么最大尝试次数应写在 claim 的 UPDATE 条件里？

回答：最大尝试次数是并发 Claim 的业务约束，必须与领取操作原子化。若先读 attempt_count 再 UPDATE，两个 Worker 可能都读到 2，且上限是 3，于是都认为自己可以执行第三次。AgentHub 在 claim_ingestion_job() 的 UPDATE 条件里写 attempt_count < knowledge_ingestion_max_attempts，只有真正领取成功才增加次数，避免重复投递额外消耗额度。

追问：attempt_count 是否等于实际 Embedding API 请求次数？

追问回答：不是。它统计整个 IngestionJob 被成功领取执行的次数；一次领取可能分很多批编码，也可能在内部发生向量查询或 Provider 重试。需要模型用量和费用时，另按编码批次、供应商请求或实际结果记录，这两个指标控制不同层次。

源码定位： 源码

RT23｜达到最大次数后，为什么不能立即把所有同 ID 任务设为 FAILED？

回答：达到尝试次数上限，只表示不能再批准新的领取，不意味着当前最后一次合法执行已经失败。比如 Worker A 正在第三次执行、租约还有效，另一个对账 Worker 此时不能将同 Job 直接改为 FAILED。需要结合状态、有效 owner、租约是否过期和下一次可领取时间统一判定；现有 Worker 仍可在合法租约下提交 READY。

追问：怎样写边界测试？

追问回答：构造三个并发场景：A 已领取最后一次且仍有有效租约；A 已失租且次数耗尽；队列重复投递同一 Job。分别断言首次可正常提交、过期进入受控失败/对账、重复消息不启动新的 Provider 计算，并检查 attempt_count 无越界。

源码定位： 源码

RT24｜租约续不上了，为什么仅让续租协程退出不够？

回答：续租失败意味着 Worker 已失去继续推进持久任务的资格。如果只停止心跳协程，主协程仍可能解析下一页、发起新 Embedding 批次或把旧结果写回。AgentHub 在耗时阶段边界使用租约检查，阻止失租后继续安排后续工作；最终 READY/FAILED 提交再核对 Token。这样把任务所有权落实到业务操作，而不只是后台定时器。

追问：能否立即停止已经开始的同步编码或远端 Qdrant upsert？

追问回答：已进入线程的同步函数和已发出的网络请求可能继续执行。项目的保护重点是禁止失租者发起下一批工作及提交终态；Qdrant 用稳定 Point ID 降低重复写入影响。若要更强取消能力，需要支持 Cancel 的底层客户端或远端 fencing，并处理清理与重建。

源码定位： 源码

RT25｜取消 asyncio 协程是否能取消已经发出的外部写入？

回答：asyncio.Task.cancel() 给 Python 协程发送取消信号，能停止仍受事件循环控制的后续步骤，但请求可能已经离开本机进入外部订单系统。AgentHub 对 WRITE 保存派发状态与 UNKNOWN_OUTCOME，取消 Run 时停止后续推进，同时保留已 CLAIMED Action 的真实执行记录。取消操作与业务撤销是两回事：前者终止本地工作流，后者必须作为新的受控业务动作执行。

追问：用户点“停止”后，页面应显示什么？

追问回答：显示 Run 的停止状态，并列出仍需确认的外部动作。若退款结果是 UNKNOWN，页面标明“结果待核对”，提供只读状态查询或人工处理入口；若明确未派发，则显示未执行。不要用一个“已取消”覆盖所有 ToolCall 的结果。

源码定位： 入库 Worker · 动作执行

RT26｜至少一次消息交付和业务恰好一次是一回事吗？

回答：Celery 的 acks_late=True 和 Worker Lost 重投配置支持在执行者故障后重新交付消息，因此任务可能被消费多次。AgentHub 使用 PostgreSQL 的 Run/Job、唯一身份、原子 Claim、租约和结果写回来限制业务执行，并通过对账处理遗漏交付。对于能重放的摄取任务，还利用确定性 Chunk/Point ID；对于外部 WRITE，则由 Approval Claim 和远端幂等协议管理副作用。

追问：简历怎么准确描述这里的可靠性设计？

追问回答：可以说“采用 Celery 至少一次交付语义，通过数据库原子 Claim、租约续期、幂等身份和对账控制重复执行与故障恢复”。再配一条受控 Worker 崩溃测试，展示消息重新交付后数据库只允许一个有效 owner，而不是把 Celery 当作业务恰好一次的保证。

源码定位： Worker · 工单执行

RT27｜数据库已提交 Run，队列投递失败了，怎么处理？

回答：Run 创建与 Redis 投递跨越两个系统，可能出现 PostgreSQL 已 COMMIT、API 崩溃而消息未发出的窗口。恢复路径要从数据库发现长期 QUEUED、未获执行权的 Run，判断是否符合重投条件，再发送相同 run_id；Worker 端按状态和租约去重。通用 Transactional Outbox 可在创建 Run 的同一事务中写 DispatchIntent，由独立派发器重试发送并保存交付尝试。

追问：AgentHub 有哪些已实现的持久交付意图？

追问回答：审批恢复路径已有 resume_pending 等持久状态，用来辅助对账与重复恢复；其他任务也有各自的 Job/Run 状态与周期 Reconcile。需要按不同入口分别核查提交与投递之间的窗口，再决定是否统一抽象 Outbox，而不是假设全部任务已经共用同一张通用派发表。

源码定位： 源码

RT28｜审批有 resume_pending 了，为什么还说恢复交付值得改进？

回答：resume_pending 把“审批已经作出决定，Run 应继续”的意图保存在数据库，即使派发瞬间失败，协调器仍能扫描并恢复。但发出一个 resume 任务和真正安全继续之间还有 Run 所有权、Approval Execution Claim、Checkpoint 和当前权限检查。重复入队是可接受的恢复策略，重复执行实际外部动作则要靠业务条件拒绝。

追问：两个 dispatcher 同时发现 resume_pending，怎么防双执行？

追问回答：派发器可利用数据库领取条件减少重复消息，最终由 Worker 重新加载 Run 并领取执行租约；恢复到 Approval 后还要通过 NOT_STARTED→CLAIMED 的原子条件更新。两个层次共同决定谁能推进和谁能调用外部工具。

源码定位： 审批服务 · API · 后台任务

RT29｜为什么 Run 过期租约通常转 NEEDS_ATTENTION，而入库可重新领取？

回答：文档摄取是可重入的计算管线：解析源文件、分块、计算向量，用同一 Revision/Point ID upsert，重投主要增加计算成本。AgentRun 可能已经批准并派发退款、回滚等外部动作，旧 Worker 崩溃后无法简单判断副作用是否发生。AgentHub 对租约到期的 Run 采用 NEEDS_ATTENTION 等受控状态，先核对 Action/Checkpoint，再决定下一步。

追问：怎样逐步扩大 Run 的自动恢复覆盖？

追问回答：先把步骤分类为纯计算、只读、可幂等写入和不可确定写入；纯计算可从明确 checkpoint 继续，只读可在权限许可下重放，WRITE 要具备稳定外部 operation_id、结果查询或补偿协议。每类建立崩溃注入测试，再开放自动恢复的条件。

源码定位： Run 租约 · 入库 claim

RT30｜协调器和重试器的职责有什么不同？

回答：重试器处理一次已知失败或未完成的任务尝试，控制退避与次数；协调器从数据库全局检查状态和租约，识别失联 owner、重复派发、超时审批和待恢复的 Run，决定下一步归属。AgentHub 的 Celery Beat 周期启动不同 Reconcile Task，由服务检查持久记录后执行补偿式推进。协调器需要遵循与正常 Worker 相同的锁和状态转换协议。

追问：协调器发现某 Run 很久没有新事件，但 owner 还在续租，应怎样处理？

追问回答：先将其判为慢或无进展的任务，观察当前阶段、最后 Step 时间与外部等待；不能直接夺取活跃租约。只有达到明确定义的失租、超时或可取消条件，才在事务中改变状态。这样维护进程不会与正常执行者竞态修改同一个 Run。

源码定位： 源码

RT31｜你怎么证明一个幂等修复真的幂等？

回答：幂等测试要验证“重复提交同一逻辑操作，业务事实不被重复创建”。例如使用同一个 client_token 并发提交同一 Turn，最终数据库只有一个对应 Turn/Run；同 Key 但不同输入应报冲突。对于 Approval，两个 Worker 同时 Claim，只有一个更新成功；对于外部订单，还要检查受控 MCP Server 记录的真实调用次数和 operation_id 复用。

追问：两次请求都返回 HTTP 200，可以认定幂等吗？

追问回答：还要检查数据表数量、业务状态、事件顺序、外部模拟服务接到的请求数量及返回是否指向相同对象。一个 Handler 可能每次都成功新建记录并返回 200，那是重复成功，不是幂等。

源码定位： 测试 · 服务

RT32｜为什么不同操作要统一加锁顺序？

回答：多个流程若以不同顺序锁相同记录，会形成死锁。例如审批取消先锁 Approval 再锁 Run，而恢复流程先锁 Run 再锁 Approval，两者并发就可能互相等待。AgentHub 的并发代码需要统一 Run、Approval 等相关对象的锁顺序，把状态检查和更新放在短事务内，必要时在冲突处安全重试整个事务。统一顺序比盲目增加更多锁更重要。

追问：是不是锁越多，系统越安全？

追问回答：锁的范围应与所维护的不变量一致。锁内只执行数据库检查和必要更新，模型调用、MCP 网络请求和长期计算在提交后进行；还要测 PostgreSQL 锁等待和死锁日志，缩短争用时间。

源码定位： 源码

RT33｜为什么审批表要同时有 decision_status 与 execution_status？

回答：decision_status 保存授权事实：PENDING、APPROVED、DENIED 等；execution_status 保存动作事实：NOT_STARTED、CLAIMED、SUCCEEDED、FAILED、UNKNOWN_OUTCOME。一个 Approval 先获批准，再由执行者 Claim 并发送到远端。把两者合成单个枚举会掩盖“已批准却未执行”和“已批准但结果未知”两类完全不同的业务情况，也会干扰取消与恢复。

追问：APPROVED + UNKNOWN_OUTCOME 对应什么业务状态？

追问回答：说明有权操作人同意了该次冻结参数，执行器已经可能把 WRITE 送到远端，但没有可靠的最终回执。后续走查询/对账，页面展示审批已通过、执行结果待确认，不再重新批准或盲重发。

源码定位： 模型

RT34｜审批到底绑定什么？为什么不能只存“用户点击同意”？

回答：审批绑定的是 workspace_id、run_id、tool_revision_id、规范化参数哈希与 proposal_ordinal 组成的具体逻辑动作。用户批准“订单 O001 退款 199 元”，并不等于以后任何订单或任意金额都能使用该许可。ApprovalService.create_or_get() 依据冻结身份复用相同请求，后续 claim_execution() 在明确的 APPROVED/NOT_STARTED 条件下授权执行。

追问：审批后模型把金额改为 299 元，原批准能继续用吗？

追问回答：金额变化意味着 canonical_args_hash 变化，应形成新的 Action 身份和 Approval。旧审批仍保留以供审计，新提议按新的风险和权限规则判断。参数不能在批准和真正执行之间被悄悄修改。

源码定位： 服务 · 运行恢复

RT35｜为什么不能用参数哈希作为全局动作去重键？

回答：相同参数并不总是同一业务意图：同一 Run 中可能先退一笔 199 元，后因新订单另提一笔 199 元。把参数哈希作为全局唯一键会错误合并两次独立操作。AgentHub 在动作身份中包含 Run、ToolRevision 和 proposal ordinal，区分有意重复提议与网络导致的同一次重投。外部支付系统仍应使用自己认可的 operation_id 去重。

追问：proposal_ordinal 为什么要能在恢复中保持稳定？

追问回答：如果每次恢复按当前时间重新分配序号，同一次动作会获得新逻辑 ID，旧 Approval 失去关联，可能再次请求批准或重复派发。因此序号应来自稳定的提议位置或持久记录，并在 checkpoint 和重放过程中复用。

源码定位： 源码

RT36｜管理员批准后，是否可以用管理员权限继续执行原 Run？

回答：审批者的权限用于决定能否批准一次高风险操作，不应该被借给原 Run 当作执行者身份。AgentRun 仍按提交者及其工作区上下文运行，Approval 另存 decided_by 和 decision source。AgentHub 的 Worker 和恢复入口重新校验 Run Actor，工具执行时使用对应 ToolExecutionContext；管理员批准只是使指定 Action 具备被领取的条件。

追问：为什么审计要分别记录申请者、审批者和实际执行者？

追问回答：三者承担不同责任：申请者提出业务需求，审批者承诺允许指定操作，执行者/Worker 负责实际派发与回执。故障审查时可以分别回答“谁要求”“谁允许”“谁执行”“外部返回什么”，而不是把三个人合成一个 admin 身份。

源码定位： 运行服务 · Worker

RT37｜两个审批员同时给出相反决定，如何保证结果明确？

回答：两个审批者并发作出相反决定时，服务在事务中锁定 Approval，并要求当前状态仍为 PENDING。先提交的一方完成状态转换；后到的一方读取已决状态，得到冲突或当前决定，不覆盖原结果。后端还记录决定者和决定时间。前端禁用按钮只改善交互体验，数据库才是跨浏览器和多人并发的仲裁点。

追问：怎样测试真实审批竞争？

追问回答：在测试数据库启动两个并发 Session，使用屏障让它们同时到达 Decision 入口，分别提交 APPROVE 和 DENY；最终只有一个持久决定，Execution 的有效前置条件与最终决定一致。重复读取返回同一决定证据。

源码定位： 源码

RT38｜个人自动审批偏好如何防止“自己给自己提权”？

回答：委托审批是在用户事先保存的偏好范围内，让平台对 LOW 或 MEDIUM 等允许的动作自动形成决定。delegation.py 仍检查用户权限、工具风险、既往拒绝等约束；ToolPolicy.requires_human() 对 HIGH 和 MCP WRITE 保持强制人工。个人设置只能缩小等待成本，不能修改平台策略或 AgentVersion 所允许的工具 Effect。

追问：用户选择 MEDIUM 自动审批后，高风险退款能否自动执行？

追问回答：不能。MCP WRITE 在 ToolPolicy 中被要求人工审批；委托等级不会覆盖强制人工条件。可在受控测试中分别创建 LOW READ、MEDIUM READ 和 HIGH WRITE，核对 decision_source 与是否出现真实人工决定。

源码定位： 源码

RT39｜为什么“读取工具都不需要审批”这个说法不准确？

回答：风险不仅来自数据修改，也可能来自读取生产日志、客户身份或核心指标。ToolPolicy 根据 Effect、Risk 和 ApprovalPolicy 共同判定：可自动执行的 READ 需要 approval_policy=NEVER 且 requires_human=False；高风险读取会要求人工。当前 MCP 导入规则限定 READ 的配置组合，高风险 READ 的审批执行还需要匹配专门路径，因此“所有 READ 都免审批”不能概括平台行为。

追问：产品要求所有 MEDIUM READ 也要人工批准，应修改哪些层？

追问回答：先在风险政策和 ToolRevision 合同中明确 MEDIUM READ 的审批要求，扩展批准后 READ 的执行与恢复逻辑，保证发布、模型可见工具、授权界面、Approval Claim 与结果回填一致。改动应包含跨级风险组合测试以及既有发布版本的兼容处理。

源码定位： 源码

RT40｜项目允许自己批准自己吗？

回答：AgentHub 的人工审批要求操作者具有 approve_action。ApprovalService.decide() 在执行 APPROVED 时检查 requested_by 与当前用户：普通组织成员申请的动作不得由自己批准，Organization OWNER/ADMIN 是明确例外；本人拒绝自己提出的动作不触发这条 APPROVED 专用限制。个人委托则通过持久偏好与风险规则另行形成决定。审批记录保存 decided_by 和 decision_source=HUMAN/DELEGATED，可追溯授权来源。

追问：为什么 HUMAN/DELEGATED 需要持久保存？

追问回答：二者的依据和审计路线不同。HUMAN 对应具体操作者与时间，DELEGATED 对应持久个人偏好、适用范围和策略判定。复盘外部退款时，决定来源决定应该查哪份授权证据和是否违反平台强制人工规则。

源码定位： 服务 · 委托

RT41｜取消 Run 与撤销待审 Approval 为什么必须放在同一个事务？

回答：Run 取消与未决定 Approval 撤销属于同一个业务状态变化。若先把 Run 置为 CANCELLED 再单独处理 Approval，进程中途崩溃可能留下“Run 已取消，审批却仍可批准”的记录。AgentHub 在同一数据库事务中锁定并更新两类对象，使后续决定无法继续领取已经取消的动作。对已 CLAIMED 的执行则保留实际执行结果与对账路径。

追问：怎样用数据库故障注入验证原子取消？

追问回答：在更新 Run 和 Approval 之间主动抛出异常，验证 rollback 后两者都保持旧状态；正常提交时二者同时完成有效转换。再对并发审批/取消做竞争测试，检查最终只有一种合法组合，且没有新增的外部写入。

源码定位： 运行服务 · 审批服务 · 测试

RT42｜修复代码后，旧数据库里已经不一致的记录怎么办？

回答：修复代码只能保证未来请求遵循新规则，旧数据库可能已经有错误的 Approval/Run 组合、缺失引用或不一致的状态。应先写只读诊断查询统计受影响范围，再设计一次性或可重复执行的 Repair，按最小状态转移修复，保留原始审计线索与操作记录。对于 UNKNOWN_OUTCOME，需要业务证据支持才能改变结果，不能直接通过数据清洗改成 FAILED。

追问：为什么修复脚本也必须幂等？

追问回答：部署中断可能执行到一半，运维重跑脚本时不能再次生成虚假审批、追加重复审计或多次扣减计数。使用稳定目标身份、条件 UPDATE、修复版本标记和事务边界，重复执行应得到相同最终状态；先在复制数据集和 Dry Run 上核对影响数量。

源码定位： 协调器 · 回归测试

RT43｜为什么取消不能把 CLAIMED 或 UNKNOWN_OUTCOME 直接改成“未执行”？

回答：取消代表不再继续组织新的执行，CLAIMED 说明某个执行者已取得本次动作执行权，UNKNOWN_OUTCOME 说明外部可能已经执行。将这两类状态直接改成 NOT_STARTED，会丢失派发证据，让重试机制认为可以重新写入。AgentHub 保留 Action 原状态，通过对账确认是否成功、失败或需补偿，Run 状态和 Action 状态分别展示。

追问：业务方要求撤销已经发出的退款，怎么处理？

追问回答：先查询原退款实际状态；若外部系统支持撤销，生成一条独立补偿操作，定义新 ToolRevision/参数和审批，使用新的 operation_id 派发并记录结果。补偿不是改写历史记录，应把原操作与补偿动作关联起来供审计。

源码定位： 运行服务 · 协调器

RT44｜为什么动作 claim 用条件 UPDATE，而不是先读再写？

回答：先 SELECT 看到 NOT_STARTED 再 UPDATE 的两步之间存在竞争，两个 Worker 可能同时认为自己可执行。ApprovalService.claim_execution() 使用带 decision_status=APPROVED、execution_status=NOT_STARTED 的条件 UPDATE，让数据库原子决定唯一获权者；受影响行数为 1 才允许调用外部 WRITE。它保护本地执行资格，并与 Run 级租约共同建立所有权。

追问：这个 Claim 能实现外部业务 exactly-once 吗？

追问回答：Claim 成功后仍可能发生“外部执行完成、数据库写回前崩溃”。此时应用不能按 NOT_STARTED 重跑，而要保留 CLAIMED/UNKNOWN 并使用远端幂等键或查询回执核对。完整的恰好一次效果依赖双方认可的业务操作身份。

源码定位： 源码

RT45｜本地 create_ticket 怎么做到重复调用不生成重复工单？

回答：内部 create_ticket 可以利用稳定的业务幂等键与 PostgreSQL 唯一约束，确保同一次提交只有一条工单。Service 对相同 Key 检查请求内容是否一致，重复相同请求复用原对象，不同内容返回冲突；工单对象本身还绑定 Workspace、Customer 和版本字段。并发下数据库的唯一约束负责最后仲裁，冲突后回读原提交结果。

追问：只写 SELECT 判断不存在，再 INSERT 足够吗？

追问回答：两个事务可以同时读到“没有”，随后都 INSERT。应将 Key 唯一性下沉数据库，捕获唯一冲突后按原请求摘要比对并读取结果。对于响应丢失，客户端继续使用原 Key，而不是生成一个新 Key 重发。

源码定位： 源码

RT46｜FAILED 与 UNKNOWN_OUTCOME 有什么本质区别？

回答：FAILED 表示有足够证据确定此次动作没有达到成功结果，例如请求在派发前被拒绝，或远端明确返回业务错误；UNKNOWN_OUTCOME 表示操作可能已经到达外部系统但最终状态不清。AgentHub 根据 DispatchState 与 McpCallStatus 映射 ActionResult，对远端 WRITE 的 MAYBE_DISPATCHED 超时保留 UNKNOWN，并进入查询/人工核对流程。两者的重试权限不同。

追问：HTTP Timeout 一定属于 UNKNOWN 吗？

追问回答：要看超时发生的位置：连接建立前并有明确未派发证据，可归入失败；请求已经交付或派发状态不明的 WRITE，应归 UNKNOWN；只读查询可按单次超时与重试策略处理。HTTP 异常只是传输事件，业务结果要结合派发记录和远端回执。

源码定位： 动作执行 · 协调器

RT47｜为什么恢复审批时不能随便加载“最新 checkpoint”继续？

回答：审批恢复必须对应当次 Run 的冻结 AgentVersion、提议的 logical_action_id、ToolRevision、参数哈希及图执行位置。随意选择“最新 checkpoint”可能把之后的用户消息、另一个工具提议或不同预算状态带进旧审批。AgentHub 使用持久 Checkpoint 与恢复绑定检查，确认历史状态、Approval 和 Run 的身份一致后才继续执行。

追问：Checkpoint 丢了，能否从日志凑出相似上下文继续？

追问回答：日志有可能缺失模型内部消息、参数、预算预占与事件顺序。应将 Run 置为受控恢复/人工处理状态，先恢复原 Checkpoint 备份或通过正式重建协议核对完整输入；不能用近似聊天记录替换已经被批准的具体动作上下文。

源码定位： 源码

RT48｜为什么远端 MCP 写工具不应该在外层粗暴套一个超时后宣称失败？

回答：超时应由 MCP Client 或受控网络边界记录派发阶段和真实异常，再由 McpActionExecutor 把结果映射为 SUCCEEDED、FAILED 或 UNKNOWN_OUTCOME。如果在 ActionRuntime 外面简单套 wait_for(..., 30)，捕获 TimeoutError 就写 FAILED，会丢失“请求其实已经成功”的可能性，也可能取消了用于记录回执的子任务。项目的 DispatchState 设计就是为了保持这种可解释性。

追问：是否因此取消所有超时设置？

追问回答：仍需要连接、请求和单次工具上限，避免无限等待；只是超时后按派发证据分类，并让 Action 状态保留待核对。可为远端提供 operation_id 与状态查询工具，把超时后续处理做成只读对账而不是再执行 WRITE。

源码定位： 源码

RT49｜如果面试让你讲最近一个真正有价值的修复，你怎么讲？

回答：可以选择项目里已经进入主线的“文档修订归属复合外键”或“摄取尝试上限原子化”修复来说明工程价值。以复合外键为例：旧 Chunk 两个独立外键只确认 Document 与 Revision 分别存在，允许跨文档错配；改动在模型和 Alembic 中增加四字段关联约束，迁移先检测历史脏数据，再通过真实 PostgreSQL 迁移测试验证错误组合会被拒绝。讲清问题数据例子、修改位置、并发/迁移场景和回归证据。

追问：如果这个修复不是我本人提交的，面试怎么回答？

追问回答：明确“我阅读并复核过这次修复”，展示自己独立追踪过的模型、迁移和测试；然后讲本人实际完成过的一项代码修改，用 commit 和验证记录说明贡献。面试官追问细节时，理解系统设计和个人交付两类信息分别呈现。

源码定位： 运行 · 审批 · 测试

RT50｜让你接入一个新的“创建外部订单”工具，你会如何设计完整闭环？

回答：接入 create_external_order 时，先定义订单幂等身份、输入 Schema、必需字段和受控业务范围，再通过 MCP Connection 导入 WRITE ToolRevision，配置审批规则并发布 AgentVersion。Runtime 取得具体订单参数后创建 Approval，绑定哈希和 proposal ordinal；批准后 ActionRuntime 原子 Claim，向外部发送稳定 operation_id，保存明确回执或 UNKNOWN_OUTCOME。补充只读 get_order_status(operation_id) 用于恢复核对，向用户提供执行状态与关联订单 ID。

追问：这项功能上线前最关键的故障测试是什么？

追问回答：构造“远端订单已创建成功、回执丢失、Worker 崩溃”，随后重启并重复交付任务。期望数据库仍有唯一 logical_action_id，不再无依据地产生第二个外部订单；通过同 operation_id 查询复用外部结果，最终把未知状态收敛成可核实的订单事实。

源码定位： 审批模型 · 动作执行
