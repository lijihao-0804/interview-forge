缓存与数据库一致性落地

7.1 多级缓存

本地缓存（Caffeine）→ Redis → 数据库
本地缓存快但多实例不一致，Redis 共享但网络有开销，DB 兜底

7.2 一致性方案回顾

  • Cache Aside：读先查缓存，未命中查库再回填；写先更新 DB 再删缓存；
  • 延迟双删：删除缓存 → 更新 DB → 延迟再删一次，缩小并发窗口；
  • binlog 订阅（Canal）：监听 MySQL binlog 异步删缓存，最终一致；
  • 强一致场景：不要依赖缓存，直接走 DB 或加分布式锁串行化。

7.3 热点 key 处理

  • 多副本分散热点 key（key_01 ~ key_10）避免单点；
  • 本地缓存兜底热点，降低 Redis 压力；
  • 布隆过滤器挡不存在请求（防穿透），见《Redis》。

7.4 Cache Aside 与延迟双删代码

// 读：未命中查库回填
public Product getById(Long id) {
    Product p = redis.get("product:" + id);
    if (p != null) return p;
    p = productMapper.selectById(id);
    if (p != null) redis.set("product:" + id, p, 30, TimeUnit.MINUTES);
    return p;
}

// 写：先更新 DB，再删缓存
public void update(Product p) {
    productMapper.update(p);
    redis.delete("product:" + p.getId());
    // 延迟双删：并发下“旧读回填脏缓存”的窗口，延迟再删一次
    delayedExecutor.schedule(
        () -> redis.delete("product:" + p.getId()), 500, TimeUnit.MILLISECONDS);
}

要点：删缓存而非更新缓存（并发写容易互相覆盖写回旧值）；延迟双删的 500ms 要略大于一次读请求的回填耗时；更彻底的方案是 Canal 订阅 binlog 异步删缓存，业务代码零侵入。

7.5 面试追问

  • 问：更新 DB 后为什么删缓存而不是更新缓存？
  • 答：更新缓存并发下容易写入旧值，删除后按需回填更简单可靠。
  • 问：延迟双删的延迟多久？
  • 答：略大于读请求回填缓存的时间（通常几百毫秒到 1 秒），缩窗口但非绝对。
  • 问：缓存和数据库强一致怎么做？
  • 答：不加缓存或锁串行化；绝大多数场景接受最终一致。
