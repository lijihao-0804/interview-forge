2.1 为什么需要注册中心

服务地址会随扩缩容变化，硬编码 IP 不可行。注册中心维护“服务名 → 实例列表”的映射，提供注册、发现、健康检查。

启动：服务启动后向注册中心注册（服务名 + IP + 端口）
保活：心跳续约；注册中心发现心跳超时则剔除
发现：调用方从注册中心拉取/订阅目标服务实例列表
调用：负载均衡选一个实例发起调用

2.2 Nacos vs Eureka

对比 Nacos Eureka
定位 注册中心 + 配置中心 注册中心
CAP AP/CP 可切换 AP
健康检查 主动探测 + 心跳 心跳
配置管理 原生支持（动态配置） 无
现状 Spring Cloud Alibaba 主流 2.x 从未开源发布，现为 1.x 维护状态

临时 vs 持久实例：Nacos 里临时实例走心跳、心跳断了就剔除；持久实例走主动探测、不自动摘除（适合 K8s 等有状态场景）。Eureka 自我保护：当心跳续约低于阈值（默认 15 分钟内低于 85%）时，Eureka 进入自我保护模式、不再剔除实例并亮红色警告——宁可保留可能已挂的实例，也不让注册表被误清空，这正是 AP 取向的体现。

2.3 Nacos / Eureka / Consul 对比

对比 Nacos Eureka Consul
一致性模型 AP（可切 CP） AP CP
健康检查 心跳 + 主动探测 客户端心跳 心跳 + gRPC 探测
配置中心 内置（动态刷新） 无（需 Spring Cloud Config） 内置 KV
雪崩保护 有（非健康实例保护阈值） 有（自我保护机制） 无

注册中心的本质权衡是 AP vs CP：服务发现要的是可用性（列表旧一点也别不可用），所以 Eureka/Nacos 默认 AP；Consul 选 CP，保证一致但分区时可能拒绝注册。

2.4 配置中心动态刷新

@RestController
@RefreshScope                       // 配置变更后 Bean 自动重建
public class BizController {
    @Value("${biz.rate-limit:100}")
    private int rateLimit;          // Nacos 控制台改配置 → 推送 → 立即生效，不用重启
}

动态刷新原理：客户端长轮询 Nacos（30s 超时机制实现准实时）→ 配置变更返回新值 → 发布 RefreshEvent → @RefreshScope 的 Bean 销毁重建，下次注入新值。

2.5 面试追问

  • 问：服务注册发现流程？
  • 答：注册 → 心跳续约 → 调用方发现 → 负载均衡调用；实例下线被剔除。
  • 问：Nacos 和 Eureka 区别？
  • 答：Nacos 还能当配置中心、可切换 AP/CP；Eureka 2.x 从未开源发布（2018 年官方叫停开发），现为 1.x 维护状态。
  • 问：注册中心挂了会怎样？
  • 答：已注册实例还能靠本地缓存继续调用，但新实例/变更感知失效，所以要高可用部署。
  • 问：注册中心选 AP 还是 CP？
  • 答：服务发现优先可用性（AP），注册列表短暂陈旧可容忍；配置管理要强一致（CP），改配置必须所有实例看到同一份。
