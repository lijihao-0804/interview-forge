后端追问：两次评分和一次慢请求

一名学员同时打开两个标签页，对同一道题点了两次评分。另一次排查里，压测打到 150 个虚拟用户，连健康检查都要等几秒。回答这两件事时，要指出等候发生在哪里，以及当时怎样量到它。

我们两个人打开同一道题，服务端怎样找到各自的进度？

我会沿着评分请求看。普通读者可以打开公共题页，点评分时浏览器发出 POST /api/complete。FastAPI 从会话认出账号，再用已认证的用户名选择个人 SQLite 文件。客户端只需提交题号和评分。个人 API 对未登录请求返回 401。管理接口还要检查角色。两个账号即使都提交第 739 题，也各自在自己的库里写。

这套结构适合单机上的按人读写。不同用户的学习写操作分布在不同文件，认证和站点设置仍共用一个库。如果要做跨账号统计，就得处理多份库，这也是这项选择的代价。

两个标签页同时评分，怎样避免复习轮数长两次？

我把“今天评过没有”的检查放在写事务里。complete_round 先执行 BEGIN IMMEDIATE，取得这个库的写锁，再按北京时间查题目的记录。第一个手动评分写入卡片和评分日志。第二个请求等锁释放，看到已有结果，就返回相同的到期日。这一天的复习轮数仍是一轮。

我还会把这两次操作的顺序调过来测。上午力扣通过后自动记为“良好”，下午本人点“忘了”，系统用旧日志保存的评分前状态重算，并把当天那条日志改成手动评分。反过来，先手动评过，之后到的自动评分会沿用已有结果。

写入由一个 worker 处理，下次刷首页时换了 worker，缓存怎么办？

在单机共享模式里，每个 worker 都会比对用户库主文件和 WAL 日志文件的标识、大小与时间戳。文件签名变了就重新取仪表盘，重建过程中签名又变就跳过这次缓存写入。测试让一个进程先读到缓存，另起进程修改数据库，再回到第一个进程读，断言两次拿到的签名不同。

10 月 3 日测出三秒多的 P95，你怎样定位等候发生在哪里？

当时测的是同一台服务器回环地址上的 /api/health。我把服务版本、虚拟用户总数 150、测试窗口约六秒都固定，给发压客户端的连接分配函数计时。用一个 HTTP 连接池时，每秒 190.9 次请求，P95 是 3389 毫秒，池分配累计占了 5.047 秒。只把客户端换成六个池，每秒到了 703.1 次，P95 降到 620 毫秒。两组请求由同一套服务处理，这个对照定位到了发压工具本身的一处瓶颈。

要回答“多少人能同时刷题”，这次测量还差什么？

修正脚本后又跑了一组阶梯测试。150 个虚拟用户那一档，健康检查每秒 824.7 次，P95 为 443 毫秒，错误数为零。这个端点很轻，整档约六秒，发压进程也接近吃满一个核。要评估刷题高峰，我会在独立发压机上混合登录后的面板读取、评分写入，预热后延长采样，同时观察数据库锁等待、服务端 CPU 和客户端排队。这样才能给业务负载定一个有条件的容量范围。
