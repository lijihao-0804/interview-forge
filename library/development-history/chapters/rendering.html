聊天回答越写越长时，读者最先察觉到的往往是滚动不跟手。前端把“马上看到新文字”和“看到排版完整的答案”放到两个时刻，才有余地把这两件事都做好。

一张还没写完的表格

假设模型在回答里输出 Markdown 表格。第一小段发来了表头，过几段才有分隔线，最后才是数据行。如果每收到一小段就把累计全文交给解析器，再换掉整个气泡，前面的段落会被一遍遍扫描。回答分成 n 个等长片段时，解析器读到的累计长度依次是 1、2，一直到 n 个片段。重复工作就藏在这个加法里。

让文字、滚动和排版各按自己的节奏走

  1. 收到文字增量时先追加到气泡的原文缓冲。约 100 毫秒的调度把密集到达的片段合成一次纯文本预览，未完成的代码块也可以直接读。
  2. 页面单独调度滚动。读者停在底部时跟随新文字。如果已经向上翻去读某一段，就保留当前位置。
  3. 收到结束事件后，用完整原文做 Markdown 排版。此时表格和代码块的边界已经齐全，预览可以换成正式答案。

读者先看到文字。最后一段数据到齐，表格才排好。预览也仍会写入累计文本。换来的好处是，模型切得再碎，也不至于让每个片段都触发一次全文排版。

给调度器一个可以重复的场景

项目的 Node 测试从正式前端脚本取出调度函数，在同一个同步循环内送入 1,000 个片段，其中混有表格、列表和代码。此次复跑记录到 1 次预览刷新。结束后，测试还检查了最终 HTML 是否真的含有表格和代码块，以及关闭自动跟随后滚动位置是否保持。真实对话的片段分散到达时，刷新次数会随到达节奏变化。

面试官追问：如果改成每帧渲染完整 Markdown 呢？

可以少渲染几次，但每次仍要解析全文。项目把动画帧留给滚动。正文先按时间合并成纯文本，结束时再解析一次。回答这题时，我会分别指出调度频率和每次调度做的工作。
