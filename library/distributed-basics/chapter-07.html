6.1 什么是幂等

同一个请求重复执行多次，结果与执行一次相同，不产生副作用。支付、下单、转账、库存扣减必须幂等，否则用户多点一次按钮就重复扣款。

6.2 实现方案

方案 做法 适用
唯一键去重 业务唯一键 + 去重表/唯一索引，重复插入失败即已处理 落库类操作
Token 机制 前端先取 token，提交时带 token，服务端消费一次 表单提交
状态机 只允许合法状态流转，已支付不能重复支付 订单状态
乐观锁 update set x=x+?, version=version+1 where version=旧值；影响行数为 0 则并发冲突，重试 更新类
分布式锁 处理前加锁，防止并发重复 高并发场景

6.3 与防重区别

幂等针对“同一业务多次执行结果一致”，防重更侧重“重复请求被拦截”；实践中常配合使用：分布式锁挡并发，唯一键/状态机保证落库不重复。

6.4 幂等代码三件套

// 1. Token 机制：进入表单页先领 token，提交时校验 + 删除原子完成
String token = UUID.randomUUID().toString();
redis.opsForValue().set("token:" + token, "1", 10, TimeUnit.MINUTES);

// 提交时：delete 返回 true = 第一次提交；false = 重复提交，直接拒绝
Boolean first = redis.delete("token:" + token);
if (Boolean.FALSE.equals(first)) throw new RepeatSubmitException();

-- 2. 乐观锁：并发/重复更新只有一条生效
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;    -- 影响行数 0 → 已处理过，按业务放弃或重试

// 3. 去重表：与业务同事务（见消息队列幂等一节），挡“重投”而非“并发”

组合拳：token 挡前端重复点击，乐观锁挡并发更新，去重表挡消息重投——三层手段覆盖三类重复来源，面试按这个框架分层回答。

6.5 面试追问

  • 问：接口幂等怎么实现？
  • 答：唯一业务键去重、token、状态机、乐观锁、分布式锁，按场景组合。
  • 问：支付回调为什么必须幂等？
  • 答：回调可能重发多次，不幂等会重复入账。
  • 问：分布式锁和幂等什么关系？
  • 答：锁挡并发进入，幂等保证重复执行结果一致，两者互补。
