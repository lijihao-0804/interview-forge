从单机到分布式

请通过“启动学习站.cmd”进入，才能写入数据库。

1.1 为什么要分布式

  • 性能：单机 CPU/内存/磁盘到瓶颈，水平扩展分摊压力；
  • 可用性：单点故障会挂掉整个系统，多副本提高可用；
  • 容量：数据量超过单机存储上限，需要分片；
  • 组织协作：大团队按业务拆分独立开发部署。

1.2 分布式带来的问题

问题 表现 应对
网络不可靠 请求丢失、超时、重复 重试 + 幂等、超时熔断
时钟不一致 时间戳排序不可靠 逻辑时钟/业务版本
数据一致 多副本/多服务状态漂移 分布式事务、对账补偿
可用性 单点故障、脑裂 多副本、选主、隔离
排查困难 问题分散在多个服务 链路追踪、日志聚合

时钟三件套：物理时钟（NTP 同步精度有限，跨机器不能直接比时间戳）、Lamport 逻辑时钟（计数器，只保证事件偏序）、向量时钟（能判断因果并发）。

1.3 架构演进五步

1. 单体架构：一个 war 包搞定一切 → 团队 <10 人、日活万级完全够用
2. 垂直拆分：按业务拆成多个应用（订单系统、用户系统），各自连自己的库
3. SOA：抽公共服务（用户中心、支付中心），ESB/Dubbo 做服务治理
4. 微服务：拆得更细 + 注册中心/网关/链路追踪全套基础设施
5. 云原生：容器化 + K8s + Service Mesh，基础设施下沉

每一步的驱动力都是具体的痛：单体发布慢 → 垂直拆分；公共服务重复建设 → SOA；SOA 服务粒度太粗、扩展不灵活 → 微服务。面试讲架构演进，重点不是报名词，而是说出每一步“解决了什么、又带来了什么”。

数据库维度的同步演进：单库 → 读写分离 → 分库分表（垂直分库到业务库，水平分表到数据片）——分库分表正是后面“分布式事务”“分布式 ID”两章的根因：库一拆，跨库事务和全局唯一 ID 的需求就来了。

1.4 面试追问

  • 问：分布式和单机最大的区别？
  • 答：单机假设“调用必达、状态一致”，分布式必须面对网络不可靠和部分失败。
  • 问：为什么分布式系统难做？
  • 答：没有全局时钟、没有全局状态视图，只能通过协议和权衡逼近“看起来一致”。
  • 问：你们项目为什么拆微服务？
  • 答：说具体的痛（发布互相阻塞、热点模块无法单独扩容），再讲拆分收益，不要背概念。
