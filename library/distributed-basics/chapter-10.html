分布式锁对比

8.1 为什么单机锁不够

synchronized/ReentrantLock 只锁单 JVM；微服务多实例部署时，同一资源可能被多台机器并发操作，需要跨进程的锁。

8.2 三种实现

方案 原理 优点 缺点
Redis SET key uid NX EX + Lua 释放 性能高、实现简单 主从切换可能丢锁（红锁有争议）
ZooKeeper 临时顺序节点 + watch，最小序号拿锁 可靠、无过期误删 性能较低、依赖 ZK
etcd 租约 lease + 续期 + revision 排序 可靠、支持续期 需要运维 etcd

ZK 锁的惊群优化：不 watch 根下全部子节点，只 watch 自己前一个节点；前一个节点释放/失效后，重新取最小序号判断自己是否拿到锁。

// Redis 加锁（原子）
SET lock:order:1001 uid-xxx NX EX 30
// 释放锁（Lua 原子：比较 value 再删除）
if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end

要点：value 用唯一 ID 防止误删别人的锁；加锁和释放都要原子；用 Redisson 看门狗自动续期避免业务没跑完锁过期。

8.3 Redisson 分布式锁代码

RLock lock = redisson.getLock("lock:order:1001");
lock.lock();                            // 不指定 leaseTime 才启用看门狗：默认 30s，每 10s 自动续期
try {
    // 业务处理，进程仍存活且未释放时由看门狗续期
} finally {
    lock.unlock();                     // Lua 原子释放：只删自己持有的锁
}

// 抢不到就放弃，避免大量线程阻塞
boolean ok = lock.tryLock(2, TimeUnit.SECONDS);   // 2 秒内没拿到返回 false

如果需要可重入、自动续期和等待超时，Redisson 可以封装“NX 加锁 + 唯一 value + Lua 原子释放 + 看门狗续期”等细节；手写 SET NX EX 也可以，但必须自行补齐唯一标识、原子释放、租约/续期、故障和 fencing token 等边界，不能把客户端库当成跨资源强一致的证明。

8.4 面试追问

  • 问：分布式锁三要素？
  • 答：互斥、防死锁（过期）、防误删（唯一 value + 续期）。
  • 问：Redis 和 ZK 锁怎么选？
  • 答：追求性能选 Redis；追求强可靠、可容忍稍慢选 ZK/etcd。
