Memory 架构

在构建 Agent 记忆系统时，仅仅定义短期记忆和长期记忆的概念是不够的，还需要设计具体的 Memory 架构（Memory Architecture）。Memory 架构决定了记忆如何存储、如何组织以及如何被 检索使用，这直接影响 Agent 的性能、响应速度以及系统扩展能力。

在实际工程中，Agent 的长期记忆通常不会直接存储在 Prompt 或简单文件中，而是借助专门的存储 系统进行管理。目前比较常见的实现方式主要可以分为两类：Vector Memory（向量记忆）和 Database Memory（数据库记忆）。很多复杂系统会同时结合这两种方式，从而构建更加灵活和高效 的记忆系统。

Vector Memory

Vector Memory 是当前 AI Agent 系统中最常见的一种记忆架构。其核心思想是将文本信息转换为向量 表示（Embedding），并存储在向量数据库中。当需要检索记忆时，通过计算向量相似度来找到与当 前任务最相关的信息。 这种方法本质上是一种语义检索（Semantic Retrieval）机制。相比传统的关键词匹配，向量检索能 够理解文本的语义关系，因此在处理自然语言任务时效果更好。

一个典型的 Vector Memory 工作流程如下：

用户对话或任务信息

→ 文本向量化（Embedding）

→ 存入向量数据库

→ 新任务触发检索

→ 计算向量相似度

→ 返回最相关的记忆内容

例如，用户曾经在系统中讨论过一个项目：

“我正在开发一个 RAG 系统，用于智能客服。”

当用户在未来再次提到：

“帮我优化之前那个客服系统的架构。”

系统可以通过向量检索识别出“客服系统”和“RAG 系统”之间的语义关联，从而找到之前存储的相 关记忆。

常见的向量数据库包括：

  • Milvus

  • Pinecone

  • Weaviate

  • Chroma

  • FAISS

这些系统通常支持高效的向量相似度搜索，可以在海量数据中快速找到最相关的记忆片段。 Vector Memory 的优点在于： 首先，它能够实现语义级别的检索能力，即使用户表达方式发生变化，也能找到相关信息。其次，它 具有良好的扩展性，可以存储大量文本数据，并支持快速检索。 但它也存在一定局限。例如向量检索更适合处理文本语义信息，对于结构化数据或精确查询（如订单 编号、用户ID等），效果往往不如传统数据库。

Database Memory

与 Vector Memory 不同，Database Memory 主要用于存储结构化信息。在很多业务系统中，Agent 需要管理的数据并不是自然语言，而是明确的结构化数据，例如： 用户信息

订单记录

任务状态

系统配置 操作日志

这些数据通常需要通过精确查询进行访问，因此更适合存储在传统数据库中，例如：

  • MySQL

  • PostgreSQL

  • MongoDB

  • Redis

在 Database Memory 架构中，Agent 可以通过查询接口或工具调用的方式访问数据库。例如： 用户请求：

“帮我查询一下订单 893472 的状态。”

Agent 在推理阶段识别到这是一个结构化查询任务，然后调用数据库查询接口，从数据库中获取对应 数据，并将结果返回给用户。

Database Memory 的优势在于：

首先，它非常适合处理结构化信息和精确查询。其次，它能够保证数据一致性和事务管理，这在业务 系统中尤为重要。

但与 Vector Memory 相比，Database Memory 并不具备语义理解能力，因此通常不会单独用于自然 语言记忆检索。

在真实的 Agent 系统中，Vector Memory 与 Database Memory 往往是协同使用的。Vector Memory 主要负责语义记忆，例如用户历史对话、经验知识和文本信息，而 Database Memory 则负 责存储结构化数据，例如用户资料、业务数据和任务状态。

通过这种混合架构，Agent 可以同时具备语义理解能力和结构化数据处理能力，从而在复杂应用场景 中保持良好的性能与扩展性。
