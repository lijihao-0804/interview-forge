系统设计题套路

3.1 答题框架

1. 明确需求：功能、规模（QPS、数据量）、非功能（一致性、可用性）
2. 容量估算：QPS、存储、带宽，粗略数量级即可
3. 架构分层：客户端 → 网关 → 业务服务 → 存储（DB/缓存/MQ）
4. 核心链路：把一次请求完整走一遍
5. 关键点：缓存、MQ、分库分表、幂等、限流、高可用
6. 扩展演进：流量再大怎么扩容、哪些是瓶颈

3.2 母题一：秒杀（见《微服务与高并发》）

静态化 + 限流 → Redis 预热 + Lua 预扣 → MQ 异步 → DB 条件更新 → 隔离降级 → 对账。

3.3 母题二：短链系统

需求：长链转短链，跳转还原；估算：亿级条目、千级 QPS
方案：发号器（号段/自增优先）生成唯一 ID → base62 编码成短码
存储：短码 → 长链映射表（MySQL + Redis 缓存）
跳转：一般用 302（301 会被浏览器/代理缓存，改映射不生效、统计失真），命中缓存直接跳
扩展：多机房发号分段，防止 ID 冲突；布隆过滤器挡无效码回源；短码过期清理

关键技术矛盾：雪花 ID 是 64 位，base62 编码后约 10~11 位，达不到行业惯例的 6~8 位；而亿级条目用 6~7 位 base62 就够（62⁶ ≈ 5.7×10¹⁰），所以主流是号段/自增发号 → base62，雪花留给需要趋势递增的分布式场景。

3.4 母题三：IM 聊天

需求：单聊/群聊、消息收发、历史记录
方案：长连接（WebSocket）保在线；消息先落库/发 MQ
读扩散 vs 写扩散：群聊小群写扩散（每人一份）、大群读扩散（拉取最新）
历史记录：MySQL 分库或消息存储；未读数用 Redis 计数
可靠性：消息带 seq 去重；离线消息上线拉取

3.5 面试追问

  • 问：设计题从哪开始？
  • 答：先确认需求和量级，再画分层架构，最后讲关键点和扩展。
  • 问：容量估算没数据怎么办？
  • 答：说数量级即可：1 万日活 × 每人 10 次 = 10 万次/天，平均约 1~2 QPS；若假定绝大部分流量（约九成）集中在 1% 时段，峰值约 100~200 QPS（要说明这个集中假设；若只集中 10%，峰值只有约 10~20 QPS）。
