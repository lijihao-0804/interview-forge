# InterviewForge 项目全面深度审查报告

- **审查日期**：2026-09-19
- **审查基线**：`main` 分支 `86c3cc6`（feat: expand admin operational metrics）
- **审查方式**：五个专项并行深审（安全与认证 / AI 子系统 / 前端 / 数据层与业务逻辑 / 构建测试与仓库卫生），全部发现均要求带 `文件:行号` 证据，报告中的关键结论（表名 bug、明文凭证、公开仓库运维信息、登录跳转 404、开放重定向绕过等）已逐条人工复核属实。
- **范围**：`interview_forge/`（约 3.6 万行 Python，含 FastAPI 服务层、AI 子系统、analytics）、根目录页面（index/cockpit 等）、`assets/`、`pages/`、`tools/`、`scripts/`、`tests/`、`docs/`、git 仓库卫生。不包含生产 VPS 实机（nginx 配置、systemd、防火墙等只能在服务器上核实的问题单独标注）。

---

## 一、总体结论

**应用代码本身的工程质量明显高于同类个人项目水准**：密码哈希、会话生成、SQL 参数化、按用户隔离数据库、关键写路径的事务与唯一索引双保险、AI 密钥加密存储、前端 XSS 纪律、日志脱敏等核心安全基本功都做对了，且已有 389 个测试、覆盖面很广的发布校验脚本。数据层专项未发现任何 P0 级数据损坏风险。

**真正的高危点集中在"部署与运维面"而不是代码逻辑**：

1. 公开 GitHub 仓库里躺着一份含生产服务器 IP、root SSH 方式、部署路径、同服其他服务端口的运维文档（已实测仓库 Public，该文档被 git 跟踪）；
2. 部署文档暗示 nginx 可能直接以仓库目录为静态根，若属实，`/data/auth.db`（全部账号与密码哈希）、`/data/users/*/*.db`（明文力扣 Cookie）、`/.git/` 可被任何人直接下载，绕过应用层全部门禁——**这是当前唯一可能导致全量账号泄露的路径，需要立即上服务器核实**；
3. 用户的 LeetCode 登录 Cookie（可直接登录其力扣账号的活会话）明文落盘，而项目对 AI API Key 反而有 Fernet 加密基建，却没用在凭证上；
4. AI 聊天通道完全没有每日配额，任何登录用户可无限消耗上游 API 费用，管理端的"每日上限"对聊天根本不生效。

其余问题集中在：FastAPI async 路由在事件循环上跑同步 SQLite/scrypt 造成的全局卡顿、若干实锤功能性 bug（管理端统计恒为 0、admin 页退出登录 404、hot100 到期双计）、README 对外数字失真、无 CI 与 dev 依赖声明等工程效能短板。

## 二、高优先级问题（P1）

### P1-1 公开仓库包含生产服务器完整运维信息 ⚠️ 最高优先级

- **位置**：`docs/InterviewForge-SSH部署与版本更新指南.md:3-5, 17-21, 121-122`（已确认被 git 跟踪，最近提交 `5106af4`）
- **证据**：文档写明 "Hostinger 吉隆坡 VPS（76.13.217.130）…… `ssh root@76.13.217.130`"、应用目录 `/opt/interview-forge`、服务监听 `127.0.0.1:8765`、`filebrowser` 公网 8899 端口、`openclaw-gateway` 本机 18789~18792，以及备份与回滚全流程。经实测 `github.com/lijihao-0804/interview-forge` 为 **Public** 仓库。
- **影响**：任何人都拿到了这台 VPS 的完整攻击侦察资料：root 入口（若未禁密码登录则是直连密码爆破面）、部署路径、同服其他服务的公网端口。
- **修复建议**：
  1. 立即将该文档移出公开仓库（转 private 仓库或删除）；
  2. 由于 git 历史已公开，视为"信息已泄露"处理：root 改密钥登录 + 禁密码、检查 8899/18789-18792 端口暴露面、必要时更换 IP；
  3. 历史清理需 `git filter-repo`（注意这会改写历史，需与远端协调）。

### P1-2 nginx 疑似直接以仓库目录为静态根，可能暴露 auth.db、用户库与 .git（需上服务器核实）

- **位置**：`docs/InterviewForge-SSH部署与版本更新指南.md:46`："只改了纯文档/前端静态页时，`git pull` 后**不需要重启**（nginx 直接发新文件）"
- **影响**：这句话暗示 nginx 配置里存在以 `/opt/interview-forge` 为 root 的静态 location。若属实，则 `/data/auth.db`（账号、scrypt 哈希、**全部 30 天有效 session token**）、`/data/users/<用户名>/*.db`（含明文力扣 Cookie，见 P1-3）、`/.git/`（整库源码与历史）都能被直接下载——应用层虽有 `_sensitive()` 门禁（`interview_forge/api/routers/static.py:41-57` 会拦截 `/data/`、`/.git/`、`/docs/`），但那只对经过 FastAPI 的请求生效。仓库是直接 `git clone` 到 web 目录的，`.git` 就在 web 根下。
- **修复建议**：立即核实 `/etc/nginx/sites-available/hot100`。若存在静态 root：必须加 `location ^~ /data/ { deny all; }`、`location ^~ /.git { deny all; }`（以及 `/docs/`、`/tools/`），或全部流量改走 `proxy_pass`。**本条无法在本地代码库证实/证伪，是当前最需要人工确认的一条。**

### P1-3 用户 LeetCode 登录 Cookie 明文存储

- **位置**：`interview_forge/services/leetcode.py:123-137`（`set_credentials` 将用户提交的 `LEETCODE_SESSION`/`leetcode_csrf` 原样 `INSERT INTO credentials`）；旧版 `interview_forge/server/study_server.py:25` 注释自述"明文保存在本机"。
- **影响**：`LEETCODE_SESSION` 是可直接登录用户力扣账号的活会话凭证。任何拖库/备份泄露/共享 VPS 上的其他本地用户，读取 `data/users/*/` 即可获得全部用户的力扣会话。讽刺的是，同项目对 AI provider API key 已有完整 Fernet 加密基建（`interview_forge/ai/config_store.py:139-165`），却未用于此。
- **做得对的部分**：凭证不回显（`/api/leetcode/status` 只返回布尔）、日志键名脱敏覆盖 `leetcode_session|cookie|token`（`observability/logging.py:27-32`）。
- **修复建议**：复用现成 Fernet 基建加密 credentials 表的 value；`data/` 目录权限收紧为运行用户独占；`/api/export?kind=db` 导出整库时剔除 credentials 表（当前会导出明文 Cookie 副本）。

### P1-4 AI 聊天无任何每日配额与用户门控，上游 token 消耗不可控

- **位置**：`interview_forge/api/routers/chat.py`（全文件仅 `require_user`）；`interview_forge/ai/chat/service.py:482-840`（`stream_reply` 只检查 `config.enabled/configured` 与并发声明锁，全流程无 quota 调用，grep 证实 chat/ 目录无 "quota"）。
- **对照**："一键分析"路径有完整的每日配额 + beta 门控（`ai/tasks.py:511-516`、`ai/ai_coach.py:130`，`AI_DAILY_LIMIT = 3`）；管理端 `/api/admin/users/ai-quota/*` 只对分析生效。
- **影响**：AI 启用后任何登录用户可无限次流式对话（仅受全局并发 2 与单会话串行限制），恶意用户可用多会话打满并发持续消耗上游 API 费用；管理员的"每日上限/重置"对聊天完全无效。
- **修复建议**：为 chat 增加按用户每日计数（可复用 `ai_daily_quota` 表加业务维度），或在 `stream_reply` 的 `_try_claim_model` 前做原子配额检查；至少在 UI 明示"每日上限仅限一键分析"。

### P1-5 SSRF 防护代码已写好但未接线：生成路径不受保护

- **位置**：`interview_forge/ai/config_store.py:121-123`（`validate_network_target` 注释明确"解析后拒绝不安全地址"，但 **全仓库无任何调用方**）；保存入口 `create_provider`（config_store.py:360-381）只做 URL 形状校验；真实聊天/分析流量走 LangChain `ChatOpenAI(base_url=...)`（`ai/providers/chat_model.py:22-23`），无 pinned transport；云元数据黑名单只存在于探针路径（`network.py` 的 `PinnedHTTPTransport`，仅 4 个探针点使用）。
- **影响**：拥有 admin 权限者可保存一个解析到 `169.254.169.254`（云元数据）或内网地址的 provider，聊天/分析流量与 `discover_models`（带有限内容回显）都会直接访问该地址。单管理员自托管场景风险有限，但项目支持多管理员。
- **修复建议**：在 `create_provider`/`update_provider` 中调用 `validate_network_target(base_url)`（代码已存在，只差接线）；生成路径复用 `PinnedHTTPTransport` 或至少复用解析校验结果。

### P1-6 多个 async 路由在事件循环上直接跑同步 SQLite / scrypt / 全量分析，阻塞整个进程

- **位置**：
  - `interview_forge/api/routers/analytics.py:84-87, 102`：`compile_learning_context(analytics_cached(...))` 会全量读 4 张表并对每一行做 canonical-JSON 哈希（`analytics/cache.py:137-145`、`analytics/learning_analytics.py:139-173`、`metrics.py:180-215`），重度用户可达数百毫秒；
  - `interview_forge/api/routers/auth.py:60, 81, 100, 126, 141, 172`：登录（scrypt 校验 + auth.db 读写）、注册、登出、写 150KB 头像 BLOB、改密码、反馈全部同步执行；
  - `interview_forge/api/routers/admin.py:122-128`（`_admin_write` 直接执行含 scrypt 的操作）；`routers/leetcode.py:60-64, 117-119`；`routers/chat.py:35`；
  - 另外**每个**请求的 `require_user → session_user`（`api/support.py:44-61`）都会在事件循环上打开一次 auth.db。
- **影响**：单进程 uvicorn 共享一个事件循环，阻塞期间所有请求（包括正在进行的 SSE 聊天流）排队。对照：学习类 POST 路由已正确走 `run_in_threadpool`（`routers/study.py:305`），AI chat 内部全部 `asyncio.to_thread`——说明团队知道正确做法，只是没有推广。
- **修复建议**：把上述路由统一沉到 `run_in_threadpool`/`asyncio.to_thread`；补一条"async 路由不得在 loop 线程执行 DB"的架构断言测试（可仿照 `test_architecture_v2.py` 的源码扫描法）。

### P1-7 前端：admin.html 两处跳转 `/login.html` 是不存在的路径，退出登录直接 404

- **位置**：`pages/admin.html:616`（`location.replace("/login.html?next=/admin.html")`）、`:623`（登出后 `location.replace("/login.html")`）。服务端公开页只有 `/pages/login.html`（`api/routers/static.py:23, 133`）；同文件 `:304` 用的是正确路径。
- **影响**：管理员退出登录 → 404；管理员会话过期 → 经登录页登录成功后再 404。
- **修复建议**：两处改为 `/pages/login.html`（带 `?next=` 编码）。一行级修复。

### P1-8 对外宣称数字失真：README/搜索页声称 709 章，实际 736 章，且根因是模板硬编码

- **证据**：`library/manifest.json` 37 模块共 **736** 章、`library/search-index.json` 也是 736 项；而 `README.md:3,24,30,169` 与 `guide.html` 多处写 **709**。根因：README 模板把数字硬编码在 `scripts/build/build_hot100.py:1108,1129,1135,1258`，新增章节后未同步；`check_hot100.py` 没有"README 数字 vs manifest"对账，校验不拦截。
- **修复建议**：章节数改为由 manifest 动态注入；`check_hot100.py` 增加一条 summary 对账断言。

### P1-9 校验/测试依赖未声明 + 完全没有 CI 与 lint 基础设施

- **证据**：`requirements-server.txt`、`requirements-ai.txt` 均不含 `beautifulsoup4` 与 `pytest`，但 `scripts/check/check_hot100.py:41` `from bs4 import BeautifulSoup`（共 5 处 import）、pytest 是唯一质量门载体——新环境按文档装完依赖后，"errors: 0" 门禁直接 ImportError 跑不起来。同时：无 `.github/`、无 `pyproject.toml`、无 ruff/black/mypy/pre-commit 配置；`check_hot100.py` 注释自称"退出码 1（CI 判失败）"但仓库根本没有 CI 消费这个退出码。
- **修复建议**：新增 `requirements-dev.txt`（pytest、beautifulsoup4）；建立最小 CI：`pytest -q` + `python tools/check_hot100.py`（断言 errors:0）+ `node --check` 三步，再加零配置 ruff。

## 五、确认做得好的方面（正面结论）

审查中逐条验证过、无需担心的方面（引用位置供复查）：

1. **密码与会话基本功**：scrypt（n=2^14、随机盐）+ `hmac.compare_digest` + 登录防时序侧信道假校验（`services/auth.py:251-264, 348`）；token 用 `secrets.token_urlsafe(32)`、每日清理过期、改密码/停用吊销全部会话。
2. **SQL 与 IDOR**：全库参数化，仅有的 f-string SQL 拼的是代码内常量列名；所有业务数据按会话用户名推导的 per-user DB 隔离，**没有任何以请求参数指定 user 的写接口**；admin 接口路由层 + service 层双重校验角色。
3. **路径与请求体**：静态服务先 `resolve()` 再强制前缀在 ROOT 内，`_sensitive()` 双重 unquote + normpath 拦截 `/data/`、`/.git/` 等；`read_json` 限长 1-4096 字节、拒绝 chunked、校验声明长度。
4. **日志脱敏**：JSONL 日志对 password/token/cookie/prompt 等键名统一 `[redacted]`（`observability/logging.py:27-56`）。
5. **AI 密钥与注入防御**：API Key Fernet 加密落盘、无任何回读通道、日志硬过滤 24 个内容字段；untrusted 上下文显式放 user 消息并加"不是系统指令"框架；ACTION 工具强制人工确认、执行只读服务端持久化的 canonical 参数；工具循环有 max_rounds=3 / max_calls_per_turn=6 / 相同调用去重硬上限。
6. **配额原子性**：`ai_daily_quota` 在每用户独立库、`BEGIN IMMEDIATE` 内条件 UPDATE + rowcount 判断，并发请求无法绕过预留。
7. **前端 XSS 纪律**：30 处 innerHTML 使用点逐一核对，用户可控数据一律 `esc()`/`textContent`；AI markdown 先转义后渲染、链接协议白名单拒绝 `javascript:`/`data:`；postMessage 严格校验 origin。
8. **service-worker 策略成熟**：网络优先、API 不缓存、activate 清旧缓存、非导航失败不回退 HTML。
9. **时区治理**：`assets/time-utils.js` 用明确契约（naive = +08:00）+ Intl 固定 `Asia/Shanghai`，全站统一入口，并有专门测试覆盖 UTC 午夜边界。
10. **事务与调度**：关键写路径全部 `BEGIN IMMEDIATE` + 部分唯一索引双保险，有 40 线程并发回归测试；复习间隔（题 1/3/7/15/30/60、章 3/7/15/30/60/90）与文档一致且有边界测试；力扣轮次从 AC 自然日 `COUNT(DISTINCT date(...))` 派生，天然防重复推进。
11. **analytics 读侧工程质量**：只读打开、锁错误转 503 + Retry-After、脏数据进 `data_quality` 不抛异常、规则版本对配置哈希防 ID 复用。
12. **仓库卫生**：git 历史无任何 .db/.pem/.env/pyc 曾被提交；`.gitignore` 覆盖完整；tools→scripts 重构为 6 行薄 shim 且有兼容测试。
13. **校验脚本覆盖面**：题号/围栏/必需章节/全站本地死链/HTML 结构/重复 id/Mermaid 渲染回归/vendor 字节一致性/`node --check` JS 语法，同类脚本中属上乘。
14. **测试规模健康**：41 个测试文件、389 项收集 1.52s 成功，抽样运行通过。
