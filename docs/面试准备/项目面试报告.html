一分钟自我介绍

你好，我关注后端和 AI 应用开发。InterviewForge 是个面试学习平台。刷题时，我可能刚在力扣通过一道题，却觉得明天还得再练。系统把提交结果和本人评分分别留下，根据评分安排复习。

比如在题页点“忘了”，FastAPI 会在个人 SQLite 库的一个事务里更新复习卡和评分日志，再把下次日期返回。之后问助手“该复习哪几题”，它可以查真实队列。要把一道题排进明天的计划，服务端先存待确认操作，点确认才会写入。

这里有两个值得展开的问题。同一天重复点击怎么算？模型给出建议之后，哪一层保证它不会擅自改计划？

如果有三分钟，接下来怎么讲？

再用一分钟讲一个冲突。 上午同步力扣得到自动 Good，下午自己点“忘了”。如果两个评分都累加，调度器会把一次练习算成两次。手动评分需要回到自动评分之前的状态重算，当日保留一条评分日志。

最后一分钟交给证据。 打开覆盖同日评分的测试，再打开聊天工具的确认测试，指出一处能推翻自己说法的断言。谈个人贡献时，补上本人实际作出的决定、改动或验证过程。

画出系统边界

先在白板上标出公开内容、个人学习事实，以及一次模型请求能看到的资料。公开页面可以由构建产物提供。涉及个人进度后，账号和事务就参与进来。

构建期内容
Python 构建脚本生成页面、章节路由清单和搜索索引。当前清单有 49 个模块、880 条章节路由。搜索索引另收录题页，共 1201 项。游客可以直接阅读公开页面。
HTTP 与身份
FastAPI 将静态内容、学习、聊天、分析等入口分到各自路由。认证库维护账号与会话。服务端根据已认证用户名选择用户库，客户端提交题号或会话 ID，无须也无权指定数据文件。
个人学习事实
个人 SQLite 保存提交、复习卡、评分日志、聊天消息与待确认动作。学习服务读写这些记录。每用户一个文件简化单机部署，也意味着跨账号统计与备份得处理多个库。
AI 运行时
ChatService 收集本题需要的资料，模型适配器负责接入供应商，工具运行时校验参数和权限。长回答走 SSE，复习调度或设置写入各有业务函数。

“能在线练代码”这条支线属于哪一层？

登录用户从练习页发送 Python 或 Java 代码与样例输入。/api/practice/run 校验语言和字节上限后，把固定结构的请求交给单独的 runner。Linux runner 负责沙箱执行并收集退出状态和有界输出。练习区按可见样例判定结果，覆盖范围取决于样例。这一服务和 AI 工具执行各有入口。

为一道题评分

第 1 题《两数之和》有四档评分。点击“忘了”属于用户对记忆的判断，即使今天已经通过过这题，这个判断仍然有价值。

  1. 浏览器发出业务意图。 recordReview 确认登录并向 POST /api/complete 提交题号和评分。后端的 _write_json 在认证后解析请求，将同步业务调用交给线程池。
  2. 写锁包住读、算、写。 complete_round 使用 BEGIN IMMEDIATE，在同一个用户库里核对北京时间的完成日期、现有卡片和最近的评分日志。同一目标当天再次手动评分会沿用第一次手动结果。
  3. 按来源解决冲突。 如果当天先从力扣 AC 推出自动 Good，后来的手动评分会使用旧日志保存的前置状态重算，替换该日志。相反的顺序则保留手动结果。兼容接口仍可保留每次提交尝试，次数与复习轮次各有含义。
  4. 把决定返回给人。 FSRS-4.5 根据评分、稳定性、难度、经过天数和目标保持率更新 review_cards 与 review_logs。事务提交后使学习缓存失效，前端展示服务端返回的 next_due。

用一个测试，把“自适应”讲具体

固定时间为 9 月 7 日，目标保持率取 0.9。两张独立的新卡首次评分，选择“忘了”的卡 9 月 8 日到期，选择“很轻松”的卡 9 月 21 日到期。第三种情况是同一张卡先手动点“忘了”再点“很轻松”，当天仍保留“忘了”且只有一条评分日志。这些日期是固定输入下的调度输出。

向助手提问

在同一个聊天框输入“解释 TCP 三次握手”和“给我看五道待复习题”，分别需要通用知识和此刻的个人队列。两者发往同一个端点。服务端选择上下文及可用工具，模型可以在绑定的目录中提出调用，服务端再决定这次调用能否执行。

  1. 从 HTTP 到本轮消息。 浏览器用 fetch 向 POST /api/chat/sessions/{session_id}/stream 发文本与可选页面信息。路由检查账号、会话与模型配置，随后扣聊天日配额。ChatService 先占用会话，再保存用户消息并发出 message.start，随后尝试领取模型调用槽。
  2. 选择应带入的历史。 ContextBuilder 按消息 ID 截取本轮之前的记录。话题由用户消息建立。切换到新的独立问题会跳过不相干的旧内容。“它的复杂度呢”会优先接回最近话题。浏览器残留的选区要与当前提问相关，才加入页面资料。
  3. 读取本人的事实。 明确的学情意图可以预先编译精简的学习资料。模型也可以选择 get_review_queue(limit=5)，经参数校验后从当前用户库读取队列，将到期日、补练原因和标记等作为工具结果回给模型。普通技术问答无需预取个人学情。
  4. 完成与持久化。 message.delta 增量送到浏览器。前端以约 100 毫秒间隔合并纯文本预览，结束时渲染完整 Markdown。正常有文本的回答保存为一条助手消息，再发 message.done。必要时，前端也能重新读取已存消息。

预算为什么要在每次实际调用模型之前再算？

第一次组装后，模型还可能发出调用，工具响应也会变长。admit_request 统算消息、工具定义、调用参数和完整结果。已知模型窗口时先预留输出空间。旧对话按用户轮整体淘汰，调用与对应结果一起保留。系统指令、完整当前问题和本轮工具交换是必需项。如果放不下，编排器返回预算错误，该次不会调用供应商。这样可以保住长问题末尾的限制。

默认策略允许至多 3 个可用工具的模型轮次、合计 6 次工具调用、同时至多 3 个只读工具。当轮次等限制生效时，还可有一次关闭工具的收尾回答。token 只作本地估算，供应商实际用量和模型能力目录仍要分开看。

逐轮请求预算工具上限实际调用与收尾完整交换与溢出测试

聊天、长期记忆和一键学情分析分别给出什么？

聊天按当前任务重建输入。长期记忆单独存储，以当前任务相关性选择适用偏好。用户说“请用 Python 举例”可以是适用偏好，不能据此推断他今天做过某道题。

一键分析另走 POST /api/coach/analyze。确定性编译器将个人统计整理成快照，验证器检查薄弱项和数据型建议是否引用本次快照中的 support_refs。启发式建议单独标明。一个引用 ID 真正存在，只能证明能定位该依据，推论是否合理仍需评估。

找一段站内资料

假设面试官把问题改为“我想看站内讲 TCP 的原文，给我一个能打开的章节”。聊天需要带回书架提供的标题、链接和索引片段。使用关键词 TCP，当前书架索引的首个标题命中是《TCP 与 UDP》，位于“计算机网络”模块。

  1. 沿用书架搜索。 默认工具目录中的只读工具 search_library 直接调用站内搜索函数。搜索用不区分大小写的连续字串匹配，标题、模块名、索引正文的命中权重依次为 3、2、1。正文命中时截取附近片段，仅标题命中时片段可能为空。
  2. 限定模型能拿走的内容。 关键词或短语限 1 至 120 个字符。最多返回 3 条命中，可以请求更少。没有匹配时返回空列表。每条索引片段最多 200 个字符。工具把索引地址转为规范的站内 HTML 路径，过滤无效命中并按地址去重。索引足以回答“去哪里读”，要读完整段落则打开原页。
  3. 让出处跟着实际工具结果走。 编排器按调用顺序收集进入累计结果预算的资料，按 URL 去重。助手回答成功入库后，message.done.library_sources 与用户库的 chat_messages.metadata_json 提供相同的资料清单。前端用标题、模块名、地址渲染“本轮检索资料”，刷新后从历史恢复。索引片段供模型判断相关性，资料清单只保存定位原页所需的三个字段。

面试官问“资料清单能证明什么？”

它能让人打开这轮实际提供给模型的站内资料，检查回答是否与原文一致。一条章节链接只能定位候选资料。要判定回答里某句话是否有充分依据，还要核对对应段落。这一版用词面搜索，关键词的同义改写也可能漏召回。

从例子回源码《TCP 与 UDP》原页索引排序检索与站内地址结果预算与出处收集出处渲染

为什么这条测试里调用了三次工具，用户只看到两个链接？

受控模型在同一轮分别检索“TCP”“线程池”“TCP 与 UDP”。三条工具观察都送到模型，其中两条指向同一 TCP 章节。最终的资料列表按 URL 合并为两条，重新读取聊天历史仍是同样两条。把结果预算压低，模型收到预算错误，完成事件和历史记录里都不再出现那个来源。索引读取失败或模型未能完成回答，也不会冒出一条没有对应回答的出处。

如果供应商无法绑定工具，编排器退回文本流，明确告知模型站内检索不可用。这条分支也先检查请求预算。需要站内出处的问题应向用户说明资料暂不可取。

搜索参数、索引与真实目标观察、完成事件与个人历史的对应断言

确认一次写操作

用户接着说“把第 1 题排进明天的计划”。这次会改变个人数据，真正具有写入权限的是服务端业务函数。前端展示的确认卡对应一条已持久化的操作。

模型提出
编排器收到 pin_problem_for_tomorrow(problem_id=1)。服务端按工具的 Pydantic 参数模型校验，在当前用户库写一条 pending 状态的 chat_action_requests 记录。同轮、同工具、同规范参数可复用待确认行。
用户确认
tool.confirmation_required 携带确认信息。用户点击后，浏览器另发 POST /api/chat/actions/{action_id}/confirm。接口只接受空参数体，执行参数从先前保存的行读取。刷新页面可通过待确认列表重新找到卡片。
服务端领取
claim_pending 条件更新同一个 ID、状态仍为 pending 且尚未过期的行。成功领取者才执行，并记录结果。再次确认已经成功的行会复用已存结果。当前账号之外的数据文件不会因猜中同一 ID 被打开。
后续动作完成
安排明日计划可在本次执行中完成。换成 sync_leetcode 时，处理函数先返回后台任务 ID 和 started。同步任务结束后才把完成、部分完成或失败状态合并回来，供下次查询或追问使用。

源码与断言实际业务动作待确认行与条件更新确认执行读取动作最终状态重复、取消及跨用户测试

确认成功，但在外部动作执行后、结果落库前进程退出怎么办？

条件更新可以挡住并发点击。若外部系统已接受动作，当前进程还没存下最终结果就退出，本地状态就有不确定窗口。排障要先查任务 ID 和下游记录。若业务将来要求崩溃后自动恢复，应让下游支持幂等键或结果对账，再设计恢复执行。

两次故障复盘

一次问候为什么引出了旧学习计划？

现象。 11 月 13 日的脱敏审查记录里，一次长会话间隔约 23 天后只收到简短问候，回答却带出了之前的算法与学习规划。当时涉及审查的库里没有长期记忆记录。

诊断。 旧链路按近期消息与容量取历史。上一轮助手自己扩展的内容，可以作为下一轮的背景再次出现。旧摘要跨多个话题，单纯缩短窗口仍可能留下旧主题。当时的 trace 未保留完整请求，单个模型句子的成因无法唯一还原。

修法和验证。 用用户消息建立话题锚点。新话题跳过无关摘要，真追问保留相应片段。只有相关时才加入页面或待确认状态。回归测试既检查“换题不带旧内容”，也检查“继续解释”仍有指代对象。实测对象是模型入口的消息，线上回答污染率需要单独抽样。

当时的观察、样本与局限实际组装换题、短追问与页面切换

为什么 150 个虚拟用户让人误判成服务端瓶颈？

现象。 10 月 3 日的一轮健康检查压测中，高并发下延迟显著增加。若马上调数据库，就跳过了发压端本身排队的可能。

对照。 同一台 VPS 的回环接口，保持 150 个虚拟用户、约 6 秒窗口和同一个服务，改变发压客户端的连接池划分，并在压测进程内计时连接分配函数。

改变客户端就能显著改变测量值，原样本不足以推出服务端硬连接上限。同样也推不出 AI 聊天容量。若要回答聊天能承受多少并发，应测真实请求形状、流连接时长、模型等待和错误率。

连续追问

先自己回答，再展开。每题的第二问都要求说出哪一层兑现了前一句承诺。

用了 LangChain，项目里还自己实现了什么？为什么要限制循环？

模型接口负责表达工具定义、绑定和传输调用。项目自己定义每项工具的参数、读写类别、超时、结果限额与确认流程，还要把回复和事件映射到前端。若模型重复调用同一个工具，先用校验后的默认参数做规范化，再计数。读工具在本轮内可复用结果。达到限制时，编排器给每个未执行调用补上有明确错误的工具响应，最后可关闭工具生成收尾文本。

工具目录工具执行超限、取消与只读并发

为什么用 SQLite？四个 worker 会把同一天重复算四次吗？

读写集中在单个用户，独立文件适合当前部署。WAL 让读和写有较好的重叠，同一数据库文件依然要串行写入。评分判断与更新同处写事务，即使两个请求到了不同进程，也会读到前一个提交后的状态。模型并发槽在共享模式下另用 OS 文件锁协调。_claim_session 的集合是进程内的，跨 worker 的同会话互斥还需要共享机制。

数据库初始化会话占用跨进程模型槽与缓存测试

助手说“同步完成”，用户却没看到新记录，先查什么？

先分清本轮处在等待用户确认、操作被领取、后台任务执行或数据落库的哪一步。查持久动作行与后台结果，前者的 succeeded 可能只表示启动成功。若第二页拉取失败，任务可能保留已取到的记录并标记部分完成。只有任务最终结果给出成功，才能答“同步完成”。历史动作缺最终结果时就回答未知。

分页、进度与后台结果后续页失败的处理旧操作状态的回答依据

算出输入指纹，可以还原当时的 prompt 吗？

准备上下文的 hash 标识组装好的 messages，配置指纹来自已审定的非敏感字段，每轮请求指纹再覆盖实际准入后的消息和工具 schema。它们适合核对“两次输入或配置是否变化”。哈希不携带原文，trace 也有元数据白名单。完整重放仍需要原始输入、配置、工具响应、模型版本与运行条件。

trace 元数据准备、配置及请求身份测试

为什么用 SSE？用户按下停止，哪里已经停了？

一次用户提问后，大量小事件由服务端单向发回。用 POST 提交问题和页面信息，用 fetch 读返回流，命名事件承载文字和确认卡。用户确认另发 HTTP 请求。停止会中断浏览器请求，服务端可关闭异步生成器并清理当前批的任务。已经启动的同步线程或外部工作有自己的生命周期。实测的 1000 个瞬时 delta 合并为 1 次预览刷新，只说明突发合并路径生效。

心跳、断开与清理流式渲染实验

下一步如何判断要不要做向量检索？

先从术语精确命中、中文同义改写、跨章节问题、无合适资料四类真实提问取样，分别标出可接受章节。固定题集、预算和候选数，再比较词面检索与候选语义方案的命中、错引、时延及成本。还要单独检查回答的陈述是否被引用段落支持。当前可验证的是站内关键词检索和来源传递。
