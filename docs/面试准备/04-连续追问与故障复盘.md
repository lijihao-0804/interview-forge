# 连续追问与故障复盘

基线：`2b01df99`，2026-10-02。以下是依据项目事实编排的模拟对话，不是声称曾在某家公司发生的真实面试。先自己回答，再对照“落点”；不要照念面试官台词。

## 1. “你说做了 Agent，那我不断问为什么”

**面试官：先说业务，再说架构。**

落点：用户要基于实际学习记录理解薄弱点和复习安排；静态内容、动态事实、AI 解释分开。不要以“现在大模型很火”开场。

**面试官：不用 Agent，用普通 API 或规则能不能做？**

可以。评分、权限、复习日期与任务执行本来就用规则。需要自然语言理解、多个只读查询和结果解释时使用受限模型工具循环。不是每个功能都值得让模型规划。

**面试官：模型想改计划怎么办？**

提出 ACTION 后生成持久 pending 行，用户确认 action_id，服务器条件领取并执行。模型没有直接改库的权限。

**面试官：你用了框架，自己做了什么？**

指向 ToolRuntime、ContextBuilder、ActionRequestStore 和 SSE 前端；讲清参数校验、并发限制、确认状态与持久化。根据本人实际参与再讲贡献，不以“框架调用很多”替代设计说明。

**面试官：写操作成功但落库前崩溃呢？**

承认存在跨系统不确定窗口。pending 条件领取解决的是并发点击；下一阶段需要下游幂等键/状态查询和执行恢复。把范围说准，比回答“有锁所以只会执行一次”更好。

准备展示：[ToolRuntime](E:/interview-forge/interview_forge/ai/tools/runtime.py)、[ActionService](E:/interview-forge/interview_forge/ai/actions/service.py)。

## 2. “你说优化了流式性能，把证据拿出来”

**面试官：用户看到的现象是什么？**

回答较长时，滚动和 Stop 操作可能变迟钝。源码热点是 delta 中全文 Markdown、innerHTML 重建和 scrollHeight 读取。

**面试官：为什么接近 O(n²)？**

若累计长度随 n 个 chunk 线性增长，且每次都处理从头到当前的全部长度，总量近似 `1 + 2 + ... + n`。实际 parser 复杂度和 chunk 大小不同，所以说“重复扫描接近二次增长”，不假装证明所有浏览器行为严格 O(n²)。

**面试官：你用了 requestAnimationFrame，不还是每帧全文渲染？**

RAF 只负责合并滚动；文本预览另用约 100ms scheduler，流中不做完整 Markdown。done 才做一次完整格式化，正常结束不重拉历史。

**面试官：优化后复杂度严格 O(n) 吗？**

不能这么说。100ms 预览仍设置累计全文，持续很久的回答仍有重复文本处理；主要消掉逐 delta 的昂贵 Markdown/DOM 重建，并降低频率。若将来极长输出仍有瓶颈，可以研究尾部追加、分块或虚拟化，但要先测，且注意代码块/表格跨块语法。

**面试官：你给的一次刷新是怎么来的？**

同步瞬间送入 1000 delta，timer 合并到一次预览。本次 harness 实际输出 `delta_count=1000, render_count=1`。它是突发调度证据，不是 paced streaming 或真实浏览器耗时评测。不要用一次测试的 max_render_ms 对外许诺性能。

准备展示：[scheduler 与 harness](E:/interview-forge/tests/test_ai_assistant_streaming.js)、[前端实现](E:/interview-forge/assets/ai-assistant.js)。

## 3. “你说同步可靠，为什么用户还是看到失败？”

**面试官：首先怎么定位？**

查任务创建/开始/结束时间、错误类别、服务实际 Python 环境和上游响应类型。页面“很快失败”或管理员表格 `0ms` 只是线索，也可能来自短耗时取整、早期校验或快速 challenge，不能据此认定根因。

**面试官：403 就是 Cookie 过期？**

不一定。检查 Cloudflare 特征、content-type 与安全错误分类；401/403 与明确未登录响应、challenge 页面要分开处理。建议成对更新 SESSION/csrftoken，更新后仍 challenge 再排出口网络。

**面试官：为什么别人可以同步？**

先比较账号凭证状态、请求阶段、任务模式和依赖运行环境。不同人不同时间成功，不证明所有同出口请求必然成功；也不证明问题一定在单个用户。按证据缩小，不凭感觉二选一。

**面试官：第二页失败怎么办？**

保留已取得的数据，标记 partial/degraded，带续传位置；前端刷新本次已经改变的数据，并显示部分完成。

**面试官：你增量是不是完整的？**

当前只取最新一页，最多 100 条，超过此窗口可能漏更旧新增记录。这是明确边界，需要全量回填。不能因为做了 cursor 就把所有同步模式都说成完整续传。

准备展示：[错误分类、分页与任务](E:/interview-forge/interview_forge/services/leetcode.py)、[reliability tests](E:/interview-forge/tests/test_leetcode_reliability.py)。

## 4. “AI 说成功了，但用户说没成功，谁对？”

**面试官：先解释三种成功。**

HTTP 受理成功、Action 确认处理成功、后台同步任务成功，不能互相替代。模型说过的内容也不是事实来源。

**面试官：旧聊天怎么影响这次判断？**

历史 assistant 可能曾误报，或把几天前的动作当成当前。当前上下文需要服务端新查询的 pending 与 recent action 投影，附时间和最终状态；如果没有最终结果就写未知。

**面试官：前端不显示确认卡呢？**

从网络事件、actions 接口、session/user 一致性、持久 pending 行、前端渲染、滚动与层级逐层查。确认卡应是结构化事件/状态的呈现，不是从模型“请点击确认”这句话解析出一个按钮。

**面试官：多发一次请求不就好了？**

只有当前真实没有 pending、旧操作失败/过期或用户明确重新请求时才讨论新 action。仅根据历史模型文字判断“一直在等确认”会把用户困住；也不能默认重复提交就能修复 UI 丢失。

**面试官：你能保证模型再也不误报？**

不能保证自然语言永远正确。可以改善权威数据投影和提示约束，再用固定场景评测误报；真正的按钮状态和任务完成仍由服务器状态决定。

准备展示：[RecentActionContext](E:/interview-forge/interview_forge/ai/chat/recent_action_context.py)、[action follow-ups tests](E:/interview-forge/tests/test_action_list_followups.py)。

## 5. “数据正确性：缓存、并发、调度一起问”

**面试官：管理员设置保持率，为什么有时不生效？**

要检查从设置存储到评分调用的完整传参链。当前路由实时读设置，兼容完成函数漏传时也读设置；纯 FSRS 计算要求显式参数。不是只在管理页面显示保存成功就算闭环。

**面试官：改设置是不是把旧 due 都改了？**

没有。它只影响下一次评分。批量重排可能突然改变大量用户今日复习量，要作为独立产品行为设计。

**面试官：迁移怎么不损坏旧记录？**

先有备份，迁移按旧间隔和完成日期建立卡片，保留已有 due，不制造虚假 review_log，INSERT OR IGNORE 不覆盖已有 FSRS 状态，测试重跑不改变既有卡。

**面试官：两个请求同时评分呢？**

在写事务内做同日检查，不依赖前端禁用按钮；第二个返回既有状态。SQLite WAL 不是多写并行，事务不能夹外部模型调用。

**面试官：缓存为什么没马上更新？**

查看业务写 commit 后的学习缓存失效、客户端乐观更新/回滚以及模块刷新。HTTP ETag/SW 与学习数据缓存是不同层，不能把所有 stale 问题都归为浏览器缓存。

准备展示：[FSRS migration tests](E:/interview-forge/tests/test_fsrs_migration.py)、[study service](E:/interview-forge/interview_forge/services/study.py)。

## 6. “下次用户翻十倍，怎么改？”

**面试官：先加 Redis、MQ、微服务行不行？**

先知道瓶颈在哪里。要补代表性负载，区分 API、同步任务、长连接、LLM 等待、SQLite 写锁和前端性能。当前没有真实 QPS/P99，不能先说 Redis 一定解决。

**面试官：直接开四个 worker？**

目前进程内会话占用、模型并发控制和力扣任务字典有边界。多进程必须先将需要全局成立的任务领取与并发状态移到共享存储；各用户库迁移还需处理多进程首次连接竞争。

**面试官：存储怎么迁移？**

围绕认证、学习和 AI 各自数据 ownership 抽接口，建立集中数据库的用户隔离、索引和事务；用影子读或离线比对验证，再决定切换。现在只能讲演进方案，不能说已具备这套能力。

**面试官：要测哪些指标？**

端到端延迟与错误率、SSE TTFT/完整 turn 时长、任务排队时间、锁等待、活跃连接、模型 token 成本和浏览器长任务。必须明确每项起止点；middleware 记录响应创建时间可能早于 SSE 结束。

准备展示：[进程内 task facade](E:/interview-forge/interview_forge/runtime/task_manager.py)、[观测 Trace](E:/interview-forge/interview_forge/observability/ai_trace.py)。

## 7. “前端为什么改 padding 还挡住输入框？”

**面试官：现象和真正根因是什么？**

AI Drawer 的底部被认证胶囊覆盖。认证 Widget 在父页面，z-index 高于 Drawer；不是 iframe 内 composer 高度不足。不断补底部 padding 只能移动内容，没解决层级关系。

**面试官：怎么修？**

Drawer 打开时在根节点设置统一 class，CSS 隐藏父页面的 auth/feedback/theme 及已展开 panel；关闭清理状态恢复。Drawer/backdrop 层级统一高于普通悬浮 Widget。入口按钮仍沿原有 hidden 逻辑。

**面试官：为什么不在 JS 里遍历改 display？**

统一状态交给 CSS，恢复时不需要猜每个组件原 display 是什么，也能覆盖后续动态创建的 Widget。

**面试官：验证组合？**

先开聊天室/Feedback 再开 AI、手机宽度、滚动到底、关闭后恢复。源码约束测试与真实视觉测试互补；最近这轮浏览器工具超时，所以不能冒称本轮完成了全部视觉验收。

准备展示：[ai-launcher.js](E:/interview-forge/assets/ai-launcher.js)、[ai-launcher.css](E:/interview-forge/assets/ai-launcher.css)。

## 8. “你到底贡献了什么，AI 帮你写算不算你做的？”

**面试官：代码是你手写的吗？**

据实说明 AI 辅助程度和自己的职责。可讲自己怎样定义问题、定位根因、约束修改范围、review 补丁和执行验证。不要以“我能解释”自动替代“我独立实现”。

**面试官：怎样证明你理解？**

现场画一条执行链，打开关键函数，解释为什么这个条件在事务内、为什么当前行按 ID 排除、为什么 Stop 不保证同步线程立刻停止。能够指出现有局限，比背一个架构名词更有证明力。

**面试官：你会怎么改进？**

选一个清晰目标，给出最小改动和验证。例如先补 paced stream 和浏览器长任务测量，而不是为了流式优化换整套前端框架；先补模型语义评测，再判断是否需要向量记忆。
