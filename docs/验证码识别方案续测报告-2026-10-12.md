# 验证码静态 OCR 续测报告

日期：2026-10-12。数据仍为原来的 13 张固定图片。

> 本机接入更新：新策略现已接入预约执行器，默认使用双版候选分数整体匹配。静态续测数据保留如下；接入后的回归和浏览器验证见文末“本机全流程接入”。线上部署尚未执行。

## 实测结论

找到了一条比换模型更有效的本地路径：**读取 ddddocr 的候选字符分数，利用提示中已知的目标字，搜索三个不同字框的整体最佳分配**。

在人工核对的 13 张图片上：

- ddddocr 标准版单模型的候选分数匹配：13/13 题位置全对，39/39 个目标字选中正确框，平均约 0.091 秒/题，进程 RSS 约 150 MB。
- 标准版加 beta 的平均候选分数匹配：13/13 题位置全对，平均约 0.193 秒/题，RSS 约 206 MB。
- 字框顺序和目标顺序随机打乱后，双版三轮全部为 13/13；字框向外扩 3 像素后也为 13/13。
- 单图编号拼图加整体分配显著改善 DeepSeek：三轮分别为 11/13、9/13、11/13，平均约 0.72–0.81 秒/请求。但它仍有波动，表现未超过本地候选分数匹配。

这些数字只适用于这组静态图片。方法在这组图片上筛选，尚无独立的新图测试集；三轮重复是同一批图的重复运行，不能算成 39 张独立图片。

## 更正首轮的计分口径

首轮报告的大部分统计只判断“是否分配出了三个目标”，没有人工核对每个目标所分配的框是否正确。因此：

1. “输出三个不同编号”只能叫分配齐全，不能直接叫位置正确。
2. 首轮 tiny 等路线的计数保留为历史分配统计，不能把它们当成已验证的定位准确率。
3. 本轮独立复核了生产本地路线，实际位置正确仍为 9/13，正确目标位置为 34/39。

本轮给每个检测框按从左到右排序编号，人工建立目标字到框编号的答案表。推理只读取图片、检测框和图片提示中的目标字；答案表只用于评分。打乱字框和目标顺序仍保持相同正确率，检查了对固定编号顺序的依赖。

## 为什么候选分数匹配有效

原实现读取模型最终给出的字符串，例如一个字框被输出成拉丁字母或其他汉字，就会直接认为目标字没找到。这个字符串丢掉了模型对其他字符的分数。

新的实验利用了两个已知条件：提示中已经给出三个目标字，并且这三个目标要对应不同字框。具体算法：

1. 用已有 ddddocr 检测器得到字符框。
2. 对每框调用 classification(..., probability=True)，读取完整字符表的时间步分数。
3. 对每个提示字，取它在各时间步上的最大分数，形成“目标字 × 字框”的分数矩阵。
4. 双版情况下，对标准版和 beta 的分数取平均；单版则直接使用其分数。
5. 枚举三个目标在不同字框上的排列，最大化分数对数之和；选出整体最佳的一对一分配。
6. 从选中框计算像素中心，保存静态位置标注图。

这里的分数是 CTC 时间步概率最大值的代理，不是经过校准的“本次定位正确概率”。没有训练新模型，也没有把人工正确框编号提供给识别函数。字符表只需关注提示中的三个字，而不是在约 8210 个字符中仅相信 top-1 输出。

这解释了为什么此前认为“认不出来”的公、令、量等字，在候选限定和整体匹配后能恢复正确位置：它们的候选分数仍足以区分其他框。

## API 请求方式的影响

此次改为：将字框整理到一张统一大小的编号拼图中，要求模型一次性给出三个不同框的分配；使用系统指令和 response_format=json_object 约束输出，关闭 thinking。

相比逐框独立选字，这种方式让模型能对照全部字形，并利用“不同目标对应不同框”的约束。在新增 6 张图片中，JSON 拼图三轮分别有 5/6、3/6、5/6 位置全对，原图加拼图两轮均为 5/6；此前独立字框多图请求的历史结果只达到 1/6 分配齐全。

初始拼图请求仅靠文字要求 JSON，max_tokens=128，模型仍输出解释，有 5/13 次在给出 JSON 前截断。加入系统输出约束、JSON 模式和 512 token 上限后，三轮均无输出截断，实际正文很短。low 推理会修正某些难例，但 2048 token 预算仍被消耗在推理上；19 次 low 试验有 5 次截断，平均耗时显著增加。本轮没有证据支持把 low 推理作为默认快路径。

API 的具体参数以官方 [Thinking Mode 文档](https://api-docs.deepseek.com/guides/thinking_mode/) 为依据；请求正文和处理逻辑见实验脚本。

## 重复性与异常输入检查

| 检查 | 结果 | 含义 |
|---|---|---|
| 原图、双版、随机字框和目标顺序，3 轮 | 每轮 13/13 全对 | 当前方法不依赖原始编号顺序；重复图不增加独立样本量 |
| 字框向外扩 3 像素 | 13/13 全对 | 对这一个裁剪扰动保持结果 |
| 单模型标准版和单模型 beta，基于同一轮分数独立评分 | 均为 13/13 全对 | 此数据集没有显示双版比单版更准；双版可能提供更多互补信息，仍需新图验证 |
| 把一个目标字替换成图中不存在的“猫” | 13/13 仍输出齐全分配；0/13 题全对 | 强制匹配无法自行确认目标确实存在 |
| 从检测结果删除一个真实目标框 | 13/13 仍输出齐全分配；0/13 题全对 | 检测漏框时，算法可能把不存在的正确位置硬分配给其他框 |

正确输入的双版最佳与次佳对数分差范围为 4.34–13.35；删除目标框后的错误分配分差也可达 12.43，两者重叠。正确输入的最小选中字分数约 0.000128，而删除目标框后的错误输入有些最小分数约 0.000361。因此不能简单用一个较大的分差，或未经校准的绝对分数阈值，保证定位正确。

下一步最有价值的是独立的新图盲测，以及包含检测漏框/识别混淆的样本来校准拒绝条件；当前结果不支持宣称未知样本始终 100% 正确。

## 发现的生产分配函数问题

现有 assign_targets 在计算各目标最佳框时检查 used，但 used 在该阶段始终为空；最终写入 assignment 时没有再次检查框是否占用。合成的最小复现中，一个框 std=研、beta=这，两个目标会都被分配到同一个框，返回两个目标却只有一个唯一框。

静态续测阶段仅在实验脚本中实现了真正的一对一整体匹配，记录了上述缺陷。随后在本机接入阶段修复了旧分配器共用字框的问题，并将新算法接入执行器，详情见文末。

## 本机全流程接入

新算法已经接入 interview_forge/services/gym_automation.py，默认策略为 probability。执行顺序为：读取网页图片与提示 → 检测字框 → 提取标准版/beta 候选分数 → 整体一对一分配 → 检查双版位置一致 → 重新核对图片和提示未变化 → 使用最新显示矩形换算坐标 → 按提示顺序点击 → 检查当前页或新标签页的订单确认页。

检测框不足、候选格式无效、字框越界、模型位置不一致、同分分配或选中框缺少候选支持时，不进入自动点击。点击坐标额外检查字框唯一性、显示尺寸和原图范围。上述检查仍不能保证所有未知新图都正确；真实网站的验证结果是下一阶段需要记录的数据。

旧四路识别可用 --captcha-strategy legacy 显式选择；默认路径不初始化 PaddleOCR、不读取 DeepSeek 凭据或发 API 请求。环境自检也将 DeepSeek 凭据列为 legacy 的可选项。验证码刷新失败后转人工处理，不再自动关闭弹窗并重复提交预约。
