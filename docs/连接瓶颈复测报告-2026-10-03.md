# 连接瓶颈复测报告

> 后续已补充协议一致性、客户端CPU与握手配对证据。以《连接悬崖根因与压测修正-2026-10-03.md》为最新结论；本报告保留为初轮测试记录，尤其不要直接比较两个平台默认curl的并发结果。

日期：2026-10-03，北京时间。生产版本：`be63a02161aebcc5cd91fc8f2663ee75ab71752a`。

## 结论先行

外网高并发退化真实存在，但目前没有证据证明它是 nginx worker_connections 或服务器 SYN 队列太小。独立 curl 在 VPS 上 150 并发全部成功；Windows 外网同类请求出现 TLS 失败。HTTPX 的本机持续测试也显著退化，而服务器 nginx 耗时很低，说明客户端调度/连接池因素不能排除。

不能把外网测试中的“约 60 RPS 平台”直接解释为服务器只支持 64 个连接，也不能据此承诺调高内核参数后会释放 1,800 人容量。

未更改生产代码、systemd、nginx、内核或 SSH。仅执行本项目短时只读 GET 测试、采样与一个已授权账号的登录/注销抽验。没有触发力扣、AI 外部调用、学习评分或写入学习状态。登录会话测试后注销。

## 现状核实

- 题解目录有 100 个 HTML；正确授权路径 0001、0108 返回 200。此前“嘈希表”错误 URL 的 404 不是目录缺失。
- systemd 已启用 IF_SHARED_RUNTIME=1 与四 worker；四个 worker 均参与本轮工作。
- LimitNOFILE=524288、TasksMax=19092。
- nginx 全局现有 worker_processes auto、worker_connections 768。768 是每 worker 连接预算，不是全站 64 连接硬上限；代理请求还会占 upstream 连接。
- somaxconn=4096、tcp_max_syn_backlog=1024、syncookies=1；当前 nf_conntrack_max 路径不存在，不能假定已启用后盲写。
- 应用监听 127.0.0.1:8765，监听 backlog 显示 2048，抽查 Recv-Q=0。
- 验收时服务 active，内存可用约 14GB；未发现内存不足证据。

## 方法与限制

复用 scripts/benchmarks/http_load.py 的 run_stage；新增本地 connection_probe_local.py 作为薄包装，不改应用。每档目标 6 秒，50/100/150 VU，HTTPX timeout=10s、连接池 180、关闭环境代理 trust_env=False。错误率 >5% 或 P95>5秒后停止后续加压。实际阶段会等待在途请求收尾，因此时长超过 6 秒。

Windows 外网与 VPS 测试开头存在时间重叠；结果不是严格隔离容量基准。各阶段短、无预热，不能外推稳态、日活或真实在线人数。HTTPX VU 是闭环协程数量，不等于精确实时 TCP 连接数。

独立 curl 使用 --parallel --parallel-max 150、300 个 GET、单请求 max-time 10s。不依赖 HTTPX；这是有限请求突发，不是持续压力或 RPS 标定。未安装新全局工具。

VPS curl exit=0；Windows curl exit=35，表示 TLS 连接错误。不能仅凭汇总码判断全部 27 次失败都是同一根因；尚未保存逐请求握手错误或抓包。没有禁用证书验证。

独立客户端结果明显不同，足以否定“客户端总体 CPU 低，所以完全排除客户端”的论证；总体 CPU 不能排除单线程、事件循环和连接池争用。HTTPX 吞吐不是纯服务端容量。

## 服务端证据

VPS 六档测试窗口的主机 TCP 扩展计数差值：ListenOverflows=0、ListenDrops=0、TCPReqQFullDoCookies=0、TCPReqQFullDrop=0、TCPSynRetrans=0。该计数是主机级、非项目专属，零增量只约束本次采样窗口，不能反证所有历史网络问题。

37.26 秒窗口四 worker 用户+内核 CPU ticks 增量分别为 366、262、515、540。说明四者均工作、负载不完全均匀；未换算 CPU 占比，未连续采样，不宣称均衡或无 CPU 瓶颈。

测试中途汇总本域日志尾部的 5802 条 health：nginx request_time P50=2ms、P95=14ms，>=1秒及>=15秒均为0。这是混合窗口中途快照，不是每条客户端请求的 request_id 对齐。nginx 时间从收到 HTTP 请求后开始，不能覆盖客户端连接池排队、TCP/TLS 建连及请求到达前的延迟。

因此“秒级客户端延迟 = SYN 重传”没有被证据支持。更合理的候选包括：HTTPX 客户端调度/连接池争用、Windows 网络/安全软件/本地代理链、跨境路径与 TLS 建连异常。尚不能在这些候选中选定唯一根因。

1. P0诊断：隔离运行、加预热，使用第二台外网设备/不同网络重复 curl；保留逐请求安全握手错误与连接/TTFB/总耗时，显式记录代理路径。约1–2小时。
