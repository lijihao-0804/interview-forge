> 1. **第五、十三节"03-题解 部署缺失/全线 404"是误报**。根因是本报告构造的探测 URL 存在错别字（`%E5%98%88`=嘈，应为 `%E5%93%88`=哈，即"嘈希表"），该错字从冒烟测试一路带入了所有压测场景；而对照路径"00-总览"恰好拼对返回 200，加深了误判。复测确认：**目录 100 个 HTML 完整存在，正确授权路径返回 200**（复测报告《现状核实》节）。不存在部署缺失。
> 2. **第十三节"连接悬崖 = 服务器 SYN 队列/连接预算不足"的归因被否定，且最终根因已定位（2026-10-03 深夜）：DNS 污染。** 服务器窗口内 `ListenDrops/ListenOverflows/TCPReqQFull*/TCPSynRetrans` 增量全为 0；loopback 修正客户端后 825 RPS@150VU 零错误。最终鉴别实验链：:80 纯 HTTP 150VU 609 RPS 零悬崖（排除服务器/通用 TCP）；国内大站 :443 对照干净（排除本机/家庭网络）；权威 DNS（Cloudflare NS）确认真实 A 记录 = 76.13.217.130（真机 93ms/证书正确/200 OK），而本机 ISP 解析器返回 182.16.61.114/117——7.7 秒建连、证书校验失败，为链路注入的假答案（DNS 污染）。当天所有"TLS 失败/秒级建连/连接悬崖"均为间歇性解析到污染 IP 所致；被污染的流量从未到达服务器，与服务器计数器全零完全自洽。**这是可用性问题而非性能问题**：使用默认 ISP DNS 的国内访客会间歇性无法访问。

## 〇、一句话结论（保留原文供对照，结论以顶部更正为准）

生产端容量：**混合负载稳态 ~89 RPS / 100 并发可用（P99 4.7s）/ 150 并发过载、200 并发严重过载（错误率 8.7%）**；延迟底座是跨境 RTT（P50 ≈ 183ms）；**瓶颈定位在服务端处理链（连接层天花板 ~120 RPS，重 DB 端点减半至 60–80），客户端与传输层已实测排除**；304 协商缓存路径达到连接层天花板（121 RPS），是收益最大的已落地优化。按自然浏览模型估算可支撑 **300–900 同时在线、日活万级**（详见第十节）。**另发现一个与性能无关的 P0 部署事故：03-题解 全部 100 页在生产 404**（详见第五节）。

### 容量解读

1. **饱和点**：混合场景 RPS 在 VU 50→100 之间进入平台期（58.5→65.4），VU 150 反而降到 58.1 且 P99 破 11s——这是典型的服务端排队饱和曲线，拐点约 **60–65 RPS（混合）**。
2. **分场景吞吐排序**：304 阅读页（≈121）> 搜索（≈95）≈ 登录页（≈95）> bootstrap（≈62）。动态聚合 API 是最重的路径，符合预期。
3. **优雅降级**：全部阶段错误率 <1.7%，无 5xx 风暴、无连接拒绝——过载表现为变慢而非崩溃。
4. **真实用户换算**：混合 65 RPS、按每人 5–10 秒一次请求的自然浏览节奏，支撑 **300–600 人同时在线**阅读/复习无感；100 并发连接下 P99 仍在 5 秒内。

## 六、方法、口径与局限（诚实声明）

1. **客户端侧限制**：单台家庭宽带 Windows 机器发起全部并发，VU≥100 时客户端 TLS/事件循环可能参与瓶颈（304@VU100 的回落最可能是两者叠加）；RPS 绝对值偏保守，但"RPS 平台期 + 延迟陡增"的饱和形态是服务端排队信号，结论方向可靠。
2. **网络底座**：跨境 RTT ~180ms 计入全部数字；同机房（VPS 本机）压测的延迟会显著更低，本报告数字代表**真实用户视角**。
3. **只读口径**：全程零写请求，mark/plan/settings 未压测——避免污染生产数据；写路径容量留待专用测试账号后再测。
4. **熔断机制生效一次**：首轮混合场景因题解页 404 占比 20% 触发错误率熔断（15.8%），已确认为部署缺陷而非过载，换路径后重跑。
5. **测试时长**：全部阶梯每阶段 40 秒，总施压约 15 分钟，未对服务造成持续性压力。

## 九、瓶颈诊断

### 9.1 证据链

1. **客户端排除**：decompose 采样客户端 CPU 2–4%（峰值 10–34% 瞬时），远非瓶颈。
2. **传输层排除**：正文耗时 ≈0ms；101KB 页面的 200 路径与 304 的差距主要体现在尾部（P95/P99），P50 差距很小——带宽只在高并发聚合时参与。
3. **分层天花板**：health（无 DB、无文件、只有会话校验）封顶 **~121 RPS**——这就是 nginx+uvicorn+每请求会话查库这条公共管线的能力上限；bootstrap 在其上叠加重 DB 聚合后降到 **60–82 RPS**，即 DB 聚合是动态路径的首要增重项。
4. **排队特征**：所有场景 RPS 进入平台期后 P50/P95 同步陡增（health@VU100：P50 185→346ms、P95 675→4455ms）——典型的单队列饱和，而非错误风暴（错误率始终 <2%）。
5. **RTT 底座**：全部 P50 的下限 ≈183–188ms（= me/304 的 P50），跨境 RTT 决定低并发时的用户体感；服务端处理在低并发时只增加 36–143ms（login 225−health 186=39ms；bootstrap 324−186=138ms）。

### 9.2 结论：瓶颈在哪

| 排序 | 瓶颈 | 证据 | 对策 |
|---|---|---|---|
| 1 | **跨境 RTT（~183ms）**——低并发体感的绝对主导 | 一切 P50 下限=纯 RTT | 国内/香港节点或 CDN 静态加速（静态资源可全 CDN 化） |
| 2 | **每请求会话查库 + 单事件循环管线**——高并发第一天花板（~121 RPS） | health 无 DB 无文件仍封顶 121 | uvicorn `--workers 2`（多进程绕开单循环）、会话校验加内存缓存 |
| 3 | **重 DB 聚合（bootstrap）**——动态路径吞吐减半 | bootstrap 60–82 vs health 121 | dashboard 读缓存/物化汇总 |
| 4 | 共享 VPS 邻户噪声（低并发段 ±25% 波动） | 三组方差 | 升配或独享核 |

未能在服务端内部验证的假设（无 SSH 数据）：uvicorn worker 数（仓库源码显示按默认单 worker 启动，与 ~121 RPS 的事件循环天花板吻合，但建议登机确认）与 VPS CPU 型号/配额。

## 十三、⚠️ 新的结构性发现：并发连接悬崖（~64–75 连接，优化前即存在）

复测中发现吞吐随并发**下降**而非持平（health：50 VU→238 RPS，75 VU→63 RPS），且该悬崖在 10-02 的旧数据中同样存在（旧 health@100VU 也是 79 RPS + P95 4.5s）——**与本次优化无关，是此前被掩盖的独立瓶颈**。夹逼定位与特征：

| VU | RPS | P50 | 特征 |
|---|---|---|---|
| 50 | 237.8 | 181ms | 健康：P50=纯 RTT |
| 64 | 103.9 | 240ms | 开始劣化（P95 2.8s） |
| 75 | 63.3 | 414ms | 崩塌 |
| 88–200 | 58–63 | 870–2834ms | **吞吐锁死 ~60 RPS，延迟随 VU 线性增长** |

三个诊断证据：①与端点无关（health/css/HTML/mixed 全部同一悬崖位置）；②崩塌区 P50 ≈1s ≈ **TCP SYN 重传间隔**，且错误率 0%（SYN 被静默丢弃后重传成功）；③客户端 CPU 仅 5.8%（排除客户端）。**判定：~64–75 个并发 TCP 连接处，连接建立被静默丢弃**——指向服务器内核/网络栈的连接队列而非应用：

- 最可能：nginx `worker_connections` 配置偏小，或内核 `net.core.somaxconn` / `net.ipv4.tcp_max_syn_backlog` / `nf_conntrack_max` 偏低（SYN 静默丢 + 1s 重传 + 0 错误的完整签名）；
- 次要嫌疑：nginx 与 uvicorn 之间的 upstream 连接池上限。

**修复清单（服务器 root 操作，全部一行级）**：

```
nginx.conf:  worker_connections 4096;  listen <port> backlog=4096;
sysctl:      net.core.somaxconn=4096
             net.ipv4.tcp_max_syn_backlog=8192
             net.ipv4.tcp_syncookies=1
             net.netfilter.nf_conntrack_max=262144 （若启用 conntrack）
```

**修复前的重要提示**：真实浏览器用户每人大约维持 1–2 个活跃连接（keepalive 复用），~64 连接意味着**几十个真实用户同时活跃时新连接就可能被丢**——这是当前发挥 4 worker 容量的头号障碍：不修它，多 worker 带来的 235 RPS 无法被超过 ~64 并发连接的负载真实享受到。

**另一个多 worker 配套项**：源码中进程内会话缓存由环境变量 `IF_SHARED_RUNTIME=1` 门控——确认部署环境已设置，否则 4 个 worker 下每个请求都直查 auth.db（低并发已被 uvloop 掩盖，但值得补上）。

## 十四·补、路径鉴别实验（2026-10-03，ZCode 补充；配合《连接悬崖根因与压测修正》）

在客户端连接池修复（ShardedTransport）之后，补三个鉴别实验，把外网退化进一步收窄：

| 实验 | 结果 | 排除/指向 |
|---|---|---|
| **纯 HTTP :80** 50/100/150 VU（无 TLS） | 239 / **541.9** / **609.5 RPS**，P50 89–151ms，零错误零悬崖 | 排除服务器、排除通用 TCP 路径、排除客户端——悬崖是 **443 特异** |
| **国内大站 :443** 150 并发对照（百度，300 请求） | 300/300 成功，TCP P95 88ms，TLS P95 722ms 有界，无秒级尾 | 排除本机、家庭网络——Windows 可正常做 150 并发 TLS 握手 |
| （抓包既有证据）hot100.xyz :443 | TCP connect P95 7251ms（秒级在 TCP 段），SYN-ACK 重复 19 个，服务器应答 0.052ms | SYN-ACK 回程在跨境段被丢/延迟 |

**新结论**：退化特定于“跨境 :443 的 TLS 建连”这一组合——同机同网到国内 443 干净、到本站 80 干净、唯独到本站 443 在高新建连速率下秒级退化。指向 ISP/GFW 对跨境 443 的 DPI/QoS 或云边缘防护，二者需热点对照（换 ISP）与 VPS→公网 IP（跳过 ISP）分离。另：:80 的 P50=89ms 揭示真实 RTT ≈89ms——此前 HTTPS 全部 P50 里的另外 ~90ms 是 443 建连税的摊销。

**对真实用户的影响评估**：退化与“新建握手速率”耦合——浏览器用户每人偶发 1–6 次握手，不会触发；235 RPS 的 50 VU TLS 稳态也证明中低握手速率下路径可用。受影响的只有单源高频率新建 TLS 连接的场景（即压测本身、或极端滥用），因此**它不是生产容量风险，而是测量方法论约束**：对外容量数字应以 VPS 本机（825+ RPS）+ 真实用户视角（50 VU TLS 稳态 235 RPS）分别表述。
