# InterviewForge AI 学习教练与上下文工程规划

> 规划时间：2026-09-07
>
> 规划状态：方案设计，尚未实现。
>
> 目标：在 InterviewForge 中保留并逐步实现 AI 学习分析、课程推荐、学习路线规划和对话式学习教练能力。

---

## 一、总体目标

InterviewForge 后续增加一个“AI 学习教练”，能够基于用户已经产生的真实学习数据完成以下工作：

- 一键分析用户当前学习情况；
- 判断用户学了几轮、哪些题目反复失败、哪些内容已经逾期；
- 识别“曾经 AC、最近又 WA”的题目；
- 发现“看过很多次但没有真正完成”的题目或章节；
- 根据用户提出的目标推荐书籍和学习顺序；
- 结合用户已有基础、目标和可用时间制定学习计划；
- 允许用户继续追问分析结果；
- 在用户明确确认后，将建议写入复习计划或学习安排。

核心定位：

> 一个掌握用户真实学习记录、能够给出有证据学习建议的 AI 学习教练。

---

## 二、核心原则

### 2.1 数据事实由系统计算，AI 负责解释和规划

不能让 AI 直接阅读整份数据库后自行统计“学了几轮”“失败最多的题目”。这些内容应该由后端确定性计算，再传给 AI。

推荐链路：

```text
用户问题
  ↓
识别任务类型
  ↓
确定所需数据
  ↓
从数据库聚合事实
  ↓
筛选最相关的证据
  ↓
限制上下文数量和长度
  ↓
调用 AI 生成解释或计划
  ↓
用户确认后执行写操作
```

### 2.2 不把整个网站塞给 AI

上下文不是越多越好。整站内容会带来：

- 重点被无关内容稀释；
- 上下文长度和调用成本增加；
- 响应速度变慢；
- 书籍或用户数据泄漏范围扩大；
- AI 更容易把自然语言中的推断误当成事实。

后续应实现一个“上下文编译器”，根据当前任务按需取数，生成有限大小、可审计的上下文包。

### 2.3 先实现受控 AI，再逐步演进为 Agent

第一版不追求完全自主的 Agent。建议分为：

1. 只读的学习分析；
2. 生成学习路线和计划草案；
3. 用户确认后写入计划；
4. 最后再加入受控工具调用和连续对话。

AI 默认不能直接修改学习记录、删除数据、修改权限或替用户执行不可逆操作。

## 三、现有数据基础盘点

当前项目的主要后端在 `tools/study_server.py`，每个用户拥有独立学习库。现有数据已经足够支撑第一版分析，但需要先做统一聚合。

### 3.1 当前可用数据

| 数据类别 | 当前来源 | 可支持的分析 |
|---|---|---|
| 用户基本信息 | 用户表、个人设置 | 编程语言、昵称、基础偏好 |
| 题目学习行为 | `study_events` | 浏览次数、最近浏览、完成轮次 |
| 书架学习行为 | `content_events` | 章节浏览、章节完成、模块进度 |
| 做题结果 | `submissions` | AC/WA、提交次数、语言、最近状态 |
| 学习状态 | `marks` | mastered、reviewing、weak |
| 学习计划 | `plan_pins`、`/api/plan` | 已排期题目、今日计划 |
| 复习状态 | `/api/daily` | 到期、逾期、待复习内容 |
| 总体进度 | `/api/dashboard` | 总题数、轮次、活跃天数、连续学习 |
| 课程目录 | `tools/library_catalog.py` | 课程标题、分类、简介、顺序 |
| 课程内容 | `books/`、生成后的 `library/` | 章节标题和知识点正文 |

### 3.2 当前“轮次”的定义

当前题目轮次不是简单的手动字段，而是根据 AC 记录推算：

- 同一天同一道题多次 AC，只计一轮；
- 不同日期 AC，才会增加该题的完成轮次；
- 如果只浏览题目、没有 AC，不能算完成一轮；
- 总体轮次由题目完成情况汇总得出。

AI 分析必须使用后端已经定义好的轮次结果，不能自行重新解释。

### 3.3 当前数据的不足

课程目录目前已有标题、分类、简介和顺序，但前置关系、标签、难度和预计学习时间还不够结构化。后续课程推荐需要补充这些元数据。

提交记录也可能不是完整的力扣历史，因为数据来源可能是手动记录、浏览器扩展或同步记录。因此 AI 上下文必须带上数据质量信息，不能把不完整记录当成完整事实。

## 四、第一步：建立上下文数据协议

第一步不是开发聊天界面，而是定义“AI 上下文数据协议”，明确：

1. 每类数据的来源；
2. 每个字段的含义；
3. 确定性聚合指标；
4. 不同任务需要哪些字段；
5. 每类数据的数量上限；
6. 每个字段的最大字符数；
7. 数据的新鲜度和可信度；
8. 必须排除的隐私数据；
9. AI 返回结果的结构。

建议最终提供类似下面的内部接口：

```text
build_ai_context(
    user_id,
    task="learning_diagnosis",
    user_query="我最近学习情况怎么样",
    budget="medium"
)
```

这个接口返回的是经过筛选的上下文包，不是整库导出。

## 五、上下文分层设计

### 5.1 默认上下文

每次任务都可以携带，但必须保持很短：

```json
{
  "profile": {
    "language": "java",
    "current_goal": "Java后端面试"
  },
  "overall": {
    "completed_problems": 87,
    "total_problems": 100,
    "current_round": 2,
    "active_days_14": 9,
    "streak": 3,
    "overdue_count": 12
  },
  "data_as_of": "2026-09-07T16:20:00+08:00"
}
```

默认上下文只回答：

- 用户主要学习方向；
- 用户的总体学习进度；
- 最近是否活跃；
- 是否存在明显逾期；
- 数据截至什么时间。

### 5.2 任务上下文

根据任务类型加载不同的数据，不使用一个无限膨胀的通用 Prompt。

#### 学习分析

- 最近 7/14/30 天学习汇总；
- 高频 WA 题；
- AC 后再次 WA 的题；
- 多次浏览但没有 AC 的题；
- 到期和逾期题；
- 薄弱标记题；
- 各课程进度；
- 最近学习活动。

#### 课程推荐

- 用户当前目标；
- 用户已有基础；
- 已完成或正在学习的课程；
- 课程标签；
- 前置课程关系；
- 难度和预计学习时间；
- 5～8 个候选课程的简介。

#### 今日计划

- 每日目标；
- 今日到期内容；
- 薄弱题；
- 最近刚学习过的内容；
- 用户可用时间。

#### 单题复盘

- 当前题目题面和标签；
- 用户提交统计；
- 最近几次提交结果；
- 用户标记；
- 相关题解章节；
- 相邻知识点。

#### 对话追问

- 当前对话最近 4～8 轮；
- 历史对话摘要；
- 上一轮使用过的事实和证据；
- 用户本轮问题涉及的对象。

## 六、确定性指标设计

所有需要精确的指标先由后端计算。

### 6.1 总体学习指标

- 总题数、已完成题数、完成比例；
- 当前完成轮数；
- 最近 7/14/30 天活跃天数；
- 当前连续学习天数；
- 今日完成数量；
- 当前逾期数量；
- 各书架模块完成比例；
- 最近一次学习时间。

### 6.2 题目风险指标

每道题可以聚合成：

```json
{
  "problem_id": 1,
  "title": "两数之和",
  "view_count": 8,
  "submit_count": 6,
  "ac_count": 2,
  "wa_count": 4,
  "last_status": "wa",
  "last_activity_at": "2026-09-07T14:30:00+08:00",
  "next_due": "2026-09-05",
  "is_overdue": true,
  "mark": "weak"
}
```

建议识别四类问题：

1. `repeat_wa`：多次提交仍然没有 AC；
2. `wa_after_ac`：曾经 AC，之后又出现 WA；
3. `view_without_ac`：浏览次数多但没有 AC；
4. `due_overdue`：已经到期但没有复习。

### 6.3 课程指标

每个模块建议形成：

```json
{
  "module_id": "java-concurrency",
  "title": "Java 并发编程",
  "progress": 0.35,
  "viewed_count": 18,
  "completed_count": 9,
  "last_studied_at": "2026-08-30T18:20:00+08:00",
  "overdue_count": 4,
  "is_in_progress": true
}
```

## 七、重要数据筛选规则

上下文选择不能只按时间排序，建议综合考虑：

```text
优先级 = 相关性 × 时间新鲜度 × 异常程度 × 可行动性
```

示例：

| 数据情况 | 优先级 |
|---|---:|
| 最近一次 WA，且连续失败 4 次 | 很高 |
| 曾经 AC，最近又 WA | 很高 |
| 已逾期 10 天 | 高 |
| 看过 8 次但从未 AC | 高 |
| 半年前 AC 过一次 | 中 |
| 最近刚 AC 且没有异常 | 低 |
| 与当前学习目标无关 | 不发送 |

建议第一版的数量上限：

- 高频问题题目：最多 10 道；
- 逾期题目：最多 10 道；
- 薄弱模块：最多 5 个；
- 候选课程：最多 5～8 个；
- 最近活动：最多 14 天的日汇总；
- 原始提交记录：仅在诊断具体题目时提供最近 5 条；
- 课程正文：只在确实需要解释时检索，每个章节限制字符数。

## 八、事实、推断、证据和建议必须分开

上下文中应该明确区分四种信息。

### 8.1 事实

数据库直接聚合出来的结果：

```text
最近 14 天活跃 9 天。
题目 1 提交 6 次，其中 4 次 WA。
Java 并发课程完成度 35%。
```

### 8.2 推断

规则引擎根据事实得到的信号：

```text
题目 1 可能是当前薄弱题。
用户在二分查找方向存在重复失败。
Java 并发是当前课程断点。
```

### 8.3 证据

支撑推断的具体数据：

```text
题目 1 最近 3 次提交均为 WA。
二分查找相关题目共 8 道，只有 3 道 AC。
并发课程最近一次学习是 21 天前。
```

### 8.4 建议

由 AI 生成的行动：

```text
今天先复习题目 1、题目 2，再阅读 Java 并发中的 JMM 和线程池章节。
```

上下文建议使用以下结构：

```json
{
  "facts": [],
  "derived_signals": [],
  "evidence": [],
  "requested_output": "study_diagnosis"
}
```

这样可以减少 AI 把推断误当成事实的情况。

## 九、上下文预算

第一版使用固定预算和硬上限，不根据模型支持的最大上下文无限扩张。

| 部分 | 建议范围 |
|---|---:|
| 系统规则 | 800～1200 tokens |
| 用户问题 | 200～500 tokens |
| 用户学习摘要 | 500～1000 tokens |
| 重点证据 | 1000～2500 tokens |
| 课程或题解内容 | 1500～3500 tokens |
| AI 输出 | 800～1500 tokens |

普通学习分析先控制在 4K～8K 输入 tokens。后续根据实际模型、响应速度和成本再调整。

每个字段都应设置最大长度，特别是：

- 用户输入；
- 课程简介；
- 题面和题解正文；
- 历史对话；
- 错误输出和提交信息。

## 十、课程推荐所需的元数据

当前 `tools/library_catalog.py` 已有课程 ID、标题、分类、简介和顺序。后续建议为课程补充结构化字段：

```python
{
    "id": "java-concurrency",
    "title": "Java 并发编程",
    "category": "Java 语言",
    "tags": ["Java", "并发", "线程池", "JMM", "锁"],
    "prerequisites": ["java-core"],
    "difficulty": 3,
    "estimated_hours": 12,
    "career_tracks": ["Java后端", "校招"]
}
```

推荐流程：

```text
用户目标
  ↓
标签匹配
  ↓
过滤已经掌握的内容
  ↓
补齐前置课程
  ↓
按照课程关系排序
  ↓
AI 解释推荐理由和学习顺序
```

AI 不需要从所有 Markdown 中自由寻找路线，而是先由系统筛选候选课程，再让 AI 完成排序、解释和个性化调整。

## 十二、AI 输出协议

AI 不应只返回一大段不可解析的文字。后端应要求结构化 JSON，再由前端渲染。

学习分析可以使用：

```json
{
  "summary": "...",
  "strengths": [],
  "weaknesses": [],
  "evidence": [],
  "actions": [],
  "confidence": "medium"
}
```

课程推荐可以使用：

```json
{
  "goal_understanding": "...",
  "recommendations": [
    {
      "module_id": "java-concurrency",
      "order": 1,
      "reason": "...",
      "focus": [],
      "estimated_hours": 12
    }
  ],
  "skipped_modules": [],
  "next_action": "..."
}
```

所有结论应尽量绑定证据 ID 或对象 ID，便于前端提供“查看依据”的入口。

## 十三、学习教练的功能分层

### 13.1 第一层：只读分析

第一期优先实现：

- 一键学习分析；
- 薄弱题分析；
- 重复 WA 分析；
- 逾期复习分析；
- 学习进度和学习习惯分析。

这一层不写入任何学习数据。

### 13.2 第二层：学习路线和计划草案

支持：

- 根据目标推荐书籍；
- 生成 7 天、14 天、30 天学习计划；
- 安排每日题目和章节；
- 根据剩余时间重新规划；
- 跳过已经掌握的内容。

AI 只返回计划草案，用户点击“采用计划”后才写入系统。

### 13.3 第三层：工具调用 Agent

可以提供以下受控工具：

```text
get_learning_summary()
get_problem_stats()
get_due_items()
search_modules(keyword)
get_module_outline(module_id)
get_recent_submissions(problem_id)
save_learning_plan(plan)
```

其中前六个是只读工具，`save_learning_plan` 属于写操作，必须经过用户确认。

## 十四、持久化与缓存设计

每个用户的学习库可以增加以下表：

```text
ai_sessions
- id
- user_id
- title
- created_at
- updated_at

ai_messages
- id
- session_id
- role
- content
- created_at

ai_insights
- id
- insight_type
- snapshot_hash
- result_json
- model
- created_at

learning_plans
- id
- goal
- plan_json
- status
- created_at
- completed_at
```

`ai_insights` 用于缓存同一份学习快照的分析结果：

- 数据没有变化时不重复调用 AI；
- 中控台打开时可以直接显示上次分析；
- 可以比较建议是否被执行；
- 可以追踪不同模型或 Prompt 的效果。

每次上下文建议带有：

```text
schema_version
data_as_of
snapshot_hash
model
prompt_version
```

## 十五、数据质量、隐私与安全

### 15.1 数据质量

上下文必须带数据质量信息：

```json
{
  "data_quality": {
    "submission_source": "manual+leetcode_sync",
    "last_sync_at": "2026-09-07T15:00:00+08:00",
    "has_full_submission_history": false,
    "module_tags_complete": false,
    "confidence": "medium"
  }
}
```

如果数据不足，AI 应该明确说：

> 当前只掌握最近 7 天的记录，关于长期薄弱点的判断可信度有限。

不能让 AI 把不完整记录包装成确定结论。

### 15.2 隐私边界

默认不放进学习分析上下文：

- 密码和会话令牌；
- 力扣登录凭证；
- 管理员信息；
- 头像原始数据；
- 与当前学习目标无关的聊天记录；
- 其他用户的数据；
- 不必要的用户名、联系方式和设备信息。

用户数据必须在服务端按当前用户隔离读取，API Key 只能保存在后端环境变量或服务器配置中，不能写入浏览器代码。

### 15.3 内容注入防护

书籍 Markdown、题解内容和用户输入都属于不可信数据。传给 AI 时必须明确标注为资料内容，不能让其中的文本覆盖系统规则。

例如题解正文中出现“忽略之前指令”时，模型只能把它当作普通学习资料，不能当成系统指令执行。

## 十六、推荐的模型接入方式

后端增加统一的模型适配层，不让前端绑定具体模型厂商：

```text
AI_PROVIDER=openai-compatible
AI_BASE_URL=...
AI_API_KEY=...
AI_MODEL=...
```

这样未来可以切换：

- 云端大模型；
- OpenAI 兼容接口；
- DeepSeek 等服务；
- 本地 Ollama 模型。

第一版优先采用服务端 API 调用，并保留供应商替换能力。若以后使用本地模型，再单独评估模型质量、显存和响应速度。

## 十七、分阶段实施路线

### 阶段一：数据盘点和确定性分析

目标：不接 AI，先确保事实准确。

- 盘点现有表、接口和字段；
- 定义轮次、薄弱题、逾期题等指标；
- 编写学习分析聚合函数；
- 输出结构化 JSON；
- 用固定测试数据验证结果；
- 检查手动记录和力扣同步记录的差异。

验收标准：人工能够确认每个指标来源清楚，重复计算结果稳定。

### 阶段二：上下文编译器

目标：根据任务生成有限大小的上下文包。

- 实现任务类型识别；
- 实现默认上下文；
- 实现学习分析、课程推荐、今日计划、单题复盘四种模板；
- 添加字段最大长度和列表数量上限；
- 添加数据新鲜度、可信度和快照哈希；
- 确认敏感数据不会进入上下文。

验收标准：相同任务在数据量增大后，上下文仍然保持可控，不会把整库传出。

### 阶段三：一键 AI 学习分析

目标：在中控台提供第一项 AI 能力。

- 接入服务端模型适配层；
- 使用固定 Prompt 和结构化输出；
- 返回总结、优势、薄弱点、证据和行动建议；
- 支持分析结果缓存；
- 前端提供“查看依据”入口。

验收标准：每条重要结论都能回到具体学习数据，数据不足时能提示低可信度。

### 阶段四：课程推荐和学习路线

目标：根据用户目标推荐课程和顺序。

- 补充课程标签、前置关系、难度、预计时间；
- 先由规则筛选候选课程；
- AI 负责排序、解释和个性化调整；
- 支持跳过已掌握内容；
- 支持时间约束。

验收标准：推荐结果有明确依据，不会把用户已经掌握的课程无理由排在前面。

### 阶段五：学习计划和对话教练

目标：让用户可以继续追问并采用计划。

- 保存 AI 会话；
- 对历史对话做摘要；
- 生成 7/14/30 天计划；
- 用户确认后写入计划；
- 增加只读工具调用；
- 所有写操作保留确认环节。

验收标准：AI 无法绕过确认直接修改学习记录，失败或超时不会破坏原有数据。

## 十八、测试与评估

第一版至少准备以下测试场景：

1. 新用户没有任何学习数据；
2. 只有浏览记录，没有提交记录；
3. 题目多次 WA 但从未 AC；
4. 题目曾经 AC，最近又 WA；
5. 数据只有最近 7 天；
6. 有大量旧数据但最近没有学习；
7. 用户目标与现有课程不匹配；
8. 用户输入“我只有 30 分钟”；
9. 课程缺少标签或前置关系；
10. 课程正文中包含可能影响模型的指令文本；
11. 同一份数据重复请求，验证缓存是否生效；
12. AI 服务不可用，验证网站核心学习功能是否正常。

评估重点：

- 事实是否准确；
- 证据是否完整；
- 推荐是否符合用户目标；
- 是否重复推荐已掌握内容；
- 是否能正确处理数据不足；
- 输出是否足够简洁可执行；
- AI 失败是否影响原有网站；
- 是否发生跨用户数据泄漏。

## 十九、第一版明确不做的事情

为了控制风险，第一版不做：

- 让 AI 直接读取整份数据库；
- 让 AI 自动修改学习记录；
- 让 AI 自动标记题目为已掌握；
- 让 AI 自动删除历史数据；
- 让 AI 自动操作管理员功能；
- 让 AI 在浏览器端直接持有 API Key；
- 让 AI 自动执行代码或访问服务器 Shell；
- 让 AI 无限制读取全部书籍正文；
- 依赖 AI 代替后端计算统计指标。

---

## 二十、最终决策

InterviewForge 的 AI 能力采用“确定性数据分析 + 受控上下文编译 + 结构化 AI 输出”的路线。

第一步先盘点和规范数据，第二步实现上下文编译器，第三步才接入一键 AI 学习分析。课程推荐和对话式 Agent 在此基础上逐步增加。

最终目标不是让 AI 显得无所不知，而是让它能够：

1. 说清楚用户当前真实状态；
2. 给出具体数据作为依据；
3. 推荐符合用户目标的内容；
4. 给出用户今天可以执行的下一步；
5. 在数据不足时诚实说明不确定性。
