# 从长聊天里找回原话：区分检索、引用和归属

用户记得大意时，检索工具先在当前账号、当前会话、本轮用户发问之前的消息中选出候选；最终答复再核对哪段原文真正支持请求。相似的向量、正确的消息 ID 以及正确的说话人，是三个不同的判断。

## 四道旧题暴露了什么

下面分析的是上一轮已发布版本那一次运行。候选来自同一份冻结历史、同一组工具参数的回放；旧版只保存结果大小，没有在执行时保存候选 ID。编号是合成语料内的位置，不是线上账号的全局编号。

| 原题 | 预期位置 | 工具为什么漏掉 |
| --- | ---: | --- |
| p02，树的逐层处理 | 417 | 查询只剩“等着处理的小孩”，树和逐层的线索丢失。该查询下目标在混合排序第 140 位。 |
| p08，发布检查报错 | 565 | 含有相似标题的记录抬高相对阈值，目标虽然在混合得分中排第 3，但没通过入选门槛。 |
| h02，受访者的收藏方法 | 461 | 查询只剩爱好的别称，漏了“谁讲的”和“物件受潮后怎么收”；目标混合排序第 30。 |
| h04，更改失败后的处理 | 335 | 两次查询都把他人在会上发言的记录排在前面，目标未进候选；普通答复引用了与用户立场相反的会议意见。 |

两个额外对照排除了仅调排名就能解决问题的解释。a01 有两次独立的备选安排，旧版只取到其中一条。h05 已经找对原句、编号和来源卡，但“你当时说”的标题把同事的话归给了记笔记的用户。引用来自某人的消息，并不代表引文里第一人称说的就是此人。

## 这次如何处理

显式索要原话时，语义检索为核对环节保留多条相互竞争的候选；混合排序、向量相似度以及消息作者都提供线索，作者只影响候选顺序，不是说话人的身份过滤器。发送者相同的两条笔记完全可以记录不同的人。普通检索和明确只找最早一条沿用各自原有的返回限制。

若模型把原问题缩成几个过窄的词，允许在本轮的工具预算内按用户描述再找一次。核对模型只在有原文依据的候选中选择。最终生成的来源卡重新读取同一会话内的文本，验证角色、逐字引文和偏移；仅凭语义接近不会生成一段新的“原话”。

## 怎样核对一次失败

1. 看检索工具是否覆盖了目标消息。新版在账号内的工具审计中记录实际返回的消息 ID，成功读取和命中本轮缓存均有记录，不在审计里复制原文。旧版候选只能回放重建；当索引状态改变时，重建排序未必与当时完全相同。
2. 看最终答复和来源卡。核对消息 ID、Unicode 字符偏移、原文长度和 SHA-256，可以发现拼接、改写或来源已修改。然后读引文上下文，区分发出消息的账号、消息中被引述的人以及被讨论的对象。
3. 对多解检查是否把每条原话分别映射到对应 ID，能否说清为何不能唯一确定。单条同主题引用、只列一串编号、引用正确原文却颠倒立场，都不能计作完整答案。
