# 探索式开发何时需要一份规格

## 先看谁还没拿定主意

为图书馆做一个座位热度图时，馆员可能还说不清想看楼层、时段还是具体座位。此时用 Vibe Coding 快速做两个能点的版本很划算。一个按楼层着色，一个按时间展示空座变化，让馆员用两者回答“午休时该开放哪一层”。观察他在哪一步停下来，再决定保留哪种视图。原型用虚构的占用记录就能完成这轮比较。

但当这幅图要对外显示“当前可用座位”，颜色会影响读者是否白跑一趟。团队可以写一份短规格，列出可用、已预订、维护中三种状态的取数规则，明确数据超过五分钟未更新时显示“状态待确认”。把这些约定连同示例交给开发和测试，改图例时便有共同依据。

## 把原型转成交付条件

保留一次馆员实际做过的查询作为验收场景：选择二楼、筛选十点，已维护的座位不应被计入可用数。再用一份时间已过期的数据检查提示。有些试验性的配色可以继续调整，而状态含义已经可以写成测试。

被追问“规格越详细越好吗”，可以回答哪种变化最贵。配色变化十分钟就能演示，先做出来再聊；两个终端对同一座位给出不同状态会影响现场安排，就应先把数据口径定下来。规格的篇幅取决于这些分歧需要多少证据才能消除。
