### 📝 算法笔记：283. 移动零 (Move Zeroes)

------

- **📌 核心题意**：

  给定一个数组 `nums`，编写一个函数将所有 `0` 移动到数组的末尾，同时保持非零元素的相对顺序。

  **请注意** ，必须在不复制数组的情况下原地对数组进行操作。

  **示例 1:**

  **输入:** nums = `[0,1,0,3,12]`<br>**输出:** `[1,3,12,0,0]`

  **示例 2:**

  **输入:** nums = `[0]`<br>**输出:** `[0]`

  **提示**:

  - `1 <= nums.length <= 104`
  - `-231 <= nums[i] <= 231 - 1`

  **进阶：**你能尽量减少完成的操作次数吗？

- **🧠 思考过程**：

  1. **直觉与痛点（开辟新数组）**：

     最简单的想法是新建一个同样大小的数组，遇到非零的数字就按顺序塞进去，剩下的空位自然全是 0。

     **痛点**：空间复杂度是 $O(N)$，违反了题目“原地修改”的硬性要求（空间复杂度必须为 $O(1)$）。

  2. **破局思路（快慢双指针）**：

     既然不能用新数组，我们就用**两个指针（游标）**在原数组上打配合：

     - **快指针 `fast`**：像前线侦察兵，负责遍历整个数组，寻找**非零元素**。

     - **慢指针 `slow`**：像后方收容所，它永远指向**下一个非零元素应该存放的位置**。

       一旦快指针找到一个非零元素，就把它和慢指针指向的值**交换**，然后慢指针前进一步。

  3. **逻辑推演（以 `nums = [0, 1, 0, 3, 12]` 为例）**：

     初始状态：`fast = 0`, `slow = 0`

     - `fast=0`，指向 `0`。是零，侦察兵跳过。

     - `fast=1`，指向 `1`。是非零！把它和 `slow` (索引0) 交换。数组变成 `[1, 0, 0, 3, 12]`。此时 `slow` 前进到 1。

     - `fast=2`，指向 `0`。跳过。

     - `fast=3`，指向 `3`。是非零！把它和 `slow` (索引1) 交换。数组变成 `[1, 3, 0, 0, 12]`。`slow` 前进到 2。

     - `fast=4`，指向 `12`。是非零！把它和 `slow` (索引2) 交换。数组变成 `[1, 3, 12, 0, 0]`。`slow` 前进到 3。

       遍历结束，所有的 0 自然被“挤”到了最后面。

- **🛠️ Java 规范代码**：

```java
class Solution {
    public void moveZeroes(int[] nums) {
        // 定义慢指针，记录下一个非零元素应该放置的位置
        int slow = 0;
        
        // fast 作为快指针，遍历整个数组
        for (int fast = 0; fast < nums.length; fast++) {
            // 当快指针发现非零元素时，执行交换操作
            if (nums[fast] != 0) {
                // 优化点：只有在 fast 和 slow 不相等时才交换，避免自己和自己交换的无用功
                // 只有当slow停在0之后两者才会不相等
                if (fast != slow) {
                    int temp = nums[fast];
                    nums[fast] = nums[slow];
                    nums[slow] = temp;
                }
                // 非零元素安顿好后，慢指针向后移动一位，准备接收下一个非零元素
                slow++;
            }
        }
    }
}
```

- **⏱️ 复杂度分析**：
  - **时间复杂度**：$O(N)$。快指针 `fast` 只需要把数组从头到尾遍历一次，每次交换操作都是 $O(1)$ 的时间。
  - **空间复杂度**：$O(1)$。只使用了两个额外的整型变量 `fast` 和 `slow`，完全是在原数组上进行操作。

------

#### 💡 面试避坑与考点拓展

1. **思路变体：覆写与补零法（另一种常见解法）**
   - **逻辑**：也是双指针，遇到非零元素不交换，而是直接**覆盖**到 `slow` 的位置。等 `fast` 遍历完，非零元素都排在前面了，最后再把 `slow` 之后的所有位置统一赋值为 `0`。
   - **优缺点对比**：覆写法的代码稍微简单一点点，但在**数组全是 0 的极端情况下**（例如 `[0,0,0,0,0]`），覆写法最后还要跑一个循环把所有位置赋值为 0，而我们目前写的**“交换法”**遇到全 0 数组时，`fast!=0` 的条件进不去，根本不会发生任何内存写操作，性能更优。
2. **高频追问：为什么这段代码不仅移动了 0，还能保证非零元素的“相对顺序”不乱？**
   - **回答**：因为我们的快指针是从左到右顺序扫描的。先遇到的非零元素，一定会先被塞到慢指针靠前的位置。这就好像在队列里把 0 剔除，剩下的元素自然会按原来的先后顺序往前补位。

这道题是双指针（对撞指针）的巅峰之作，也是面试中极大概率遇到的超级高频题。它完美展现了如何通过简单的数学逻辑，将 $O(N^2)$ 的暴力解法优化到 $O(N)$。

这道题的核心难点不在于写代码，而在于“证明为什么这么移动指针是正确的”。

### 📝 算法笔记：11. 盛最多水的容器 (Container With Most Water)

------

- **📌 核心题意**：

  给定一个长度为 `n` 的整数数组 `height` 。有 `n` 条垂线，第 `i` 条线的两个端点是 `(i, 0)` 和 `(i, height[i])` 。

  找出其中的两条线，使得它们与 `x` 轴共同构成的容器可以容纳最多的水。

  返回容器可以储存的最大水量。

  **说明：**你不能倾斜容器。

  **示例 1：**

  ![](https://__LC_IMG_ROOT__/lc-13d3d3c3661fa5.jpg)

  **输入：**[1,8,6,2,5,4,8,3,7]<br>**输出：**49 <br>**解释：**图中垂直线代表输入数组 [1,8,6,2,5,4,8,3,7]。在此情况下，容器能够容纳水（表示为蓝色部分）的最大值为 49。

  **示例 2：**

  **输入：**height = [1,1]<br>**输出：**1

  **提示：**

  - `n == height.length`
  - `2 <= n <= 105`
  - `0 <= height[i] <= 104`

- **🧠 思考过程**：

  1. **直觉与痛点（暴力枚举）**：

     最简单的办法是用两个 `for` 循环，把所有可能的两根线组合都算一遍面积，挑出最大的。

     **痛点**：时间复杂度是 $O(N^2)$。当数组很大时，直接超时。我们需要一种能“一次遍历”就找到答案的方法。

  2. **破局思路（对撞双指针）**：

     我们把两个指针分别放在数组的**最左端**和**最右端**。此时，容器的**宽度是最大的**。

     接下来，我们要向中间收缩指针来寻找其他组合。关键问题来了：**该移动左指针还是右指针？**

  3. **逻辑推演（核心推导：为什么要移动短板？）**：

     - 假设当前左板高 `x`，右板高 `y`，且 `x < y`（左边是短板）。
     - 此时容器的高度受限于短板，即高度为 `x`。
     - **如果移动长板（右指针往左移）**：容器的宽度减小了。而高度呢？由于左边的短板 `x` 没动，新容器的高度绝对不可能超过 `x`。宽度变小，高度又不可能增加，所以**面积必定减小**！这完全是无效操作。
     - **如果移动短板（左指针往右移）**：容器的宽度虽然减小了，但我们有可能会遇到一根比 `x` 高得多的新木板。只要新木板足够高，就能弥补宽度减小带来的损失，**面积就有可能增大**！
     - **结论**：每次只移动两者中较短的那根木板，并不断记录过程中的最大面积。

- **🛠️ Java 规范代码**：

```java
class Solution {
    public int maxArea(int[] height) {
        // 定义双指针，分别指向数组的头和尾
        int left = 0;
        int right = height.length - 1;
        
        int maxArea = 0; // 用于记录全局最大面积
        
        // 当左指针和右指针相遇时，循环结束
        while (left < right) {
            // 1. 计算当前的宽度和高度
            int width = right - left;
            int currentHeight = Math.min(height[left], height[right]);
            
            // 2. 计算当前面积，并更新全局最大面积
            int currentArea = width * currentHeight;
            maxArea = Math.max(maxArea, currentArea);
            
            // 3. 核心贪心逻辑：谁短，就移动谁
            if (height[left] < height[right]) {
                left++;  // 左边是短板，左指针右移寻找更高的板
            } else {
                right--; // 右边是短板（或一样高），右指针左移寻找更高的板
            }
        }
        
        return maxArea;
    }
}
```

- **⏱️ 复杂度分析**：
  - **时间复杂度**：$O(N)$。左右指针相向而行，每个元素最多被访问一次，总共执行 $N$ 次面积计算。
  - **空间复杂度**：$O(1)$。只需要常数级别的额外空间来存储指针和最大面积变量。

------

#### 💡 面试避坑与考点拓展（可能会被追问）

1. **灵魂拷问：“你怎么证明移动短板不会漏掉最优解？”**
   - **解答模板**：这其实是一个“消减搜索空间”**的过程。当我们在最外侧计算完面积后，假设左板是短板（索引为 `i`），右板是长板（索引为 `j`）。因为左板限制了高度，所以左板 `i` 和它右边的任意一根板（`i+1` 到 `j-1`）组合，面积都**绝对不可能超过 `i` 和 `j` 的组合（宽度更小，高度最多不变）。
   - 既然 `i` 已经不可能创造出更大的面积了，我们就把 `i` 这个选项彻底淘汰（`left++`），这就相当于一次性排除了剩余的所有无效组合，绝对不会漏掉最优解。
2. **细节追问：如果左右板一样高怎么办？**
   - **解答**：随便移动哪一个都可以，或者两个一起移动（`left++` 且 `right--`）。因为如果它们俩一样高，中间无论有什么板子，受限于这两根边缘板的高度限制，和其中任何一根单独组合的面积都不可能大于它们俩直接组合的面积。所以这两根板子的使命已经结束了，都可以淘汰。

### 📝 算法笔记：15. 三数之和 (3Sum)

------

- **📌 核心题意**：

  给你一个整数数组 `nums` ，判断是否存在三元组 `[nums[i], nums[j], nums[k]]` 满足 `i != j`、`i != k` 且 `j != k` ，同时还满足 `nums[i] + nums[j] + nums[k] == 0` 。请你返回所有和为 `0` 且不重复的三元组。

  **注意：**答案中不可以包含重复的三元组。

  **示例 1：**

  **输入：**nums = [-1,0,1,2,-1,-4]<br>**输出：**[[-1,-1,2],[-1,0,1]]<br>**解释：**<br>nums[0] + nums[1] + nums[2] = (-1) + 0 + 1 = 0 。<br>nums[1] + nums[2] + nums[4] = 0 + 1 + (-1) = 0 。<br>nums[0] + nums[3] + nums[4] = (-1) + 2 + (-1) = 0 。<br>不同的三元组是 [-1,0,1] 和 [-1,-1,2] 。<br>注意，输出的顺序和三元组的顺序并不重要。

  **示例 2：**

  **输入：**nums = [0,1,1]<br>**输出：**[]<br>**解释：**唯一可能的三元组和不为 0 。

  **示例 3：**

  **输入：**nums = [0,0,0]<br>**输出：**[[0,0,0]]<br>**解释：**唯一可能的三元组和为 0 。

  **提示：**

  - `3 <= nums.length <= 3000`
  - `-105 <= nums[i] <= 105`

- **🧠 思考过程**：

  1. **直觉与痛点（哈希表硬干）**：

     之前做“两数之和”用了哈希表，那“三数之和”能不能套两层循环，第三个数去哈希表里找？

     **痛点**：可以做，但**去重简直是地狱**！因为数组没排序，你很难判断新找到的三元组是不是之前已经找过。如果强行把三元组排序后放进 Set 里去重，不仅代码奇丑无比，甚至会超时。

  2. **破局思路（排序 + 定一动二）**：

     面对“去重”和“组合”问题，**第一步永远是：把数组排个序！**

     排序后，相同的数字全挨在一起，去重变得轻而易举。同时，有序数组天然适合**双指针**。

     **核心策略**：先固定一个数（设为 `nums[i]`），那么问题就瞬间降维打击，变成了：**在 `i` 后面的有序数组里，用双指针寻找“两数之和等于 `-nums[i]`”的组合。**

  3. **逻辑推演（以 `[-1, 0, 1, 2, -1, -4]` 为例）**：

     - **第一步排序**：变成 `[-4, -1, -1, 0, 1, 2]`。
     - **遍历固定 `i`**：
       - 当 `i` 指向 `-4` 时，我们需要在后面找两数之和为 `4`。左指针 `L` 指向 `-1`，右指针 `R` 指向 `2`。加起来才 `1`，太小了，`L` 右移...
       - 当 `i` 指向第一个 `-1` 时，需要找两数之和为 `1`。找到 `[-1, 0, 1]`。
       - **去重高光时刻**：当 `i` 指向第二个 `-1` 时，如果不跳过它，又会找出一遍 `[-1, 0, 1]`。所以遇到和前一个数相同的 `i`，直接 `continue` 跳过！双指针 `L` 和 `R` 遇到重复数字也是同理跳过。

- **🛠️ Java 规范代码**：

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

class Solution {
    public List<List<Integer>> threeSum(int[] nums) {
        List<List<Integer>> result = new ArrayList<>();
        
        // 1. 灵魂步骤：对数组进行全面排序
        Arrays.sort(nums);
        
        // 2. 遍历数组，固定第一个数 nums[i]
        for (int i = 0; i < nums.length - 2; i++) {
            // 极致剪枝：如果当前排好序的最小数已经大于 0，那后面再怎么加也不可能等于 0 了，直接结束
            if (nums[i] > 0) {
                break;
            }
            
            // i 的去重逻辑：如果现在的 i 和上一个 i 的值一样，说明这个数字作为“基准”已经搜过了，跳过
            if (i > 0 && nums[i] == nums[i - 1]) {
                continue;
            }
            
            // 3. 降维打击：在 i 之后的区间内，用双指针寻找两数之和等于 -nums[i]
            int left = i + 1;
            int right = nums.length - 1;
            
            while (left < right) {
                int sum = nums[i] + nums[left] + nums[right];
                
                if (sum == 0) {
                    // 找到了一组，加入结果集
                    result.add(Arrays.asList(nums[i], nums[left], nums[right]));
                    
                    // L 和 R 的去重逻辑：跨过所有相同的数字，避免产生重复的三元组
                    while (left < right && nums[left] == nums[left + 1]) {
                        left++;
                    }
                    while (left < right && nums[right] == nums[right - 1]) {
                        right--;
                    }
                    
                    // 去重完毕后，双指针双双向内收缩，继续寻找下一组
                    left++;
                    right--;
                } else if (sum < 0) {
                    // 和太小，说明左边的数小了，左指针右移
                    left++;
                } else {
                    // 和太大，说明右边的数大了，右指针左移
                    right--;
                }
            }
        }
        
        return result;
    }
}
```

- **⏱️ 复杂度分析**：
  - **时间复杂度**：$O(N^2)$。数组排序的时间复杂度是 $O(N \log N)$。外层遍历 `i` 需要 $O(N)$，内部双指针相向而行遍历剩余数组也需要 $O(N)$。嵌套起来是 $O(N^2)$。综合来看取最高阶 $O(N^2)$。
  - **空间复杂度**：$O(\log N)$ 或 $O(N)$。这取决于 Java `Arrays.sort()` 底层使用的排序算法（快排或 TimSort）所带来的递归栈空间开销。（注意：不计算用来存放结果的 `result` 列表的空间）。

------

#### 💡 面试避坑与考点拓展

1. **致命陷阱：`i` 的去重为什么是 `nums[i] == nums[i - 1]` 而不是 `nums[i] == nums[i + 1]`？**
   - 这是无数人栽跟头的地方！假设数组是 `[-1, -1, 2]`。
   - 如果是看后面：`nums[i] == nums[i + 1]`。当 `i=0` 时，你发现 `-1 == -1`，你**跳过了第一个 `-1`**。结果导致你错失了合法的 `[-1, -1, 2]` 组合！
   - 如果是看前面：`nums[i] == nums[i - 1]`。当 `i=1` 时，你发现它和前面的 `i=0` 长得一样，说明以 `-1` 打头阵的所有组合都在上一步找过了，此时跳过。这才是真正的去重！
2. **双指针去重时机的考究**
   - 在代码中，`L` 和 `R` 的去重操作是在 `sum == 0` 的大括号内部执行的。为什么不在 `sum < 0` 或 `sum > 0` 的时候也用 `while` 去重？
   - 回答：因为没必要。如果 `sum < 0`，你写 `left++` 即使遇到了相同的数字，下一步计算 `sum` 依然 `< 0`，循环会自然而然地让它继续 `left++`，所以不需要单独写一层 `while` 去跳过，让外层的大 `while` 自己转就行，代码更简洁。

### 📝 算法笔记：42. 接雨水 (Trapping Rain Water)

------

- **📌 核心题意**：

  给定 `n` 个非负整数表示每个宽度为 `1` 的柱子的高度图，计算按此排列的柱子，下雨之后能接多少雨水。

  **示例 1：**

  ![](https://__LC_IMG_ROOT__/lc-0fc9878b0edfad.png)

  **输入：**height = [0,1,0,2,1,0,1,3,2,1,2,1]<br>**输出：**6<br>**解释：**上面是由数组 [0,1,0,2,1,0,1,3,2,1,2,1] 表示的高度图，在这种情况下，可以接 6 个单位的雨水（蓝色部分表示雨水）。

  **示例 2：**

  **输入：**height = [4,2,0,3,2,5]<br>**输出：**9

  **提示：**

  - `n == height.length`
  - `1 <= n <= 2 * 104`
  - `0 <= height[i] <= 105`

- **🧠 思考过程**：

  1. **直觉与痛点（竖向切片法）**：

     不要横向看，我们要**一列一列地看**。对于任意一个位置 `i`，它能装多少水，完全取决于**它左边最高的柱子（`leftMax`）\**和\**它右边最高的柱子（`rightMax`）**。

     *原理（木桶效应）*：位置 `i` 的水面高度 = `min(leftMax, rightMax)`。

     *位置 `i` 的水量* = `水面高度 - 柱子本身的高度`（如果算出来是负数，就是 0）。

     **痛点**：如果对每个柱子都向左、向右扫描一遍找最高点，时间复杂度是 $O(N^2)$，太慢了！如果用两个数组把每个位置的 `leftMax` 和 `rightMax` 提前存起来（动态规划法），时间是 $O(N)$，但空间复杂度也是 $O(N)$。能不能把空间也压榨到 $O(1)$？

  2. **破局思路（双指针 + 动态极值）**：

     我们用两个指针 `left` 和 `right` 分别站在数组的两端，相向而行。

     同时，我们维护两个变量：`leftMax`（记录左指针走过的最大高度）和 `rightMax`（记录右指针走过的最大高度）。

  3. **逻辑推演（核心灵魂：谁小结算谁）**：

     当你站在两端时，比较 `leftMax` 和 `rightMax`：

     - **如果 `leftMax < rightMax`**：

       对于左指针 `left` 当前所在的柱子来说，它的右边**一定**存在一个高度至少为 `rightMax` 的“高墙”。既然右边有靠山，那 `left` 这个位置能装多少水，就**唯一取决于较矮的 `leftMax`**！我们就可以放心地结算 `left` 位置的水量，然后 `left++`。

     - **如果 `leftMax >= rightMax`**：

       同理，对于右指针 `right` 来说，它的左边有靠山（`leftMax`），所以它能装多少水，**唯一取决于 `rightMax`**！我们结算 `right` 位置的水量，然后 `right--`。

- **🛠️ Java 规范代码**：

```java
class Solution {
    public int trap(int[] height) {
        // 应对极端情况：数组为空或长度不足以形成凹槽
        if (height == null || height.length < 3) {
            return 0;
        }
        
        // 1. 初始化双指针
        int left = 0;
        int right = height.length - 1;
        
        // 2. 初始化左右两端走过的历史最高柱子
        int leftMax = 0;
        int rightMax = 0;
        
        int totalWater = 0; // 记录总装水量
        
        // 3. 左右指针相向而行，直到相遇
        while (left < right) {
            // 先更新当前的左右两端最大值
            leftMax = Math.max(leftMax, height[left]);
            rightMax = Math.max(rightMax, height[right]);
            
            // 4. 核心逻辑：谁的瓶颈低，就结算谁，并向前移动
            if (leftMax < rightMax) {
                // 左边的历史最高比右边的历史最高矮
                // 说明 left 位置的短板一定是 leftMax，右边再怎么起伏也漏不出去
                totalWater += leftMax - height[left];
                left++;
            } else {
                // 右边的历史最高较矮（或相等）
                // 说明 right 位置的短板一定是 rightMax
                totalWater += rightMax - height[right];
                right--;
            }
        }
        
        return totalWater;
    }
}
```

- **⏱️ 复杂度分析**：
  - **时间复杂度**：$O(N)$。左右指针只把整个数组遍历了一遍，每次比较和计算都是常数时间操作。
  - **空间复杂度**：$O(1)$。只使用了几个变量，没有任何额外的数组开销。这是面试官最想看到的终极形态。

#### 💡 面试避坑与考点拓展（灵魂拷问）

- **面试官追问：“在 `leftMax < rightMax` 时，你凭什么断定 `left` 右边没有更矮的板子导致漏水？”**

  - **满分回答**：因为 `rightMax` 是从最右侧扫描过来的历史最高点。即使 `left` 和 `right` 中间存在非常深的坑洞或者极其高耸的山峰，都不会影响 `left` 位置的储水能力。

    - 如果中间有山峰，那未来的 `rightMax` 会更大，`left` 的水面依旧由 `leftMax` 决定。

    - 如果中间是深坑，深坑不会拉低右侧已知的 `rightMax` 这个物理屏障。

      因此，只要我们手握左右两端的历史最高记录，我们就可以断言：**水是从短板溢出的，只要确认了哪边是绝对的短板，就可以直接结算那一列的水量。
