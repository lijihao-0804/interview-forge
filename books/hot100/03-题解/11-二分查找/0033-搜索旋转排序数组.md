# 33. 搜索旋转排序数组

[← 二分查找专题](../../02-专题/11-二分查找.md) · [总目录](../../../../README.md) · [复习清单](../../00-总览/03-复习清单.md)

| 题目信息 | 内容 |
|---|---|
| 难度 | 中等 |
| 核心模式 | 识别有序半边 |
| 时间复杂度 | O(log n) |
| 空间复杂度 | O(1) |


## 题目与约束

整数数组 `nums` 按升序排列，数组中的值 **互不相同** 。

  在传递给函数之前，`nums` 在预先未知的某个下标 `k`（`0 <= k < nums.length`）上进行了 **向左旋转**，使数组变为 `[nums[k], nums[k+1], ..., nums[n-1], nums[0], nums[1], ..., nums[k-1]]`（下标 **从 0 开始** 计数）。例如， `[0,1,2,4,5,6,7]` 下标 `3` 上向左旋转后可能变为 `[4,5,6,7,0,1,2]` 。

  给你 **旋转后** 的数组 `nums` 和一个整数 `target` ，如果 `nums` 中存在这个目标值 `target` ，则返回它的下标，否则返回 `-1` 。

  你必须设计一个时间复杂度为 `O(log n)` 的算法解决此问题。

  **示例 1：**

  **输入：**nums = [4,5,6,7,0,1,2], target = 0<br>**输出：**4

  **示例 2：**

  **输入：**nums = [4,5,6,7,0,1,2], target = 3<br>**输出：**-1

  **示例 3：**

  **输入：**nums = [1], target = 0<br>**输出：**-1

  **提示：**

  - `1 <= nums.length <= 5000`
  - `-104 <= nums[i] <= 104`
  - `nums` 中的每个值都 **独一无二**
  - 题目数据保证 `nums` 在预先未知的某个下标上进行了旋转
  - `-104 <= target <= 104`

## 核心不变量

> 每轮至少有一半有序，再判断 target 是否落在其中。

## 完整推导

### 思路推导
  1. **直觉与痛点（被扭断的数组）**：

     $O(\log n)$ 的要求直接封死了 `for` 循环线性查找的退路，逼着我们必须用二分。

     **痛点**：二分查找的精髓是“拿中间的值和目标比，决定去左边还是右边”。但现在数组被扭断了，`[4,5,6,7,0,1,2]` 的中间是 7，目标如果是 0，它既比 7 小，又在 7 的右边！传统的比大小逻辑彻底失效。

  2. **破局思路（局部有序定理）**：

     仔细观察这个被扭断的数组，无论你从哪个位置把它一分为二（切一刀），**它的左半边和右半边，必定有一半是完全单调递增的！**

     - 比如 `[4,5,6,7, 0,1,2]`，切在 7：左半边 `[4,5,6,7]` 是完全有序的！右半边包含断点。
     - 比如 `[6,7,0,1, 2,4,5]`，切在 1：右半边 `[1,2,4,5]` 是完全有序的！左半边包含断点。

  3. **核心微操（指哪打哪）**：

     既然总有一半是有序的，那事情就好办了。

     每次算出 `mid` 后，我们先**判断哪一半是有序的**：

     - **如果左半边有序**：我们利用有序的特性，看看 `target` 是不是落在 `[left, mid)` 的闭区间内。如果在，那必定在左边（`right = mid - 1`）；如果不在，那必定在右边那个乱序的半区里（`left = mid + 1`）。
     - **如果右半边有序**：同理，看看 `target` 是不是落在 `(mid, right]` 内。如果在，去右边找（`left = mid + 1`）；不在，去左边找（`right = mid - 1`）。
### Java 实现（局部有序判断满分版）
```Java
class Solution {
    public int search(int[] nums, int target) {
        int left = 0;
        int right = nums.length - 1;

        while (left <= right) {
            int mid = left + (right - left) / 2;

            if (nums[mid] == target) {
                return mid; // 运气好，直接命中
            }

            // 🌟 核心判断：左半边是否完全有序？
            // 致命细节：这里必须是 <=，不能是 <。因为当 left == mid 时（数组只剩一两个元素），它也是一个合法的“有序区间”！
            if (nums[left] <= nums[mid]) {
                // 进入了“左半边完全单调递增”的分支
                // 既然它单调递增，那我们就看看 target 是否老老实实呆在这个区间里
                if (nums[left] <= target && target < nums[mid]) {
                    // target 在这个有序区间内，向左压缩
                    right = mid - 1;
                } else {
                    // target 不在这个有序区间内，肯定在右边那个带有断点的半区，向右压缩
                    left = mid + 1;
                }
            }
            // 否则，右半边必定完全有序
            else {
                // 进入了“右半边完全单调递增”的分支
                // 看看 target 是否老老实实呆在右半边有序区间里
                if (nums[mid] < target && target <= nums[right]) {
                    // target 在右边，向右压缩
                    left = mid + 1;
                } else {
                    // target 不在右边，肯定在左边那个带有断点的半区，向左压缩
                    right = mid - 1;
                }
            }
        }

        return -1; // 搜遍了全图也没找到
    }
}
```
### 复杂度
  - **时间复杂度**：$O(\log N)$。虽然里面多了一层判断，但我们每次依然是无情地**砍掉一半**的数据，完美的二分效率。
  - **空间复杂度**：$O(1)$。只动用了常数级别的指针变量。

### 易错点与扩展（面试细节生死线）

1. **踩坑警告（致命错误）：为什么是 `nums[left] <= nums[mid]`，漏掉等于号会怎样？**
   - 假设数组是 `[3, 1]`，我们要找 `1`。
   - 第一轮：`left = 0`, `right = 1`, `mid = 0`。此时 `nums[left] == 3`, `nums[mid] == 3`。
   - 如果你写的是 `nums[left] < nums[mid]`，它会认为左半边无序，从而跳进 `else`（右半边有序）分支。
   - 然后它判断 `target (1)` 是否在右半边 `(nums[mid], nums[right]]` 即 `(3, 1]` 内。这显然是个假命题，于是错误地执行 `right = mid - 1`，导致错过了正确答案！
   - **结论**：在计算机里，**只包含一个元素的区间 `[3]` 是天然有序的**，所以必须要有 `=` 号，承认 `left == mid` 时的有序合法性。
2. **面试追问：“如果数组里允许有【重复的数字】，比如 `[1, 0, 1, 1, 1]` 找 `0`，这个算法还能用吗？”（对应力扣 81 题：搜索旋转排序数组 II）**
   - **满分抢答（直击退化痛点）**：不能直接用！
   - 如果有重复数字，可能会遇到 `nums[left] == nums[mid] == nums[right]` 的情况（比如 `left` 测出是 1，`mid` 是 1，`right` 也是 1）。此时你根本不知道断点在左边还是右边，局部有序定理在这里失效了！
   - **破局办法**：遇到这种情况，只能暴力把 `left` 往前挪一步（`left++`），或者 `right` 往后挪一步（`right--`），跳过重复干扰项，直到这三个数不全相等，再重新启动二分。这也是为什么如果有重复数字，算法最坏会退化成 $O(N)$ 的原因。
