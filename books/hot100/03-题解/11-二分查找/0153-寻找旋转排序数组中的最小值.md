# 153. 寻找旋转排序数组中的最小值

| 题目信息 | 内容 |
|---|---|
| 难度 | 中等 |
| 核心模式 | mid 与 right 比较 |
| 时间复杂度 | O(log n) |

## 题目与约束

已知一个长度为 `n` 的数组，预先按照升序排列，经由 `1` 到 `n` 次 **旋转** 后，得到输入数组。

  请找出并返回数组中的 **最小元素** 。数组中的所有整数都是 **唯一** 的。

  **硬性要求**：你必须设计一个时间复杂度为 $O(\log n)$ 的算法解决此问题。

[🔗 前往力扣原题验证 →](https://leetcode.cn/problems/find-minimum-in-rotated-sorted-array/?envType=study-plan-v2&envId=top-100-liked)

## 核心不变量

> nums[mid] > nums[right] 时最小值一定在右侧。

## 完整推导

### 思路推导
  1. **直觉与痛点（找断点）**：

     最小值其实就是这个旋转数组的“断崖点”。我们怎么用二分法判断这个断崖点在左边还是右边呢？

  2. **破局思路（寻找绝对的参照物）**：

     在 33 题中，我们通过比较 `nums[left]` 和 `nums[mid]` 来判断左半边是否有序。但这道题，**最佳的参照物是 `nums[right]`**！

     我们将 `nums[mid]` 和最右边的数字 `nums[right]` 进行火星撞地球般的对比：

     - **场景 A (`nums[mid] > nums[right]`)**：比如 `[4, 5, 6, 7, 0, 1, 2]`，`mid` 是 `7`，`right` 是 `2`。中间的值居然比最右边的值还大！这违背了升序规律，说明**断崖（最小值）必定在右半边！** 于是，我们大手一挥：`left = mid + 1`。
     - **场景 B (`nums[mid] < nums[right]`)**：比如 `[6, 7, 0, 1, 2, 4, 5]`，`mid` 是 `1`，`right` 是 `5`。中间值比右边小，说明**从 `mid` 到 `right` 这一段是完美升序的，没有任何断崖！** 既然这一段是升序的，那么最小值绝对不可能在 `mid` 的右边。它要么是 `mid` 本身，要么在 `mid` 的左边。于是，我们谨慎收缩：**`right = mid`**。

  3. **核心微操（循环终止的奥秘）**：

     既然每次都在逼近，那什么时候停下？

     当 `left == right` 时，搜索区间只剩下一个元素了，这个元素就是我们要找的最小值！所以循环条件是 **`while (left < right)`**。
### Java 实现（绝美逼近版）
```Java
class Solution {
    public int findMin(int[] nums) {
        int left = 0;
        int right = nums.length - 1;

        // 🌟 致命细节 1：这里是 left < right，不是 <=
        // 因为我们不需要像找 target 那样去检查最后一个元素是否匹配
        // 当 left == right 时，它们共同指向的就是那个被逼入死角的最小值！
        while (left < right) {
            int mid = left + (right - left) / 2;

            // 拿中间值和【右边界】做比较
            if (nums[mid] > nums[right]) {
                // 中间比右边大，说明断崖在右半边，最小值必定在 mid 之后
                left = mid + 1;
            } else {
                // 🌟 致命细节 2：这里是 right = mid，绝对不能是 mid - 1！
                // 因为 nums[mid] 可能是真正的最小值（比如 [7, 0, 1, 2] 中的 0）
                // 如果写成 mid - 1，就会把真正的最小值给扔掉！
                right = mid;
            }
        }

        // 循环结束时，left 和 right 重合，这就是最小值的位置
        return nums[left];
    }
}
```
### 复杂度
  - **时间复杂度**：$O(\log N)$。经典的二分查找，每次无情排除一半的空间。
  - **空间复杂度**：$O(1)$。只使用了常数级别的游标变量。

### 易错点与扩展（面试的关键追问）

1. **关键追问 1：“为什么比较的参照物是 `nums[right]`，能不能用 `nums[left]`？”**
   - **满分避坑指南**：**强烈不建议用 `left`！** * 假设给你一个完全没有旋转（或者旋转了 $N$ 次）的原始升序数组，比如 `[1, 2, 3, 4, 5]`。
   - 如果你用 `nums[mid] > nums[left]` (`3 > 1`) 来判断，你会误以为断崖在右边，从而让 `left = mid + 1`，直接把真正的最小值 `1` 给丢掉了！
   - 而如果你用 `nums[right]`，`3 < 5`，程序会执行 `right = mid`，慢慢向左收缩，最终完美定格在 `1` 上。**用 `right` 作为参照物，可以完美兼容“数组未发生旋转”的边界情况！**
2. **面试追问 2：“如果数组里有重复元素呢？比如 `[2, 2, 2, 0, 1, 2]`，这个算法还能跑吗？”（对应力扣 154 题：寻找旋转排序数组中的最小值 II - Hard 难度）**
   - **满分优化思路**：如果有重复元素，就会出现 `nums[mid] == nums[right]` 的情况（比如上面例子中 `mid` 指向 `2`，`right` 也指向 `2`）。
   - 此时你根本不知道断崖在左边还是右边。怎么办？
   - **绝境求生法**：既然 `nums[mid]` 和 `nums[right]` 一样大，那我们保留 `mid` 就够了，直接把 `right` 砍掉一格（**`right--`**），缩小范围继续试！这就是那道 Hard 题的全部核心代码，仅仅多了一行 `else if (nums[mid] == nums[right]) right--;`，极其优美！
