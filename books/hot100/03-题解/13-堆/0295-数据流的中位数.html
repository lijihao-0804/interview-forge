题目信息 内容
难度 困难
核心模式 大顶堆 + 小顶堆
时间复杂度 插入 O(log n)，查询 O(1)
空间复杂度 O(n)

题目与约束

设计一个数据结构，支持两个操作：addNum(int num) 向数据流中添加一个整数；findMedian() 返回当前所有元素的中位数。中位数定义为：元素个数为奇数时取排序后中间的那个数，为偶数时取中间两个数的平均值。

🔗 前往力扣原题验证 →

核心不变量

两堆元素数之差不超过一，且左堆所有值不大于右堆。

完整推导

思路推导

  1. 直觉与痛点（动态排序的绝望）：

中位数把所有数字分成了“左边较小的一半”和“右边较大的一半”。

如果用动态数组 ArrayList 维护，新来一个数，为了保持有序，我们需要用二分查找找到位置并插入，移动元素需要 O(N) 的时间。数据量一旦大起来，动态插入会彻底卡死。

  1. 降维破局（双堆对顶，各据一方）：

我们其实根本不需要让所有数字都严格有序！我们只需要牢牢把控住“左半区的最大值”和“右半区的最小值”。

由此，我们创造出两个大本营：

  • 大顶堆（maxHeap）：占领左半区，装较小的一半数字。因为是大顶堆，所以它的堆顶是左半区的最大值（最接近中位数）。
  • 小顶堆（minHeap）：占领右半区，装较大的一半数字。因为是小顶堆，所以它的堆顶是右半区的最小值（同样最接近中位数）。
  1. 核心黄金天规（双堆平衡法则）：

为了让两个堆的堆顶能完美拼凑出中位数，我们必须死守两条红线：

  • 天规一（大小王交叉）：大顶堆的所有数字必须 ≤ 小顶堆的所有数字（即 maxHeap.peek() <= minHeap.peek()）。
  • 天规二（数量均衡）：两个堆的人数差不能超过 1。我们约定：奇数时让大顶堆多装一个。也就是说，大顶堆的大小永远等于小顶堆的大小，或者比小顶堆多 1。
  1. 高能微操：新数字来踢馆，如何以 O(logN) 优雅倒腾？

很多同学在写 addNum 时，用大量的 if-else 判断新数字该进哪个堆，结果把边界条件写得一团糟。这里有一个永远不会出错的“脑筋急转弯”标配打法：

  • 不管新数字是谁，先让它进大顶堆洗礼一下。

  • 然后把大顶堆的堆顶（也就是左半区最大的大哥）弹出来，踢进小顶堆。这样小顶堆就成功吸收了新鲜血液，且绝不违反天规一。

  • 这时候检查一下：如果小顶堆的人数居然比大顶堆多了，那就不满足天规二（大顶堆要撑起半边天）。于是再从小顶堆弹出一个堆顶，扔回大顶堆。

    这一番极其丝滑的“连环倒腾”，一行多余的判断都不用写，两个堆自动维持完美平衡！

    Java 实现规范代码（极简双堆对顶版）

import java.util.Collections;
import java.util.PriorityQueue;

class MedianFinder {
    // 大顶堆：存储较小的一半数字，堆顶是左半区的最大值
    private PriorityQueue<Integer> maxHeap;
    // 小顶堆：存储较大的一半数字，堆顶是右半区的最小值
    private PriorityQueue<Integer> minHeap;

    public MedianFinder() {
        // Java 默认是小顶堆，传入 Collections.reverseOrder() 即可变成大顶堆
        maxHeap = new PriorityQueue<>(Collections.reverseOrder());
        minHeap = new PriorityQueue<>();
    }

    public void addNum(int num) {
        // 🌟 核心优雅连招，无需任何条件判断：
        // 1. 先进大顶堆过水
        maxHeap.offer(num);
        // 2. 剥削大顶堆的头子，送进小顶堆
        minHeap.offer(maxHeap.poll());

        // 3. 维护数量平衡：大顶堆的人数要 >= 小顶堆的人数，且差值不能超过 1
        if (minHeap.size() > maxHeap.size()) {
            maxHeap.offer(minHeap.poll());
        }
    }

    public double findMedian() {
        // 如果两个堆人数相等（偶数个数字），中位数就是两个堆顶的平均值
        if (maxHeap.size() == minHeap.size()) {
            return (maxHeap.peek() + minHeap.peek()) / 2.0;
        }
        // 如果人数不相等（奇数个数字），中位数必然是大顶堆的堆顶
        else {
            return maxHeap.peek();
        }
    }
}

复杂度

  • 时间复杂度：
  • addNum：O(logN)。每次插入和弹出操作都是对二叉堆的调整，代价是对数级别的。
  • findMedian：O(1)。中位数永远就在两个堆的嘴尖上（堆顶），看一眼直接返回，极速响应。
  • 空间复杂度：O(N)。需要两个堆合力装下数据流里的所有数字。

易错点与扩展（面试高频连环追问）

  • 面试进阶追问 1：“如果数据流中 99% 的数字都在 0 到 100 之间，你还用双堆吗？”
  • 满分抢答（计数排序大显神威）：这时候用堆就亏大了！既然数字范围极度紧凑（[0, 100]），我们应该直接开辟一个长度为 101 的计数数组（Bucket）！
  • 每次来一个数，对应的频次加 1（count[num]++），耗时 O(1)。
  • 寻找中位数时，我们维护一个全局总数 N，直接从 0 到 100 累加频次，找到第 N/2 个数字对应的位置。因为桶的长度只有 101，这个遍历也是 O(1) 的常数级！空间更是压缩到了极点。
  • 面试进阶追问 2：“如果 99% 的数字在 0 到 100 之间，但有 1% 的数字是不可预测的巨大超级大离群点（Outliers）呢？”
  • 高级风控架构方案：我们可以把两个方案缝合起来！
  • 用一个长度为 101 的数组记录 [0, 100] 内的正常数字，并记录低于 0 的个数和高于 100 的个数。
  • 对于那些极少数越界的超级大离群点，我们单独用两个小规模的双堆去挂载在两头。在寻找中位数时，先排除两边的离群点数量，再定位到中央的计数数组中。这种“主仓+边缘流控”的设计思想，直接对齐现代分布式大数据的风控模型。
